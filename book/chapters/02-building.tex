\chapter{Compiling and Running Mathilda}
\label{ch:building}

Before you can compute anything, you have to get Mathilda onto your machine and
build it. For most newcomers this is the single largest hurdle---not the
mathematics, but the toolchain\index{building!prerequisites}---so this chapter treats it carefully and
completely. By the end you will have obtained the source, installed the handful of
libraries it needs, compiled the program, started an interactive session, and
learned your way around the read--eval--print loop. If you have built open-source C
programs before, much of this will be familiar and you can skim; if you have not,
follow it line by line and you will be fine.

Mathilda is distributed as \emph{source code}, not as a pre-built binary. That is a
deliberate consequence of the mission of Chapter~\ref{ch:about}: a system meant to
be read, checked, and carried forward is one you compile yourself, on your own
hardware, from source you can inspect. The good news is that the build is ordinary
and undramatic---a C project with a plain \texttt{makefile}, a few well-known
libraries, and no exotic build system to learn.

\section{Obtaining the source}
\label{sec:obtaining}
\index{building!obtaining the source}

Mathilda lives in a public Git repository. To get a copy, clone it and step
inside:

\begin{shell}
$ git clone https://github.com/stblake/Mathilda.git
$ cd Mathilda
\end{shell}

\noindent
Everything the rest of this chapter does happens from inside that top-level
\texttt{Mathilda/} directory. Two files there are worth knowing about from the
start: \texttt{README.md} is the quick-start and the authoritative list of
dependencies, and \texttt{SPEC.md} describes the system's architecture. You do not
need to read either to build the program, but they are where to turn when something
is unusual about your platform.

\section{The toolchain and its dependencies}
\label{sec:prerequisites}

Mathilda is written in C99 and leans on a small set of best-in-class numerical
libraries (introduced in \S\ref{sec:libraries}). Building it therefore needs a C
compiler and those libraries' development headers. Only three of the libraries are
required; the rest are optional and the build \emph{degrades gracefully}\index{graceful degradation} without
them---it detects what is present, switches on the corresponding features, and
switches off the ones whose libraries are missing, always producing a working
binary.

\subsection{A real GCC, not clang}
\label{sec:gcc-not-clang}
\index{GCC!required, not clang}

The one platform rule that trips people up: Mathilda must be built with a genuine
\textbf{GCC}, never Apple's or LLVM's \texttt{clang}. The build enforces this for
you. Its makefile auto-detects a real GCC---trying \texttt{gcc-16}, \texttt{gcc-15},
\ldots\ down to a plain \texttt{gcc}---and if the compiler it is about to use reports
itself as clang, it stops immediately with a message telling you how to fix it,
rather than silently producing an unsupported binary.%
\calloutnote{Under the hood}{The rule is not arbitrary. On macOS the plain
\texttt{gcc} command is a symlink to Apple's clang, which both miscompiles a few of
Mathilda's constructs and---more importantly---hides the strict-C99 portability
warnings that the project's Linux continuous-integration build treats as errors.
Building with real GCC on every platform keeps one standard of correctness. The fix
is always the same: install GCC from Homebrew.}
On Linux the plain \texttt{gcc} is already real GCC, so there is nothing to do. On
macOS, install one from Homebrew (see below); the makefile will then find and prefer
it automatically. If you ever need to point it at a specific compiler, pass it
explicitly, for example \texttt{make CC=gcc-16}.

\subsection{The libraries}
\label{sec:libraries-list}

\paragraph{Required.} These three must be present or the build cannot proceed:
\begin{itemize}
  \item \textbf{GMP}\index{GMP}, the GNU Multiple Precision Arithmetic Library---arbitrary-precision
        integers, the foundation of all of Mathilda's exact arithmetic.
  \item \textbf{MPFR}\index{MPFR}---correctly rounded arbitrary-precision reals, so that \B{N}
        can give you a hundred trustworthy digits. It is on by default; you can build
        without it, but almost no one should.
  \item \textbf{GNU~Readline}\index{GNU Readline}---the interactive session's fallback line
        reader. On an ordinary terminal Mathilda uses its own line editor
        (\S\ref{sec:editing}), but a build with Readline is what turns the
        terminal features on at all; without it (\texttt{USE\_READLINE=0}, as on
        native Windows) the session reads plain lines.
\end{itemize}

\paragraph{Optional.} Each of these unlocks a family of features when present and is
simply omitted when absent:
\begin{itemize}
  \item \textbf{FLINT}\index{FLINT} (version~3.0 or newer)---fast, rigorous polynomial arithmetic
        over algebraic number fields and rigorous numerics for many special
        functions. Every FLINT~3 release builds, from the 3.0.1 that Ubuntu~24.04
        ships to the current one: the two interfaces that changed in FLINT~3.3 are
        selected at compile time by the library's own version
        macro.\index{FLINT!supported versions} Distributions that ship only
        FLINT~2.x are detected as too old and the accelerated paths are switched off
        automatically.
  \item \textbf{GMP-ECM}\index{GMP-ECM}---the Elliptic Curve Method for the harder cases of integer
        factorization.
  \item \textbf{LAPACK}\index{LAPACK} and \textbf{BLAS}---fast machine-precision linear algebra. On
        macOS the build finds Apple's \textbf{Accelerate} framework and you need
        install nothing.
  \item \textbf{FFTW}---fast Fourier transforms; without it \B{Fourier} falls back to
        a slower $O(n^2)$ transform.
  \item \textbf{Raylib}\index{Raylib}---the interactive window that \B{Plot}, \B{Plot3D}, and \B{Show}
        draw into. Without it those functions print a text placeholder and return
        normally (see Chapter~\ref{ch:graphics}).
\end{itemize}

\noindent
POSIX threads, used to spread the packed-array kernels across your cores, are on by
default on macOS and Linux and need no extra package. \textbf{CMake} is needed only
to build the test suite (\S\ref{sec:tests}).

Every optional backend is governed by a build-time flag you can force on or off. The
defaults auto-detect, so you rarely need to touch them, but they are worth knowing:

\begin{table}[htbp]
  \centering
  \small
  \begin{tabular}{@{}llp{0.52\linewidth}@{}}
    \toprule
    \textbf{Flag} & \textbf{Default} & \textbf{What it enables} \\
    \midrule
    \mcode{USE\_MPFR}     & \mcode{1} & Arbitrary-precision reals: \mcode{N[expr, prec]}, precision tracking. \\
    \mcode{USE\_FLINT}    & \mcode{1} & Fast FLINT ($\geq 3.0$) kernels for number fields and rigorous numerics. \\
    \mcode{USE\_LAPACK}   & \mcode{1} & Fast machine-precision linear algebra (Accelerate on macOS). \\
    \mcode{USE\_ECM}      & \mcode{1} & Elliptic Curve Method factorization via GMP-ECM. \\
    \mcode{USE\_FFTW}     & \mcode{1} & FFTW-backed \mcode{Fourier}; naive $O(n^2)$ transform when off. \\
    \mcode{USE\_THREADS}  & \mcode{1} & POSIX-thread parallelism for the packed-array kernels. \\
    \mcode{USE\_GRAPHICS} & \mcode{1} & Interactive 2D/3D plot windows via Raylib. \\
    \bottomrule
  \end{tabular}
  \caption{Optional-backend flags. Each auto-detects; append e.g.\ \mcode{USE\_LAPACK=0}
  to a \mcode{make} command to force one off.}
  \label{tab:use-flags}
\end{table}

\subsection{Installing the dependencies}
\label{sec:installing-deps}
\index{building!installing dependencies}

On \textbf{Debian or Ubuntu}, install the three required libraries and as many of the
optional ones as you want:

\begin{shell}
# Required
$ sudo apt install libgmp-dev libmpfr-dev libreadline-dev

# Optional, each auto-detected by the build
$ sudo apt install libflint-dev          # FLINT >= 3.0 (Ubuntu 24.04+/Debian 12+)
$ sudo apt install libecm-dev            # GMP-ECM factorization
$ sudo apt install liblapacke-dev libopenblas-dev   # LAPACK/BLAS
$ sudo apt install libfftw3-dev          # FFTW
$ sudo apt install libraylib-dev         # interactive graphics
$ sudo apt install cmake                 # only for the test suite
\end{shell}

\noindent
On \textbf{Fedora or RHEL} the package names are \texttt{gmp-devel},
\texttt{mpfr-devel}, \texttt{readline-devel}, and then \texttt{flint-devel},
\texttt{gmp-ecm-devel}, \texttt{lapack-devel}/\texttt{openblas-devel},
\texttt{fftw-devel}, and \texttt{cmake}.

On \textbf{macOS} with Homebrew, install a real GCC (\S\ref{sec:gcc-not-clang}) and
the libraries; Accelerate is already part of the system, so you do not install
LAPACK:

\begin{shell}
$ brew install gcc gmp mpfr readline cmake
# Optional
$ brew install flint fftw raylib gmp-ecm
\end{shell}

\section{Building}
\label{sec:building}
\index{building!compiling}

With the dependencies in place, build the program with a single command. The
makefile auto-discovers every source file, configures the internal dependencies, and
links the executable with \texttt{-std=c99 -O3}:

\begin{shell}
$ make -j
\end{shell}

\noindent
The \texttt{-j} flag builds in parallel across your cores; on Linux you can be
explicit with \texttt{make -j\$(nproc)}. The first build compiles several hundred
source files and takes a little while; afterwards, \texttt{make} rebuilds only what
changed. When it finishes you will have an executable called \texttt{Mathilda} in the
current directory.

Want a leaner binary, or missing a library you do not care about? Turn any optional
backend off explicitly (Table~\ref{tab:use-flags}). For instance, to build without
MPFR and without the LAPACK acceleration:

\begin{shell}
$ make -j USE_MPFR=0 USE_LAPACK=0
\end{shell}

\paragraph{If the build stops.} The three failures new users hit, and their fixes:
\begin{itemize}
  \item \emph{``\,'gcc' is clang, not GCC\,''}---you are on macOS with only Apple's
        compiler. Run \texttt{brew install gcc} and build again; the makefile will
        find the real GCC on its own (\S\ref{sec:gcc-not-clang}).
  \item \emph{A missing header such as \texttt{gmp.h} or \texttt{readline/readline.h}}---%
        a required library's development package is not installed. Install it from
        \S\ref{sec:installing-deps} and rebuild.
  \item \emph{FLINT features quietly absent}---your distribution ships FLINT~2.x.
        The build detects this, falls back to \texttt{USE\_FLINT=0}, and still
        succeeds; install FLINT~$\geq 3.0$ from source or a backport if you want the
        accelerated paths.
\end{itemize}

\subsection{Native Windows}
\label{sec:building-windows}
\index{building!on Windows}

Mathilda also builds as a \emph{native} Windows program---not under a POSIX emulation
layer such as Cygwin---using GCC from the \textbf{MSYS2} distribution. The supported
environments are UCRT64 (which the continuous-integration job uses) and MINGW64; the
Clang-based MSYS2 environments are refused for the same reason as Apple's compiler
(\S\ref{sec:gcc-not-clang}). From a UCRT64 shell:

\begin{shell}
$ pacman -S mingw-w64-ucrt-x86_64-gcc mingw-w64-ucrt-x86_64-gmp \
            mingw-w64-ucrt-x86_64-mpfr mingw-w64-ucrt-x86_64-make \
            mingw-w64-ucrt-x86_64-pkg-config
$ make USE_ECM=0 USE_READLINE=0 USE_GRAPHICS=0 USE_LAPACK=0 -j4
\end{shell}

\noindent
The result is \texttt{Mathilda.exe}. Two capabilities are reduced, both because native
Windows lacks the POSIX facility behind them. \B{TimeConstrained} is
\emph{cooperative only}: the evaluator loop and the heavy kernels poll the deadline, so
a runaway computation is stopped at its next check, but there are no asynchronous
signals to interrupt a single long-running C routine that never returns to the loop.
And POSIX threads are off, so the packed-array kernels run on one core. There is no
GNU Readline either, so the REPL reads plain lines, without the editor, history,
completion, colour, and status line of \S\ref{sec:repl}; the script and pipe modes of
\S\ref{sec:scripts} are unaffected. Everything else---timing, memory reporting,
\mcode{Pause}---goes through a small portability layer and behaves as on the other
platforms.

\section{Your first session}
\label{sec:first-session}
\index{REPL!starting}

Start the interactive session by running the binary with no arguments:

\begin{shell}
$ ./Mathilda

Mathilda <version> - A small, open source computer algebra system.

Free, open source software with ABSOLUTELY NO WARRANTY.

Return evaluates (Esc Return forces an incomplete input); Tab completes,
Ctrl-R searches the history, Ctrl-C interrupts (twice quits).
Type / for commands and /help for keys; Ctrl-D or Quit[] exits.

In[1]:=
\end{shell}

\noindent
The banner is a summary of the keys this chapter goes on to explain
(\S\ref{sec:repl}), and its first line names the version you just built. (If the
session is using the Readline fallback rather than Mathilda's own editor,
\S\ref{sec:editing}, the banner is a longer paragraph saying the same things.) The
libraries the binary was compiled against are available at any time from
\B{\$Version}\index{version!\$Version}, and the version number alone from \B{\$VersionNumber}:

\begin{codepairs}
\pair{02-building/version/1}{The full version string: Mathilda's version and every library
it was built against---exactly the build you are running.}
\pair{02-building/version/2}{Just the number, as a machine-readable value you can
compare against in a script.}
\end{codepairs}

The \texttt{In[1]:=} is the \emph{prompt}\index{REPL!In[] and Out[]}: Mathilda is waiting for you to type an
expression. Type one, press Return, and it prints the result on an
\texttt{Out[1]=} line and prompts again. Here is the whole of a first session---exact
arithmetic, an exact symbolic value, and a machine-precision number on demand:

\begin{codepairs}
\pair{02-building/first-session/1}{Ordinary arithmetic. The answer is the exact
integer~$4$.}
\pair{02-building/first-session/2}{\B{Sin} of $\pi/6$ is returned \emph{exactly}, as
the rational $1/2$---not a decimal.}
\pair{02-building/first-session/3}{Ask for a number with \B{N} and you get one: here
a quick machine-precision value of $\pi$.}
\end{codepairs}

\noindent
That is the entire rhythm of the system: you type an expression, Mathilda evaluates
it to a fixed point, and it shows you the result. Everything else in this book is
variations on that loop.

\section{How the REPL works}
\label{sec:repl}
\index{REPL}

The interactive loop---read an expression, evaluate it, print it, repeat---is where
you will spend most of your time, so it is worth knowing its conveniences.

\subsection{Results persist, and you can name them}
\label{sec:session-state}

A session has \emph{memory}. Everything you define stays in force until you leave, so
you can name a result on one line and use it on the next:

\begin{codepairs}
\pair{02-building/session-state/1}{Assign with \mcode{=}. The assignment returns the
value, so you see it echoed.}
\pair{02-building/session-state/2}{\mcode{x} now stands for $1024$ everywhere.}
\pair{02-building/session-state/3}{And keeps standing for it until you reassign or
clear it.}
\end{codepairs}

Beyond your own names, the session numbers everything for you.
Each result is stored as \mcode{Out[n]}, matching the \texttt{Out[n]=} label beside
it, and each input as \mcode{In[n]}. The special symbol \mcode{\%} is shorthand for
the most recent result and \mcode{\%\%} for the one before it, so in an interactive
session \mcode{\% + 1} adds one to whatever was just printed, and \mcode{Out[3]}
recalls the third result exactly.%
\calloutnote{Under the hood}{\mcode{In[n]}, \mcode{Out[n]}, and \mcode{\%} are a
feature of the \emph{interactive} loop---the REPL records each result as it prints
it. A script run with \mcode{-file} (\S\ref{sec:scripts}) and the machine pipe used
by front-ends do not keep this history, so reach for a named variable, as above, for
anything you want to reuse in a script.}

A trailing semicolon suppresses the printed output. The expression is still
evaluated and its value still stored---you just do not see it, which is exactly what
you want for setup lines and large intermediate results:

\begin{codepairs}
\pair{02-building/suppression/1}{The semicolon suppresses the \texttt{Out[]} line;
the assignment still happens.}
\pair{02-building/suppression/2}{Proof that it did: \mcode{a} is $3$, so \mcode{a\^{}2}
is $9$.}
\end{codepairs}

\subsection{The line editor}
\label{sec:editing}
\index{REPL!line editor}

When both ends of the session are a terminal, Mathilda reads your input with its
own line editor, which lives in the source tree under \texttt{src/term/}. It behaves
like a modern shell prompt, with three things a shell prompt does not do. The input
is coloured as you type it: builtins, your own defined symbols, numbers, strings,
comments, and patterns such as \mcode{x\_} each get their own colour, and the
bracket at the cursor is underlined together with its partner, while a closing
bracket that matches nothing turns red. An input may run over several lines, and
the up and down arrows move between those lines before they reach the history.
And \texttt{Tab} and \texttt{Ctrl-R} open lists in place under the cursor, described
below.

The keys are the familiar Emacs-style ones. \texttt{Ctrl-A} and \texttt{Ctrl-E} go to
the start and the end of the line, \texttt{Alt-B} and \texttt{Alt-F} move a word
at a time, \texttt{Ctrl-K} and \texttt{Ctrl-U} kill to the end and to the start of
the line, \texttt{Ctrl-Y} yanks the last kill back, and \texttt{Ctrl-\_} undoes.
\texttt{Ctrl-L} clears the screen. \texttt{/help} (\S\ref{sec:customising}) prints
the full table.

For an expression too long or too structured to sit comfortably on one line, you need
do nothing special: just keep typing.\index{REPL!multiline input} Pressing Return
evaluates the buffer \emph{only} once it forms a complete
expression---every \mcode{(}, \mcode{[} and \mcode{\{} closed, and every string and
comment finished. Until then, Return simply opens a fresh line and waits, so a
bracket you have opened but not yet closed carries you onto the next line
automatically:

\begin{shell}
In[1]:= Table[i^2,
{i, 1, 4}]
Out[1]= {1, 4, 9, 16}
\end{shell}

\noindent
You close the final brace, press Return, and the whole thing runs as one
expression---the line breaks inside it are just whitespace, exactly as they are in a
script. (On screen the editor indents the continuation lines under the prompt;
what is evaluated, and what goes into the history, is exactly what you typed.)
Should you ever want to submit an \emph{incomplete} line as it stands---to
see the parser's error, say, rather than being carried onto a new line
forever---press \texttt{Esc} then \texttt{Return} (or \texttt{Alt-Return}), which
forces evaluation regardless. A block you paste is inserted as typed text, so its
line breaks never submit it half-way.

\paragraph{Completion.}\index{REPL!completion} \texttt{Tab} completes the word at the
cursor. With one candidate it is inserted; with several, the common prefix is
inserted and a list opens under the word, and the row beneath the list shows the
first line of the selected name's documentation---the same text \mcode{?Name}
prints (\S\ref{sec:help}). Typing narrows the list, \texttt{Tab} and the arrows move
through it, and \texttt{Return} inserts the choice without evaluating. Completion
reads the symbol table; it never evaluates anything, and it never creates a symbol.
It also knows where it is: directly after the \mcode{[} of a call, or after a comma
at that depth, the head's \emph{options} come first, so typing \texttt{Tab} after
\texttt{NIntegrate[f, \{x, 0, 1\}, } offers \texttt{AccuracyGoal -> } and its
siblings.

\paragraph{History.}\index{REPL!history} The up arrow recalls earlier inputs, a
multi-line one whole. \texttt{Ctrl-R} opens the history as a list, newest first and
each distinct input once, under a \texttt{search:} prompt; whatever you type filters
it by substring, \texttt{Return} puts the selected input back in the editor (a
second \texttt{Return} evaluates it), and \texttt{Esc} restores what you had.
\index{REPL!history file}The history outlives the session. Every accepted input is
appended, the moment you press Return, to the file \texttt{\textasciitilde/.mathilda\_history}, so a
crash or a forced quit loses nothing, and the next session's up arrow reaches it.
Two environment variables control it:

\begin{shell}
$ MATHILDA_HISTFILE=~/work/proj.history ./Mathilda   # a history per project
$ MATHILDA_HISTSIZE=5000 ./Mathilda                  # keep 5000 entries (default 1000)
$ MATHILDA_HISTSIZE=0 ./Mathilda                     # no history at all
\end{shell}

\noindent
Setting \texttt{MATHILDA\_HISTFILE} to the empty string keeps the up arrow for the
current session but writes no file. Blank lines, comment-only lines, and an input
identical to the one before it are not recorded.

\paragraph{Colour.}\index{REPL!colour} Prompts, results, message heads, and the
syntax colouring all come from a colour \emph{theme} (\S\ref{sec:customising}).
Colour follows the usual conventions: setting \texttt{NO\_COLOR} turns it off,
setting \texttt{CLICOLOR\_FORCE} turns it on even when the output is not a terminal,
and otherwise each of standard output and standard error is coloured only when it
is a terminal---so \texttt{./Mathilda 2>err.txt} leaves \texttt{err.txt} plain.
Without colour, the session writes no escape sequence at all.

\paragraph{The Readline fallback.}\index{GNU Readline!fallback} Setting
\texttt{MATHILDA\_EDITOR=readline}, or running on a terminal that declares
itself \texttt{TERM=dumb}, makes the session read with GNU~Readline instead. History,
the history file, completion, \texttt{Ctrl-C}, colour, the slash commands, and the
status line all still work; what is lost is the editor's colouring as you type and
its popup lists. (Readline completes an ambiguous prefix to its common part and lists
the candidates on a second \texttt{Tab}.)%
\calloutnote{Pitfall}{Multi-line input under the fallback needs a genuine GNU~Readline.
macOS ships a \texttt{libedit} stand-in under the same header name that cannot do it,
so the build prefers a Homebrew \texttt{readline} when one is present. Linked against
\texttt{libedit}, the fallback reads one line at a time, its prompts are uncoloured,
and \texttt{Ctrl-C} at the prompt is ignored rather than clearing the line. None of
this affects the default editor, which needs no Readline features at all.}

\subsection{Getting help}
\label{sec:help}
\index{REPL!getting help}

To see what a function does, type a question mark before its name---\mcode{?Sin},
say---and Mathilda prints its usage message: a one-line signature and a short
description, drawn from the function's own built-in documentation. Every builtin
carries one. This is the same text that titles the function's reference card; for
\B{Sin} it reads:

\usagebox{Sin}

To \emph{discover} functions rather than look one up, \B{Names} lists every symbol
matching a string pattern---a quick way to see what a fresh session already knows:

\begin{codepairs}
\pair{02-building/help/1}{Every built-in name beginning with \mcode{Bessel}. The
\mcode{*} is a wildcard.}
\end{codepairs}

\noindent
For the fuller machine-readable story about a symbol---its attributes and
definitions as well as its usage---there is also \B{Information}, of which
\mcode{?name} is the everyday shorthand. At the prompt, \texttt{Tab} is often
quicker still: the completion list (\S\ref{sec:editing}) shows each candidate's
first line of documentation as you move through it.

\subsection{While it runs: the status line and \texttt{Monitor}}
\label{sec:statusline}
\index{REPL!status line}

Most inputs return before you notice. One that takes longer than 200~milliseconds
gets a live line at the bottom of the terminal, redrawn about ten times a second
and erased just before the result is printed. Two examples from the REPL's own
documentation (\texttt{docs/spec/repl.md}), in the plain-ASCII form the line takes
when the terminal has no UTF-8 locale:

\begin{shell}
| Integrate | Together | 3.2s | cpu 3.1s | mem 412 MB (2.5%) | peak 1.17 GB
/ Table 3400/10000 [###.......] 34% | eta 6.4s | 2.1s | cpu 2.1s | mem 96 MB (0.6%)
\end{shell}

\noindent
Reading left to right: a spinner, the head of what you asked for, the builtin
running at this moment (the first line is an \B{Integrate} that has handed work to
\B{Together}), the elapsed and CPU time, the resident memory as a share of the
machine's RAM, and the peak. The memory figure turns yellow at 60\% and red at 85\%,
which is usually your cue to press \texttt{Ctrl-C} before the machine starts to
swap. The second line shows \emph{loop progress}\index{REPL!loop progress}:
\B{Do}, \B{Table}, \B{Sum}, \B{Product}, \B{Nest}, \B{NestList}, \B{Fold},
\B{FoldList}, \B{NestWhile}, and \B{FixedPoint} report their step and their total,
so the line can draw a bar and, after a second of progress, an estimate of the time
remaining. For nested loops the outer loop and the one directly inside it are both
shown. (With a UTF-8 locale the spinner is an animated Braille glyph, the separators
are middle dots, and the bar is drawn with block characters.)

The line is careful not to get in the way. Anything printed while it is showing---a
\B{Print}, a message, the output of a C library---goes through the thread that
draws it, which erases the line, writes the output, and redraws, so the two never
overwrite each other. A quick evaluation draws nothing, so its output is byte for
byte what it would be without the feature. \texttt{MATHILDA\_SPINNER=0} turns the
line off, as do a dumb terminal, a redirected standard stream, a script, and the
pipe protocol.

\index{Monitor@\mcode{Monitor}}%
\mcode{Monitor[expr, mon]} puts a value of your own into the line: it evaluates
\mcode{expr} and, while that runs, shows the current value of \mcode{mon}. A
typical use is to watch a loop variable, or a running quantity, in a long
computation:

\begin{shell}
In[1]:= x = 0.5; Monitor[Do[x = Sin[x] + 0.01; Pause[0.02], {i, 100}], {i, x}]
\end{shell}

\noindent
Here the line shows \texttt{Do 41/100}, the bar, and the current
\mcode{\{i, x\}} pair, refreshed as it changes. The monitor expression is
evaluated only when the line wants a fresh value, about ten times a second, and its
messages are suppressed, so watching costs almost nothing. Outside the interactive
session there is no line to draw, and \mcode{Monitor} simply evaluates
\mcode{expr} and returns its value---so it is safe to leave in a script:

\begin{codepairs}
\pair{02-building/monitor/1}{In the pipe that builds this book there is no status
line, so \mcode{Monitor} just returns the value of the sum.}
\end{codepairs}

\paragraph{After the result.}\index{REPL!took note} When a result took a second or
more, a dim line beneath it records what it cost: the wall time, the CPU time, and
the peak resident memory during the evaluation, in the form
\texttt{took 3.21 s \(\cdot\) cpu 3.18 s \(\cdot\) peak 412 MB}. A CPU time much larger
than the wall time means the work ran on several cores; much smaller means it was
waiting. \texttt{/timing off} drops the note and \texttt{/timing always} shows it
after every result. Separately, \texttt{/statusline} (or \texttt{MATHILDA\_STATUSLINE=1}
at start-up) prints a one-line summary after every result---the last time, the
memory in use, and the current context---which is off by default.

\subsection{Interrupting and leaving}
\label{sec:leaving}
\index{REPL!interrupting}

\texttt{Ctrl-C} during an evaluation stops it. The result is
\texttt{Out[n]= \$Aborted} and the session carries on, with everything you defined
before the interrupted input still in place. The interrupt is the same abort that
evaluating \mcode{Abort[]} raises, so every frame on the way out cleans up after
itself---a \B{Block} or \B{Module} restores its variables, \mcode{CheckAbort} can
catch it, and \mcode{AbortProtect} defers it to the end of its body. The heavy C
kernels that poll for a deadline (Gr\"obner bases, cylindrical decomposition,
\B{FactorInteger}, compiled numeric loops, and others) stop within their polling
period.%
\calloutnote{Pitfall}{A few computations never come back to the evaluator and never
poll: the compiled virtual machine's innermost loop, a LAPACK call, stage two of
GMP-ECM. A single \texttt{Ctrl-C} cannot reach them. For those, a \emph{second}
\texttt{Ctrl-C} within one second ends the whole process, with the terminal
restored and the exit status 130, the shell's convention for ``killed by
\texttt{Ctrl-C}''. Your inputs survive in the history file; your session's
definitions do not.}

\texttt{Ctrl-C} at the prompt, with nothing running, discards what you have typed
(a multi-line input included) and shows the same \texttt{In[n]:=} again; it does
not end the session. To leave, evaluate \mcode{Quit[]}\index{Quit@\mcode{Quit}} (or type
\texttt{/quit}), or press \texttt{Ctrl-D} on an empty line. Either way
\B{\$Epilog} runs first, if you have set it. \texttt{Ctrl-Z} suspends the session
to the shell in the usual way, and \texttt{fg} brings it back with your input
redrawn.

\subsection{Customising the session}
\label{sec:customising}
\index{REPL!customising}

\paragraph{Slash commands.}\index{REPL!slash commands} A line that begins with
\texttt{/} is a command to the session, not an expression. It is never evaluated,
gets no \texttt{In[n]} or \texttt{Out[n]}, and leaves the line counter alone.
(No Mathilda input can begin with \texttt{/}: \mcode{/.}, \mcode{//}, \mcode{/@}, and
\mcode{/;} all need something on their left, so nothing is lost.) Typing \texttt{/}
into an empty input opens a menu of the commands with a summary of each, filtered as
you type. The built-in ones are:

\begin{table}[htbp]
  \centering
  \small
  \begin{tabular}{@{}lp{0.62\linewidth}@{}}
    \toprule
    \textbf{Command} & \textbf{Effect} \\
    \midrule
    \texttt{/help}                       & the commands, the keys, and the per-user files \\
    \texttt{/theme [name]}               & the theme picker, or choose a theme by name \\
    \texttt{/history [n]}                & the last \texttt{n} inputs (default 20), numbered \\
    \texttt{/timing [on|off|always]}     & the \texttt{took} note: after results of 1\,s or more (the default), never, or always \\
    \texttt{/statusline [on|off]}        & the summary line after each result \\
    \texttt{/clear}                      & clear the screen and the scrollback \\
    \texttt{/mods}                       & the mods loaded, their status, commands, and hooks \\
    \texttt{/quit}                       & end the session, as \mcode{Quit[]} \\
    \bottomrule
  \end{tabular}
  \caption{The REPL's built-in slash commands.}
  \label{tab:slash-commands}
\end{table}

\paragraph{Themes.}\index{REPL!colour themes} Every colour the session draws comes
from one of five themes: \texttt{dark} (the default), \texttt{light} (chosen
automatically when the terminal reports a light background), \texttt{high-contrast},
\texttt{mono} (no colour, only bold, dim, underline, and reverse), and
\texttt{ansi} (the terminal's own sixteen-colour palette). \texttt{/theme} opens a
picker whose preview---a prompt, a result, a message, the status line, a took
note---switches as you move through the list; \texttt{Return} applies and saves the
choice and \texttt{Esc} puts back the theme you had. \texttt{/theme light} sets one
directly. The choice is saved as a line \texttt{theme = light} in
\texttt{\textasciitilde/.mathilda/config}, and \texttt{MATHILDA\_THEME=}\emph{name} overrides
the file for one session.

\paragraph{Mods.}\index{REPL!mods} After the banner, the interactive session
evaluates the file \texttt{\textasciitilde/.mathilda/init.m}, if there is one, and then every
\texttt{\textasciitilde/.mathilda/mods/}\emph{name}\texttt{.m}, in name order. A mod is ordinary
Mathilda code, so it can define functions you always want to hand. It can also set
the session hooks \B{\$PreRead} (applied to the input text), \B{\$Pre} (to each
input before evaluation), \B{\$Post} (to each result), and \B{\$PrePrint} (to each
result before printing). And it can add slash commands of its own with
\mcode{SlashCommand}\index{SlashCommand@\mcode{SlashCommand}}:
\mcode{SlashCommand["name", f, "summary"]} makes \texttt{/name rest} evaluate
\mcode{f["rest"]}, with the rest of the line as a trimmed string, and print the result
unless it is \mcode{Null}. Two such commands, from the REPL's documentation:

\begin{shell}
(* ~/.mathilda/init.m *)
SlashCommand["vars", Function[s, Names["Global`*"]], "list my symbols"];
SlashCommand["n", Function[s, N[ToExpression[s], 30]], "30 digits: /n Pi"];
\end{shell}

\noindent
After that, \texttt{/n Pi} prints thirty digits of \(\pi\), and both commands appear
in the \texttt{/} menu and in \texttt{/help} under the name of the file that added
them. \mcode{SlashCommand["name", None]} removes a command and
\mcode{SlashCommand[]} lists them all; the built-in commands cannot be redefined. A
mod that emits messages, is interrupted, or calls \mcode{Quit[]} is reported in one
dim line and the session goes on without it, so a broken mod cannot lock you out.
\texttt{MATHILDA\_MODS=0} skips \texttt{init.m} and the mods for one session, and
\texttt{MATHILDA\_CONFIG\_DIR} moves the whole \texttt{\textasciitilde/.mathilda} directory
elsewhere.%
\calloutnote{Under the hood}{None of this machinery is visible outside the
interactive session. A \texttt{-file} script, the pipe protocol, and a build without
Readline install no signal handler, print no colour, complete nothing, read no
configuration file, load no mods, and write no history, so their output is byte
for byte what it was before the editor existed. The terminal is handed back and
forth between two owners: the editor holds it, in raw mode, while you type; for the
evaluation it passes to a status thread that points standard output and standard
error at a pipe it drains, which is how a \mcode{Print} and the status line can
share the screen. The editor itself is terminal-free---bytes in, drawing out through
a callback---so its unit tests drive it with a small terminal emulator, and a
latency gate holds its slowest keystroke on a 200-line input under 2~ms.}

\section{Running scripts and other modes}
\label{sec:scripts}
\index{building!running scripts}

The REPL is one of three ways Mathilda can run. It is chosen automatically: if you
name a file, Mathilda runs it as a script; otherwise, if its input is an interactive
terminal, it starts the REPL you have just met; and if its input is a pipe, it speaks
a machine protocol instead (below).

\paragraph{Scripts.} Point Mathilda at a file of expressions with \texttt{-file} (a
bare filename means the same thing) and it evaluates each one in order and exits.
Crucially, \emph{nothing is echoed}: there are no \texttt{In[]}/\texttt{Out[]} lines,
so the output is exactly and only what the script chooses to \B{Print}. Given a file
\texttt{area.m}:

\begin{shell}
$ cat area.m
(* area.m -- a tiny script. Nothing is echoed; only what we Print appears. *)
r = 3;
Print["Area of a disk of radius ", r, " is ", N[Pi r^2]]

$ ./Mathilda -file area.m
Area of a disk of radius 3 is 28.2743
\end{shell}

\noindent
This is the mode to use for batch work, for reproducible computations kept under
version control, and for anything you want to pipe into another program. (It is also
how this very book is built: every transcript you see was produced by feeding its
inputs to the real binary.)

\paragraph{Exit status.}\index{exit status}\index{scripts!exit status} A script ends
when its last expression has been evaluated, with exit status~0. It can also end
itself: \mcode{Quit[]}\index{Quit@\mcode{Quit}} stops the script at that statement, and
\mcode{Quit[n]}---or its synonym \mcode{Exit[n]}---stops it with exit
status~\(n\), which is what a shell, a \texttt{makefile}, or a continuous-integration
job reads to decide whether a step succeeded. Because \mcode{Quit} is an ordinary
function, it works anywhere evaluation reaches: inside an \B{If}, inside a file read
with \B{Get} (which then ends the outer script too), deep in a function. A script
that checks an identity and reports the verdict to the shell:

\begin{shell}
$ cat check.m
(* check.m -- exit 0 if the identity holds, 1 if it does not. *)
ok = Simplify[Sin[x]^2 + Cos[x]^2] === 1;
Print["identity holds: ", ok]
If[ok, Exit[0], Exit[1]]
Print["never reached"]

$ ./Mathilda -file check.m; echo "status $?"
identity holds: True
status 0
\end{shell}

\noindent
In the interactive session \mcode{Quit[n]} likewise exits with status~\(n\), after
running \B{\$Epilog}; the pipe protocol ignores it, since a front-end, not the
kernel, decides when its kernel goes away.

\paragraph{The command line.} A few options round out the picture; \texttt{--help}
lists them all:

\begin{shell}
$ ./Mathilda --help
Mathilda <version> - a small, open source computer algebra system.

Usage: ./Mathilda [options] [file]

  -file <path>    evaluate every expression in <path>, then exit
  -h, --help      show this message and exit
  -v, --version   print version information and exit

A bare <file> argument is equivalent to -file <file>. With no file,
Mathilda starts the interactive REPL when stdin is a terminal, and
otherwise speaks the NDJSON pipe protocol on stdio.
\end{shell}

\paragraph{The pipe protocol.} That last sentence describes the third mode. When
Mathilda's input is not a terminal and no script was named, it speaks a line-oriented
JSON protocol on its standard input and output, designed for a front-end---a
notebook, an editor plugin, a web interface---to drive it programmatically.%
\calloutnote{Under the hood}{The protocol is \emph{NDJSON}: one JSON request per
line in, one or more JSON responses per line out, each result carrying both a text
form and a \LaTeX{} form so a graphical front-end can render it. You will not use
this mode by hand, but it is what lets Mathilda sit behind a richer interface than a
terminal.}

\subsection{Embedding Mathilda in a C program}
\label{sec:embedding}
\index{embedding!C API}\index{building!installing}

The pipe protocol drives Mathilda as a separate process. Sometimes you want the
kernel \emph{inside} your own program instead: a Python extension module, a Jupyter
kernel, a mobile app (where the operating system forbids spawning child processes),
or simply a C program that needs a symbolic integral. For that the build produces a
library, and \texttt{make install} puts it where a compiler can find it:

\begin{shell}
$ make -j lib                       # libmathilda.a and the shared libmathilda
$ sudo make install                 # default prefix /usr/local
$ make install prefix=$HOME/.local  # or anywhere you like, no sudo
\end{shell}

\noindent
Besides the \texttt{Mathilda} executable and its tree of \texttt{.m} bootstrap files,
the install ships the embedding API: the header \texttt{mathilda\_ffi.h}; a static
library \texttt{libmathilda.a}; a shared library (\texttt{libmathilda.so.0} on Linux,
\texttt{libmathilda.0.dylib} on macOS, \texttt{libmathilda.dll} on Windows); and a
\texttt{pkg-config} file, \texttt{mathilda.pc}. The interface is deliberately tiny.
\texttt{mathilda\_ffi\_init} starts the kernel once. \texttt{mathilda\_ffi\_eval} takes
an input string, evaluates it, and returns the same text the REPL would print after
\texttt{Out[n]=}, in a string that \emph{you} own and release with
\texttt{mathilda\_ffi\_free}. Here is a complete host program:

\begin{ccode}[host.c --- a complete embedding host]
/* host.c -- evaluate a few Mathilda expressions from C. */
#include <stdio.h>
#include <mathilda_ffi.h>

int main(void)
{
    const char* inputs[] = {
        "Integrate[1/(1 + x^3), x]",
        "Factor[x^6 - 1]",
        "N[Pi, 40]",
    };
    int i;

    mathilda_ffi_init();                 /* once, before any evaluation */

    for (i = 0; i < 3; i++) {
        char* out = mathilda_ffi_eval(inputs[i]);   /* caller owns it */
        printf("%s\n  = %s\n", inputs[i], out);
        mathilda_ffi_free(out);
    }
    return 0;
}
\end{ccode}

\noindent
Compile it with the flags \texttt{pkg-config} reports, and run it:

\begin{shell}
$ gcc host.c $(pkg-config --cflags --libs mathilda) -o host
$ ./host
Integrate[1/(1 + x^3), x]
  = 1/3 Log[1 + x] + ArcTan[(-1 + 2 x)/Sqrt[3]]/Sqrt[3] - 1/6 Log[1 - x + x^2]
Factor[x^6 - 1]
  = (-1 + x) (1 + x) (1 + x + x^2) (1 - x + x^2)
N[Pi, 40]
  = 3.1415926535897932384626433832795028841971
\end{shell}

\noindent
(On Linux, if you installed under a prefix the dynamic loader does not search, set
\texttt{LD\_LIBRARY\_PATH} to its \texttt{lib} directory, or run \texttt{ldconfig}
after a system-wide install.) A few rules of the road. The kernel keeps global state
(the symbol table), so the calls are \emph{not} reentrant: initialise once, and
serialise every call from a multi-threaded host behind a lock. State persists between
calls exactly as in a REPL session, so a definition made in one
\texttt{mathilda\_ffi\_eval} is visible to the next. A parse error never yields
\texttt{NULL}; it returns the string \texttt{\$Failed (parse error)}. And for a
richer front end there are siblings: \texttt{mathilda\_ffi\_eval\_latex} returns
\LaTeX, \texttt{mathilda\_ffi\_eval\_json} a JSON object that can carry plot data,
and \texttt{mathilda\_ffi\_eval\_cell} evaluates a whole notebook cell and streams
the same events as the pipe protocol to a callback you supply.

\calloutnote{Under the hood}{Mathilda is part C and part its own language: at start-up
the kernel loads \texttt{init.m} and the other bootstrap files from its
\texttt{internal/} tree, and without them many functions are incomplete. An installed
\emph{shared} library finds that tree relative to its own location on disk
(\texttt{<libdir>/../share/mathilda/internal}), so a host needs no configuration. A
program linked \emph{statically} has no such anchor, and must say where the tree is,
by setting the \texttt{MATHILDA\_HOME} environment variable or by calling
\texttt{mathilda\_ffi\_set\_home(dir)} before \texttt{mathilda\_ffi\_init}; the path
is recorded in the installed \texttt{mathilda.pc}, as
\texttt{pkg-config --variable=internaldir mathilda}, and
\texttt{pkg-config --static --libs mathilda} lists the libraries a static link needs.
Both libraries are compiled with \texttt{-fvisibility=hidden}: the shared library
exports only the \texttt{mathilda\_ffi\_*} entry points, so none of the kernel's
thousands of internal names can collide with your program's. They are also compiled
as position-independent code, so the static archive can itself be linked into a
shared object, which is how a Python extension module embeds it.
\texttt{make check-install} stages an install in a scratch directory and proves all
of this from the installed files alone.}

\section{Building and running the tests}
\label{sec:tests}
\index{building!test suite}

Mathilda ships a large suite of C-based unit tests. You do not need them to use the
system, but running them is the surest way to confirm your build is sound---and if
you go on to modify Mathilda (Chapter~\ref{ch:contributing}), they are how you check
you have not broken anything. The suite is built with CMake, which auto-detects the
same optional backends as the main build:

\begin{shell}
$ cd tests
$ mkdir -p build && cd build
$ cmake ..
$ make -j

# Run every test binary
$ for t in *_tests; do ./$t; done
\end{shell}

\bigskip
\noindent
That is everything you need to obtain, build, and run Mathilda, and to find your way
around a session. With a working binary in front of you and the prompt waiting, we
can turn to the mathematics. The next chapter is a whirlwind tour of what the system
can do---arithmetic, number theory, algebra, calculus, and more---so that the
detailed chapters afterwards feel like a return to places you have already seen.
