Feature additions and fixes recorded during this week.

## Solve[…, Integers]: four unbounded Diophantine families vs sympy (2026-08-22)

Closed the four unbounded conic/quadric families that `Solve[…, Integers]`
declined but sympy's `diophantine` returns parametrically. Each declined only
when unbounded (the bounded forms already solved); these add the missing
parametric-family emitters. All are symbolic `Solve` paths — no packed/NDArray/
`Compile[]` surface, no new builtin symbol.

- **General homogeneous ternary quadratic** (`si_solve_ternary_general`,
  `src/solve/solveint_ternary_general.c`): `a x^2 + b y^2 + c z^2 + d xy + e yz +
  f zx == 0` with cross terms / non-symmetric coefficients — everything the
  symmetric `x^2+y^2==k z^2` solver declines, including multi-representation `k`
  (`65 = 5·13`). Congruent `mpq` diagonalisation decides Legendre solvability and
  finds a Holzer-bounded witness; the complete **projective** chord family is
  built directly in the original coordinates (only the witness is mapped back).
  Anisotropic forms return the trivial-only `{{0,0,0}}` (a proof). Matches
  sympy / Mathematica's up-to-scaling representation.
- **Extended ("general") Pythagorean** (`si_solve_general_pythagorean`,
  `src/solve/solveint_pythag.c`): `x_1^2 + … + x_k^2 == y^2` for `k >= 3`
  (`x^2+y^2+z^2==w^2`, …) via the stereographic parametric family.
- **General binary quadratic** (`si_solve_bqf_parametric`,
  `src/solve/solveint_bqf_parametric.c`): the **parabolic** case (`delta = B^2 -
  4AC == 0`, e.g. `x^2-4xy+4y^2-3x==0`, and the degenerate `y==x^2`) via the
  classical congruence method — a finite union of one-parameter families; and the
  **hyperbolic** case (`delta > 0` non-square, cross term, `x>0 && y>0`, e.g.
  `x^2-3xy+y^2==1`) via the fundamental-unit automorphism
  `M = [[t-Bu,-2Cu],[2Au,t+Bu]]` — one closed-form `ConditionalExpression` family
  per orbit-base solution.
- **Fix**: the general ternary witness search used the wrong Holzer-bound pair,
  spuriously declining solvable forms whose witness sat outside the (too small)
  box — `x^2+y^2==65 z^2` among them.
- **Fix**: added a small-box witness pre-scan to the general ternary solver so a
  large-coefficient form with a tiny witness (e.g. `99991 x^2 - 99989 y^2 - 2 z^2
  == 0`, solution `(1,1,1)`) solves instantly instead of declining when the full
  Holzer box exceeds the node cap.
- **Large-discriminant hyperbolic BQF now solved**: the hyperbolic path found its
  orbit-base solutions by a direct `(x,y)` search bounded by `s_min · unit`, so a
  large discriminant (huge fundamental unit) made it decline — `x^2 - 9 x y +
  5 y^2 == 1` (`delta = 61`, unit ≈ 3.5×10⁹) and `x^2 - 1001 x y + 500 y^2 == 1`
  (`delta = 10⁶`). Rewrote it to reduce to `X^2 - delta Y^2 == N` and scan `Y`
  over the **Nagell bound** (independent of the unit size), mapping each `(X,Y)`
  representative back and advancing into the positive quadrant. Both now solve in
  sub-millisecond; small cases (`delta = 5, 32`) verified unchanged and complete
  against brute force. Benchmark: on the four former gaps Mathilda is now
  sub-millisecond across the board and no longer declines any of the hyperbolic
  suite (vs sympy's 8–50 ms; PARI has no one-shot binary-quadratic solver).

All four verified complete against brute force (projective for the ternary /
general-Pythagorean cones, exact for the binary-quadratic families); unit tests
in `tests/test_solve_integers.c` (`test_ternary_general`,
`test_general_pythagorean`, `test_bqf_parabolic`, `test_bqf_hyperbolic`).

## Export: graphics to PDF, PNG, and JPEG (2026-08-22)

`Export["file", plot]` now writes a `Graphics` object (the result of `Plot`, `ListPlot`,
`Graphics`, …), not just an `Image`. `Export["ex.pdf", Plot[Sin[x], {x, 0, 10}]]` and the
`.png`/`.jpeg` equivalents all work.

- **PDF** is a resolution-independent **vector** file from a new dependency-free emitter,
  `src/graphics/graphics_export.c` (raylib-free, always compiled, works headless). It
  walks the graphics primitive tree directly — `Line`/`Point`/`Polygon`/`Disk`/`Circle`/
  `Rectangle`/`Arrow`/`Text` with the colour/`Opacity`/`Thickness`/`PointSize` directives —
  applies a world→page transform, and draws a framed axis with "nice" ticks and numeric
  labels. Text uses the PDF base-14 Helvetica, so nothing is embedded.
- **PNG/JPEG** reuse the Raylib renderer offscreen (`graphics_render_rgba` in `render.c`,
  reusing `graphics_render_in_region`), so the raster is pixel-identical to the on-screen
  plot. The pixels are encoded by the vendored `stb_image_write` (so JPEG works regardless
  of the Raylib build's format support). They need `USE_GRAPHICS` and a GUI session; with
  none they return `$Failed` gracefully — the fragile step is guarded by a GUI-session
  check (`CGSessionCopyCurrentDictionary` on macOS, `DISPLAY`/`WAYLAND_DISPLAY` on Linux)
  because Raylib's `InitWindow` aborts inside GLFW rather than failing cleanly when no
  monitor is available.
- Dispatch lives in `builtin_export` (`src/imageio.c`), which branches to the graphics
  path when the object is `Graphics[...]`; the existing `Image` path is unchanged.
  `Graphics3D` export is not yet supported. Docs in `docs/spec/builtins/file-io.md`.

## NMinimize / NMaximize: constrained solutions no longer returned infeasible (2026-08-21)

`NMinimize[{x^2 + y^2, x + y >= 2}, {x, y}]` returned `{1.9998, {x -> 0.999971,
y -> 0.999929}}` — `x + y = 1.99990`, violating its own constraint by ~1e-4 and
reported as the solution with no warning. Affected `Method -> Automatic` (i.e. the
default, which resolves to `DifferentialEvolution`).

**Cause.** One constant was doing two jobs. `NM_FEAS_EPS` steered Deb's feasibility
rule during the search *and* decided what was returned, and it was compared against
`nm_eval_pen`'s **squared** violation total — so `1e-8` meant a `1e-4` tolerance on
the actual violation, not the `1e-8` it read as.

**Fix.** Two thresholds, named for their jobs, each stated as a violation and squared
at the definition site (`findmin_internal.h`):

- `NM_FEAS_RANK` — search-time ranking, loose (violation 1e-4; squares to 1e-8, the
  historical value, so search trajectories are unchanged). Deliberately loose: Deb's
  rule only compares objectives when both points count as feasible, so a threshold
  tighter than the achievable residual degenerates it into pure
  violation-minimisation. Measured — a tight ranking threshold sent the 15-dimensional
  `test_minimax_chebyshev` from 0.125116 to 1.85479.
- `NM_FEAS_RETURN` — the return path, tight (violation 1e-5) and **enforced**. A result
  that cannot meet it is reported `{Infinity, x -> Indeterminate}` rather than returned
  and called feasible.

Also added a last-chance continuous refinement in `nm_local_polish`'s mixed-integer
branch: when the answer would otherwise be rejected and continuous coordinates exist,
pin the integers and refine, adopting only on a Deb improvement.

**Result.** `{2.0, {x -> 1.0, y -> 1.0}}`, residual ~4e-12. All eight methods feasible.
No speed regression (exp-89 C1 0.259 ms vs 0.255 baseline; C2 faster).

**Tests.** The 29 existing tests could not catch this: every feasibility assertion was
a *one-sided* band that a point failing to reach the boundary passes trivially. Added
two-sided assertions that fail against a pre-fix binary, per-method feasibility, and a
threshold-regression guard. 83/83 pass.

**Known limitation, now explicit.** `test_fixed_charge_flow` (50-variable coupled
flow-conservation MINLP) asserts `Infinity`: the solver's best answer there has a flow
residual of 20.0 — the entire demand — and was previously accepted under a 1e-2
tolerance. Mixed-integer feasibility reaches only ~1e-3 per constraint against ~4e-12
for continuous problems, which is why the return bound is 1e-5 rather than tighter.
Recorded with three other follow-ups in `NMINIMIZE_FEASIBILITY_BUG.md`.

## Benchmarks: NMinimize/NMaximize vs SciPy and Mathematica — experiments 89, 90 (2026-08-21)

Two new gap-driven benchmark experiments, picked up by `benchmarks/run_all.py`'s
directory glob with no manifest edit.

- **`benchmarks/89-nminimize-nmaximize/`** — the timed race, fair-comparison envelope
  applied (the convention set by `81-dual-annealing` / `85-basin-hopping`). 18 cases:
  engine-matched DifferentialEvolution, the default `Method -> Automatic` path,
  `NMaximize` (which previously had **one line** of benchmark coverage in the whole
  tree), constrained, and an indexed-vs-explicit variable pair. Result: **18 AHEAD,
  0 SLOWER, 0 CHECK-FAIL** — 7×–350× faster than the best of scipy 1.17.1 and
  Mathematica.
- **`benchmarks/90-nminimize-testbed/`** — the full hard corpus. The `CHECK` carries
  *solution quality* (`Boole[Abs[fbest - fstar] < tol]`) rather than the objective
  value, so a `CHECK-FAIL` reads as "the systems disagree about whether they solved
  it" instead of a discarded row. Mathilda solves 2 of 7 where scipy solves 4 of 7,
  and wins drop-wave, which scipy misses.

Three findings recorded by the run:

- **Naming `Method` cuts the DE generation budget 7.5×.** `nm_de.c:77-86` allocates
  `150n` generations under `Method -> Automatic` with no `MaxIterations`, but only
  `100` when `Method` is named. Under the implicit budget 5 of 6 seeds fail
  Rastrigin 5-D, which the default solves. Benchmarks that pin `Method` for
  "fairness" must also pin `MaxIterations` or they measure a default, not an
  algorithm.
- **Indexed variables cost 41×.** `Table[v[i], {i,1,5}]` vs explicit names on the
  same problem: 119.7 ms vs 2.9 ms, collapsing a 56× lead over scipy to 1.4×.
- **Constrained solutions are returned infeasible by ~1e-4.** Recorded separately in
  `NMINIMIZE_FEASIBILITY_BUG.md`; root-caused to `NM_FEAS_EPS = 1e-8` being tested
  against a *squared* violation in `nm_eval_pen`, giving an effective tolerance of
  `sqrt(1e-8) = 1e-4` on the actual constraint. Affects DifferentialEvolution (and
  therefore `Automatic`) only.

Note: `benchmarks/REPORT.md` and `history.jsonl` remain dated 2026-08-06, which
predates `NMinimize` landing (2026-08-14). No optimization experiment added since —
63, 79–86, and these two — has appeared in the canonical report. A full
`make bench-gap` is required; `--only` runs deliberately leave it untouched.

## Build: Linux LAPACK/BLAS link fix — plain `make` on Ubuntu (2026-08-21)

Fixed undefined-reference link failures to Fortran LAPACK (`dgeev_`, `zgesv_`,
`dgesdd_`, …) and CBLAS (`cblas_dgemm`, `cblas_ddot`) when building on
Ubuntu/Debian with `liblapacke-dev` installed. The makefile's tier-2 LAPACK
autodetection linked only `pkg-config --libs lapacke`, which on Debian/Ubuntu is
just `-llapacke`: the transitive `-llapack -lblas` are hidden behind
`Requires.private` and a non-static `--libs` never expands them. Since Mathilda
calls Fortran LAPACK and `cblas_*` **directly** (no LAPACKE C wrappers), the link
failed even though headers resolved. The tier-2 branch (`makefile`) now appends
`-llapack` and a BLAS provider (`-lblas`/`-lopenblas`/`-lcblas`) after
`-llapacke` when the `.pc` omits them — matching the `/usr/include` tier, the
FLINT-block fixup idiom, and the CI `EXTRA_LIBS="-llapack -lblas"` workaround, so
plain `git clone && make` now links on Ubuntu without the manual escape hatch.
Recommended packages unchanged: `sudo apt install liblapacke-dev libopenblas-dev`.
The CMake test build was already correct (`find_package(LAPACK)` supplies the
full `LAPACK_LIBRARIES`).

## Solve[..., Integers]: sum-of-three-cubes mod-9 impossibility (2026-08-21)

New global obstruction `si_solve_three_cubes_mod9` (`src/solve/solveint_cubes.c`),
dispatched in `solveint_solve_integer` right after the Fermat short-circuit
(before the bounded Booker engine). Every cube is `≡ {−1, 0, 1} (mod 9)`, so
`± x^3 ± y^3 ± z^3` can never be `≡ 4` or `5 (mod 9)`; hence
`x^3 + y^3 + z^3 == k` with `k ≡ ±4 (mod 9)` has **no** integer solution, and
`Solve[x^3 + y^3 + z^3 == 4, {x, y, z}, Integers]` now returns `{}` as a proof
with **no bound required** — the previously-declined unbounded case. Handles
signed variants and negative `k`; gated to unit `±1` cube coefficients so it
never over-fires (squares, non-unit coefficients, and reachable residues fall
through unchanged). Unit tests: `test_three_cubes_mod9`
(`tests/test_solve_integers.c`, 14 cases incl. guards). Held-out gate
(`make check-diophantine-heldout`) green; `check-c99` clean. Docstring and
`docs/spec/builtins/solutions-of-equations.md` updated; the `Solve` reference
page and the Diophantine tutorial (`cubics-and-thue.md`) reflect the new
behaviour.

## Solve[..., Integers]: Wikipedia gap closure — ternary quadratics, Ramanujan–Nagell, symmetric Egyptian, Frye one-sided box (2026-08-20)

Closed the remaining unbounded-nonlinear gaps from the Wikipedia "Diophantine
equation" page, each validated against a brute-force oracle (`make
check-diophantine-heldout`, 0 wrong answers; valgrind delta 0).

- **Homogeneous ternary quadratic / Legendre (Tier 2 E).** New
  `si_solve_ternary_quadratic` (`src/solve/solveint_ternary.c`), hooked in the
  `Expr*`-family block of `solveint_solve_integer` after the generalised-Pell
  block. For a single homogeneous diagonal degree-2 equation in 3 variables over
  an unbounded domain it decides solvability by **Legendre's theorem** (per-prime
  Legendre symbols, `mpz_legendre`): an unsolvable form returns the trivial
  solution `{{x->0,y->0,z->0}}` (a proof — *not* `{}`, matching Mathematica),
  a solvable one the **complete** integer family. `Solve[x^2+y^2==3z^2,…]` →
  `{{0,0,0}}`; `Solve[x^2+y^2==z^2,…]` → the Pythagorean parametrisation;
  `Solve[x^2+y^2==2z^2,…]` → the full family incl. the tangent point `(1,1,1)`.
  The family is the sign/swap orbit of a chord/tangent parametrisation from a
  sum-of-two-squares witness plus the tangent line `C·P0` (whose odd multiples
  the chord map alone misses), verified complete + sound vs brute force for every
  single-representation solvable `k`. `k` with ≥2 primes ≡1 (mod 4) (multiple
  representations, e.g. 65=5·13) declines rather than emit an incomplete family.

- **Unbounded Ramanujan–Nagell `x^2 + D == 2^n` (Tier 3 F, route A).** New
  `si_solve_ramanujan_nagell` (`src/solve/solveint_rn.c`), before the MPoly
  stage (reuses the shared exponential-shape parser `si_exp_collect`). For the
  class-number-1 case (`D` squarefree, `D ≡ 7 (mod 8)`, `h(Q(√−D))==1` — for
  base 2 this is exactly `D=7`) the factorisation forces `U_{n−2}=±1` for the
  Lucas sequence `Q=(1+D)/4`; the Bilu–Hanrot–Voutier primitive-divisor theorem
  bounds `n≤32`, so a finite exact scan returns the complete set.
  `Solve[2^n-7==x^2 && n>0 && x>0,…]` → `{n=3,4,5,7,15}`. A Lucas cross-check
  guards the result; out-of-scope inputs (base≠2, `D≢7 mod 8`) decline.

- **Symmetric Egyptian fractions without an ordering.** `si_solve_reciprocal`
  (`src/solve/solveint_reciprocal.c`) previously required an explicit
  `x<=y<=z` ordering (the total-order builder failed under bare positivity). It
  now recognises the fully-symmetric case and emits every distinct permutation of
  each ascending representative, so `Solve[4/5==1/x+1/y+1/z && x>0&&y>0&&z>0,…]`
  returns all 12 tuples (was unevaluated); each permutation is re-verified.

- **Frye biquadrate one-sided / signed box.** `si_solve_biquadrate_frye`
  (`src/solve/solveint_frye.c`) no longer requires the target `w` to be
  two-sided bounded by the user: `w^4 = x^4+y^4+z^4` gives a sound magnitude
  bound `|w| ≤ (Σ hi^4)^{1/4}` from the summand box, so an upper-only box
  (`w<500000`) or an unconstrained `w` now engage. The search runs on `|w|` and
  emits **both** signs, each filtered by `si_verify` against the user's box —
  keeping the answer complete and honouring the sign (`0<w` keeps only `+w`).
  Engagement is not tractability: a cold scan of a wide window is intrinsically
  the 1988 computation; the fast path remains a witness window near the known `w`.

## Solve[Integers]: famous power-sum searches (Frye, Lander–Parkin) + non-separable box sieve (2026-08-20)

Three additions to the integer solver (`src/solveint.c`), all registered in
`si_try_special_forms` / at the leaf-search decline point, that make
`Solve[…, Integers]` find Diophantine solutions it previously left unevaluated.

**Frye's biquadrate search** (`si_solve_biquadrate_frye`) —
`x^4 + y^4 + z^4 == w^4`, Frye 1988's minimal counterexample to Euler's
conjecture. `Solve[x^4+y^4+z^4==w^4 && 0<x<y<z<w<10^6, {x,y,z,w}, Integers]`
now returns `{x→95800, y→217519, z→414560, w→422481}` in **~11 min on a single
core** — the computation that needed a 16384-processor Connection Machine for
~33 hours in 1988. A **witness search** (find-first, ascending in `w`;
`__int128` throughout): the mod-5 structure forces `625 | (w^4−C^4)` with
`N=(w^4−C^4)/625 = a^4+b^4`; extra moduli coprime to 5 plus Frye's prime-factor
constraint (`P ≠ 1 mod 8 ⇒ exponent ≡ 0 mod 4` in `N`) and a mod-2¹⁶ 4th-power
fast reject cut the work ~10×, from a ~2 h to a ~11 min single-core run. All
sound necessary conditions — no real primitive solution is dropped. Declines
(never a spurious `{}`) if the node budget (`MATHILDA_FRYE_MAXNODES`) is spent
with nothing found.

**Ordering-aware 128-bit MITM** (`si_solve_separable_mitm`) — a separable power
sum `Σ cᵢ vᵢ^k == c₀ y^k` over an ordered box. Splits the variables along their
ordering chain into a contiguous hash prefix / iterate suffix and enumerates
only ordered combinations, with `__int128` partial sums and a modular residue
sieve. This solves the **Lander–Parkin** quintic
`Solve[x^5+y^5+z^5+w^5==r^5 && 0<x<y<z<w<r<1000, {x,y,z,w,r}, Integers]` →
`27^5+84^5+110^5+133^5=144^5` and its 2×–6× multiples, complete, in ~6.5 s
(the plain int64 `mitm_solve` rejects the box on its unordered `~10^9` iterate
product; the ordered `C(1000,3)≈1.6×10^8` fits). Engages only when it adds
capability the plain MITM lacks (int64 overflow, or a chain that makes the
iterate side fit), so small boxes are unchanged.

**Modular-sieved leaf search** (`si_solve_box_modsieve`) — a last resort for a
single polynomial equation whose ordering-pruned box exceeds `SI_MAX_NODES`
(where the ordinary leaf search declines). Prunes the innermost enumerated
variable to residues mod a small `M` for which the leaf equation can vanish
(sound necessary condition), keeping the search **exhaustive**: complete set /
proven `{}` when it finishes in the raised budget, decline otherwise. Closes
big non-separable cross-term boxes, e.g. `x^2+xy+y^2==z^2 && 0<x<y<z<15000`
(16386 solutions, ~6 s), validated identical to the ordinary engine on the
sub-box it can already exhaust.

Voronoi minima walk** for signature-(2,1) quartics `K = Q(θ)` with a real
quadratic subfield `F = Q(θ²)`. In the `(log|σ0|, log|σ1|)` plane the unit

{(±1,0)}` and `==-1 → {}` (both == PARI `thue`).

*proposes*; p-saturation (rank == r, unconditional) is the proof, so a
non-fundamental proposal DECLINEs, never a wrong answer. The fallback fires only
when the box fails (so the box-solved quartics `x^4-{2,3,5,6,7,8,13,15,17}y^4` are

## Thue solver M5: totally complex fields via the imaginary-part bound (2026-08-20)

The Thue engine declined fields with **no real embedding** (`r1 = 0`): the
Tzanakis–de Weger reduction needs a real type-index `i0`. M5 closes this — not by
porting the complex-`i0` Baker bound, but with an **elementary, rigorous** bound
that the totally-complex structure hands you for free. Every root `theta_i` is
non-real, so for real integers `x, y`,

    |x - theta_i y| >= |Im(theta_i)| * |y|

(the imaginary part alone) — there is no real root for `x/y` to approach, so *no*
factor can be small. Hence

    |m| = |a0| * prod_i |x - theta_i y| >= |a0| * |y|^n * prod_i |Im theta_i|,

giving `|y| <= (|m| / (|a0| * prod_i |Im theta_i|))^{1/n}` directly — **no
fundamental units, no torsion enumeration, no Baker/LLL**. Each `y` in that
(small) range is closed by exact univariate root-finding (`thue_form_xpoly` +
`fmpz_poly_int_roots`); `prod|Im theta_i|` is a certified `arb` lower bound
(precision-escalated) so the `|y|` bound is a rigorous over-estimate.
`thue_solve_totally_complex` (`src/solvethue.c`) runs where the engine used to
decline (`nf_r1(K) < 1`).

Solves the whole totally-complex family, **any `m`** (not just `|m|=1`):
the cyclotomic quartic `x^4+x^3y+x^2y^2+xy^3+y^4 == 1` over `Q(zeta_5)` → its 6
points (0.5 ms), `x^4+y^4 == {1,2,17,82}` → `{4,4,8,8}`, `== 3 -> {}` (proven,
not a sum of two 4th powers), and higher cyclotomics `Phi_7`/`Phi_10`. Benchmark

now solves 6/6); the remaining 5 declines are 2 correct reducible-perfect-power

## Solve[…, Integers]: abs-value ordering constraints + Booker at smaller boxes (2026-08-20)

`Solve[x^3 + y^3 + z^3 == 63 && Abs[x] < Abs[y] < Abs[z] < 10000, {x,y,z},
Integers]` was returned **unevaluated** while the box form (`Abs[x] < 10000 &&
Abs[y] < 10000 && Abs[z] < 10000`) solved in ~0.46 s. The chained inequality
was never the problem — the parser folds it to `Inequality[…]` and the solver
already decomposes that pairwise; the gap was that `register_inequality`
(`src/solveint.c`) had no case for `Abs[var] OP Abs[var]`, so `|x|<|y|` and
`|y|<|z|` contributed neither a bound nor an ordering and left `x`, `y`
unbounded (`n_unbounded == 2` → decline). Two changes, both in `src/solveint.c`:

- **Abs-value orderings are a first-class constraint.** `|a| (< / <=) |b|` is
  parsed into a new `abs_ord_*` store, propagated to a box in `derive_bounds`
  (`|a| < |b| ≤ B ⟹ |a| ≤ B-1`, so the whole chain bounds every variable),
  enforced in `si_verify`, counted by `si_longest_chain`, pruned in
  `effective_bounds` (with an abs-aware enumeration order), and used to tighten
  the divisor method's pair windows. So `Abs[x] < Abs[y] < Abs[z] < 10000`
  returns the **6 ordered representatives** (one per permutation orbit) instead
  of the 36 permutations, and a partial chain (`Abs[x] < Abs[y] < 10000 &&
  Abs[z] < 10000`) orders only the named variables. Every use only tightens or
  filters, so it can never invent or drop a solution.

- **Booker engages for any non-trivial box.** The `2·B <= 300000` gate that kept
  the cube-root-mod-`d` engine off small/medium boxes is lowered to `2·B <= 200`.
  Its `O(α·B · roots)` work beats the leaf search's `O(B^2)` (which reached
  ~3.9 s at `|coord| < 5000`) and the divisor path's `O(B · factoring)` across
  the whole range — the `Abs[...] < 10000` cube box drops from ~0.46 s to
  ~0.02 s. Validated to return the **identical solution set** to the pre-Booker
  pipeline over a wide `(k, box)` sweep (perfect-cube `(a,-a,∛k)` families and
  signed `x^3+y^3-z^3` equations included); a truly tiny box stays on the
  leaf/mitm paths.

- **Routing fix.** The ordering `L!` node-estimate division is now gated on the
  *raw* box size, so a large separable box whose pruned estimate dips just under
  the leaf budget is still routed to the divisor/Booker fast path rather than
  the `O(B^2)` leaf search (which is what made the ordered query hang before the
  gate change).

## Fix: NSum on integer-only summands (1/Prime[n], …) (2026-08-20)

`NSum[1/Prime[n], {n, 1, Infinity}]` spewed dozens of `Prime::intpp: Positive
integer argument expected in Prime[16.1579]` and `NSum[1./Prime[n]^2, …]`
returned a poor `0.448548` (true prime-zeta `P(2) = 0.4522474…`). Both came from
one cause: `NSum`'s method selector saw monotone-decreasing terms and picked
**Euler–Maclaurin**, which samples the summand on a *continuous* tail integral
(exp-sinh quadrature) and a *complex* derivative contour — but `Prime[n]` has no
value off the integers, so every such sample emitted a message and failed,
forcing a fallback to a weakly-seeded Wynn. Fixes, all in
`src/numerical_calculus/nsum.c`:

- **Per-sample messages muted.** Every summand sample funnels through
  `ns_eval_expr_at`, now wrapped in `arith_warnings_mute_push/pop`. These are
  internal trial evaluations (head terms, the far-tail ladder, the EM
  quadrature/contour nodes, the new continuity probe); their messages are noise,
  and Wolfram's NSum is likewise silent about them. The mute counter is nestable,
  so a genuinely user-facing message outside NSum is unaffected. Kills the spew
  regardless of method.
- **Euler–Maclaurin gated on a continuity probe.** `ns_build_profile` now
  evaluates the summand (through the interpreter, at its true value) at two
  non-integer index points; if neither is a finite number the summand is
  integer-only and `ns_choose_method` will not return `EulerMaclaurin` for it —
  it routes to partial-sum extrapolation, the only valid route. Two points, not
  one, so a continuous summand with an accidental pole at one probe is not
  misread. The probe runs only on the non-black-box path, so nested/multidim
  sums add no evaluations (respecting the standing NSum leak constraint).
- **Discrete path seeded with more head terms.** For a non-continuous summand the
  whole result rests on extrapolation of an irregular, slowly-converging tail, so
  the head-term count is raised (15 → 100) when the user has not pinned it (and,
  machine-only, the sequence length to ≥ 24 — the MPFR length already scales with
  the bit budget and must not be clamped). `Σ 1/Prime[n]^2` now returns `0.45217`
  (was `0.4485`); `Σ 1/Prime[n]^4 → 0.0769931` (full accuracy, fast).

**Divergence detection was deliberately not added.** At the convergence boundary
(terms → 0, `a_{k+1}/a_k → 1`) convergence is undecidable from finite samples:
the Cauchy-condensation terms of the divergent `Σ 1/(n ln n)` (ratio → 0.941 per
octave) are numerically indistinguishable from those of the convergent
`Σ 1/n^1.1` (ratio → 0.933), so any flag catching the former false-positives on
the latter — which is why `Σ 1/Prime[n]` returns a finite value here and in
Mathematica. When the extrapolation does not stabilise, the existing
`NSum::accgl`/`NSum::ncvg` warning already signals untrustworthy digits (the
divergent `P(1)` now warns with estimated error ~1e-3).

Tests: new `test_integer_only_summand` in `tests/test_nsum.c` plus a Prime case
added to `test_memory_loop`; all `nsum_tests`/`nprod_tests` pass, `make
check-c99` clean, no new leaks (macOS baseline).

## Thue solver: reducible binary forms `F(x,y) == m` (2026-08-20)

A reducible form is not a Thue equation (the Tzanakis–de Weger method needs `F`
irreducible), but when `F(x,1)` factors into **≥ 2 coprime** irreducible factors
the solution set is finite. `thue_solve_reducible_form` (`src/solvethue.c`) does
it exactly: factor `F(x,1)` over Z (FLINT `fmpz_poly_factor`), homogenise the
factors, and — since at any integer point each factor value `G_i(x,y)` is an
integer with `prod G_i(x,y)^{e_i} = m/content` — enumerate the finitely many
**signed divisor assignments** and solve each system `{ G_i(x,y) = d_i }`:
parametrise the line of one linear factor, substitute into a second factor to get
a univariate whose integer roots (via `fmpz_poly_factor`) are the candidate
points, and verify every factor equation and `F == m` exactly. When there is **no
linear factor** (e.g. two irreducible quadratics), eliminate `y` via the resultant
`Res_y(G_0-d_0, G_1-d_1)` (sampled and integer-interpolated) and integer-root the
result. Complete finite set, or a proven `{}`. A **pure power of a single factor** (e.g. `(x-y)^3 == 1`)
has infinitely many / PARI-refused solutions → DECLINE. `thue_solve_binary_form`
dispatches here when `F(x,1)` is reducible; the irreducible path is unchanged.

Works for **any `m`** (not just `|m| = 1`). Cross-checked vs PARI/GP `thue()` over
a 90-case reducible grid (`x^3-y^3`, the Thomas family, `x^4-y^4`, biquadratic,
repeated-factor forms `(x-1)^2(x-a)`, m from −20 to 20): **0 WRONG**. Benchmark
88: **CORRECT 81 -> 94**, 0 WRONG / 0 CRASH. A 150-case grid of two-quadratic
products (`m in [-5,5]`) also cross-checks 0 WRONG. Clears `thomas-t*`,

## Thue solver M3: Round-2 maximal order + O_K-basis unit search (2026-08-20)

Gate 1 previously required the equation order `Z[theta]` to already be the ring
of integers `O_K` (monogenic), declining every non-monogenic field. M3 computes
the maximal order by **Round 2 (Pohst-Zassenhaus)** and searches for units over
`O_K`, clearing the non-monogenic bucket of `SOLVE_INTEGERS.md` Tier-3 F.

- **`nf_round2_maximal_order`** (`src/numbertheory/nfround2.c`, on FLINT
  matrices). At each prime `p` with `p^2 | disc(f)`: the p-radical
  `I_p = ker(Frobenius^k)` (`k` minimal with `p^k >= n`; an F_p nullspace), a
  Z-basis of `I_p` by HNF, then the ring of multipliers `O' = (I_p : I_p)` as the
  F_p kernel of "multiply-by-a on `I_p/pI_p`" assembled and HNF'd, `O' = (1/p)H'`.
  Iterate at each `p` until the index stops dropping. `O_K` is returned as an
  integral basis `(1/D)*W` (integer HNF `W` of theta-power numerators, shared
  denominator `D`), with `[O_K:Z[theta]]` and `d_K = disc(f)/index^2`. The
  β-change-of-basis is exact over Q (`H_I` is singular mod p); every completeness
  decision is exact. Validated against PARI `nfinit`: Dedekind cubic `t^3-t^2-2t-8`
  (index 2, d_K -503), `Q(cbrt 10/17/20)`, `Q(d^{1/4})` incl. the index-16
  `Q(12^{1/4})`.
- **O_K representation.** `NumberField` carries `(W, D, index)`; the monogenic
  fast path is `W = I, D = 1` (byte-for-byte unchanged). A field element with
  integer O_K-coords `c` is `(1/D)v`, `v = sum_i c_i W[i]` in `Z[theta]`; a unit
  then satisfies `|N(u)|=1 <=> |N(v)|=D^n`, and `embed(u)=embed(v)/D`, so the
  existing exact `nf_norm_int`/`nf_embed_int` on the integer vector `v` are
  reused. The solvethue reconstruction stays in theta-coords and is unchanged;
  only the unit search walks the O_K lattice `L={sum c_i W[i]}` (`nfunits.c`),
  and p-saturation multiplies the character by `D^{-1} mod q`. The unit is stored
  as `(v, D)` and solvethue builds `(1/D)v`. The Voronoi fallback (rank-1 complex
  cubic) walks `Z[theta]` and its result `w` is stored as `D*w`; p-saturation
  rejects it if it is only a power of the true fundamental unit.
- **Baker bound needs no change:** the unit embeddings enter only as log-ratios
  `log|eps^(k)/eps^(j)|`, where the `1/D` cancels.
- **Safety.** The M2 general-`m` μ-enumeration is gated to monogenic fields
  (`nf_ok_index == 1`): over a non-monogenic field it would miss `O_K\Z[theta]`
  reps, so `|m| != 1` non-monogenic DECLINEs.

**Result.** `Solve[x^3 - d y^3 == +-1 && …, {x,y}, Integers]` now returns the
complete set for non-monogenic `Q(cbrt d)` — `d = 10, 12, 17, 19, 20`, the
Dedekind cubic, and non-monogenic quartics `Q(d^{1/4})` — e.g.
`x^3-17y^3==1 -> {(1,0),(18,7)}`, `x^3-20y^3==1 -> {(1,0),(-19,-7)}`,
`x^4-12y^4==1 -> {(-1,0),(1,0)}`. Benchmark 88: **CORRECT 65 -> 81**, 0 WRONG / 0
CRASH; cross-checked vs PARI over a 130-case non-monogenic grid (0 WRONG).
Larger-regulator non-monogenic quartics still DECLINE (O_K-Voronoi is a
follow-on). Tests: `tests/test_numberfield.c` (index + d_K vs PARI, incl.
multi-round quartics), `tests/test_thue.c`. c99-clean, macOS `leaks` = 0,
`USE_FLINT=0` degrade compiles.

## Thue solver M2: general `m` (`|m| != 1`) via μ-enumeration (2026-08-19)

The Thue engine (`src/solvethue.c`) previously required `|m| = 1`, where
`beta = x - theta*y` is a **unit**.  For general `m`, since `N(x - theta*y) =
F(x,y) = m` for a monic form, `beta` is an algebraic integer of **norm m**, so
`beta = mu * prod eps_k^{b_k}` where `mu` ranges over a finite set of
bounded-norm representatives (Tzanakis–de Weger §II.1).  M2 implements this for
the **rank-1 complex cubic** case (the `|m| != 1` bucket of `SOLVE_INTEGERS.md`
Tier-3 F).

- **μ-enumeration** (`thue_norm_reps_cubic11`).  A canonical orbit rep reduces
  by the fundamental unit to `|sigma1(mu)| in [1, e^R)`; the norm then forces
  `|sigma2(mu)| <= sqrt|m|`.  Those embedding bounds map, through the inverse
  Vandermonde, to a finite integer coordinate box; keep the points with
  `N == m` exactly.  Over-coverage of unit orbits is safe — the final `(x,y)`
  set is deduped.  Box too large ⇒ DECLINE.
- **μ-aware Baker bound.**  `thue_exponent_bound` now takes the μ-set: the
  linear form's `delta` gains the `log|mu^(k)/mu^(j)|` (real) / `arg` (complex)
  term per μ, the reduction loops over μ, and the constants `C4` (`/mu_`), `Y2p`
  (`*mu_+`), and `V0` (`+mu`-ratio height) use the M-set min/max.  Every
  μ-constant is an **over-estimate** — a too-large bound is safe (the de-Weger
  reduction shrinks it, or the box check declines), only a too-small bound could
  miss a solution.  `|m| = 1` passes `NULL/0` and is byte-for-byte unchanged.
- **Per-μ enumeration.**  `beta = mu * prod eps_k^{b_k}` over `|b_k| <= B` and
  each μ; reconstruct `(x,y)` (require `beta in Z + Z*theta`), verify `F == m`.

**Result.**  `Solve[x^3 - d y^3 == m && Element[{x,y}, Integers], {x,y},
Integers]` now returns the complete set for `|m| != 1` over rank-1 complex
cubics — e.g. `x^3-2y^3==2 -> {(0,-1)}`, `==3 -> {(1,-1),(-5,-4)}`,
`==10 -> {(2,-1),(4,3)}`, and `==4/5/9/73/100 -> {}` (proven).  Cross-checked
against PARI/GP `thue()` over a **270-case** grid (many `d`, `m` of both signs
up to 250): **0 WRONG**, every solved case matches, larger-regulator fields
DECLINE safely.  Out of scope (rank-2 totally-real `|m| != 1`, `|a0| != 1`,
non-monogenic) still DECLINEs.  Tests: `tests/test_thue.c`.  c99-clean, macOS
`leaks` = 0, `USE_FLINT=0` degrade compiles.

## Thue solver M1: Voronoi units for large-regulator complex cubics (2026-08-19)

The Thue engine's Gate 2 (fundamental units) found units by an exact
coefficient-box search, so it only reached **small-regulator** fields: a
fundamental unit's coordinates grow with the regulator, and `Q(cbrt 15)` (unit
coordinate `30`), `Q(cbrt 42)` (`42`), `Q(cbrt 97)` (~10 digits), `Q(cbrt 41)`
(24-digit unit, regulator `56.3`) all exceeded any box and **DECLINED**. New
`src/numbertheory/nfvoronoi.c` implements **Voronoi's algorithm** for the
fundamental unit of a rank-1 complex cubic (signature `(1,1)`), the M1 item of
[`docs/design/thue_completion_plan.md`](../../design/thue_completion_plan.md).

- **Chain of minima.** Walk `theta_0 = 1, theta_1, ...` where each `theta'` is
  the *second-kind adjacent minimum* — the `O_K` element minimising `sigma1`
  subject to `sigma1 > sigma1(theta)` and `|sigma2| < |sigma2(theta)|`. `sigma1`
  strictly increases; the first `theta_k` with `|N| = 1` is the fundamental unit
  (the chain length is polynomial in the regulator, so `Q(cbrt 41)`'s reg-56
  unit is ~48 steps).
- **Well-conditioned neighbour search.** The neighbour is *not* a short Minkowski
  vector (it minimises `sigma1` under an anisotropic `|sigma2| < 1` constraint),
  so the real column of the `theta^{-1}O_K` Minkowski lattice is rescaled by
  `1/U = 2^-u` to make the box isotropic; `U` grows until the box first captures
  a neighbour. LLL (`lll_reduce_q`) reduces the rescaled lattice — an appended
  identity block records the unimodular transform, giving the reduced basis' `O_K`
  preimages directly — then a small enumeration reads off the minimal-`sigma1`
  point. `arb`/`acb` with adaptive precision; every strict comparison is
  interval-safe.
- **Contract preserved (propose-then-certify).** Voronoi only *proposes* the
  unit; the existing exact **p-saturation + `|N| = 1`** test certifies it, so a
  wrong proposal DECLINEs, never a wrong answer. The certifier is now **mpz** end
  to end (`eval_coords_mod`, `p_saturate`, storage), so a 24-digit unit is
  handled the same as a one-digit one — no int64 truncation.
- **Result.** `Solve[x^3 - d y^3 == +-1 && Element[{x,y}, Integers], {x,y},
  Integers]` returns the complete set (`{(+-1, 0)}`) for `d = 15, 41, 42, 97`
  and any monogenic complex cubic whose unit outgrew the box. Benchmark 88
  (`benchmarks/88-thue-equations/`, PARI/GP `thue()` oracle): **CORRECT 48 -> 56,
  0 WRONG / 0 CRASH**. Non-monogenic (`d = 10, 12, 17, 20`) and `|m| != 1` stay
  correct DECLINEs (M2/M3). Tests: `tests/test_numberfield.c` (regulators match
  PARI `bnfinit` to 6 digits, exact `|N| = 1`), `tests/test_thue.c` (rigorous
  auto-bound path). c99-clean, macOS `leaks` = 0, `USE_FLINT=0` degrade compiles.

## Perf: Thue solver — profiling-driven speedups (2026-08-19)

Benchmark 88's timings (vs PARI/GP `thue()`) motivated a profiling pass on
`src/solvethue.c` / `src/numbertheory/nfunits.c`. `THUE_DEBUG=1` now prints
per-phase timings. The three changes are all constant-factor (no answer
changes; benchmark stays 0 WRONG / 0 CRASH):

- **Enumeration power-precompute.** The completeness enumeration rebuilt
  `prod eps_k^{b_k}` from scratch with `nf_elem_pow` at each of the `(2B+1)^r`
  lattice points. Now the powers `eps_k^j` (`j in [-B,B]`) are precomputed once,
  so each point is `r-1` multiplications. This was the dominant cost of the
  slow cases: Thomas conductor-7 cubic 283 → 33 ms (8.7x), `x^7-2y^7=1` 934 →
  166 ms (5.6x), `x^4-4x^2y^2+y^4` 217 → 41 ms (5.2x).
- **Unit search: certify-in-loop + saturation early-out.** `nf_fundamental_units`
  grew its coefficient box until it held `r+8` candidate units — so a rank-1
  cubic whose unit sits at `B=1` still scanned all `25^3 = 15625` box points
  (~14 ms of norm tests). It now grows one shell at a time and tries to CERTIFY
  the shortest `r` independent units by p-saturation after each shell, stopping
  the moment it certifies (a non-fundamental early set fails saturation, so the
  box keeps growing rather than declining — coverage is preserved). And
  `p_saturate` early-outs once the mod-`p` character-matrix rank has stalled
  below `r` for 12 consecutive primes (a non-fundamental set never reaches full
  rank, so scanning the whole 200-prime budget was wasted). Together:
  `x^3-2y^3=1` 14 → **1.4 ms**, `x^3-6y^3=1` → 2.7 ms, `x^4-3y^4=1` 90 → 4.8 ms,
  `x^4-6y^4=1` 119 → 31 ms. The common cubic/quartic cases are now FASTER than
  PARI's compute time.
- **Adaptive reduction precision.** The Baker/de-Weger reduction ran at a
  blanket 1600-bit `arb`; it is now sized from `K3` (the reduction's `c0 ~
  K3^q`) and escalated on demand, with `c0` capped so `log2(c0) <= prec-128`
  keeps `floor(c0*mu)` exact. Modest on its own (precision was not the
  bottleneck) but removes the worst-case tax on easy fields.

Net: simple cubics/quartics solve in 1–6 ms (beating PARI's 6–9 ms compute
time); the remaining gap is on high-degree (sextic ~120 ms, septic ~166 ms) and
many-solution forms. `make check-c99` clean, 0 leaks (MSL), all suites pass.

## Feature: number-field arithmetic layer + Thue-equation engine (2026-08-19)

Tier-3 F (Thue equations). Two new subsystems land the shared
number-field prerequisite `SOLVE_INTEGERS.md` §6-F names, and the Thue
reconstruction engine that sits on top. Built on FLINT/ANTIC
(`USE_FLINT`; the whole feature degrades to a clean decline without it).

**Number-field layer** (`src/numbertheory/numberfield.{c,h}`,
`nfunits.{c,h}`) — for `K = Q(theta)`, theta a root of a monic irreducible
integer polynomial:

- **Gate 1 — maximal-order certification.** `nf_field_create` computes
  `disc(f)`, factors it (`facint_factor_complete`, new public entry in
  `src/facint.c`, complete-or-DECLINE with strong probable-prime cofactor
  checking), and runs **Dedekind's criterion** at each prime `p` with
  `p^2 | disc`. The radical is taken from the true mod-`p` factorisation
  (`nmod_poly_factor`), NOT `gcd(f, f')` — in small characteristic
  (`p | e_i`, e.g. `(x^2)' = 0` over F_2) the derivative over-counts and
  silently mis-decides exactly the small primes Dedekind runs at. Only the
  **monogenic** case (`Z[theta] = O_K`, index 1) is accepted; anything
  non-maximal, non-monic, or reducible DECLINEs. Signature `(r1, r2)` via
  an exact Sturm real-root count (FLINT-free).
- **Gate 2 — fundamental units + regulator** (`nf_fundamental_units`).
  Small-norm unit search (exact `|N| == 1`), log-embeddings from certified
  `arb`/`acb` conjugate roots, a greedy independent set, and the regulator
  from the log-lattice. Fundamentality (index 1) is certified by
  **p-saturation**: for every prime `p <= R / R0` (`R0 = 0.2`, Friedman's
  unconditional regulator lower bound) the mod-`p` matrix of p-th-power
  characters at degree-1 primes must reach full column rank `r`. Full rank
  proves saturation UNCONDITIONALLY for any prime set; if it is not reached
  within budget the routine DECLINEs (no fragile group-enlargement step).
  Validated: computed regulators match LMFDB exactly — `Q(2^(1/3))`
  `1.347377` (rank 1), the conductor-9 cyclic cubic `0.849287` (rank 2),
  `Q(2^(1/4))` `2.158001` (rank 2).

**Thue engine** (`src/solvethue.{c,h}`). For a monic form (`|a0| = 1`) with
`|m| = 1` over a monogenic field with a real embedding, `beta = x - theta*y`
is a unit, so every solution is `x - theta*y = +- prod eps_k^{b_k}`. The
engine enumerates exponent vectors, reconstructs `(x, y)` from the resulting
unit's coordinates (it must lie in `Z + Z*theta`), and verifies `F(x,y)==m`
exactly in GMP. This reconstruction is validated against the known-complete
literature solution sets (`tests/test_thue.c`, via the internal
`Solve\`ThueSolveForm[{a0..an}, m, bound]`):

```
x^3 - 2 y^3 == 1      -> {(1,0), (-1,-1)}
x^3 - 7 y^3 == 1      -> {(1,0), (2,1)}
x^3 - 3 x y^2 + y^3 == 1  -> the 6 solutions {(1,0),(0,1),(-1,-1),(2,-1),(1,3),(-3,-2)}
x^4 - 2 y^4 == -1     -> {(±1, ±1)}
```

**Rigorous automatic bound (Baker + LLL).** `thue_exponent_bound`
(`src/solvethue.c`) implements the full Tzanakis-de Weger reduction against
the paper's explicit constants (`docs/references/thue/`): the C1..C6
root/unit constants, **Waldschmidt's** linear-forms-in-logarithms lower
bound for the initial (astronomical) exponent bound K3, and the **de Weger
LLL** reduction (Prop. 3.2) that collapses K3 (~10^30-40) to a small B in a
few passes, reusing the exported `lll_reduce_q`.  All floating work is
`arb`/`acb` ball arithmetic at 1600 bits; every accept/reject that affects
completeness is exact or a rigorous outward bound.  The **Q-dependent case
(iii)** -- a fundamental unit in a proper subfield (e.g. `1+sqrt2` inside
`Q(2^{1/4})`) makes its linear-form coefficient vanish/relate, degenerating
the lattice -- is handled by detecting the small-integer relation, reducing
the independent subform, and applying the "L-trick" `A < (1/K2)log(K1/L)`.
Completeness = union of the exponent enumeration (`|Y|>Y2'`, bounded by B)
and a small-|Y| brute force; every candidate is exact-verified in GMP.

**Dispatch + result.** `si_solve_thue` (`src/solveint.c`) detects a single
homogeneous binary form of degree >= 3 equal to a constant and hands it to
the engine (slotted into `solveint_solve_integer` beside `si_solve_mordell`).
`Solve[..., Integers]` now returns the **complete solution set**:

```
Solve[x^3 - 2 y^3 == 1 && Element[{x,y},Integers], {x,y}, Integers]
  => {{x -> -1, y -> -1}, {x -> 1, y -> 0}}
Solve[x^3 - 3 x y^2 + y^3 == 1 && ..., {x,y}, Integers]
  => the 6 solutions {(1,0),(0,1),(-1,-1),(2,-1),(1,3),(-3,-2)}
Solve[x^4 - 2 y^4 == -1 && ..., {x,y}, Integers]  => {(±1,±1)}
```

Also solves e.g. `x^3-7y^3=1 -> {(1,0),(2,1)}` and the conductor-7 Thomas
cubic `x^3+x^2y-2xy^2-y^3=1` (9 solutions, matched to brute force).  Per the
"provably complete or DECLINE" contract, out-of-scope inputs decline safely
and never guess: a **non-monogenic** field (`x^3-17y^3=1`, `Q(cbrt17)` has
index 3 at p=3), `|m| != 1`, `|a0| != 1`, degree beyond reach, or a bound
too large to enumerate.

Memory: macOS `leaks` reports 0 for `numberfield_tests` and `thue_tests`;
every `mpz`/`mpq`/`mpfr` and FLINT object is paired with its clear. Builds
clean under GCC 16 with FLINT 3.6 and in the `USE_FLINT=0` degrade config;
`make check-c99` clean. New exports: `lll_reduce_q` (real-lattice LLL
wrapper over the static `lll_reduce`, `src/linalg/latticereduce.c`) and
`facint_factor_complete`. Tests: `tests/test_numberfield.c` (Gate 1 + Gate
2), `tests/test_thue.c` (reconstruction corpus + decline cases).

## UnitBox (2026-08-18)

Added `UnitBox[x]`: the rectangular pulse (box) function, `1` for
`-1/2 <= x <= 1/2` and `0` otherwise, closed at both endpoints. It sits in
`src/piecewise.c` beside its siblings `UnitStep`/`Ramp`, registered with
`Listable`, `NumericFunction`, `Orderless`, `Protected` (matching Mathematica;
`Orderless` reflects the variadic multidimensional box, like `UnitStep`).

The implementation reuses `UnitStep`'s existing `ustep_class()` sign
classifier twice, on the shifted arguments `x + 1/2` and `1/2 - x`, rather
than adding a second classifier: `x` is in the box iff neither shifted value
is negative. This gets `UnitBox` exact-symbolic-real certification (`Pi`,
`Sqrt[2]`, ...) for free, by construction, rather than by duplicating
`UnitStep`'s MPFR-precision-escalation logic.

Two things were deliberately **not** done, both unmeasured rather than
overlooked:
- No entry on the packed-array `AWARE` list in `src/pack.c` -- every existing
  entry there is backed by a measured workload, and `UnitBox` has none yet.
- No optimization of the per-element cost of building and evaluating the two
  shifted expressions (`x + 1/2`, `1/2 - x`), which `Ramp` avoids entirely by
  calling `ustep_class` directly on the argument. `UnitBox` is `Listable`, so
  this cost is paid per element; accepted for now in exchange for reusing
  `ustep_class`'s certification rather than forking it. Revisit either only
  if a packed or large-list `UnitBox` workload actually shows up.

Also deliberately out of scope for this first pass: no `SYM_UnitBox`
interned symbol (nothing compares it by pointer -- `Ramp` has none either),
and no `Interval` threading via `piecewise_interval()`/
`interval_apply_function()` -- that path only supports monotone functions
(`Floor`/`Ceiling`), and `UnitBox`, like `UnitStep` and `Ramp`, isn't one.

## Fix: Linux build — `image_to_json` maybe-uninitialized false positive (2026-08-19)

GCC (16.x, and the glibc CI toolchain) rejected `src/image.c` with
`error: 'rgba' may be used uninitialized [-Wmaybe-uninitialized]` at the
`b64_encode(rgba, npx * 4, b64)` call in `image_to_json`. It is a false
positive: the pixel loop writes `rgba[i*4 + 0..3]` for every `i` in `[0, npx)`,
exactly the `[0, npx*4)` bytes `b64_encode` reads. GCC cannot relate the loop
trip count (`npx`) to the `npx*4` bytes read — the sibling `face_build` call
does not warn only because its `if (!fu || !fv || !len) return false;` guard
proves the buffer non-empty, whereas `image_to_json` has no `npx > 0` guard, so
the degenerate `malloc(0)` path leaves the analyzer unable to prove the buffer
filled. Fixed by allocating the buffer with `calloc(npx, 4)` instead of
`malloc(npx * 4)`: GCC treats zero-initialized memory as initialized, the cost
is negligible on this once-per-image-export path, and it is also correct for a
degenerate 0-pixel image. Verified clean under `gcc -O3 -std=c99 -Wall -Wextra`
plus the makefile's full flag set.

## Fix: Linux build — clean GCC compile across the whole tree (2026-08-19)

A whole-tree GCC 16 rebuild (`-O3 -std=c99 -Wall -Wextra` plus the makefile's full
flag set) surfaced 12 warnings in four files; clang on macOS reports none of them,
so they reach only Linux users. All are now fixed; the tree compiles warning-free.

- **`src/imageio.c` — `invalid_chunk` set but not used (`-Wunused-but-set-variable`).**

- **`src/imagethin.c` — `'*' in boolean context` (`-Wint-in-bool-context`), 3 sites.**
  The zero-size-allocation guard `w*h ? w*h : 1` puts a product in a boolean context,
  which GCC flags (its suggested `&&` would be wrong here). Hoisted the product into a
  `size_t npix` local so the condition is a plain value, reused as the matching loop
  bound.
- **`-Wmaybe-uninitialized` false positives, 4 sites** — `line`/`tmp` in

## Feature: Diophantine solving in Solve[..., Integers] (2026-08-18)

`Solve` gained an algorithmic path over the `Integers` domain for polynomial
equations and systems carrying inequality / ordering / disequation
constraints — previously such an input (an `And` mixing `Equal` with
`Greater`/`Less`) was mis-routed to the linear/nonlinear *system* solvers,
which refuse it, so the query came back unevaluated.

```
Solve[x^2 + 2 y^3 == 3681 && x > 0 && y > 0, {x, y}, Integers]
  => {{x -> 15, y -> 12}, {x -> 41, y -> 10}, {x -> 57, y -> 6}}
```

New module `src/solveint.c` (entry `solveint_solve_integer`, wired into
`builtin_solve` as an `Integers` pre-pass alongside the `Modulus` one;
`Solve`SolveIntegers[eqns, vars]` is the qualified entry). The engine:

- **Stage A** separates equations from constraints and converts each equation
  residual to a sparse integer `MPoly` (`src/poly/mpoly.h`), clearing
  denominators via `Together`/`Numerator`/`Expand` (so `1/x + 1/y + 1/z == r`
  becomes polynomial).
- **Stage B** derives a finite integer box per variable by a fixpoint of
  explicit bounds, ordering propagation, and an **interval-positivity** rule:
  a sign-definite term of `Σ term == R` is bounded by the rest of its
  (in)equality — above, and below (deducing a variable's sign from an odd
  power). A single variable left unbounded is admitted only as the exactly-
  solved leaf; two or more, or a non-polynomial input, is declined.
- **Stage C** enumerates all but one variable with ordering/disequation and
  interval pruning and solves the **last variable exactly** (integer k-th
  root, quadratic discriminant, or rational-root theorem), re-verifying every
  candidate against the original conjunction. A **single separable additive
  equation** (`Σ g_i(x_i) == c` — sums of powers, the taxicab equation) takes
  a **meet-in-the-middle** path instead (~`N^ceil(n/2)` vs `N^(n-1)`), e.g. the
  four-fifth-powers search runs in well under a second.

Correctness posture: only necessary conditions tighten a bound, so an
exhausted finite search returns `{}` as a proof of no solutions; an input that
cannot be bounded to a finite box (an unbounded Pell orbit, a constraint-free
Thue equation) stays **unevaluated** rather than truncated or wrong.

**Phase 2 special forms (divisor-factoring / reciprocal).** Two shapes that
positivity cannot bound are now solved by applying the right identity:

- A single **bilinear** equation `a u v + b u + c v + d == 0`, reached by
  eliminating unit-coefficient linear equations (the router tries each
  variable pair to keep), factors as `(a u + c)(a v + b) = b c - a d` and is
  solved from the **divisors** of that constant — no enumeration of `u, v`.
  `Solve[x^2+y^2==z^2 && x+y+z==3000 && 0<x<y && z>0, {x,y,z}, Integers]` ->
  the three perimeter-3000 triangles `{500,1200,1300}, {600,1125,1275},
  {750,1000,1250}`.
- A sum of unit fractions `sum 1/x_i == R` with an ordering chain bounds the
  smallest variable to `[ceil(1/R), floor(k/R)]` and recurses, the last
  variable determined exactly.
  `Solve[4/2027 == 1/x+1/y+1/z && 0<x<=y<=z, {x,y,z}, Integers]` returns all 73
  ordered decompositions.

Both run in ~1 s and reuse `divisors_ordinary` / the `MPoly` composition path;
every candidate is re-verified against the original conjunction.

**Performance: special forms tried first + numeric verification.** The
Pythagorean-perimeter case with `z > 0` was ~7.5 s (15x slower than
Mathematica): the extra `z > 0` lets Stage B bound the whole box via the linear
equation, so the input took the ~9M-iteration leaf search instead of the
168-divisor bilinear solver, which only fired for the unbounded box. Two fixes:

- The special forms (bilinear / reciprocal) are now attempted **before** the
  enumerative fallback for *every* input, not only unbounded ones — they are
  exact and `O(#divisors)`, so they win whenever the shape matches.
- Per-candidate verification is now numeric: when every constraint is captured
  by the bound / ordering / disequation store, a candidate is checked by
  evaluating the equation `MPoly`s and the stored constraints directly, with no
  symbolic `evaluate()` (previously hundreds of full re-evaluations dominated
  the divisor and reciprocal paths). Eliminated variables are likewise
  reconstructed by numeric `MPoly` evaluation.

Result: the case drops from **7.5 s to ~0.5 ms**. Also fixed a latent leak in
`mpoly_to_expr` (`src/poly/mpoly.c`), which passed its `factors` / `terms` /
`Power`-arg arrays to `expr_new_function` — which *copies* them — without
freeing the originals.

## Feature: exponential Diophantine in Solve[..., Integers] (2026-08-18)

Equations with a **variable in the exponent** (`x^a - y^b == 1`) are now
handled, ahead of the polynomial stage that cannot represent `x^a`
(`src/solveint.c`, `si_solve_exponential`). A fully bounded box is enumerated
exactly with GMP power evaluation, and the **Catalan** shape `x^a - y^b == +/-1`
with bases and exponents `>= 2` is settled by **Mihailescu's theorem** -- the
unique solution is `3^2 - 2^3 = 1`:

```
Solve[x^a - y^b == 1 && 1<x<100 && 1<y<100 && a>1 && b>1, {x,y,a,b}, Integers]
   => {{x -> 3, y -> 2, a -> 2, b -> 3}}
Solve[x^a - y^b == -1 && ...]  => {{x -> 2, y -> 3, a -> 3, b -> 2}}
Solve[2^a - 3^b == -23 && 0<a<10 && 0<b<10, {a,b}, Integers] => {{a -> 2, b -> 3}}
```

When the box excludes `(3,2,2,3)` the answer is `{}` (Mihailescu makes this a
proof, not a truncation). Also added regression coverage confirming bounded
**elliptic / hyperelliptic** curves already resolve through the ordinary
search: `y^2 == x^3 - 10000 && 0<x<10^5 && y>0` -> `{{25,75}}`,
`y^2 == x^3 - 2` -> `{{3,5}}`, `y^2 == x^3 + 1` -> the five integral points.

## Feature: odd-power-sum divisor method in Solve[..., Integers] (2026-08-18)

A separable **sum of odd powers** with two variables sharing the exponent
(`x^3 + y^3 + z^3 == k`, `x^5 + y^5 == k`, ...) over a box too large for the
leaf search is now solved by the **divisor method** instead of an `O(N^2)`
scan. Since `e` is odd, `s = x + y` divides `m = x^e + y^e`, and the power sum
expressed in `s` and `p = x y` (Newton's recurrence
`p_k = s p_{k-1} - p p_{k-2}`) is a degree-`e/2` polynomial in `p`; for each
divisor `s` of `m` its integer roots give `p`, hence `(x, y)` via
`t^2 - s t + p`. The remaining variables are enumerated, so the cost is
`O(N * factoring)`:

```
Solve[x^3 + y^3 + z^3 == 42 && Abs[x] < 10^5 && Abs[y] < 10^5 && Abs[z] < 10^5,
      {x,y,z}, Integers]   => {}    (search space 8x10^15, ~7 s)
Solve[x^3 + y^3 == 1729 && 0 < x <= y, {x,y}, Integers]  => {{1,12},{9,10}}
Solve[x^3 + y^3 + z^3 == 3  && Abs[...] < 8000, {x,y,z}, Integers]
   => {{-5,4,4},{1,1,1},{4,-5,4},{4,4,-5}}
```

It is general over odd exponents (`x^5 + y^5 == 1267` -> `{{3,4}}`), and a size
guard keeps the factored `m ~ B^e` in the fast range (so higher powers are
admitted only over correspondingly smaller boxes; a 5th-power sum over
`Abs[...] < 10^5` would need to factor ~`10^25` per step and is declined).
Verified complete: the `== 3` box recovers all known small solutions and the
two-cube case both Ramanujan pairs. Reuses `divisors_ordinary` and the
univariate integer-root solver; runs at the search-guard boundary alongside the
linear-lattice path.

## Feature: Pell equations in Solve[..., Integers] (2026-08-18)

`Solve` now solves **Pell equations** `x^2 - D y^2 == +/-1` (D a positive
non-square) over the integers, via the continued fraction of `sqrt(D)`. The
fundamental unit generates the whole solution orbit, which is enumerated up to
any explicit bound:

```
Solve[x^2 - 61 y^2 == 1 && x > 0 && y > 0 && x < 10^10, {x, y}, Integers]
  => {{x -> 1766319049, y -> 226153980}}    (the classic fundamental solution)
```

The negative Pell `x^2 - D y^2 == -1` is handled too (the base solution exists
iff the period of `sqrt(D)` is odd), so `x^2 - 2 y^2 == -1` yields
`{{1,1},{7,5},{41,29}}` while `x^2 - 3 y^2 == -1` returns `{}`. All four sign
variants are emitted and filtered by the constraints; an unbounded Pell orbit
(no bound to terminate on) is declined. Runs instantly.

Also added the missing **integer-restriction filter** in `solve_finish`: over
`Integers`, a binding to a provably-non-integer value (a genuine `Rational`,
an irrational radical) is dropped, so `Solve[2 x == 3, x, Integers]` and
`Solve[x^2 == 2, x, Integers]` correctly return `{}` while `Solve[x^2 == 9, x,
Integers]` keeps `{{x -> -3}, {x -> 3}}`. Symbolic / parametric residues are
conservatively kept. Tests: `tests/test_solve_integers.c`.

## Feature: linear Diophantine parametric + bounded gcd test (2026-08-18)

An unconstrained multivariable linear equation now returns its full parametric
family via the gcd staircase (`si_linear_lattice`: a particular solution plus
an `(n-1)`-vector homogeneous basis, built with `mpz_gcdext`), e.g.
`Solve[x + y == 10, {x, y}, Integers]` -> `{{x -> C[1], y -> 10 - C[1]}}`,
`Solve[x + y + z == 5, {x, y, z}, Integers]` ->
`{{x -> C[1], y -> C[2] - C[1], z -> 5 - C[2]}}`; an unsolvable equation
(`gcd(a)` does not divide `b`) gives `{}`. The Integers pre-pass now also
engages for a constraint-free multivariable equation (single-variable
no-constraint cases like `x^2 == 4` still fall through unchanged).

For a boxed linear equation, unsolvability is proven by the same gcd test, so a
large no-solution box is instant:
`314159265 x + 271828182 y + 161803398 z == 1 && Abs[...] < 10^6` -> `{}`
(gcd = 3 does not divide 1). A solvable box is enumerated through the
**LLL-reduced solution lattice**: `LatticeReduce` shortens the homogeneous
basis, the coefficient search box is the exact projection of the value box
through the lattice pseudoinverse (`(B B^T)^{-1} B`), and every candidate is
checked exactly. The search box is small precisely when the coefficients are
large -- so `1000003 x + 999983 y == 7 && Abs[x] < 10^9 && Abs[y] < 10^9`
returns its 2000-point progression in well under a second, while a
small-coefficient equation over a wide box (a dense ~10^8-point lattice) is
declined rather than truncated. Completeness was checked by the 2-variable case
forming a gap-free consecutive progression and by the 3-variable results being
duplicate-free and all in-box.

## Fix: unconstrained sum of even powers in Solve[..., Integers] (2026-08-18)

An unconstrained sum of even powers wrongly returned `{}`:
`Solve[x^2 + y^2 == 25, {x, y}, Integers]` claimed no solutions where there are
twelve. Root cause: the bound propagation could only bound a variable it could
prove non-negative, so with no `x > 0` in sight it declined the whole problem —
and `Solve` then fell through to the generic (real, underdetermined) path, which
over the Integers collapses to `{}`, a *silent wrong answer*.

Fix (`src/solveint.c`, `derive_even_only_bounds`): a variable that appears only
with **even exponents** in every equation is sign-symmetric — the equations
constrain its magnitude, not its sign. Such a variable (when it carries no
explicit sign/ordering constraint) is treated as non-negative for the monotone
bounding pass — `v^even` is minimised at `0`, a sound lower bound on every
monomial it enters — and the derived `[0, B]` is then widened to the true
symmetric window `[-B, B]` so the search covers the negative branch. A companion
one-line tightening lets the bounder act on a zero allowance (`urest == 0`), so
`x^2 + y^2 == 0` yields the origin instead of `{}`.

```
Solve[x^2 + y^2 == 25, {x, y}, Integers]        (* 12 solutions, was {} *)
Solve[x^2 + y^2 == 1000000, {x, y}, Integers]   (* 28 solutions *)
Solve[x^2 + y^2 + z^2 == 29, {x, y, z}, Integers] (* 72 solutions *)
Solve[x^2 + y^2 == 0, {x, y}, Integers]         (* {{x -> 0, y -> 0}} *)
```

Counts verified against sympy's `diophantine(..., permute=True)` (12/28/72 exact
agreement). New coverage in `tests/test_solve_integers.c` (`test_sum_of_two_
squares`); `make check-c99` clean; all solve suites pass; valgrind = baseline.

## Fix: unbounded nonlinear curve no longer fabricates {} over Integers (2026-08-18)

## Fix: underdetermined linear SYSTEM no longer fabricates {} over Integers (2026-08-18)

The system sibling of the fix above, surfaced by a **held-out** Diophantine
corpus (equations drawn from standard references, none of them in the
`benchmarks/87` cases the methods were developed against).
`Solve[{x + 2 y + 3 z == 10, x - y + z == 2}, {x, y, z}, Integers]` returned
`{}` — a silent wrong answer (e.g. `{x -> -2, y -> 0, z -> 4}` satisfies both).
Root cause (`src/solvelinsys.c`): over `Integers` the linear-system specialist
solved the underdetermined system to a **rational** parametric family
(`y -> (4 + 2 x)/5`) and then rejected each RHS as "not a concrete integer",
emptying a set with infinitely many integer points.  The concrete-integer test
is only sound for a *fully determined* system; with free variables it is
category-mistaken.

Fix, two layers:

- `solvelinsys_solve_linear_system` now **declines** (returns `NULL`) for an
  underdetermined system over `Integers` rather than emitting either the wrong
  `{}` or a rational family that hides the integrality constraint.  Solve is
  left **unevaluated** (with `Solve::nsdim`), pending the HNF path that will
  express the integer family in `C[k]`.
- `src/solve.c` gains a general `solution_set_is_parametric` guard (a superset
  of the earlier lone-equation guard): any `{}` reaching the post-dispatch
  funnel over `Integers` whose *pre-filter* answer was a positive-dimensional
  parametric family (an RHS still mentioning a solve variable) is converted to
  unevaluated — an unproven `{}` is never emitted.

Determined cases are unchanged and still return sound answers:
`{x + y == 5, x - y == 1}` → `{{x -> 3, y -> 2}}`; the determined non-integer
`{x + y == 2, x - y == 1}` → `{}` (a real proof, 3/2 ∉ ℤ); inconsistent → `{}`.
New test `test_linear_system_integers_hnf`; all 8 solve suites pass,
`make check-c99` clean.

## Feature: HermiteDecomposition + linear Diophantine SYSTEMS via HNF (2026-08-18)

The follow-through to the fix above: rather than leave an underdetermined
integer linear system unevaluated, `Solve[…, Integers]` now returns the
**complete integer solution family**, via a new Hermite-normal-form primitive.

**`HermiteDecomposition[m]`** (new builtin, `src/linalg/hnf.c`) — the row HNF
of an integer matrix with its unimodular transform: `{u, r}` with `u`
unimodular (`Abs[Det[u]] == 1`), `r` the row Hermite normal form (echelon,
positive pivots, entries above each pivot reduced into `[0, pivot)`), and
`u . m == r`. Works for any `m × n` integer matrix. Each column is eliminated
with the extended-gcd `2×2` unimodular transform `[[s,t],[-b,a]]` (determinant
`(s·a_r + t·a_i)/g = 1`), recorded on `u`.

```
Solve[{x + 2 y + 3 z == 10, x - y + z == 2}, {x, y, z}, Integers]
  => {{x -> 18 + 5 C[1], y -> 8 + 2 C[1], z -> -8 - 3 C[1]}}
```

**Integer linear-system solver** (`si_solve_linear_system_hnf`, `src/solveint.c`)
— engages for an unconstrained system of `m ≥ 2` linear equations `A x == b`
(single equations keep the existing gcd-staircase path). With `P Aᵀ == R`
(row HNF of `Aᵀ`, `P` unimodular), `x = Pᵀ y` triangularises the system into
`H y == b` with `H = Rᵀ` in column-echelon form; forward substitution over the
`rank` pivot columns with an exact-division test gives the particular solution
(a divisibility failure is a **proof** of no integer solution:
`2 x + 2 y == 3 && x - y == 0 → {}`), and the free columns of `Pᵀ` (the integer
kernel lattice) become the parameters `C[k]`. A consistency check on the
non-pivot rows detects inconsistency. Determined systems read off the unique
solution or prove `{}`; a *bounded* system (any inequality) still uses the
finite leaf search.

Tests: `test_hermite_decomposition` (defining invariants + exact HNF, in
`test_latticereduce.c`), `test_linear_system_integers_hnf` (in
`test_solve_integers.c`, 74 cases pass). `make check-c99` clean; valgrind delta
vs the startup baseline is zero (macOS `leaks`: 0). `src/linalg/hnf.c` added to
the test `COMMON_SRC`.

## Feature: definite binary quadratic (rotated ellipse) in Solve[..., Integers] (2026-08-19)

Tier-2 D, first increment. A 2-variable degree-2 equation
`A x^2 + B x y + C y^2 + D x + E y + F == 0` with a **negative discriminant**
`delta = B^2 - 4AC < 0` is a compact ellipse with finitely many integer points --
but a *rotated* one (cross term `B != 0`) is not bounded by `derive_bounds`
(which only boxes sign-definite / even-only variables), so it was left
unevaluated. New `si_solve_elliptic_bqf` (`src/solveint.c`) treats the equation
as a quadratic in `x` for each fixed `y`, over the finite `y`-interval where its

## Feature: generalised Pell x^2 - D y^2 == N in Solve[..., Integers] (2026-08-19)

Tier-1 P2. The unbounded positive-orthant generalised Pell equation
`x^2 - D y^2 == N && x > 0 && y > 0` (any `N != +1`; `N = +1` keeps the existing
`si_solve_pell_parametric` path) now returns **one parametric family per
solution class** — `si_solve_genpell_parametric` in `src/solveint.c`. Previously
only `N = +1` had an unbounded parametric answer; every other `N` (including
`N = -1`) was left unevaluated.

Method: the fundamental unit `(t, u)` of `x^2 - D y^2 = 1` comes from the
continued fraction of `√D`; the **Nagell bound** `y ≤ u√(|N|/(2(t±1)))` makes the
search for fundamental solutions finite; each `(x, y)` found (all four sign
combinations) is advanced into the positive orthant and then **reduced to the
minimal representative** via `ε⁻¹` so members of one class collapse to a single
base; each base emits the closed-form orbit
`(a + b√D)(t + u√D)^C[1]` as a `ConditionalExpression` on `C[1] >= 0`.

```
Solve[x^2 - 2 y^2 == 7 && x > 0 && y > 0, {x, y}, Integers]
  => two class families, fundamentals (3,1) and (5,3)
Solve[x^2 - 2 y^2 == 5 && x > 0 && y > 0, {x, y}, Integers]  => {}   (mod-8 proof)
Solve[x^2 - 13 y^2 == -1 && x > 0 && y > 0, {x, y}, Integers] => one family, (18,5)
Solve[x^2 - 3 y^2 == -1 && x > 0 && y > 0, {x, y}, Integers]  => {}   (even CF period)
```

The search is exhaustive, so an empty result is a **proof** of no solutions
(covering negative Pell over a `D` whose `√D` has even continued-fraction
period). The finder was validated exhaustively against a brute-force
positive-orthant enumeration over ~30 `(D, N)` pairs (multi-class, negative
Pell, large fundamental unit such as `D = 61`, and unsolvable cases). New test
`test_generalized_pell` (13 property assertions: class count, class
fundamentals, equation-holds-under-substitution, unsolvable proofs). All solve
suites pass; `make check-c99` clean; valgrind delta vs baseline = 0.

## Feature: factorable binary quadratic (Runge) in Solve[..., Integers] (2026-08-19)

Tier-1 P1. A single 2-variable degree-2 equation whose quadratic part has a
**cross term** and a **perfect-square discriminant** `δ = B² − 4AC > 0` factors
into two distinct rational linear forms, so the hyperbola has finitely many
integer points — Runge's simplest case. New `si_solve_factorable_conic`
(`src/solveint.c`) completes the square to a difference of squares
`(2kU)² − V² = W` (with `U = 2Ax + By + D`, `k = √δ`, `W = −(P² + 4k²Q)`,
`P = 4AE − 2BD`, `Q = 4AF − D²`) and enumerates the divisors of `|W|`, so the
result is exhaustive and an empty answer is a **proof**:

```
Solve[x^2 + x y - 2 y^2 == 4, {x, y}, Integers]
  => 6 points {(-3,1),(-2,-1),(-2,0),(2,0),(2,1),(3,-1)}
Solve[(x - y)(x + 2 y) == 15, {x, y}, Integers]  => {}   (a mod-3 obstruction)
Solve[2 x^2 + 3 x y - 2 y^2 == 7, {x, y}, Integers]  => {(-3,1),(3,-1)}
```

Generalises the existing `si_solve_conic` (which required no cross term and a
unit `Y²` coefficient) to the cross-term case and to non-unit square
coefficients; it runs after `si_solve_conic` and `si_solve_pell` in
`si_try_special_forms`. A non-square discriminant (a genuine Pell-type conic,
`δ = 5`) or `δ ≤ 0` (parabola/ellipse) is declined, so an unbounded such
equation stays unevaluated rather than answered wrongly. New test
`test_factorable_conic` (80 solve-int cases pass); `make check-c99` clean;
valgrind delta vs baseline = 0.

## Feature: bounded-engine generalizations in Solve[..., Integers] (2026-08-18)

Four upgrades to the bounded search (`src/solveint.c`) let it solve several
classic families it previously declined:

- **Multi-leaf staged elimination** (`si_solve_multileaf`).  A variable that
  appears in exactly one equation and is univariate-solvable there is *peeled* —
  resolved by an exact root per free-variable assignment rather than enumerated.
  The **Euler brick** `x^2+y^2==a^2 && x^2+z^2==b^2 && y^2+z^2==c^2 &&
  0<x<y<z<500 && a,b,c>0` peels `a,b,c` (three square roots) and walks only
  `x<y<z`, returning all three bricks — `(44,117,240;125,244,267)`,
  `(88,234,480;250,488,534)`, `(240,252,275;348,365,373)` — in ~1 s.
- **Ordering-reduced search estimate** (`si_longest_chain`).  The search-space
  guard divides the raw box by the factorial of the longest `<=`/`<` chain, so a
  genuinely ordered box like `0<x<=y<=z<=w<1000` (`~1.7*10^8` ordered nodes, not
  `10^9`) is attempted instead of declined.
- **int64 fast leaf** (`si_leaf_roots_i64` + a per-search coefficient cache).
  Degree-≤2 leaves over small coefficients solve in registers, with a GMP
  fallback on overflow — the hot path for `10^8`-node boxes.  Unlocks
  `2(x^2+y^2+z^2+w^2)==(x+y+z+w)^2` and the four-variable Markov–Hurwitz equation
  `x1^2+x2^2+x3^2+x4^2==x1 x2 x3 x4`.
- **Non-polynomial power-leaf** (`si_solve_bounded_powerleaf`).  When one side is
  a pure power `m^e` of a leaf that appears nowhere else and every other variable
  is bounded, the others are enumerated, the remaining side is evaluated through
  the interpreter (so `Factorial`, `Binomial`, … work), and `m` is solved by an
  exact integer `e`-th root.  **Brocard's problem** `n!+1==m^2 && 0<n<100` returns
  the Brown numbers `n = 4, 5, 7` in under a millisecond.

New coverage in `tests/test_solve_integers.c` (Euler brick, quadratic form,
Markov–Hurwitz, Brocard) plus the regression bank for the correctness fix and the
already-solved cases (`y^3==x^5-x+1`, `x^2+y^3==z^7`, nine-cubes `==239`, the
`x^4+y^4==z^4+w^4 < 10^8 → {}` true negative).  `make check-c99` clean.

## Feature: closed-form Diophantine families in Solve[..., Integers] (2026-08-18)

Six further methods (`src/solveint.c`), each producing the *complete* answer for
an equation the bounded search cannot reach:

- **Binary-quadratic conic** (`si_solve_conic`).  `Y^2 == A X^2 + B X + C` with a
  perfect-square leading coefficient completes to a difference of squares
  `(2pY)^2 - (2AX+B)^2 = 4AC - B^2` and factors the constant.  Euler's
  `n^2 + n + 41 == y^2` -> `{n -> 40, y -> 41}` (D = 163), and difference-of-
  squares `x^2 - y^2 == 15` -> `{{4,1},{8,7}}`.  Exhaustive, so an empty result
  is a proof.
- **Unbounded Pell -> parametric family** (`si_solve_pell_parametric`).
  `x^2 - D y^2 == 1 && x>0 && y>0` returns the fundamental-unit family
  `x -> ((x1+y1 Sqrt[D])^C[1] + (x1-y1 Sqrt[D])^C[1])/2` (and the matching `y`)
  as a `ConditionalExpression` on `C[1] >= 1` -- e.g. D = 109 with fundamental
  `(158070671986249, 15140424455100)`.
- **Homogeneous linear system -> parametric ray** (`si_solve_linear_system_ray`).
  `m = n-1` homogeneous linear equations in `n` positive unknowns have a 1-D
  integer kernel (generalised cross product via a Bareiss determinant); if the
  primitive kernel vector is all-positive the solutions are `{v C[1] : C[1]>=1}`,
  else there is no positive solution.  Settles rational systems like
  `w == 5/6 x + y && x == 9/20 y + z && y == 13/42 z + w` (which forces
  `x = -13 z / 35`, hence `{}` -- previously left unevaluated).
- **Fixed-base exponential** (`si_solve_exponential`, new branch).
  `P^m - Q^n == +/-1` with constant bases and variable exponents is settled by
  Mihailescu (both exponents `>= 2` -> only `3^2 - 2^3`) plus the exponent-1
  cases, so `3^m - 2^n == 1` -> `{(1,1),(2,3)}` despite `m, n` unbounded.
- **Prouhet-Tarry-Escott -> {}** (`si_solve_power_sum_equal`).  Two `k`-element
  groups with equal power sums for degrees `1..k` are the same multiset (Newton's
  identities); with strict orderings this forces the groups equal, so a
  disequation like `a != d` proves emptiness -- the size-3 degree-1..3 system is
  `{}` though every variable is unbounded.
- **Unbounded Mordell** (`si_solve_mordell`).  `y^2 == x^3 + k` factors as
  `x^3 = (y-sqrt k)(y+sqrt k)` in `Z[sqrt k]`; the cube factors give the COMPLETE
  integer-point set whenever the descent is sound -- `k < 0`, `|k|` squarefree,
  `k = 2,3 (mod 4)` (so the ring is `Z[sqrt k]` with units `{+/-1}`, and a mod-8
  argument forces `x` odd + coprime to `k`, hence the factors are always coprime,
  no non-coprime casework), and `3` does not divide the class number (computed by
  counting reduced binary quadratic forms of discriminant `-4|k|`, so the ideal
  cube is a principal cube).  `y^2 == x^3 - 2` -> `(3, +/-5)`, `y^2 == x^3 - 13`
  -> `(17, +/-70)`, `y^2 == x^3 - 5` -> `{}` (PROVED, not merely unfound).
  Verified against brute force for every engaged `k` in `[-150, -2]` (49 curves,
  all matching to `x < 2*10^5`, far beyond the descent's `x <~ 4|k|/3` bound).  A
  bounded `x` still uses the ordinary leaf search; the half-integer ring
  (`k = 1 mod 4`), `3 | h`, and the real-quadratic case (`k > 0`, infinite unit
  group -- e.g. `y^2 == x^3 + 3`) are declined, never guessed.

Genuinely research-grade families remain honest declines (unevaluated, never a
wrong `{}`): Elkies `x^4+y^4+z^4==w^4` at `10^7`-scale, Cassels
`3x^3+4y^3+5z^3==0` (a Hasse-principle failure), the Pythagorean-area
`x^2+y^2==z^2 && xy==2w^2` (Fermat's right-triangle theorem), and Ramanujan-Nagell
`x^2+7==2^n` (Nagell's theorem, needs the descent in `Z[(1+sqrt(-7))/2]`).  New
tests for every method; `make check-c99` clean; valgrind = startup baseline.

## Fix: Solve drops extraneous / non-real Root[] solutions (2026-08-17)

`Solve[Sqrt[x] + 3 x^(1/3) == 5, x, Reals]` returned three `Root[]` objects
where only one is valid; Mathematica returns just the real, satisfying root.
Clearing the radicals (substituting `u = x^(1/6)`, forming the resultant cubic
`x^3 + 6 x^2 + 8625 x - 15625`) hands every branch of `x^(1/6)` to the
polynomial solver, but only the principal branch satisfies the original
equation — the other two roots are complex and extraneous. The same defect
class surfaced wherever a complex `Root[]` leaked through a real domain:
`Solve[x^5 - x - 1 == 0, x, Reals]` returned all five roots, and
`Solve[{x^2 + y^2 == 1, x^3 + y == 1/2}, {x, y}, Reals]` returned all six
complex `Root`-tuples.

Two complementary fixes:

- **`src/solverad.c` — verify `Root[]` candidates.** `verify_candidate` no
  longer accepts `Root[]` objects verbatim; they are back-substituted into the
  original equation and numerically checked like every other candidate
  (`N[Sqrt[Root[..]] + 3 Root[..]^(1/3) - 5]` is `~0` for the valid root, `O(1)`
  for the spurious ones). This rejects the extraneous roots in **both** the
  `Reals` and default `Complexes` domains. When a `Root[]` cannot be
  numericalised (`USE_MPFR=0`, non-integer coefficients) the numeric pass
  abstains and the candidate is kept, preserving prior behaviour.

- **`src/solve.c` — unified `Reals` reality filter.** A post-dispatch filter at
  `Solve`'s shared funnel (`solve_finish`) drops any solution whose bound value
  numericalises to a `Complex[re, im]` with a concrete `|im| > 1e-9`, for the
  `Reals` / `Integers` / `Rationals` domains. One location covers the
  single-variable polynomial path **and** polynomial systems (complex
  `Root`-tuples). Conservative by construction: real `Root[]` objects, concrete
  reals, and symbolic/parametric values that do not numericalise (e.g.
  `Sqrt[a]`) survive; the default `Complexes` domain is untouched.

Results now match Mathematica: `Solve[Sqrt[x] + 3 x^(1/3) == 5, x, Reals]` and
its default-domain form return one solution; `x^5 - x - 1 == 0` over `Reals`
returns one, `x^6 - x - 1 == 0` returns two, and the system above returns two
real tuples — while every `Complexes` count is unchanged
(`x^5 - x - 1 == 0` still returns five). Coverage: twelve form-invariant
`O-*` rows in `tests/solve_corpus.m` (back-substitution + count + domain
membership) and pinned-FullForm regressions in
`tests/test_solve_radicals_reals.c`.

## Parser precedence renumbering onto a 1–10000 ladder (2026-08-17)

The parser's operator precedences were renumbered from the old Mathematica-derived
scale (~10–1100) onto a clean **1–10000 ladder**: round values, spread out with
generous gaps between adjacent levels, so upcoming new operators can be inserted
between existing precedences without another renumbering. Representative mappings:
`;` 10→100, `->` 120→1500, comparisons 290→3200, `+` 310→3500, `*` 400→4500,
`^` 590→6500, `@`/`/@` 620→7000, `f[x]` 1000→9500, `[[…]]` 1100→10000.

The remap is **strictly order-preserving** (order-isomorphic): for every pair of
levels the `<`/`==` relationship is unchanged, and the printer's parenthesiser
(`get_expr_prec` and the inline `parent_prec` arguments in `src/print.c`) was
moved in lockstep with the parser table (`get_operator` in `src/parse.c`). Because
both the Pratt loop and the parenthesiser make only order comparisons on these
numbers, every parse tree and every printed form is **byte-identical** to before —
a pure renumbering with no behavioural change. Verified by diffing `FullForm`,
`InputForm` and `TeXForm` over a 73-case operator-dense corpus (identical), plus

## Finite-field Gröbner bases: modular systems in Solve and GroebnerBasis (2026-08-17)

New self-contained Buchberger engine over the prime field `GF(p)`
(`src/poly/gbmod.{c,h}`): native `uint64` residue coefficients, modular inverse
for division, lex / grevlex orders, with the coprime-leading-term criterion.
Independent of the characteristic-0 `groebner.c` engine (GMP rationals), it
reuses that engine's `gb_from_expr` parser via a `GBPoly -> GFpPoly` reduction
(refusing any coefficient whose denominator is divisible by `p`).

**`Solve[{system}, {vars}, Modulus -> p]`** (prime `p`) now solves polynomial
systems over `GF(p)` — previously refused (`solvemod.c` handled only the single
variable). The lex GF(p) basis is walked with triangular per-variable residue
enumeration (`solvemod.c` `solvemod_solve_system`): solve the last variable's
univariate generator by trying all `p` residues, back-substitute, recurse; a
variable with no univariate generator is free and ranges over all of `GF(p)`
(the leaf verifies every generator vanishes). `Solve[{x^2 + y^2 == 1, x == y},
{x, y}, Modulus -> 7]` -> `{{x -> 2, y -> 2}, {x -> 5, y -> 5}}`; a unit ideal
-> `{}`; `Solve[{x + y == 1}, {x, y}, Modulus -> 3]` enumerates the three points.
A **composite** modulus is not a field, so those systems are refused
(unevaluated); single-variable composite still works via residue enumeration.

**`GroebnerBasis[polys, vars, Modulus -> p]`** (prime `p`) computes a genuine
`GF(p)` basis, replacing the old ignored-option stub. `GroebnerBasis[{x^2+y^2-1,
(x-1)^2+y^2-1}, {x, y}, Modulus -> 7]` -> `{1 + y^2, 3 + x}` (monic lex). A
non-prime / out-of-range modulus or a denominator pole falls back to the
rational basis with a note.

## Solve: parametric nonlinear systems (coefficients in Q(params)) (2026-08-17)

`Solve` now solves **systems of nonlinear equations with symbolic parameters**.
`Solve[{x + y == a, x y == b}, {x, y}]` → the Vieta radical pair
`{{x -> (a - Sqrt[a^2 - 4 b])/2, y -> (a + Sqrt[a^2 - 4 b])/2}, {…}}`; previously
unevaluated because `gb_from_expr` rejected the free symbols `a, b`.

**Method** (`src/solvenlsys.c`). A free symbol that is neither a solve variable nor
a known constant (`Pi`, `E`, …) is a parameter. When any appear, the specialist
computes the lex Gröbner basis over the field **Q(parameters)** by reusing the
`GroebnerBasis` builtin's `CoefficientDomain -> RationalFunctions` engine (which
localises the parameters into the coefficient field), then runs the existing
triangular back-substitution — `nl_rec` already treats parameters as symbolic
coefficients, and `Solve\`SolvePolynomialEquality` already solves univariate
polynomials with symbolic coefficients. A basis generator free of every solve
variable is a field constant: a nonzero **number** means the ideal is `<1>` →
(generic) inconsistency → `{}`; a **parameter-dependent** one is a
consistency/nondegeneracy condition and is declined (unevaluated) rather than
guessed — that case-splitting is `Reduce`'s job. The result carries **no**
`ConditionalExpression` nondegeneracy guards (matching `Solve`, not `Reduce`);
positive-dimensional-in-the-variables systems are caught by `nl_rec`'s
incompleteness guard (unevaluated, never a false `{}`). Guardrail: more than three
distinct parameters declines.

Examples now solved (verified by symbolic back-substitution to `0`):
`{x^2 == a, x + y == 0}` → `x -> ±Sqrt[a]`; `{x^2 + y^2 == r^2, y == 0}` →
`x -> ±Sqrt[r^2]`.

**Refactor.** The triangular search (`NlCtx` + `nl_rec` + assembly) is now the
shared helper `run_nl_search`, used by both the rational-coefficient and
parametric paths.

**Tests.** `tests/solve_corpus.m` category **K** (`[D8]`, three cases); corpus 79/79.

## Solve: rational-function nonlinear systems (denominator clearing) (2026-08-17)

`Solve` now solves **systems of nonlinear equations containing denominators**.
`Solve[{1/x + 1/y == 1, x + y == 4}, {x, y}]` → `{{x -> 2, y -> 2}}`; previously
unevaluated because `gb_from_expr` rejected the rational equation.

**Method** (`src/solvenlsys.c`). Each equation `lhs == rhs` is put over a common
denominator (`Together`); the **`Numerator`** becomes the polynomial equation fed to
the Gröbner solver, and a non-constant **`Denominator`** is recorded per equation. A
completed tuple that drives any recorded denominator provably to zero is pruned
(`tuple_denominators_ok`, a `zero_test_decide` back-substitution alongside the existing
`verify_tuple`), since a den-zero point is a spurious root introduced by clearing.
`{(x - y)/(x + y - 2) == 0, x y == 1}` → `{{x -> -1, y -> -1}}` (the `{1, 1}` candidate
zeroes `x + y - 2` and is dropped); `{1/(x - 1) == 1/(y - 1), x + y == 2}` → `{}` (the
sole candidate `x = y = 1` is a pole). `Together` cancels removable factors, so
`(x^2 - 1)/(x - 1)` is treated as `x + 1`, matching `Solve`'s semantics. Pure
polynomial systems are unaffected (denominator `1`, nothing recorded).

**Tests.** `tests/solve_corpus.m` category **J** (`[D7]`, four cases: reciprocal sum,
spurious-locus prune, all-candidates-poles → `{}`, constant-denominator pin); corpus

## NMinimize / NMaximize: BasinHopping global method (2026-08-17)

Added `Method -> {"BasinHopping", …}` to `NMinimize`/`NMaximize` — a 7th global
engine alongside DifferentialEvolution, NelderMead, RandomSearch,
SimulatedAnnealing, SHGO, DualAnnealing, and DIRECT — mirroring
`scipy.optimize.basinhopping` (Monte-Carlo minimization, Wales & Doye 1997). New
engine `src/numerical_calculus/nm_basin_hopping.c`; enum `NM_BASIN_HOPPING`
dispatched from `nm_driver.c`.

- **Algorithm.** Each hop randomly displaces the current point (uniform
  `[-stepsize, stepsize]` per coordinate, clipped to the box), **locally minimizes**
  it (the "quench"), and accepts the move by a Metropolis rule on the two
  *locally-minimized* penalized energies (`Exp[-ΔE/T]`). Every `"StepInterval"`
  hops the step size is adapted toward `"TargetAcceptanceRate"` (grow to escape a
  basin, shrink otherwise) — scipy's `AdaptiveStepsize`, reproduced exactly. The
  lowest quenched point ever seen (by Deb's feasibility rules) is reported.
- **Reuses the shared driver.** The quench is the same `nm_local_polish`
  (BFGS / augmented-Lagrangian / integer descent) the other engines use, so box,
  general, disjunctive, and `Element[·, Integers]` constraints work with no
  engine-specific code — and, unlike `scipy.optimize.basinhopping` (box-only), this
  lets `Method -> {"BasinHopping"}` solve constrained and mixed-integer problems.
  `"SearchPoints" -> K` runs `K` independent multi-start hops (default 1, scipy's
  single run); `MaxIterations` is the hop count (default 100 = scipy's `niter`).
- **Sub-options** (per-method scoped, `NMinimize::optx`): `"Temperature"` (T, 1.0),
  `"StepSize"` (0.5), `"StepInterval"` (50), `"TargetAcceptanceRate"` (0.5),
  `"StepFactor"` (0.9), `"SuccessIterations"` (scipy's `niter_success`, off), plus
  generic `"SearchPoints"`/`"RandomSeed"`/`"PostProcess"`/`"PenaltyFunction"`.
- **Deliberate difference from scipy.** Mathilda quenches with its own
  well-behaved local minimizer, which does not overshoot across a basin boundary on
  its first step the way scipy's L-BFGS-B sometimes does; a single run therefore
  crosses widely-separated basins only via the random displacement (use
  `"SearchPoints"` for robustness on multi-basin problems). Conversely the
  adaptive-step walk reaches the global on some funnel landscapes (Rastrigin) where
  scipy's single run stalls.
- **Tests** `tests/test_basin_hopping.c` (`basin_hopping_tests`, 32 tests: analytic
  optima, standard multimodal benchmarks, constrained, mixed-integer, every
  sub-option, scoping, NMaximize, high-D stress, memory smoke). 0 leaks.
- **Benchmark** `benchmarks/85-basin-hopping/` vs `scipy.optimize.basinhopping`
  (default parameters, matched seed): 0 CHECK-FAIL, Mathilda faster per solve via
  the auto-compiled machine-precision objective.

Docs: `NMinimize` docstring (`src/info.c`), the method / sub-option tables and a
new `BasinHopping` subsection in `docs/spec/builtins/numerical-calculus.md`.
`$VersionNumber` bumped to 0.060.

## Sum / Product: finite numeric ranges now auto-compile to a machine loop (2026-08-17)

A finite `Sum`/`Product` with an **inexact** body — e.g.
`Sum[Sin[i^2]*1.0, {i, 1, 10^6}]` — previously fell back to the interpreter's
`evaluate()`-per-term expansion (plus a term array and a final fold). It now
compiles to a single native accumulation loop through the `Compile[]` engine
(`src/compile/`), returning the machine total in one pass. Measured ~22× on the
`Sin` body above (larger for cheaper bodies); `Compile[]` itself already lowered
`Sum`/`Product` this way — this wires the same engine into the interpreter-level
builtins.

- **Two strategies, one gate.** An integer iterator compiles the *whole*
  `Sum[body, {i, lo, hi[, di]}]` as a zero-argument program (new
  `autocompile_eval_closed`) — the compiler emits an integer-counted
  `OP_ADD_*`/`OP_MUL_*` loop. A real-bounded/real-step iterator
  (`{i, 0., 10., 0.1}`) compiles the *body* as `f(i)` and folds the machine terms
  in C, visiting exactly the interpreter's index points.
- **Exactness is preserved.** A one-term probe (`evaluate` the body once at the
  first index) engages the fast path *only* when the body is a machine number
  (`Real`, or a `Complex` of reals). Inexact-contagion then guarantees the
  interpreter's own total is a machine number too, so parity holds to machine
  precision. Exact sums stay on the interpreter and stay exact:
  `Sum[1/(i^2+i+1), {i, 1, 500}]` remains a `Rational`, `Product[i, {i, 1, 20}]`
  the bignum `20!`, `Sum[Round[i], {i, 1., 10.}]` the `Integer` `55`, and an empty
  range folds to the exact identity (`0` / `1`).
- **Large finite ranges now evaluate.** The compiled loop allocates nothing per
  term, so it is not bound by the interpreter's `10^8`-term memory cap: a
  `1.5×10^8`-term inexact sum that previously ground through the cap and returned
  unevaluated now returns the total.
- `$AutoCompilation = False` disables it (the interpreter computes the identical
  result). No `Compile[]` overflow-wrapping is ever inherited, so an int64
  accumulator overflow falls back rather than wrapping.
- Implemented in `src/sum/sum.c` (`sum_try_compiled`), `src/product/product.c`
  (`product_try_compiled`), and `src/compile/autocompile.c`
  (`autocompile_eval_closed`). Tests: seven cases in
  `tests/test_autocompile.c` (parity for both strategies, complex, exactness
  guards, the `$AutoCompilation` switch, and the inside-`Compile[]` path).

## Fix: finite Sum / Product with an index-predicate body no longer collapses (2026-08-17)

`Sum[If[EvenQ[k], k, -k], {k, 1, 10}]` gave `-55` instead of `5` (and
`Product[If[EvenQ[k], k, 1], {k, 1, 4}]` gave `1` instead of `8`). `Sum`/`Product`
are `HoldAll` and try the closed-form cascade first; that cascade evaluates the
body **symbolically**, and an integer-membership predicate of the index folds to a
definite Boolean for a symbolic index (`EvenQ[k] → False`, `SquareFreeQ[k] → True`),
collapsing the surrounding `If`/`Boole`/`Which` to one branch. The cascade then
telescoped the wrong summand exactly. (`EvenQ[k] → False` for symbolic `k` is
correct; the defect was `Sum` trusting the collapsed body.)

Fix (`src/sum/sum.c`, `src/product/product.c`): a finite explicit-integer range
whose held body applies `EvenQ`/`OddQ`/`PrimeQ`/`CompositeQ`/`PrimePowerQ`/
`IntegerQ`/`SquareFreeQ`/`CoprimeQ`/`Divisible` to a subexpression that **mentions
the iterator** now enumerates directly (which `Table` already did correctly) and
does not fall back to the closed form even when the span is too large — it is left
unevaluated rather than telescoped wrongly. A predicate applied only to constants
(`PrimeQ[7]`) folds identically per term and is left on the fast closed-form path.
`OddQ`, `PrimeQ` and the rest of the family shared the same defect and are fixed
together. Regression tests in `tests/test_sum.c` (+6) and `tests/test_product.c`
(+2); ordinary closed forms (`Sum[k^2, {k, 1, 10^7}]`, geometric, factorial)
unchanged, leaks-clean.

Not a bug: `EvenQ`/`OddQ` over a **real** compiled argument correctly decline to
compile (they are integer-only predicates) and fall back to the interpreter, which
answers `False` — verified, no change needed.

## Compile[]: Which / Switch / Piecewise now lower to bytecode (2026-08-17)

`Which`, `Switch` and `Piecewise` compile under `Compile[]` and every
auto-compilation path (`Plot`, `Table`, `NIntegrate`, `FindRoot`, …); before this
each bailed the **whole** enclosing body to the interpreter (the compilable subset
is a cliff, not a slope). All three lower to a single first-match-wins ladder — the
`If` branch structure repeated — sharing one `collect_ladder`/`emit_ladder` pair in
`src/compile/compile_emit_ctrl.c`, with matching type inference in
`compile_infer.c` (so the head types correctly inside a larger expression such as
`10 Which[…] + 1`).

- **Semantics preserved.** A literal-`True` guard becomes the unconditional final
  case and a literal-`False` guard is dropped, exactly as the interpreter reduces
  them, so a dead clause of an incompatible type does not force a fallback.
  `Piecewise` always yields a value (its explicit or implied-`0` default);
  `Switch` compares the discriminant to numeric-literal forms (or the bare `_`
  catch-all) with machine equality at the common numeric type. A run that matches
  nothing and has no catch-all aborts the compiled call and hands back to the
  interpreter — the `Null` (Which) or unevaluated `Switch` it would return anyway.
- **The `Round`/`Floor`/`Ceiling`/`IntegerPart`/`FractionalPart` group already
  compiled** — scalar (Real/Integer), rank-1 arrays, and directly over an
  `NDArray` object or a packed-`List` argument, both at the REPL (Listable
  ndkernel path) and through `Compile[]`; this was verified across all those
  shapes.
- `Switch` joined the CSE impure-head set, so a `Switch` subtree is never hoisted
  to program entry and evaluated unconditionally (its branches must stay guarded).
- **Tests.** Eleven randomised parity cases in `tests/test_compile.c` (Which /
  Switch / Piecewise standalone, nested, and inside arithmetic), plus a fix to the
  test harness: the interpreter reference now substitutes structurally
  (`replace_bindings`) instead of via `ReplaceAll`, which pre-evaluated a held
  `Switch` and collapsed it to its `_` catch-all before any value was bound. macOS
  `leaks`-clean over the compiled ladders including the interpreter-fallback path.

## Build fix: stb image decoders no longer collide with raylib at link time (2026-08-17, issue #65)

Linking `Mathilda` with `USE_GRAPHICS=1` on Linux failed with dozens of
`multiple definition of 'stbi_load' / 'stbi_failure_reason' / 'stbi_image_free' …`
errors. Both `src/imageio.o` and raylib's `libraylib.a` (`rtextures.c.o`) bake in
their own copy of the vendored `stb_image` implementation, and each exported the
`stbi_*` symbols with external linkage, so the two copies clashed. The reporter
worked around it with the linker flag `-z muldefs`, which merely silences the
error by keeping whichever definition the linker sees first — an ODR violation
that can mix two possibly-different stb versions across the program.

**Fix.** `src/imageio.c` now defines `STB_IMAGE_STATIC` / `STB_IMAGE_WRITE_STATIC`
before including the headers, giving every stb function *internal* linkage so its
code lives in `imageio.o` alone and exports no `stbi_*` symbols at all. This is
sound because `imageio.c` is the only translation unit that both defines and calls
these functions (as its file header already notes). The collision is removed at
the root with no linker flag. `-Wunused-function` is added to the file's existing
scoped `#pragma GCC diagnostic` block, since with internal linkage any stb entry
point `imageio.c` never calls becomes an "unused static function".

Verified against raylib 5.5: full `make` (USE_GRAPHICS=1) now links cleanly, all
`stbi_*` symbols in `imageio.o` are local (`nm` shows `t`, not `T`), and PNG/JPEG
`Export`/`Import` still round-trip correctly.

## NMinimize: Method sub-options are now scoped to the selected method (2026-08-17)

`NMinimize` / `NMaximize` accept a method with sub-options in the
`Method -> {"Name", "opt" -> val, …}` form. Previously the sub-option parser
`nm_parse_method` (`src/numerical_calculus/findmin.c`) was one flat, method-agnostic
`strcmp` table with no fall-through: a key belonging to a *different* method was
accepted and written into its shared config slot but never read by the selected
engine (e.g. `Method -> {"SHGO", "VisitingParameter" -> 2.5}` stored DualAnnealing's
`q_v`, which SHGO never consults), and a misspelled / scipy-style key
(`"Visit"`, `"Seed"`) or a top-level-only option placed inside the list
(`MaxIterations`) was dropped with **no diagnostic at all**. This was inconsistent
with top-level options, which already warn on an unrecognised name.

**What changed.** Each sub-option is now scoped to the method(s) that actually read
its `NmConfig` field. A new classifier `nm_option_owner` returns the owning-method
bitmask for a key (or "unknown"), and `nm_parse_method` consults it before the parse
chain: a key that is unrecognised, or valid only for another method, is reported with
`NMinimize::optx` and skipped — never stored. A helper `nm_method_name` gives the
method's display name for the message. Ownership was derived from the engines' actual
field reads, not guessed:

- **Every method** (generic): `"SearchPoints"`, `"RandomSeed"`, `"PostProcess"`,
  `"PenaltyFunction"`.
- **DifferentialEvolution + NelderMead**: `"Tolerance"`, `"InitialPoints"`.
- **DifferentialEvolution**: `"ScalingFactor"`, `"CrossProbability"`.
- **NelderMead**: `"ReflectRatio"`, `"ExpandRatio"`, `"ContractRatio"`, `"ShrinkRatio"`.
- **SimulatedAnnealing**: `"PerturbationScale"`, `"LevelIterations"`, `"BoltzmannExponent"`.
- **SHGO**: `"SamplingMethod"`, `"Iterations"`.
- **DualAnnealing**: `"VisitingParameter"`, `"AcceptanceParameter"`,
  `"InitialTemperature"`, `"RestartTemperatureRatio"`, `"LocalSearch"`.

The change is diagnostics-only: no computed result changes, and every valid
sub-option is parsed exactly as before. In particular the recently-added SHGO and
DualAnnealing methods keep every option they already honored — the fix closes the
"silently accepted a wrong-method or misspelled key" gap, it does not add or remove
any wired option.

**Tests.** `tests/test_shgo.c` and `tests/test_dual_annealing.c` each gain a
`test_option_scoping` case asserting that a cross-method key, an unknown key, and
`MaxIterations` inside the Method list are dropped (warning muted to stderr) so the
seed-deterministic result is identical to omitting them, while a valid-for-method key
is still honored.

**Docs.** `docs/spec/builtins/numerical-calculus.md` (NMinimize Method sub-options
section) now documents the per-method scoping and the `NMinimize::optx` message.

## NMinimize: DIRECT — DIviding RECTangles global optimization method (2026-08-17)

Added `Method -> "DIRECT"` to `NMinimize` / `NMaximize`: the deterministic
Lipschitzian global optimizer of Jones, Perttunen & Stuckman (1993), with the
locally-biased variant DIRECT-L of Gablonsky & Kelley (2001), reproducing the
reference `DIRECTv2.04` Fortran / `scipy.optimize.direct`.

**What it does.** `nm_direct` (new file `src/numerical_calculus/nm_direct.c`)
normalizes the search box to the unit hypercube, groups cells by an integer size
class (longest-side count for DIRECT-L, a `k·n+q` half-diagonal key for the
original variant) with one sorted linked list per class, and each iteration
subdivides the "potentially optimal" cells — the lower-right convex hull of the
`(size, value)` class minima passing Jones's epsilon improvement test — by
trisecting their longest sides. It is deterministic (no RNG) and requires only a
bounded box. Every center is scored through the shared `nm_eval` (compiled
machine-code objective + integer rounding + constraint penalty) and incumbents
chosen by `nm_better` (Deb rules), so box / general-constraint / mixed-integer
problems work unchanged; unlike `scipy.optimize.direct` (box-only) this makes
DIRECT usable on constrained problems. The raw incumbent is returned and then
polished by the driver's exact local optimizer unless `"PostProcess" -> False`.
The store is a realloc-doubled structure of arrays with O(1) head removal and
per-class sorted insertion, matching the Fortran's efficiency; zero leaks
(macOS `leaks`).

**Sub-options** (full `scipy.optimize.direct` parity, all scoped to DIRECT):
`"LocallyBiased"` (True = DIRECT-L default / False = original DIRECT),
`"Epsilon"` (eps, default 1e-4), `"MaxFunctionEvaluations"` (default 1000·n),
`"MaxIterations"` (default 1000), `"VolumeTolerance"` (1e-16),
`"LengthTolerance"` (1e-6), `"MinValue"` / `"MinValueTolerance"` (known-optimum
early stop). Wired through the method enum, `nm_method_from_string` /
`nm_method_name`, `nm_option_owner` + `nm_parse_method` (respecting the
owner/parse invariant), and the `nm_driver.c` dispatch + config defaults
(`findmin_internal.h`).

**Tests.** New `tests/test_direct.c` (`direct_tests`, 29 test groups): result
shape, convex/unimodal exact minima, the standard multimodal suite (Himmelblau,
Rastrigin, Ackley, Branin, six-hump camel, Styblinski-Tang 2-D/4-D,
Cross-in-tray, Shubert, Eggholder), DIRECT/DIRECT-L parity, constrained (disk,
Mishra's Bird), every sub-option, determinism, option scoping, 8-D sphere, a 5-D
Rastrigin stress case, and a memory-hygiene loop. All pass; zero leaks; no
regression in the sibling `shgo_tests` / `dual_annealing_tests` /
`nminimize_tests`.

**Benchmark.** `benchmarks/83-direct` races `scipy.optimize.direct` on nine
standard bounded multimodal problems (raw-vs-raw, scipy defaults): identical
basin on all nine (0 CHECK-FAIL), Mathilda AHEAD on all nine, ~1.5×–20× faster
per solve (its compiled objective avoids scipy's Python-callback-per-evaluation).

**Testbed benchmark.** `benchmarks/84-direct-testbed` sweeps the whole
`tests/test_nminimize.c` corpus through DIRECT with per-problem parameterisation.
The `.m`/`.py` race is the raceable subset — 18 continuous box-bounded problems
(1-D to 10-D: quartic, Gamma, Schwefel, Schaffer, Eggholder, Griewank-5/10,
scaled-quadratic, Katsuura, Rastrigin-5/8, Rosenbrock-10, modified Ackley,
Gaussian well, …): 0 CHECK-FAIL, 15 of 18 AHEAD (up to 11× on the origin-centred
high-D globals). The three losses are objective-evaluation cost, not the DIRECT
algorithm — two cheap few-hundred-eval objectives, and Katsuura-8D (29×), whose
`Round`/nested-`Sum` objective does not take the compiled fast path (a
compile-coverage gap that would slow any method equally). The README additionally
documents the non-raceable remainder: `Method -> "DIRECT"` solves 16 constrained
/ equality / disjunctive / small-integer corpus problems that scipy's box-only
`direct` cannot express (disk −4.2426, LP 3.25, equality 2.333, Himmelblau-over-
two-disks 0, integer LP 1, …), and the high-D-equality A-series and combinatorial
B-series are documented as beyond DIRECT in either system (solved by Mathilda's
DE / SLSQP / integer engines).

**Portability.** Fixed a pre-existing latent Linux-portability bug surfaced by
`make check-c99`: `src/numerical_calculus/nm_dual_annealing.c` used `M_PI`
without the C99 `#ifndef` fallback (glibc hides it under `-std=c99`); added the
guard.

**Docs.** `src/info.c` NMinimize docstring (Methods + sub-options),
`docs/spec/builtins/numerical-calculus.md` (Methods-table row, eight sub-option
rows, and a dedicated `#### DIRECT` subsection with algorithm, fidelity note,
worked examples, and benchmark results).

## Vector analysis: Grad, Div, Curl, Laplacian (2026-08-17)

operator is assembled as a Mathilda expression built out of `D[...]` and reduced
with a single `evaluate()`, so all four inherit every rule `D` already knows.

- **Grad** `Grad[f, {x1,...,xn}]` is exactly `D[f, {{x1,...,xn}}]` — the
  interpreter's array derivative already appends a new innermost tensor slot, so
  a scalar yields a vector, a vector field its Jacobian, a rank-`k` array a
  rank-`(k+1)` array.
- **Div** contracts the innermost slot of `f` against the variables:
  `Sum_i D[f_i, x_i]` for a vector, mapping over the outer structure for a
  tensor (rank-`k` → rank-`(k-1)`).
- **Curl** uses the generalized Levi-Civita form
  `(1/k!) Sum eps_{a.. i j..} d_{x_i} f_{j..}` (`k = depth f`, result depth
  `n-k-1`), covering 2-D vector → scalar, 3-D vector → vector, and rank-2
  tensor → scalar in one code path.
- **Laplacian** `Sum_i D[f, {x_i, 2}]`, applied element-wise over an array
  (result keeps `f`'s dimensions).

**Coordinate charts.** A 3-argument form computes in the orthonormal (physical)
basis of an orthogonal chart via its scale factors (Lamé coefficients): supported
charts are `"Cartesian"`, `"Polar"` (2-D), `"Cylindrical"` (3-D), `"Spherical"`
(3-D). Grad of a scalar `(1/h_i) D[f, x_i]`; Div of a vector
`(1/J) Sum_i D[(J/h_i) f_i, x_i]`; Laplacian of a scalar
`(1/J) Sum_i D[(J/h_i^2) D[f, x_i], x_i]`; Curl of a vector
`(1/(h_j h_k))[D[h_k f_k, x_j] - D[h_j f_j, x_k]]` (2-D scalar / 3-D vector).
Field ranks that would require Christoffel symbols in a curvilinear chart (tensor
fields, the vector Laplacian, the gradient of a vector field) and unrecognized
charts are left unevaluated; an unknown chart also emits `Head::chart`.

Verified against Wolfram Language reference outputs — Cartesian scalar/vector/
tensor forms match exactly (including the rank-2 tensor curl
`1/2 (x^3 - 3 x y^2 - 3 x^2 y^2 + 2 x y^3)`), and the Polar/Cylindrical/Spherical
scalar and vector examples reproduce (e.g. `Div[{r Sin[t], -r Cos[t]}, {r, t},
"Polar"]` → `3 Sin[t]`, `-Grad[k q/r, {r, t, p}, "Spherical"]` →
`{k q/r^2, 0, 0}`). New suite `tests/test_vectoranal.c` (10 groups); valgrind
shows no leaks beyond the `core_init` startup baseline; `make check-c99` clean.

## `Solve[…, Integers]`: `Solve::svars` diagnostic + Booker three-cubes reach

**`Solve::svars` diagnostic.** When an integer system carries a symbol in an
inequality/ordering constraint (`… && d > 0 && d < 100000`) that is *not* among
the solve variables — almost always a mistyped variable list, e.g. the `d`
dropped from `{x, y, z, y}` — `Solve` now emits `Solve::svars` instead of
silently declining. Operator heads and named constants are `Protected` and skip
the check, so only genuine variable-like symbols trip it; a bare parameter in an
*equation* (`a x == b`) is not flagged. Emitted once per system (deduped against
the evaluator's fixed-point confirm pass).

**Booker cube-root-mod-d for `x^3 + y^3 + z^3 == k`.** The classical divisor
method (`si_two_power_solve`) LINEARLY enumerates the third variable and factors
the ~B³ value `k − c³`, capping the reachable coordinate range at the ~3×10⁵
outer budget. Following A. R. Booker's "Cracking the problem with 33", the new
path instead enumerates the SMALL divisor `d = |a+b|` up to `α·B` (α = ∛2 − 1)
and solves the cube-root congruence `c³ ≡ k (mod d)` to pin `c` to arithmetic
progressions, recovering `{a,b}` in closed form from
`{a,b} = (sgn(m)·d ± √((4|m|/d − d²)/3))/2`. This lifts the reachable coordinate
range from ~3×10⁵ toward ~10⁶: `Solve[x^3+y^3+z^3==2 && -200000<=x,y,z<=200000,
…, Integers]` (2B = 4×10⁵, which the classical path declines) now returns all
195 solutions — including `(162001, −161999, −5400)` — in ~0.4 s.
Completeness across three roles: solutions with a coordinate ≤ `⌊k^{1/3}⌋` are
found by part 1 (small-coordinate enumeration + divisor-solve, covering the
`(a,−a,∛k)` family), the rest by Booker's α-bound in part 2. The core primitive
— all cube roots of `k` modulo `d` (factor + per-prime-power roots, analytic
Pohlig-Hellman in the 3-Sylow for large primes `p ≡ 1 mod 3`, brute for prime
powers, CRT product) — is exposed for testing as `Solve\`CubeRootsMod[k, d]` and
verified against brute force over 94 000+ `(k, d)` pairs. The Booker driver is
cross-checked against exhaustive box enumeration over 801 targets `k` (zero
mismatches), gated to `|k| < ~10⁹` and declines (rather than materialising a
huge parametric family) when a box would hold more than 200 000 tuples.
Alongside, `build_result`'s solution sort was upgraded from O(n²) selection sort
to O(n log n) `qsort`, so large integer solution sets no longer blow up.
Regressions green: `solve_integers_tests`, `solve_tests`, `solve_corpus_tests`
(0/97 non-PASS); `make check-c99` clean; no new valgrind leaks.

**SPF sieve + 128-bit reach.** The divisor enumeration now factors each `d` via a
smallest-prime-factor sieve built once per solve (`si_build_spf`, sized to
`Dmax`) — O(log d) per divisor instead of O(√d) trial division — and the
part-2 coordinate arithmetic moved to `__int128` (v³ overflows int64 past
v ≈ 2.1×10⁶) with a 128-bit `isqrt`. With `SI_BK_DMAX` raised to 3×10⁶ and a
1×10⁹-candidate backstop (`SI_BK_MAXNODES`, so an oversized box declines rather
than runs for minutes), the reachable coordinate range grows from ~1×10⁶ to
~1×10⁷: `x^3+y^3+z^3==2` returns the coordinate **5 821 795** (box radius 6×10⁶)
in ~16 s, and coordinate 1 971 055 (radius 2×10⁶) in ~4 s — all verified, still
complete, correctness re-checked (801-target box cross-check and 45 149-pair
primitive check both 0 mismatches).

**Signed three-cube normalisation (`x^3 + y^3 - z^3 == k`, …).** The three-cube
detector now accepts coefficient `±1` on each cube, not just `+1`: a variable
with `-v^3` is handled by the substitution `u = -v` (mirror its box), which
turns any `± x^3 ± y^3 ± z^3 == k` over a pure box into the pure sum
`u_x^3 + u_y^3 + u_z^3 == k` that the Booker path already solves — a
preprocessing/normalisation of the equation (already in MPoly form) to a shape
the machinery attacks. This makes the classic 1950s representation reachable:
`Solve[x^3 + y^3 - z^3 == 227 && -200000 <= x,y,z <= 200000, …, Integers]` returns
`(24579, 51748, 53534)` (and its symmetries) in ~0.9 s — i.e. `227 = 24579^3 +
51748^3 - 53534^3`. Candidates are enumerated in `u`-space and mapped back to the
original variables; the substitution is gated to a pure box (no
orderings/disequations) so it stays exact. All four sign patterns cross-checked
against exhaustive box enumeration (0 mismatches); the all-`+` path is unchanged
(801-target check still 0); `make check-c99` clean; no new valgrind leaks.

**Fermat's Last Theorem short-circuit.** `x^n + y^n == z^n` (n >= 3, equal
coefficient magnitudes, no constant term) with `x, y, z` all strictly positive
has no solutions (Wiles 1995), so `Solve[..., Integers]` now returns `{}`
immediately — before any search, and independently of any upper bound, so the
unbounded "indefinite" form is decided too:
`Solve[x^3+y^3==z^3 && z>x>y>0 && x,y,z<10000, {x,y,z}, Integers]` drops from
~2.6 s of enumeration to ~0.4 ms, and `Solve[x^3+y^3==z^3 && x>0&&y>0&&z>0, …]`
(no box) returns `{}` in ~0.1 ms instead of declining. Detection is on the
normalised equation MPoly (`si_solve_fermat`): it fires only for the exact
`a^n+b^n==c^n` shape with all three lower bounds `>= 1`, so `n = 2` still returns
its Pythagorean triples, `x^3+y^3==z^3+1` (k != 0) still solves normally, and a
box that admits `0`/negatives still enumerates the `(0, a, a)` family.
