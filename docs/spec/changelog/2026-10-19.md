# Changelog: week of 2026-10-19 (Mon) – 2026-10-25 (Sun)

## A power of a product splits in a product ; v0.6005

- **`Times` now splits off the positive numeric factors of a power of a
  product** when the exponent is not a number, as the reference does.
  `y (2 x)^b` is `2^b x^b y` and `(2 x)^b (2 x)^c` is `2^(b+c) x^(b+c)`.
  - A negative number contributes its absolute value (`(-2 x)^b` gives
    `2^b (-x)^b`), and so does a pure-imaginary coefficient.
  - `(x/2)^b` gives `2^-b`.
  - An all-numeric base splits only to combine with another factor:
    `Pi^(D/2) (2 Pi)^-D` is `2^-D Pi^(-D/2)`, the form FeynCalc's
    `FCFeynmanParametrize` tests expect, while `y (2 Pi)^b` stays.
  - A lone `(2 x)^b` stays.
  - All 46 probes match the reference.
- **The Mellin cleanup no longer shifts an isolated Gamma.** `fullsimp2` in
  `integrate_ramanujan.c` had offered `Gamma[z + n] -> Pochhammer[z, n]
  Gamma[z]` for every Gamma and kept whichever form had fewer leaves. With the
  split, `Gamma[1 - s/2]` won as `(-s/2) Gamma[-s/2]`. That form has a
  removable singularity, so the Weber-Schafheitlin integral read 0 instead of
  0.2122 at `s = 0`. The shift is now offered only to a Gamma whose argument
  differs by an integer from another one, the only kind that can cancel.

## NValues; N[x, {p, a}] ; v0.6004

- **N-values are now `NValues`, not UpValues.** This covers `N[x] = v`,
  `x /: N[x] = v`, `N[x] ^= v` and `N[f[x_], p_] := ...`. `NValues[x]` lists
  them, `NValues[x] = {...}` replaces them, and `Clear` removes them. As in the
  reference, an `N[x]` rule is stored, and matched by machine `N`, as
  `N[x, {MachinePrecision, MachinePrecision}] :> v`. `UpValues[Zeta2]` in
  FeynCalc now lists only the `Conjugate` rule. That fixes the last five of
  the `SharedObjectsUpValues` failures.
- **`N[expr, {p, a}]`** takes a precision goal and an accuracy goal. The
  precision goal decides, or the accuracy goal when `p` is `Infinity`.
- **`N` is no longer `Listable`.** The reference's `N` is only `Protected`.
  `N[Pi, {MachinePrecision, MachinePrecision}]` had threaded into
  `{3.14159, 3.14159}`. Lists still numericalize element-wise, and packed
  arrays keep their fast path.

## PolynomialGCD and Cancel over compound variables ; v0.6003

- **`PolynomialGCD` over compound variables now finds common factors.**
  - Variables like `x[i]` and `Pair[p, q]` are now opaque generators for the
    FLINT GCD and exact-division paths, as symbols are and as in the
    reference.
  - The FLINT path used to accept only symbols, so such inputs fell to the
    classical GCD. On some sizes that answered `1`: the GCD of
    `Expand[(x[3]+x[6]+x[8]+x[9]) q]` and `x[3]+x[6]+x[8]+x[9]`, where `q` is
    a five-term polynomial in `x[1]` … `x[5]` and `a`. That was a wrong value.
  - Each distinct node is replaced by a private symbol for the computation and
    put back afterwards.
  - A node is abstracted only when it is independent: not a numeric constant
    (`AlgebraicNumber[..]`, `Root[..]` and `Sin[1]` obey algebraic relations),
    and with no argument symbol that is also an ordinary variable (`Sin[x]`
    beside `x`). Otherwise the input takes the path it always did.
- **`Cancel` and `Together` therefore cancel such fractions.** FeynCalc's
  `FCFeynmanPrepare` had been carrying a 3854-leaf uncancelled `Together`
  result where the reference has 1106 leaves, and then stalled.
- **`Cancel`'s exact quotient is now expanded.** It is no longer left in the
  recursive form of the classical division
  (`(a x[1] + a x[2]) x[3] x[4] + ...`).

## Comparisons with Infinity ; v0.6002

- **`Less`, `LessEqual`, `Greater` and `GreaterEqual` now decide on the real
  infinities.** `0 < Infinity`, `Pi < Infinity`, `-Infinity < 0` and
  `Infinity <= Infinity` are `True`, and `Infinity < Infinity` is `False`,
  matching the reference on every probe. They used to stay unevaluated.
  `ComplexInfinity`, `I Infinity` and a symbolic other side still stay
  unevaluated.
- **FeynCalc's loop guards depend on this.** Its `MaxIterations -> Infinity`
  defaults test `counter < Infinity` in `NestWhileList`, which stopped after
  one element. That fed `StringRiffle::list` into the `FCLoopFindSubtopologies`
  / `FCLoopFindTopologyMappings` / `FCLoopFindMomentumShifts` failures.

## Linear box syntax ; v0.6001

- **`\!\( ... \)`, `\( ... \)` and `\*Box[...]` now parse**, in source and
  inside a string given to `ToExpression`. The boxes read as the expressions
  they display: `SuperscriptBox`, `SubscriptBox`, `FractionBox`, `SqrtBox`,
  `RowBox`, and the `FormBox`/`StyleBox`/`TagBox`/`InterpretationBox`
  wrappers (`src/linear_boxes.c`). FeynCalc's tests write powers and fractions
  copied from a notebook this way, and 48 of them failed with
  `ToExpression::sntx`.
- **A string literal now keeps `\!`, `\(`, `\)`, `\*` and the other box
  escapes** as the reference's private-use characters (U+F7C0–U+F7CD).
  Previously the backslash was dropped, so `"\(x\)"` was `"(x)"`. Every form
  prints them back as escapes.

## Return from a definition ; v0.600

- **A definition is now a `Return` boundary.** When an own, down, sub or up
  value's evaluated right-hand side is `Return[v]`, it yields `v`, as in the
  reference: `f[x_] := If[x > 0, Return[1], 2]` gives `f[3] = 1`.
- **This fixes a wrong value that came with no message.**
  - The literal `Return[v]` used to leak out. FeynCalc's
    `cartesianIntegralQ[ex_] := Which[..., Return[True], ...]` therefore read
    as not `TrueQ`, and every Cartesian integral took the Lorentz branch.
  - All 13 `FCLoopBasisIncompleteQ` / `FCLoopBasisFindCompletion` aborts were
    this bug.
- **Only one top-level `Return` is stripped**, as the reference does:
  `Return[x] + 1` and `{Return[x]}` keep it, and `Return[Return[x]]` gives
  `Return[x]`.
- **Only rules whose right-hand side mentions `Return` pay for this.** A flag
  is computed when the rule is stored, and only then is the result evaluated
  at the rule boundary.

## FormatValues: Format and tagged MakeBoxes rules ; v0.599

- **`FormatValues[f]`** is new, with `FormatValues[f] = {...}`,
  `FormatValues[f] =.` and clearing by `Clear`/`ClearAll`. It holds a symbol's
  display rules (a new `SymbolDef` list).
- **`f /: MakeBoxes[lhs, form] := ...` and `f /: Format[lhs] := ...` now define
  FormatValues.** They used to be stored as UpValues, so `UpValues[f]` listed
  typesetting rules the reference keeps elsewhere. FeynCalc's
  `SharedObjectsUpValues` tests check exactly this: 92 of their 97 failures
  are fixed. The other five are N-values, which the reference keeps in
  `NValues` and Mathilda in UpValues.
- **An untagged `Format[expr] := rhs`** is no longer a DownValue of `Format`.
  It stores the reference's two rules on `expr`'s symbol (a `MakeBoxes` rule
  and the plain rule); `Format[expr, OutputForm]` stores only the plain rule.
- **Display.** `ToString` (OutputForm) and the REPL's `Out[]` apply the plain
  rules, inside holds too. Rewrites are formatted again, and a rule that keeps
  reproducing a match stops with `Format::forml`. `InputForm`, `FullForm`,
  evaluation and a script's `Print` (as in `wolframscript`) are unaffected.
- **`Format`, `FormatValues` and `MakeBoxes` are `System` symbols** with the
  reference's attributes (`Protected`; `HoldAll`, `Protected`;
  `HoldAllComplete`). `MakeBoxes` used to be created in whatever context first
  mentioned it.

## Multinomial; Binomial's negative and half-integer closed forms ; v0.598

- **`Multinomial[n1, n2, ...]`** is new (`src/numbertheory/multinomial.c`).
  It is `Listable`, `NumericFunction`, `Orderless` and `Protected`. It
  evaluates as the product of binomials over the partial sums of the sorted
  arguments. Exact zeros drop out, two arguments give `Binomial[n1 + n2, n2]`,
  and three or more give the product only when at most one argument is
  symbolic and at most one binomial stays unevaluated. These declines were
  measured against the reference (`Multinomial[2, a, b]` stays,
  `Multinomial[2, 3, 4, a] = 1260 Binomial[9 + a, a]`). `Compile[]` lowers it
  to the same product. FeynCalc's `PaVeUVPart` used it on every call: 137 of
  its 139 failing tests now pass.
- **`Binomial` with both indices negative** follows the reference. The poles
  cancel for `m ≤ n`: `Binomial[-1, -1]` was `0` and is now `1`, and
  `Binomial[-2, -5]` is `-4`.
- **`Binomial` of exact rationals.**
  - When `m` or `n - m` is a negative integer and `n` is not, the result is
    `0` (`Binomial[1/3, 4/3]`).
  - When `n`, `m` and `n - m` are all multiples of `1/2`, the result is closed
    over `Sqrt[Pi]`: `Binomial[0, 1/2] = 2/Pi`. If `n` is also a negative
    integer, it is `ComplexInfinity`.
  - These cases were left unevaluated before.
- **`Binomial` expands a symbolic `n` only up to `k = 5`**, as the reference
  does. `Binomial[a + 6, a]` and `Binomial[a, 6]` now stay; an explicit-number
  `n` still expands to 32. `Binomial[2^70 + 1, 2^70]` now evaluates, because
  the smaller of `m` and `n - m` is used.

## Canonical order is the reference's ; v0.597

`Sort`, `Order`, `OrderedQ`, `Ordering` and every `Orderless` head, including
`Plus` and `Times`, now order expressions as the reference does. This replaces
the polynomial-degree-vector order (`src/sort.c` `expr_compare`). The rules
were measured against the reference one by one. On random lists, the
reference's `Ordering` is reproduced on 400 of 400 and on 567 of 569 held-out
cases; the two misses differ in evaluation, not in order.

- **Numbers first, by value.**
  - A complex number orders by its real part, then the size of its imaginary
    part, negative first: `-1 < -1 - I < 0 < -I < I < 1 < 1 - I < 1 + I`.
  - Equal values put Integer before Real before Rational.
- **Products** compare their non-numeric factors from the last one backwards,
  then their coefficients: `-2 x < -x < x < 2 x < x^2`, and `b < a x`.
- **Powers** compare base, then exponent: `x^-1 < Sqrt[x] < x < x^2 < x^n`.
- **Sums** compare their terms like products. A power is compared before a sum
  (`x^2 < a + x`), and a product before both.
- **Atoms come before compound expressions**, and strings before symbols.
- **Symbols** use the string collation, so case folds: `a < A < b < B`.
  `Plus`/`Times` therefore print `a b C d`, where they used to print
  `C a b d`.
- **Other expressions** compare head, then length, then arguments:
  `f[b] < f[a, b] < g[a] < f[x][a]`, and `{b} < {a, b}`.
- `Infinity` and `ComplexInfinity` order as `DirectedInfinity[1]` and
  `DirectedInfinity[]`.
- **Order-dependent code fixed along the way.**
  - `Solve` of a polynomial system lists its solutions by their values in
    variable order. It used to list them in the order of the last variable's
    roots.
  - `SolveAlways` gives its rules in variable order.
  - **A wrong answer fixed in the Meijer-G convolution**
    (`src/internal/MeijerConvolution.m`).
    - Two oscillating kernels of different frequency, such as
      `BesselJ[m, a x] BesselJ[n, b x]`, make the integral discontinuous
      where the frequencies cross (Weber-Schafheitlin). The theorem's G holds
      only on the side where its argument is below 1.
    - The stage used to trust whichever factor came first. With the factors
      swapped, Mathar M12237 gave -0.184 for 0.1105.
    - It now builds both orientations and returns a `Piecewise` on the side,
      or the one branch the assumptions decide.
  - `Factor[x^10 - 1]`, `FactorList` with extensions and others now print
    their factors in the reference's order.
- **`Simplify` no longer relied on term order to finish the Struve ODE
  identities.**
  - Its power-distribution transform now treats a positive Rational as a
    positive constant (`(z/2)^(4/3)` splits).
  - A final polish applies that transform to the reassembled result and keeps
    it on a strict improvement. The bottom-up pass simplifies each part, but
    `-4 (z/2)^(4/3) + 2^(2/3) z^(4/3)` only cancels at the top level
    (`src/simp/simp_power.c`, `src/simp/simp_builtins.c`).
- **Faster.** The per-sort symbol-set memo, the degree walk and the
  `sort_abort_reset` hook are gone. Sorting 10^5 mixed polynomial terms takes
  1.6 s against 2.5 s before.
- Several hundred unit-test expectations encoded the old order. Each change
  was checked as a pure reordering against the reference
  (`ToExpression[old] === ToExpression[new]`), and the FullForm cases against
  the reference's own argument order.

## PossibleZeroQ: an exact huge-scale point climbs every rung ; v0.596

- **The v0.593 fix stopped at the first rung that did not shrink**
  (`src/zero_test.c` `decide_numeric_huge_scale`).
  - At `|x| ~ 60` the cancellation of `(1 - Tanh[x/2]^2)^3` needs about 400
    bits. The 200-bit rung therefore still shows the uncancelled value, which
    was read as a plateau of the true value, so `False`.
  - On an exact point the ladder now climbs every rung and decides on the top
    two. A zero still falls at least half as fast as the bits added; a
    genuine value holds.
  - The shifted Weierstrass round-trips
    `D[F[x + k], x] - Cosh[x + k] Cosh[2 x + 2 k]` are `True` for every
    `k = 1..20`, whatever order the terms come in. `k = 3` and `k = 8` failed
    once the canonical order moved the sample points.
- The constant controls improved too: the residual plus `10^-2` or `10^-6` is
  now `False`, as in the reference; it was `True`.
- Not fixed: the residual plus `10^-12` is `True`. A machine-real point on
  the moderate-scale path cannot gain precision either, and there a
  residual that never shrinks is leniently read as zero. That leniency was
  already documented.
- Test: `tests/test_zero_test.c` (the shift family widened to `k = 1..20`).

## Refine/Simplify assumption rules no longer capture user symbols named like their pattern variables ; v0.595

- **A wrong answer for any variable named `r`, `p`, `rest`, `base`, `c`, `m` or
  `k`.** `Refine[1/Sqrt[r^2], r > 0]` was `-2`, `Refine[Log[p^3], p > 0]` was
  `3 Log[3]`, and `Refine[Sqrt[rest^2 y^2], rest > 0]` was `y^2 Sqrt[y^2]`.
  The same wrong values reached `Simplify[..., assumptions]` and every
  stage that refines under assumptions.
- **Cause.** The per-symbol assumption rules (`src/simp/simp_assume_rewrite.c`
  `apply_assumption_rules`) are built as text with the user's symbols pasted
  in. A user symbol `r` turned `Power[Power[r, 2], r_] :> Power[r, 2 r]` into
  a rule whose right side reused the binding.
- **Fix.** Every pattern variable now lives in the `AssumeRules`` context, which
  no user symbol shares. The rule buffer grows to 32 KB for the longer names.
  The Kovacic de-obfuscation rule (`src/calculus/dsolve_kovacic.c`), which
  pastes the ODE's independent variable, gets the same treatment, so an ODE in
  `r` or `p` is safe.
- Found while checking the canonical-order change: the Bessel-product
  convolution, taken in the other factor order, produced `Sqrt[r^2]`.
- Test: `tests/test_refine.c` (`test_pattern_name_capture`).

## Times merges numeric bases under one symbolic exponent ; v0.594

- `2^a 3^a` is `6^a`, `3^-a 5^a` is `(5/3)^a`, `2^a 3^a 5^-a` is `(6/5)^a`,
  `Sinh[1]^a Cosh[1]^-a` is `Tanh[1]^a` and `(-2)^a 3^a` is `(-6)^a`, as in
  the reference (`src/times.c`, after the radical fusion).
- **Which factors merge.** The exponents must be equal or exactly opposite and
  non-numeric, and every base a numeric quantity. A merged group admits at most
  one base that is not a positive real, so `(-2)^a (-3)^a` stays.
  - A base counts as positive when that is provable, or when it is a numeric
    quantity whose machine value is a real clear of zero (`Sinh[1]`, `Log[2]`).
- **Which exponent the merged power keeps.**
  - The exponent of a non-positive base, if the group has one, since only a
    positive base may be inverted.
  - Otherwise, if every exponent agrees, that exponent (`3^-a 5^-a` is
    `15^(-a)`).
  - Otherwise the sign without a negative leading coefficient.
- A power of a product is never split again, so the merge cannot cycle.
- `Simplify[Sinh[1]^a (1 + Cosh[1])^(-a)]` no longer depends on factor order to
  reach `Tanh[1/2]^a`.
- Test: `tests/test_eval.c` (`test_numeric_base_power_merge_v594`).

## PossibleZeroQ: huge-scale points climb the ladder on their exact value ; v0.593

- **The precision ladder now gains precision at a machine-real sample point**
  (`src/zero_test.c` `decide_numeric_huge_scale`, `zt_exactify_reals`).
  - The sampler draws its points as machine reals. At a huge operand scale
    the point goes up the MPFR ladder, but a machine number stays one under
    `N`, so every rung recomputed the same rounded point. The cancellation
    noise then plateaued and was read as a non-zero.
  - The ladder now runs on the point's exact dyadic value. A residual that
    keeps falling at least half as fast as the bits added, through the top
    rung, is a zero, even when its cancellation is deeper than the floor
    allows (`1 - Tanh[x/2]^2` at `|x| ~ 34` costs about 100 bits).
  - Example: `PossibleZeroQ[D[F[x + k], x] - Cosh[x + k] Cosh[2 x + 2 k]]`,
    with `F` the Weierstrass antiderivative of `Cosh[x] Cosh[2 x]`, was
    `False` for half of `k = 1..10`.
- Found while checking the new canonical order: the sample seed comes from
  the expression's hash, so reordering the terms moved the points onto a bad
  one.
- Not fixed, recorded: adding a constant below about `10^-2` to the same
  residual is still read as zero, because every draw lands where the scale is
  about `10^40`.
- Test: `tests/test_zero_test.c` (`test_huge_cancel_machine_point_exact_climb`).


## FeynCalc triage, batch 2: `Sequence` substitution, nested option lists, `Coefficient` ; v0.592

- **Substitution splices a `Sequence` only where a pattern variable's value
  goes** (`src/match.c` `rb_rec`): `f[x__] := HoldComplete[x]` gives
  `HoldComplete[1, 2]`.
  - A literal `Sequence[...]` written in the replacement is left to the
    evaluator, which keeps it under `Unevaluated` and `HoldComplete`.
  - Before, `If[c, {i}, Unevaluated[Sequence[]]]` in a definition's body came
    out as `Unevaluated[]`, so a `Table` over it gave `{Unevaluated[], ...}`
    instead of `{}`, and `HoldComplete[Sequence[], n]` lost its `Sequence[]`.
  - FeynCalc's topology functions (FCLoopFindTensorBasis,
    FCLoopFindSubtopologies, FCLoopFindMomentumShifts, ...) build their lists
    this way.
- **Nested option lists.**
  - `OptionValue[f, {{a -> 1}}, a]` is `1` (`src/options_builtin.c`).
  - `OptionsPattern[]` matches `{{a -> 5}}` (`src/match.c`).
  - Since v0.591 a named `OptionsPattern` binds the arguments as written, so a
    rule guard re-reading its own options sees nested lists. FeynCalc's
    `LeviCivita[x..., opts1:OptionsPattern[]][y..., opts2:OptionsPattern[]]`
    rule recursed without end until these were fixed.
- **`Coefficient`, as in the reference** (`src/poly/poly.c`):
  - Negative orders: `Coefficient[a/x, x, -1]` is `a`, and an `x^-1` term no
    longer counts as `x^0`.
  - A term with the form in a denominator (`x/(1 + x)`) has no coefficient.
  - Factors free of the form come out first, and the rest is expanded only in
    the form: `Coefficient[(a l^2 + b l^2 + c)/d, l, 2]` is `(a + b)/d`.
  - FeynCalc's `FCFeynmanPrepare` failed its "Q and J are incorrect" check
    without this, aborting about 20 loop-integral tests.
- Every case was checked against the reference. Tests: `tests/test_eval.c`
  (`test_sequence_substitution_v592`, `test_coefficient_v592`).
- **`TimeConstrained` no longer crashes a session when its timeout lands
  inside `malloc`** (`src/core.c` `tc_sigprof_handler`, new
  `src/tc_unwind_safe.c`).
  - At the deadline, the SIGPROF handler first only records the timeout and
    gives the computation 50 ms of CPU to reach a safe point. The safe points
    are the evaluator's per-step poll and the guarded GMP allocators.
  - When that grace runs out (a long C loop, such as one match over a
    50,000-term sum), the handler checks the interrupted stack before
    unwinding. It reads the PC and the frame-pointer chain from the signal
    context, and defers by 1 ms while any frame lies in the allocator, the C
    library or pthread. The image ranges are recorded at startup:
    libsystem_malloc, _platform, _c and _pthread on macOS, libc on Linux.
    A signal taken on a worker thread is deferred too.
  - Before, only GMP allocations were guarded. A jump out of a plain `free`
    left the allocator's lock held, so the next allocation trapped
    (`Illegal instruction: 4`). A loop of timed-out `Sum`/`Expand`/`Table`
    bodies crashed 3 runs in 4. FeynCalc's Lorentz tests died this way after
    the 50,000-term `DummyIndexFreeQ` test timed out, losing the 880 tests
    after it.
  - Test: `tests/test_time_constrained.c`
    (`test_tc_abort_mid_allocation_stress`).

## FeynCalc triage, batch 1: sign distribution, flat-chain parsing, `HoldPattern` definitions, N-values, indexed iterators, valued pattern heads, `OptionsPattern` guards ; v0.591

The first ranked triage of FeynCalc's unit tests named these kernel root
causes. Every behaviour below was checked against the reference.

- **`-(x + y)` distributes.**
  - **Times rule:** a product of exactly a `-1` or `-1/n` coefficient and a sum
    distributes the sign (`src/times.c`): `-(-1 + x)` is `1 - x` and
    `Times[-1/2, x + y]` is `(-x - y)/2`. `Times[-1, x + y, z]`, `-3/2`, `-1.`
    and `-(x + y)^2` stay.
  - **Parser:** a flat chain (`+`, `*`, `**`, `<>`) flattens only what it built
    itself (`src/parse.c`):
    - `(a b) c`, `Times[a, b] c` and `-(x + y) z` keep their inner node.
    - `a - b c` puts the `-1` into the bare product.
  - FeynCalc's `Factor2` builds `-Plus[...]` and relies on this (about 230
    tests).
  - **Normal forms that leaned on the old shape**, fixed at the root:
    - `Root` keeps a positive leading coefficient, as the reference does
      (`src/root.c`).
    - A negative exact coefficient under a rational power comes out as its
      magnitude (`src/power.c`): `Sqrt[-4 (1 - x^2)]` is `2 Sqrt[-1 + x^2]`, so
      `Solve[1 - x^2 + y^2 == 0, y]` is `y -> ±Sqrt[-1 + x^2]`.
    - `FactorList` reports the `-1` of a factor whose sign the product
      absorbed (`src/poly/facpoly_list.c`): `FactorList[-x - 1]` is
      `{{-1, 1}, {1 + x, 1}}`.
    - Series coefficients that vanish only once expanded are recognised
      (`src/calculus/series.c`): `Series[Beta[s, 1], {s, 0, 1}]` is
      `1/s + O[s]^2`.
    - `FunctionExpand` drops the conjugate PolyLog pairs that cancel
      (`src/special_functions/functionexpand.c`).
- **`HoldPattern[f[...]] := rhs` is a rule for `f`.** It used to land silently
  on `HoldPattern` (`src/eval.c`). FeynCalc's `DataType` default and its `SUNF`
  rules are written this way.
  - A protected tag gives `Set::write`, as in the reference.
- **N-values.** `N` applies an `N` rule attached to a symbol or head anywhere
  in an expression (`src/numeric.c`), and `N[x] = v` stores one.
- **Indexed iterator variables.** In `Table`, `Do`, `Sum` and `Product`, the
  variable can be `v[k]` (`Table[ll[1], {ll[1], 0, 2}]`): each step binds the
  DownValue `v[k] = value`, which is restored afterwards (`src/iter.c`).
  FeynCalc's PaVe reduction loops this way (about 195 tests).
- **A head symbol with a value inside a definition's pattern is evaluated:**
  `DOT = Dot; f[DOT[a_, b_]] := ...` is a rule on `Dot` (`src/eval.c`). This
  explains about 300 Dirac tests (GordonSimplify, Anti5, ...).
- **`OptionsPattern`** (`src/match.c`): `(opts:OptionsPattern[]) /; test` now
  matches, and a named `OptionsPattern` binds the arguments as written. Used by
  `Isolate`, `DiracOrder` and others (about 120 tests).
- **Lexer:** an `e` exponent needs digits after it. `2ep` was the Real `2.`
  times `p`; it is `2 ep`, while `2e5` is still `200000.`, a Mathilda
  extension.
- Tests: `tests/test_parse.c` (`test_flat_chain_provenance`) and
  `tests/test_eval.c` (`test_feyncalc_semantics_v591`,
  `test_sign_normal_forms_v591`). Several test expectations that encoded the
  old forms now hold the reference's: `D[BesselK]`, `LucasL[-7, x]`,

## `Check` and `Quiet` nest as in the reference; `Quiet[expr, msgs]` and `Check[expr, f, msgs]` honour their message lists ; v0.588

`Check[Quiet[1/0]; 5, 7]` was `7`. `Check` counted every message, including
those silenced by a `Quiet` inside it; the reference gives `5`. `Quiet[expr,
spec]` silenced every message whatever `spec` named, and `Check`'s third
argument was ignored. FeynCalc wraps internal probes in `Quiet` inside
`Check`, so its error paths fired spuriously.

- **Frame model** (`src/message.c`). Active `Quiet`s and `Check`s are frame
  stacks:
  - A message is silenced by the innermost `Quiet` whose spec names it.
  - Only the `Check`s entered inside that `Quiet` see it.
  - A message no `Quiet` covers is seen by every enclosing `Check`, so
    `Check[Check[1/0, a], b]` is `b`.
- **Specs.** A spec is `sym::tag`, `General::tag` (that tag under every head),
  `All`, `None`, or a list of these. Specs are held, as in the reference: a
  symbol whose value is a list names nothing. A silenced message is not added
  to `$MessageList`.
- **Internal probe regions** (`mth_msg_suppress_push`) are all-covering
  `Quiet` frames. Their messages no longer reach a user's `Check` outside them.
- `TimeConstrained`'s unwind restores both frame depths.
- Message heads print without a visible context: `DiracTrick::failmsg`, not
  `FeynCalc`DiracTrick::failmsg`.
- **Named emission.** The legacy printf-style helpers (`Inverse::sing`,
  `Association::`, file-system and `DateList::` messages) now go through the
  funnel by name (`mth_message_linev`), so `Check[Inverse[m], f,
  Inverse::sing]` sees them. A de-duplicated repeat of `Solve::nsdim` is
  noted by name too (`mth_msg_note_named`).
- Every case was checked against the reference. Tests: `tests/test_message.c`
  (`test_check_quiet_nesting`).

## Parser: named characters in source (`\[Mu]`, `\[Rule]`, `\[CenterDot]`, ...) ; v0.587

Named characters used to work only inside string literals. In source code,
`\[Mu] + 1` and `a \[Rule] b` were syntax errors, and so were the raw
characters (`μ + 1`). FeynCalc's unit tests are strings of input that
`ToExpression` reads, and they use named characters about 9,000 times
(`\[Rule]`, `\[Nu]`, `\[ImaginaryI]`, `\[Mu]`, ...). Every syntax error in
the Lorentz directory came from this: 325 tests.

- **Every non-ASCII character, raw or escaped** (`\[Name]`, `\:hhhh`,
  `\|hhhhhh`), is read as the reference parser reads it:
  - **Letters** form identifiers (`a\[Mu]1` and `\[Mu]$` are each one symbol).
    The name stores UTF-8, so every spelling is the same symbol.
  - **Constant letters**, alone, are the constant: `\[Pi]` is `Pi`, and
    `\[ImaginaryI]`, `\[ExponentialE]`, `\[Infinity]` and `\[Degree]` work
    the same way.
  - **Operators that have an ASCII form** reuse it: `\[Rule]`, `\[LessEqual]`
    (inside an `Inequality` chain), `\[Times]`, `\[And]`, `\[Not]`, ...
  - **The other ~230 operators** take their head, precedence and grouping
    from the reference: `\[CenterDot]`, `\[Cross]`, `\[Element]`,
    `\[Perpendicular]`, prefix `\[Del]`, postfix `\[Transpose]`, ...
  - **Whitespace characters** are spaces, and `\[IndentingNewLine]` is a line
    break that ends a statement.
- **The class table is generated from the reference parser, not written by
  hand.** `tools/classify_named_chars.wls` probes every one of the ~1100
  named characters (alone, infix, prefix, postfix, and three-way for
  grouping). `tools/gen_named_chars.py --classes` turns that into
  `src/strings/named_char_class.inc`, read through `u8_char_class`
  (`src/strings/utf8.c`).
- The raw `→` (U+2192) stays a `Rule` synonym, as before: a documented
  deviation from the reference, which reads it as `RightArrow`.
- FeynCalc Lorentz unit tests pass 1521 of 1823, up from 1225. See
  `docs/spec/operators.md` ("Named characters in source").
- Tests: `tests/test_parse.c` (`test_named_characters_in_source`).

## v0.575: MatrixRank of an inexact matrix with free symbols

## v0.574: SparseArray works everywhere (the transparency gate); stress test; Power, Eigenvalues and printing fixes

- **The SparseArray transparency gate** (`src/sparse/sparse_gate.c`). Outside

  - answer as on `Normal[s]`;
  - the same, re-sparsified when an array leads;
  - walk the sparse rows (`Map`, `Apply`, `MapThread`);
  - otherwise keep the atom, which is right for the pattern heads and for
    containers.

  The lists were derived by sweeping 1247 builtins over 22 call shapes each.
  Sparse-specific disagreements fell from 930 to ~360; the remainder are edge
  shapes whose expected answer is itself irregular. Implicit
  densifying is capped at 2^27 elements (`SparseArray::dense`). A `SPG_NATIVE`

## v0.572: SparseArray -- native sparse storage, arithmetic and element-wise functions

`SparseArray` is now a real sparse array. Until now it was an inert expression
that only `Normal` understood.

- **Representation.** A new raw-object node type, `EXPR_SPARSE` (`src/sparse/`):
  compressed sparse row generalised to any rank, values in one typed machine
  buffer (Integer / Real / Complex) or boxed, 32-bit column indices when the
  dimensions allow, and an immutable reference-counted index pattern shared
  by every element-wise derivative. `AtomQ` is True, only `_SparseArray`
  matches it, its values are never re-evaluated, and it prints as
  `SparseArray[<nnz>, dims]` (InputForm / FullForm: the standard
  `SparseArray[Automatic, dims, val, {1, {rowptr, colidx}, vals}]`, which
  reads back). `===`, hashing and ordering compare arrays by value.
- **Constructor.** It accepts:
  - position rules, and `{pos..} -> {vals..}` / `-> v`;
  - pattern rules (`->` and `:>`, conditions; a match-everything rule sets the background);
  - `Band[start(, end(, step))]` with scalar, vector, subblock and block-list values;
  - dense and packed arrays;
  - an existing SparseArray (minimise / resize / rebackground);
  - the standard form.

  The first rule for a position wins, and background-valued entries are left
  implicit. Malformed specifications emit `SparseArray::` messages (`list`,
  `rect`, `posd`, `pos`, `posr`, `rule1`, `adims`, `exdims`, `drnk`, `valnl`,
  `ilist`, `bndtr`) through `Quiet`/`Check`.

  A packed `positions -> values` rule is read straight from its buffers. The
  evaluator keeps a Rule that is SparseArray's first argument packed, unpacking
  it again if the constructor declines. A stable LSD radix sort on a composite
  (row, column) key then builds 10^6 entries in ~40 ms.
- **Structure.**
  - `Normal` gives the dense array, packed when the values and background share
    one machine type, and also converts sparse arrays nested in an expression.
  - `Length`, `Dimensions`, `VectorQ` / `MatrixQ` (with tests) and `Head` work.
  - `Part` reads an element by binary search, or a selection as a SparseArray.
    `[[0]]` is `List`, and an empty selection is `{}`.
  - Element `Part` assignment inserts, replaces, or removes on the background.
  - `s["prop"]` gives NonzeroPositions / NonzeroValues (packed), Background,
    Density, RowPointers, ColumnIndices, AdjacencyLists, BandWidth and
    Properties. Unknown names give `SparseArray::nomthd`.
- **New builtins.**
  - `ArrayRules` gives the rules with the `{_, ..}` default.
  - `ArrayQ` (depth pattern and element test) and `ArrayDepth`.
  - `Band` is now Protected.
- **Element-wise.** Every Listable head threads over SparseArray arguments. The
  background is `f` of the backgrounds, and the entries are `f` over the union
  of the explicit positions (Times over zero backgrounds: the intersection).
  Nothing is re-minimised, and alongside a dense List the result is dense.
  There are three agreeing tiers:
  - overflow-checked typed loops for Plus / Times / Power, including fused
    two-pointer merges;
  - the head's own packed/NDArray kernel run over the value vector (Sin, Exp,
    BesselJ, Floor, Abs, ...);
  - per-entry evaluation for symbolic values and user Listable functions.

  `N[s]` converts a typed buffer in one pass and keeps the pattern.
- **Performance against scipy.sparse (10^6 entries, 10^5 x 10^5).**

  | | build | `A + B` | `A B` | `2.5 A` | `A^2` | `Sin[A]` | `A + A` |
  |---|---|---|---|---|---|---|---|
  | Mathilda | 40 | 5.8 | 3.0 | 1.3 | 1.7 | 2.8 | 1.8 |
  | scipy | 41 | 10 | 7.2 | 3.8 | 3.9 | 16 | 6.8 |

  Times are in ms. Row extraction takes 0.06 ms, against 0.07 ms in scipy.
- **Deferred to the linear-algebra pass:** Dot, Transpose, Total, LinearSolve,
  Det, Inverse, eigen-solvers, Map, Flatten, and graph heads returning
  SparseArrays.

## v0.571: `<<file` and `DirectoryQ`

- **`<<file` parses as `Get["file"]`.** The name after `<<` is a file token,
  not an expression: letters, digits, `` !$*-./:?\_`~ `` and balanced `[...]`
  (`<<f[x]` is `Get["f[x]"]`, `<<a/b.m`, `` <<Foo` ``, `<<~/x-1.m`), or a string
  literal. Whitespace, `;`, `,`, `)`, `]` or `}` ends it; any other character
  is a syntax error (`<<f+1`). `Get` binds tighter than any operator, so
  `a<<f` is `Times[a, Get["f"]]` and `<<"f"[x]` is `Get["f"][x]`.
- **`>>` / `>>>` share that file-token reader.** Their bare names used to stop
  at the first character outside a small set, so `x >> f[1]` was
  `Put[x, "f"][1]` and `x >> f*g` was `Times[Put[x, "f"], g]`; they now write
  to `"f[1]"` and `"f*g"`, and `x >> f+g` is a syntax error.
- **`DirectoryQ["name"]`** (new): True for an existing directory, False for
  anything else (a file, `""`, a list, a non-string). `File["name"]` and a
  leading `~` are accepted, and the same resolution now applies to
  **`FileType`** and **`FileExistsQ`** (`FileType["~"]` is `Directory`).

## SubValues: `f[x_][y_] := ...` definitions ; v0.568

Definitions whose left-hand side has a compound head used to store nothing,
silently: `f[a][b] := ...`, `f[a][b] = v`, and deeper ones such as
`f[a][b][c] := ...`. FeynCalc has about 103 of them, for example memoised
`expandVec[head][y, dim] = ...` and `momSplit[head, All][a__]` (gap S2). They
are now SubValues, keyed on the innermost head symbol.

- **Storage.** A new `SymbolDef.sub_values` list, filled through the same
  `add_rule` as DownValues: same-LHS replacement, specificity order, scoped
  guards. `apply_sub_values` handles `OptionValue`, guards and Throw/Abort.
  The functions are `symtab_add_sub_value`, `symtab_innermost_head` and
  `symtab_remove_matching_sub_value` (`src/symtab.c`).
- **Assignment** (`src/eval.c`). Compound-head LHSs, including guarded ones,
  route to SubValues. A `Protected` innermost symbol is refused. Immediate
  `Set` evaluates the arguments inside the head.
- **TagSet.** A tag that is the innermost head (`f /: f[a_][b_] := ...`)
  stores a SubValue instead of being refused.
- **Evaluation.** A compound-head call evaluates its head first. It then
  tries its arguments' UpValues, which compound-head calls previously never
  consulted at all, and then the innermost symbol's SubValues. The innermost
  def is read from the symbol node's cached pointer: pure-function-heavy loops
  measured the same as v0.567 (interleaved runs, within noise).
- **Builtins.** `SubValues[f]` is new (`HoldAll`, `Protected`). `Definition`
  prints SubValues. `Clear`, `ClearAll` and `Remove` clear them. `Unset`
  removes one, or emits `Unset::norep`.

All 26 reference cases match. Tests are in the new `tests/test_subvalues.c`
(7 groups).

One existing gap was found along the way and is still open:
`Derivative[1][Sin]` and `D[f[x][y], y]` stay unevaluated. They already did in
v0.567, so this change did not cause it.

## Conditional rules: `lhs := Module[{...}, val /; cond]` ; v0.567

A definition whose right-hand side is a `Module`, `With` or `Block` with a
body ending in `val /; cond` now behaves as a conditional rule. "Ending in"
counts nested scopes and a `CompoundExpression`'s last statement. Before,
such a rule returned the `Condition` expression itself as its value (FeynCalc
gap S12, found while doing S6). Now:
- The guard is evaluated inside the scope.
- If it fails, evaluation falls through to the next rule, and the body's side
  effects remain.
- A later definition with the same left-hand side no longer silently replaces
  the conditional rule. Before, `m[x_] := Module[..., t /; t > 3]` followed by
  `m[x_] := "fallback"` left only the fallback.

Implementation: `Rule.scoped_cond` is set in `add_rule` (`src/symtab.c`). At
application the bound right-hand side's tail `Condition` is rewritten to
`If[TrueQ[cond], val, $ScopedConditionFail$]` and evaluated in place, for both
DownValues and UpValues. `OptionValue` is resolved first, and a `Throw` in the
guard propagates. All 16 reference cases match. Tests are in
`tests/test_condition_downvalue.c`.

- A tag that is the innermost head of a compound head,
  `clc /: MakeBoxes[clc[x___][y___], fmt] := ...` (7 FeynCalc definitions),

## `Abort[]`, `CheckAbort`, `AbortProtect`; throws no longer vanish inside callbacks ; v0.564

**Abort.** `Abort[]` used to be returned as an ordinary value: it truncated a
`CompoundExpression`, and otherwise stayed in the result as junk such as
`{1, Abort[], 3}` (FeynCalc gap L1; FeynCalc calls `Abort[]` 667 times). It
is now an in-flight sentinel, like the `Throw` node, carried up the ordinary
return path by the evaluator's argument short-circuit.
- `eval_is_inflight_abort` and `eval_is_inflight_unwind` (`src/eval.c`).
  Every site that passed a `Throw` upward now passes an abort upward too.
- It reaches `CheckAbort[expr, fail]`, or else the top level, where the result
  is `$Aborted`.
- A `-file` script prints `$Aborted` and stops.
- `Get` stops reading and propagates the abort.
- `AbortProtect` defers an abort to the end of the protected evaluation. Its
  depth counter is registered with `TimeConstrained`'s unwind registry.
- `Catch`, `Check`, `Quiet` and `TimeConstrained` do not stop an abort, and
  `CheckAbort` does not stop a `Throw`.
- 22 behaviours were checked against the reference.

**Swallowed throws.** A sweep found 22 builtins that silently dropped a
`Throw` raised inside a user callback (and so would drop an abort too). Each
read the in-flight sentinel as "not `True`". They were:
- `Select`;
- the matcher's `_?f` and `/;` (covering `Cases`, `Count`, `DeleteCases`,
  `Position`, `MemberQ`, `FreeQ`, `MatchQ` and `ReplaceAll`);
- `Sort`, `SortBy`, `GatherBy`, `SplitBy`, `Split`, `TakeWhile`,
  `LengthWhile`, `DeleteDuplicates`, `Union` with `SameTest`, `MaximalBy`,
  `MinimalBy`, `Tally` and `KeySelect`.

These callback sites now evaluate through `eval_callback`, which parks a
sentinel in `g_pending_unwind`. The enclosing `evaluate_step` frame raises it
if the builtin drops it, and `Catch`/`CheckAbort` clear it when they consume.
Parking is deliberately limited to callbacks, not every `evaluate()`. A first
version that parked everywhere surfaced a `Throw` that `Sum`'s speculative
symbolic probe evaluates and rightly ignores
(`Catch[Sum[If[i == 5, Throw[i], i], {i, 10}]]` must stay 5). `Gather[l, test]`

## Reader: `;/;` continuation, `Get` syntax errors, left-associative `/;` ; v0.563

**Statement continuation.** The file reader (`parse_next_expression`, used by
`Get` and `-file`) ends a statement at a top-level `;`. If the next token on
the same line can only continue an expression (`/;`, `//`, `/.`, `->`, `:=`,
`==`, `&&`, `&`, `::`, ...), the `;` now acts as `CompoundExpression` with an
implicit `Null`. That compound becomes the operator's left operand, as the
reference reader parses it. FeynCalc's `SharedTools.m:759` is
`lhs := rhs;/; cond;`. Before, the leftover `/; cond` failed to parse and
`Get` stopped silently, skipping about 370 lines of the bootstrap file (gap
L2). The mechanism is a new `ParserState.seed_left`: `parse_expression_prec`
can resume its infix loop with an already-parsed left operand. Across a line
break, a leading operator is still a syntax error.

**`Get` syntax errors.** The reference stops reading at a syntax error, so
Mathilda stopping was right; the gap doc's claim that it continues was wrong.
But Mathilda stopped silently. `Get` now emits `Syntax::sntx` through the
funnel, with the statement text and line number, and returns `Null`. A new
`parse_set_quiet` keeps the parser's raw diagnostics (`Expected ')'`, ...) from
being printed on top of the message. `ToExpression` and `SyntaxQ` parse
quietly too, so `Quiet[ToExpression["(1+"]]` no longer leaks output. The gap
doc's "unclosed `(` accepted as complete" was already not the case.

**`/;` is left-associative.** The new tests turned up a parser bug:
`a /; b /; c` parsed as `Condition[a, Condition[b, c]]`, where the reference
has `Condition[Condition[a, b], c]`. Fixing it required changes in the
assignment paths:
- Defining a DownValue and classifying an UpValue tag now peel every LHS
  guard, not just one.
- A delayed RHS chain `lhs := body /; t1 /; t2` hoists all of its guards
  (`hoist_rhs_conditions` in `src/eval.c`).

Chained guards work on the LHS, on the RHS, in patterns, and in UpValues.

**Tests.** `tests/test_parse.c` checks the statement reader against a
34-row table of reference parse shapes, plus `Get` error behaviour (stop,
message, `Null`, unfinished input, same-line versus next-line guard).
`tests/test_condition_downvalue.c` covers chained guards in every position.
The `mod70` expectations in `tests/test_upvalues.c`, broken since v0.299, are
corrected: they lacked the printer's `", "` spacing.

## `Dispatch`: indexed rule sets accepted by every `Replace` form ; v0.560

`Dispatch` used to be an inert symbol, so `/.`, `//.` and `Replace` returned
their input unchanged when given one, silently. FeynCalc uses it 210 times in
116 files (gap S3).

- **Normalization.** `Dispatch[rules]` normalises a single rule to a list and
  collapses `Dispatch[Dispatch[r]]`. `Normal[Dispatch[r]]` is `r`. `Replace`,
  `ReplaceList` and `ReplaceAt` unwrap it.
- **The index.** `ReplaceAll` and `ReplaceRepeated` build a hash index over
  the rules (`rule_index_build`, `do_replace_all_idx` in `src/replace.c`).
  - A rule is keyed by its literal-atom LHS or its literal head, looking
    through `HoldPattern`, `Condition`, `PatternTest`, `Pattern` and
    `Verbatim`.
  - An LHS that could match a node with a different head is tried at every
    node. That covers pattern constructs, compound heads, associations, and
    `Optional`/`x_.` arguments (`x^n_.` matches `x`).
  - Candidates are merged in original rule order, so the winning rule is the
    one the linear scan would pick.
- **Verification.** 4000 randomized comparisons of `/.` and `//.` against the
  plain list, mixing every key class, all agree.
- **Performance.** 5000 rules over 20,000 symbols take 3.8 ms against 772 ms,
  about 200x.
- **Scope.** Plain rule lists keep the existing linear path; `Dispatch` is the
  explicit opt-in.
- **Known divergence.** `Dispatch[...]` is a normal expression rather than an
  atom.

Tests are in `tests/test_replace.c`, including a randomized cross-check.
`SYM_Dispatch` is new in `src/sym_names.c`.

## `OptionValue` resolves inside a `/;` guard ; v0.557

`g[x_, OptionsPattern[]] := x /; OptionValue[o] == 1` used to stay
unevaluated for every call. A delayed RHS condition is stored in the rule's
pattern, so the matcher evaluates it before the RHS is built, and
`optionvalue_inject_context` had only ever rewritten the RHS. The bare
`OptionValue[o]` in the guard therefore never resolved and the guard never
became `True`. FeynCalc's `MemSet` guards on
`MatchQ[OptionValue[FCMemoryAvailable], _Integer?NonNegative]` this way
(gap S6).

- **The fix.** The matcher's `eval_guard_true` (`src/match.c`) applies the
  same injection to the guard whenever the match bound an `OptionsPattern`.
  Defaults resolve against `OptionsPattern[s]`'s `s`, or else the head of the
  rule being applied. `apply_down_values_def` and the UpValue path publish
  that head through `match_set_rule_head`, saved and restored around each
  match.
- **Divergence.** A guard written on the LHS resolves too, where the reference
  leaves that call unevaluated. This is documented in the spec.
- **Gap found, still open:** a `/;` at the end of a `Module`/`With`/`Block`
  body on the RHS should act as the rule's condition, but Mathilda returns the
  `Condition` expression as the value.

Tests are in `tests/test_options.c`.

## Parser: backslash-newline in a string literal is a line continuation ; v0.556

Inside a string literal, a backslash at the end of a line now drops both the

## New builtin `Signature`; `IntersectingQ` / `DuplicateFreeQ` compile ; v0.550

**`Signature[list]`** gives the sign of the permutation that puts `list` into
canonical order, or `0` when two elements are equal. FeynCalc uses it to order
Levi-Civita indices (gap B1). Its surfaces:
- **Generic path** (`src/funcprog.c`): an index sort by `expr_compare`, then a
  cycle count.
- **Buffer path**: int64 and float64 vectors are sorted as `(value, index)`
  pairs by `ndred_signature` (`src/ndreduce.c`). The head is on `AWARE` and
  `INT64_OK`.
- **Compile**: a new `ND_REDS` row lowers `Signature[v]` to an Integer for
  `_Integer` and `_Real` vectors. `nd_red_result` now lets `int_result` cover an
  int operand when the row is also `int_ok`; `MatrixRank` is unchanged.

The scalar, packed, NDArray and Compile answers agree. `Order[0., -0.]` is 0, so

**Compile lowering for the v0.549 predicates.** `make check-compile-coverage`

paths but no lowering. The fix adds:
- `NdRedSpec.bool_result`, so a predicate reduction yields a `CT_BOOL` register

## Integrate: Bessel integrals in closed hypergeometric / MeijerG form ; v0.544

A new indefinite stage, `"BesselHypergeometric"` (`src/internal/BesselHyper.m`),
runs right after `Holonomic`. It closes `c x^m Z1(b x^p) [Z2(b x^p)]` for every
pair of Bessel `J`/`Y`/`I`/`K` in one family (ordinary or modified), with any
orders, symbolic ones included. These used to come back unevaluated, single
factors included: `Integrate[BesselJ[1/3, x]^2, x]`,
`Integrate[BesselJ[1/3, x], x]`, `Integrate[BesselK[0, x], x]`,
`Integrate[BesselJ[nu, x]^2, x]`, `Integrate[BesselK[1/3, x]^2, x]`,
`Integrate[BesselJ[0, x] BesselY[0, x], x]`, `Integrate[BesselY[1, x]^2, x]`.

Everything is derived from first principles:
- **Series route.** The product series sums by Chu–Vandermonde to a 2F3 and is
  integrated term by term into a HypergeometricPFQ, with an exact `Log[x]`
  split when the integrated exponent is zero.
- **MeijerG route.** For integer or symbolic `Y`/`K` orders, where the Sin
  reflection divides by zero, the stage uses Mellin–Barnes forms whose residue
  sums reproduce the series, integrated under the contour.
- **Integer order differences.** These are rewritten by the recurrences and
  the Wronskian into diagonal products, which removes the empty Mellin strips.
  `INT D_n/x` telescopes.

**Newton–Leibniz guard.** A boundary value containing `0^p` with a
non-numeric `p` no longer counts as a closed form. Substituting x = 0 into
`x^(1+nu) MeijerG[..., x^2/4]` gives `0^(1+nu) MeijerG[..., 0]`, which is a
0 · Infinity product. Such a value now falls to `Limit`, and the integral
stays unevaluated if `Limit` cannot decide it, rather than returning a
non-number. Seen on Mathar `M12658`.

Holonomic's Bessel-product answers are unchanged (`x^2 BesselK[1/3, x]^3`,
`x BesselJ[1/3, x]^2`). New tests are in `tests/test_integrate_bessel_hyper.c`.
Each antiderivative is differentiated back at three points, to 1e-20.

## Simplify: a table-driven special-function engine (Bessel, Gamma, zeta, error functions) ; v0.536

`Simplify` now treats special functions the way `Together` treats rational
functions. A new pass, `src/simp/simp_sf_engine.c`, runs in `simp_dispatch`
before the shape pipelines. It groups special-function atoms whose shift
arguments differ by integers into **families**, using head, non-shift
arguments, and per shift argument its symbolic part and rational part mod 1.
It rewrites each family onto one basis through **affine shift matrices** (a
descriptor states only the raising relation; the engine inverts it for down
steps). It also applies **canonical generators**, **reflections** and
**Wronskian pairs**, then lets Together/Expand/Factor decide. A rewrite is kept
when the score strictly drops, or when special-function kernels are eliminated
at a bounded score cost (`Gamma[1/3] Gamma[2/3]` → `2 Pi/Sqrt[3]` ties on
score). The old `simp_bessel.c` pass is now the first descriptor module on the
engine.

Modules and relations (derivations in `docs/design/simp_special_functions.md`):

- **Bessel** (`simp_bessel.c`):
  - contiguous orders, as before;
  - the Casoratians `J[m+1] Y[m] - J[m] Y[m+1] = 2/(Pi z)` and
    `I[m+1] K[m] + I[m] K[m+1] = 1/z`, reduced with `PolynomialReduce`;
  - `BesselK` evenness, with a class-preserving canonical sign that follows a
    present `BesselI`;
  - integer-order reflection under assumptions.
- **Gamma** (`simp_sf_gamma.c`):
  - `Gamma`, incomplete `Gamma[a, z]`, `LogGamma` (slit-plane identity) and
    `BarnesG`;
  - `Pochhammer`, `Beta`, `Binomial` and `Factorial`, onto Gamma, with refold
    passes back to the input's vocabulary;
  - Euler reflection, with the sine written in the partner's argument;
  - Gauss multiplication, keyed on integer content.
- **Zeta** (`simp_sf_zeta.c`):
  - recurrences for `PolyGamma` (integer order), `HarmonicNumber[n]` and
    `[n, r]`, `HurwitzZeta`, `Zeta[s, a]` (its `((k+a)^2)^(-s/2)` convention)
    and `LerchPhi`;
  - PolyGamma reflection and multiplication;
  - the Riemann functional equation;
  - PolyLog reflection and duplication, plus Landen (`u < 1`) and inversion
    (`u < 0`). These two are gated because they fail on a real half-line.
- **Error/exponential integrals** (`simp_sf_errexp.c`):
  - `Erfc → 1 - Erf`, `Erf[z0, z1]`, `Erfi`, `InverseErf`/`InverseErfc`
    compositions;
  - the `ExpIntegralE` order recurrence;
  - `LogIntegral = ExpIntegralEi∘Log`;
  - `Si`/`Shi` at `I z`, Fresnel at `I z`;
  - `CosIntegral`/`CoshIntegral` reflection under `x > 0`.

Every domain gate came from numeric probes in all four quadrants and on the
cuts. Candidates go through one normal form (`normalize_form`) that reconciles
spellings `Together` and the evaluator leave inconsistent: expanded shift
arguments, distributed negations, odd-function signs, natural `Pi (a + b)`
trig arguments, quarter-turn folds and per-base power spelling.
`MATHILDA_NO_SF_ENGINE=1` disables the pass.

Tests: `tests/test_simp_sf_{bessel,gamma,zeta,errexp}.c` (6,131 checks, 26

## Fix: canonical string order is WL's collation ; v0.530

weight: `".hid"` came before `"a.m"`, and `"ab"` before `"a-b"`. Strings now

## Fix: `Quit[]` ends a `-file` script; `Quit[n]` sets the exit status; new `Exit` (issue #106) ; v0.527

`Quit` used to be inert. The interactive loop compared each input line with the

`Quit` is now a builtin (`src/quit.c`). Evaluating `Quit[]` or `Quit[n]` records a

## Perf: `BlakeRationalBaseDescent` — weighted base order, division-free accumulator ; v0.526

`FactorInteger[p q, Method -> "BlakeRationalBaseDescent"]` with
`p = NextPrime[⌊(355/113)^720⌋ + 123948304759283749084]` (1190 bits) and a
441-bit `q`: **62.9 s → 2.8 s** (16 threads).

- **Base order.** A single base costs about 5 ms; the time went on the search. The
  breadth-first Stern–Brocot order at height 1000 tried 189 654 bases before 355/113.
  The new default `"Order" -> "Weighted"` enumerates in ascending `a / log2(a/b)`, i.e.
  height × descent length (weighted shortest job first). It is streamed in doubling key
  bands of pruned Stern–Brocot walks. On 3000 random target bases it is 2–2.5× better on
  average than breadth-first under both a uniform and a log-height prior (18× for 355/113).
  `"HeightDoubling"` (height bands 16, 32, …) is new, and `"SternBrocot"` (breadth-first)
  and `"Sum"` remain.
- **Accumulator.** `acc_mul`'s two `mpz_tdiv_r` per step were 45% of the search. The new
  `fi_rbd_modacc.c` keeps the window product in Montgomery-reduced form on fixed-size limbs,
  with the modulus built once per `n` and shared by every thread. A REDC only multiplies by
  a unit mod an odd `n`, so the gcd needs no conversion and there is no division at all.
  Folding `y = Q(Q+3)` and `y + 2` separately also drops the `y(y+2)` product. The gain is
  about 10% on x86 (the per-step work was already near the method's information bound); an
  even `n` runs unbatched.
- **Test.** `tests/test_factorinteger.c` `test_rbd_modacc` checks that the fold equals the mpz
  product up to a unit (400 random `n` of 1–30 limbs, factors up to `2n + 3` limbs,
  planted divisors). It also checks batched and unbatched hit records for identity on
  planted structured semiprimes, for both the exact and the iterated descent.

## Perf: discrete log via Pohlig–Hellman with BSGS / Pollard ρ ; v0.524

**`MultiplicativeOrder[k, n, {r1, …}]` was a capped linear scan.** It stepped
through `k^1, k^2, …` up to `10^8` and returned unevaluated above that. A 24-bit
log took 380 ms, 630× slower than PARI's `znlog`. Any order of 32 bits or more
was left unevaluated, including a 131-bit `p` whose `p − 1` is 75011-smooth.
That was finding P3 / C8 of the group F benchmarks.

The new engine is `src/numbertheory/nt_dlog.c`, using the scheme PARI's `znlog`
uses:

- **Pohlig–Hellman** over the factored order of `k`, solving one digit at a
  time.
- **Baby-step giant-step** for primes up to 2^36. One table per prime is reused
  across digits and targets.
- **Pollard ρ** (Teske r-adding walk, Brent cycle detection) above that.
- A `uint64` Montgomery back-end for `n < 2^63`, and GMP above.
- Every answer is verified, and the search cap is gone.

`TimeConstrained` interrupts long ρ walks. The engine polls the deadline,
returns cleanly, and takes the timeout once its memory is freed. The order
computation now factors `n` and each `p − 1` with FactorInteger's engine, after
a primality test, instead of trial-dividing by every integer below 10^5. The
2-argument form gets faster on bignum moduli too: 0.37 → 0.24 ms for the 131-bit
`p`.

| 24-bit subgroup ×40 | 15 316 | 3.8 | 27 |

## Fix: `AppendTo`/`PrependTo` and Part assignment silently did nothing to a packed array; Part assignment distributes level by level ; v0.522

**`AppendTo`/`PrependTo` on a packed variable** did nothing. `a = Range[5];
AppendTo[a, 6]` came back unevaluated and left `a` unchanged, with no message.
The same happened with a packed real vector, a packed matrix row, a `Module`
local or `f[1]`. Both builtins are `HoldFirst` and read the variable's value
themselves. A packed value is an `EXPR_NDARRAY`, and they accepted only an
`EXPR_FUNCTION`. They now compute the new value by calling `Append`/`Prepend`,
so they take its buffer path and the variable stays packed. As in the
reference, they now emit `X::rvalue` for a symbol with no value and
`X::normal` for an atom value (both were silent before).

**Part assignment into a packed array** with a List right-hand side did
nothing. `m = Table[i + j, {i, 4}, {j, 4}]; m[[2]] = {0, 0, 0, 0}`,
`m[[All, 1]] = {…}` and `v[[2 ;; 4]] = {0, 0, 0}` all left the array unchanged.
The buffer writer accepted only a scalar or an `NDArray` right-hand side, and
when it declined, the caller returned the array untouched. Now a numeric List
right-hand side is packed and written on the buffer, so the result stays packed.
Anything the buffer cannot hold goes through the List path and is repacked when
the result is uniform again. A visible `NDArray` coerces into its dtype, and a
value no buffer holds leaves it unchanged with the new `Set::ndarray` message
(it used to fail silently).

**Right-hand-side distribution now follows the reference rule, level by
level.** At each subscript that selects several positions, a List whose length
equals the number of positions there is split across them; otherwise it is
stored whole. A single running counter over all leaves gave
`m[[{1,2},{1,2}]] = {{a,b},{c,d}}` → `{{{a,b},{c,d},4}, …}` (correct:
`{{a,b,4},{c,d,5},…}`), and `v[[2;;4]] = {0,0}` → `{1, 0, 0, {0,0}, …}` (correct:
every part gets `{0,0}`). `ndarray_part_set`, which compiled code also calls,
now requires the right-hand side's shape to equal the selection's, not just its
element count. Before, a `{2, 4}` selection would have been filled element-wise
from an 8-vector, where the reference stores the vector whole in each row.

- Not changed: `Sow`/`Reap` were correct throughout. Their results lose
  packing because `List` is deliberately not packed-aware (the no-nesting
  invariant, `src/pack.c`), so `Sow` stays off `AWARE`. `AppendTo`/`PrependTo`
  are `EXEMPT` in `check-packed-aware`, with the reason recorded.
- Tests: `test_part_assign_packed`, `test_part_assign_levelwise` and
  `test_appendto_packed` in `tests/test_part.c`. All expected values come from
  the reference.

## Fix: machine-real `Det`/`Inverse`/`LinearSolve` recursion; `NDArray` beside a plain List; `Boole` and `IntegerExponent` over arrays ; v0.521

**`Det`, `Inverse` and `LinearSolve` ran to `$RecursionLimit`** on a small
machine-real matrix whenever their buffer path declined: a non-square `Det`, a
singular `Inverse`, or a singular `LinearSolve`. The answer was rows of
`Hold[List][...]`. Each builtin packs a below-threshold machine List to reach
the buffer path. On decline that path delisted and re-evaluated, which called
the same builtin on the same plain List, which packed it again. This was not
specific to `NDArray`: the plain `Det[{{1., 2., 3.}, {4., 5., 6.}}]` did it
too.

The three pack-and-try sites now probe through `linalg_try_fast`. Under it,
`linalg_delist_and_reeval` returns NULL for the probed call only, and the
builtin's generic path answers with its one message (`::matsq`, `::sing`,
`::nosol`).

That generic path had never been reached for a singular machine system, and
it invented exact values in a Real answer:
- `LinearSolve[{{1., 2.}, {2., 4.}}, {3., 6.}]` was `{3., 0}`;
- `RowReduce[{{1., 2., 1.}, {2., 4., 2.}}]` kept an exact `1`, because exact
  polynomial division in no variables divided `1./1.` structurally.

A free variable's `0` and a constant-over-constant division now take the
input's exactness. Exact input is unchanged.

**A visible `NDArray` beside a plain List** that the evaluator could not lift
into a buffer was threaded as a scalar:
- `NDArray[{1., 2., 3.}] + {1, 2}` gave two whole arrays instead of

- `NDArray[{1., 2.}] + {x, y}` gave `{nd + x, nd + y}` instead of
  `{1. + x, 2. + y}`.

The transparency gate materialises a packed argument there, but by design
never touches a visible one. A Listable call that still has a plain List
argument after the lift now delists its visible arrays, so it threads exactly
as the List does. Same-shape numeric Lists are lifted first and keep the
buffer path.

**`Boole` and `IntegerExponent` over arrays.**
- `Boole` of a non-bool visible array (or an empty bool one) now takes the
  List path: `Boole[NDArray[{1., 0.}]]` is `{Boole[1.], Boole[0.]}`.
- `IntegerExponent[array]` (base 10) gets a unary int64 kernel through the
  same helper as the binary form; it used to stay unevaluated on a visible
  array.

Tests:

## New builtins: `BitShiftLeft` and `BitShiftRight` ; v0.517

**`BitShiftLeft[n, k]`** (`src/bitwise/bitshiftleft.c`) is `n 2^k`;
**`BitShiftRight[n, k]`** (`src/bitwise/bitshiftright.c`) is
`IntegerPart[n / 2^k]`. A negative `k` shifts the other way, the one-argument
forms shift by one place, and both have Attributes `Listable` and `Protected`.

- A right shift truncates toward zero:
  `BitShiftRight[-5, 1]` is `-2`.
- Exact at any size, through GMP (`mpz_mul_2exp`, `mpz_tdiv_q_2exp`), with
  results normalised back to int64.
- Other numbers are scaled by `2^k`: reals exactly via `ldexp` /
  `mpfr_mul_2si`, keeping the precision; rationals via `Times`; complex
  numbers per part.
- Messages through the funnel: `::intm` for a non-machine-integer `k`, `::argt`
  for the wrong arity, and `General::ovfl` / `Overflow[]` and
  `General::unfl` / `Underflow[]` for unrepresentable shifts. `Underflow` is a
  new Protected symbol.
- One machine helper, `ndint_bitshiftleft_i64` (and `_right_`), is shared by
  the scalar path, the NDArray kernels and Compile (`OP_BSHL_I` /
  `OP_BSHR_I`).
- Packed/NDArray: binary and unary int64 kernels on `AWARE` and `INT64_OK`,
  with whole-buffer arms for a scalar `k`, a scalar `n` and two buffers.
  - The arms use logical shifts only, because x86 has no 64-bit arithmetic
    right shift before AVX-512.
  - The per-element-count arms are a fast single-direction pass plus a general
    fallback. On x86-64 the fast pass is in AVX2 intrinsics, where the
    variable shifts are defined for any count, so it needs no lane masks. That
    took `BitShiftLeft[v, kv]` from 0.47 ms to 0.043 ms at 10^5.
  - An overflowing left shift abandons the buffer for the exact List path; it
    never wraps.
- Speed against NumPy (x86-64):
  - at 10^5 elements, within 1-3 µs on every arm (for example
    `BitShiftLeft[v, kv]` 0.043 vs 0.041 ms, `BitShiftRight[v, kv]` 0.043 vs
    0.045 ms). That gap is the shared per-call floor (`BitNot[v]` 0.031 vs
    `np.invert` 0.030 ms).
  - at 10^7 elements, at parity.
- `Compile[]` lowers both at scalar and array shape, and auto-compilation
  follows.

## Fix: `Collect` with a pattern variable; numeric coefficients are not powers of a numeric key ; v0.516

**`Collect[expr, patt]` now collects when `patt` is a pattern.** Previously it
compared keys structurally, so a pattern key such as `Power[_, 1/2]`, `f[_]`,
`x^_` or `Derivative[_][f][_]` never matched, and the input came back
unchanged. `Sqrt[x]` was never the problem: it is stored as `Power[x, 1/2]`
and only *printed* as `Sqrt`. The variable spec is now expanded first. Every
distinct subexpression of `expr` that matches the pattern, at levels 1 to
Infinity with heads excluded (as in `Cases`), becomes a collection variable of
its own, in canonical order, spliced in where the pattern stood.

- `Collect[1 + 3 Sqrt[1 + x^2] + x Sqrt[1 + x^2], Power[_, 1/2]]` is
  `1 + (3 + x) Sqrt[1 + x^2]`.
- `Collect[a f[1] + b f[1] + c f[2] + d f[2], f[_]]` is
  `(a + b) f[1] + (c + d) f[2]`.
- Alternatives, `Condition`, `PatternTest`, a mixed list (`{f[_], x}`),
  equations and the `h` argument all work. With no match there is no
  variable, so `Collect[c + d, f[_], h]` is `h[c + d]`.

**`Collect` no longer reads an integer coefficient as a power of a numeric
key.** A `Sqrt[2]` key decomposes to base `2`, so the coefficient `2` used to
be taken as `Sqrt[2]^2`:

- `Collect[2 x + 2 y, Sqrt[2]]` gave `2 (x + y)`; it is now `2 x + 2 y`.
- `Collect[3 x + 3 y, 3^(1/3)]` gave `3 (x + y)`; it is now `3 x + 3 y`.

A pattern key could reach this through a nested radical (`Sqrt[_]` matching
the inner `Sqrt[2]` of `Sqrt[3 + Sqrt[2]]`).

Also fixed: `Collect` threading over an equation or a logic head leaked its
argument buffer.

## New builtin: `BitSet` ; v0.513

`BitSet[n, k]` sets to 1 the bit of `n` that is the coefficient of `2^k`
(two's complement, unlimited digits). It is the sixth member of the
`src/bitwise/` family (`src/bitwise/bitset.c`). Its attributes are `Listable`
and `Protected`.

- **Exact at any size.** The result grows as needed: `BitSet[42, 9]` is
  `554` and `BitSet[0, 64]` is `2^64`. A negative `n` already has its high bits
  set (`BitSet[-1, 100]` is `-1`). Answers that fit int64 are computed in
  int64; the rest go through `mpz_setbit` into a fresh node, normalised back
  when they fit (`BitSet[-2^64, 63]` is `-2^63`).
- **Silent where it does not apply.** These stay unevaluated with no message,
  as the reference system does:
  - a negative `k`;
  - a bignum `k`;
  - any non-integer argument;
  - the wrong argument count.

  There are no symbolic rules.
- **One machine helper for every surface.** `ndint_bitset_i64`
  (`src/ndinteger.h`) is the int64 answer for the scalar builtin, the NDArray
  kernel and Compile's new `OP_BSET_I`. It declines `k < 0` and bit 63 and up
  of a non-negative `n`, and each surface then falls back to the exact path.
- **Packed / NDArray.** A binary int64 kernel on `AWARE` and `INT64_OK`, with
  whole-buffer arms for a scalar `k` (a constant mask), a scalar `n`, and two
  buffers. The per-element-`k` arms are bound by the variable 64-bit shift,
  which baseline x86-64 cannot vectorise. On x86 the same C loop is therefore
  also compiled with `target("avx2")` and chosen at start-up with
  `__builtin_cpu_supports`; arm64's NEON vectorises the plain loop. At 10^5
  elements, against NumPy:
  - `BitSet[v, 5]`: 0.05 ms vs 0.05 ms;
  - `BitSet[7, kv]`: 0.065 ms vs 0.098 ms;
  - `BitSet[v, kv]`: 0.08 ms vs 0.12 ms.

  At 10^7 elements, `BitSet[v, kv]` takes 26 ms vs 45 ms. A buffer element
  with no int64 answer abandons the buffer for the List path, so nothing is
  truncated.
- **Compile[].** `OP_BSET_I` lowers at scalar and array shape and bails to
  the interpreter where the helper declines. Auto-compilation follows.
- **Tests.** 19 BitSet cases in `tests/test_bitwise.c`:
  - the documented examples;
  - negatives, the int64 boundary at k = 62/63/64, and bignums with
    demotion;
  - operand immutability, and silent unevaluated forms checked with
    `Check`;
  - Listable shapes and `tdlen`;
  - the oracles `BitOr[n, 2^k]`, idempotence, read-back, and binary digits;

  - `CompileDiagnostics`, and auto-compile on/off agreement.

## New builtin: `BitNot` ; v0.512

`BitNot[n]` is the bitwise NOT of an integer in two's complement: `-1 - n`.

  - compiled: 0.040 ms

## New builtin: `BitOr` ; v0.511

`BitOr[n1, n2, ...]`, the bitwise OR of integers in two's complement, is the
fourth member of the `src/bitwise/` family (`src/bitwise/bitor.c`), built as
the dual of `BitAnd`. Its attributes are `Flat`, `Listable`, `OneIdentity`,
`Orderless` and `Protected`.

- **Exact at any size.** Machine integers OR in int64. Bignums go through
  `mpz_ior` into a presized result node, read in place, using the BitAnd
  accumulator scheme (the first BigInt is set into the node, not ORed with
  `0`). A result that fits is normalised back to a machine integer, which
  matters more here than for AND: a negative int64 sign-extends over any
  positive bignum (`BitOr[-5, 2^70]` is `-5`).
- **Symbolic simplification.** Identical arguments collapse to one, the
  integers combine, a `-1` absorbs everything (including non-integers:
  `BitOr[-1, 2.5]` is `-1`) and a `0` is dropped. `BitOr[]` is `0`.
  `BitOr[x, y, y, x]` is `BitOr[x, y]`, `BitOr[1, 2, x]` is `BitOr[3, x]`,
  `BitOr[-1, 2, x]` is `-1`.
- **No diagnostic for non-integers.** `BitOr[2.5, 3]` stays unevaluated
  without a message, as for BitAnd.
- **Packed / NDArray.** The int64 kernel `ndk_BitOr_ii`, with array | scalar
  and array | array whole-buffer arms, is on `AWARE` and `INT64_OK`. The n-ary
  array form is folded on the buffer. At 10^5 elements Mathilda and NumPy
  `bitwise_or` take:
  - `BitOr[v, 255]`: 0.035 ms vs 0.034 ms
  - `BitOr[v, w]`: 0.044 ms vs 0.043 ms
  - `BitOr[u, v, w]`: 0.089 ms vs 0.085 ms
- **Compile[].** The new opcode `OP_BOR_I` is folded left for any arity, and
  the generic n-ary array fold picks it up. `CompileDiagnostics` reports
  `Compiled -> True` at scalar, array | scalar, array | array and n-ary shapes.
- **Tests.** 21 BitOr cases in `tests/test_bitwise.c`: every documented
  example; bignums across the int64 boundary; oracles `a + b == BitOr + BitAnd`,
  `BitOr == BitXor + BitAnd` and De Morgan over random 200-bit integers; operand
  immutability; List == packed == NDArray == Compile bit-equality. The leak gate
  `tests/scripts/bitwise_leakcheck.sh` is extended to BitOr and reports 0 leaks.

## Performance: BitXor two-array buffers and bignums ; v0.509

- **Array ⊕ array.** `NDBinaryKernel` gains an optional trailing arm,
  `whole_ii`, for two int64 buffers of the same shape: the counterpart of
  `whole_i` for `ndarray_map_binary2`. Without it the two-array map calls
  `to_int_i` once per element through a function pointer, with a
  dtype-dispatching read of each operand. BitXor provides a plain `a[i]^b[i]`
  loop. At 10^5 elements with warm caches:
  - `BitXor[v, w]`: 0.15 ms → 0.073 ms (NumPy `bitwise_xor` 0.054 ms)
  - `BitXor[u, v, w]`: 0.30 → 0.14 ms (NumPy 0.11)
  - the compiled two-array form: 0.14 → 0.063 ms

  At 10^7 all of these are memory-bound and level with NumPy. The arm is
  opt-in, so every existing kernel is unchanged. Their positional initialisers
  now spell the new field as an explicit `NULL`, which keeps `-Wextra` clean.
- **Bignums.** The BitXor accumulator now reads BigInt operands where they
  live and XORs them into the result node itself, presized to the widest
  operand. Previously each operand was copied into a temporary mpz, the
  accumulator grew by reallocation, and the result was copied once more.
  Machine operands fold into an int64 that is XORed into the bignum once.
  1,000 bignum pairs: 0.84 ms → 0.62 ms. The rest is the evaluator's
  per-element Listable threading, which `Plus` pays as well (≈1 µs/pair).

## New builtin: `BitXor` ; v0.508

`BitXor[n1, n2, ...]`, the bitwise XOR of integers in two's complement, is the
second member of the `src/bitwise/` family (`src/bitwise/bitxor.c`). Its
attributes are `Flat`, `Listable`, `OneIdentity`, `Orderless` and `Protected`.

- **Exact at any size.** Machine integers XOR in int64, which cannot overflow.
  Bignums go through `mpz_xor`, and a result that fits is normalised back to a
  machine integer.
- **Symbolic simplification.** Identical arguments cancel in pairs. An odd
  number of `-1` arguments becomes `BitNot[...]`, and this happens before the
  integer constants combine. The combined constant is dropped when it is `0`
  and pulled out as `BitNot` when it is `-1`. So `BitXor[x, x]` is `0`,
  `BitXor[1, 2, x]` is `BitXor[3, x]`, and `BitXor[1, -1, x]` is
  `BitNot[BitXor[1, x]]`.
- **Diagnostics.** `BitXor::int` is emitted for a concrete non-integer number
  that is still present after pair cancellation. It routes through the funnel,
  so `Quiet` and `Check` see it.
- **Packed / NDArray.** The int64 kernel `ndk_BitXor_ii` has a whole-buffer arm
  and sits on `AWARE` and `INT64_OK`. The n-ary array form is folded on the
  buffer inside the builtin, one pass per operand.
  `BitXor[Range[10^7], 5]` takes about 22 ms, on par with NumPy's
  `bitwise_xor`.
- **Compile[].** The new opcode `OP_BXOR_I` is folded left for any arity.

The compiler change that makes BitXor's array shapes lower is general:
- **Array ⊕ array.** `OP_V_KERN2` now accepts two arrays of the same rank and
  dispatches to `ndarray_map_binary2`, the routine the interpreter's kernel step
  already uses. The old refusal rested on a stale "no array-array map" premise.
- **N-ary arrays.** A Flat, Listable, Orderless head with a binary kernel is
  folded from an array operand, one kernel step per operand.

So `GCD[v, w]`, `LCM[v, w, 6]`, `ArcTan[v, w]` and the like now compile where
they used to send the whole body to the interpreter. An int/float result-dtype
mismatch from the promoting map declines to the interpreter, so no answer
changes.

`Infinity::indet`; it now declines non-finite endpoints, so the Gaussian–Bessel integral
returns `E^(-b^2/(4p))/(2p)` silently. The Beta stage accepts the wider convergence
strip that a `Log[1-x]^j` weight allows, and takes a limit where substitution gives 0·∞:
`Integrate[Log[x] Log[1 - x]/x, {x, 0, 1}]` is now `Zeta[3]`.

## `Series` expands Gamma-family heads at their poles; Mellin removable points ; v0.491

`Series[Gamma[s], {s, 0, n}]` and the `PolyGamma`/`Beta` analogues now expand at poles,
so `Limit[Gamma[s] Sin[s], s -> 0]` evaluates. The Mellin stage used this to take the
limit at a removable point instead of evaluating a 0·∞ form unmuted. The value
`Integrate[E^-x Sin[x]/x, {x, 0, Infinity}]` is now `Pi/4`, with no spurious
`Infinity::indet`, so `Check[]` no longer takes its failure branch.

## Half-integer `StruveH` is elementary; `D` rules for `StruveH` and `StruveL` ; v0.490

`StruveH[k + 1/2, x]` reduces to elementary functions (DLMF 11.4.4/11.4.5):
`StruveH[1/2, x]` gives `Sqrt[2]/(Sqrt[Pi] Sqrt[x]) - Sqrt[2] Cos[x]/(Sqrt[Pi] Sqrt[x])`.
Orders −9/2 to 9/2 were checked against reference values. `D[StruveH[nu, x], x]` is now
`(2^-nu x^nu/(Sqrt[Pi] Gamma[3/2 + nu]) + StruveH[nu - 1, x] - StruveH[nu + 1, x])/2`, and
`StruveL` has the analogous rule.

## Nielsen `PolyLog` real values stay real; `D[PolyLog[n, p, z], z]` ; v0.489

`PolyLog[0, 2, 2.]` came back with a spurious `-6e-16 I`: a small integer power of the

## `HypergeometricU[-n, b, z]` terminates to a polynomial ; v0.488

For a non-positive integer `a`, Tricomi U is a polynomial (DLMF 13.2.7):

## `?Minimize` / `?Maximize` describe the current scope ; v0.486

The docstrings now list the supported problem classes and the actual special return

## `Minimize`/`Maximize`: TimeConstraint bounds the whole call; separable, simplified, many-inequality, open-pole and polyhedral fixes ; v0.485

- **TimeConstraint.** It now bounds the whole call. One wall-clock deadline is set at entry
  and clamps every internal probe. A per-top-level decline memo stops the evaluator from
  re-running a declined call. Previously each stage got a fresh budget, and a declined call
  was re-run, so a 30 s default could become minutes.
- **Separable objectives under a constant factor.** A halved 3-variable Styblinski–Tang
  went from 141 s (then unevaluated) to 15 ms. A constant multiplier is spread over the sum
  before the separable split, and a variable-free denominator is no longer treated as a
  rational objective.
- **Simplified exact optima.** The value and each coordinate take the smallest of the raw,
  `Together` and `Expand` forms: `{14 - 2 Sqrt[13], {x -> 2 - 2/Sqrt[13], ...}}`.
- **More than 6 inequalities.** The `MZ_MAX_INEQ = 6` cap is replaced by the sound KKT
  bounds: active sets of at most n regular, or n+1 singular. A 3-variable 0/1 knapsack
  now solves.
- **Pole on an open boundary.** The denominator's sign is proved on the region itself,
  not its closure: `Minimize[{(x^2+1)/(x+1), x > -1}, x]` gives `-2 + 2 Sqrt[2]`.
- **Polyhedral regions.** Boundedness of a linearly constrained region is decided by 2n
  linear checks. An exact LP dropped from 2.3 s to 15 ms, and an equality-constrained case
  from 5.1 s to 57 ms.

The compiled lowering multiplied `x` by a 0/1 mask, so a chopped negative came back as

## A definite `Integrate` that succeeds no longer emits `Integrate::nonelem` ; v0.481

- **The bug:** `Check[Integrate[Log[1 + a^2 x^2]/(1 + x^2), {x, 0, Infinity}, Assumptions -> a > 0], failed]` printed `Integrate::nonelem` and returned `failed`, although the integral evaluates to `Pi Log[1 + a]`. Because the message marks the evaluation as failed, `Check[]` gave a wrong answer.
- **Cause:** a definite integral first tries an antiderivative (Newton–Leibniz). That probe runs a complete top-level indefinite cascade, and its exit flushed the held `nonelem` message as soon as the cascade declined. A later definite stage then answered, but the message had already been emitted.
- **Fix:** `src/calculus/integrate.c` now wraps the definite driver (`integrate_definite_scoped`). While a definite integral is running, a `nonelem` message from an indefinite probe (or from the depth-0 method surface) is passed up to a definite-level payload instead of being printed. The outermost definite frame emits it only if the whole definite call declined, so a definite integral that really fails (`Integrate[x^x, {x, 1, 2}]`) still reports it as before, and indefinite declines are unchanged.
- **Tests:** `test_no_spurious_nonelem` in `tests/test_integrate_diffunderint.c` covers the reported integral and the Bose integral `x^3/(E^x - 1)` (no message, `Check` returns the value), a definite integral that genuinely fails (caught, and silenced under `Quiet`), and an indefinite `Exp[x^2] Sin[x]` (still caught).

## `Unprotect` takes effect on every builtin (issue #103) ; v0.480

- **The bug:** for 154 builtins (`Sin`, `Plus`, `Hold`, `Set`, `Table`, …), `Unprotect` returned the name as if it had worked, but `Attributes` still listed `Protected` and assignments were still refused. `ClearAttributes` on those symbols was ignored the same way.
- **Cause:** their attributes came from the static `builtin_attrs[]` table in `src/attr.c`, cached per symbol as `base_attributes`. `get_attributes` returned `base_attributes | attributes`, so a cleared bit was put back on every lookup. - **Tests:** three cases in `tests/test_clearall_remove_protect.c`: `Unprotect`/`Protect` round trips on `Sin` and `Hold`, defining `Sec[42]` after `Unprotect`, and `ClearAttributes`/`SetAttributes` on `Cos` and `Range`. The expectations were checked against WL.

## Mixed exact and inexact arguments numericalize; the special-function numeric gaps closed ; v0.477

`Zeta[2., Sqrt[2]]` is now a number, as `Sin[2.]` is, and so is every special function given an inexact argument beside an exact irrational one. A sweep of 279 calls over every special function — all-machine, and with each argument in turn left as an exact irrational constant — was run against the reference. With the evaluator rule below already in, 42 calls still disagreed, all in heads that had no numeric path for those arguments at all. After the fixes below, two disagree, and they are a deliberate difference (`HarmonicNumber`, below). The new tests are in `tests/test_mixed_numericalize.c`; every expectation was verified against the reference.

### The evaluator rule

- When a `NumericFunction` builtin declines a call whose arguments are numbers, numeric quantities or Lists of them, with at least one inexact and at least one irrational exact argument, the evaluator calls it once more with the irrational arguments numericalized to the lowest precision among the inexact ones (machine precision being the floor). `numeric_mixed_args_call` (`src/numeric.c`) does this, and it is step 5a of `evaluate_step`.
- Integers and rationals are not converted, since they are often an index (`BesselJ[2, …]`, `ProductLog[1, …]`). `NHoldFirst` / `NHoldRest` positions are skipped. `Flat` heads keep their own contagion pass.
- A decline that emitted a message is not retried. A symbolic argument or a user-defined `NumericFunction` head leaves the call unevaluated, as in the reference.
- The rule fixed, among others:
  - `Zeta`, `BesselJ`/`Y`/`I`/`K`, `Gamma`, `Beta`, `PolyLog`, `Hypergeometric0F1`/`1F1`/`2F1`/`PFQ`/`U`, `ArcTan`, `Log[b, x]` and `Binomial`;
  - `Pochhammer`, `EllipticE`/`F`/`Pi`, `ExpIntegralE`, `HurwitzZeta`, `LerchPhi`, `Whittaker*`, `StruveH` and `MeijerG`;
  - the orthogonal polynomials.
- `Zeta[2.`30, Sqrt[2]]` gives 30 digits.
- Deliberate difference: `HarmonicNumber[Pi/3, 1.36]` evaluates. The reference evaluates the all-machine call but leaves the mixed one unevaluated.

### Heads that had no numeric path

- **`Surd` (new).** The real n-th root. Exact (`Surd[-8, 3] = -2`, `Surd[Sqrt[2], 3] = 2^(1/6)`), machine (`sf_surd_r`, shared by packed, `NDArray` and `Compile`) and MPFR.
  - Messages: `::noneg`, `::indet`, `::preal`, `::int`, `::argr` and `::argrx`.
  - An integer-valued real `n` is accepted (documented difference).
- **`KroneckerDelta` (new).** `NumericFunction` and `Orderless`. Identical arguments give 1, numeric arguments compare by `Equal`, and one unequal pair gives 0.
- **`Max` / `Min`** order real numeric quantities with the numbers and keep the winner exact: `Max[1, Pi] = Pi`, `Max[1., Pi] = Pi`. These stayed unevaluated before.
- **`HeavisideTheta` / `DiracDelta` with several arguments** (`src/internal/distributions.m`). A product: 0 or 1 by the signs. Positive arguments are dropped.
- **`StieltjesGamma`.**

  - `StieltjesGamma::intnm` for a bad order.
- **`ExpIntegralE`** of any real, complex or arbitrary-precision order goes through arb's `acb_hypgeom_expint`. Before, only integer orders at machine precision evaluated. `E_s(0.)` for `s ≤ 1` is `ComplexInfinity`.
- **`PolyGamma` of non-integer order**, in the reference's Riemann–Liouville convention:
  - It was fitted to the reference's values and then confirmed to about 22 digits; arb's own generalisation differs.
  - It is a new arb kernel, `flint_num_polygamma_frac`.
  - Integer orders that the ladder declined now also fall to arb.

  - Types 1 and 2 map to arb type 0; type 3 maps to arb type 1.
  - Checked inside and outside (-1, 1) and at complex `x`.
  - `N` of the four-argument form works; the type label `2.` is accepted.
- **`FactorialPower[x, n, h]`**, the step form, was never implemented.
  - It covers a positive integer, a negative integer or a non-integer `n` for numeric `x` and `h`.
  - `FactorialPower[5, -2] = 1/42` now evaluates.
- **`QPochhammer`.**
  - A non-integer `n` is `(a; q)_∞ / (a qⁿ; q)_∞`. A negative integer `n` is exact.
  - A complex or MPFR infinite product evaluates through arb; it used to be rounded to a double.

`MatchQ[f[1, g[]], f[_, n_.*a:_g]]` returned `False`; the reference gives the opposite. The
cause was the **parser**. `:` was an ordinary low-precedence infix operator, so
`n_.*a:_g` parsed as `Optional[n_.*a, _g]`, a different and silently wrong
pattern. In the reference, `:` takes its left operand at **atom level**: the bare symbol
(`Pattern`) or blank token (`Optional`) right before it. `parse_colon_suffix`
(`src/parse.c`) now attaches `:` in `parse_primary`. A `colon_hold` marker stops
an inner token from claiming the `:` that ends a `sym:p` operand (`a:b:c` is
`Optional[a:b, c]`). This was checked against 100 forms from the reference and
all agree, except two that the reference rejects and Mathilda still accepts leniently. The
forms include `n x_:0` → `Times[n, x_:0]`, `x + a:_g == b` →
`Plus[x, a:(_g == b)]`, `x?f:_`, `x|a:b` and `x:a:b:c:d:e`. A parse of all 646
tracked `.m`/`.wl` files with the old and new binaries found no change in real
code.

**Exhaustive corpus.** `tools/gen_match_exhaustive_corpus.py` crosses 18
construct families with shared subject sets. The families are Blank and head
patterns, sequences, nonlinear names, `sym:p` with every operator, Optional and
defaults, Alternatives, PatternTest/Condition, Repeated, Except/HoldPattern/
Verbatim, (Orderless)PatternSequence, Longest/Shortest, literal number
structure, KeyValuePattern, Orderless/Flat/OneIdentity heads, query heads at
level specs, definitions, and parse shapes. A named pattern is asked through
`ReplaceList`, which pins bindings, backtracking order and completeness, not just
yes/no. **Every expected value comes from a reference kernel**, with each
case in a fresh context. That gives 11,385 gating cases
(`tests/match_exhaustive_corpus.m`, ctest `match_exhaustive_corpus_tests`, about
35 s). Another 413 known divergences are annotated report-only cases in
`tests/match_exhaustive_observe.m`. An ordering-only divergence keeps a gating
multiset twin (`Sort[ReplaceList[…]] === Sort[{…}]`). The runner's parent no
longer polls on a fixed 20 ms sleep, which had put a 20 ms floor under every
case (at least 6 s for the old 300-case corpus, which now runs in 1.4 s).

**Matcher bugs the corpus found, all fixed and checked against the reference:**
- **Alternatives:** a name in a branch that was not taken is bound to
  `Sequence[]` once the whole match succeeds (`1 /. (x_ | y_) :> {x, y}` is
  `{1}`). A later occurrence can still bind it.
- **`sym:p` backtracking:** the name is bound first and `p` is matched with the
  real continuation. Before, `ReplaceList[2 x, p:x_.*y_ :> …]` found one of
  three matches.
- **OneIdentity** applies only through Optional/defaults, as in the reference. Before,
  `h[x_]` matched `x`, `h[a, b]` (as `x -> h[a, b]`) and, under Flat, `h[]`, and
  `h[a]` matched twice. A Flat head no longer repeats its default match
  (`x_. + y_` against `a + x`).
- **Orderless:** a literal element takes only the first equal argument
  (`ReplaceList[o[a, a], o[a, x_] :> x]` is `{a}`).
- **OrderlessPatternSequence** matches a contiguous run at its own position, in
  any order, and its elements may be sequence patterns. Before, it matched any
  subset anywhere: `f[1, 2, 3]` matched `f[3, OrderlessPatternSequence[1, 2]]`.
  Four hand-written corpus rows had encoded that and were corrected.
- **`x__..`** and other variable-width repeats backtrack into their unit split
  through a continuation (`ReplaceList[f[a, a], f[x__..] :> {x}]` is
  `{{a}, {a, a}}`). The sequence commit step is shared (`seq_commit`).
- **Level specs:** a mixed spec like `{2, -1}` matched nothing in `Cases`,
  `Count`, `Position`, `DeleteCases` and `MemberQ`. One `in_level_spec` helper
  replaces five copies, and it walks `Depth` only when a bound is negative.
- **Redefinition:** an alpha-equivalent left-hand side replaces the rule
  (`f[x_] := x^2; f[y_] := y^3` is one rule). Each rule stores an alpha-invariant
  hash, so 3,000 distinct definitions cost the same as before.
- **Dispatch arity:** `PatternSequence`, `OrderlessPatternSequence`,
  `Longest`/`Shortest` and sequence-branch `Alternatives` arguments make a
  DownValue variable-arity. `q[PatternSequence[a_, b_], c_]` never fired before.
- **`OptionsPattern[{o -> v}]`:** inline defaults are used by `OptionValue`.
- The hand-written corpus row `1 /. (x_ | y_) :> {x, y}` → `{1, y}` had been
  written from memory and was wrong; it now expects `{1}`.

**Known, recorded, not fixed here.** The reference's `ReplaceList` enumeration under Flat
without OneIdentity wraps one-operand slices both ways and repeats matches.
Orderless enumeration *order* with Optional elements follows the reference's canonical
order, which sorts patterns after other expressions; Mathilda's `expr_compare`
does not (`Sort[{{2, x}, {1, 2 x}}]` also differs). SubValues
(`f[x_][y_] := …`) are not implemented. `SequenceCases` and `SequencePosition`
are missing.

## Documentation site: formulae blank after in-site navigation

Most formulae on the docs site rendered blank when a page was reached by
clicking a link (Material's `navigation.instant`), though a direct load or

Verified in headless Chrome over a five-page instant-navigation chain and a

## Number-theory review, batch 6: partitions ; v0.474

This applies the DivisorSigma review to `IntegerPartitions`, `PartitionsP` and `PartitionsQ`. Expectations were verified against the reference; the new tests are in `tests/test_partitions_review.c`.

### IntegerPartitions

**Semantics fixed**:
- **A negative length step** (`{6, 2, -2}`: lengths 6, 4, 2) was read as step 1.
- **A number as the part spec** (`IntegerPartitions[6, All, 2]`, parts `Range[2]`) was unevaluated.
- **`m`** accepts `None` and Take sequences (`{3}`, `{2, 4}`, `{1, -1, 3}`). A sequence past either end clamps with `::take` (`{2, 30}` of 11 rows is rows 2–11).

- a range-mode walk with no part list, which also serves `IntegerPartitions[10^7, {2}]`;
- an ascending-list walk;
- an int64 count-vector walk for unsorted or repeated lists.

The results match the reference on 11,083 grid cases over n, length spec, part spec and m, and on 4,800 unsorted and repeated part-list cases.

### PartitionsP and PartitionsQ

- **Small n**: `p(n)` and `q(n)` for `n < 1000` come from tables filled once at startup (under a millisecond). Before, every call reran the O(n^1.5) recurrence:

## Number-theory review, batch 3: primes ; v0.472

This applies the DivisorSigma review to `Prime`, `PrimePi`, `NextPrime`, `PrimeQ`, `PrimeNu`, `PrimeOmega` and `PrimePowerQ`. Expectations come from the reference.

### Prime counting: a tuned Deleglise–Rivat

`PrimePi`'s `Automatic` method is now a properly tuned Deleglise–Rivat (`src/numbertheory/primecount.c`).
- **Tuning**: $y = \alpha x^{1/3}$ with $\alpha = 0.0008\ln^3 x$.
- **Trivial leaves** are counted rather than visited.
- **Easy leaves** come from the π table, and above √z only prime $m$ are walked.
- **Hard leaves** (only at levels with $p_{b-1} \le \sqrt z$) use a bitset sieve with monotone popcount sweeps in place of a Fenwick tree.
- **Quotients** come from a precomputed reciprocal with an exact correction.
- **The fix that made α > 1 correct**: the old easy-leaf formula $\varphi(v, b-1) = \pi(v) - b + 2$ is only valid for $v \ge p_{b-1}$; below $p_b$ the right value is $\varphi = 1$.

## `DivisorSigma`: options, messages, docstring, and a performance pass ; v0.470

These are review fixes to `DivisorSigma` (`src/numbertheory/divisorsigma.c`). Every expectation was checked against the reference. See `docs/spec/builtins/number-theory.md`.

- **Options.** `Options[DivisorSigma]` was `{}` and is now `{GaussianIntegers -> False}`.
- **Messages.** These now match the reference, all through the `Quiet`/`Check` funnel:
  - one argument gives `argr` (it used to give `argrx`); no arguments give `argrx`;
  - a third positional argument gives `nonopt`;
  - an unknown option gives `optx` (it used to be silent);
  - a `GaussianIntegers` value that is not Boolean, including `Automatic`, gives `opttf` (it used to be silent).
  - `RuleDelayed` options are accepted, and of repeated settings the first wins (it used to be the last).
- **Docstring.** It now covers both call forms, what each kind of `k` gives, the domain of `n`, and the option.
- **Attributes.** They stay `{Listable, NHoldAll, Protected}`, which is what the reference reports.

### Performance

The scalar builtin no longer builds and evaluates a `Times`/`Power`/`Plus` tree for a machine `k`.

- **Machine integer `k`.** The answer comes exactly from the factorisation, in int64 through the shared helper `ndint_divisor_sigma_i64`, or in GMP by a Horner sum. A negative `k` uses `sigma_-k(n) = sigma_k(n)/n^k`.
- **Machine real `k`.** The answer is computed in `double` by a Horner sum per prime. That is more accurate than the closed form it replaces: at most 5.8 ulp from a 40-digit reference over `n <= 3000`, where the closed form reached 31 ulp at `k = 3.7`.
  - **One deliberate difference from the reference:** `DivisorSigma[0., 6]` is now `4.`. The closed form gives `0/0`, so it was `Indeterminate`, here and in the reference.
- **Packed and NDArray `int64` buffers.**
  - The per-element kernel raises `p^k` once per prime instead of once per exponent step.
  - A large buffer now builds one table of smallest prime factors, at one byte per integer of range. It does this through a new optional whole-buffer arm on `NDBinaryKernel` (`whole_i`, used by `ndarray_map_binary`). The rule for when to build the table was measured: always below 4·10⁶; up to 5·10⁷ once the buffer has at least `4 sqrt(max)` elements; never above 5·10⁷. Before this, every element was factored by trial division, so the cost grew as N^1.5.
- **`Compile`.** The scalar form `DivisorSigma[k, x]` now lowers, to a new `OP_DSIG_I` that calls the same helper. When the helper declines, `OP_DSIG_I` bails to the interpreter unconditionally, so `IF_NOCHK` cannot waive the bail. DivisorSigma is out of the `check-compile-coverage` baseline.

## New builtin: `PrimePowerQ` ; v0.469

`PrimePowerQ[expr]` and `PrimePowerQ[expr, GaussianIntegers -> v]` (`src/facint.c`, `Listable | Protected`, `Options -> {GaussianIntegers -> Automatic}`). It covers integers up to sign, rationals (via the reciprocal), Gaussian integers and Gaussian rationals. All 183 generated test expectations, and the hand-written ones, come from the reference, including its `argt`/`exact`/`nonopt`/`optx`/`opttfa`/`par` messages and its `GaussianIntegers :> v` quirk (always `False`). See `docs/spec/builtins/number-theory.md`.

- **One primality test per input.** The new shared kernels are `mth_prime_power_base_u64` and `mth_prime_power_base_mpz` (`src/facint.h`; they also report the prime base, which the Gaussian rule needs).
  - **Machine integers:** trial division by the odd primes below 64, then one deterministic Miller–Rabin test, then exact roots for k ∈ {2, 3, 5, 7}.
  - **Bignums:** trial division by the primes below 2^10 (one `mpz_remove` on a hit), then reduction to the primitive root, then one `PrimeQ` test on that root. The reduction uses FLINT `fmpz_is_perfect_power`, or GMP `mpz_perfect_power_p` + `mpz_root` under `USE_FLINT=0`.

A real buffer degrades element by element so that `::exact` fires per element. A new `primepowerq` probe in `tools/numeric_sweep.py` confirms that the plain, packed and NDArray surfaces agree.
- **Compile.** The new `OP_PPQ_I` opcode (int to `CT_BOOL`) calls the same helper, so the scalar form compiles and matches the interpreter bit for bit for every int64, including `INT64_MIN`. The direct array form `PrimePowerQ[v]` joins `Positive`/`EvenQ` in `tools/compile_coverage.py` `BASELINE`, because the int-to-bool elementwise array lowering does not exist yet. `Table[PrimePowerQ[v[[i]]], ...]` does compile.

## New builtin: `RandomPrime` ; v0.468

## Parser and matcher: `0..` and Repeated / RepeatedNull (issue #100) ; v0.467

`0..` was a parse error: the number lexer read `0.` as a real and left a stray `.`. `0...` silently became `Repeated[0.]`. Every expected value in the new tests comes from the reference.

- **Tokenization.** `..`/`...` win over a decimal point, so `0..` is `Repeated[0]`, `0...` is `RepeatedNull[0]`, `-1..` is `Repeated[-1]`, and `1..2` is `(1..)*2`. `1.5..` and `.1..` are unchanged. The same fix applies to precision literals: `2.5`10..` is `Repeated[2.5`10]`. Headed and sequence blanks now take the dots as the repeat operator: `{_Integer..}`, `x__..` and `_h...` were syntax errors. As in the reference, a bare `_.` is still Optional, so `_...` is `(_.)..` and `_..` stays a syntax error. `Repeated[_]` now prints as `(_)..` so that it reads back.
- **Multi-argument units.** `{a, b, a, b}` now matches `{PatternSequence[a, b]..}` (it was `False`). The repeat bounds count units (`Repeated[PatternSequence[1, 2], {2}]` takes four arguments). `(PatternSequence[a, b] | c)..` and `{x__..}` work, with each repetition binding the same `x`. Fixed-width units are checked in one pass. The variable-width search is iterative and tries only feasible widths, so a failing match over 40 000 arguments takes milliseconds.
- **Sequence alternatives.** `MatchQ[{a, b, d}, {PatternSequence[a, b] | c, d}]` is `True`. Named alternatives (`x:(PatternSequence[a, b] | c)`) bind the consumed sequence.
- **Repeat specs.** `Repeated[p, -1]`, `Repeated[p, {a, b}]` and `Repeated[p, {2.5}]` used to match as if unbounded. They now issue `Repeated::range`, and `Repeated[p, {3, 2}]` and `Repeated[p, 0]` issue `Repeated::order`; all of them match nothing. The messages go through the message funnel, so `Quiet` and `Check` apply. A BigInt bound is treated as unbounded instead of overflowing an `int`.
- `Repeated` and `RepeatedNull` now have the `Protected` attribute.
- New suite `tests/test_repeated.c`, with 107 checks of reference-verified answers. `test_parse.c` gains `test_parse_repeated_tokens` and a print round-trip check.

## Parser: prefix `+` (issue #101) ; v0.466

`+x` was a parse error (`Unexpected character: '+'`); a leading `+` was only
accepted as the sign of a numeric literal. It now parses as in the reference
Language, to a one-argument `Plus`, which the evaluator reduces to its operand:

- `+x` evaluates to `x`; `FullForm[Hold[+x]]` is `Hold[Plus[x]]`.
- The operand binds tighter than binary `+` and looser than `*`/`^`:
  `+a b` is `Plus[Times[a, b]]`, `+a^2` is `Plus[Power[a, 2]]`, and
  `+x == y` is `Equal[Plus[x], y]`.
- A signed literal is unchanged (`+5` is the integer `5`), as is `++x`
  (`PreIncrement`).

## Correctness/performance: the v0.464 limitations closed; Reduce transcendental roots; InputForm round-trip ; v0.465

- **Reduce over the reals with transcendental breakpoints.** `Reduce` now solves univariate exp-trig-polynomial inequalities and equations whose roots `Solve` cannot find. It isolates the real roots with certified arb interval arithmetic on a provably bounded region and returns them as exact rationals or as transcendental `Root[{f, x0}]` objects. `Reduce[Sin[x] > x/2, x, Reals]` gives `x < Root[{#1 - 2 Sin[#1] &, -1.89549}] || 0 < x < Root[{#1 - 2 Sin[#1] &, 1.89549}]`, as the reference does. Infinitely many roots (`Sin[x] > 0`) or no provable bound still leaves Reduce unevaluated. `Root[{f, x0}]` is certified by interval Newton, refines to any precision under `N`, canonicalises x0 and its body, and gives `Root::invrt` for an x0 that is not at a root. A six-digit printed x0 reads back.
- **Reduce input normalisation.** `Not[a > b]` folds to `a <= b`, with De Morgan through `And` and `Or`, and over Reals a relation side carrying `Re`/`Im`/`Conjugate` is ComplexExpanded. A residual that vanishes on a whole interval (`ArcCos[1 - 2 x^2] - 2 ArcSin[x]` on [0, 1]) is decided cell by cell instead of burning the isolation budget. This restores `Refine[Cos[x] > 0, -Pi/2 < x < Pi/2] = True`, `Simplify[ArcCos[1 - 2 x^2] - 2 ArcSin[x], 0 < x < 1/2] = 0` and `Simplify[Sqrt[E^(2 I x)] - E^(I x), -Pi/2 < x < Pi/2] = 0`. All three had regressed in v0.464, which had removed the unsound one-sample shortcut that had decided them by luck.
- **Rules on ordered Flat heads are cheap again.** A failing rule on `**`, `Dot`, `And`, `Or` or a user `Flat` head paid a full match at every start offset after v0.462: seconds at n = 100 for `ff[x_, y_, x_]`, and n³ for `And[x_, Not[x_]]`. Offsets and spans that cannot match are now skipped using the pattern's first single-operand element as an anchor, and a group that cannot equal an already-bound name is rejected without being built. Repeated-name and anchored rules now cost about what v0.461 did. `PatternSequence[...]` elements now also match interior runs.
- **FactorInteger: bignum Fermat and Lehman.** The Fermat residue filter tests 64 candidates per block with precomputed bit masks: 0.5 ns per value instead of 10 ns. The Lehman sweep gives k = 1 about 5/6 of each round, and a larger "Iterations" never finds less. Near-square factors are cheap again (NextPrime[10^25]·NextPrime[10^25+10^16] takes 2.5 ms, against 77 ms in v0.464), and ratio-3, 5/7 and 2/3 factors stay at a few ms. The default Lehman budget is now 2^28.
- **InputForm round-trips machine reals.** `InputForm`/`FullForm` and `ToString[_, InputForm]` print a machine real as the shortest decimal that reads back to the same double (6 digits before), with the machine mark `` ` `` on a 17-digit mantissa and `*^` exponents. A machine `*^` literal now parses with one correct rounding (`1.5*^-5` was one ulp off).
