# Changelog: week of 2026-11-09 (Mon) – 2026-11-15 (Sun)

## Build: MacPorts dependencies are detected
- The makefile and the CMake test build now find libraries installed with
  MacPorts. The prefix comes from the `port` command on `PATH` (usually
  `/opt/local`), or from an explicit `MACPORTS=<prefix>`. Its `include`, `lib`
  and `lib/pkgconfig` directories are added to every dependency probe
  (gmp/mpfr, GMP-ECM, SuiteSparse, ARPACK, and the pkg-config probes for
  FLINT, PCRE2, FFTW and Raylib).
- MacPorts' GNU Readline is used in preference to Apple's libedit shim.
- The MacPorts GCC names `gcc-mp-16` … `gcc-mp-13` are tried after Homebrew's
  `gcc-NN`.
- When both are installed, the one that provides GMP owns the build, so two
  GMPs never meet in one link. If Homebrew has `gmp`, MacPorts is not
  auto-detected, and existing Homebrew builds get exactly the same flags as
  before. If Homebrew lacks `gmp`, MacPorts is added. (A first version of this
  change ignored MacPorts whenever any `brew` existed. That broke a
  MacPorts-based Mac which also had a Homebrew holding only fftw.)
  Mathilda installs its own GMP allocator (`mp_set_memory_functions`), which
  only one copy of GMP would get, so mixing the two is not merely untidy.
- MacPorts is never skipped silently. When it is installed but ignored because
  Homebrew provides GMP, `make` prints a notice with the switch to use it
  instead: `make HOMEBREW= SYSTEM_PREFIX=`. On an Intel Mac Homebrew is
  `/usr/local`, which is also `SYSTEM_PREFIX`, so both must be cleared.
  `MACPORTS=` (empty) opts out and silences the notice. No version bump (build
  tooling only).

## Build: compiles against FLINT 3.0 again (Ubuntu 24.04 LTS)
- `src/linalg/flint_mat_bridge.c` (exact `QRDecomposition`'s square-part
  split, v0.6368) called `fmpz_divisible_ui`, which FLINT only added in 3.1.
  Ubuntu 24.04 ships FLINT 3.0.1, so the build failed there with an implicit
  declaration error. It now calls `fmpz_divisible_si`, which exists in every
  FLINT 2.x/3.x. The CI runner's FLINT (3.4) is too new to see this. Every
  FLINT-using source was syntax-checked against the 3.0.1 headers, and this was
  the only such call. Reported by email; v0.6469.

## Tooling: the xeus kernel takes its link line from the makefile (issue #131)
- New `make print-libs`: one stdout line, the exact transitive link libraries
  of `libmathilda.a` for the given `USE_*` flags (the same words the installed
  `mathilda.pc` carries as `Libs.private`).

  `MATHILDA_MAKE_FLAGS`) instead of guessing the set with `find_library`, which

  of `xmathilda` failed with undefined references to SuiteSparse, ARPACK and
  LAPACKE/FlexiBLAS symbols the makefile had detected. `MATHILDA_EXTRA_LIBS`
  still pins an exact list; empty (the new default) means "ask the makefile".

  using only `make print-libs` and runs it. Build-only; no version change.

## Tooling: `make check-install` runs the installed executable (PR #130)
- `tools/check_install.sh` gains a CLI step: the installed `bin/Mathilda`,
  run from outside the source tree with `MATHILDA_HOME` unset, must print
  `4` for `2 + 2`, `0` for `HeavisideTheta[0]` (proving the bootstrap modules
  loaded), and the canonical (`pwd -P`) install prefix for
  `$InstallationDirectory`. Previously only the embedding library was run
  from an install, so a startup crash in the executable alone (issue #129)
  went unseen. Contributed by Rolf Mertig. Test-only; no version change.

## AppellF1, AppellF2, AppellF3, AppellF4 (v0.6485)
- New heads (Listable, NumericFunction, Protected; docstrings; spec entry in
  `special-functions.md`): the four Appell functions of two variables, in the
  reference system's argument order. Files `src/special_functions/appell.c`
  (builtins, exact rules, machine kernel, the expansion planner) and
  `appell_arb.c` (ball arithmetic), `flint_num_appell` / `flint_appell_d` on the
  shared precision ladder.
- Exact rules: `x = 0`, `y = 0` and vanishing parameters to `Hypergeometric2F1`;
  F1 also `x = y`, `a = c`, `c = b1 + b2`, `x = 1`, `y = 1`, `a = 0` and the
  polynomial for a negative integer `a`. `D` in `x` and `y` by the
  contiguous-parameter formulas; parameter derivatives stay inert.
- Numerics: one outer series whose terms carry the analytically continued Gauss
  function of the other variable; F1's five Euler substitutions (two valid on one
  side of an extra ray only, the sector test checked against the integral) and
  F2's three Pfaff transformations pick the smallest outer ratio; the inner
  functions by a three-term recurrence in `m` in its stable direction (four
  recurrences, derived and checked numerically), one by one when its roots are
  close. F1 with no convergent expansion is its Euler integral (endpoint series
  plus `acb_calc_integrate`), cuts from below.
- Surfaces: n-ary ND kernels (scalar == packed == `NDArray` == `Compile[]` scalar
  and rank 1, real and complex, bit for bit); rows in the arbitrary-precision
  compile registry; `compile_coverage.py` shapes and precision bodies. All of
  `check-c99`, `check-messages`, `check-packed-aware`, `check-array-exactness`,
  `check-nd-surfaces`, `check-compile-coverage` (both passes) green.
- Found on the way: FLINT 3.6's `acb_hypgeom_2f1` returns an indeterminate ball for
  `2F1(-0.0721, 1.15; 102.33; 0.514 - 0.614 i)` (a large `c` inside the unit disk);
  the Appell start values therefore use their own direct series there. Complex
  ball products wrap (up to √2 a step), so long products run on midpoints with an
  explicit bound. mpmath's `appellf3`/`appellf4` lose digits near the region
  boundaries (`appellf4(0.3, 0.2, 1.5, 1.7, 0.2, 0.3)` = 1.1075 at 60 digits; the
  value is 1.0248673980), and the reference system's F1 at `(10., -20.)` is wrong
  in the sixth digit.
- Accuracy vs mpmath (400 points): machine median 0.4-1.0 ulp, max 5-45 ulp; 30
  digits within `1.5*10^-35`. Timings: scalar 3-5 µs (wolframscript 0.9-7 ms,
  mpmath 1.5-6 ms); 50 digits 0.5-1.1 ms (wolframscript 1.5-5.2 ms, mpmath
  8-23 ms); 10^6 packed 1.3-5.4 s (F3 38 s on its arb route). Open: F2/F3/F4
  beyond their series regions, the hard F3 arb route, the integer-parameter
  closed forms.
- Tests: `tests/test_appell.c` (7 groups; 28 reference points, reductions,
  contiguous relations, the F1 and F4 PDEs, D, buffers / `NDArray` / `Compile[]`,
  arbitrary-precision `Compile[]`). valgrind: definitely lost identical 1x / 4x
  (13,504 B startup baseline).

## RandomChoice: batched draws (v0.6468)
- The packed `RandomChoice[list, n]` / `RandomChoice[w -> list, n]` producer
  now draws its indices a block at a time with the generator state held in
  registers: `RandomChoice[{1., 2.}, 10^6]` takes ~1.6-2.5 ms (was ~6 ms;
  numpy's `default_rng(1).choice` takes ~18 ms on the same machine).
- The draws are unchanged: a seeded batch equals the same number of single
  `RandomChoice` calls and leaves the generator in the same state.
- `Log` over a packed array was measured against numpy too. It already runs
  at the libm floor (~5.6 ms per 10^6, numpy ~6.4 ms). A correctly rounded
  table-driven log was prototyped and is slower than libm on this hardware,
  so `Log` is unchanged.

## NSum: step-function and digit-length summands (v0.6467)
- A summand defined through `Round[n]` (or `Floor`/`Ceiling`) is recognised as a
  step function of the index and no longer goes to Euler–Maclaurin:
  `NSum[h[n], {n, 1, Infinity}]` with `h[n_?NumericQ] := 1/Round[n]^2` is now
  π²/6 to machine precision (was 1.62533), `Σ 1/(n IntegerLength[n]^2)` is
  4.325970846720485 (was 3.32572, no warning).
- New integer-series engine (`src/numerical_calculus/nsum_blocks.c`) for
  integer-only summands: Levin u from the best start for a smooth head; for a
  head smooth on geometric blocks `b^(k-1) <= n < b^k` (digit/bit-length
  summands) the sum becomes the series of block sums, each by Euler–Maclaurin
  in `log n` over interpolated integer samples, summed recursively.  Exact to
  the target at machine precision and `WorkingPrecision -> 60` for
  `1/(n IntegerLength[n]^2)`, `1/(n BitLength[n]^2)`, `1/(n IntegerLength[n]!)`,
  `(-1)^BitLength[n]/(n BitLength[n])`, `1/f(n)` with `f(n) = n^2 f(BitLength[n])`.
- Structures nested past any reachable index return with an `NSum::accgl`
  error that brackets the true sum instead of a confident wrong value.

## Fold / FoldList: inner pure functions, exact rationals (v0.6466)
- A pure function applied inside a fold body is beta-reduced before
  compiling. An example is `{#1[[2]], g[#1, #2]} &` with `g` a `Function`.
- Rational constants, seeds and negative integer powers fold exactly in
  GMP rationals. A division by zero still goes through the interpreter,
  with its message.
- SIAM D10 50-digit cases are 5–11× faster.

## RandomChoice: array-valued choices pack (v0.6465)
- If every choice is an array of the same shape with one machine element
  type, `RandomChoice[w -> {{3, 1}, {3, -1}}, n]` and its uniform form now
  return a packed `n × 2` array (or `dims ++ cellShape` in general).
- The draw sequence is unchanged, so a seeded run gives the same values.
- On 10⁶ pairs: 35 → 20 ms, and consumers such as `FoldList` read the buffer
  directly.

## Fold / FoldList: compiled rows, vector states and exact folds (v0.6464)
- The automatic compiled fold loop now covers four more shapes. The result
  is bit-identical to the interpreter's in each case.
  - **Elements that are rows**, read through constant parts (`#2[[j]]`). On
    10⁶ pairs, `FoldList[#2[[1]] + #2[[2]]/#1 &, 1., pairs]` takes 34 ms
    (was 1.33 s).
  - **Exact rows with a `Real` accumulator**, when every value the body
    computes carries the accumulator.
  - **Vector accumulators** `{x1, ..., xA}` with a `List` body. In doubles, a
    pair state over 10⁶ steps takes 55 ms (was 1.67 s), and the history is a
    packed `(n+1) × A` array.
  - **Exact-integer folds**, scalar or vector, in GMP. A pair recurrence over
    10⁴ steps reaching 4,739 digits takes 3.1 ms (was 33 ms).
- SIAM D10 (random-recurrence constants) moves from 3–13× slower than scipy
  to faster than it at machine precision, and within 1.3× at 50 digits.

## GroebnerBasis: Method -> "F4", Method -> "Buchberger" (v0.6463)
- `Method -> "F4"` computes every basis over Q from F4 at each prime of the
  multi-modular routes, skipping the direct run.
  - The primes are combined by CRT and rational reconstruction, then
    certified.
  - If F4 does not cover the case (for example
    `CoefficientDomain -> Integers` or `MonomialOrder -> EliminationOrder`),
    you get the Buchberger basis with a `GroebnerBasis::f4na` note.
- `Method -> "Buchberger"` now switches F4 off. Before, it ran the same
  engines as `Automatic`.
- `Automatic` is unchanged: F4 for every basis over GF(p), Buchberger
  elsewhere.
- The docstring now names all four methods and states that F5 is not
  implemented. It also corrects two stale claims, about the default method
  and about `Modulus` falling back to the rational basis.

## Lookup: Key[k] inside a key list (v0.6462)

## Element: exact constants in Integers, Rationals, Algebraics (v0.6461)
- `Element[x, dom]` for an exact constant `x` and `dom` one of `Integers`,
  `Rationals` or `Algebraics`:
  - **Algebraic constants** decide from their canonical algebraic (qqbar)
    form. `Element[Sqrt[2], Rationals]` is `False`;
    `Element[(1 + Sqrt[2])^2 - 2 Sqrt[2], Integers]` is `True`.
  - **One-atom transcendentals** are `False` in all three domains: any
    `c0 + c1 T^k` with algebraic coefficients and `T` one of `Pi`, `E`,
    `Log[r]` or `E^r`. Examples: `Element[Log[2], Rationals]`,
    `Element[1 + 3 Pi^2, Algebraics]`.
  - **Anything else** is left unevaluated, because no proof is implemented:
    `Pi + E`, `E Pi`, `EulerGamma`.
- This was found by SIAM holdout B (bd20 wp50), where a
  `Which[Element[Log[2], Rationals], ...]` branch never decided.

## NIntegrate: Bessel products on a half line; machine I kernel segfault; I^(n/2) sign (v0.6470)
- **Segfault (B4).** `NIntegrate[BesselI[5/6, x/5] BesselJ[3/8, 5/8 x] BesselK[5/6, x/5], {x, 0, Infinity}]`
  crashed. The machine `I_nu` Miller recurrence (`sf_machine_bessel.c`) sized
  its start index `N = nu + |z| + ...` with an `int` cast; for an exp-sinh node
  far out on the half line (`|z|` ~ 10^300, where the Hankel branch declines
  because `e^z` overflows) the cast overflowed to `INT_MIN`, passed the
  `MILLER_MAXN` test, and the loop indexed `w[]` from about -2^31. The bound is
  now checked in double before the conversion (the kernel declines to MPFR).
- **Wrong value with no clear signal (B3).** Products of Bessel functions on
  `[a, Infinity)` at machine precision went to the zero-to-zero + Wynn
  fallback, which has no model for several frequencies at once (`J_mu J_nu` has
  `e^(+-2ix)` and a non-oscillating part): `J_{7/4} J_{3/4}` of `7x/4` gave
  `0.6305` (true `2/7`), `J_0 J_1` `0.5205`, `J_3 J_0` `-0.49947` (no message),
  `J_{1/2} J_{3/2}` `0.49989` (no message). Such integrands now take the
  WorkingPrecision contour rotation (each Hankel group on its own decaying ray)
  at ~24 digits and round to machine; a product of circular functions of
  several frequencies takes it after exp-sinh fails. A rounding-level imaginary
  part of a real integrand is dropped. `BesselI` of a real-linear argument is
  admitted in the rotated amplitude, so the B4 integrand is now exact to all
  digits: `0.928235622639061296138394194801` (30 digits, matching a
  zeros-plus-Levin summation in mpmath; mpmath's own `quadosc` is off at 1e-7).
- **`(+-I)^(n/2)` was reduced mod 4 instead of mod 8** (`power.c`), so `I^(5/2)`
  evaluated to `I^(1/2)` and `I^(-9/2)` to `I^(3/2)` -- a sign error in every
  product of fractional `I` powers. This is what made the WorkingPrecision
  rotation return complex garbage for fractional orders
  (`NIntegrate[BesselJ[5/4, x] BesselJ[1/4, x], {x, 0, Infinity}, WorkingPrecision -> 20]`
  was `0.3447 - 0.0608 I`; it is `1/2`).
- **`|z|` beyond the double range in the MPFR Bessel kernels.** `bessel_hankel_plan`
  rejected `rz = Inf`, which sent `K` (and `I`, `J`, `Y`) at an astronomically
  large MPFR argument to the power series with a 300000-bit guard -- minutes per
  sample; `NIntegrate[BesselJ[1, x] BesselJ[1, 3 x]/x, ...]` hung. The leading
  asymptotic term is exact there.
- Validated against closed forms (G&R 6.512.3 `1/(2a)`, Weber-Schafheitlin,
  `-(2/Pi) ArcSinh[1]/Sqrt[2]` for `e^-x Y_0`) and mpmath on 15 cases
  (`tests/test_nint.c: test_bessel_products_halfline`,
  `tests/test_power_integer_radical.c: test_i_half_integer_powers`).
- Open: divergent products (`J_{5/2}(3x) J_{1/2}(3x)`, `J_0(x) J_0(2x)/x`,
  `J_{1/3} J_{2/3}`) are not detected as divergent; they run to the time limit.

## D through Sum / Product; applied derivatives of built-ins; Bessel order derivative (v0.6471)
- **`D` threads over `Sum` / `Product`** (`deriv.c`). `D[Sum[x^k/k, {k, 1, n}], x]`
  used to go through the generic chain rule and give
  `x^(-1 + k) Derivative[1, 0][Sum][x^k/k, {k, 1, n}]` -- the bound index
  leaked. It is now `Sum[x^(k - 1), {k, 1, n}]` (which closes to
  `(x^n - 1)/(x - 1)`); a `Product` gives `Product[f] Sum[D[f]/f]`. A limit
  that depends on `x` leaves the `D` unevaluated.
- **`Derivative[n..][f][args]` for a built-in `NumericFunction` `f`** evaluates
  to its closed form, as `D` gives it: `Derivative[1][Sin][x]` -> `Cos[x]`,
  `Derivative[0, 1][BesselJ][n, z]` -> `(BesselJ[n - 1, z] - BesselJ[n + 1, z])/2`,
  `Derivative[1][Gamma][0.5]` -> `-3.48023`. Before, every applied derivative of
  a built-in stayed inert, so `N[Derivative[0, 1][BesselJ][3/8, 5/8]]` was
  unevaluated (now `0.247419323528419`, mpmath). The closed form is memoised per
  operator; a derivative with no closed form, and any user symbol, stays inert.
- **Order derivative of the Bessel functions.** `Derivative[1, 0][BesselJ|BesselI][nu, z]`
  (any order) and `[BesselY|BesselK]` (non-integer order) have numeric values at
  inexact arguments, from arb's power series of `0F1~(; nu + t + 1; -+z^2/4)` in
  the order (`flint_num_bessel_order_deriv`, rigorous ball, precision ladder):
  `N[Derivative[1, 0][BesselJ][3/8, 5/8]]` = `-0.6916337659766911`, at 30 digits
  `-0.691633765976691104277513251373` (mpmath `diff` agrees to all digits; I, Y,
  K also checked). Note `Derivative[0, 1]` is the derivative in `z`, as in the
  reference.
- Tests: `tests/test_deriv.c` (`test_d_through_sum`, `test_builtin_applied_derivative`).

## Integrate: wrong answers from a missed square and from PossibleZeroQ sample aborts (v0.6473)
- **`Integrate[1/(Sqrt[b^2 + c^2] + b Cos[x] + c Sin[x]), x]` was `0`** (G&R
  2.558.4d), after `Power::infy` / `Infinity::indet`. Through `u = Tan[x/2]`
  the denominator is `(A - b) u^2 + 2 c u + A + b`, `A = Sqrt[b^2 + c^2]`, a
  perfect square only through `A^2 = b^2 + c^2`. Hermite reduction's gcd
  (`PolynomialGCD`, which treats `A` as a free variable) missed it, and
  Rothstein-Trager divided by the zero discriminant. With a symbolic radical in
  the coefficients the Hermite gcd is now Euclid's algorithm with every
  remainder put over a common denominator, so `Sqrt[p]^2 -> p` decides
  (`intrat.c`). The answer is `-2 Cos[x/2]/(c Cos[x/2] + (Sqrt[b^2 + c^2] - b) Sin[x/2])`
  after Simplify, i.e. `-2/((A - b) Tan[x/2] + c)`.
- **PossibleZeroQ reported `True` when its first sample was uninformative**
  (`zero_test.c`). A point whose value is `Indeterminate` only by rounding
  (`Coth[63.9]` is exactly `1.0`, so `(-1 + Coth[x])^(3/2)` in a denominator is
  `1/0`) or an `Overflow[]` residue aborted the sampler to UNKNOWN, which the
  builtin reports as `True`. Both are now re-drawn like an IEEE overflow. That
  is how wrong antiderivatives passed Integrate's differentiate-back verifier:
  `Integrate[Cosh[x] Coth[x]^2, x]` came out as the NEGATIVE of the true
  antiderivative (G&R 2.423.39; now the correct `Sinh - Csch`, still in a
  `Coth`-radical form), and `Integrate[Sinh[x]/Sqrt[Sinh[x]^2 - 49/16], x]`
  (G&R 2.462.3b instance) was wrong on `x > ArcSinh[7/4]`. The G&R 2.462.10
  instances (`Cosh/Sqrt[a^2 + Cosh^2]`) now differentiate back at the corpus
  points, and the 2.619 `Sqrt[-Cos[2 a x]]` instances are left unevaluated
  rather than returned with a spurious factor `I`.
- Tests: `tests/test_intrat.c: test_square_through_symbolic_radical`,
  `tests/test_zero_test.c: test_uninformative_points_are_redrawn`.
- Open (B9): `Integrate[1/(Sqrt[a + b x] (alpha + beta x)), x, Assumptions -> beta (a beta - b alpha) > 0]`
  ignores the assumption when choosing `ArcTan` vs `ArcTanh`, so it returns the
  `ArcTan` form with `Sqrt[16 alpha b beta - 16 a beta^2]` of a negative radicand
  (analytically correct, not real-form); the LogToReal sign decision
  (`intsimp_sign_pos_assumption`) does not consult `Assumptions`.

## Compile / auto-compilation: every special function at arbitrary precision (v0.6482)
- `Compile[..., WorkingPrecision -> n]`, and the arbitrary-precision
  auto-compilation behind `NIntegrate` / `NSum` / `FindRoot` / `NDSolve` at
  `WorkingPrecision -> n`, now lower every special function — 142 heads (Erf,
  the Bessel / Hankel / Airy / Kelvin / Struve / Anger–Weber families, Gamma and
  its relatives, Beta(Regularized), the hypergeometric functions, MeijerG, the
  elliptic integrals, Jacobi elliptic, EllipticTheta, Weierstrass and Mathieu
  families, Zeta / HurwitzZeta / PolyLog / LerchPhi / DirichletL, the orthogonal
  polynomials, ProductLog, the Riemann functions, ...) — for real AND complex
  arguments. Before, any of them sent the WHOLE high-precision body to the
  interpreter at every sample (`MATHILDA_COMPILE_DIAG=1`: "no machine lowering
  for this head at these argument types"). Measured on v0.6481: 23 of 151
  numeric heads lowered for a real argument, 11 for a complex one; now 151 and
  145 (the 6 real-only heads have no complex evaluator to dispatch to).
- Mechanism: one table-driven opcode, `OP_MG_SPECIAL`, and a registry
  (`src/compile/compile_mgd_special.c`: head, arity range, real / complex /
  complex-valued-on-the-real-line). The call hands its MPFR / ncpx operands to
  the head's OWN arbitrary-precision evaluator — the builtin `N[f[...], n]`
  reaches — so compiled == uncompiled by construction and no numerics were
  added. Closed parameters stay exact (the `2` of `BesselJ[2, x]`, the parameter
  Lists of `HypergeometricPFQ` / `MeijerG` / `WeierstrassP`); a closed call
  (`BesselJZero[0, 3]`, `Gamma[1/3]`) folds to a constant at the working
  precision; `HankelH1` & co. of a real argument compile to an MPFR complex
  result. The registry also covers the complex domain of the elementary
  functions the mpfr / ncpx opcode set lacks (`Sinh`, `ArcSin`, `Log2`, ... of
  a complex), and `Arg`, `Log[b, x]`, `ArcTan[x, y]`, `ArcSec`, `ArcCsc`,
  `ArcCoth`, `Re` / `Im` / `Conjugate`. A point the evaluator declines (a
  complex value in a real program, a non-finite value) is interpreted, as
  before.
- Introspection: ``Internal`CompileArbitraryPrecisionHeads[]`` (the registry)
  and ``Internal`CompileArbitraryPrecisionStats[]`` (compiled special-function
  calls and declines, arbitrary-precision compiled calls that fell back,
  auto-compilations that bailed, auto-compiled points that declined).
- Measured (wall time, a loaded machine; same results to every printed digit):
  one special function alone runs at about the interpreter's speed (compiled
  `Erf` at 30 digits 22.4 µs/call vs 19.6 µs interpreted; `BesselK[1/3, x]`
  433 vs 402 µs) — the arb evaluation dominates, plus a CompiledFunction call
  and the boxing; a body with arithmetic around it
  (`Erf[x] x^2 + Sin[x] Exp[-x] + Sqrt[1 + x^2] - Log[2 + x]`) 43 vs 67 µs
  (1.55×). `NIntegrate` at `WorkingPrecision -> 30 / 50` over seven
  special-function integrands on [1/10, 1]: 0.9–1.4×, typically within noise,
  because those integrands converge in a few dozen samples whose cost is the
  special functions themselves. Where arithmetic surrounds the special
  function, at 30 digits: `NIntegrate[Sin[3 x] Erf[x] Exp[-x] (1 + x^2)/(2 + x),
  {x, 0, 1}]` 13.1 → 5.5 ms (2.4×), `NDSolve` of
  `y' == -Erf[t] y + Sin[t] y^2/(1 + t^2)` on [0, 1] 67 → 49 ms (1.4×),
  `FindRoot[Erf[x] BesselJ[0, x] - x/10, {x, 2}]` 1.25 → 0.70 ms (1.8×);
  `NSum[Erfc[k/3]/k^2 + Sin[k]/k^3, {k, 1, Infinity}]` 1.50 → 1.48 s (its cost
  is the acceleration machinery).
- Tests: `tests/test_compile_mpfr_special.c` (new suite, 1784 checks): every
  registry head, real and complex, at 30 and 50 digits — lowers, runs without a
  decline, agrees with the interpreter to the requested precision — mpmath
  reference values, composite bodies, and NIntegrate / NSum / FindRoot / NDSolve
  end to end (no auto-compile bail, == uncompiled, == mpmath to 25 digits).

## Table: arbitrary-precision iterators are auto-compiled (v0.6483)

## AngerJ / WeberE: a negative order at small z (v0.6489)
