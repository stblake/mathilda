# Changelog: week of 2026-10-26 (Mon) – 2026-11-01 (Sun)

## One node per symbol and per small integer (v0.6059)

- **The gap.** On the issue #112 trace (n = 14), Mathilda's peak memory was
  126 MB against the reference's 102 MB, while being faster on every timed row.
  The 135,135-term result held 5.4 nodes per term. Each term had its own
  `Times` head-symbol node (56 B) and its own coefficient node (`4` or `-4`).
- **Symbols.** Every `SymbolDef` now owns one canonical `Expr` node
  (`SymbolDef.node`, made on first use). `expr_new_symbol` hands out a
  reference to it instead of allocating.
  - This is sound because symbol nodes are immutable once shared: a mutator
    unshares first (`expr_unshare`, `deep_copy_private`). The only in-place name
    writes are the constructors and `alpha_rename`, which works on a private
    copy.
  - The node's definition cache starts empty, so the evaluator still resolves
    it through `symtab_get_def`. That keeps `Names` unchanged: symbols that C
    code makes, such as `True` and `Null`, still become defined on first
    evaluation.
  - A `Module` local still gets a fresh, counted node per occurrence, as its
    reclamation needs.
- **Small integers.** Integers in [-256, 1024] share one node per value. Integer
  nodes are never written after construction.
- **Never freed.** A canonical node that `expr_free` finds at refcount 1 (a
  wrapped 32-bit count, or an over-free) is re-pinned instead of freed.
- **Tests.** `test_expr_sharing` and `test_expr_pool` asserted a fresh node per
  constructor. They now use private atoms where they count references, and a
  new case checks sharing and pinning.
- **Results** (issue #112, n = 14):

  | | v0.6058 | v0.6059 | reference |
  |---|---|---|---|
  | peak (`MaxMemoryUsed[]`) | 120 MB | 94.5 MB | 102 MB |
  | generation | 2.50 s | 2.29 s | 6.52 s |

## Module locals: reclaimed during long evaluations, names freed (v0.6058)

Follow-ups to v0.6056, listed as outstanding in `SYMBOL_TABLE_IMPROVEMENTS.md`.

- **Escaped locals no longer wait for the statement to end.** An escaped local
  (returned, stored, captured by a closure) used to be queued and retried only
  when the outermost evaluation finished. A `Do` that stores and drops a
  `Module` result or a closure per iteration therefore kept every local until
  the loop ended.
  - `evaluate()` now also sweeps the queue in a nested evaluation once it holds
    `g_temp_sweep_at` entries: 4096, then twice the survivors of the last
    sweep. Each held local is re-walked an amortised O(1) times.
  - This is as safe as the `Module`-exit reclaim that already ran mid-evaluation.
    A frame that reads a local's definitions holds an expression naming it, and
    that node, outside the local's own rules, keeps the counts unequal.
  - `MATHILDA_TEMP_SWEEP_EAGER=1` sweeps at every `evaluate()` exit. The ASan
    audit runs with it.
- **Names are freed with the symbol.** v0.6056 kept every reclaimed name (about
  23 B per local) in case something held the raw pointer. An audit of every
  long-lived holder of a symbol name found three that could outlive the
  symbol, and each is fixed:
  - **`CompiledFunction`** stored its parameter names as raw pointers, and a
    parameter named only in the argspec (`Module[{x}, Compile[{{x, _Real}},
    2.0]]`) had no other node. It now pins them with a `List` of the parameter
    symbols.
  - **Timeouts.** A `TimeConstrained` timeout left two globals set by the frames
    it abandoned: the rule head a `/;` guard resolves `OptionValue` against, and
    the certified evaluator's bound variable. `tc_run_guarded` now restores both.
  - **The `MATHILDA_PACK_DIAG=gate` table** copies the head names it records.
- **Results** (200,000 iterations inside one `Do`; the reference in brackets):

  | | before | after | reference |
  |---|---|---|---|
  | `l = Module[{a, b = k}, a + b]` | +49.6 MB | +0.9 MB | +0.002 MB |
  | `fs = mk[k]` (closure) | +41.4 MB | +0.9 MB | +0.002 MB |
  | 400,000 non-escaping locals | +9.4 MB | +0.1 MB | ~0 |
  | issue #112 skeleton, memory left | +2.9 MB | +0.15 MB | +0.005 MB |

## Symbol-table follow-ups: ordered iteration, cheaper Module and rule application (v0.6057)

`SYMBOL_TABLE_IMPROVEMENTS.md`, items 2–5, each now records its outcome.

- **5 — Insertion order.** An intrusive insertion-order list (O(1) unlink on
  reclamation) drives `symtab_for_each` and the whole-table walks. Enumeration
  is definition order, independent of buckets and resizes.
- **4 — One copy per changed path.**
  - `substitute_scoping` shares subtrees no local occurs in, and compares

  - rule+`Module` per call: 2.60 → 1.81 µs (the reference: 2.27). Bare
    `Module`: 1.58 → 1.50 µs.
- **2 — Redundant interning removed** (fully lazy names would be materialised
  by ordering, hashing and printing anyway).
  - A local is interned once (`symtab_intern_def`), its node and value are
    built from the `SymbolDef`, and `$ModuleNumber` uses its interned name.
  - No measurable change since v0.6056 keeps the table small; kept as the
    simpler code.
- **3 — Integer symbol ids: declined on measurements.** Identity is already
  an interned-pointer compare, and no string-keyed side table remains hot.
- **Results.**
  - Issue #112 at n = 14: generation 2.9 → 2.6–2.7 s, `TimeUsed[]` 3.2 →
    2.9–3.0 s, Cases + Union 0.26–0.28 s.
  - Skeleton 0.65 → 0.54 s (the reference: 0.71 s).
  - Clean under ASan and `leaks`.

## Module locals are reclaimed (v0.6056)

- **The bug.** `Module` registered each local `Temporary` but never removed
  one. Every call left a symbol and its value behind for the whole session:
  548 bytes per call, and +111,005 symbols (+44 MB) after one issue #112
  trace, where the reference keeps +11.
- **Other constructs are clean.** Measured per call against the reference:
  `Block`, `With`, `Function` (including nested and capture-avoiding forms),
  `Table`, `Sum`, rules and `Compile` all stay at 0 symbols and 0 bytes.
  `Unique[]` keeps its symbols in both systems, as it should.
- **How it works** (`src/symtab.c`, "Module-local reclamation").
  - **Counting.** A local made from a never-interned name is counted: each live
    node naming it caches its `SymbolDef` and is counted in `temp_nodes`.
  - **The reclaim test.** It is reclaimed when a walk of its own rule lists
    finds every such node, each through refcount-1 parents, so self-references
    like `x$1 = {x$1}` do not keep it alive.
  - **When.** At its `Module`'s exit. An escaped local (returned, captured by a
    closure, rule or UpValue) is queued and retried when the outermost
    evaluation ends, once something was queued or a queued local lost a node.
  - **What is kept.** Name strings are kept, so no raw pointer can dangle.
  - **Kill switch.** `MATHILDA_NO_TEMP_RECLAIM=1`.
- **Results.**
  - +9 symbols after the trace.
  - `Module` costs 50 B per call (the kept names), down from 548.
  - The trace is faster too: generation 3.2 → 2.9 s, `MaxMemoryUsed[]`
    154 → 128 MB.
- **Checks.**
  - Escape semantics match the reference: closures, rules, UpValues, `Throw`,
    `Reap`, recursion, nesting, and a cleared `Temporary`.
  - Clean under AddressSanitizer: the trace, the Expand corpus, and the
    scoping corpus.
  - An audit found no long-lived `SymbolDef*` holder that could reach a freed
    local, and sweeps run only at the top level for that reason.
  - Pinned in `modular_tests`.

## Sum enumerates finite ranges; per-call overhead (v0.6055, issue #112)

- **Wrong answers in Sum.** A finite numeric range was summed in closed form
  first, which evaluates the body at a symbolic index. That is wrong for a body
  that takes the index apart:
  - `Sum[Length[Delete[{2, 3, 4}, m]], {m, 1, 3}]` was `9`; it is `6`.
  - `Sum[dt @@ Delete[list, m], ...]` collapsed to `dt[list, m]`.
  - The issue #112 trace skeleton (integer arithmetic in place of `g`)
    returned `0` instead of `4`.

  Ranges of at most 10^6 terms are now enumerated, the reference's own switch
  point: it expands `Sum[x^i, {i, 0, 10^6}]` term by term. This also gives
  the reference's forms: `Sum[x^i, {i, 0, 5}]` is the explicit polynomial.
- **Each Sum term is evaluated once.** The compiled path's inexactness probe
  evaluated the body at the first index and threw the value away, so the
  enumeration evaluated it again.
  - In the trace, that first term is a whole recursive `diracTr` subtree, so
    every recursion level redid its first branch.
  - Removing it took generation from 4.7 s to 3.1–3.2 s. The skeleton's base
    rule now fires 135135 times, as in the reference, not 322560.
  - The integer index also advances by direct addition instead of an
    evaluated `Plus`.
- **Symbol table.**
  - Each node stores its full name hash, so chain walks compare integers
    before `strcmp`.
  - The table grows by doubling instead of a fixed 65535 buckets. `Module`
    mints a symbol per local per call, and a run leaves about 10^5 of them, so
    the chains had become long.
  - `disasm`'s kernel-name lookup takes the alphabetically first alias,
    independent of bucket order.
  - The skeleton is 12% faster and at parity with the reference
    (0.65 s against 0.71 s).
- **Not done here.** A real redesign — reclaiming `Module` locals (the
  reference keeps +11 symbols after the trace, Mathilda +111,005 and +44 MB)
  and lazily named locals — is written up in `SYMBOL_TABLE_IMPROVEMENTS.md` for
  a dedicated session.
- **Result.** Issue #112 at n = 14: generation 4.7 s → 3.1–3.5 s, `TimeUsed[]`
  5.1 s → 3.5 s.

## Expand: opaque kernels as FLINT generators (v0.6054, issue #112 follow-up)

- **What changed.** `flint_expand_polynomial_kernels` expands a polynomial
  whose generators include opaque kernels in packed `fmpq_mpoly` arithmetic.
  Before, FLINT's expander accepted symbols only, so `f[1]`, `g[x[i], x[j]]`,
  `Sin[x]` or `Log[y]` sent the whole expansion to term-by-term distribution.
  - Kernels are found through a hash table (`expr_hash` + `expr_eq`); the GCD
    abstraction's linear generator scan would be quadratic here.
  - Monomial summands are pushed and combined once, not added one at a time.
  - Each generator renders back as a shared copy of its kernel node, and the
    result is evaluated.
- **Results.**

  | Expand | before | after |
  |---|---|---|
  | `(f[1] + ... + f[6])^8` | 78 ms | 4.9 ms |
  | `(x + Sin[x] + g[y] + 1)^12` | 26 ms | 1.4 ms |
  | `(1 + Log[x] + Log[y])^15 (Log[x] - 2)` | 6.0 ms | 0.4 ms |

- **Exactness.** Expand never looks inside a kernel, and the result is
  evaluated, so kernels that interact under `Times` come out exactly as
  before: `(Sin[x] + Csc[x])^3` is `3 Csc[x] + Csc[x]^3 + 3 Sin[x] + Sin[x]^3`.
  - **Excluded** are kernels whose multiplication has its own semantics, which
    collecting `k k` into `k^2` before evaluation would bypass:
    - System heads without `NumericFunction` (`List`, `Interval`,
      `SeriesData`, `ConditionalExpression`, `DirectedInfinity`,
      `AlgebraicNumber`, `Root`, ...);
    - heads with UpValues (`g /: g[a_] g[b_] := ...` fires on `g[1] g[1]` but
      not on `g[1]^2`);
    - user rules for `Plus`/`Times`/`Power`.
  - **Checked.** 190 expansions (43 hand-picked interaction cases and 150
    random kernel polynomials) are byte-identical to v0.6053.
- **When it is used.** Only when sums are multiplied together (a power of a
  sum, or two or more sum factors). Distributing one kernel over an
  already-expanded sum, which is every step of the issue #112 Dirac trace, is
  linear and stays classical. FLINT's lex-ordered output would have to be
  fully re-sorted there, and taking the path unconditionally cost that
  benchmark 25% (4.7 s → 5.8 s).

## Symbolic evaluation: INERT fixed points, adaptive Orderless sort, Times/Plus/Expand fast paths (v0.6053, issue #112)

The Dirac-trace benchmark from issue #112 (n = 14, 135135 terms), run on one
machine, v0.6052 → v0.6053:

| | v0.6052 | v0.6053 |
|---|---|---|
| trace generation | 18.5 s | 4.5 s |
| `Cases[res, _g, Infinity] // Union // Length` | 0.84 s | 0.33 s |
| `TimeUsed[]` | 19.8 s | 4.8 s |
| `MaxMemoryUsed[]` | 224 MB | 174 MB |

(v0.6049 was 24.1 s / 3.62 s / 462 MB.)

- **INERT fixed points (eval.c).** Every OwnValue binding (an iterator, a
  `Module` local) bumped the eval clock and so invalidated every cached fixed
  point. Only literal GROUND data survived. The recursion's 10^4-10^5-term
  symbolic sums were therefore re-canonicalised after every binding: `Sum` over
  13 stored pieces took 12 s against 2.3 s for `Plus @@`, and `Do` reading a
  stored 135135-term list never finished.
  - **What is INERT.** A fixed point built from numbers, symbols with no value
    or rules, and calls of `Plus`/`Times`/`Power`, a ground head, or a
    rule-free user head. It carries a second flag bit (bit 62).
  - **What invalidates it.** Each symbol it relied on is flagged
    `inert_observed`. A binding or DownValue for a flagged symbol, or for one
    of those builtin heads, advances `g_inert_epoch`. So does every other
    (conservative) clock bump, attribute change, `Clear`/`Remove`, and
    `Block` restore.
  - **Effect.** Reading a stored 2002-term symbolic sum 200 times in a `Do`
    loop went from 0.90 s to 42 µs. Fifteen invalidation scenarios (values,
    DownValues, UpValues, attributes, `Times`/`Power` rules, iterators, `Block`,
    `Module`, DownValue-stored results) match the reference, and are pinned in
    `eval_timestamps_tests`.
- **Builtins certify their own fixed points.** The evaluator ran `Plus` and
  `Times` a second time on their own result, only to see it unchanged.
  - `builtin_plus` now stamps its result (`eval_mark_fixed_point`) when every
    term is a machine integer, a rule-free symbol, or an evaluated
    `Times`/`Power`/user-headed call, and no rule can fire.
  - The new `Times` fast path does the same.
  - `Plus` also re-emits an unmerged term's own evaluated node, rather than an
    unevaluated `coeff * base` rebuild.
- **Adaptive Orderless sort.** `expr_orderless_sort` detects ascending runs
  and merges them pairwise, O(n log k) for k runs. A sum of k canonical sums is
  k sorted runs. `expr_compare` gains exact fast paths for two machine integers
  and for two calls with the same non-arithmetic head.
- **`Times` fast path.** A product of machine-integer coefficients and
  distinct opaque factors (non-System, rule-free heads or symbols) is its
  folded coefficient followed by the sorted factors. It skips the collector's
  passes, none of which can fire on such a product.
  `MATHILDA_TIMES_FAST_CHECK=1` runs both paths and aborts on a mismatch.
- **Expand.**
  - An already-expanded product or sum (stamped, with nothing to distribute)
    is returned as is. Before, every term was multiplied back together factor
    by factor.
  - An allocation-free term-count bound skips the kernel-degree estimate when
    it already fits.
  - The field expander's scan declines at the first opaque node.
  - Head dispatch compares interned pointers.
- **Rule application.** A rule with no bindings (`res[14] = ...`) returns its
  right-hand side without walking it: 20 ms → 0.4 µs per read of a 10^4-term
  value.
- **Cases `_h`** collects a match without the matcher or a `MatchEnv`.
- **`intern_symbol`** recognises an already-canonical pointer through a small
  pointer cache. Re-hashing `SYM_*` names was about 10% of the workload.
- **Block fix (wrong answer).** `Block` restored values and rules behind the
  evaluator's back, so a fixed point stamped inside it survived:
  - `x = 5; Block[{x}, x + y]` gave `x + y`; now `5 + y`.
  - `Block[{f}, f[3]]` with `f[a_] := a^2` gave `f[3]`; now `9`.
  - `test_rule_dispatch` had pinned the stale `{99, lf[2]}`. 13.2 and 14 both
    give `{99, 21}`.
- **Sort bug caught in development, not shipped.** The run detector's
  early-out first treated a short unsorted input as sorted. It is covered by
  a 4000-case ordering stress check.

## Dirac-trace benchmark: DownValue sharing, Expand, Union, Cases; Echo and EchoTiming (v0.6052, issue #112)

The issue's benchmark builds a 135135-term Dirac trace and then runs
`Cases[res, _g, Infinity] // Union`. Results at n = 14, on one machine, before →
after:

| | HEAD | v0.6052 |
|---|---|---|
| generation | 24.1 s | 18.8 s |
| Cases + Union | 3.62 s | 0.88 s |
| MaxMemoryUsed | 462 MB | 224 MB |

- **DownValue right-hand sides are shared, not rebuilt.** `replace_bindings`
  rebuilt every node of a rule's right-hand side, even where no binding
  reached it. The copy lost its evaluation stamp and cached hash, so each read
  of `res[n]` re-sorted the 135135-term sum. Unchanged subtrees now come back
  as the original node (a refcount bump), as OwnValues already did.
- **Expand estimates the result size once.** A subexpression's term bound never
  exceeds its parent's, so the recursion no longer re-runs the size estimate
  at every level. The kernel table is also screened by the memoized hash.
- **Union deduplicates before sorting.** Without `SameTest` it hashes first
  and sorts only the distinct elements; here 946k elements reduce to 91.
- **Cases tests `_h` by head.** A plain `_h` pattern is a pointer comparison
  on compound nodes, with no matcher call and no MatchEnv allocation.
- **New `Echo` and `EchoTiming`**, as the issue requested. `Echo[expr]`,
  `Echo[expr, label]` and `Echo[expr, label, f]` print `>> ...` and return
  `expr`. `EchoTiming[expr]` and `EchoTiming[expr, label]` print the
  `AbsoluteTiming` seconds. Attributes match the reference.
- **Still open.** The rest of generation is per-term `Times`/`Plus`
  canonicalisation inside the classical distributor, because FLINT's expander
  declines opaque kernels such as `g[a, b]`. Letting it treat them as
  generators is the next step.

## Factor over Gaussian coefficients: 63 s to 26 ms (v0.6051, issue #114)

FLINT's `fmpq_mpoly_factor` declines `Complex` coefficients, so a
multivariate polynomial with `I` in it went to the classical factoriser. On
the issue's 28-term, 30-kernel irreducible polynomial that took 63 s.
- **Degree-one irreducibility.** `factor_degree_one` now concludes P is
  irreducible when P is degree 1 in some variable v with
  gcd(coefficient of v, constant term) = 1 (Gauss's lemma). Before, it moved on
  to the next variable and then fell into the variable-specialisation split.
  The shortcut is gated on every variable being a genuine indeterminate:
  `x^2 + s x - 6` with s = `Sqrt[3]` is linear in s with coprime
  coefficients, yet equals `(x - Sqrt[3]) (x + 2 Sqrt[3])`.
- **Gaussian FLINT zero test.** `flint_mpoly_is_zero` declined `Complex`, so
  every gcd and exact division recursed through `is_zero_poly_depth`. It now
  maps `Complex[a, b]` to `a + b tau` and decides over `Q[gens, tau]` when tau
  has degree at most 1. `MATHILDA_ZEROTEST_DIFF=1` agrees with the classical
  path on the regression set.
- Factoring over Q(I) itself is unchanged and matches the reference:
  `Factor[Expand[(x + I)^2 (1 + y)]]` is `(I + x)^2 (1 + y)`.

## Together combines a sum with no denominators (v0.6050, issue #113)

- `Together[(-a - b) f[c] + (a + b) f[c]]` came back unchanged; the reference
  gives 0. Both fast paths decline here: ratcanon has no generator for
  `f[c]`, `Dot` or `Sin`, and the FLINT combine needs a denominator. The
  classical Plus combine then handed an unexpanded numerator to
  `cancel_recursive`, whose `den == 1` early-out returned it as is. The
  numerator of a denominator-free sum is now expanded (and re-evaluated, since
  `expr_expand` returns an unevaluated tree), as the reference does:
  `Together[(a + b)^2 + c]` is `a^2 + 2 a b + b^2 + c`.
- **Cancel: a variable in an exponent is not an embedded rational.** The fix
  let Risch-Norman verify an ansatz whose residual had looked nonzero. That
  exposed Cancel declining on `y^(1/(a - 1))`, because its soundness gate
  walked into the exponent. The gate now skips exponents:
  `Cancel[(a^2 - 1) y^(1/(a - 1))/(a - 1)]` reduces, as `PolynomialGCD`
  already did.
  `Integrate[x^(1/(a - 1)) y^(1/(a - 1)), x]` is now
  `(-x^(1 + 1/(-1 + a)) y^(1/(-1 + a)) + a x^(1 + 1/(-1 + a)) y^(1/(-1 + a)))/a`.
  Its derivative check is 0; the reference writes the same antiderivative as
  `((-1 + a) x^(a/(-1 + a)) y^(1/(-1 + a)))/a`.

## Simplify: log fusion is sound, and fuses rational multiples (v0.6049)

SimpLogRules' fuser rewrites `Sum c_i Log[a_i]` as `Log[Prod a_i^c_i]`.
**Wrong answers removed.**
- **The unsound gate.** Without provable positivity, the fuser accepted any
  result that "collapsed to a small constant". The two forms differ by
  `2 Pi I k`, so that gate was unsound:
  - `Simplify[Log[x] + Log[1/x]]` was 0, which is false on the negative axis
    (`Log[-2] + Log[-1/2] = 2 Pi I`).
  - `Simplify[Log[-x] + Log[-1/x], x > 0]` was 0; the value is `2 Pi I`.
  - `Log[x^2 - y^2] - Log[x - y] - Log[x + y]` was 0; it is `-2 Pi I` at
    `x = -2, y = 1`.
- **The new rule.** Without positivity the fuser fuses only a numeric
  constant, and only when a 30-digit evaluation shows the difference is 0,
  which decides `k` exactly.

**Rational multiples.** When every coefficient is an integer multiple `r_i` of
the first, the fuser builds `c Log[Prod a_i^r_i]`. Evaluation never merges
`Sqrt[a] Sqrt[b]`, so the old form could not cancel: `1/2 Log[1 - x] +
1/2 Log[(1 + x)/(1 - x)]` is now `1/2 Log[1 + x]` under `0 < x < 1`. A
negative common factor is flipped, so `Log[2 x] - Log[x]` stays `Log[2]`.

**Positivity of Log arguments.**
- Now also proved through the reduction entailment and Refine, so compound
  arguments such as `1 - x` and `(1 + x)/(1 - x)` on a box count.
- `prov_pos` derives `Tan[u] > 0` and `Cot[u] > 0` from same-signed `Sin[u]`
  and `Cos[u]`.

**Region identities.** A sampled constant such as `ArcTanh[1/4] -
1/2 Log[5/3]` (the sample `x = 1/4`) is certified through `TrigToExp`, but
only when every resulting Log argument is a positive real. `ArcTan`'s complex
logs would otherwise "prove" its Pi-valued addition residue is 0. So
`Simplify[ArcTanh[x] - Log[(1 + x)/(1 - x)]/2, 0 < x < 1/2]` is 0. Before,
only the symmetric interval `-1 < x < 1` worked, because its sample `x = 0`
gives 0 directly.

## Series: large composition coefficients are kept expanded (v0.6048)

Composing an elementary function with a series multiplied its coefficients
unexpanded. Products of `x/A^k` terms then nested at every step. Only
radical-bearing coefficients were expanded (issue #41).
- **Example.** `Series[E^(-x + A x Sqrt[w]/(A Sqrt[w] + w)), {w, 0, 1}]` took
  39 s, and order 2 did not finish in 60 s.
- **Effect on Gruntz.** The Gruntz limits of thesis examples 8.11 and 8.17,
  which contain such a factor, took 159 s and 178 s.
- **Fix.** A coefficient past 128 leaves is now expanded too. The series takes
  2.2 s, both limits about 3 s, and `gruntz_tests` 11 s instead of 444 s.
- **Why 128.** At 64 leaves, the psi tower
  `Exp[Exp[PolyGamma[0, PolyGamma[0, x]]]]/x` answers its correct `1/Sqrt[E]`,
  but only after 109 s of Expand, where it otherwise declines in 0.6 s
  (`tasks/todo.md`).

## Limit: a negative constant times a divergent exponential is -Infinity (v0.6046)

`Limit[-E^x, x -> Infinity]` was **Infinity**. So were `-E^E^x` and
`-2 x^x`. `Limit[E^(-E^x), x -> Infinity]` was Infinity rather than 0, because
its exponent is such a product.
- **Cause.** The log reduction for a power product (`layer5_log_reduction`)
  took the Log of *every* factor. A constant `-1` contributed `Log[-1] = I Pi`
  beside a divergent log, and `Infinity + I Pi` exponentiated to `Infinity`.
- **Fix.** The constant factors now stay out of the log and multiply the
  result afterwards. An infinite result takes its direction from `Sign` of
  the constant, which also folds `Sqrt[2 Pi] Infinity` from Gamma's Stirling
  form. A constant of unknown sign gives no answer from this layer.
- **Found by** `gruntz_tests`. Thesis example 8.8 is right under
  `Method -> "Gruntz"`, but the Automatic cascade answered Infinity first.
  `limit_tests` now pins these cases.

## Uninitialised slots freed on glibc: QRDecomposition and DSolve's first-order series (v0.6045)

## Limit's Assumptions option reaches Series, Simplify and the zero tests (v0.6044)

`Limit[x (ArcTan[a x] - Pi/2), x -> Infinity, Assumptions -> a > 0]` returned
`DirectedInfinity[(-1 + Sqrt[a^2]/a) Pi/2]` rather than `-1/a`.

- **`SYM_Limit`** is now an interned symbol (`sym_names.c`).

## PolynomialLCM over a radical tower: coprime inputs give their clean product (v0.6043)

## IrreduciblePolynomialQ: Extension -> Automatic runs the multivariate probe (v0.6042)

`IrreduciblePolynomialQ[x^2 + 2 Sqrt[3] x y + 3 y^2, Extension -> Automatic]`
was True. The polynomial is `(x + Sqrt[3] y)^2`.
- **Why it missed.** Factor applies an extension only to univariate input. For

## Sum: Gosper antidifferences are certified (v0.6041)

`Sum[Binomial[3, k] x^k, {k, 0, 3}]` was **0**, and `{k, 0, 2}` gave `-x^3`. A
finite sum tries the closed-form cascade before enumerating, and
`Sum`Gosper` returned a false antidifference.
- **Cause.** Gosper's key equation is solved by `SolveAlways`, which solves
  for *every* symbol except the summation index. For `Binomial[3, k] x^k` it
  returned `x -> -1` beside the ansatz coefficients. Only the coefficient rules
  were applied, giving an `F` valid at `x = -1` alone.
- **Fix, two guards.**
  - A solution is accepted only when it binds the coefficients and nothing
    else.
  - `F = R t` is returned only when `R(k+1) r(k) - R(k) - 1` is identically 0,
    with `r` the term ratio. This is an exact rational-function identity, so a
    false antidifference becomes a decline.
- **Messages.** The internal `SolveAlways` probe now runs under `Quiet`. Its
  `Solve::nsdim` used to print for every under-determined ansatz and make
  `Check[Sum[...], ...]` take its failure branch.
- **Found by** `expand_tests`: `Expand[(x + 2)^60] === Sum[Binomial[60, k] x^k
  2^(60 - k), {k, 0, 60}]`. That suite was compiled but never registered with
  ctest; see the harness entry below.

## Root's canonical order no longer depends on LAPACK roundoff (v0.6040)

On Linux, `N[ToNumberField[E^(Pi I/4), I AlgebraicNumber[Sqrt[2], {1, 2}]]]`
gave `-0.707 + 0.707 I`, which is the wrong root.
- **Cause.** The numeric Root path sorts its QR eigenvalue estimates into
  canonical order before Newton refines them. The comparison was exact. All
  four roots of `49 + 18 x^2 + x^4` lie on the imaginary axis, so their
  estimated real parts were roundoff of either sign, and the roundoff differs
  between LAPACK builds (Accelerate on macOS, OpenBLAS on Linux). That noise,
  not the order, decided what `Root[..., 4]` meant.
- **Fix.** The sort now treats Re and |Im| as equal when they agree within the
  estimates' accuracy: 2^-30 relative on the machine LAPACK path, half the
  working precision on the MPFR QR path. Truly equal parts then fall

- **Found by** the new CI ctest job (`algebraicnumber_tests`).
- **Tests.** `test_root_numeric` pins the order of two root sets whose real
  parts are equal: `49 + 18 x^2 + x^4` and `x^4 + 1`.

## Integrate: an exponential of a trig function gets a correct tower (v0.6038)

`Integrate[E^Sin[x], x]` declined only after the cascade's 10 s
ParallelMixedSpecial budget had run out. It now declines in 0.66 s, and
`dsolve_m34_stress` passes (`y'' + Cos[x] y' - Sin[x] y == 0` needs that integral).

The cause was a wrong tower rather than a missing certificate.
- **The tower.** BuildTower rewrites the trig functions of one argument
  through a tangent. When the integrand is even it uses `s -> t r, c -> r` with
  `r^2 = 1/(1 + t^2)`. The evenness and parity tests reduce modulo `r^2` by
  PolynomialRemainder, which treats a transcendental `r` (`E^(t r)`, from

  `E^(r Tan[x])`, with `r` a free symbol, and `E^Cos[x]` became `E^r`. A
  reduction now counts only when the pair it returns is free of `r`. These
  integrands take the half-angle tangent:
  `E^Sin[x] -> E^(2t/(1 + t^2))`, `t = Tan[x/2]`.
- **The search.** The free `r` then appeared as a factor of a derivative, and
  `ClassifyPrime` on a constant does not terminate. `TowerSpecialPlaces` now
  keeps only the factors that carry a generator. That case is still reachable
  with a real parameter, as in `E^(a Tan[x])`.

## DSolve: wrong "no solution" answers, a lost Cos/Sin basis, Kummer, and six spins ; v0.6037

**Wrong answers.**
- **An IVP at a basis singularity.**
  `DSolve[{y'' + x y' - 2 y == 0, y[0] == 1, y'[0] == 0}, y, x]` was `{}`, a claim
  that no solution exists; the answer is `1 + x^2`. Six corpus IVPs (§2.2.11–2.2.20)
  did the same. The basis carries `(x^2/2)^(1/4)/Sqrt[x]`, a removable 0/0 at the
  point. The fit read `0 == 1`, and since v0.461 a literal False makes a linear
  system inconsistent. When the body is non-finite at a condition point, the fit
  now PowerExpands it (the real basis is written for `x > 0`), differentiates,
  then substitutes, falling back to the one-sided limit. The six IVPs meet their
  ODE and both conditions to 30 digits.
- **A symbolic oscillator's basis.** `y'' + a^2 y == 0` came back as

## A failing rule on a wide sum no longer tries every subset ; v0.6032

Matching a sum against `c1_. Cosh[a_] + c2_. Cosh[b_] + r___ /; cond`, the
negative-argument rule TrigReduce applies at the end, took time exponential in
the number of terms whenever the condition failed: 0.04 s at 8 terms, 10 s at
16. Two independent subset scans in the Flat matcher caused it, and each was
2ⁿ on its own:

- **The Optional-coefficient element.** For a Flat head, an element may take a
  group `Plus[t1, ..., tk]` of the operands, and the matcher drops the k > 1
  spans only when the element's head can never match such a group.
  `Times[c1_., Cosh[a_]]` kept them, because Times is OneIdentity with an
  Optional argument, and through defaults that can absorb a group
  (`Power[y_, n_.]` takes `2 x` as `y`). But once the optionals take their
  defaults, what is left must match the group. Two or more required arguments
  keep the Times head, and one required call on a fixed head that is not
  OneIdentity (`Cosh[a_]`) cannot equal a Plus. Those spans are now skipped.
- **The leftover retry.** When the whole-expression match fails, ReplaceAll
  retries a Flat head with the pattern augmented by a trailing
  `$FlatRest$___`, so that `a + b + c /. a + b -> w` gives `c + w`. With an
  `r___` already in the pattern, `r` was no longer last, so it ran through
  every subset of the operands. For an Orderless head this retry can never
  succeed when the pattern has an untyped, untested `___`/`__` whose name
  appears nowhere else in the pattern and in no guard of the replacement. Any
  augmented match becomes a plain match by giving the leftovers to `r`, and
  nothing reads `r` to reject that. The retry is skipped in that case. A
  condition that does read `r` (`a + r___ /; Length[{r}] == 2`) still gets it.

The TrigReduce call takes 5 ms, down from 20.6 s. `DSolve` of the forced
system `{x' == 2x + 4y + 3E^t, y' == 5x - y - t^2}` (§2.2.10-924) went from
0.3 s to 50 s when v0.591 made `-(u + v)` distribute: the
variation-of-parameters Simplify then handed TrigReduce a 16-term Cosh/Sinh
sum with `Sqrt[89]` coefficients. It now takes 1 s, and
`dsolve_corpus_2_2_10` passes again. Results are unchanged: the matcher, rule,
pattern and trig suites and the 311-case match stress corpus pass, and a probe
set of flat-leftover and OneIdentity-default rewrites gives the same output as
before. New test: `test_match_flat_orderless_no_subset_blowup` (30 terms).

## N[expr, p] keeps its p-digit promise under cancellation ; v0.6031

`N[expr, p]` used to evaluate once, at a fixed working precision (p digits plus
64 guard bits), and reported p digits whether cancellation had destroyed them
or not. At `p = 20`, `N[Cos[10^-20] - 1]` came back as an exact `0.0`; the
true value is `-5*10^-41`. At `p = 32` it had 11 correct digits out of 32. The
exact zeros `E^(I Pi/4) - (-1)^(1/4)` and `Sin[Pi/7]^2 + Cos[Pi/7]^2 - 1` came
back as `10^-52`- and `10^-60`-size values, and which precisions showed the
noise looked random. Now:

- MPFR addition and subtraction record the worst cancellation, i.e. the leading
  bits a sum lost (`note_cancellation`). When that exceeds the guard headroom,
  `N` re-evaluates with 64 more bits, until two successive results agree to p
  digits, up to `p + $MaxExtraPrecision` digits.
- At the limit, a part still shrinking is the residue of an exact cancellation
  and becomes `0`. Any other part that never settled gives `N::meprec`.
- A higher precision that comes back worse (`Overflow[]`) stops the climb. That
  is what exposed the BarnesG overflow fixed in v0.6030.

Only the `N` builtin's `N[expr, p]` adapts. Internal working-precision
numericalization evaluates once, and an expression that cancels nothing pays
nothing: `dsolve_corpus_2_2_51` went from 144 s to 134 s. New tests:
`test_n_adaptive_precision` and `test_barnesg_arbitrary_precision`, and
`numeric_tests` passes again. The full suite shows no regressions, and
`fit_tests`, `integer_assume_simplify_tests`, `numeric_tests` and
`sf_machine_error_tests` now pass.

## BarnesG at arbitrary precision goes through arb ; v0.6030

`N[BarnesG[37/10], 80]` was `Overflow[]`, and at 200 digits it did not finish.
The numeric kernel uses a fixed 12-term asymptotic series. To reach D digits it
shifts the argument by `R ~ 10^((D+4)/24)` and divides out R Gamma factors:
about 50 of them at 30 digits and about 3200 at 80. At 80 digits,
`Exp[(Z^2/2) Log[Z]] ~ e^(4*10^7)` came back `Overflow[]`, after the cost had
grown 50-fold. Above machine precision, `BarnesG` now uses arb's
`acb_barnes_g` (`flint_num_barnesg`), which is rigorous at any precision:
80 digits take 0.6 ms and 200 digits 1.7 ms. The series remains the fallback
and the machine path, so the machine-precision surfaces still agree bit for
bit. The 75- and 200-digit values agree, and
`N[BarnesG[x + 2] - x Gamma[x]^2 BarnesG[x] /. x -> 17/10, 30]` is `0.0` in
1 ms, down from 1.15 s.

## Erf of a huge complex argument keeps its imaginary part ; v0.6029

`Erf[1.*^300 + 1.*^300 I]` was the Real `1.0`. From first principles,
`erf z = 1 - erfc z`, with `erfc z ~ e^(-z^2)/(z Sqrt[Pi])`. At this `z`,
`|e^(-z^2)| = 1`, so `erfc z` has magnitude about `4*10^-301`, and `erf z` is
1 plus a complex number of that size, which fits in a double. For `|z|^2 > 400`,
arb's `erf` is accurate relative to `|erf z| ~ 1`, so the imaginary part came
back as the midpoint 0. `Erf` now computes `1 - erfc z` with `erfc` from arb.
`erfc` carries both parts componentwise and is never close to 1 here, so
nothing cancels. For `Re z < 0` it uses oddness instead. When arb's 53-bit
`erfc` is itself `[0 +- r]` (as at `10^300 (1 + i)`), `erfc` is retried at a
higher precision, as `Erfc[]` already did. Result:
`Erf[1.*^300 + 1.*^300 I] = 1.0 - 8.18*^-302 I`, which is exactly `1 - Erfc`
of the same argument, and `Erf[-z] = -Erf[z]`. The imaginary part is now kept
from `10^10` up to `10^300`. Values whose imaginary part is below the double
range, such as `Erf[1.*^3 + 20. I]` (`Im ~ 10^-434125`), are still a correctly
rounded `1.0`. The test that expected `Erf` to stay unevaluated now asserts
the derived properties.

## N: the inexact-contagion flag leaves NumericSpec ; v0.6028

`Fit[{{0,1},{1,0},{3,2},{5,4}}, {1, x, x^2}, x, WorkingPrecision -> 24]`
returned the exact fit `135/199 - 53/199 x + 38/199 x^2` in `fit_tests` at
`-O2`, and the right 24-digit fit at `-O3` and standalone. The result
depended on the build because of undefined behaviour. `NumericSpec` had gained
a third field, `contagion`, in v0.6019. Over 30 call sites declare
`NumericSpec s;` and set only `.mode` and `.bits`, so the flag was stack
garbage there. When it happened to be nonzero, `N` refused to thread into
non-numeric heads, including `List`, so a numericalized coefficient vector
stayed exact. Any of those callers could be affected, not just `Fit`. The
flag is now file-static state in numeric.c: the public `numericalize()`
saves it, forces it off and restores it, and only the inexact-operand pass
of `Plus` / `Times` turns it on. So no caller can leave it uninitialised, and
`NumericSpec` is back to two fields, with a comment saying why. `1.0 x[1]`
still stays `1.0 x[1]`, and `N[x[1]]` is still `x[1.]`.

## Simplify / Refine / Reduce: E^(I x) is not positive, 2 n is not even, for real x, n ; v0.6027

For real (not integer) `n`, `Simplify[Arg[Exp[I Pi (2 n + 1/2)]] - Pi/2,
Element[n, Reals]]` returned `0`. That is false: at `n = 0.3` the expression is
`-4.398`. Three separate unsound steps, each fixed at its source:

- **Positivity** (`prov_pos`): "a positive base to any power is positive"
  treated `E^((2 I) n Pi)` as positive, so `Arg[I E^(2 I n Pi)]` became `Pi/2`.
  It now requires a real exponent (`p^q = Exp[q Log[p]]` is positive only for
  real `q`), as the `Exp[...]` branch already did.
- **Reduce over the Reals**: the univariate sign diagram assumes a real-valued
  function. It sampled `E^(I x)` at `x = 0`, saw `1 > 0` and no real root, and
  answered `True` for `Reduce[E^(I x) > 0, x, Reals]` (the truth is
  `x == 2 Pi k`). `Refine` uses that entailment, so `Refine[Arg[E^(I x)],
  Element[x, Reals]]` became `0`. An ordering inequality with a visibly
  complex side now becomes its real meaning, `Im[l - r] == 0 && Re[l - r] > 0`
  (through `ComplexExpand`), before any engine sees it. If that does not
  settle, the call stays unevaluated. `Reduce[I > 0, x, Reals]` is `False`.
- **Parity of an exponent** (`ivp_term_decompose`): an even literal coefficient
  returned "vanishes mod 2" before the other factors were shown to be integers.
  So `(-1)^(2 n)`, reached as `E^(2 I n Pi)` through the one ungated branch of
  the root-of-unity rule, became `1` for real `n`. Every factor is now checked
  first.

`Simplify[E^(2 I n Pi), Element[n, Integers]]` is still `1`, `E^(I n Pi)` is
still `(-1)^n`, and `E^(2 I n Pi + x)` is still `E^x`. New tests:
`test_complex_valued_inequalities` (test_reduce.c) and seven soundness and
integer checks in test_integer_assume_simplify.c. Full suite: no regressions,
and `integer_assume_simplify_tests` passes again.

## Dialog ; v0.6025

## Definitions are ordered by pattern generality ; v0.6022

- **FeynCalc:** this is `DiracTrace-ID7`.

## ReleaseHold releases a held head ; v0.6014

- **`ReleaseHold` now strips one layer of `Hold` (and `HoldForm`,
  `HoldComplete`, `HoldPattern`) at every position, heads included**, as the
  reference does. `ReleaseHold[Hold[f][x]]` is `f[x]` (it was left as it was),
  and `ReleaseHold[Hold[Hold[f]][x]]` is `Hold[f][x]`.
- **FeynCalc:** this fixes 7 of the 13 `ToFCPartialFractionForm` failures and
  removes the first blocker in 5 more. Its `FRH` releases the
  `Hold[Coefficient][...]` calls it builds. The rest wait on `Apart` with
  radical or `I` linear factors.

## D of a compound head ; v0.6013

- **`D` now differentiates through a compound head**, as the reference does.
  `D[g[a][x], x]` is `Derivative[1][g[a]][x]`, by the same chain rule as for
  a symbol head. It used to stay unevaluated.
- **A head that depends on the variable** adds the derivative through the
  head, applied to the arguments: `D[g[x][x], x]` is
  `Derivative[1][g[x]][x] + Derivative[1][g][x][x]`.
- **FeynCalc:** all 18 `FCLoopGLIDifferentiate` failures. It differentiates
  `GLI[topo, {..}][m]` and then looks for the `Derivative[1][GLI[...]]` heads.
- **Inactive integrals and held expressions.**
  - An inactive integral over a non-list variable now differentiates by the
    reference's Leibniz form: `D[Inactive[Integrate][f[u], Sqrt[x]], x]` is
    `f[u]/(2 Sqrt[x])`. It used to stay inert.
  - Other inactive integrals stay inert, and so does a held expression:
    `D[Hold[x], x]` was `Derivative[1][Hold][x]`.
- **`Factor` of a rational expression** now factors the numerator and the
  denominator with the FLINT multivariate factoriser that a direct
  `Factor[poly]` uses. The classical path had taken ~50 s on a 7-variable
  FeynCalc case.

## Internal`SyntacticNegativeQ reads sums and complexes as the reference does ; v0.6012

- **A sum is now read by its first term**, so `-a - b` and `-1 + x` are
  `True` and `x - y` stays `False`. A sum used to be always `False`.
- **A complex number is now read by its imaginary part alone**:
  `Complex[-1, 2]` is `False` (it was `True`), and `Complex[1, -2]` is `True`.
- **FeynCalc:** this fixes 2 more `SUNSimplify` failures.
  `colorFactor[a] /; SyntacticNegativeQ[a] :> -colorFactor[ExpandAll[-a]]`
  never fired on a negative sum, so the colour factor stayed unexpanded.
- **Mathilda's own caller is unaffected.** `MinusSignQ` in the special-function
  integrator already tests a sum's first term itself.

## OptionsPattern in any position ; v0.6011

- **`OptionsPattern[]` now matches when it is not the last pattern element.**
  It takes a leading run of option arguments, longest first and down to none,
  and leaves the rest to the later elements, as in the reference. Before, it
  took every remaining argument and failed on any that was not an option, so
  `MatchQ[t[x], t[OptionsPattern[], a_]]` was `False`.
- **The `Orderless` case.** On an `Orderless` head the slot sorts first, so
  `SetAttributes[s, Orderless]; s[x, y] /. s[args__, OptionsPattern[]] :> ...`
  never matched. That was a silent wrong value.
- **FeynCalc:** this was 10 of the 17 `SUNSimplify` failures. `SUND` is
  `Orderless`, and both its "unique coloured objects" step and its own
  DownValues are written this way.

## A condition does not reorder a definition ; v0.6010

- **DownValue order no longer promotes a conditioned rule.**
  - Each condition layer used to add to a rule's specificity score, so
    `f[p[a1_, b1_]] := "gen" /; True` was tried before an earlier
    `f[p[a_, a_]] := "spec"`.
  - A rule written `rhs /; c1 /; c2` jumped ahead of ones with a single
    condition.
  - In both cases a different rule fired, with no message: a wrong value.
- **Conditions and pattern tests (`x_?test`) are now neutral, as in the
  reference, wherever they sit in the pattern.** Between two rules that are
  the same once the guards are removed, the guarded one still goes first:
  `g[x_] := 1; g[x_ /; x > 0] := 2` tries the guard first.
- **FeynCalc:** this was all 28 `FromGFAD` failures. `fromGFAD`'s eikonal rule
  `... /; c1 /; c2` had moved ahead of the square-completion rules.

## Rational and Complex numbers are atoms to rules and searches ; v0.6009

- **Replacement rules no longer reach inside a number** (a wrong value until
  now). This covers `ReplaceAll`, `ReplaceRepeated` and `Replace` at any level:
  - `{1/2} /. 2 -> 3` was `{1/3}`, and `{1/2} /. 1 -> 5` was `{5/2}`.
  - `{1/2} /. Rational -> f` was `{f[1, 2]}`, and `{I} /. Complex -> h` was
    `{h[0, 1]}`.
  - All of these now stay as they are, as in the reference. A rule for the
    whole number (`Rational[a_, b_] -> ...`) still applies.
- **`Cases`, `Count`, `Position` and `DeleteCases` treat a number as an atom.**
  `Count[{1/2}, 2, Infinity]` is `0` and `Position[{I}, Complex]` is `{}`.
  `DeleteCases[{1/2}, 2, Infinity]` used to corrupt the number into
  `Rational[1]`.
- **`FreeQ` and `MemberQ` now see a number's head at the number's own level**
  when heads are included. `FreeQ[I x, Complex]` and `FreeQ[f[1/2], Rational]`
  are `False`, and `MemberQ[f[1/2], Rational, {1}, Heads -> True]` is `True`.
  `FreeQ` keeps `Heads -> True` with an explicit level spec.
- **FeynCalc:** its `MomentumCombine` gates its complex-momentum step on
  `FreeQ[expr, Complex]`. All 16 `FCLoopSwitchEtaSign` failures were this.
- **`Limit` rejects a number as its variable**, with `Limit::ivar`, as the
  reference does. `Block[{x}, x = 5; Limit[Sin[x]/x, x -> 0]]` used to answer
  `0`, and then `1` once `/.` stopped rewriting inside `1/5`.
- **Exposed: a test of real-form Risch output was vacuous.** The check
  `FreeQ[g, Complex]` behind it never saw complex numbers, so it always passed.
  It now shows that `1/(3 + 5 Cos[x])` still integrates to complex-argument
  logs. That case is asserted for correctness only until the real
  reconstruction handles it.

## Times: numeric powers over a coprime basis ; v0.6008

- **When an exponent is symbolic, `Times` now writes numeric powers whose
  bases share a factor over one coprime basis**, as the reference does.
  - `4^a 6^b` is `2^(2 a + b) 3^b`, and the coefficient is absorbed:
    `12 2^n` is `3 2^(2 + n)` and `4^a/2` is `2^(-1 + 2 a)`.
  - Equal exponents merge first (`2^a 8^a` is `16^a`), and
    `(2/3)^a (9/4)^b` is `(2/3)^(a - 2 b)`.
  - The basis comes from gcds alone, so FeynCalc's products of huge prime
    powers collapse with no factoring.
  - All 16 probes match the reference.
- **The O3 split now reads bignum rationals.** Its sign test had looked only at
  `int64` rationals, so `(p/N^4)^a` was not split when `N^4` was a bignum.

## Simplify: exponent normal form and a cross-term coprime basis ; v0.6007

- **Equal exponents and arguments, written differently, now cancel.**
  `Simplify[a^(3 (-1 + e)) - a^(-3 + 3 e)]` and
  `Simplify[g[2 (1 + e)] - g[2 + 2 e]]` are `0`, as in the reference. Before
  and after the search, two compound exponents (or ordinary-head arguments) in
  the same place that agree after `Expand` both take the factored expansion.
  An exponent whose expansion is strictly smaller is expanded:
  `Simplify[la^2 (la^2)^(e - 1), la > 0]` is `la^(2 e)`, where it was
  `la^(2 + 2 (-1 + e))`.
- **Numeric powers across the whole expression are written over one coprime
  basis** (gcds only), with each basis power held as an opaque generator while
  the search runs. Terms that are one power family in different clothes then
  cancel. FeynCalc's `FactorList2` check, a sum of products of random-prime
  powers, is now `0`, and `FactorList2` ID6 now passes.

## Powers with a symbolic exponent as polynomial generators ; v0.6006

- **`Variables`, `Factor` and `FactorList` read `b^(n + k t)` as
  `b^n (b^t)^k`**, as the reference does (`src/poly/expsplit.c`).
  - `Variables[x^(1 + e) + x^(2 + e)]` is `{x, x^e}`.
  - `Factor[x^(2 + e) - x^e]` is `(-1 + x) x^e (1 + x)`.
  - `FactorList[(x + y)^(-3 + 3 e)]` is `{{1, 1}, {(x + y)^e, 3}, {x + y, -3}}`.
  - Each power was previously one opaque atom: `Factor` and `FactorList`
    left such sums unfactored, and `Variables` listed `x^(1 + e)` itself.
- **How it works.** Each `b^t` becomes a private symbol, the builtin runs on
  the rewritten input, and the generators go back in (`K^k -> b^(k t)`).
  - An integer coefficient of `t` is the generator's degree. A non-integer one
    keeps its term whole (`x^(e/2)`).
  - A numeric base is a constant to `Variables`, as there.
- **Results.**
  - The 14 new expectations are identical to the reference's output.
  - FeynCalc's `FactorList2` ID7, ID8 and ID11 now pass.
  - ID5, ID6 and ID10 still need `Simplify` to normalise exponents
    (`a^(3 (-1 + e)) - a^(-3 + 3 e)`).
