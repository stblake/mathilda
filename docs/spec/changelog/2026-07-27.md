# Changelog: week of 2026-07-27 (Mon) – 2026-08-02 (Sun)

Feature additions and fixes recorded during this week.

## `Compile[]` over machine integers: overflow, result heads, integer-only heads, integer arrays (2026-07-29)

`CT_INT` was in the compiler's type lattice from the start, but only `double` was
a first-class citizen: 18 integer opcodes against 69 real ones, no integer
buffers, and no overflow discipline. Machine-integer arithmetic silently wrapped.

```
In[1]:= Compile[{{n, _Integer}}, n^3][3000000]
Out[1]= 8553255926290448384          (* was; the interpreter says 27000000000000000000 *)

In[2]:= Compile[{{n, _Integer}}, n^3][3000000]
Out[2]= 27000000000000000000         (* now *)
```

**Overflow detection.** Every integer opcode that can overflow — `ADD_I`,
`SUB_I`, `MUL_I`, `NEG_I`, `ABS_I`, `POWI_I`, `INC_I` and the immediate forms —
tests for it and abandons the call, so the interpreter re-runs the body and
promotes to a bigint. The compiled answer is then the interpreted one by
construction. Loop accumulators inherit this: `Sum`, `Product` and a `Do` over an
integer local all lower to the same opcodes. The optimiser's constant folding
refuses to fold an overflowing integer operation for the same reason.

Two crashes and a wrong answer were fixed alongside:

- `Compile[{{a, _Integer}, {b, _Integer}}, Mod[a, b]][5, 0]` took the process
  down with `SIGFPE`. Both integer divisions now guard the two inputs the
  hardware traps on — a zero divisor, and `INT64_MIN / -1` whose quotient is not
  representable. `Mod[5, 0]` is unevaluated in the interpreter, so the compiled
  path hands it back.
- `Abs[-9223372036854775808]` returned a **negative** number, in the interpreter
  itself (`src/complex.c`), not just under `Compile`. Negating `INT64_MIN` wraps
  to itself; it now promotes to a bigint like every other arithmetic head.

**`RuntimeOptions`.** `Compile[…, RuntimeOptions -> {"CatchMachineIntegerOverflow"
-> False}]` (or the shorthand `RuntimeOptions -> "Speed"`; `"Quality"` is the
default `True`) keeps the wrapped `int64` instead of deferring. It is opt-in
because it makes the object answer differently from the interpreter once a result
leaves the machine-integer range. `Options[Compile]` reports it and
`SetOptions[Compile, …]` moves the default.

The choice is baked into each instruction (`IF_NOCHK` in `flags`) rather than
tested per execution, so **it costs nothing at run time** — measured at 10^8
iterations, median of 7:

| body | checks on (default) | option off | built without detection |
|---|---|---|---|
| `s = s + i` | 0.665 s | 0.663 s | 0.662 s |
| `s = s + (i 7 + 3)` | 0.993 s | 0.998 s | 0.953 s |

The detection itself costs 0–4% (about 0.13 ns per checked operation — the
overflow flag is already set by the `add`, so all it costs is a branch the
predictor never takes). Only a build with `-DVM_NO_INT_CHECK` recovers that 4%,
so the option is a **semantics** switch, not a performance one.

**Auto-compilation always checks.** `Plot`, `Table`, `NIntegrate`, `FindRoot`
and `NDSolve` compile behind the user's back as an optimisation, so a wrapped
integer there would turn a transparent speed-up into a silently wrong answer in
code that never mentioned `Compile`. `autocompile.c` masks `COMPILE_WRAP_INT`
off explicitly, and `SetOptions[Compile, …]` cannot reach it.

**Integer result heads.** A value compares equal whether it came back as the
Integer `35` or the Real `35.`, so the numeric parity tests could not see this
class at all. Sweeping all 103 `NumericFunction` heads with integer arguments
found 68 head divergences, of which 10 were integer-CLOSED and are now fixed:
`Power` (a runtime integer exponent, via `POW_II` — negative exponents are
Rationals and defer), `Factorial`, `Gamma`, `Binomial`, `Pochhammer`,
`Fibonacci`, `LucasL`, `Im`, `Arg` and `FractionalPart`. Each computes exactly
and abandons the call outside the domain where the interpreter returns an integer
at all — `Factorial[-1]` is `ComplexInfinity`, `7^-3` is `1/343`, `Arg[-3]` is
`Pi`. The remaining 58 are the documented divergence: the interpreter answers
symbolically (`Sin[3]`) or as a Rational (`3/2`), and no machine type holds those.

**Integer-only heads.** `GCD`, `LCM` (both n-ary), `PowerMod` (including the
modular inverse), `Divisible`, `EvenQ`, `OddQ`, `IntegerLength` and
`IntegerExponent` now compile over integer arguments. The `Bit*` family is
deliberately excluded: `BitAnd`, `BitOr`, `BitXor`, `BitNot`, `BitShiftLeft` and
`BitShiftRight` are **not implemented in the interpreter** — they come back
unevaluated — so a compiled path that answered them would answer where the
interpreter declines.

**Integer arrays.** A new `NDT_INT64` dtype gives packed machine-integer buffers,
which is what `Range[n]`, `Table[i, {i, 1, n}]` and `ConstantArray[0, n]` were
waiting for — all three used to bail, because the interpreter holds exact
Integers there and a `float64` buffer would have answered with different element
heads rather than merely faster.

```
In[3]:= Compile[{{n, _Integer}}, Range[n]][5] === Range[5]
Out[3]= True

In[4]:= Compile[{{v, _Integer, 1}}, Total[v]][{9007199254740993, 1}]
Out[4]= 9007199254740994          (* exact past 2^53 *)
```

`{v, _Integer, r}` is now a legal argument spec; a List of Integers packs into an
int64 buffer and comes back as a List of Integers. `NDT_INT64` is
compiler-internal — `NDArray[…]` never infers it, `DataType -> "int64"` is
refused, and the boundary always unpacks — so it cannot escape into the
interpreter. Packing, unpacking and `Total` use exact `int64` accessors
(`ndt_get_i` / `ndt_set_i`) rather than the generic `ndt_get` / `ndt_set` pair,
which routes through a `double` and is exact only to 2^53.

Elementwise FUSION stays real/complex only: the tile opcodes (`VADD_R`, `VMUL_C`,
…) have no integer forms, so an integer chain takes the ordinary per-element loop
— correct, just not strip-mined.


## `Compile[]`: the functional-programming heads enter the compilable subset (2026-07-29)

`Nest`, `Fold`, `FixedPoint`, `NestWhile`, `Map`, `Scan` and `Table` now lower to
bytecode. Before this the only functional head in the subset was `Nest`, and it
accepted exactly one spelling of its function argument — `Function[u, body]`.
`Nest[Cos, x, 5]` bailed; so did `Nest[#^2 &, x, 5]`.

```
In[1]:= CompileDiagnostics[{{v, _Real, 1}}, Fold[Plus, 0., v]]
Out[1]= {"Compiled" -> True, "ResultType" -> "Real", "Instructions" -> 12, ...}

In[2]:= nb = NDArray[Table[N[i]/1000., {i, 1, 200000}]];
        mc = Compile[{{v, _Real, 1}}, Map[Function[u, u^2 + 1.], v]];
        Timing[Do[mc[nb], {20}]]
Out[2]= {0.0085, Null}          (* interpreted: 2.34 s — 277x *)
```

### One resolver for every function argument

The VM has no function value — no closure, no function register — and it should
not have one: a lambda is inlined at its use site. What was missing was the
*compile-time* counterpart, so `fn_resolve` / `emit_apply` / `infer_apply`
(`src/compile/compile.c`) now answer "which function is this, and how do I paste
it in?" in one place, mirroring `apply_pure_function` (`src/purefunc.c:207`).
Accepted: `Function[u, body]`, `Function[{u, …}, body]`, `Function[body]` with
`#`/`#1`/`#2`, a bare head (`Sin`, `Plus`, any of the 93 machine kernels), a
`CompiledFunction`-valued symbol, `Composition[…]` and `Identity`.

`extract_function` is gone; `Nest` was retargeted onto the resolver and gained
every spelling at once, with no lowering of its own — which is the point of
having one resolver rather than a private parser per head.

Three refusals are load-bearing, because in each the interpreter's own answer is
not a machine number: a `Slot` is invisible under a **named** lambda (the named
path substitutes names only, `purefunc.c:247`, so `Function[u, # + u]` leaves a
live `Slot[1]`); arity is **exact** (a short call leaves the surplus parameter
symbolic, `purefunc.c:271`); and `Function[params, body, attrs]` can hold its
arguments, which an inlined body does not reproduce.

`Slot[k]` needed a second binding mechanism — it is an `EXPR_FUNCTION`, not a
symbol, and the scope stack matches interned symbol *pointers*. One flat frame is
exact rather than approximate: `substitute_slots` deliberately does not recurse
into a nested `Function`, so only the innermost frame is ever visible.

### `Map` has two lowerings, and they are a cost split, not a subset split

When the body threads elementwise, `Map[Function[u, body], v]` **is** `body` with
`u` bound to the whole array — which the existing fusion strip-mines and threads.
Ten lines, and 6.6x over the general per-element loop on `#^2 + 1.`. Three
conditions make the rewrite legal, each matching a way the interpreter's `Map`
differs from threading: the body must be `Listable` throughout (or
`Map[Function[u, Total[u]], v]` would become `Total[v]`), it must read exactly
one array and that array must be the parameter, and the result must keep rank 1
and the promised element type. Everything else takes the general loop, which is
correct for any body — `Map[Function[u, If[u > 0, u, -u]], v]` compiles and is
47x the interpreter.

### Where these heads decline, and why

Each refusal is a case where compiling would *diverge*, not merely be harder:

- **`Table` takes integer iterators only.** The interpreter walks a real
  iterator by repeated addition against a `1e-14` slack (`src/list/table.c:90`),
  so a closed-form `lo + k·di` differs in the last bits and, at the endpoint, in
  the element **count**.
- **`Table` refuses an integer-valued body**, as `ConstantArray` already refuses
  an integer fill: `Table[i, {i, 1, n}]` holds exact `Integer`s and a packed
  buffer has no integer dtype. `Table[1.0 i, {i, 1, n}]` is the compilable
  spelling.
- **`Map` refuses rank ≥ 2** (there it maps over *rows*, not elements) and any
  body whose result element type differs from the source's — `Map` over a packed
  array repacks with the **source** dtype (`src/funcprog.c:289`), so
  `Map[Abs, complexvector]` comes back complex-typed with real values.
- **`Fold` over an empty vector**, and **`Nest` / `FixedPoint` with a negative
  count**, fail the call: all three are *unevaluated* in the interpreter, where a
  counted loop would silently hand back the seed.
- **`FixedPoint` / `NestWhile` with no bound** carry the same 10⁶-application cap
  the interpreter uses (`ITER_SAFETY_CAP`, `src/funcprog.c:2062`) and fail on
  reaching it, so the call drops to the interpreter, which gives up in its turn.

`SameQ` is not `Equal`, and the difference is what makes the unbounded forms
terminate: `expr_eq` calls two NaNs the same (`src/expr.c:622`), so a compiled
`FixedPoint` whose orbit reaches NaN stops there instead of grinding to the cap.
New `OP_SAMEQ_R` / `OP_SAMEQ_C` implement exactly that rule (componentwise for
complex, mirroring `expr_eq`'s recursion into `Complex[re, im]`) rather than
composing it from four instructions in the innermost loop.

### Fixes found on the way

- **A built array took its result kind from an unrelated argument.** The
  boundary chose `List` vs `NDArray` from the *arguments* alone, so a body that
  constructs its result while also taking a packed argument answered with the
  wrong head:
  `Compile[{{v,_Real,1}}, ConstantArray[1., 3]][NDArray[{1., 2.}]]` gave
  `NDArray[{1., 1., 1.}]` where the interpreter's `ConstantArray` gives a `List`.
  Every array-constructing head would have inherited it. A program now reports
  whether its array result was *built* or *derived*, and only a derived one
  follows the arguments.
- **`compiled_eval_real` computed the abort flag and dropped it.** Harmless while
  no opcode an all-Real program could contain was able to fail — array ops can,
  and an all-Real program has no array registers. The new `OP_FAIL` made it
  reachable, and an unbounded `FixedPoint` at the cap would have returned
  whatever the accumulator held.
- **`Do` / `While` / `For` in result position returned `0`, not `Null`.**
  `Compile[{n}, Do[Sin[1.], {n}]][3]` gave `0` against the interpreter's `Null`.
  `Null` is not worth a fifth type in the lattice, so a statement-shaped head is
  now declined in the one position where the difference shows; inside a
  `CompoundExpression` its value is dropped and nothing is observable.
- **`Fold` / `FoldList` left an `NDArray` unevaluated.** `Fold`'s element walk
  looked straight past a packed argument (an `NDArray` is atomic), so
  `Fold[Plus, 0., NDArray[{1., 2.}]]` came back as itself while the identical
  `List` call folded fine. It now materialises once and reuses the general path,
  so the two agree by construction; `FoldList` gives its history back packed,
  matching `Map[f, NDArray[…]]`.

### Also compiled: the delegated structural heads, and the history builders

`Reverse`, `Sort`, `Accumulate`, `Flatten`, `Transpose`, `Take[a, n]` and
`Drop[a, n]` lower to a single new opcode that calls the interpreter's OWN
`NDArray` entry point (`ndstruct_reverse`, `ndred_accumulate`, …), each of which
already takes the whole call and promises a result identical to the equivalent
`List` call. That is the `Part` trick again, and it buys the same thing: the
compiled subset of these heads IS the interpreted one by construction. The win
is not the operation — it was already a fast buffer walk — but that a body
*containing* one no longer bails wholesale:

```
In[1]:= CompileDiagnostics[{{v, _Real, 1}}, Total[Take[Sort[v], 3]]]
Out[1]= {"Compiled" -> True, "ResultType" -> "Real", "Instructions" -> 8, ...}
```

When the ND layer meets a case its fast path does not handle it returns a nested
`List` rather than a packed array, and the VM treats exactly that as the signal
to hand the call back — so `Sort[v, Greater]` (a comparator is a function value
the ND path cannot call back into) and `Take[v, {2, 4}]` decline cleanly.

`NestList` and `FoldList` compile too. Their length is known before the loop
starts — `n + 1`, or the source length plus one for a seed — so they are the
existing `Nest`/`Fold` loops writing every iterate into a buffer. `NestList`
always *builds* its result, so it comes back as a `List`; `FoldList` follows its
source, matching the interpreter, which packs the history with the source dtype.
Both refuse an integer element type, the rule `ConstantArray` and `Table` follow.

### The selection heads: an interpreter gap, then the lowerings

`Select`, `TakeWhile`, `LengthWhile`, `SelectFirst`, `AllTrue`, `AnyTrue`,
`NoneTrue`, `Join`, `Differences`, `First`, `Last`, `Most`, `Rest`,
`RotateLeft`, `RotateRight`, `Riffle` and `Partition` all left an `NDArray`
**unevaluated**:

```
In[1]:= Select[NDArray[{1., 2., 3.}], # > 1 &]
Out[1]= Select[NDArray[{1.0, 2.0, 3.0}], #1 > 1 &]     (* before *)
Out[1]= NDArray[{2.0, 3.0}]                            (* now *)
```

An `NDArray` is an *atomic* value, so a builtin that walks
`arg->data.function.args` looks straight past one — while the identical `List`
call worked fine. `ndstruct_delist_repack` is the shared fix: materialise, reuse
the ordinary `List` implementation, repack a rectangular numeric result with the
source dtype. The ANSWER therefore comes from the `List` path and is identical to
it by construction; only the packing is new. `MapThread` gained the matching
repack, so it no longer unpacks data that arrived packed.

That had to come first, because compiling any of these would otherwise have
answered where the interpreter declines. With it done, `Select`, `TakeWhile`,
`LengthWhile`, `AllTrue`, `AnyTrue`, `NoneTrue`, `First` and `Last` compile too —
one predicate loop with four things done with the answer. `First`/`Last` lower
as `v[[1]]`/`v[[-1]]` rather than duplicating the indexing, so the range check
that makes `First[{}]` decline comes along for free.

An **empty** result declines: the interpreter cannot pack `{}` either, so it
answers with a `List`, and a length-0 array would be a different value.

### `Do` closes with `OP_LOOP`, and the `numloop` retarget is off the table

The disassembly of `Do[s = s + 1. i, {i, 1, n}]` said it plainly: **four of the
eight inner-loop instructions were pure loop control** — test, branch,
increment, back-edge — while `OP_LOOP`, which does increment, test and branch in
one instruction and which the fused array loops had been using all along, was
not used by any counted loop. A unit step now closes with it (the bound register
holds `hi + 1`, since `OP_LOOP` tests `++i < a`), keeping the entry guard
because a bottom-tested loop would otherwise run an empty range once. Non-unit
and negative steps keep the general form — `OP_LOOP` steps by one. 8 inner
instructions down to 5, and 1.21x on the plain loop.

This came out of investigating whether the legacy double-only stack machine
(`src/numloop.c`) could now be retired in favour of this engine. **It cannot,
and the plan that said otherwise was wrong.** Measured on identical bodies:

| body | this engine | `numloop` | |
|---|---|---|---|
| `Nest[(u + 2./u)/2 &, 3., 2·10⁶]` | 0.032 s | 0.081 s | engine **2.5×** |
| `While`, 10⁶ iterations | 0.015 s | 0.023 s | engine **1.6×** |
| `Do[s += Sin[1. i], {i,1,10⁶}]` | 0.026 s | 0.022 s | `numloop` **1.2×** |
| `Map[u^2+1. &, list]`, 2·10⁵ | 0.030 s | 0.028 s | `numloop` **1.1×** |

`Map` over a plain `List` pays this engine's boundary cost — packing 200 000
`Expr` nodes and unpacking them again — which `numloop` skips by walking the
List directly. Retargeting wholesale would have made the two most common loop
constructs *slower*, so `numloop` stays.

### Measured, packed in and packed out, 200k elements

| body | compiled | interpreted | ratio |
|---|---|---|---|
| `Map[Function[u, u^2 + 1.], v]` | 0.0085 s | 2.34 s | **277x** |
| `Map[Function[u, Sin[u] Exp[-u] + Sqrt[u]], v]` | 0.059 s | 6.38 s | **109x** |
| `Map[Function[u, If[u > 0.1, Sqrt[u], u^2]], v]` (general loop) | 0.080 s | 3.80 s | **47x** |
| `Fold[Plus, 0., v]` | 0.050 s | 0.947 s | **19x** |

Measure with a packed argument. Over a plain `List` the same comparison reads
1.0x, because both sides are then dominated by packing 200 000 `Expr` nodes at
the boundary and unpacking them again — and because the interpreter's `Map`
over a `List` already has the legacy `numloop` fast path, so the "interpreted"
side is not interpreted at all.

## Fix: `N[]` destroyed exact arguments before the function ever saw them (2026-07-29)

```
In[1]:= N[Sin[3141592653589793238]]
Out[1]= -0.641653                      (* wrong *)

In[2]:= N[Sin[3141592653589793238], 30]
Out[2]= -0.4463151633593201122016036193238
```

`N` numericalizes *leaves* and re-evaluates, so the leaf conversion is the one
step that must never lose information. In machine mode it was `(double)v`:
`3141592653589793238` became `3141592653589793280`, dropping the 42 low bits —
exactly the ones argument reduction needs — before `Sin` was reached. The trig
condition number is |x|, so at 3·10¹⁸ every digit was gone.
`Sin[3141592653589793238.]` was always right only because the parser builds that
literal as a 62-bit MPFR straight from its text.

The same defect hit the two-argument form from the other side:
`N[Sin[3141592653589793238], 10]` requested 34 bits and rounded the leaf to 34
bits first, answering `-0.32885101403`.

**Fix** — `numericalize` (`src/numeric.c`) is now a wrapper that scans the
input, evaluates at a working precision at which no exact leaf is lossy, and
rounds **once** at the end. Both terms are derived rather than tuned: an exact
integer or dyadic rational is carried at its own mantissa width, where it is
represented exactly; every other exact rational at `p + ⌈log₂|x|⌉ + 64` bits,
since a relative 2⁻ᵂ on an argument of size |x| reaches the answer amplified by
|x|. One choke point, so every builtin is fixed at once — measured across ~50
elementary and special functions.

Arguments a double *can* hold exactly (`10^20`, `2^53`, `3/4`, `1/3`) keep
taking the plain machine path, byte for byte. An inexact argument is still a
different question with a different answer: `Sin[1.0*^25]` is the sine of that
double (`-0.305258`), not of 10²⁵ (`-0.744790`).

Three defects found while sweeping for the above, all in the same family:

- **Machine numbers regained their exponent range.** `N[Exp[1000]]` was `inf.0`;
  it is now `1.97007×10⁴³⁴`, and `N[Exp[-1000]]` is `5.07596×10⁻⁴³⁵` rather than
  `0.` — a 53-bit mantissa with an arbitrary exponent, the representation
  `N[1001!]` already used. On a degenerate machine result `N` recomputes once in
  MPFR and keeps the answer only if it is genuinely better, so the normal path
  pays nothing. Past MPFR's own exponent range the result stays infinite.
- **`N[Gamma[2^53+1]]` aborted the process** with `GMP memory exhausted`.
  `Factorial`'s int64 branch called `mpz_fac_ui` with no size check while the
  BigInt branch above it declined for precisely that reason. It now predicts the
  result size from Stirling and stays symbolic past a 256 MB budget
  (`src/numbertheory/factorial.c`).
- **Leaf conversion rounds to nearest.** GMP's `mpz_get_d` / `mpq_get_d`
  truncate toward zero where an IEEE conversion rounds, which left
  `N[10^25, MachinePrecision]` and `1.0*^25` naming two doubles 2³¹ apart.
- **Comparisons on a machine number outside IEEE range.** `compare_numeric`
  read every operand as a `double`, which saturates 4×10²⁵⁷⁰ to `+inf` and
  5×10⁻⁴³⁵ to `0`, so it gave up and left the whole comparison unevaluated —
  `N[1001!] > 10^6` never worked. Now, and only when a plain `double` would
  saturate, both sides are compared in MPFR; in-range values keep the existing
  tolerant double comparison unchanged. Pre-existing, but the overflow fix
  above makes it reachable far more often (any `Abs[…] < tol` over a
  difference too small for a double).
- **A `Rational` leak in `numericalize`.** `expr_to_mpz` *initialises* its
  target (`mpz_init_set`), so the `mpq_init` in front of it allocated limbs
  that were immediately leaked. Under valgrind the numeric workload now
  matches the trivial `1+1` baseline exactly — 13,376 bytes / 418 blocks of
  documented macOS startup noise, and no frame from any changed file in a
  definitely-lost stack.

**Tests** — `tests/test_numeric_largearg.c` checks 15 elementary functions × 10
hard arguments against correctly-rounded MPFR oracles, plus the reported
transcript, the low-precision two-argument form, the overflow class, the
Factorial guard, and a non-regression block pinning the fast path.
`tests/test_numeric_stress.c` sweeps the invariant `N[f[x]] == N[f[x], 30]`
across every elementary and special function over an argument ladder; the
combinations neither path can answer live in `test_numeric_stress_gaps.inc` and
are asserted to stay there, so the list can neither grow nor rot silently.

`tests/CMakeLists.txt` gained `enable_testing()` — without it CMake generated no
`CTestTestfile.cmake` and `ctest` ran zero tests, which made every existing
`add_test()` line inert. `numeric_tests` and `trig_tests`, which had no
`add_test()` at all, are registered too.

## Fix: `Sqrt[]` of a large integer trial-divided to `sqrt(n)` (2026-07-29)

`Sqrt[3141592653589793238]` took **24 seconds**; `FactorInteger` of the same
number takes 3.6 ms. Extracting the square part of an integer radicand needs its
prime factorisation, and `power.c` did that by trial division all the way to
`sqrt(n)` — up to 3·10⁹ iterations for an `int64`. Measured on stock `power.c`:
three such calls cost 94 s.

The trial-division loop now stops at 10⁵ (~0.1 ms, and it certifies every
residue below 10¹⁰ as prime); anything larger goes to the general factoriser
behind `FactorInteger`. `factor_out_kth_power` is derived from that
factorisation instead of running a second `sqrt(n)` loop of its own.

**24 s → 7 ms (~3400×)**, with every extracted form byte-identical — verified by
diffing the output of stock and patched binaries over the radical corpus
(`Sqrt[12]` → `2 Sqrt[3]`, `Sqrt[72]` → `6 Sqrt[2]`, `12^(1/3)` →
`2^(2/3) 3^(1/3)`, `(16/81)^(1/4)` → `2/3`, `Sqrt[-12]` → `2 I Sqrt[3]`, …).
The pre-existing limitation that a radicand above `int64` is not reduced at all
(`Sqrt[4 * 3141592653589793238]` stays whole) is unchanged.

Found by the new `tests/test_numeric_stress.c`, which timed the case out.
`tests/test_power_integer_radical.c` pins both halves: the extracted forms, and
a budget that a regression to `O(sqrt(n))` cannot meet.

## Fix: `ArcSec` / `ArcCsc` / `ArcCoth` took the wrong branch at machine precision (2026-07-29)

For real `0 < x < 1` these return a complex value, and the machine path
disagreed with both the MPFR path and `ArcCos[1/x]`:

```
N[ArcSec[1/3]]      0. - 1.76275 I     (wrong)
N[ArcSec[1/3], 30]  0. + 1.762747... I (right, and what mpmath gives)
```

`ArcCos`, `ArcSin` and `ArcTanh` each carry an explicit correction for C99's
branch-cut convention on `(1, ∞)` differing from Mathematica's. Their reciprocal
counterparts call `cacos(1/c)` / `casin(1/c)` / `catanh(1/c)` and never got it,
so the reciprocal landing on that cut flipped the sign of the imaginary part.
Pre-existing and independent of argument size — `ArcSec[1/3.]` on a plain
machine real was wrong too. Also surfaced by the new stress sweep.

The `NDArray` element-wise kernels (`src/ndkernels.c`) carried the same
omission — `UK_ESC_FLIP` for `ArcSin`/`ArcCos`/`ArcTanh`, plain `UK_ESC` for the
reciprocals — so `ArcSec[NDArray[{0.3, …}]]` and `ArcSec[{0.3, …}]` disagreed.
Both now use a shared `UK_ESC_RECIP_FLIP` whose condition is `0 < |x| < 1`

## Fix: the Linux build broke on `jn` / `yn`, and the gate that lets it happen (2026-07-29)

`make` failed on Linux (issue #37) in `src/ndkernels.c`:

```
src/ndkernels.c:245:11: error: implicit declaration of function 'jn'
                                                [-Wimplicit-function-declaration]
  245 |     *rr = jn((int)nre, zre); *ri = 0.0; return isfinite(*rr);
```

`jn` and `yn` — the Bessel functions of integer order used by the `BesselJ` /
`BesselY` NDArray kernels — are X/Open extensions to `<math.h>`, not C99. glibc
hides them under `-std=c99`; Darwin exposes them whatever the standard, so the
break was invisible on the machine it was written on. GCC 14 promoted implicit
declarations from a warning to an error, which is why the build stopped rather
than quietly producing a binary that assumed `jn` returns `int` and truncated
every Bessel value it computed. `ndkernels.c` now requests the X/Open namespace
before its first include, the convention already used by `src/core.c`,
`src/repl.c` and `src/loadmodule.c`:

```c
#ifndef _XOPEN_SOURCE
#define _XOPEN_SOURCE 600
#endif
```

This is the second time the class has shipped — issue #36 was `M_PI` — so the
larger part of the change is making it the last:

- **`make check-c99` now covers functions, not just constants.**
  `tools/check_math_constants.py` becomes `tools/check_c99_portability.py` and
  keeps its `M_PI` check, adding a curated table of POSIX-only functions (`jn`,
  `yn`, `strdup`, `fileno`, `clock_gettime`, the `<unistd.h>` surface, …) mapped
  to the feature-test macros that expose each one. A file passes by defining a
  sufficient macro *before its first `#include`*; one defined after it is
  reported separately, because the preprocessor has already read the header it
  was meant to unlock. Run against the unfixed tree, it prints the file, the two
  symbols, and the exact block to paste.
- **Linux CI.** `.github/workflows/build.yml` compiles the whole tree against
  glibc on every push and pull request, with the optional dependencies (FLINT,
  LAPACKE, PCRE2, FFTW, ECM) installed so the autodetected paths are actually
  built. A checker only catches what is on its list; the compiler catches
  everything.
- **`-Werror=implicit-function-declaration`** is now in `CFLAGS`. On GCC 14 this
  is already the default; on older GCC and on clang it is a warning that
  scrolls past in a `-j12` build, leaving a binary that guesses the signature.
  The silent-wrong-answer outcome is worse than the failed build.

## Comparisons: `Indeterminate` is unordered, per IEEE 754 / ISO 60559 (2026-07-29)

`Indeterminate` is Mathilda's NaN — `0/0`, `Infinity - Infinity` and
`0 ComplexInfinity` all normalise to it. IEEE 754 / ISO 60559 makes a NaN
*unordered* with respect to every value, itself included: the five comparison
predicates yield `False` and the negated one yields `True`. The comparison
heads now follow that rule.

Previously `builtin_equal` reached its structural-identity shortcut
(`expr_eq`) first, so two `Indeterminate`s compared equal:

```mathematica
In[1]:= Indeterminate == Indeterminate
Out[1]= False                            (* was: True  *)

In[2]:= Indeterminate != Indeterminate
Out[2]= True                             (* was: False *)

In[3]:= Indeterminate < Indeterminate
Out[3]= False                            (* was: unevaluated *)

In[4]:= Indeterminate == 1
Out[4]= False                            (* was: unevaluated *)

In[5]:= 0/0 == 0/0
Out[5]= False

In[6]:= 1 < Indeterminate < 3
Out[6]= False
```

| Head | With an `Indeterminate` argument |
|------|----------------------------------|
| `Equal`, `Less`, `LessEqual`, `Greater`, `GreaterEqual` | `False` |
| `Unequal` | `True` |
| `SameQ`, `UnsameQ` | unchanged |

**Implementation.** `src/comparisons.c` gains `is_nan_operand` (the
`Indeterminate` symbol, or an `EXPR_REAL` holding a machine NaN — the state
`expr_eq`'s `isnan` branch already models) and `has_nan_operand`. It is
consulted in four places: ahead of the pair loop in `builtin_equal`, ahead of
`expr_eq` in `builtin_unequal`'s pair loop, at the top of
`evaluate_inequality` (shared by `Less`/`LessEqual`/`Greater`/`GreaterEqual`),
and at the top of `decide_pair`, which covers parser-folded chains routed
through `Inequality`. Since every argument of a chain takes part in at least
one adjacent pair, a single `Indeterminate` anywhere decides the whole
expression.

**`SameQ`/`UnsameQ` are deliberately exempt.** They test structural identity of
expressions rather than mathematical equality of values — the distinction IEEE
itself draws between its comparison predicates and `totalOrder`, which does
order a NaN with itself. `Indeterminate === Indeterminate` stays `True`. The
rule keys on `Indeterminate` as an *operand*, so a compound operand that merely
contains one (`{1, Indeterminate} == {1, Indeterminate}`) still decides
structurally and is `True`.

This is a deliberate divergence from Mathematica, where
`Indeterminate == Indeterminate` returns `True`.

Docstrings for `SameQ`, `Equal`, `Unequal`, `Less`, `Greater`, `LessEqual` and
`GreaterEqual` updated; `docs/spec/builtins/comparisons.md` gains an
"Indeterminate and IEEE unordered comparison" section. Covered by
`test_indeterminate_ieee_unordered` in `tests/test_comparisons.c` (30 cases,
including the ordinary comparisons that must stay unchanged).

## `MapAt` / `ReplaceAt`: association aliasing fix and one shared position walker (2026-07-28)

A review of `MapAt` against its Wolfram specification turned up a
data-corruption bug and six behavioural deviations, plus ~230 lines of
duplication: `replaceat_at_path`/`builtin_replace_at` were a near-verbatim clone
of the `MapAt` walker, minus its association branch.

**`MapAt` on an association mutated its input (fixed).** `expr_copy` is a
refcount bump, not a deep copy, so the association branch's
`rule->data.function.args[1] = nv` wrote through a node shared with the caller:

```mathematica
In[1]:= a = <|"x" -> 1, "y" -> 2|>;
In[2]:= MapAt[f, a, "x"]
Out[2]= <|"x" -> f[1], "y" -> 2|>
In[3]:= a
Out[3]= <|"x" -> f[1], "y" -> 2|>   (* before: `a` was destroyed *)
```

Association entries are now rebuilt as fresh `Rule` nodes (preserving
`RuleDelayed`), so nothing reachable from the input is ever written.

**One walker for both.** `expr_apply_at_path` and `expr_apply_at_positions`
(`src/part.c`, declared in `part.h`) resolve a position path and hand the
addressed part to a `PartLeafFn` callback — `f[part]` for `MapAt`, the rule set
for `ReplaceAt`. `part.c` already owned this vocabulary on the read side
(`expr_part`) and the write side (`expr_part_assign`); this is the third face of
it. The `Span` normaliser is now shared with `Part` (`span_resolve`), taking the
hand-rolled copies in the tree from eight to six. `ReplaceAt` gains association
positions for free — `ReplaceAt[<|"a" -> 1|>, 1 -> 9, Key["a"]]` was previously
a silent no-op.

**Empty position lists.** `MapAt[f, expr, {}]` is an empty list of *positions*
and now maps nothing; the position of the whole expression is the empty path,
`{{}}`. Both spellings previously applied `f` to the whole expression. The same
rule now governs `ReplaceAt`.

**Positions that do not exist leave the call unevaluated**, matching
`Part[{a, b, c}, 5]` — an out-of-range index, an absent key, a malformed `Span`
(zero step, symbolic bound), or a path running into an atom. Both previously
returned the expression silently unchanged. `Rational` and `Complex` are now
treated as atoms, as they are for `Part` and `MapIndexed`, so `MapAt[f, 1/2, 1]`
no longer manufactures a `Rational[f[1], 2]`.

**New in `MapAt`:** the operator form `MapAt[f, pos][expr]`; `All`, `Span` and
the head index `0` on associations; `NDArray` input (materialise, map, repack);
and `UpTo[n]` bounds inside a `Span`, inherited from `Part`'s normaliser.

**Held arguments (`MapAt`, `Map`, `MapAll`).** These three built `f[part]` and
evaluated it eagerly, which defeated an enclosing `Hold`.
`MapAt[f, Hold[1 + 1], 1]` gave `Hold[f[2]]`; it now gives `Hold[f[1 + 1]]`, and
`Map`/`MapAll` likewise. The application is left for the evaluator's fixed-point
loop, as `MapIndexed` and `assoc_map_values` already did. `Map`'s NDArray branch
evaluates explicitly before repacking, since `map_try_repack` needs real machine
numbers; `map_ndarray_axis` is unchanged (packed numeric elements cannot be held).

**The same aliasing bug in two more places.** Reviewing `MapAt` turned up two
further in-place writes through a refcount-shared association entry, both
silent data corruption and both association-only (the plain-`List` paths were
already pure):

```mathematica
In[1]:= u1 = <|"x" -> 1|>; u2 = u1; u2[["x"]] = 99; u1
Out[1]= <|"x" -> 1|>       (* before: u1 became <|"x" -> 99|> *)

In[2]:= w = <|"x" -> 1|>; ReplacePart[w, "x" -> 9]; w
Out[2]= <|"x" -> 1|>       (* before: w became <|"x" -> 9|> *)
```

Every association value rewrite in the tree now goes through one helper,
`assoc_entry_with_value` (`src/assoc.c`), which builds a fresh entry and copies
the head so a `RuleDelayed` entry stays delayed. `Part` assignment
(`assoc_entry_assigned`, `src/part.c`, covering the `Key[k]`, positional, `All`,
`Span` and key-list forms, and still appending an absent key), `ReplacePart`,
and the new walker all use it. `is_rule2` moved from `funcprog.c` to `assoc.c`
so the guard against a malformed `Association[1, 2]` is shared rather than
re-spelled at each site.

Tests: `tests/test_mapat.c` (+15 cases: association purity, `All`/`Span`/`0` on
associations, operator form, `Hold`, `{}` vs `{{}}`, malformed specs),
`tests/test_replaceat.c` (+6, including association positions and purity), and
`tests/test_association.c` (+8 aliasing regressions across `Part` assignment,
`ReplacePart`, and `RuleDelayed` preservation).

## `MapIndexed`: level specifications, `Heads`, and nested associations (2026-07-28)

`MapIndexed` implemented only a fraction of its Wolfram surface: the two-argument
form at depth 1. A level spec was rejected outright, positions never accumulated
past one component, `Heads -> True` did nothing, `Options[MapIndexed]` was empty,
and `MapIndexed[]` failed silently. It now reproduces the documented behaviour in
full.

**Level specifications.** `MapIndexed[f, expr, levelspec]` accepts `n`,
`Infinity`, `{n}` and `{n1, n2}` with either bound negative or `Infinity`.
Positive levels count indices from the root, negative levels count depth, and the
two mix — `MapIndexed[f, h0[h1[h2[h3[h4[a]]]]], {2, -3}]` selects exactly the
parts at level 2 or deeper *and* of depth 3 or more. Level 0 is the whole
expression, whose position is `{}`. An empty range (`0`, `{3,1}`) is the
identity, which also keeps a packed `NDArray` packed instead of unpacking it to
produce a copy.

**Full positions.** The second argument is now the position `Part` and `Extract`
take, accumulated down the traversal: `{1,2}` for the second part of the first
part, `{0}` for a head, `{Key[a], Key[b]}` for a value two associations deep.
`Extract[expr, #2]` is `#1` at every visited part, which the tests assert
directly. Positions ride on a stack-threaded frame chain rather than a heap
stack, so a position `List` is materialised only at the nodes actually mapped.

**`Heads -> True`.** Heads are visited as part 0 of their node —
`MapIndexed[f, {a,b,c}, Heads->True]` gives
`f[List,{0}][f[a,{1}],f[b,{2}],f[c,{3}]]`. Depth is computed heads-aware to
match, so a negative bound combined with `Heads -> True` selects the same node
`Depth[expr, Heads->True]` implies. (`Scan` inherits the heads-blind `get_depth`
and still mis-selects there; noted, not fixed here.) `MapIndexed` also joins the
`Options[]` defaults table, so `Options[MapIndexed]` answers `{Heads -> False}`.

**Associations at every level.** An association's parts are its values: the
`Rule` wrapper is not a level of its own, which is what makes a two-deep position
`{Key[a], Key[b]}` rather than four components long. `RuleDelayed` entries stay
delayed, and the `Association` head is never mapped.

**Fix: `MapIndexed[f, Association[a, b]]` segfaulted.** `is_association()` checks
only the head, and `builtin_association` leaves a malformed `Association[a, b]`
intact rather than rejecting it, so reading `args[1]` of the entry `a` type-punned
a symbol's `SymbolDef*`. Entries are now shape-checked before being read. The same
bug was reachable through `Map`, whose `assoc_map_values` has the matching guard
added — `Map[f, Association[a, b]]` crashed too.

**Behaviour changes.** An atom is now returned rather than left unevaluated
(`MapIndexed[f, a]` is `a`, matching `Map[f, a]`); `Rational` and `Complex` are
atomic, as they already are for `Depth` and `Level`, so `MapIndexed[f, 1/2]` is
`1/2` rather than `f[1,{1}]/f[2,{2}]`. Malformed trailing arguments now report
`MapIndexed::nonopt` / `MapIndexed::optx` and leave the call unevaluated instead
of being silently ignored, and `MapIndexed[]` reports `MapIndexed::argb`. Nothing
regressed: every 3-or-more-argument form was already unevaluated.

`MapIndexed` continues to defer the `f[…]` applications rather than evaluating
one per node. Wolfram specifies that it "always effectively constructs a complete
new expression and then evaluates it", and the difference is observable through a
held head: `MapIndexed[f, Hold[1+1, 2+2]]` gives `Hold[f[1+1,{1}], f[2+2,{2}]]`,
where `Map` — which evaluates per node — collapses it to `Hold[f[2], f[4]]`.

### Shared level-spec parsing

`Scan`'s private level-spec parser moves up beside `parse_level_spec` in
`funcprog.c` as `parse_level_spec_strict`, now shared with `MapIndexed`. Unlike
the lenient parser it accepts `Infinity` in either slot and *reports* failure
instead of silently falling back to the caller's default. `Map`, `Apply` and
`MapAll` deliberately still use the lenient one; migrating them is a separate
change with its own regression surface. (Worth knowing until then:
`Map[f, e, {2, Infinity}]` silently maps at level 1.) Alongside it, the four
places that read a level-spec or option head without checking it was a symbol now
go through `head_is`, `parse_options` checks the rule's arity before reading its
arguments, and `RuleDelayed` is accepted as an option shape across the family, so
`Heads :> True` is honoured.

### Testing

`tests/test_mapindexed.c` is new: 42 tests whose expected values are Wolfram's own
documented outputs for the same inputs, so the file doubles as a conformance
record. It covers the default level, every level-spec form (positive, `{n}`,
ranges, `Infinity`, negative, mixed, empty), `Heads` in all four spellings, atoms,
`Rational`/`Complex`, associations (flat, empty, nested, mixed key types,
`RuleDelayed`, malformed), `NDArray` at the default and non-default levels and
nested inside a list, and each diagnostic path. Three round-trip tests assert the
`Extract[expr, #2] === #1` property rather than a hand-written position list, and
`test_hold_defers_evaluation` pins the construct-then-evaluate rule that `Map`
gets wrong.

An anti-vacuity check confirmed the suite fails when an expectation is corrupted.
Under valgrind, `mapindexed_tests` leaks **less** than the untouched `mapat_tests`
control (13,376 B / 418 blocks vs 14,048 B / 425 blocks) and **no leak stack names
any Mathilda source file** — the residue is the documented macOS
dyld/libobjc/CoreFoundation baseline. `scan_tests` and the other 21 suites
touching `Map`/`Apply`/`Scan`/associations/options pass unchanged.

## Fix: `NLimit` reported a limiting value for oscillations that have none (2026-07-28)

`NLimit` samples `expr` on a geometric ladder and accelerates the sequence.  Its
only acceptance gate asked whether the *extrapolant* was plausible next to the
sample scale — nothing asked whether the sample sequence converges.  Since an
extrapolator returns a number for any input, every oscillatory non-limit was
reported as a limit:

```mathematica
In[1]:= NLimit[(Cos[x^2]/x^2 - Cos[(x+1)^2]/(x+1)^2) x^3, x -> Infinity]
Out[1]= -5.28256          (* an amplitude-modulated oscillation of growing envelope *)
```

The reported case was one of a family.  `x Sin[x]` gave `0.331263`,
`Sin[x] Sin[x^2]` gave `0.29418`, `Sin[1/x]/x` (at `x -> 0`) gave `0.331263`,
and so did plain `Sin[x]`, `Cos[1/x]`, `Sin[x^2]`, `x Cos[x]`, `Sqrt[x] Sin[x]`,
`Sin[Log[x]]`.  Only monotone divergence (`NLimit[1/x, x -> 0]`) was caught, by
the existing magnitude test.

### The criterion: does the envelope decay?

A limit exists only if the oscillation envelope decays — that is exactly what
separates `Sin[x]/x` (limit `0`) from `x Sin[x]` (no limit), and it is the one
statistic that survived measurement against the full regression battery.  Two
alternatives were tried and rejected: *increment contraction* misses bounded
oscillations (`Sin[x] Sin[x^2]` scores 0.45, well inside the accept range),
and *agreement of the extrapolants across independent Scales* has genuinely
overlapping distributions — a real near-zero limit like `Sin[x]/x^2` disagrees
across scales more than some true non-limits do, so no threshold exists.

The gate (`src/numerical_calculus/nlimit.c`) runs in two stages:

1. **Screen** — count the direction reversals of the sample increments
   `S_k − S_{k-1}`.  Monotone and smoothly-converging samples score zero and
   skip stage 2 entirely, so every ordinary limit follows exactly the path it
   followed before; the common case costs nothing.
2. **Envelope** — over the default `Terms -> 7` window a decaying and a
   non-decaying envelope simply are not distinguishable, so the diagnosis gets
   its own far wider ladder: 20 octaves sampled twice, at `Scale 2^k` and
   `Scale φ 2^k` with `φ = (Sqrt[5] − 1)/2`.  Because `1/2 < φ < 1` the merged
   sequence is a deterministic alternation (no sort needed), and the φ offset
   breaks the power-of-two aliasing that would otherwise hide `Sin[Pi x]`.
   With `env` the ratio of `max |f|` over the half nearest the limit point to
   `max |f|` over the half furthest from it, `env > 0.6` refuses the limit.

Measured over the regression battery: `env ≤ 0.22` for every limit that exists
(worst: `Sin[x]/x^(1/4) -> 0`) against `env ≥ 0.92` for every non-limit (worst:
`Sin[x] + Sin[Pi x]`), so the threshold sits between them with ~2.7× and ~1.5×
margin.  The verdict is a property of the expression, not of `Terms`, `Scale`
or `Method`, and the same gate runs on the MPFR path at the requested working
precision.

```mathematica
In[2]:= NLimit[x Sin[x], x -> Infinity]
        NLimit::osc: The sampled values oscillate with a non-decaying envelope;
                     no limiting value exists as the limit point is approached.
Out[2]= NLimit[x Sin[x], x -> Infinity]

In[3]:= NLimit[Sin[x]/x, x -> Infinity]     (* same oscillation, decaying envelope *)
Out[3]= 0.0142131
```

Oscillations whose envelope decays keep their limits — `Sin[x]/x`,
`Sin[x]/Sqrt[x]`, `Sin[x]/x^2`, `Exp[-x] Sin[x]`, `x Sin[1/x]` — and the wider
ladder also catches `Sin[Log[x]]`, which oscillates too slowly for the default
sampling window to see at all.

**Known blind spots**, both documented rather than papered over: an envelope
decaying slower than about `x^(-1/10)` across the diagnostic window cannot be
told from a non-decaying one and is refused (the safer of the two errors); and a
function sampled exactly on its own zeros (`Sin[Pi x]`, whose samples at
`x = 2^k` all vanish) presents no reversal for the screen to see.

New message `NLimit::osc`.  `tests/test_nlimit.c` gains
`test_oscillatory_divergence`, `test_oscillatory_is_option_independent` and
`test_oscillatory_false_positives` (the last being the guard against refusing a
limit that exists), and `nlimit_tests` — built but never registered — is now
wired into `ctest`.  Valgrind shows byte-identical totals at 0, 4 and 40
oscillatory calls: no per-call growth.

## Fix: the Knowles quasiquadratic case was unreachable from its reduced spelling (2026-07-28)

Two spellings of one integrand gave two different answers:

```
Integrate[E^(1/2 Log[Log[x]] - 1/Log[x])/(x Log[x]^2), x]   -Sqrt[Pi] Erf[1/Sqrt[Log[x]]]
Integrate[E^(-1/Log[x])/(x Log[x]^(3/2)), x]                unevaluated
```

They are the same function — `E^(1/2 Log[Log x])` *is* `Sqrt[Log x]`. The Knowles
erf engine (`src/calculus/knowles_erf.c`) handles this quasiquadratic case by
solving in `s = Sqrt[Log x]`, and its own `collapse_exp_of_log` pre-pass turns
the merged spelling into the reduced one. But the engine is only reachable
through `rt_integrate`, and `builtin_rischtranscendental`'s scope gate

```c
if (rt_has_algebraic_of_x(f, x)) return NULL;
```

bailed out first: `Log[x]^(-3/2)` is `Power[Log[x], Rational[-3, 2]]`, an
x-dependent base under a rational exponent, so the gate read it as an algebraic
extension. The merged spelling carries no radical and sailed through; the
reduced one never reached the dispatcher at all.

The gate is right about `Sqrt[x]` — the recursive Risch algorithm is a decision
procedure only over a purely transcendental tower. A fractional power of a
transcendental **kernel** is a different animal, and it is exactly Knowles Part I
§6. It is now admitted as a narrow exception (`rt_try_kernel_radical`): when
*every* algebraic site in the integrand is such a power, each is rewritten

```
g^(p/q)  =  g^n E^(r Log g),    n = Floor[p/q],  r = p/q - n
```

— the exact inverse of `collapse_exp_of_log`, and precisely the merged spelling —
and the constructive integrator runs on the result.

**Soundness.** The rewritten tower hides an algebraic relation: `E^(r Log g)` is
not transcendental over the lower field, since its `q`-th power is `g^p`. Nothing
on this path may therefore be trusted by construction, so the answer is returned
**only** behind a diff-back check against the original integrand, and the
non-elementary decision half deliberately does not run there — no
`Integrate::nonelem` certificate can be issued from a field whose transcendence
assumption is violated. A verified antiderivative is correct whatever field it
was found in; an unverified one is discarded.

A genuine radical of `x` is still refused and left to the algebraic routes:
`Sqrt[x]`, `Sqrt[1+x^2]`, `Cos[Sqrt[x]]` and `Sqrt[1+E^x]` all return exactly
what they did before. The admission is narrow enough that the only behaviour
that changed is the quasiquadratic family:

```
Integrate[E^(-1/Log[x])/(x Log[x]^(3/2)), x]   -Sqrt[Pi] Erf[1/Sqrt[Log[x]]]
Integrate[E^(1/Log[x])/(x Log[x]^(3/2)), x]    -Sqrt[Pi] Erfi[1/Sqrt[Log[x]]]
```

Tests: the four pins in `tests/test_knowles_erf.c` that had been failing now
pass, and four new ones pin the gate's continued strictness on genuine algebraic
integrands.

## Every `Limit` and `NLimit` method is now a head of its own (2026-07-28)

`Limit` and `NLimit` each run a cascade of strategies selectable with
`Method -> m`. Following the pattern already set by the `Integrate` and `Sum`
cascades (`Integrate`DerivativeDivides`, `Sum`Gosper`, ...), every setting is
now also callable directly:

```
Limit`Series[f, x -> a]       ==  Limit[f, x -> a, Method -> "Series"]
NLimit`EulerSum[f, z -> z0]   ==  NLimit[f, z -> z0, Method -> "EulerSum"]
```

The new heads:

| | |
|---|---|
| `Limit` | `Limit`Automatic`, `Limit`Substitution`, `Limit`RationalFunction`, `Limit`Asymptotic`, `Limit`Bounded`, `Limit`Series`, `Limit`LHospital`, `Limit`Gruntz`, `Limit`Oscillatory` |
| `NLimit` | `NLimit`Automatic`, `NLimit`EulerSum`, `NLimit`SequenceLimit`, `NLimit`Levin`, `NLimit`LevinU`, `NLimit`LevinT`, `NLimit`LevinV` |

**Each has its own `Information` string** describing what that strategy
actually does — the rule it applies, the hypotheses it needs, and when it
declines. `?NLimit`EulerSum` used to report *"No information available"*; it
now gives the Richardson/Romberg tableau, its convention (`2^j - 1`
denominators, matching `ND`), and the tail shapes it cannot annihilate.

Semantics are inherited wholesale from the `Method` option, including the one
that matters: **a named method that does not apply leaves the call
unevaluated** rather than falling back to the cascade, so
`Limit`RationalFunction[Sin[x]/x, x -> 0]` echoes itself. That makes these
heads the natural way to ask *does this layer decide the limit?* — useful when
testing or debugging a single strategy. The two positional arguments and every
other option (`Direction`, `Assumptions`, `Scale`, `Terms`, `WynnDegree`,
`WorkingPrecision`) are forwarded untouched; a `Method` option is dropped,
since the head already names the method. Attributes are
`{Protected, ReadProtected}`.

The plumbing is one shared helper, `common_method_alias` (`src/common.c`),
which rebuilds `head`m[args...]` as `head[args..., Method -> "m"]` and calls
the standard builtin directly — so it stands in the evaluator's seat and owns
the constructed call. Tests: `test_method_heads` in `tests/test_limit.c` and
`tests/test_nlimit.c`, the latter also exercising the new path in the
existing memory loop.

## `Limit`: an oscillatory normal form that *proves* a limit does not exist (2026-07-28)

New module `src/calculus/limit_osc.c` (+ `.h`), a decision layer in the
`compute_limit` cascade at `x -> ±Infinity`, also reachable as
`Method -> "Oscillatory"`. The motivating case was

```
In[1]:= Limit[(Cos[x^2]/x^2 - Cos[(x+1)^2]/(x+1)^2)/(1/x^3), x -> Infinity]
Out[1]= Indeterminate
```

which is asymptotically `2 x Sin[x^2 + x + 1/2] Sin[x + 1/2] + O(1)`. Every
pre-existing layer treats an oscillation as an opaque *bounded head*: the
squeeze envelope bounds each `Cos` by 1, which leaves two envelopes of size `x`
and fails, and neither Series nor the Gruntz mrv engine has a leading term to
latch onto. Nothing in the system could see that the two oscillations do not
cancel.

**The normal form.** `TrigToExp` + `Expand` rewrites `f` as

```
f(x) = c_0(x) + SUM_j c_j(x) E^(I theta_j(x))
```

with oscillation-free amplitudes and pairwise-distinct real phases. Two
canonicalisations make it a *normal* form: the exponent of each `E`-factor is
expanded (so `E^(I (1+x)^2)` and `E^(I (1 + 2x + x^2))` are one group), and the
constant part of a phase is folded into the amplitude (so `Cos[x]` and
`Cos[x+1]` share the phase `x`, and distinct phases then differ by a
*non-constant* function). Distinct phases are asymptotically orthogonal, so
nothing can cancel between groups — the form decides the limit.

**Four rules, all theorems** (proofs in the module header):

| | hypothesis | verdict |
|---|---|---|
| R1 | every `\|c_j\| -> 0` | `Limit[c_0]` (squeeze) |
| R3 | `SUM \|c_j\| / \|c_0\| -> r < 1`, `c_0 -> ±oo` | `Limit[c_0]` |
| R0 | one group strictly dominates, phase `-> ±oo`, `arg c` bounded | `Indeterminate` (IVT gives two accumulation values) |
| R2 | phases are real polynomials, `Limit[c_0]` finite, some `\|c_j\| /-> 0` | `Indeterminate` (Weyl mean / mean-square) |

R2 is the one that settles the motivating case, where all four groups have
modulus `~ x/2` and no single term dominates: the Cesàro mean of `\|f\|^2` is
`\|lim c_0\|^2 + SUM (lim \|c_j\|)^2` because every cross term dies by van der
Corput, so a surviving oscillation is incompatible with any finite limit;
`±Infinity` is ruled out by the window mean `(1/T) INT_T^2T f`.

**Newly decided** (all previously left unevaluated):

```
Limit[x Sin[x], x -> Infinity]                      Indeterminate
Limit[E^x Cos[x], x -> Infinity]                    Indeterminate
Limit[Sin[x] + Cos[x], x -> Infinity]               Indeterminate
Limit[Sin[x]^2, x -> Infinity]                      Indeterminate
Limit[Cos[x] - Cos[x + 1], x -> Infinity]           Indeterminate
Limit[Sin[x] Sin[x^2], x -> Infinity]               Indeterminate
Limit[Cos[x] + Cos[Pi x], x -> Infinity]            Indeterminate
Limit[Sin[x^2] + Cos[x], x -> Infinity]             Indeterminate
Limit[Sin[x + 2 Pi] - Sin[x], x -> Infinity]        0
Limit[x^2 (2 + Cos[x]), x -> Infinity]              Infinity
```

**Abstentions are kept honest.** `a Sin[x]` stays unevaluated (`a = 0` has the
limit `0`); so does `x^2 (1 + Cos[x])`, where the envelope exactly equals the
smooth part, and `Tan[x]`, whose `TrigToExp` image leaves an exponential in a
denominator so the normal form is incomplete. Sub-limits of amplitudes are
requested through a callback into `compute_limit`, keeping the caller's
recursion-depth and `Direction` bookkeeping in force.

The module is deliberately robust against un-flattened `Times`/`Plus` nodes:
`TrigToExp` currently returns `Times[c, Times[x, E^(I x)]]` (an evaluator
flatness invariant that an un-re-evaluated builtin result can violate), and a
collector that missed the inner `E`-factor would silently mis-classify the whole
limit.

**Finite limit points** reduce to the same analysis through `x = a ± 1/t` with
`t -> +Infinity`: an oscillation at a point is an oscillation at infinity in
`t`, with the very same normal form. A two-sided limit takes both sides and
requires them to agree. So

```
Limit[Sin[1/x]/x, x -> 0]                           Indeterminate
Limit[Sin[1/x] + Cos[1/x], x -> 0]                  Indeterminate
Limit[Sin[1/x]^2, x -> 0]                           Indeterminate
Limit[Cos[1/x] - Cos[1/x + 1], x -> 0]              Indeterminate  (was 0)
```

Tests: `tests/test_limit_oscillatory.c` (`limit_oscillatory_tests`), 9 groups
covering each rule plus the abstentions. One assertion in `tests/test_limit.c`
was updated: `Limit[Sin[x^2] + Cos[x], x -> Infinity]` used to record the
*abstention*, and now records the proof.

## Fix: plain substitution no longer hides a cancelled discontinuity (2026-07-28)

Both substitution fast paths in `src/calculus/limit.c` guarded only the
*top-level* result against a residual infinity. That misses the case where the
divergence cancels on the way:

```
Limit[Cos[1/x] - Cos[1/x + 1], x -> 0]     gave  0
```

Substituting `x -> 0` turns both terms into `Cos[ComplexInfinity]`, which the
`Plus` cancels to a confident `0`. The function actually oscillates over
`[-2 Sin[1/2], 2 Sin[1/2]]`. New `has_divergent_inner_arg_at` refuses the
substitution whenever an *inner argument* of a function node blows up at the
point — that is exactly discontinuity, so plain substitution was never a valid
limit there. The check runs on the **`Together`-cancelled** form, so a removable
singularity such as `(x^2 - 1)/(x - 1)` at `1` keeps its fast path. The
oscillating case now reaches the oscillatory layer and returns
`Indeterminate`.

## Fix: `Limit` no longer reports `E^DirectedInfinity[I]` as a limit (2026-07-28)

`exp_of_limit` (the `f^g -> Exp[g Log f]` reduction in `src/calculus/limit.c`)
folded the log-limit back through `Exp[...]` and returned whatever came out.
For a log-limit that diverges along a *non-real* ray that is an unfolded
symbol, so

```
Limit[E^(I x), x -> Infinity]     gave  E^DirectedInfinity[I]
Limit[E^(I x)/x, x -> Infinity]   gave  E^DirectedInfinity[I]     (should be 0)
```

— the second is an outright wrong answer, the `1/x` having been swallowed. The
reduction now refuses any result that still carries an infinity flavour, so
both fall through to the oscillatory layer and come back as `Indeterminate`
and `0` respectively.

**Two downstream consequences**, both of them the fix working as intended:

- `Limit[x^n, n -> Infinity]` is now honestly unevaluated instead of
  `E^DirectedInfinity[Log[x]]`. Without knowing `|x|` the limit is `0`,
  `ComplexInfinity` or `Indeterminate`, so there is no value to give. (The
  `Assumptions -> Abs[x] R c` dispatch is unaffected and still answers.) The
  pin in `tests/test_limit_assumptions.c` was updated.
- The Frullani pre-pass in `src/calculus/integrate_ramanujan.c` used to read
  its `x -> Infinity` boundary value straight out of that leaked form: it took
  `Limit[E^(-a x), x -> Infinity]`, matched `E^DirectedInfinity[dir]`, and
  resolved `dir < 0` under the assumptions. With `Limit` correctly declining,
  `Integrate[(E^(-a x) - E^(-b x))/x, {x, 0, Infinity}, Assumptions -> a > 0 && b > 0]`
  stopped closing on the Ramanujan route. New `frullani_boundary` asks `Limit`
  first and, when it declines, takes the limit of the *exponent* instead —
  `Limit[-a x, x -> Infinity]` is decidable — and re-wraps it as `E^(...)` for
  the existing sign resolution. The consumer now reconstructs what it needs
  from a valid limit rather than depending on `Limit` to emit an invalid one.

## The substring predicates: `StringContainsQ`, `StringFreeQ`, `StringStartsQ`, `StringEndsQ` (2026-07-28)

Added the four substring-containment predicates in one new translation unit,
`src/strings/regex/stringcontainsq.c`, registered in `regex_init()` (docstrings
in `info.c`, symbols in `sym_names.c`). Until now the only way to ask "does this
string contain that?" was `StringCount[s, p] == 0` or
`StringMatchQ[s, ___ ~~ p ~~ ___]`.

All four ask a single question — *does any rule match anywhere?* — so they share
one core (`sq_dispatch`) and differ only in an `SqKind` tag, realising the
Wolfram Language identities directly:

```
StringFreeQ  [s, p] == !StringContainsQ[s, p]
StringStartsQ[s, p] ==  StringContainsQ[s, StartOfString ~~ p]
StringEndsQ  [s, p] ==  StringContainsQ[s, p ~~ EndOfString]
```

- `StringContainsQ["bcde", "b" ~~ __ ~~ "e"]` → `True`;
  `StringFreeQ["abcade", x_ ~~ x_]` → `True`.
- Any pattern the shared translator understands works, including
  `RegularExpression[...]` mixed with string patterns:
  `StringContainsQ["bac 123", RegularExpression["a.*"] ~~ DigitCharacter ..]`
  → `True`.
- A list of patterns is `Alternatives`
  (`StringFreeQ["cad", {"a", "b"}]` → `False`); an empty list matches nothing.
- A list of subjects threads
  (`StringContainsQ[{"aba", "bcd", "cea"}, "a"]` → `{True, False, True}`).
  Unlike `StringCount` / `StringMatchQ`, a non-string subject — or a subject
  list holding one — leaves the call unevaluated rather than passing the element
  through: a Boolean predicate answering `{False, 7}` would be wrong.
- Operator form: `StringFreeQ["ac", IgnoreCase -> True]["BACCD"]` → `False`;
  `Select[{"abc", "xyz", "bat"}, StringContainsQ["a"]]` → `{"abc", "bat"}`. A
  curried option is carried into the eventual application.
- `Options[head]` → `{IgnoreCase -> False}` on all four, honouring `SetOptions`
  with an explicit call option overriding it.
- **Attributes**: `Protected` (not `Listable` — each hand-threads over the
  subject so the pattern argument is never threaded).
- Arity: `head[]` reports
  `head::argt: head called with 0 arguments; 1 or 2 arguments are expected.`

Matching uses one `regex_match()` per rule with an early exit on the first hit,
rather than the `regex_scan()` enumerator the counting and extraction builtins
use — a predicate never needs to know where or how often the pattern occurred.

### New string-pattern heads: `StartOfString` and `EndOfString`

The shared translator (`src/strings/regex/string_pattern.c`) gained the two
zero-width anchors, mapping to PCRE's absolute `\A` and `\z`. They benefit the
whole regex string family, not just the new predicates:

```mathematica
In[1]:= StringCount["abcabc", StartOfString ~~ "abc"]
Out[1]= 1

In[2]:= StringPosition["abcabc", "abc" ~~ EndOfString]
Out[2]= {{4, 6}}

In[3]:= StringReplace["abcabc", StartOfString ~~ "abc" -> "X"]
Out[3]= "Xabc"
```

This is also how `StringStartsQ` / `StringEndsQ` anchor: rather than thread a new
anchor mode through the shared rule builder (eight call sites), they synthesise a
temporary `StringExpression[StartOfString, patt]` and hand it to the unmodified
builder unanchored. That is safe because the translator parenthesises every
child, so an alternation-bearing pattern becomes `(?:(?:\A)(?:a|b))` rather than
the broken `\Aa|b` — `test_anchor_grouping` pins that down with
`StringStartsQ["zb", RegularExpression["a|b"]]` → `False`.

### Tests

`tests/test_stringcontainsq.c` (new, wired into `tests/CMakeLists.txt` as
`stringcontainsq_tests`) covers all fifteen groups: literals, string
expressions, regular expressions, pattern lists, subject threading, `IgnoreCase`,
`Options`/`SetOptions`, the operator form, `StringStartsQ`/`StringEndsQ`, anchor
grouping, the new anchors across `StringCases`/`StringCount`/`StringPosition`/
`StringReplace`, arity and unevaluated cases, and attributes. `test_duality`
asserts each of the four identities above over a table of subjects crossed with
patterns, so the four cannot drift apart.

operator form and the synthesised anchor wrapper) reports byte-for-byte the same
valgrind totals as a `Do[1 + 1, {5000}]` control.

## `StringCount`, and a shared scanner for the string-pattern family (2026-07-28)

Added `StringCount` in a new translation unit `src/strings/regex/stringcount.c`,
registered in `regex_init()` (docstring in `info.c`, symbol in `sym_names.c`).
It answers "how many matches?" without materialising them: it runs the same
match enumeration as `StringCases` but records a 40-byte span per match instead
of a `malloc` + `expr_new_string` + `List` element.

- `StringCount["the cat sat on the mat", "at"]` → `3`.
- `StringCount["string", patt]` accepts any string expression the pattern
  translator supports — `DigitCharacter`, `NumberString`, `x_ ~~ x_`,
  `Except[...]`, `RegularExpression["..."]`, and so on:
  `StringCount["x=1.5, y=-2", NumberString]` → `2`.
- A list of patterns counts occurrences of any of them; a `Rule`/`RuleDelayed`
  pattern counts matches of its left-hand side (a replacement cannot change a
  count); a list of subjects threads, with non-string elements passed through:
  `StringCount[{"a1", 5, "b22"}, DigitCharacter]` → `{1, 5, 2}`.
- Options `Overlaps -> False` (default), `True`, or `All`, and
  `IgnoreCase -> True`, both seeded from `Options[StringCount]` so `SetOptions`
  works: `StringCount["AAAA", "AA"]` → `2`,
  `StringCount["AAAA", "AA", Overlaps -> True]` → `3`,
  `StringCount["AAAA", x__, Overlaps -> All]` → `10`,
  `StringCount["aAbB", "a", IgnoreCase -> True]` → `2`.

### The shared scanner

The three `Overlaps` policies previously existed only as `static` helpers inside
`stringposition.c`. Rather than triplicate them, they were extracted into
`regex_common.{c,h}` as `regex_scan()` / `regex_scan_free()` (plus
`regex_match_opt()` for trailing-option decoding), and `StringCases`,
`StringCount` and `StringPosition` were all rebuilt on top. Consequences:

- `StringCount[s, p, opts] === Length[StringCases[s, p, opts]] ===
  Length[StringPosition[s, p, opts]]` now holds by construction for every
  pattern and every option setting, not just at the defaults. `test_invariants`
  in `tests/test_stringcount.c` pins it.
- **`StringCases` gained `Overlaps` and `IgnoreCase`**, closing a real WL gap —
  it previously rejected any third argument outright.
  `StringCases["AAAA", "AA", Overlaps -> True]` → `{"AA", "AA", "AA"}`;
  `StringCases["AAA", x__, Overlaps -> All]` →
  `{"AAA", "AA", "A", "AA", "A", "A"}`;
  `StringCases["aAbB", "a", IgnoreCase -> True]` → `{"a", "A"}`.
  `Options[StringCases]` is `{IgnoreCase -> False, Overlaps -> False}`
  (`StringPosition` keeps `Overlaps -> True`, matching WL).
- The scanner allocates its capture pool only when a caller asks for it, so
  `StringCount` and `StringPosition` never pay for capture offsets while
  `StringCases` still expands `$0`/`$n` templates — including under
  `Overlaps -> All`, where offsets are rebased to be subject-relative.
- The `Overlaps -> False` policy is now a streaming leftmost-match scan (the old
  `StringCases` loop) rather than collect-every-overlap-then-greedily-filter
  (the old `StringPosition` loop). The two are equivalent; the streaming form is
  `O(matches)` instead of `O(all overlapping candidates)`. `StringPosition`'s
  existing suite is unchanged and still passes.
- `StringCases` and `StringCount` now emit `::argrx` when called with fewer than
  two positional arguments, instead of silently returning unevaluated. The WL
  occurrence-limit form `StringCases["s", patt, n]` remains unsupported and is
  still left unevaluated *without* a message, since "2 arguments are expected"
  would misdescribe it.

- **Attributes**: `Protected` (not `Listable` — the family hand-threads over a
  list of subjects so the pattern argument is never threaded). Tests in
  `tests/test_stringcount.c` (13 groups: literals, string patterns, regexes,
  pattern lists, rule patterns, threading, all three `Overlaps` modes,
  `IgnoreCase`, `Options`/`SetOptions`, cross-builtin invariants, zero-width
  matches, error paths, and the new `StringCases` options), plus four new
  `StringCases` groups in `tests/test_stringfns.c`. `leaks`: 0 leaks across
  `stringcount_tests`, `stringfns_tests`, `stringposition_tests`,
  `strings_tests` and `regex_tests`; `make check-c99` clean.

## Riffle list built-in (2026-07-27)

New `Riffle[list, x]` / `Riffle[list, {x1, x2, ...}]` in
`src/list/riffle.{c,h}`, registered in `src/list/list_init.c` with
`Protected` and a docstring. Interleaves separators into the gaps between
successive elements: a non-list second argument goes in every gap, while a
`List` second argument is consumed cyclically left to right, so
`Riffle[{a,b,c,d}, {x,y}]` gives `{a, x, b, y, c, x, d}`. Only a `List`
separator cycles — any other head (e.g. `f[x, y]`) is one separator.

Separators never precede the first element or follow the last, so `n` elements
have exactly `n - 1` gaps and the result has `2n - 1` slots. Three degenerate
cases fall out of that invariant and are all covered by tests:

- `n <= 1` — no gaps, so the input passes through unchanged whatever the
  separator is. Checked *before* the `2n - 1` output sizing, since `n == 0`
  would otherwise underflow `size_t` to `SIZE_MAX`.
- An empty separator list — nothing to interleave, same pass-through; this also
  keeps the cycling index from dividing by zero.
- Separators in excess of the gap count are never indexed, so
  `Riffle[{a,b,c}, {x,y,z}]` leaves `z` unused.

The head of the first argument is preserved rather than forced to `List`
(`Riffle[f[a,b], x]` gives `f[a, x, b]`), matching the convention in
`reverse.c` and `subsets.c`; it is also what makes `Riffle[{}, 0]` give `{}`
with no special case.

One pass, `O(n)` copies, and a single exactly-sized allocation — the output
length is known up front from `n`, so no growable buffer is used. The builtin
only reads its argument and returns a wholly fresh tree, so the evaluator's
ownership of the input expression is untouched.

`tests/test_list.c:test_riffle` covers the 15-row acceptance table from
md-czh.1. Packed arrays (`EXPR_NDARRAY`) are a distinct representation from
`List` and are left unevaluated for now — tracked as md-2aa.

## New builtin: `Gather` (2026-07-27)

`Gather[list]` collects structurally identical elements of a list into
sublists, in order of each element's first occurrence, with input order
preserved inside each sublist:

```mathematica
In[1]:= Gather[{1, 7, 3, 7, 2, 3, 9}]
Out[1]= {{1}, {7, 7}, {3, 3}, {2}, {9}}

In[2]:= Gather[{a, b, a}]
Out[2]= {{a, a}, {b}}
```

Unlike `Split`, equal elements are collected from anywhere in the list rather
than only from adjacent runs, so the two non-adjacent `a`s above share a group.
`Gather[list]` is exactly `GatherBy[list, Identity]`.

Implementation. Rather than duplicate the grouping logic, the hash-indexed loop
inside `builtin_gatherby` was hoisted into a shared engine
`assoc_gather_core(list, f)` (`src/assoc.c`, declared in `src/assoc.h`); the
`KeyIndex` helpers it needs are static to that translation unit, so the core
lives there. Passing `f == NULL` selects the identity key — the element is its
own group key, taken by `expr_copy` with no expression application built or
evaluated. That keeps `Gather` at a true O(n) with none of the `n` `Identity[x]`
evaluations that spelling it as `GatherBy[list, Identity]` would incur, and
makes the two agree by construction rather than by coincidence.
`builtin_gatherby` is now a two-line delegation; its behaviour, including the
association path, is unchanged.

New files `src/list/gather.{c,h}` (`builtin_gather`), registered in
`src/list/list_init.c` with `Protected` and a docstring, included from
`src/list/list.h`. Association input is inherited from the shared core:
`Gather[assoc]` gathers the entries by value into sub-associations with keys
preserved, matching `GatherBy[assoc, Identity]`. Non-list, non-association
arguments and any arity other than 1 return unevaluated.

Tests: `test_gather` in `tests/test_list.c` covers the grouping table above
(including `{}`, singletons, all-equal, all-distinct, and non-adjacent repeats),
asserts `Gather[l]` and `GatherBy[l, Identity]` print identically on every case,
and checks the unevaluated fallbacks. `tests/CMakeLists.txt` gains
`../src/list/gather.c`.

## New list builtin: Subdivide (2026-07-27)

`Subdivide` generates equally spaced points spanning an interval, including
both endpoints — the complement to `Range`, which takes a step size and need
not land on its upper bound. Three forms, each returning `n + 1` points
(`n` counts the *parts* the interval is cut into):

- `Subdivide[n]` — `{0, 1/n, 2/n, ..., 1}`, spanning 0 to 1.
- `Subdivide[max, n]` — spanning 0 to `max`.
- `Subdivide[min, max, n]` — spanning `min` to `max`; point `i` is
  `min + i (max - min)/n`.

New module `src/list/subdivide.{c,h}` (`builtin_subdivide`), registered in
`src/list/list_init.c` with `Protected` and a docstring, exported via
`src/list/list.h`.

**Exactness.** Two independent guarantees. The endpoints are *copied, never
computed*, so no arithmetic can touch them; and each interior point is derived
directly from its index as the single fraction `(min n + i (max - min))/n`
rather than as `previous + step`, so there is no accumulator for error to
collect in. That fraction is reduced once by `make_rational()`, which returns a
plain `Integer` when the reduced denominator is 1 — hence whole-number points
printing as integers alongside rationals in one list:
`Subdivide[10, 4] → {0, 5/2, 5, 15/2, 10}`.

**Descending intervals** are supported with no special case: the formula is
applied verbatim, so `max < min` simply yields a negative step —
`Subdivide[3, 1, 4] → {3, 5/2, 2, 3/2, 1}`. Nothing branches on the sign of the
step, compares the endpoints, sorts, or takes an absolute value. A degenerate
interval has step 0 and repeats the endpoint: `Subdivide[5, 5, 2] → {5, 5, 5}`.

**Two evaluation paths.** A machine-integer fast path handles endpoints with
`|value| <= 2^31` under the `n <= 10^6` cap, where int64 overflow is excluded by
precondition rather than by per-operation checks. Everything else — bigint,
rational, real, or symbolic endpoints — defers arithmetic to the core evaluator
by building `Plus[min, Times[i, max - min, Power[n, -1]]]`, the strategy
`src/list/rescale.c` already uses. So `Subdivide[10^20, 4]` stays exact in
bigints and `Subdivide[a, b, 2]` returns `{a, a + 1/2 (-a + b), b}` with exact
symbolic endpoints. For the two-argument form the implied lower endpoint takes
on the exactness of the supplied one, so an inexact interval carries no lone
exact `0`: `Subdivide[1.0, 4] → {0., 0.25, 0.5, 0.75, 1.}`.

`n` must be a positive integer; zero, negative, rational, real, symbolic, and
oversized `n` all leave the expression unevaluated, as does an argument count
outside 1–3.

Tests: `test_subdivide()` in `tests/test_list.c` — 15 rows covering all three
forms, lowest-terms reduction, mixed integer/rational output, the descending
and degenerate intervals, and the unevaluated cases. Clean under
`-std=c99 -Wall -Wextra`, clean under AddressSanitizer, and `leaks`-clean over
300 iterations of both the fast and general paths.

## Auto-compilation of Plot / Plot3D / Table / NIntegrate / FindRoot (2026-07-27)

The numeric builtins now transparently use the `Compile[]` bytecode engine as a
fast path: each compiles its held body once as a function of its sample
variable(s) and evaluates it over machine numbers with no `Expr` allocation,
instead of running the full symbolic evaluator at every one of the thousands of
sample points. Uncompilable bodies (any construct outside the compilable subset,
e.g. `Zeta`) transparently keep the interpreter path, so results are unchanged.

New shared adapter `src/compile/autocompile.{c,h}`: `autocompile_new(body,
vars, nvars)` (→ `NULL` if uncompilable), `autocompiled_eval_real` /
`autocompiled_eval_complex`, `autocompiled_free`. The header is self-contained
(no `<complex.h>`/`compile.h` leak — `double _Complex` is a builtin type) so it
never pollutes callers with the `I` macro.

Correctness rule shared by the callers: a compiled *real* program returns a
non-finite value exactly where the interpreter would instead produce a *complex*
result (e.g. `Sqrt` of a negative). Callers that exclude non-real points (Plot)
drop it; callers that need the contribution (NIntegrate, FindRoot, real-iterator
Table) fall back to the interpreter at that single point.

- **Plot / Plot3D** — compiled in the per-curve/per-surface setup; a non-finite
  or non-real sample excludes the point, matching the existing behaviour
  (`Plot[Sqrt[x], {x,-1,1}]` still drops the negative half). **~215×** on a
  400-point 2-D curve; **~11×** on an 80×80 surface.
- **Table** — ONLY the inexact (machine-real) iterator branch, where the
  interpreter already yields machine reals; exact iterators
  (`Integer`/`BigInt`/`Rational`) and symbolic bodies are untouched and
  bit-for-bit unchanged (`Table[i^2,{i,1,5}]`, `Table[2^i,…]` BigInt,
  `Table[Sin[i],…]` symbolic). Per-element interpreter fallback keeps
  `Table[Sqrt[x],{x,-1.,1.,1.}]` complex. **~128×** on a 50k-element real table.
- **NIntegrate** — the 1-D machine-precision integrand (`ni_eval_at`), for the
  finite / half-line / whole-line real cases. Complex-contour abscissae and the
  MPFR path are untouched; a complex-valued integrand falls back per sample
  (`NIntegrate[Sqrt[x-1],{x,0,2}] → 2/3 + (2/3)I`). **~353×** on a batch of 50
  integrals. Fixed a latent bug the change exposed: the oscillatory
  amplitude/phase decomposition value-copies the sampler context and swaps its
  body, which must reset the compiled program (`ni_ctx_rebody`).
- **FindRoot** — the scalar, machine-precision, real function (Newton / Secant /
  Brent, and the finite-difference-derivative path used when `D` is inert, e.g.
  `Zeta'`). Complex-root, MPFR, and multivariate-system solves keep the
  interpreter. **~19×** on 5000 scalar solves.

Tests: `tests/test_autocompile.c` — end-to-end parity through the real builtins,
non-real exclusion / per-point fallback, uncompilable fallback, and the
oscillatory regression. All `leaks`-clean. MPFR paths untouched throughout.

### Follow-up: multi-dimensional NIntegrate and FindRoot systems

- **Multi-D NIntegrate** — the multi-dimensional machine chokepoint
  `ni_mc_sample` (shared by the Genz–Malik cubature and Monte-Carlo engines) now
  compiles the body once as `f(v_1..v_d)` and writes the complex result straight
  into the sample slot (no boxing). A box where the integrand goes complex (e.g.
  `Sqrt[x+y-1]` over the unit square) still contributes its imaginary part via the
  per-point interpreter fallback. **~504×** on a 2-D 500k-point Monte-Carlo
  integral.
- **FindRoot systems** — `fr_run_newton_system_real` compiles each component
  `f_i` and each symbolic Jacobian entry `D[f_i, x_j]` as functions of all
  variables, used at the residual/Jacobian/step-check evaluation sites via a
  shared `fr_try_compiled` helper. An uncompilable component or Jacobian row
  (e.g. `LogGamma`, whose derivative `PolyGamma` is evaluable) stays on the
  interpreter while the rest runs compiled; the linear solve is unchanged.
  **~6.9×** on a 2×2 nonlinear system. (Systems with an *inert* Jacobian entry,
  e.g. `Zeta'`, still fail as before — a pre-existing limitation.)

## Compile engine M3a — rank-1 machine arrays (2026-07-27)

The `Compile[]` bytecode engine was scalar-only. It now carries **rank-1 machine
vectors** as a first-class value category, delegating every buffer operation to
the existing NDArray subsystem, so a compiled program can take `NDArray`
arguments, compute over whole buffers, and return an `NDArray` or reduce to a
scalar — with no `Expr` allocation per element and no evaluator round-trip per
operation.

**Type lattice.** `CompileType` now packs array types into the same integer as
the scalars (`CT_ARR + 4*(rank-1) + elem`), so every field that already carried a
`CompileType` — inference results, register types, declared argument types —
carries array types with no parallel plumbing. New helpers `CT_ARRAY(elem,rank)`
/ `CT_IS_ARRAY` / `CT_ELEM` / `CT_RANK`, plus a `CT_ERR` sentinel that makes the
enum's underlying type signed (so the existing `(int)t < 0` checks are well
defined). `CompileValue` gained an `Expr* a` member: an array argument is
**borrowed**, an array result is **owned by the caller**.

**Compilable over arrays.** `Plus`, `Times`, `Subtract`, `Minus`, `Divide`,
`Power` (vector⊕vector, vector⊕scalar broadcast, and scalar^vector); every
elementary and special function with a registered ND unary kernel (`Sin`, `Exp`,
`Log`, `Gamma`, `Abs`, `Re`/`Im`/`Arg`/`Conjugate`, `Floor`/`Ceiling`/`Round`,
…); the two-argument ND binary kernels (`Log[b,v]`, `ArcTan[v,y]`, `BesselJ[n,v]`,
`Mod`); and the array→scalar reductions `Total[v]` and `Length[v]`, which let
whole expressions such as `Total[(v - Total[v]/Length[v])^2]/Length[v]` compile
end to end. Real and complex (`complex64`) element types both work.

**New C entry point.** `ndred_total_all(a)` in `ndreduce.h` — full reduction of
an NDArray to a scalar, taking the *array* rather than the enclosing call, so a
caller that already holds the operand needs no wrapper call node. Shares
`ndred_total`'s summation, so the rounding is identical.

**Correctness contract**, lifted unchanged from the scalar engine: a program that
promised a real element type but whose buffer would leave the real axis (e.g.
`Sqrt[v]` with a negative entry, which the ND layer promotes to a complex dtype)
fails the call, and the caller falls back to the interpreter — it never returns a
wrong-typed result. Shape mismatches, allocation failures, and kernels that
decline an element fail the same way.

**Lifetime.** Array registers live in their own contiguous bank above the scalar
registers, so a slot is either always-array or never-array and teardown cannot
mistake a `double` for a pointer. Operand frees are encoded in the consuming
instruction's flag bits (which occupy what was padding — `Instr` did not grow),
so they happen *after* the operand is read and the result may still reuse an
operand's register. Every array register is NULLed before a call (the frame is
reused across calls) and swept afterwards, including on the abort path.

**Not yet in the subset** (each bails cleanly to the interpreter rather than
aliasing a handle): array-valued `If` branches, `With`/`Module` locals, `Sum`
accumulators and `Nest` state — all of which would need to *copy* an array
handle where the engine only moves one — a bare array argument as the whole
result, and rank ≥ 2. The user-facing `Compile[]` argspec has no array form yet,
so this is reachable from C (`compile_expr` with a `CT_ARRAY(...)` argument
type), not yet from the REPL.

**Measured.** Parity with the interpreter is *exact* (max relative error 0.0)
across 34 array bodies, because both paths run the same ND kernels. The speedup
is therefore only the per-operation evaluator round-trip that the compiled
program avoids: **2.3× at length 16, 1.0× at length 4096** for
`Total[Sin[v] Exp[-v] + Sqrt[v]]`. Large-vector gains need loop *fusion* (one
buffer pass for a chain of elementwise ops instead of one per operation), which
is M3b work, not delegation.

Tests: `tests/test_compile.c` — 34 parity bodies (real + complex vectors),
7 must-bail cases, the real-element runtime contract, 5000-call frame reuse, an
array temporary freed per iteration inside a `Do` loop, and the two performance
points. `leaks`-clean and ASan-clean.

## Compile engine — counted iterators, global folding, callee inlining

Four fixes to the compiled fast path, found by profiling a Newton-fractal
benchmark that ran an order of magnitude slower than expected.

**`Do` accepted only `{i, lo, hi}`.** Every other counted spelling the
interpreter supports made the *whole* surrounding `Compile[]` bail, so the body
ran in the interpreter — a silent 37× cost, not a small one. `Do`, `Sum` and
`Product` now share one spec parser matching `src/iter.c`:

| spec | meaning |
|------|---------|
| `n`, `{n}` | repeat n times, binding no iterator symbol (`Do` only) |
| `{i, hi}` | `i = 1, …, hi` |
| `{i, lo, hi}` | `i = lo, …, hi` |
| `{i, lo, hi, di}` | step `di`, a nonzero integer literal (loop test flips for `di < 0`) |

`Sum`/`Product` deliberately reject the bare-count forms because the interpreter
does (`sum.c`, `product.c`); the compiled path must not answer where the
interpreter declines. List iteration and non-literal steps bail as before.

**Nested `Table` could not compile its inner body.** `Table[f, {y,…}, {x,…}]`
desugars to nested `Table`s, and the inner one sees `y` only as a symbol-table
OwnValue, which made it an uncompilable free symbol. `compile_expr_ex` gained
`COMPILE_FOLD_GLOBALS`, resolving such a symbol to the machine number it
currently holds. It is opt-in and used *only* by `autocompile.c`, whose programs
live and die inside one builtin call; a user `Compile[]` object outlives its
defining scope, so it keeps bailing, which stays correct however the global is
later reassigned. Any body that could *mutate* a global mid-iteration (a `Set`
to a non-local) already bails, so a folded constant can never go stale.

**`Table` element types.** The compiled path routed every result through a
`double`, so an integer-valued body (`If[…, 1, 2]`, `Round[x]`) came back as
`1.` instead of `1`. New `autocompiled_eval_boxed` returns an Expr of the
result's own type; `Table` uses it. `Plot`/`NIntegrate`/`FindRoot` keep the
unboxed real path.

**Calling a `CompiledFunction` from a compiled body** previously bailed, costing
an evaluator round-trip per point (~2.3 µs of a 3.1 µs call — 72% of runtime).
The compiler now inlines the callee: arguments are lowered in the caller's
environment and coerced to the declared parameter types, then the body is
lowered with *only* the parameters in scope, so a caller argument sharing a name
with a callee global cannot capture it. Arity mismatch, array-typed parameters
and self-reference (depth-capped) all bail to the interpreter.

Measured on `Table[newt[x + I y, 25], {y,-1,1,2./199}, {x,-1,1,2./199}]`
(200 × 200 × 25 complex Newton steps): **4.45 s → 0.046 s (97×)**. The same
expression written inline without `Compile[]` now also fully compiles, at
0.042 s, and the two agree exactly.

`While` and `For` bodies go through the same paths and were verified alongside
`Do` — wrapped in `Compile[]`, inline in an auto-compiled `Table`, and as an
inlined callee — with identical results and timings.

Tests: `tests/test_compile.c` — 9 iterator spellings, exact integer counts, the
two must-bail forms, and a **multi-statement loop body** (four locals of three
types, five statements per iteration, a two-armed `If` mutating state in both
arms) written as `Do`/`While`/`For`: the three must agree *bitwise* with each
other and match an independent C reference (200 random points, max rel err
9.2e-15). `tests/test_autocompile.c` — result-type preservation, nested-`Table`
folding, fold freshness and the mutating-body fallback, 8 inlining cases each
checked against an interpreted twin (a DownValue never compiles, so a capture
bug shows up as a mismatch), and the same multi-statement body driven through
`Table` all three ways plus as an inlined callee.

One test deserves note: `test_multiline_bodies_really_compile` asserts, via the
same `autocompile_new` the builtin uses, that each loop body *actually compiles*.
Every parity check would otherwise pass vacuously if nothing compiled — agreement
with the interpreter is trivially true when you are the interpreter. Verified by
sabotage: disabling `COMPILE_FOLD_GLOBALS` leaves the three-way parity assertions
green (all three fall back and agree with each other) while this guard fails with
`multi-line Do body did not compile`. It runs first, before the behavioural
tests. `leaks`-clean.

## `Compile[]` M5 — optimising code generation, coverage audit, any-rank arrays

Four separable pieces of work on the numeric compiler (`src/compile/`).

> **Read the M5b section below before quoting any number here.** These were
> measured in a `tests/` build that had no `CMAKE_BUILD_TYPE` and so compiled at
> `-O0`. The ratios hold (both sides were built identically); the absolute
> figures were inflated. At `-O3` the dispatch-bound Horner baseline is
> **295 ns/call for 80 arithmetic operations (3.7 ns/op)**, and the work below
> takes it to **~200 ns/call (2.5 ns/op), ~1.45×** — not the 2.0× the `-O0`
> numbers suggested.

### Lazy operand addressing in the VM

`NEXT()` recomputed all three operand pointers for every instruction regardless
of which the opcode used — the hottest ops (`ADD_R`, `MUL_R`) read two and the
unary ops read one, so most of that work was wasted on the common case. Operands
are now addressed at the point of use, letting the C compiler fold the address
computation into the load.

**649 → 427 ns/call (1.53×)** on Horner *at `-O0`*; at `-O3` the same change is
worth appreciably less, because the C compiler was already folding some of that
address arithmetic. No behavioural change.

### A bytecode optimiser (`src/compile/optimize.c`, new)

The emitter lowers each `Expr` node independently and previously had **no middle
end at all** — no constant folding, no dead-code elimination, no loop-invariant
hoisting. There is now a pass pipeline between emission and the finished program:

- `compile_internal.h` extracts `Slot`/`Instr`/the opcode enum so the optimiser
  is its own translation unit. `OPLIST` now carries a KIND per opcode and drives
  three things that could previously drift apart: the opcode enum, the VM's
  computed-goto jump table, and the optimiser's instruction-property table.
- CFG construction and real backward liveness, then per-block value numbering
  (constant folding, CSE, copy propagation), liveness-driven dead-code
  elimination, and loop-invariant code motion over natural loops.
- Array registers and the impure array opcodes are excluded throughout: their
  ownership lives in instruction flags, not in the dataflow the scalar passes
  reason about.
- `OP_LOOP` folds increment, test and branch into one instruction — a counted
  loop otherwise spends four instructions per iteration on control alone.

Horner **427 → 335 ns/call** at `-O0`. Measured properly at `-O3`, the optimiser
alone is worth **1.33×** on Horner, **1.29×** on `Nest` and **1.25×** on
Newton/`While` (LICM), and the whole of M5 takes the dispatch-bound body from
**295 → ~200 ns/call (~1.45×)**.

`COMPILE_NO_OPT` is the A/B switch. The correctness gate is **bitwise identity**,
not accuracy: 18 bodies compiled both ways must agree bit for bit over a
randomised sweep (compared with `memcmp`, so `NaN` must equal `NaN` and `-0.0`
must differ from `+0.0`). A pass that reassociated a sum or contracted a
multiply-add would still look accurate while breaking the engine's stated parity
contract with the interpreter.

### `NDArray` of any rank

The delegated NDArray path was already rank-general; the compiler's own
front-door gate rejecting rank ≠ 1 was the only thing keeping matrices and higher
tensors out. With it lifted, elementwise bodies compile at **rank 2, 3 and 4**
with exact parity (max relative error 0.0 — both paths call the same kernels).
`Total` deliberately stays rank-1: at rank ≥ 2 it reduces only the *leading*
axis, which is a different operation.

### Elementwise fusion — implemented, correct, and off by default

`COMPILE_FUSE` lowers an elementwise chain to **one** counted loop over the flat
index, whose body is ordinary scalar bytecode reading through `A_LOAD` and
writing through `A_STORE`, instead of one full-length NDArray pass and one
temporary buffer per operation. Lowering it that way makes it rank-agnostic (a
flat index never looks at the shape), lets a trailing `Total` fold into an
accumulator in the same pass, and puts the scalar optimiser — including LICM —
inside the loop. Fusability is not analysed up front: the body is lowered
speculatively with array leaves bound to element registers and rolled back if the
ordinary scalar emitter cannot do it, so the fusable set is by construction
exactly the scalar-compilable set.

It is **off by default because it is not yet faster**: the loop runs the scalar
VM once per element, and at ~4 ns per bytecode instruction that costs more than
the temporary buffers it saves — 70 ns/element fused against 61 delegated for
`Total[Sin[v] Exp[-v] + Sqrt[v]]` at length 65536. The next step is block
strip-mining (each opcode processing a tile of ~64 elements in a vectorisable C
loop, so dispatch amortises 64× and temporaries stay in L1); the lowering here is
its foundation. Parity-tested at every rank, real and complex.

**A correctness rule this turned up:** fusion may only thread where the
interpreter threads, i.e. where the head is `Listable`. `Max[v, w]` is the trap —
it is *not* Listable, so the interpreter returns the single largest element and an
elementwise loop would quietly answer something else. `If`, `With` and `Sum` are
the same story.

### `NumericFunction` coverage is now audited by the build

When `compile_expr` cannot handle a head it returns `NULL`, the caller quietly
interprets, and the result is still correct — just an order of magnitude slower.
A coverage gap is therefore invisible: it looks exactly like a working fast path.

`tests/test_compile_coverage.c` enumerates every symbol carrying
`NumericFunction` and probes it by actually compiling `Head[x]` (and the 2- and
3-argument forms). `KNOWN_GAPS` lists the heads that legitimately do not compile
yet, each with its reason, and the audit fails in **both** directions: a head
outside the list that stops compiling is a regression, and a head inside it that
starts compiling means the list is stale.

Current state: **103 `NumericFunction` heads, 55 compile, 48 known gaps.** Most
remaining gaps are modules that compute in MPFR at ≥ 53 bits and round at the end
(`Zeta`, `PolyLog`, `Airy*`, `ExpIntegralEi`, …), so closing them means writing
genuinely new double-precision implementations rather than lifting an existing
path.

Running the audit immediately found three heads bailing even though the
interpreter evaluates them — each costing the whole surrounding body:

| Head | Was | Now |
|---|---|---|
| `Mod[x, y]` real | required two integers | uses the registered machine kernel (`Mod[2.5, 1.2]` → `0.1`) |
| `Quotient[x, y]` real | required two integers | `Floor[a/b]`, keeping the interpreter's *integer* result |
| `Arg[x]` real | deliberate "require complex" bail | widened to complex, reusing `ARG_C` (`0` for `x > 0`, `Pi` for `x < 0`) |

Each was checked against the interpreter before being added, so the compiled path
still never answers where the interpreter declines; all six new parity tests
agree to 0.0 relative error over 200–300 randomised trials.

### Call boundary

`cf[x]` no longer does a `malloc`/`free` per call for argument boxing (small
arities use stack storage), and an all-`Real` signature now takes the unboxed
`compiled_eval_real` entry point instead of always going through `CompileValue`.

### Tests

`tests/bench_compile.c` (new) is a performance gate whose primary assertion is
that **every benchmarked body actually compiled**, plus a machine-independent
ratio check that the optimiser never makes a body slower.
`tests/test_compile_coverage.c` (new) is the coverage audit.
`tests/test_compile.c` gains the optimiser A/B gate, any-rank parity, opt-in
fusion parity, and the `Listable` bail checks. All compile, CompiledFunction,
autocompile, NDSolve, NIntegrate, FindRoot and NDArray suites pass unchanged.

## `Compile[]` M5b — strip-mined array fusion (now on by default)

### Measurement correction, first

The `tests/` CMake build had no `CMAKE_BUILD_TYPE`, so it compiled with **no
optimisation flags at all**. Every absolute figure recorded in the M5 section
above came from `-O0` code. The build is now `Release`, and the *ratios* in that
section still hold (both sides were built identically) but the absolute numbers
were inflated — the dispatch-bound Horner body is **206 ns/call at `-O3`**, not
335.

### Strip mining

Fusion previously ran the scalar VM once per element, which cost more than the
temporary buffers it saved, so it shipped disabled. Each opcode now processes a
**tile of `VBLOCK` = 64 elements** in a loop shaped so the C compiler can
vectorise it: dispatch is amortised 64-fold, and every temporary is a 512-byte
tile that stays in L1 instead of a full-length heap buffer that page-faults.

At `-O3`, length 65536, fused against the delegated NDArray path:

| body | ns/element | speedup |
|---|---|---|
| `v^2 + 2 v + 1` | 2.3 | **3.4×** |
| `Total[v^2 + 2 v + 1]` | 2.8 | **3.0×** |
| `Total[v + v v]` | 1.7 | **2.4×** |
| `Total[Sin[v] Exp[-v] + Sqrt[v]]` | 12.9 | **1.9×** (libm-bound) |

Fusion is therefore **on by default**; `COMPILE_NO_FUSE` turns it off for A/B.

The lowering deliberately reuses the ordinary emitter rather than adding a second
one: tile-ness rides on the register number (the virtual-bank trick M3a already
used for array handles), and the four existing choke points — `binop`, `unop`,
`kern_unop`, `kern_binop` — swap in the tile form of whatever opcode the scalar
lowering picked. The vectorisable set is one table, not a parallel emitter that
could drift.

### Five latent type-inference bugs this exposed

`infer_type` dropped array-ness in five places: the unary math heads, two-argument
`Log`, one- and two-argument `ArcTan`, `Power` with a literal exponent, and the
binary-kernel path. Each computed the correct *element* type and then returned it
as a scalar. That was harmless while every array operation was delegated to the
ND layer — which chooses its own result dtype — and became two distinct faults as
soon as fusion started trusting these types: the wrong output buffer, and whole
bodies never being recognised as fusable at all. Fixing them is what took
`Total[Sin[v] Exp[-v] + Sqrt[v]]` from 1.0× (silently still delegated) to 1.9×.

### Three further correctness fixes

- **`Power` with an integer exponent** emits `POWI` directly rather than through
  `unop()`, so that site had to make the tile decision itself — otherwise a
  strip-mined `v^3` read the tile *pointer* as a double. A safety net in `ins_f`
  now turns any scalar opcode handed a tile register into a clean bail instead of
  a wrong answer.
- **A complex-to-real tile op** (`Abs`, `Re`, `Im`, `Arg`) may not write into its
  operand's register: it reads through `double _Complex*` and writes through
  `double*`, so the compiler is entitled to assume the two cannot overlap.
  Element-at-a-time the overlap is benign — which is exactly what makes it a bug
  that appears only once the loop vectorises.
- **The fused store honours the element-type promise.** A real-typed program that
  produced a non-finite element is precisely where the interpreter would have
  gone complex, so the call fails to the interpreter rather than handing back a
  real array full of `NaN`. The check is accumulated branchlessly and tested once
  per tile, so it does not break vectorisation.

### One place fusion had to be made *less* capable

The interpreter leaves `ArcTan[NDArray, NDArray]` **completely unevaluated** — the
ND binary kernels are defined as one array plus one broadcast scalar, so there is
no array-by-array path. A fused loop would happily compute it. Answering where
the interpreter declines is the same class of bug as answering differently, so
`fuse_listable` refuses a two-argument node with a registered binary kernel when
both operands are arrays. `Log[b, x]` is the documented exception, and not an
arbitrary one: it lowers to the arithmetic identity `Log[x]/Log[b]`, so the
interpreter threads it array-by-array too.

### Tests

- **340 body × length combinations** across lengths straddling the tile boundary
  (1, 2, 3, 7, 31, 63, 64, 65, 66, 127, 128, 129, 255, 256, 257, 1000, 4097). The
  partial final tile is the one thing a length-64 test can never reach.
- **21 bodies** checked fused against delegated.
- **120 randomised elementwise trees** — Listable heads only, each guaranteed to
  reach an array leaf, since a body of pure scalars is not an array program and a
  bare argument array cannot legally be the result.
- **200 repeated calls** at varying lengths: the frame and tile bank are reused
  across calls, so a stale tile would only ever show up on the second one.
- `compile_tests` is `leaks`-clean and **ASan + UBSan clean**.

## `Compile[]` M5c — CSE, per-call frames, and compiled-to-compiled calls

### CSE, moved to the Expr level

The bytecode optimiser has had a value-numbering CSE since M5 and it **almost
never fired**. The reason was structural rather than a bug in the pass:
`binop`/`unop` pop their operands *before* allocating the destination, so a
computation normally writes into one of its own operand registers (`SIN_R t1, t1`).
The value-number entry keyed on that register is invalidated by the very
instruction that created it, and the value is genuinely gone — no bytecode-level
pass can recover it without first changing how registers are allocated.

Doing it on the `Expr` sidesteps that, and is where the information is richest
anyway. A chosen subtree is computed **once** into a register reserved *below*
the temp stack (by raising `nlocals`) — the same discipline that already protects
arguments, so neither temp allocation nor any of the explicit `temp_top` resets
in the loop lowerings can reach it. Occurrences are keyed on the `Expr` pointer,
because the planner walks the very tree the emitter will walk.

`Sin[x y] + Cos[x y] Sin[x y] + Sin[x y]^3`: 13 → 10 instructions,
**37.0 → 25.0 ns/call (1.48×)**. Both `x y` and `Sin[x y]` are hoisted;
candidates are emitted smallest-first, so the larger picks up the smaller's
register rather than recomputing it.

Eligibility is deliberately narrow, and every clause earns its place:

- **every free symbol must be an argument.** A subtree mentioning a loop variable
  or a `With`/`Module` local cannot be hoisted to program entry, where that name
  is not bound yet. Loop-*invariant* hoisting is a different job, and the
  optimiser's LICM pass already does it.
- **no control flow and no assignment** anywhere inside, so evaluating it early
  and unconditionally is observationally identical.
- **scalar-typed only**: an array value carries ownership, and a tile belongs to
  the fused loop that created it.

`COMPILE_NO_CSE` is the A/B switch, and the bitwise-identity harness now runs its
whole corpus once per pass — **50 body/pass combinations** must agree bit for bit
with and without each of CSE and the optimiser.

### Frames come from the C stack

The frame used to be a single buffer owned by the `CompiledProgram` and mutated
through a `const CompiledProgram*`: a program was neither reentrant nor
thread-safe, because two live calls shared one register file and (after M5b) one
set of tile buffers. A C-stack frame is per-thread and naturally nested, so both
properties fall out with no arena to own, grow or free — and with no allocation
at all for any program fitting the fixed 512-slot buffer, which is every
realistic one. Tile storage moved into the frame for the same reason.

### `OP_CALL`

A compiled callee that is not inlined is now **called**: machine values in
consecutive registers, its own frame, no `Expr` and no evaluator round-trip.
Previously inlining was the only mechanism, and where the inliner declined — its
depth cap, the scope budget — the *whole body* bailed to the interpreter.

Inlining remains the default, being the faster of the two (no frame, no argument
copy). The choice is now a cost model: a callee larger than `INLINE_MAX_INSTRS`
is called instead, because past that size pasting it in at every use site costs
more in code size and compile time than the call costs at run time.

**Precisely what this does not do:** it does not make a *self*-recursive
`Compile[]` compile. `Compile[]` does not fold globals — by design, since the
object outlives its defining scope — so a body cannot resolve the very symbol it
is about to be assigned to. What `OP_CALL` fixes is deep and awkward call shapes
bailing wholesale.

### A real optimiser bug this exposed

In the value-numbering pass, an instruction writing register `d` cleared every
alias *pointing at* `d` but not `d`'s own stale alias. So `MOVE d <- a` followed
by anything that writes `d` left `alias[d]` still pointing at `a`, and a later
read of `d` was copy-propagated back to `a` — the value from *before* the write.
Every other opcode happened to re-establish `alias[d]` immediately afterwards; a
`CALL`, which writes `d` without being a `MOVE`, is what made it visible.

### Tests

Eleven nested applications of a compiled callee, checked against an interpreted
`DownValue` twin (which never compiles, and is therefore an honest reference) —
max relative error 2e-16 over 100 points. The same chain inside a `Do` loop,
where the caller's frame is live across every re-entry: the test the old
per-program frame could not have passed. `compile_tests` is `leaks`-clean and
ASan + UBSan clean.

Two *test-harness* bugs were found and fixed on the way, both of which had made
the new tests report failures that were not in the engine: a `snprintf` with a
`%.17g` format and no argument; and, once that was fixed, the fact that a
17-digit literal is read by Mathilda as an **arbitrary-precision** number, so the
reference computed in MPFR and came back as `EXPR_MPFR` rather than a machine
`Real`. References are now built by substitution rather than by formatting a
literal — the same lesson the array tests already encode.

## `Compile[]` M5d — array argspec, and a Plot3D leak

### `Compile[{{v, _Real, r}}, …]`

Until now the whole array engine — fusion, any-rank, the reductions — was
reachable only from C: `Compile[]`'s argspec parser accepted `_Real`, `_Integer`
and `_Complex` but had no rank, so an array parameter could not be declared at
all. It now takes the three-element form the Wolfram Language uses, with the
element type restricted to `Real` or `Complex` (the packed buffer formats are
float and complex only — there is no integer dtype to hold a rank-*r* Integer
array), and rank bounded by `CT_MAX_RANK`.

```
f = Compile[{{v, _Real, 1}}, v^2 + 2 v + 1];   f[{1., 2., 3.}]   → {4., 9., 16.}
g = Compile[{{m, _Real, 2}}, Sin[m] + 1];      g[{{0., 1.}}]     → {{1., 1.84147}}
h = Compile[{{v, _Real, 1}}, Total[v^2]];      h[{1., 2., 3.}]   → 14.
```

A plain nested `List` argument is packed into an `NDArray` at the boundary and
that temporary is released after the call; an `NDArray` passed in directly is
**borrowed** and left alone.

**The result kind follows the argument kind.** Given `List`s the function returns
a `List`; given `NDArray`s it returns an `NDArray`. This is not cosmetic: the
interpreter fallback threads a `List` argument and returns a `List`, so returning
a packed array would mean the compiled path answering with a *different head*
from the fallback for the very same input — visible to the user the moment one
element is symbolic and the fast path declines.

Shapes that must not take the fast path all fall back and stay correct: a ragged
list (cannot be packed), a rank mismatch, and a symbolic element. Malformed
argspecs (`{v, _Real, 0.5}`, `{v, _Integer, 2}`) leave `Compile[…]` unevaluated
rather than guessing.

### Plot3D: primitives leaked on the no-surface path

`build_surface_primitives` returns `NULL` when no cell was filled, and freed the
primitive *array* without freeing the `Expr`s in it. `any` is set only by the
polygon-fill passes, but the per-surface colour directive, the mesh lines and the
`ExclusionStyle` edges are all pushed independently of it — so a plot producing
those but no filled cell (every cell clipped away by `RegionFunction`, or every
sample excluded) leaked every primitive it had built.

Found while auditing the compiler work for leaks: `autocompile_tests` reported
one more leaked node than the pre-change baseline, which turned out to be this
path being reached slightly differently rather than anything the compiler did.

### Machine kernels for the exponential-integral family

Nine more `NumericFunction` heads now compile — **coverage 55 → 64 of 103**.

`ExpIntegralEi`, `LogIntegral`, `SinIntegral`, `CosIntegral`, `SinhIntegral`,
`CoshIntegral` and `Sinc` had no double-precision path at all: their modules
compute in MPFR and round at the end, which is right for arbitrary-precision work
but left the NDArray element-wise fast path and the `Compile[]` VM stuck on a
degrade sentinel — and in the compiler's case that meant the *whole surrounding
body* fell back to the interpreter. `src/special_functions/expint_machine.c`
provides real double implementations (series where they are well conditioned,
modified-Lentz continued fractions and asymptotic forms beyond).

`InverseErf` and `InverseErfc` were free: `inverf.c`/`inverfc.c` already
contained pure double algorithms that were simply never exposed or registered.

Every one is registered real-closed with a `real` function only, and **declines**
for an argument whose true value is complex or infinite — `Ci`, `Chi` and `li` of
a negative argument, `Ei` at zero, `li` at one, `InverseErf` at ±1. That is the
engine's standing contract: a real-typed fast path gives way exactly where the
interpreter would leave the real axis. It works end to end —
`CosIntegral[NDArray[{-1., 2.}]]` degrades to the List path and returns the
complex value, rather than the array path inventing a real one.

Accuracy is verified against each module's own MPFR implementation, not asserted:
max relative error ≤ 1.7e-15 (a few ulps) over 300–400 randomised points per
function, plus a chained body and twelve out-of-domain arguments that must all
decline.

One subtlety worth recording: `li(0)` is 0 by the limit, but the interpreter
answers `Indeterminate`, so the machine kernel declines there too rather than
being the only path that produces a number.

### More machine kernels — coverage 64 → 77 of 103

`src/expint_machine.*` grew into `src/special_functions/sf_machine.*` and gained
double implementations for **Erfi** (all-positive Maclaurin series, so no
cancellation, with an asymptotic tail), **ProductLog** (Halley), **FresnelC** /
**FresnelS**, **PolyGamma** (digamma by recurrence + asymptotic, reflection below
zero), **HarmonicNumber**, **Zeta** (Euler–Maclaurin above the critical strip,
the functional equation below), **HurwitzZeta**, and the real continuations of
**Fibonacci** and **LucasL** — all matching their MPFR implementations to machine
precision over 200–400 randomised points each.

`PolyGamma` had to be a **binary** kernel even though it is usually written
unary: the evaluator canonicalises `PolyGamma[x]` to `PolyGamma[0, x]` before
anything downstream sees it. `psi^(n)` for `n >= 1` comes from
`(-1)^(n+1) n! zeta(n+1, x)`, which is why `HurwitzZeta` came along for free.

**`UnitStep`, `Clip` and `Rescale` are lowered by hand rather than registered**,
because for these the *result type* is the whole difficulty:

- `UnitStep[0.5]` is the Integer `1`, not `1.` — a real-valued kernel would
  answer with a different head from the interpreter. A comparison already leaves
  0/1 in the integer half of the slot, so the lowering is the comparison, typed
  `CT_INT`.
- `Clip` and `Rescale` take a *list* of bounds, which no kernel signature can
  express; a literal two-element `List` is destructured in the lowering. Both are
  gated on the bounds being Real, because with exact bounds the interpreter
  returns an exact value where it clips (`Clip[5, {1, 3}]` is the Integer 3) and
  a Real where it does not — no single compiled type matches that.

### Two bugs found by the new parity tests

**`ProductLog` was wrong on `[0.35, 1/e]`.** The seed-selection thresholds left a
gap: the Maclaurin seed covered `|z| < 0.35` and the next one only applies once
`|log z| < 1`, i.e. `|z| > 1/e = 0.3678…`. Arguments in between fell through to
the *asymptotic* seed `L1 - log L1`, and with `log z` negative there `log(log z)`
is complex, so the iteration converged to something that is not a Lambert W value
at all — `ProductLog[0.35]` returned `-2.6422`, whose `w e^w` is `-0.188`, not
`0.35`. The bound is now 0.5, leaving margin on both sides. This is an
interpreter bug, not a compiler one; the compiled path disagreeing with it is
what surfaced it.

**Two tests used `Zeta` as their example of an uncompilable head** — in
`test_compile.c` and `test_ndsolve_compile.c`. Now that `Zeta` compiles they
failed, which is the coverage ratchet working: an assumption written into a test
in 2026-07 stopped being true and said so.

### Pochhammer, Binomial, LegendreP — coverage 77 → 80 of 103

`Pochhammer[a, n]` = `Gamma(a+n)/Gamma(a)` (an exact product for small
non-negative integer `n`, otherwise through `lgamma`), `Binomial[n, k]` through
the same route, and `LegendreP[n, x]` by the three-term recurrence for
non-negative integer degree — a non-integer degree needs the hypergeometric form
and is left to the MPFR path, matching how `BesselJ`/`BesselY` already decline a
non-integer order.

`Binomial` had been classified as "exact integer semantics, not a machine
function", which was wrong: the interpreter evaluates it for real arguments
(`Binomial[5.5, 2.]` is `12.375`) and returns a Real for Real arguments, so a
machine kernel answers the same question rather than a different one.
`FactorialPower` moves the other way — the interpreter leaves
`FactorialPower[5.5, 2.]` *unevaluated*, so it is now recorded as a deliberate
exclusion rather than a pending kernel, alongside `Factorial2`.

**A portability catch worth recording:** the first draft used `lgamma_r` to get
the sign of Gamma alongside its log. That is POSIX, not C99 — the main build
accepted it because macOS headers expose it, and the test build did not. The sign
is now computed directly from the parity of `floor(x)` (Gamma alternates sign on
the negative axis), which also avoids the non-thread-safe global `signgam`.

### Airy — coverage 80 → 84 of 103, and a band deliberately left to MPFR

`AiryAi`, `AiryBi`, `AiryAiPrime` and `AiryBiPrime` come from one implementation:
the ascending series generated by the recurrence `c_{n+3} = c_n/((n+3)(n+2))`
that `y'' = x y` gives directly, and the standard asymptotic expansions beyond.

**The two expansions do not meet in double precision, and that is a property of
the functions rather than of the code.** The series computes a decaying `Ai` as a
difference of growing terms and loses about `2ζ/ln 10` digits; the asymptotic
series has a smallest attainable error of order `e^(-2ζ)`. Measured against the
MPFR implementation:

| region | best relative error |
|---|---|
| series, \|x\| ≤ 2.5 | ~1e-15 |
| series, \|x\| = 3 | 3e-13 |
| asymptotic, \|x\| = 3.5 | **1e-5** |
| asymptotic, \|x\| = 6 | 2e-10 |
| asymptotic, \|x\| ≥ 8 | ~1e-15 |

So the kernel covers `|x| ≤ 2.5` and `|x| ≥ 8` and **declines the band between**,
where the MPFR path answers. Covering it properly needs a third method
(Chebyshev fits, or the modified-Bessel route). Shipping a fast path that is
quietly wrong to five digits would be far worse than being slower over one
interval — and the decline is the same mechanism the engine already uses
wherever a real fast path cannot answer.

This also caught the bail tests a third time: `Zeta`, then `AiryAi`, were each in
turn the example of "a head with no machine kernel", and each in turn started
compiling. The audit exists so that stops being a silent assumption.

**Coverage now 84 of 103 (82%), from 55 at the start of this work.** The 19
remaining are 12 pending numerics (`PolyLog`, `LerchPhi`, `BesselI`/`K`/`JZero`,
`BarnesG`, `Hyperfactorial`, `QPochhammer`, the four hypergeometrics) and 7
deliberate exclusions — `Factorial2` and `FactorialPower`, which the interpreter
leaves unevaluated on reals, and `GCD`, `LCM`, `DigitSum`, `ReIm` and
`QuotientRemainder`, whose semantics are exact-integer or not a single machine
number.

### The last 12 numerics — coverage 84 → 93 of 103, and an interpreter bug found on the way

`PolyLog`, `LerchPhi`, `QPochhammer`, `BesselI`, `BesselK` and the four
hypergeometrics (`Hypergeometric0F1`, `1F1`, `2F1`, `HypergeometricPFQ`) now have
real double kernels in `src/special_functions/sf_machine.c`. That closes every
gap in the coverage audit that was pending work rather than a deliberate
exclusion.

`sf_machine_pfq` is the single implementation; `sf_machine_hyper0f1/1f1/2f1` are
thin wrappers over it. Two implementations of the same series is how a fix to one
silently misses the other — and `Hypergeometric1F1` canonicalises to
`HypergeometricPFQ` before the evaluator ever sees it, so the pFq form is the one
that actually runs.

`HypergeometricPFQ` was also listed as an uncovered head when it was not: the
audit probes each head with `Head[x]` … `Head[x,y,z,w]`, and pFq's real signature
is *two lists and a scalar*. It joins `Clip` and `Rescale` in the `PROBES` table
of shape overrides. A coverage audit that measures the wrong signature reports a
gap that is really a defect in the probe.

**The parity test then failed — and it was the interpreter that was wrong.**
`Hypergeometric1F1[1., 2., -40.]` has the closed form `(e^z - 1)/z`, against
which:

| z | interpreter (before) | compiled kernel |
|---|---|---|
| -40 | **5.3e-2** | 1.7e-17 |
| -37 | 5.0e-4 | 2.4e-17 |
| -30 | 1.6e-6 | 0.0 |
| -20 | 2.6e-10 | 4.0e-17 |
| -10 | 1.9e-14 | 3.8e-17 |

`machine_sum` in `hypergeopfq.c` summed the series in plain doubles. For negative
real `z` that series alternates, and its largest term exceeds the value it sums to
by a factor of order `e^|z|` — at `z = -40` that is 2e17, so every bit of the
answer had already cancelled away before the loop finished. Summing more terms
cannot recover them.

The fix measures the loss instead of guessing it: `machine_sum` tracks
`max|term| / |sum|` and reports `log2` of it, and the dispatcher re-sums through
the existing MPFR path at `53 + lost + 16` bits when that exceeds 4, rounding
back to a machine number. Reporting the loss rather than estimating it from `|z|`
keeps the bound exact for every `p`, `q` and parameter set, including the many
where nothing cancels at all (all-positive terms give `lost = 0` and cost
nothing). Machine-precision arguments still give a machine-precision answer — but
now it is the correctly rounded one, so the *argument* precision decides the
output type rather than the conditioning of the series.

Errors at every `z` in the table above are now 0.0 or one ulp.

**Coverage 93 of 103 (90%).** The remaining 10 are all deliberate, and
`test_compile_coverage.c` now says so in its own header rather than describing
them as pending: `BesselJZero`, `BarnesG`, `Hyperfactorial`, `Factorial2` and
`FactorialPower`, which the *interpreter* leaves unevaluated on machine reals — a
kernel for those would make the compiled path answer where the interpreter
declines, the one divergence the engine forbids — and `GCD`, `LCM`, `DigitSum`,
`ReIm`, `QuotientRemainder`, whose semantics are exact-integer or not a single
machine number.

That structural half is also where the NDSolve bail test now takes its example.
`Zeta`, then `AiryAi`, then `PolyLog` were each used as "a head with no machine
kernel" and each in turn started compiling; `BarnesG` and `QuotientRemainder`
cannot move without breaking interpreter parity, so they will not.

### Threading the fused array loop — 3.2-6.6x at a million elements

A fused elementwise MAP is now split across cores. `OP_APAR` sits immediately
before the strip loop and either fans it out and jumps past it, or falls straight
through into exactly the serial loop that was always emitted there. Declining is
therefore free and always safe — the fallback is not a second implementation, it
is the same instructions.

Measured at 1M elements (16 cores, wall clock, minimum of repeated trials):

| body | serial | threaded | |
|---|---|---|---|
| `Sqrt[v] + v^2` | 2524 us | 782 us | **3.2x** |
| `Sin[v] Exp[-v] + Sqrt[v]` | 14376 us | 2611 us | **5.5x** |
| `Gamma[v] + Erf[v]` | 35900 us | 5479 us | **6.6x** |

Memory-bound bodies gain least, which is the expected shape: `Sqrt[v] + v^2`
reads and writes 16 MB for about three flops per element, so it saturates
bandwidth long before it saturates cores.

**Only maps, never reductions.** Each output element of a map is computed by the
same operations on the same inputs whichever core runs it, so the threaded and
single-threaded programs agree BITWISE — `COMPILE_NO_PAR` gives the A/B and a
test asserts `memcmp` equality over 20 runs at lengths straddling the fan-out
threshold. A reduction is a different matter: floating-point addition is not
associative, so per-thread partial sums would give a genuinely different answer
from the serial fold, and the engine's contract is to agree with the interpreter
rather than merely to come close. Reductions stay serial.

The mechanism is a lifted sub-program. Rather than teach `vm_run` to stop at an
arbitrary pc — a comparison on every dispatch, forever, for one loop — the loop's
instruction range is copied out at finalize time with its jump targets rebased
and its own `OP_RET` appended, so a worker calls the ordinary `vm_run` entry.
The VM's hot path is untouched. Extraction happens after the optimiser, which is
the only correct point: LICM and compaction both move instruction indices, so a
range recorded at emit time would name the wrong instructions by the time it was
used.

Workers are safe with no locking because each gets its own frame, seeded by
copying the parent's registers: scalars by value, array handles as borrowed
pointers (workers only read inputs and write disjoint output elements), and tile
registers re-pointed at the worker's own scratch. Nothing is allocated or freed
across a thread boundary. ThreadSanitizer reports no races; `leaks` reports zero.

#### Two measurement bugs found on the way, both of which had been hiding results

**`tests/CMakeLists.txt` never defined `MATHILDA_THREADS`.** The top-level
makefile always has. So every `nd_parallel_for` in the test build compiled down
to its serial fallback, and no test had ever executed the threaded ND path at
all — not for NDArray maps, not for reductions, not for anything. A guard that
cannot reach the code it guards is worse than no guard, because it reads as
covered. Now set via `find_package(Threads)`; the ND suites pass with it on.

**`bench_compile.c` timed with `clock()`.** That is CPU time summed over every
thread, so a region that scales *perfectly* reports as N times *slower*. The
first measurements of this work came back at 0.56-0.83x and looked like a real
regression; instrumenting the region directly showed it running 6.4x faster than
serial at the same moment the benchmark called it a loss. Every other
`tests/bench_*.c` already used `clock_gettime(CLOCK_MONOTONIC)` — this file was
the exception. Any benchmark a threaded path can reach must be wall-clock.

A pre-fault of the output buffer was added while chasing the wrong explanation
(concurrent first-touch page faults) and then removed once measured: it cost
about 5% rather than saving anything.

### Airy's uncovered band is closed — a third method, and the direction is the point

`2.5 < |x| < 8` used to decline: the ascending series computes a decaying `Ai` as
a difference of growing terms and loses about `2ζ/ln 10` digits, and the
asymptotic expansion has a floor of order `e^(-2ζ)` that only clears double
precision from `|x| ≥ 8`. Between them the best either could do was ~1e-5.

The band is now covered by **Taylor marching of the defining ODE**. About a point
`x0`, writing `y(x0 + h) = Σ c_k h^k` and matching `y'' = (x0 + h) y` term by term
gives

```
(k+2)(k+1) c_{k+2} = x0 c_k + c_{k-1},    c_{-1} = 0
```

with `c_0 = y(x0)`, `c_1 = y'(x0)`. Nothing is approximated: `Ai` and `Bi` are
entire, so this converges for every `h`, and a short step (0.25) converges in a
handful of terms. No fitted coefficients, no new special function, and the same
recurrence shape the ascending series already uses.

**Which direction to march is the whole problem, and getting it wrong is how this
method quietly loses digits.** `y'' = x y` has a recessive and a dominant
solution, and rounding error in the recessive one is amplified by the dominant
one's growth. For `x > 0`, `Bi` grows across the band by a factor of
`e^(ζ(8) − ζ(2.5)) ≈ 2.4e5` — so marching `Ai` forward from 2.5 would let a
1e-16 seed error reach ~1e-11. Each solution is therefore marched in the
direction in which it **dominates**:

| | seeded from | direction |
|---|---|---|
| `Bi`, `Bi'` (x > 0) | ascending series at `|x| = 2.5` | forward, growing |
| `Ai`, `Ai'` (x > 0) | asymptotic at `|x| = 8` | backward, growing as x falls |
| all four (x < 0) | ascending series at `x = −2.5` | one march; neither solution dominates in the oscillatory region |

Measured against the MPFR path over 300 points per function per sign:

| | former band | for comparison |
|---|---|---|
| `AiryAi` | 7.4e-17 / 7.2e-16 | 1.0e-15 in the series region |
| `AiryBi` | 2.6e-15 / 9.3e-16 | 2.9e-16 |
| `AiryAiPrime` | 1.4e-16 / 2.0e-15 | 1.1e-15 |
| `AiryBiPrime` | 2.6e-15 / 1.6e-15 | 5.0e-16 |

The band is now at least as accurate as the two regions that were already
accepted — in places better than the ascending series manages at `|x| = 2.5`.
Two further parity sweeps run across `[-12, 12]` so a discontinuity at either
seam would show. **No Airy argument on the real axis declines any more**, and the
four entries that asserted the decline are gone from the bail list.

### `NUMERIC_FUNCTION_MISSING.md` — and what it found

New top-level document enumerating every `ATTR_NUMERICFUNCTION` head that lacks a
machine fast path, generated from the build rather than hand-maintained
(`COVERAGE_REPORT=1 ./compile_coverage_tests` dumps the table).

Writing it turned up something the coverage audit had never been asked: it probes
with `_Real` arguments only.

| | of 103 |
|---|---|
| full fast path (real **and** complex) | 52 |
| real only — **complex bails** | 41 |
| no fast path at all | 10 |

**Complex arguments are now the single largest source of silent interpreter
fallback in the engine** — larger than every exotic function put together. The
cause is uniform: `sf_machine.c` kernels were registered with a `real` function

### Complex arguments: first three heads, and two result-HEAD bugs the work exposed

Acting on `NUMERIC_FUNCTION_MISSING.md`, the three complex cases that are cleanly
typed are closed: **`Sign`, `FractionalPart`, `Rescale`**. Complex coverage
52 → 55 of 103.

`Sign`'s complex kernel (`z/|z|`, 0 at the origin) had been in the registry the
whole time — the compiler's own inline lowering for `Sign` matched the head first
and bailed on a complex operand, so `try_kernel` was never consulted. A bespoke
lowering that shadows a registered kernel is a coverage gap that no amount of
kernel-writing fixes.

`FractionalPart` needed one componentwise function; `Rescale` is
`(x - lo)/(hi - lo)`, which carries a complex `x` through unchanged. **`Clip`
deliberately does not** — `Min`/`Max` need an order, and the interpreter leaves
`Clip[1. + I, {0., 2.}]` unevaluated, so the compiled path must too.

#### The other four are type-blocked, not mechanical

`Floor`, `Ceiling`, `Round` and `IntegerPart` on a complex return
`Complex[Integer, Integer]` — `Head /@ ReIm[Floor[1.5 + 2.5 I]]` is
`{Integer, Integer}`. The type lattice has `CT_INT` and `CT_COMPLEX` (a
`double _Complex`) but nothing for a complex *integer*, so answering with
`CT_COMPLEX` would give `Complex[Real, Real]` and differ from the interpreter in
head. They need a new type, not a new function pointer. The write-up originally
listed all seven as "cheap and mechanical"; checking result *types* rather than
values cut that to three.

#### `parity_head` — a test for the class of bug the value tests cannot see

The numeric parity tests compare values, and a value compares equal whether it
came back as the Integer `-1` or the Real `-1.`. But those are not
interchangeable downstream (`IntegerQ`, exact arithmetic, printing), so a
compiled path with the wrong result head is answering *differently* from the
interpreter. `parity_head` compares the compiled program's declared result type
against the head the interpreter produces, over every head whose result type
differs from its argument type.

It found two live divergences immediately:

- **`Sign[-2.5]`** is the Integer `-1` in the interpreter; the compiled path
  declared `CT_REAL` and answered `-1.`. `OP_SIGN_R` now writes the integer slot.
  (The tile form `VSIGN_R` stays real — it feeds packed float arrays, where a
  real dtype is the right answer.)
- **`IntegerPart[2.5]`** is the Integer `2`; the compiled path went through the
  registered kernel, which returns a double, and declared `CT_REAL`. It now has a
  bespoke lowering alongside `Floor`/`Ceiling`/`Round` via a new `OP_TRUNC_R` —
  truncation toward zero, which is *not* `Floor` for a negative argument
  (`IntegerPart[-1.5]` is `-1`, `Floor[-1.5]` is `-2`). The kernel stays for the
  array path.

This is the same failure mode `UnitStep` was given a bespoke lowering for, and it
had recurred twice since without being noticed.

### `Quotient` at complex argument was rounding, not flooring

`Quotient[m, n, d]` is `Floor[(m - d)/n]` by definition, and every branch of
`builtin_quotient` agreed except the complex one, which used `round`. So
`Quotient[5.5 + 1. I, 3.]` returned `2` while `Floor[(5.5 + 1. I)/3.]` returned
`1`, and the complex result disagreed with the real result for the same quotient.
Now floors, and matches `Floor[m/n]` at every argument tried including a Gaussian
divisor (`Quotient[10 + 2 I, 3 + I]` = `3 - I`).

### Dead degrade-sentinel scaffolding removed

`ndkernels.c` still carried the `ND_DEGRADE_U`/`ND_DEGRADE_B` descriptors and the
loops that registered them, but both name lists were empty — every head that once
needed a sentinel now has a real kernel. A zero-length array is not standard C99
and gcc was warning that the loop guard is always false. Removed, with a comment
recording how to register a sentinel if one is ever needed again: an explicit
"known, and deliberately has no fast path" reads differently from an absent
registry entry, and the coverage audit distinguishes them.

### Complex `Gamma` and `LogGamma` — and a branch-cut bug in both of the interpreter's own paths

`Gamma` and `LogGamma` now compile for `_Complex`. Coverage 55 → 57 of 103.

**No new numerics were written.** Both already had a `double complex` Lanczos
series inside the interpreter (`gamma.c:gamma_lanczos`,
`loggamma.c:lg_lanczos`); they are now exposed as `gamma_machine_complex` /
`loggamma_machine_complex` and registered as the `cplx` kernels. The compiled and
interpreted paths therefore agree *bit for bit* by construction — every new
parity test reports `max_rel = 0.0e+00` — and there is exactly one place where
the branch structure lives. (Worth checking for an existing implementation before
writing a kernel: `Sign`'s complex kernel was already present too.)

`Beta`, `Binomial`, `Pochhammer` and `Hypergeometric0F1` turned out to have
complex kernels already, so the expected knock-on did not need doing.

#### The reflection formula was using a principal log, in both paths

`LogGamma` is the *continued* log-gamma, not `Log[Gamma[z]]` — its imaginary part
grows without bound with `Im z`. For `Re(z) >= 1/2` both implementations get that
right by summing the log of each Lanczos factor. For `Re(z) < 1/2` both used the
reflection

```
LogGamma(z) = Log(pi / sin(pi z)) - LogGamma(1-z)
```

with a **principal** log. That is short by a multiple of `2 pi i` outside the
strip `-1 < Re(z) < 0`, so `LogGamma[-4.5 + 3 I]` came back exactly equal to
`Log[Gamma[-4.5 + 3 I]]` — not continued at all — while the `Re(z) >= 1/2` branch
and the real axis both gave the true continuation. The function was discontinuous
across its own reflection boundary, and the machine path disagreed with the MPFR
path by `2 pi i`.

The winding can be factored out analytically. From

```
sin(pi z) = e^(-i pi z) (e^(2 i pi z) - 1) / (2i)
```

the second factor stays near `-1` whenever `Im(z) > 0` (since
`|e^(2 i pi z)| = e^(-2 pi Im z) < 1`), so *its* principal log is safe, and the
entire winding sits in the `-i pi z` term where it is exact:

```
log sin(pi z) = -i pi z + Log((e^(2 i pi z) - 1) / (2i))
```

with the mirrored form below the real axis. At `Im(z) = 0` this is the limit from
above — which is the convention the real path already documented
(`Im = -Pi Ceiling[-z]`), so the two now agree where they meet. They did not
before: `LogGamma[-1.5]` gave `0.860047 - 2 pi I` while `LogGamma[-1.5 + eps I]`
gave `0.860047 + 0 I`.

Both implementations had the defect and both are fixed — the MPFR
(`lcx_loggamma`) one needs no complex `exp`, since the exponent is
`-2 pi y + 2 pi i x` and expands directly. The two now agree to display precision
at every point checked, including `Re(z) < -10`.

#### Why the pre-existing test never saw it

`test_loggamma_machine_complex` had one reflection assertion, at `Re = -0.5` —
inside the single strip where a principal log happens to be correct. It passed
throughout.

The new `test_loggamma_complex_branch` pins the branch by three properties rather
than by hand-copied constants (which would only restate whatever the code does):

1. `Exp[LogGamma[z]] == Gamma[z]`, at `Re(z)` well past the good strip. `Gamma`
   is single-valued and has its own separate Lanczos, so this catches everything
   except the winding number.
2. `Im -> 0+` equals the real-axis value, whose imaginary part is fixed
   independently by the documented `Im = -Pi Ceiling[-z]`. **This is what pins the
   winding.**
3. Machine and MPFR paths agree — two implementations that had the same defect
   and were fixed separately.

Reverting the machine-path fix makes it fail with
`Im[LogGamma[-1.5 + 1e-8 I]]: expected -6.28318530717959, got 7.03156640645245e-09`,
which is the bug exactly.

### The exponential-integral family at complex argument — 57 → 63 of 103

`ExpIntegralEi`, `LogIntegral`, `SinIntegral`, `CosIntegral`, `SinhIntegral` and
`CoshIntegral` now compile for `_Complex`.

**Again no new numerics.** Each module already had a `double complex` ascending
series — sitting behind `#ifndef USE_MPFR`, i.e. dead code in every normal build.
They are now compiled unconditionally, wrapped in the shared kernel ABI
(`expintegralei_machine_complex`, …) and registered. `LogIntegral` is
`Ei[Log z]` with a principal log, the same identity the symbolic path uses, so
`LogIntegral[-1.]` is complex (`Ei[i Pi]`) exactly as the interpreter returns it.

#### The work was a cancellation gate, and the budget was measured rather than chosen

These series converge everywhere but are only *usable* where the terms do not
dwarf the value they sum to — which stops being true well before `|z|` gets
large, and depends on the direction of `z`, not only its modulus. So the peak
term is tracked and compared against the result, the same measured-loss approach
the `HypergeometricPFQ` fix used.

The budget was then set from data, not from a guess. Compiled-vs-MPFR error over
a 63-point polar grid out to `|z| = 32`:

| budget | worst error | coverage |
|---|---|---|
| `1e9` (~30 bits) | **1.3e-08** | 63/63 |
| `1e4` (~13 bits) | 5.7e-13 | 59–63/63 |
| `1e3` (~10 bits) | **4.7e-14 – 4.2e-13** | 59–63/63 |

`1e3` is strictly better than `1e4` here — ten times the accuracy at the same
coverage — so that is the setting. The initial `1e9` would have shipped a fast
path wrong in the eighth digit, which is exactly the failure this project treats
as worse than being slow.

Declines remain for `|z| >= 12` on `CosIntegral`/`SinIntegral` and beyond 32 for
the rest; the MPFR path answers there.

#### The gate belongs to the kernel, not to the series

It was first written inside the shared series, which also changed the
*interpreter's* behaviour in a `USE_MPFR=0` build — where declining leaves the
user with an unevaluated expression rather than eight correct digits. The series
now reports its peak term through an out-param and the **ABI wrapper** applies
the gate: the kernel has somewhere to fall back to, so declining costs only
speed, while the interpreter's last-resort path keeps answering.

A test pins the contract in **both** directions — inside the budget it must not
decline (or the fast path silently is not one), outside it must.

Parity against the interpreter is 3.2e-16 to 1.1e-15 across the covered region.
Unlike `Gamma`, these are not bit-identical to the interpreter: its complex path
is MPFR, so these are genuinely approximations held to a tolerance.

## Compile: bail diagnostics, and auto-compilation of nine more builtins (2026-07-27)

### `CompileDiagnostics` — a bail can now say why

The engine's central usability problem was that failing to compile is *silent*.
`compile_expr` returns nothing, the caller quietly interprets, the answer is
still correct, and the only symptom is being 10–40× slower. Worse, the cost is
not proportional: the compilable subset is a **cliff**, so one unsupported head
anywhere in a body loses the entire body, including every head in it that would
have compiled.

New builtin **`CompileDiagnostics[argspec, expr]`** (`HoldAll`, `Protected`)
answers "did this compile, and if not, what stopped it". On failure it names the
**innermost** subexpression the emitter could not lower — the actual cause, not
the construct containing it. On success it reports the result type, the
instruction count, the number of hoisted common subexpressions, and the
instruction count with the optimiser off, so what code generation removed is
visible rather than inferred.

The implementation is one wrapper, not forty edits. Every bail is a plain
`return false` from somewhere inside the emitter; renaming that function to
`emit_node` and giving `emit` a three-line wrapper that records the node on the
way back up captures the deepest cause with **no bail site knowing diagnostics
exist** — so a bail added tomorrow is diagnosed the day it is written.
Speculative lowering (fusion probing) rolls the record back with the rest of the
emitter state, since a speculative failure is not a bail.

`MATHILDA_COMPILE_DIAG=1` prints the same report to stderr whenever a numeric
builtin falls back, which is how the wirings below were audited.

**It immediately found two rotted tests.** `test_autocompile.c` built its
FindRoot interpreter reference out of `Zeta` ("a head with no machine kernel"),
and `test_compiledfunction.c` tested the uncompilable-fallback path the same
way. `Zeta` got a machine kernel during M5, and both checks silently became
compiled-vs-compiled. The fix generalises: an interpreter reference built out of
a **user DownValue** (`uncid[t_] := t`) cannot expire when coverage grows, and
computes bit-for-bit the same numbers, so parity becomes exact rather than
approximate.

### Nine more builtins auto-compile

`ContourPlot`, `DensityPlot`, `ComplexPlot`, `ParametricPlot`, `PolarPlot`,
`ParametricPlot3D`, `VectorPlot`, `StreamPlot`, and `NSum`/`NProduct` now
compile their held bodies once and sample them over machine numbers. Measured
against the previous build, same machine, `-O3`:

| builtin | before | after | speedup |
|---|---|---|---|
| `PolarPlot`, 3000 points | 33.5 ms | 2.0 ms | **16.8×** |
| `ParametricPlot`, 3000 points | 16.2 ms | 1.9 ms | **8.4×** |
| `NProduct` | 174.9 ms | 21.9 ms | **8.0×** |
| `StreamPlot` | 230.6 ms | 32.3 ms | **7.1×** |
| `NSum` | 114.7 ms | 17.8 ms | **6.4×** |
| `ContourPlot`, 150² | 52.0 ms | 10.0 ms | **5.2×** |
| `ComplexPlot`, 150² | 109.4 ms | 42.9 ms | **2.5×** |
| `DensityPlot`, 150² | 90.5 ms | 45.7 ms | **2.0×** |
| `VectorPlot`, 60² | 9.8 ms | 6.6 ms | **1.5×** |
| `ParametricPlot3D`, 100² | 35.4 ms | 32.8 ms | **1.1×** |

The bottom three are **not** cases where the fast path underperformed — the
diagnostic confirms all three bodies compile. Sampling is simply no longer the
bottleneck: they build one `Rectangle`/`Arrow`/`Polygon` expression per cell, and
constructing those thousands of `Expr` nodes now dominates. That is the next
thing to attack in the plot pipeline, and it is not a compiler problem.

Three things were needed beyond the established pattern:

- **A parametric body is a pair**, and a compiled program returns one machine
  number. The pair is written out literally as `List[x(t), y(t)]`, so each
  component compiles as its own program (three for `ParametricPlot3D`),
  all-or-nothing — a half-compiled body still pays the whole evaluator
  round-trip.
- **`ComplexPlot` needs a complex ARGUMENT**, not merely a complex result: its
  variable ranges over a region of the plane. New `autocompile_new_z` /
  `autocompiled_eval_z` declare the variables `CT_COMPLEX`. Its subset is
  genuinely smaller — `Zeta[z]` compiles for `_Real` and bails for `_Complex` —
  which is the complex-kernel gap in `NUMERIC_FUNCTION_MISSING.md` showing up as
  a measurable 0.7 s for a 40×40 grid.
- **`NSum` has two samplers, not one.** Every method (Direct, Wynn, Levin,
  Euler–Maclaurin, CVZ, the far-tail ladder, the profiler) draws terms through
  one chokepoint, so compiling once covers all of them. But wiring only that
  gave **no speedup at all**: the Euler–Maclaurin correction samples the same
  summand at *continuous* real x through a separate path, and that is where an EM
  sum's time actually goes. Covering both took `Sin[n]/n^3` from 122 ms to
  18 ms. `NProduct` is `Exp[NSum[Log f]]` and inherits it.

MPFR paths are untouched throughout: `NSum` compiles nothing when
`WorkingPrecision` is set, because a double cannot carry a 30-digit term.

**On declining, every one of these falls through to the interpreter for that one
sample** rather than reporting a hole. A compiled real program declines both
where the interpreter has no real value *and* where a kernel is outside its
covered domain, and only the interpreter distinguishes them; re-evaluating the
few declining points costs no more than never having compiled.

### Fixed: `ParametricPlot`/`ParametricPlot3D`/`PolarPlot` leaked one `Expr` per sample

`symtab_add_own_value` **copies** its replacement, so the caller owns the
temporary. These three passed `expr_new_real(t)` inline and never freed it,
leaking one node per sample point — 529 blocks / 34 KB for a single default
`ParametricPlot`. Every other sampler in `src/graphics/` already had the
free. The fast path made it visible by not creating the binding at all; the
interpreter path is now leak-free too (0 blocks where the previous build leaked
157–901).

### Testing

`tests/test_autocompile.c` gains parity tests for all nine wirings. Each
compares the plot against the same plot with its body wrapped in an identity
`DownValue`, forcing the interpreter while computing identical numbers, and
compares **every machine number in the output** (`Cases[g, _Real, Infinity]` —
coordinates and colours) plus the count, so a structural divergence in an
adaptive sampler fails too. Agreement is **exact (0.0)** everywhere except
`ComplexPlot`, which differs by one ulp because C99 complex division and the
interpreter's `Complex[]` arithmetic round differently.

An anti-vacuity guard asserts, through the same API the builtins use, that each
body really does compile — every parity test above would pass if nothing
compiled at all.

## Compile: constant operands folded into the instruction (2026-07-27)

A constant reaching a binary op cost a whole instruction to materialise it into
a register, and that instruction re-executed on **every call**. In a polynomial
body it was a third of the whole stream: `Compile[{{x, _Real}}, 1.5 + 2.5 x]`
emitted five instructions, two of which were constant loads.

A new instruction kind `K_BINK` — `dst = f(R[a], imm)` — carries the constant in
the instruction. Eighteen opcodes cover real and integer add / subtract /
multiply / divide and the four order comparisons, in both operand orders where
the operation is not commutative.

The rewrite lives in the optimiser, not the emitter, and reuses machinery that
was already there: `pass_vn` already tracks which registers hold constants (for
folding), so a binary op with **exactly one** constant operand (two would have
folded outright) becomes its immediate form, and the existing DCE deletes the
now-dead `CONST`. Nothing in the emitter changed.

Two details are load-bearing:

- **The surviving operand always becomes `a`**, so the VM never has to ask which
  side the constant was on — one register read, no branch.
- **A comparison with the constant on the LEFT is rewritten by swapping the
  predicate**, not by adding eight more opcodes. `k < x` becomes `x > k`, which
  is NaN-safe: both are false for a NaN `x`. Negating a predicate would not be.

Every form is a **single** arithmetic operation, so no floating-point contraction
into an FMA is possible and the result is bit-identical to the register form it
replaced — which the optimiser's existing opt-vs-no-opt `memcmp` gate checks over
eight new bodies covering every shape of the rewrite.

### What it is worth, measured rather than extrapolated

| | instructions | time |
|---|---|---|
| Horner, degree 40 | 121 → 81 (**−33%**) | 181 → 173 ns/call (1.05×) |
| `1.5 + 2.5 x` | 5 → 3 (−40%) | |
| `Exp[-x^2/2]/Sqrt[2 Pi]` | 9 → 6 (−33%) | |
| `Table[deg-5 poly, 10^6 points]` | | 140 → 129 ms (**1.09×**) |
| Newton (`While`) micro-bench | 20 → 14 | 382 → 340 ns (1.12×) |
| Plot / NIntegrate / NSum / ContourPlot | | 1.00–1.03× |

**A third fewer instructions buys nowhere near a third of the time.** The removed
`CONST`s were the cheapest instruction in the set — a slot copy with no
dependency — and the surrounding multiply-add chain is serially dependent, so the
machine was never instruction-count-bound. The honest summary is ~9% where a body
is constant-heavy arithmetic (polynomial evaluation, which is common), and
1–3% otherwise. Worth recording, because the instruction-count number on its own
would have supported a 1.5× claim.

Compile *time* rises ~20% for constant-heavy bodies: removing the `CONST`s gives
DCE something to report, which earns the optimiser another round. That is ~1 µs
on a body then evaluated thousands of times, and the end-to-end measurements
above already include it. The rewrite itself deliberately does **not** report
progress — DCE runs in the same round, so claiming progress bought only an extra
CFG build and liveness solve.

An anti-vacuity guard sits beside the A/B gate: every A/B body stays
bitwise-identical whether or not the rewrite fires, so a separate check asserts
the instruction count actually drops by the number of constants in the body.

## Indexed machine arrays in `Compile[]` — M3c (2026-07-27)

`Compile[]` bodies can now index, mutate and create machine arrays, which is
what makes a hand-written finite-difference stencil (or any other indexed
numeric kernel) compilable at all. Before this, `Part` was outside the subset,
so a body containing `u[[i, j]]` fell back to the interpreter *in its entirety*.

**`Part` reads cover the full spec vocabulary**, via two lowerings chosen by the
shape of the subscript list:

- One scalar integer subscript per axis — `v[[i]]`, `m[[i, j]]`,
  `t[[i, j, k]]`, negatives counting from the end, computed indices like
  `v[[2 k + 1]]` — lowers **inline**: one new `A_AXIS` instruction per axis
  folds the multiply by the axis length, the 1-based/negative resolution and the
  range check together, then the element is read with the same `A_LOAD` the
  fused elementwise loop already used. No allocation. `u[[i, j]]` is four
  instructions.
- Everything else — `Span`, `All`, a list of positions, partial indexing
  (`m[[2]]` for a row), and mixtures like `m[[k, 2 ;; 4]]` — delegates to the
  interpreter's own `ndarray_part` through a new `A_PART`, so the compiled
  answer *is* the interpreted answer by construction rather than by agreement.
  A `PartSpec` carried in the instruction's immediate holds the literal specs
  and the registers of the computed ones, which is what lets one subscript list
  mix both.

The range check is **per axis, not on the flat index**: `m[[1, ncols + 5]]` is
in range as a linear offset and would silently read the next row.

**`Part` assignment** with the same vocabulary — `u[[i, j]] = x`,
`u[[2 ;; 4]] = 0.`, `u[[All, 2]] = 0.`, `u[[{1, 3}]] = 7.`,
`u[[1 ;; 3]] = w` — plus `+=`, `-=`, `*=`, `/=` on a scalar position. The target
must be an array the program **owns** (a `Module`/`With` local), because the
write goes into the buffer in place; an argument array is borrowed and writing
through it is refused at compile time.

**`ConstantArray[v, n]` / `ConstantArray[v, {n1, …}]`** create arrays at any
rank (new `A_NEW`), and **`Module`/`With` locals may be arrays**, including as
the result (new `A_COPY` for a borrowed initialiser, `A_XFER` for the handle
transfer out of the scope). An *integer* fill is deliberately refused:
`ConstantArray[0, n]` holds exact integer zeros in the interpreter and an
`NDArray` has no integer dtype, so compiling it would answer differently.

Also: **`Length`** now works at any rank (it is `dims[0]`, the number of rows;
`Total` stays rank-1 because it reduces only the leading axis), and **`Do`
accepts several iterators** (`Do[body, {i, …}, {j, …}]`), nesting them with the
last varying fastest as the interpreter does.

**Soundness change:** `A_LOAD` is no longer a *pure* opcode. It was pure while
the only writer was fusion, which stores solely into a fresh result buffer; once
user code can write a buffer it also reads, a pure load would be CSE'd across an
intervening store, and LICM would hoist a loop-invariant load out of the very
loop that mutates it. Both cases are now regression-tested.

## `TimesBy` / `DivideBy`, and `Part` assignment on `NDArray` (2026-07-27)

Two interpreter bugs found by the tests above.

**`TimesBy` was registered but had no implementation** — `TimesBy[x, 2]` silently
did nothing, on a `Part` target *or* on a plain symbol — while the compiled path
implemented it, so a compiled body could answer where the interpreter declined.
`increment_core` now takes a combining mode (`Plus`/`Times`, with or without
inversion) instead of a `negate` flag, and `TimesBy` and the new `DivideBy` join
`AddTo`/`SubtractFrom` on it. The `*=` and `/=` operators are new too: neither
parsed before, so `x *= 2` was a syntax error.

**`Part` assignment into an `NDArray` silently ignored every non-integer spec.**
`a[[2 ;; 4]] = 0` worked on a `List` and did nothing at all on the equivalent
`NDArray`. The per-axis selector behind `ndarray_part` is now shared with a new
`ndarray_part_set`, so a write names exactly the elements a read of the same spec
would, and `nd_part_assign` covers `Span` / `All` / position lists / partial
indexing. (The copy it writes into is built explicitly rather than with
`expr_copy`, which is a refcount bump — writing through that would have reached
every other holder of the array.)

## CompilePrint — bytecode disassembly for a CompiledFunction (2026-07-27)

`CompilePrint[cf]` prints the bytecode of a `CompiledFunction`: the signature,
each argument's register and declared type, the result register, the sizes of
the three register banks, the instruction/CSE/parallel-loop counts, and then one
line per instruction giving the opcode with its raw operands on the left and a
readable rendering on the right.

Code generation was otherwise invisible. `CompileDiagnostics` reports how *much*
code a body produced; nothing anywhere reported *which*. The questions that
actually come up have no other answer: which twelve instructions the optimiser
left out of forty, whether the constants got folded into the instructions
(`K_BINK`) or are still costing a `CONST` each, whether an array chain fused into
a strip-mined loop or is delegating per operation, whether `OP_APAR` was emitted
so the map will really fan out, and which machine kernel a special function
lowered to.

- Registers are named by bank and numbered by frame slot — `R` scalar, `V` array
  handle, `T` strip-mining tile — so an array argument, which lives below
  `arr_base` like every other argument, still reads as `V0`.
- **No addresses are ever printed.** Machine-kernel immediates (bare function
  pointers taken from an `NDUnaryKernel` / `NDBinaryKernel` / `NDNaryKernel`) are
  reverse-resolved to their symbol names through `symtab_for_each`, and callee
  programs and parallel loops are numbered. The listing is therefore
  deterministic and diffable, which is what makes it assertable in a test.
- Operand *shape* is always read from `compile_op_kind[]`, the same table the
  optimiser and `patch_reg` use, so a new opcode cannot be decoded one way in the
  disassembler and another way in the passes. `OPLIST` now drives four things;
  the opcode-name table is the fourth expansion.
- `OP_CONST` carries no type tag and the register's static type does not survive
  into the finished program, so the constant's type is recovered from the first
  instruction that *reads* it — following `MOVE` chains, since initialising a
  `Module` local puts one between the constant and anything that says what it is.
- An object whose body did not compile has no bytecode to show, so it reports the
  bail reason and the offending subexpression instead.
- Attributes are `Protected` only — deliberately **not** `HoldAll`, unlike
  `Compile` and `CompileDiagnostics`, because the argument has to evaluate down to
  the compiled object. Returns `Null`; a non-`CompiledFunction` argument is left
  unevaluated.

Implementation: `src/compile/disasm.c` (`compiled_disassemble` on a program,
`compiled_function_disassemble` on an object; both return a `malloc`'d string the
caller frees). `struct CompiledProgram` and `ParLoop` moved from `compile.c` into
`compile_internal.h` so the disassembler can see the program's shape — a pure
relocation, no behaviour change.

### Fixed: a fused array argument was reported as never read

`fuse_collect` resolved an array leaf directly through `arg_find` without setting
`argdep`, and a fully fused body never reaches `emit`'s symbol case — so
`compiled_arg_deps` reported that `Compile[{{v, _Real, 1}}, v^2 + 2 v + 1]` does
not depend on `v`. Harmless so far only because the consumer (NDSolve's colored-FD
Jacobian) passes scalar arguments; a client that fed it an array signature would
have concluded the function was constant in that argument. Surfaced by
`CompilePrint` printing `(unused)` next to an argument that plainly was used.

## Fixed: DensityPlot clamped the raw value under ColorFunctionScaling -> False (2026-07-27)

`densityplot.c` applied the `[0,1]` clamp to the colour-function argument
unconditionally, including when `ColorFunctionScaling -> False` asked for the raw
value. Every cell below 0 (or above 1) therefore got the colour of the nearest
endpoint, and the option was useless for any function whose range is not already
inside the unit interval — which is most of them, and all signed ones.

The failure is silent and the picture is plausible: a field that has gone
negative renders as a uniform block, exactly as a correct plot of a genuinely
constant field would. It was caught while producing the snapshot figures for
`docs/compile_example/COMPILE_EXAMPLE.md`, where two of five frames of an
oscillating wave came out blank and disagreed with the amplitude table printed
beside them.

The clamp belongs to the scaling branch only, where it absorbs float error at the
ends of `(avg - zmin)/zspan`. With scaling off the value now reaches the colour
function untouched; the colour function owns its own domain, and both built-in
ramps (`thermal_rgb`, `named_color_ramp`) already clamp internally so they stay
well defined either way. Covered by
`test_densityplot_unscaled_color_function_gets_raw_value` in `tests/test_graphics.c`.

## The Compile[] tutorial: bytecode walkthrough and solution snapshots (2026-07-27)

`docs/compile_example/` — the Markdown, the rendered PDF, the snapshot figure,

the body is rebuilt at every sample point (145 s per frame instead of 0.1 s), and
`Max[Flatten[u]]` stops being the amplitude once the wave goes negative.

## Fixed: `Do` / `For` / `While` / `Nest` speculatively evaluated user code (2026-07-28)

The automatic numeric-loop fast path (`src/numloop.c`) compiles a loop body's
arithmetic to a double-stack program. Its expression walker collapses any
**variable-free** subexpression to a single machine constant, which is what
folds `Pi`, `Sqrt[2]`, `Rational[p, q]` and plain literals uniformly. The fold
was performed by `const_fold()`, which *evaluates* whatever it is handed — and
it was handed anything, including calls to user-defined functions. Two bugs
followed.

**Correctness: side effects fired one time too many.** The fold runs once while
the block is being built, before the loop starts. When the folded call turned
out not to be a machine number the build bailed and the interpreter ran the
loop properly — but the probe's evaluation had already happened:

```mathematica
f[] := (c = c + 1; 1.5);
c = 0; Do[y = f[], {5}]; c
(* was 6, now 5 *)
```

**Performance: the probe was not even the same computation, and was slower than
the loop it was trying to replace.** `const_fold` calls `numericalize` *before*
evaluating, so exact integers in the subexpression became machine reals first.
An integer that is an argument is usually harmless; an integer that ends up as a
`Table` iterator bound or a `Part` subscript is not, because neither resolves
against a `Real`. A stencil step `istep[grid, grid, lam, 41]` was therefore
probed as `istep[grid, grid, lam, 41.]`, whose body collapsed into one huge
symbolic `Plus` holding an unevaluated `Part[<1681-element grid>, 1., 1.]`.
`Plus` groups like terms by hashing each non-numeric base, so this cost
`O(grid)` *per stencil point* — the discarded probe ran ~4× slower than the real
evaluation, and the loop then did the work again.

Because the trigger is a *literal* in the loop body, the slowdown appeared
wherever a scoping construct substitutes a value into that body — `With`, and
any `f[n_] := Module[{...}, ... Do[...] ...]` where `n` arrives as a number.
`Module` and `Block` alone were never at fault: `Block` rebinds symbols rather
than substituting, and `Module` renames rather than inlining, so both leave the
body's arguments symbolic and dodged the probe entirely.

**A third bug, same root, found while fixing it: a delayed OwnValue was frozen
as a loop constant.** `x := (c = c + 1; 1.5)` is a held expression re-run on
every read, but folding treated it like a value:

```mathematica
zz := (c = c + 1; 1.5);
c = 0; Do[y = zz + 1., {5}]; c
(* was 1 -- the body ran once and the rest of the loop reused the frozen
   constant; now 5 *)
```

**The fix.** A new `const_foldable()` gate restricts folding to a syntactic
numeric grammar — numeric literals, the arithmetic/elementary heads the block
already lowers (`Plus`, `Times`, `Power`, `Subtract`, `Divide`, `Rational`, `N`,
and the unary kernels `Sin` … `ArcTan`, `Sqrt`, `Abs`, `Log`, `Exp`), and bare
symbols whose read is a pure lookup (no OwnValue at all, as for `Pi`/`E`, or an
OwnValue that is already a number, as `x = 2.5` leaves it). Anything else bails
to the interpreter without being evaluated, which is always a correct outcome —
the fast path is an optimisation, never a semantic. The fix sits in the single
shared walker, so it covers `Do`, `For`, `While`, `Nest`, `NestWhile`,
`FixedPoint`, `Fold` and `Map` at once.

Measured on the wave-equation march from `docs/compile_example/COMPILE_EXAMPLE.md`
(since untracked; interpreted arm, n = 41, 39 steps), all arms bit-identical:

| arm | before | after |
|---|---:|---:|
| top level | 4.24 s | 4.10 s |
| `Block[{...}, ...]` | 4.20 s | 4.09 s |
| `Module[{...}, ...]` | 4.24 s | 4.07 s |
| `With[{lam = ..., n = ...}, ...]` | **13.23 s** | **4.06 s** |
| `run[n_] := Module[{...}, ...]`, called `run[41]` | **12.68 s** | **4.09 s** |

The folding the gate protects is unaffected — `Do[s = s + Pi i, {i, 1, 10^6}]`
stays at 115× the interpreter, `Do[s = s + Sqrt[2] i + 1/3, ...]` at 209×,
`Do[s = s + i^2, ...]` at 22×, `Do[x = Cos[x], {10^6}]` at 17×. A body whose
loop-invariant term is a *non-arithmetic* builtin (e.g. `Length[v]`) now declines
the fast path rather than folding it; that shape loses its acceleration, which is
the deliberate price of never evaluating anything the user could observe.

Regression tests in `tests/test_numloop.c`: `test_no_speculative_side_effect`,
`test_no_speculative_side_effect_range`, `test_no_speculative_numericalize`,
`test_no_fold_of_delayed_ownvalue`, `test_const_fold_still_folds_numerics`. Each
was checked to fail against the unfixed build.

## `Compile[]` option `RuntimeAttributes -> Listable`, and $VersionNumber 0.019 (2026-07-28)

`Compile[argspec, body]` now takes the `RuntimeAttributes` option. The default is
`{}` and the only other setting is `Listable` (accepted as either
`RuntimeAttributes -> Listable` or `RuntimeAttributes -> {Listable}`); the
resulting `CompiledFunction` then threads over its list-valued arguments the way
a `Listable` symbol does. Before this, a list handed to a scalar parameter simply
failed to box and the whole call fell through to the interpreter, where it was
the *body's* own heads that decided whether anything threaded — so
`Compile[{{x, _Real}}, x^2][{1., 2.}]` happened to give `{1., 4.}` (Power is
Listable) while `Compile[{{x, _Real}}, If[x > 0, 1., -1.]][{1., -2.}]` came back
unevaluated. Threading is now the object's own property and independent of what
the body is made of.

Semantics (`cf_thread` in `src/compile/compiled_function.c`, run before argument
boxing, so a list is never handed to a scalar parameter):

- **Rank-aware.** A slot threads only over the levels its declared type does not
  consume: rank 0 for a scalar parameter, so any list threads, versus rank *r*
  for `{v, _Real, r}`, which takes an *r*-deep list whole. A `Listable`
  `Compile[{{v, _Real, 1}}, Total[v]]` therefore maps over the rows of a matrix
  and still takes a plain vector as one argument — the reason the threading lives
  next to the signature rather than in the evaluator's generic `apply_listable`,
  which knows nothing about parameter types.
- **Recursive**, through `compiled_function_apply` itself: nested lists thread
  level by level, and each leaf independently takes the bytecode or the
  interpreter path, so one symbolic element in an otherwise numeric list yields
  the symbolic answer for that element only.
- **Non-list arguments** are reused for every element; `{}` threads to `{}`;
  unequal lengths report `Thread::tdlen` (naming the actual call) and leave the
  application unevaluated, matching the evaluator's answer for a `Listable`
  symbol.
- **`NDArray` arguments** thread by the same rank rule — one row at a time via
  `ndarray_part` — and the result is packed back into an `NDArray`, flattening
  any already-packed inner results first so a rank-2 array over a scalar
  parameter comes back as one rank-2 array rather than a list of rows. A packed
  array and the `List` it packs now give the same answer, which they did not
  before.

Surface details: `Options[Compile]` reports `{RuntimeAttributes -> {}}` and
`SetOptions[Compile, …]` is honoured; an unrecognised option name, or a
`RuntimeAttributes` value that is not one of the two spellings, leaves
`Compile[…]` unevaluated rather than silently building an object that ignores it;
`CompilePrint` prints an `Attributes  Listable` line for such an object.

Tests: `test_cf_runtime_attributes` and `test_cf_runtime_attributes_arrays` in
`tests/test_compiledfunction.c` (26 assertions). The discriminating body is
`If[x > 0, …]`, deliberately not an arithmetic one — with a list substituted for
`x`, Plus/Power are themselves `Listable`, so a test built on `x^2` would pass
with the feature removed. `valgrind --leak-check=full` on the suite reports no
leak record in any Mathilda frame.

Also fixed while verifying that: `render_meaning` in `src/compile/disasm.c` left
the tail of its 32-byte opcode-base buffer uninitialised, and the optimiser's
inlined vectorised `strcmp` reads a whole word past the terminator, so memcheck
reported a conditional on uninitialised data (harmless, but it made a clean
valgrind run of the suite impossible). The buffer is now zeroed.

`$VersionNumber` / `$Version` are bumped to **0.019** (`src/version.h`).

## Portability fix: POSIX `<math.h>` constants break the Linux build (2026-07-28)

Fixes [issue #36](https://github.com/stblake/mathilda/issues/36) — `make` failed
on Linux with:

```
src/special_functions/sf_machine.c:250:32: error: 'M_E' undeclared
  250 |         double p = sqrt(2.0 * (M_E * x + 1.0));
```

`M_PI`, `M_E` and the rest of the `M_*` family are POSIX, **not** C99. glibc
hides them under `-std=c99`, while Darwin exposes them implicitly — so the bug
compiles cleanly on macOS and only surfaces for users building on Linux. The
project convention (SPEC.md §10) is a per-file guarded fallback right after
`#include <math.h>`, as in `src/trig.c` and `src/numeric.c`.

A sweep of every `M_*` use across `src/` and `tests/` found **five** files
missing the guard, not one. `sf_machine.c` was merely the first the reporter's
build reached; `src/graphics/plot_common.c` — compiled unconditionally, not
gated on `USE_GRAPHICS` — would have been the very next error.

- `src/special_functions/sf_machine.c` — added the `M_E` guard (it already
  guarded `M_PI`). Used by the `ProductLog` branch-point series.
- `src/graphics/plot_common.c` — added the `M_PI` guard (domain-colouring
  phase→hue map).
- `tests/test_cosintegral.c` — `M_PI`, `M_PI_2`.
- `tests/test_coshintegral.c`, `tests/test_rationalize.c` — `M_PI`.

### Regression gate: `make check-c99`

Because this class of defect is invisible on the maintainer's platform, the fix
is paired with a checker rather than left to review. `tools/check_math_constants.py`
scans every git-tracked `.c`/`.h`/`.inc` under `src/` and `tests/` (excluding
`src/external/`) for uses of all thirteen POSIX `M_*` constants that lack a
matching guard in the same file, and prints a paste-ready `#ifndef` block for
each. Comments and string literals are stripped first, so prose mentions such as
`numeric.c`'s "`M_PI` and `M_E` are POSIX/GNU extensions" are not flagged.

```bash
make check-c99      # exits nonzero, naming every offending file
```

Verified non-vacuous: run against the pre-fix tree it reports exactly those five
files and exits 1; against the fixed tree it exits 0. Both edited sources also
compile clean under `gcc -std=c99 -D_ANSI_SOURCE`, which reproduces glibc's
strict hiding behaviour on macOS.
