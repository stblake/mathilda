# Changelog: week of 2026-07-27 (Mon) – 2026-08-02 (Sun)

Feature additions and fixes recorded during this week.

## Auto-compilation of Plot / Plot3D / Table / NIntegrate / FindRoot (2026-07-27)

The numeric builtins now transparently use the `Compile[]` bytecode engine as a
fast path: each compiles its held body once as a function of its sample
variable(s) and evaluates it over machine numbers with no `Expr` allocation,
instead of running the full symbolic evaluator at every one of the thousands of
sample points. Uncompilable bodies (any construct outside the compilable subset,
e.g. `Zeta`) transparently keep the interpreter path, so results are unchanged.

New shared adapter `src/compile/autocompile.{c,h}`: `autocompile_new(body,
vars, nvars)` (→ `NULL` if uncompilable), `autocompiled_eval_real` /
`autocompiled_eval_complex`, `autocompiled_free`. The header is self-contained
(no `<complex.h>`/`compile.h` leak — `double _Complex` is a builtin type) so it
never pollutes callers with the `I` macro.

Correctness rule shared by the callers: a compiled *real* program returns a
non-finite value exactly where the interpreter would instead produce a *complex*
result (e.g. `Sqrt` of a negative). Callers that exclude non-real points (Plot)
drop it; callers that need the contribution (NIntegrate, FindRoot, real-iterator
Table) fall back to the interpreter at that single point.

- **Plot / Plot3D** — compiled in the per-curve/per-surface setup; a non-finite
  or non-real sample excludes the point, matching the existing behaviour
  (`Plot[Sqrt[x], {x,-1,1}]` still drops the negative half). **~215×** on a
  400-point 2-D curve; **~11×** on an 80×80 surface.
- **Table** — ONLY the inexact (machine-real) iterator branch, where the
  interpreter already yields machine reals; exact iterators
  (`Integer`/`BigInt`/`Rational`) and symbolic bodies are untouched and
  bit-for-bit unchanged (`Table[i^2,{i,1,5}]`, `Table[2^i,…]` BigInt,
  `Table[Sin[i],…]` symbolic). Per-element interpreter fallback keeps
  `Table[Sqrt[x],{x,-1.,1.,1.}]` complex. **~128×** on a 50k-element real table.
- **NIntegrate** — the 1-D machine-precision integrand (`ni_eval_at`), for the
  finite / half-line / whole-line real cases. Complex-contour abscissae and the
  MPFR path are untouched; a complex-valued integrand falls back per sample
  (`NIntegrate[Sqrt[x-1],{x,0,2}] → 2/3 + (2/3)I`). **~353×** on a batch of 50
  integrals. Fixed a latent bug the change exposed: the oscillatory
  amplitude/phase decomposition value-copies the sampler context and swaps its
  body, which must reset the compiled program (`ni_ctx_rebody`).
- **FindRoot** — the scalar, machine-precision, real function (Newton / Secant /
  Brent, and the finite-difference-derivative path used when `D` is inert, e.g.
  `Zeta'`). Complex-root, MPFR, and multivariate-system solves keep the
  interpreter. **~19×** on 5000 scalar solves.

Tests: `tests/test_autocompile.c` — end-to-end parity through the real builtins,
non-real exclusion / per-point fallback, uncompilable fallback, and the
oscillatory regression. All `leaks`-clean. MPFR paths untouched throughout.

### Follow-up: multi-dimensional NIntegrate and FindRoot systems

- **Multi-D NIntegrate** — the multi-dimensional machine chokepoint
  `ni_mc_sample` (shared by the Genz–Malik cubature and Monte-Carlo engines) now
  compiles the body once as `f(v_1..v_d)` and writes the complex result straight
  into the sample slot (no boxing). A box where the integrand goes complex (e.g.
  `Sqrt[x+y-1]` over the unit square) still contributes its imaginary part via the
  per-point interpreter fallback. **~504×** on a 2-D 500k-point Monte-Carlo
  integral.
- **FindRoot systems** — `fr_run_newton_system_real` compiles each component
  `f_i` and each symbolic Jacobian entry `D[f_i, x_j]` as functions of all
  variables, used at the residual/Jacobian/step-check evaluation sites via a
  shared `fr_try_compiled` helper. An uncompilable component or Jacobian row
  (e.g. `LogGamma`, whose derivative `PolyGamma` is evaluable) stays on the
  interpreter while the rest runs compiled; the linear solve is unchanged.
  **~6.9×** on a 2×2 nonlinear system. (Systems with an *inert* Jacobian entry,
  e.g. `Zeta'`, still fail as before — a pre-existing limitation.)

## Compile engine M3a — rank-1 machine arrays (2026-07-27)

The `Compile[]` bytecode engine was scalar-only. It now carries **rank-1 machine
vectors** as a first-class value category, delegating every buffer operation to
the existing NDArray subsystem, so a compiled program can take `NDArray`
arguments, compute over whole buffers, and return an `NDArray` or reduce to a
scalar — with no `Expr` allocation per element and no evaluator round-trip per
operation.

**Type lattice.** `CompileType` now packs array types into the same integer as
the scalars (`CT_ARR + 4*(rank-1) + elem`), so every field that already carried a
`CompileType` — inference results, register types, declared argument types —
carries array types with no parallel plumbing. New helpers `CT_ARRAY(elem,rank)`
/ `CT_IS_ARRAY` / `CT_ELEM` / `CT_RANK`, plus a `CT_ERR` sentinel that makes the
enum's underlying type signed (so the existing `(int)t < 0` checks are well
defined). `CompileValue` gained an `Expr* a` member: an array argument is
**borrowed**, an array result is **owned by the caller**.

**Compilable over arrays.** `Plus`, `Times`, `Subtract`, `Minus`, `Divide`,
`Power` (vector⊕vector, vector⊕scalar broadcast, and scalar^vector); every
elementary and special function with a registered ND unary kernel (`Sin`, `Exp`,
`Log`, `Gamma`, `Abs`, `Re`/`Im`/`Arg`/`Conjugate`, `Floor`/`Ceiling`/`Round`,
…); the two-argument ND binary kernels (`Log[b,v]`, `ArcTan[v,y]`, `BesselJ[n,v]`,
`Mod`); and the array→scalar reductions `Total[v]` and `Length[v]`, which let
whole expressions such as `Total[(v - Total[v]/Length[v])^2]/Length[v]` compile
end to end. Real and complex (`complex64`) element types both work.

**New C entry point.** `ndred_total_all(a)` in `ndreduce.h` — full reduction of
an NDArray to a scalar, taking the *array* rather than the enclosing call, so a
caller that already holds the operand needs no wrapper call node. Shares
`ndred_total`'s summation, so the rounding is identical.

**Correctness contract**, lifted unchanged from the scalar engine: a program that
promised a real element type but whose buffer would leave the real axis (e.g.
`Sqrt[v]` with a negative entry, which the ND layer promotes to a complex dtype)
fails the call, and the caller falls back to the interpreter — it never returns a
wrong-typed result. Shape mismatches, allocation failures, and kernels that
decline an element fail the same way.

**Lifetime.** Array registers live in their own contiguous bank above the scalar
registers, so a slot is either always-array or never-array and teardown cannot
mistake a `double` for a pointer. Operand frees are encoded in the consuming
instruction's flag bits (which occupy what was padding — `Instr` did not grow),
so they happen *after* the operand is read and the result may still reuse an
operand's register. Every array register is NULLed before a call (the frame is
reused across calls) and swept afterwards, including on the abort path.

**Not yet in the subset** (each bails cleanly to the interpreter rather than
aliasing a handle): array-valued `If` branches, `With`/`Module` locals, `Sum`
accumulators and `Nest` state — all of which would need to *copy* an array
handle where the engine only moves one — a bare array argument as the whole
result, and rank ≥ 2. The user-facing `Compile[]` argspec has no array form yet,
so this is reachable from C (`compile_expr` with a `CT_ARRAY(...)` argument
type), not yet from the REPL.

**Measured.** Parity with the interpreter is *exact* (max relative error 0.0)
across 34 array bodies, because both paths run the same ND kernels. The speedup
is therefore only the per-operation evaluator round-trip that the compiled
program avoids: **2.3× at length 16, 1.0× at length 4096** for
`Total[Sin[v] Exp[-v] + Sqrt[v]]`. Large-vector gains need loop *fusion* (one
buffer pass for a chain of elementwise ops instead of one per operation), which
is M3b work, not delegation.

Tests: `tests/test_compile.c` — 34 parity bodies (real + complex vectors),
7 must-bail cases, the real-element runtime contract, 5000-call frame reuse, an
array temporary freed per iteration inside a `Do` loop, and the two performance
points. `leaks`-clean and ASan-clean.

## Compile engine — counted iterators, global folding, callee inlining

Four fixes to the compiled fast path, found by profiling a Newton-fractal
benchmark that ran an order of magnitude slower than expected.

**`Do` accepted only `{i, lo, hi}`.** Every other counted spelling the
interpreter supports made the *whole* surrounding `Compile[]` bail, so the body
ran in the interpreter — a silent 37× cost, not a small one. `Do`, `Sum` and
`Product` now share one spec parser matching `src/iter.c`:

| spec | meaning |
|------|---------|
| `n`, `{n}` | repeat n times, binding no iterator symbol (`Do` only) |
| `{i, hi}` | `i = 1, …, hi` |
| `{i, lo, hi}` | `i = lo, …, hi` |
| `{i, lo, hi, di}` | step `di`, a nonzero integer literal (loop test flips for `di < 0`) |

`Sum`/`Product` deliberately reject the bare-count forms because the interpreter
does (`sum.c`, `product.c`); the compiled path must not answer where the
interpreter declines. List iteration and non-literal steps bail as before.

**Nested `Table` could not compile its inner body.** `Table[f, {y,…}, {x,…}]`
desugars to nested `Table`s, and the inner one sees `y` only as a symbol-table
OwnValue, which made it an uncompilable free symbol. `compile_expr_ex` gained
`COMPILE_FOLD_GLOBALS`, resolving such a symbol to the machine number it
currently holds. It is opt-in and used *only* by `autocompile.c`, whose programs
live and die inside one builtin call; a user `Compile[]` object outlives its
defining scope, so it keeps bailing, which stays correct however the global is
later reassigned. Any body that could *mutate* a global mid-iteration (a `Set`
to a non-local) already bails, so a folded constant can never go stale.

**`Table` element types.** The compiled path routed every result through a
`double`, so an integer-valued body (`If[…, 1, 2]`, `Round[x]`) came back as
`1.` instead of `1`. New `autocompiled_eval_boxed` returns an Expr of the
result's own type; `Table` uses it. `Plot`/`NIntegrate`/`FindRoot` keep the
unboxed real path.

**Calling a `CompiledFunction` from a compiled body** previously bailed, costing
an evaluator round-trip per point (~2.3 µs of a 3.1 µs call — 72% of runtime).
The compiler now inlines the callee: arguments are lowered in the caller's
environment and coerced to the declared parameter types, then the body is
lowered with *only* the parameters in scope, so a caller argument sharing a name
with a callee global cannot capture it. Arity mismatch, array-typed parameters
and self-reference (depth-capped) all bail to the interpreter.

Measured on `Table[newt[x + I y, 25], {y,-1,1,2./199}, {x,-1,1,2./199}]`
(200 × 200 × 25 complex Newton steps): **4.45 s → 0.046 s (97×)**. The same
expression written inline without `Compile[]` now also fully compiles, at
0.042 s, and the two agree exactly.

`While` and `For` bodies go through the same paths and were verified alongside
`Do` — wrapped in `Compile[]`, inline in an auto-compiled `Table`, and as an
inlined callee — with identical results and timings.

Tests: `tests/test_compile.c` — 9 iterator spellings, exact integer counts, the
two must-bail forms, and a **multi-statement loop body** (four locals of three
types, five statements per iteration, a two-armed `If` mutating state in both
arms) written as `Do`/`While`/`For`: the three must agree *bitwise* with each
other and match an independent C reference (200 random points, max rel err
9.2e-15). `tests/test_autocompile.c` — result-type preservation, nested-`Table`
folding, fold freshness and the mutating-body fallback, 8 inlining cases each
checked against an interpreted twin (a DownValue never compiles, so a capture
bug shows up as a mismatch), and the same multi-statement body driven through
`Table` all three ways plus as an inlined callee.

One test deserves note: `test_multiline_bodies_really_compile` asserts, via the
same `autocompile_new` the builtin uses, that each loop body *actually compiles*.
Every parity check would otherwise pass vacuously if nothing compiled — agreement
with the interpreter is trivially true when you are the interpreter. Verified by
sabotage: disabling `COMPILE_FOLD_GLOBALS` leaves the three-way parity assertions
green (all three fall back and agree with each other) while this guard fails with
`multi-line Do body did not compile`. It runs first, before the behavioural
tests. `leaks`-clean.

## `Compile[]` M5 — optimising code generation, coverage audit, any-rank arrays

Four separable pieces of work on the numeric compiler (`src/compile/`).

> **Read the M5b section below before quoting any number here.** These were
> measured in a `tests/` build that had no `CMAKE_BUILD_TYPE` and so compiled at
> `-O0`. The ratios hold (both sides were built identically); the absolute
> figures were inflated. At `-O3` the dispatch-bound Horner baseline is
> **295 ns/call for 80 arithmetic operations (3.7 ns/op)**, and the work below
> takes it to **~200 ns/call (2.5 ns/op), ~1.45×** — not the 2.0× the `-O0`
> numbers suggested.

### Lazy operand addressing in the VM

`NEXT()` recomputed all three operand pointers for every instruction regardless
of which the opcode used — the hottest ops (`ADD_R`, `MUL_R`) read two and the
unary ops read one, so most of that work was wasted on the common case. Operands
are now addressed at the point of use, letting the C compiler fold the address
computation into the load.

**649 → 427 ns/call (1.53×)** on Horner *at `-O0`*; at `-O3` the same change is
worth appreciably less, because the C compiler was already folding some of that
address arithmetic. No behavioural change.

### A bytecode optimiser (`src/compile/optimize.c`, new)

The emitter lowers each `Expr` node independently and previously had **no middle
end at all** — no constant folding, no dead-code elimination, no loop-invariant
hoisting. There is now a pass pipeline between emission and the finished program:

- `compile_internal.h` extracts `Slot`/`Instr`/the opcode enum so the optimiser
  is its own translation unit. `OPLIST` now carries a KIND per opcode and drives
  three things that could previously drift apart: the opcode enum, the VM's
  computed-goto jump table, and the optimiser's instruction-property table.
- CFG construction and real backward liveness, then per-block value numbering
  (constant folding, CSE, copy propagation), liveness-driven dead-code
  elimination, and loop-invariant code motion over natural loops.
- Array registers and the impure array opcodes are excluded throughout: their
  ownership lives in instruction flags, not in the dataflow the scalar passes
  reason about.
- `OP_LOOP` folds increment, test and branch into one instruction — a counted
  loop otherwise spends four instructions per iteration on control alone.

Horner **427 → 335 ns/call** at `-O0`. Measured properly at `-O3`, the optimiser
alone is worth **1.33×** on Horner, **1.29×** on `Nest` and **1.25×** on
Newton/`While` (LICM), and the whole of M5 takes the dispatch-bound body from
**295 → ~200 ns/call (~1.45×)**.

`COMPILE_NO_OPT` is the A/B switch. The correctness gate is **bitwise identity**,
not accuracy: 18 bodies compiled both ways must agree bit for bit over a
randomised sweep (compared with `memcmp`, so `NaN` must equal `NaN` and `-0.0`
must differ from `+0.0`). A pass that reassociated a sum or contracted a
multiply-add would still look accurate while breaking the engine's stated parity
contract with the interpreter.

### `NDArray` of any rank

The delegated NDArray path was already rank-general; the compiler's own
front-door gate rejecting rank ≠ 1 was the only thing keeping matrices and higher
tensors out. With it lifted, elementwise bodies compile at **rank 2, 3 and 4**
with exact parity (max relative error 0.0 — both paths call the same kernels).
`Total` deliberately stays rank-1: at rank ≥ 2 it reduces only the *leading*
axis, which is a different operation.

### Elementwise fusion — implemented, correct, and off by default

`COMPILE_FUSE` lowers an elementwise chain to **one** counted loop over the flat
index, whose body is ordinary scalar bytecode reading through `A_LOAD` and
writing through `A_STORE`, instead of one full-length NDArray pass and one
temporary buffer per operation. Lowering it that way makes it rank-agnostic (a
flat index never looks at the shape), lets a trailing `Total` fold into an
accumulator in the same pass, and puts the scalar optimiser — including LICM —
inside the loop. Fusability is not analysed up front: the body is lowered
speculatively with array leaves bound to element registers and rolled back if the
ordinary scalar emitter cannot do it, so the fusable set is by construction
exactly the scalar-compilable set.

It is **off by default because it is not yet faster**: the loop runs the scalar
VM once per element, and at ~4 ns per bytecode instruction that costs more than
the temporary buffers it saves — 70 ns/element fused against 61 delegated for
`Total[Sin[v] Exp[-v] + Sqrt[v]]` at length 65536. The next step is block
strip-mining (each opcode processing a tile of ~64 elements in a vectorisable C
loop, so dispatch amortises 64× and temporaries stay in L1); the lowering here is
its foundation. Parity-tested at every rank, real and complex.

**A correctness rule this turned up:** fusion may only thread where the
interpreter threads, i.e. where the head is `Listable`. `Max[v, w]` is the trap —
it is *not* Listable, so the interpreter returns the single largest element and an
elementwise loop would quietly answer something else. `If`, `With` and `Sum` are
the same story.

### `NumericFunction` coverage is now audited by the build

When `compile_expr` cannot handle a head it returns `NULL`, the caller quietly
interprets, and the result is still correct — just an order of magnitude slower.
A coverage gap is therefore invisible: it looks exactly like a working fast path.

`tests/test_compile_coverage.c` enumerates every symbol carrying
`NumericFunction` and probes it by actually compiling `Head[x]` (and the 2- and
3-argument forms). `KNOWN_GAPS` lists the heads that legitimately do not compile
yet, each with its reason, and the audit fails in **both** directions: a head
outside the list that stops compiling is a regression, and a head inside it that
starts compiling means the list is stale.

Current state: **103 `NumericFunction` heads, 55 compile, 48 known gaps.** Most
remaining gaps are modules that compute in MPFR at ≥ 53 bits and round at the end
(`Zeta`, `PolyLog`, `Airy*`, `ExpIntegralEi`, …), so closing them means writing
genuinely new double-precision implementations rather than lifting an existing
path.

Running the audit immediately found three heads bailing even though the
interpreter evaluates them — each costing the whole surrounding body:

| Head | Was | Now |
|---|---|---|
| `Mod[x, y]` real | required two integers | uses the registered machine kernel (`Mod[2.5, 1.2]` → `0.1`) |
| `Quotient[x, y]` real | required two integers | `Floor[a/b]`, keeping the interpreter's *integer* result |
| `Arg[x]` real | deliberate "require complex" bail | widened to complex, reusing `ARG_C` (`0` for `x > 0`, `Pi` for `x < 0`) |

Each was checked against the interpreter before being added, so the compiled path
still never answers where the interpreter declines; all six new parity tests
agree to 0.0 relative error over 200–300 randomised trials.

### Call boundary

`cf[x]` no longer does a `malloc`/`free` per call for argument boxing (small
arities use stack storage), and an all-`Real` signature now takes the unboxed
`compiled_eval_real` entry point instead of always going through `CompileValue`.

### Tests

`tests/bench_compile.c` (new) is a performance gate whose primary assertion is
that **every benchmarked body actually compiled**, plus a machine-independent
ratio check that the optimiser never makes a body slower.
`tests/test_compile_coverage.c` (new) is the coverage audit.
`tests/test_compile.c` gains the optimiser A/B gate, any-rank parity, opt-in
fusion parity, and the `Listable` bail checks. All compile, CompiledFunction,
autocompile, NDSolve, NIntegrate, FindRoot and NDArray suites pass unchanged.

## `Compile[]` M5b — strip-mined array fusion (now on by default)

### Measurement correction, first

The `tests/` CMake build had no `CMAKE_BUILD_TYPE`, so it compiled with **no
optimisation flags at all**. Every absolute figure recorded in the M5 section
above came from `-O0` code. The build is now `Release`, and the *ratios* in that
section still hold (both sides were built identically) but the absolute numbers
were inflated — the dispatch-bound Horner body is **206 ns/call at `-O3`**, not
335.

### Strip mining

Fusion previously ran the scalar VM once per element, which cost more than the
temporary buffers it saved, so it shipped disabled. Each opcode now processes a
**tile of `VBLOCK` = 64 elements** in a loop shaped so the C compiler can
vectorise it: dispatch is amortised 64-fold, and every temporary is a 512-byte
tile that stays in L1 instead of a full-length heap buffer that page-faults.

At `-O3`, length 65536, fused against the delegated NDArray path:

| body | ns/element | speedup |
|---|---|---|
| `v^2 + 2 v + 1` | 2.3 | **3.4×** |
| `Total[v^2 + 2 v + 1]` | 2.8 | **3.0×** |
| `Total[v + v v]` | 1.7 | **2.4×** |
| `Total[Sin[v] Exp[-v] + Sqrt[v]]` | 12.9 | **1.9×** (libm-bound) |

Fusion is therefore **on by default**; `COMPILE_NO_FUSE` turns it off for A/B.

The lowering deliberately reuses the ordinary emitter rather than adding a second
one: tile-ness rides on the register number (the virtual-bank trick M3a already
used for array handles), and the four existing choke points — `binop`, `unop`,
`kern_unop`, `kern_binop` — swap in the tile form of whatever opcode the scalar
lowering picked. The vectorisable set is one table, not a parallel emitter that
could drift.

### Five latent type-inference bugs this exposed

`infer_type` dropped array-ness in five places: the unary math heads, two-argument
`Log`, one- and two-argument `ArcTan`, `Power` with a literal exponent, and the
binary-kernel path. Each computed the correct *element* type and then returned it
as a scalar. That was harmless while every array operation was delegated to the
ND layer — which chooses its own result dtype — and became two distinct faults as
soon as fusion started trusting these types: the wrong output buffer, and whole
bodies never being recognised as fusable at all. Fixing them is what took
`Total[Sin[v] Exp[-v] + Sqrt[v]]` from 1.0× (silently still delegated) to 1.9×.

### Three further correctness fixes

- **`Power` with an integer exponent** emits `POWI` directly rather than through
  `unop()`, so that site had to make the tile decision itself — otherwise a
  strip-mined `v^3` read the tile *pointer* as a double. A safety net in `ins_f`
  now turns any scalar opcode handed a tile register into a clean bail instead of
  a wrong answer.
- **A complex-to-real tile op** (`Abs`, `Re`, `Im`, `Arg`) may not write into its
  operand's register: it reads through `double _Complex*` and writes through
  `double*`, so the compiler is entitled to assume the two cannot overlap.
  Element-at-a-time the overlap is benign — which is exactly what makes it a bug
  that appears only once the loop vectorises.
- **The fused store honours the element-type promise.** A real-typed program that
  produced a non-finite element is precisely where the interpreter would have
  gone complex, so the call fails to the interpreter rather than handing back a
  real array full of `NaN`. The check is accumulated branchlessly and tested once
  per tile, so it does not break vectorisation.

### One place fusion had to be made *less* capable

The interpreter leaves `ArcTan[NDArray, NDArray]` **completely unevaluated** — the
ND binary kernels are defined as one array plus one broadcast scalar, so there is
no array-by-array path. A fused loop would happily compute it. Answering where
the interpreter declines is the same class of bug as answering differently, so
`fuse_listable` refuses a two-argument node with a registered binary kernel when
both operands are arrays. `Log[b, x]` is the documented exception, and not an
arbitrary one: it lowers to the arithmetic identity `Log[x]/Log[b]`, so the
interpreter threads it array-by-array too.

### Tests

- **340 body × length combinations** across lengths straddling the tile boundary
  (1, 2, 3, 7, 31, 63, 64, 65, 66, 127, 128, 129, 255, 256, 257, 1000, 4097). The
  partial final tile is the one thing a length-64 test can never reach.
- **21 bodies** checked fused against delegated.
- **120 randomised elementwise trees** — Listable heads only, each guaranteed to
  reach an array leaf, since a body of pure scalars is not an array program and a
  bare argument array cannot legally be the result.
- **200 repeated calls** at varying lengths: the frame and tile bank are reused
  across calls, so a stale tile would only ever show up on the second one.
- `compile_tests` is `leaks`-clean and **ASan + UBSan clean**.
