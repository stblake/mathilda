# Changelog: week of 2026-07-27 (Mon) – 2026-08-02 (Sun)

Feature additions and fixes recorded during this week.

## Auto-compilation of Plot / Plot3D / Table / NIntegrate / FindRoot (2026-07-27)

The numeric builtins now transparently use the `Compile[]` bytecode engine as a
fast path: each compiles its held body once as a function of its sample
variable(s) and evaluates it over machine numbers with no `Expr` allocation,
instead of running the full symbolic evaluator at every one of the thousands of
sample points. Uncompilable bodies (any construct outside the compilable subset,
e.g. `Zeta`) transparently keep the interpreter path, so results are unchanged.

New shared adapter `src/compile/autocompile.{c,h}`: `autocompile_new(body,
vars, nvars)` (→ `NULL` if uncompilable), `autocompiled_eval_real` /
`autocompiled_eval_complex`, `autocompiled_free`. The header is self-contained
(no `<complex.h>`/`compile.h` leak — `double _Complex` is a builtin type) so it
never pollutes callers with the `I` macro.

Correctness rule shared by the callers: a compiled *real* program returns a
non-finite value exactly where the interpreter would instead produce a *complex*
result (e.g. `Sqrt` of a negative). Callers that exclude non-real points (Plot)
drop it; callers that need the contribution (NIntegrate, FindRoot, real-iterator
Table) fall back to the interpreter at that single point.

- **Plot / Plot3D** — compiled in the per-curve/per-surface setup; a non-finite
  or non-real sample excludes the point, matching the existing behaviour
  (`Plot[Sqrt[x], {x,-1,1}]` still drops the negative half). **~215×** on a
  400-point 2-D curve; **~11×** on an 80×80 surface.
- **Table** — ONLY the inexact (machine-real) iterator branch, where the
  interpreter already yields machine reals; exact iterators
  (`Integer`/`BigInt`/`Rational`) and symbolic bodies are untouched and
  bit-for-bit unchanged (`Table[i^2,{i,1,5}]`, `Table[2^i,…]` BigInt,
  `Table[Sin[i],…]` symbolic). Per-element interpreter fallback keeps
  `Table[Sqrt[x],{x,-1.,1.,1.}]` complex. **~128×** on a 50k-element real table.
- **NIntegrate** — the 1-D machine-precision integrand (`ni_eval_at`), for the
  finite / half-line / whole-line real cases. Complex-contour abscissae and the
  MPFR path are untouched; a complex-valued integrand falls back per sample
  (`NIntegrate[Sqrt[x-1],{x,0,2}] → 2/3 + (2/3)I`). **~353×** on a batch of 50
  integrals. Fixed a latent bug the change exposed: the oscillatory
  amplitude/phase decomposition value-copies the sampler context and swaps its
  body, which must reset the compiled program (`ni_ctx_rebody`).
- **FindRoot** — the scalar, machine-precision, real function (Newton / Secant /
  Brent, and the finite-difference-derivative path used when `D` is inert, e.g.
  `Zeta'`). Complex-root, MPFR, and multivariate-system solves keep the
  interpreter. **~19×** on 5000 scalar solves.

Tests: `tests/test_autocompile.c` — end-to-end parity through the real builtins,
non-real exclusion / per-point fallback, uncompilable fallback, and the
oscillatory regression. All `leaks`-clean. MPFR paths untouched throughout.

### Follow-up: multi-dimensional NIntegrate and FindRoot systems

- **Multi-D NIntegrate** — the multi-dimensional machine chokepoint
  `ni_mc_sample` (shared by the Genz–Malik cubature and Monte-Carlo engines) now
  compiles the body once as `f(v_1..v_d)` and writes the complex result straight
  into the sample slot (no boxing). A box where the integrand goes complex (e.g.
  `Sqrt[x+y-1]` over the unit square) still contributes its imaginary part via the
  per-point interpreter fallback. **~504×** on a 2-D 500k-point Monte-Carlo
  integral.
- **FindRoot systems** — `fr_run_newton_system_real` compiles each component
  `f_i` and each symbolic Jacobian entry `D[f_i, x_j]` as functions of all
  variables, used at the residual/Jacobian/step-check evaluation sites via a
  shared `fr_try_compiled` helper. An uncompilable component or Jacobian row
  (e.g. `LogGamma`, whose derivative `PolyGamma` is evaluable) stays on the
  interpreter while the rest runs compiled; the linear solve is unchanged.
  **~6.9×** on a 2×2 nonlinear system. (Systems with an *inert* Jacobian entry,
  e.g. `Zeta'`, still fail as before — a pre-existing limitation.)

## Compile engine M3a — rank-1 machine arrays (2026-07-27)

The `Compile[]` bytecode engine was scalar-only. It now carries **rank-1 machine
vectors** as a first-class value category, delegating every buffer operation to
the existing NDArray subsystem, so a compiled program can take `NDArray`
arguments, compute over whole buffers, and return an `NDArray` or reduce to a
scalar — with no `Expr` allocation per element and no evaluator round-trip per
operation.

**Type lattice.** `CompileType` now packs array types into the same integer as
the scalars (`CT_ARR + 4*(rank-1) + elem`), so every field that already carried a
`CompileType` — inference results, register types, declared argument types —
carries array types with no parallel plumbing. New helpers `CT_ARRAY(elem,rank)`
/ `CT_IS_ARRAY` / `CT_ELEM` / `CT_RANK`, plus a `CT_ERR` sentinel that makes the
enum's underlying type signed (so the existing `(int)t < 0` checks are well
defined). `CompileValue` gained an `Expr* a` member: an array argument is
**borrowed**, an array result is **owned by the caller**.

**Compilable over arrays.** `Plus`, `Times`, `Subtract`, `Minus`, `Divide`,
`Power` (vector⊕vector, vector⊕scalar broadcast, and scalar^vector); every
elementary and special function with a registered ND unary kernel (`Sin`, `Exp`,
`Log`, `Gamma`, `Abs`, `Re`/`Im`/`Arg`/`Conjugate`, `Floor`/`Ceiling`/`Round`,
…); the two-argument ND binary kernels (`Log[b,v]`, `ArcTan[v,y]`, `BesselJ[n,v]`,
`Mod`); and the array→scalar reductions `Total[v]` and `Length[v]`, which let
whole expressions such as `Total[(v - Total[v]/Length[v])^2]/Length[v]` compile
end to end. Real and complex (`complex64`) element types both work.

**New C entry point.** `ndred_total_all(a)` in `ndreduce.h` — full reduction of
an NDArray to a scalar, taking the *array* rather than the enclosing call, so a
caller that already holds the operand needs no wrapper call node. Shares
`ndred_total`'s summation, so the rounding is identical.

**Correctness contract**, lifted unchanged from the scalar engine: a program that
promised a real element type but whose buffer would leave the real axis (e.g.
`Sqrt[v]` with a negative entry, which the ND layer promotes to a complex dtype)
fails the call, and the caller falls back to the interpreter — it never returns a
wrong-typed result. Shape mismatches, allocation failures, and kernels that
decline an element fail the same way.

**Lifetime.** Array registers live in their own contiguous bank above the scalar
registers, so a slot is either always-array or never-array and teardown cannot
mistake a `double` for a pointer. Operand frees are encoded in the consuming
instruction's flag bits (which occupy what was padding — `Instr` did not grow),
so they happen *after* the operand is read and the result may still reuse an
operand's register. Every array register is NULLed before a call (the frame is
reused across calls) and swept afterwards, including on the abort path.

**Not yet in the subset** (each bails cleanly to the interpreter rather than
aliasing a handle): array-valued `If` branches, `With`/`Module` locals, `Sum`
accumulators and `Nest` state — all of which would need to *copy* an array
handle where the engine only moves one — a bare array argument as the whole
result, and rank ≥ 2. The user-facing `Compile[]` argspec has no array form yet,
so this is reachable from C (`compile_expr` with a `CT_ARRAY(...)` argument
type), not yet from the REPL.

**Measured.** Parity with the interpreter is *exact* (max relative error 0.0)
across 34 array bodies, because both paths run the same ND kernels. The speedup
is therefore only the per-operation evaluator round-trip that the compiled
program avoids: **2.3× at length 16, 1.0× at length 4096** for
`Total[Sin[v] Exp[-v] + Sqrt[v]]`. Large-vector gains need loop *fusion* (one
buffer pass for a chain of elementwise ops instead of one per operation), which
is M3b work, not delegation.

Tests: `tests/test_compile.c` — 34 parity bodies (real + complex vectors),
7 must-bail cases, the real-element runtime contract, 5000-call frame reuse, an
array temporary freed per iteration inside a `Do` loop, and the two performance
points. `leaks`-clean and ASan-clean.

## Compile engine — counted iterators, global folding, callee inlining

Four fixes to the compiled fast path, found by profiling a Newton-fractal
benchmark that ran an order of magnitude slower than expected.

**`Do` accepted only `{i, lo, hi}`.** Every other counted spelling the
interpreter supports made the *whole* surrounding `Compile[]` bail, so the body
ran in the interpreter — a silent 37× cost, not a small one. `Do`, `Sum` and
`Product` now share one spec parser matching `src/iter.c`:

| spec | meaning |
|------|---------|
| `n`, `{n}` | repeat n times, binding no iterator symbol (`Do` only) |
| `{i, hi}` | `i = 1, …, hi` |
| `{i, lo, hi}` | `i = lo, …, hi` |
| `{i, lo, hi, di}` | step `di`, a nonzero integer literal (loop test flips for `di < 0`) |

`Sum`/`Product` deliberately reject the bare-count forms because the interpreter
does (`sum.c`, `product.c`); the compiled path must not answer where the
interpreter declines. List iteration and non-literal steps bail as before.

**Nested `Table` could not compile its inner body.** `Table[f, {y,…}, {x,…}]`
desugars to nested `Table`s, and the inner one sees `y` only as a symbol-table
OwnValue, which made it an uncompilable free symbol. `compile_expr_ex` gained
`COMPILE_FOLD_GLOBALS`, resolving such a symbol to the machine number it
currently holds. It is opt-in and used *only* by `autocompile.c`, whose programs
live and die inside one builtin call; a user `Compile[]` object outlives its
defining scope, so it keeps bailing, which stays correct however the global is
later reassigned. Any body that could *mutate* a global mid-iteration (a `Set`
to a non-local) already bails, so a folded constant can never go stale.

**`Table` element types.** The compiled path routed every result through a
`double`, so an integer-valued body (`If[…, 1, 2]`, `Round[x]`) came back as
`1.` instead of `1`. New `autocompiled_eval_boxed` returns an Expr of the
result's own type; `Table` uses it. `Plot`/`NIntegrate`/`FindRoot` keep the
unboxed real path.

**Calling a `CompiledFunction` from a compiled body** previously bailed, costing
an evaluator round-trip per point (~2.3 µs of a 3.1 µs call — 72% of runtime).
The compiler now inlines the callee: arguments are lowered in the caller's
environment and coerced to the declared parameter types, then the body is
lowered with *only* the parameters in scope, so a caller argument sharing a name
with a callee global cannot capture it. Arity mismatch, array-typed parameters
and self-reference (depth-capped) all bail to the interpreter.

Measured on `Table[newt[x + I y, 25], {y,-1,1,2./199}, {x,-1,1,2./199}]`
(200 × 200 × 25 complex Newton steps): **4.45 s → 0.046 s (97×)**. The same
expression written inline without `Compile[]` now also fully compiles, at
0.042 s, and the two agree exactly.

`While` and `For` bodies go through the same paths and were verified alongside
`Do` — wrapped in `Compile[]`, inline in an auto-compiled `Table`, and as an
inlined callee — with identical results and timings.

Tests: `tests/test_compile.c` — 9 iterator spellings, exact integer counts, the
two must-bail forms, and a **multi-statement loop body** (four locals of three
types, five statements per iteration, a two-armed `If` mutating state in both
arms) written as `Do`/`While`/`For`: the three must agree *bitwise* with each
other and match an independent C reference (200 random points, max rel err
9.2e-15). `tests/test_autocompile.c` — result-type preservation, nested-`Table`
folding, fold freshness and the mutating-body fallback, 8 inlining cases each
checked against an interpreted twin (a DownValue never compiles, so a capture
bug shows up as a mismatch), and the same multi-statement body driven through
`Table` all three ways plus as an inlined callee.

One test deserves note: `test_multiline_bodies_really_compile` asserts, via the
same `autocompile_new` the builtin uses, that each loop body *actually compiles*.
Every parity check would otherwise pass vacuously if nothing compiled — agreement
with the interpreter is trivially true when you are the interpreter. Verified by
sabotage: disabling `COMPILE_FOLD_GLOBALS` leaves the three-way parity assertions
green (all three fall back and agree with each other) while this guard fails with
`multi-line Do body did not compile`. It runs first, before the behavioural
tests. `leaks`-clean.

## `Compile[]` M5 — optimising code generation, coverage audit, any-rank arrays

Four separable pieces of work on the numeric compiler (`src/compile/`).

> **Read the M5b section below before quoting any number here.** These were
> measured in a `tests/` build that had no `CMAKE_BUILD_TYPE` and so compiled at
> `-O0`. The ratios hold (both sides were built identically); the absolute
> figures were inflated. At `-O3` the dispatch-bound Horner baseline is
> **295 ns/call for 80 arithmetic operations (3.7 ns/op)**, and the work below
> takes it to **~200 ns/call (2.5 ns/op), ~1.45×** — not the 2.0× the `-O0`
> numbers suggested.

### Lazy operand addressing in the VM

`NEXT()` recomputed all three operand pointers for every instruction regardless
of which the opcode used — the hottest ops (`ADD_R`, `MUL_R`) read two and the
unary ops read one, so most of that work was wasted on the common case. Operands
are now addressed at the point of use, letting the C compiler fold the address
computation into the load.

**649 → 427 ns/call (1.53×)** on Horner *at `-O0`*; at `-O3` the same change is
worth appreciably less, because the C compiler was already folding some of that
address arithmetic. No behavioural change.

### A bytecode optimiser (`src/compile/optimize.c`, new)

The emitter lowers each `Expr` node independently and previously had **no middle
end at all** — no constant folding, no dead-code elimination, no loop-invariant
hoisting. There is now a pass pipeline between emission and the finished program:

- `compile_internal.h` extracts `Slot`/`Instr`/the opcode enum so the optimiser
  is its own translation unit. `OPLIST` now carries a KIND per opcode and drives
  three things that could previously drift apart: the opcode enum, the VM's
  computed-goto jump table, and the optimiser's instruction-property table.
- CFG construction and real backward liveness, then per-block value numbering
  (constant folding, CSE, copy propagation), liveness-driven dead-code
  elimination, and loop-invariant code motion over natural loops.
- Array registers and the impure array opcodes are excluded throughout: their
  ownership lives in instruction flags, not in the dataflow the scalar passes
  reason about.
- `OP_LOOP` folds increment, test and branch into one instruction — a counted
  loop otherwise spends four instructions per iteration on control alone.

Horner **427 → 335 ns/call** at `-O0`. Measured properly at `-O3`, the optimiser
alone is worth **1.33×** on Horner, **1.29×** on `Nest` and **1.25×** on
Newton/`While` (LICM), and the whole of M5 takes the dispatch-bound body from
**295 → ~200 ns/call (~1.45×)**.

`COMPILE_NO_OPT` is the A/B switch. The correctness gate is **bitwise identity**,
not accuracy: 18 bodies compiled both ways must agree bit for bit over a
randomised sweep (compared with `memcmp`, so `NaN` must equal `NaN` and `-0.0`
must differ from `+0.0`). A pass that reassociated a sum or contracted a
multiply-add would still look accurate while breaking the engine's stated parity
contract with the interpreter.

### `NDArray` of any rank

The delegated NDArray path was already rank-general; the compiler's own
front-door gate rejecting rank ≠ 1 was the only thing keeping matrices and higher
tensors out. With it lifted, elementwise bodies compile at **rank 2, 3 and 4**
with exact parity (max relative error 0.0 — both paths call the same kernels).
`Total` deliberately stays rank-1: at rank ≥ 2 it reduces only the *leading*
axis, which is a different operation.

### Elementwise fusion — implemented, correct, and off by default

`COMPILE_FUSE` lowers an elementwise chain to **one** counted loop over the flat
index, whose body is ordinary scalar bytecode reading through `A_LOAD` and
writing through `A_STORE`, instead of one full-length NDArray pass and one
temporary buffer per operation. Lowering it that way makes it rank-agnostic (a
flat index never looks at the shape), lets a trailing `Total` fold into an
accumulator in the same pass, and puts the scalar optimiser — including LICM —
inside the loop. Fusability is not analysed up front: the body is lowered
speculatively with array leaves bound to element registers and rolled back if the
ordinary scalar emitter cannot do it, so the fusable set is by construction
exactly the scalar-compilable set.

It is **off by default because it is not yet faster**: the loop runs the scalar
VM once per element, and at ~4 ns per bytecode instruction that costs more than
the temporary buffers it saves — 70 ns/element fused against 61 delegated for
`Total[Sin[v] Exp[-v] + Sqrt[v]]` at length 65536. The next step is block
strip-mining (each opcode processing a tile of ~64 elements in a vectorisable C
loop, so dispatch amortises 64× and temporaries stay in L1); the lowering here is
its foundation. Parity-tested at every rank, real and complex.

**A correctness rule this turned up:** fusion may only thread where the
interpreter threads, i.e. where the head is `Listable`. `Max[v, w]` is the trap —
it is *not* Listable, so the interpreter returns the single largest element and an
elementwise loop would quietly answer something else. `If`, `With` and `Sum` are
the same story.

### `NumericFunction` coverage is now audited by the build

When `compile_expr` cannot handle a head it returns `NULL`, the caller quietly
interprets, and the result is still correct — just an order of magnitude slower.
A coverage gap is therefore invisible: it looks exactly like a working fast path.

`tests/test_compile_coverage.c` enumerates every symbol carrying
`NumericFunction` and probes it by actually compiling `Head[x]` (and the 2- and
3-argument forms). `KNOWN_GAPS` lists the heads that legitimately do not compile
yet, each with its reason, and the audit fails in **both** directions: a head
outside the list that stops compiling is a regression, and a head inside it that
starts compiling means the list is stale.

Current state: **103 `NumericFunction` heads, 55 compile, 48 known gaps.** Most
remaining gaps are modules that compute in MPFR at ≥ 53 bits and round at the end
(`Zeta`, `PolyLog`, `Airy*`, `ExpIntegralEi`, …), so closing them means writing
genuinely new double-precision implementations rather than lifting an existing
path.

Running the audit immediately found three heads bailing even though the
interpreter evaluates them — each costing the whole surrounding body:

| Head | Was | Now |
|---|---|---|
| `Mod[x, y]` real | required two integers | uses the registered machine kernel (`Mod[2.5, 1.2]` → `0.1`) |
| `Quotient[x, y]` real | required two integers | `Floor[a/b]`, keeping the interpreter's *integer* result |
| `Arg[x]` real | deliberate "require complex" bail | widened to complex, reusing `ARG_C` (`0` for `x > 0`, `Pi` for `x < 0`) |

Each was checked against the interpreter before being added, so the compiled path
still never answers where the interpreter declines; all six new parity tests
agree to 0.0 relative error over 200–300 randomised trials.

### Call boundary

`cf[x]` no longer does a `malloc`/`free` per call for argument boxing (small
arities use stack storage), and an all-`Real` signature now takes the unboxed
`compiled_eval_real` entry point instead of always going through `CompileValue`.

### Tests

`tests/bench_compile.c` (new) is a performance gate whose primary assertion is
that **every benchmarked body actually compiled**, plus a machine-independent
ratio check that the optimiser never makes a body slower.
`tests/test_compile_coverage.c` (new) is the coverage audit.
`tests/test_compile.c` gains the optimiser A/B gate, any-rank parity, opt-in
fusion parity, and the `Listable` bail checks. All compile, CompiledFunction,
autocompile, NDSolve, NIntegrate, FindRoot and NDArray suites pass unchanged.

## `Compile[]` M5b — strip-mined array fusion (now on by default)

### Measurement correction, first

The `tests/` CMake build had no `CMAKE_BUILD_TYPE`, so it compiled with **no
optimisation flags at all**. Every absolute figure recorded in the M5 section
above came from `-O0` code. The build is now `Release`, and the *ratios* in that
section still hold (both sides were built identically) but the absolute numbers
were inflated — the dispatch-bound Horner body is **206 ns/call at `-O3`**, not
335.

### Strip mining

Fusion previously ran the scalar VM once per element, which cost more than the
temporary buffers it saved, so it shipped disabled. Each opcode now processes a
**tile of `VBLOCK` = 64 elements** in a loop shaped so the C compiler can
vectorise it: dispatch is amortised 64-fold, and every temporary is a 512-byte
tile that stays in L1 instead of a full-length heap buffer that page-faults.

At `-O3`, length 65536, fused against the delegated NDArray path:

| body | ns/element | speedup |
|---|---|---|
| `v^2 + 2 v + 1` | 2.3 | **3.4×** |
| `Total[v^2 + 2 v + 1]` | 2.8 | **3.0×** |
| `Total[v + v v]` | 1.7 | **2.4×** |
| `Total[Sin[v] Exp[-v] + Sqrt[v]]` | 12.9 | **1.9×** (libm-bound) |

Fusion is therefore **on by default**; `COMPILE_NO_FUSE` turns it off for A/B.

The lowering deliberately reuses the ordinary emitter rather than adding a second
one: tile-ness rides on the register number (the virtual-bank trick M3a already
used for array handles), and the four existing choke points — `binop`, `unop`,
`kern_unop`, `kern_binop` — swap in the tile form of whatever opcode the scalar
lowering picked. The vectorisable set is one table, not a parallel emitter that
could drift.

### Five latent type-inference bugs this exposed

`infer_type` dropped array-ness in five places: the unary math heads, two-argument
`Log`, one- and two-argument `ArcTan`, `Power` with a literal exponent, and the
binary-kernel path. Each computed the correct *element* type and then returned it
as a scalar. That was harmless while every array operation was delegated to the
ND layer — which chooses its own result dtype — and became two distinct faults as
soon as fusion started trusting these types: the wrong output buffer, and whole
bodies never being recognised as fusable at all. Fixing them is what took
`Total[Sin[v] Exp[-v] + Sqrt[v]]` from 1.0× (silently still delegated) to 1.9×.

### Three further correctness fixes

- **`Power` with an integer exponent** emits `POWI` directly rather than through
  `unop()`, so that site had to make the tile decision itself — otherwise a
  strip-mined `v^3` read the tile *pointer* as a double. A safety net in `ins_f`
  now turns any scalar opcode handed a tile register into a clean bail instead of
  a wrong answer.
- **A complex-to-real tile op** (`Abs`, `Re`, `Im`, `Arg`) may not write into its
  operand's register: it reads through `double _Complex*` and writes through
  `double*`, so the compiler is entitled to assume the two cannot overlap.
  Element-at-a-time the overlap is benign — which is exactly what makes it a bug
  that appears only once the loop vectorises.
- **The fused store honours the element-type promise.** A real-typed program that
  produced a non-finite element is precisely where the interpreter would have
  gone complex, so the call fails to the interpreter rather than handing back a
  real array full of `NaN`. The check is accumulated branchlessly and tested once
  per tile, so it does not break vectorisation.

### One place fusion had to be made *less* capable

The interpreter leaves `ArcTan[NDArray, NDArray]` **completely unevaluated** — the
ND binary kernels are defined as one array plus one broadcast scalar, so there is
no array-by-array path. A fused loop would happily compute it. Answering where
the interpreter declines is the same class of bug as answering differently, so
`fuse_listable` refuses a two-argument node with a registered binary kernel when
both operands are arrays. `Log[b, x]` is the documented exception, and not an
arbitrary one: it lowers to the arithmetic identity `Log[x]/Log[b]`, so the
interpreter threads it array-by-array too.

### Tests

- **340 body × length combinations** across lengths straddling the tile boundary
  (1, 2, 3, 7, 31, 63, 64, 65, 66, 127, 128, 129, 255, 256, 257, 1000, 4097). The
  partial final tile is the one thing a length-64 test can never reach.
- **21 bodies** checked fused against delegated.
- **120 randomised elementwise trees** — Listable heads only, each guaranteed to
  reach an array leaf, since a body of pure scalars is not an array program and a
  bare argument array cannot legally be the result.
- **200 repeated calls** at varying lengths: the frame and tile bank are reused
  across calls, so a stale tile would only ever show up on the second one.
- `compile_tests` is `leaks`-clean and **ASan + UBSan clean**.

## `Compile[]` M5c — CSE, per-call frames, and compiled-to-compiled calls

### CSE, moved to the Expr level

The bytecode optimiser has had a value-numbering CSE since M5 and it **almost
never fired**. The reason was structural rather than a bug in the pass:
`binop`/`unop` pop their operands *before* allocating the destination, so a
computation normally writes into one of its own operand registers (`SIN_R t1, t1`).
The value-number entry keyed on that register is invalidated by the very
instruction that created it, and the value is genuinely gone — no bytecode-level
pass can recover it without first changing how registers are allocated.

Doing it on the `Expr` sidesteps that, and is where the information is richest
anyway. A chosen subtree is computed **once** into a register reserved *below*
the temp stack (by raising `nlocals`) — the same discipline that already protects
arguments, so neither temp allocation nor any of the explicit `temp_top` resets
in the loop lowerings can reach it. Occurrences are keyed on the `Expr` pointer,
because the planner walks the very tree the emitter will walk.

`Sin[x y] + Cos[x y] Sin[x y] + Sin[x y]^3`: 13 → 10 instructions,
**37.0 → 25.0 ns/call (1.48×)**. Both `x y` and `Sin[x y]` are hoisted;
candidates are emitted smallest-first, so the larger picks up the smaller's
register rather than recomputing it.

Eligibility is deliberately narrow, and every clause earns its place:

- **every free symbol must be an argument.** A subtree mentioning a loop variable
  or a `With`/`Module` local cannot be hoisted to program entry, where that name
  is not bound yet. Loop-*invariant* hoisting is a different job, and the
  optimiser's LICM pass already does it.
- **no control flow and no assignment** anywhere inside, so evaluating it early
  and unconditionally is observationally identical.
- **scalar-typed only**: an array value carries ownership, and a tile belongs to
  the fused loop that created it.

`COMPILE_NO_CSE` is the A/B switch, and the bitwise-identity harness now runs its
whole corpus once per pass — **50 body/pass combinations** must agree bit for bit
with and without each of CSE and the optimiser.

### Frames come from the C stack

The frame used to be a single buffer owned by the `CompiledProgram` and mutated
through a `const CompiledProgram*`: a program was neither reentrant nor
thread-safe, because two live calls shared one register file and (after M5b) one
set of tile buffers. A C-stack frame is per-thread and naturally nested, so both
properties fall out with no arena to own, grow or free — and with no allocation
at all for any program fitting the fixed 512-slot buffer, which is every
realistic one. Tile storage moved into the frame for the same reason.

### `OP_CALL`

A compiled callee that is not inlined is now **called**: machine values in
consecutive registers, its own frame, no `Expr` and no evaluator round-trip.
Previously inlining was the only mechanism, and where the inliner declined — its
depth cap, the scope budget — the *whole body* bailed to the interpreter.

Inlining remains the default, being the faster of the two (no frame, no argument
copy). The choice is now a cost model: a callee larger than `INLINE_MAX_INSTRS`
is called instead, because past that size pasting it in at every use site costs
more in code size and compile time than the call costs at run time.

**Precisely what this does not do:** it does not make a *self*-recursive
`Compile[]` compile. `Compile[]` does not fold globals — by design, since the
object outlives its defining scope — so a body cannot resolve the very symbol it
is about to be assigned to. What `OP_CALL` fixes is deep and awkward call shapes
bailing wholesale.

### A real optimiser bug this exposed

In the value-numbering pass, an instruction writing register `d` cleared every
alias *pointing at* `d` but not `d`'s own stale alias. So `MOVE d <- a` followed
by anything that writes `d` left `alias[d]` still pointing at `a`, and a later
read of `d` was copy-propagated back to `a` — the value from *before* the write.
Every other opcode happened to re-establish `alias[d]` immediately afterwards; a
`CALL`, which writes `d` without being a `MOVE`, is what made it visible.

### Tests

Eleven nested applications of a compiled callee, checked against an interpreted
`DownValue` twin (which never compiles, and is therefore an honest reference) —
max relative error 2e-16 over 100 points. The same chain inside a `Do` loop,
where the caller's frame is live across every re-entry: the test the old
per-program frame could not have passed. `compile_tests` is `leaks`-clean and
ASan + UBSan clean.

Two *test-harness* bugs were found and fixed on the way, both of which had made
the new tests report failures that were not in the engine: a `snprintf` with a
`%.17g` format and no argument; and, once that was fixed, the fact that a
17-digit literal is read by Mathilda as an **arbitrary-precision** number, so the
reference computed in MPFR and came back as `EXPR_MPFR` rather than a machine
`Real`. References are now built by substitution rather than by formatting a
literal — the same lesson the array tests already encode.

## `Compile[]` M5d — array argspec, and a Plot3D leak

### `Compile[{{v, _Real, r}}, …]`

Until now the whole array engine — fusion, any-rank, the reductions — was
reachable only from C: `Compile[]`'s argspec parser accepted `_Real`, `_Integer`
and `_Complex` but had no rank, so an array parameter could not be declared at
all. It now takes the three-element form the Wolfram Language uses, with the
element type restricted to `Real` or `Complex` (the packed buffer formats are
float and complex only — there is no integer dtype to hold a rank-*r* Integer
array), and rank bounded by `CT_MAX_RANK`.

```
f = Compile[{{v, _Real, 1}}, v^2 + 2 v + 1];   f[{1., 2., 3.}]   → {4., 9., 16.}
g = Compile[{{m, _Real, 2}}, Sin[m] + 1];      g[{{0., 1.}}]     → {{1., 1.84147}}
h = Compile[{{v, _Real, 1}}, Total[v^2]];      h[{1., 2., 3.}]   → 14.
```

A plain nested `List` argument is packed into an `NDArray` at the boundary and
that temporary is released after the call; an `NDArray` passed in directly is
**borrowed** and left alone.

**The result kind follows the argument kind.** Given `List`s the function returns
a `List`; given `NDArray`s it returns an `NDArray`. This is not cosmetic: the
interpreter fallback threads a `List` argument and returns a `List`, so returning
a packed array would mean the compiled path answering with a *different head*
from the fallback for the very same input — visible to the user the moment one
element is symbolic and the fast path declines.

Shapes that must not take the fast path all fall back and stay correct: a ragged
list (cannot be packed), a rank mismatch, and a symbolic element. Malformed
argspecs (`{v, _Real, 0.5}`, `{v, _Integer, 2}`) leave `Compile[…]` unevaluated
rather than guessing.

### Plot3D: primitives leaked on the no-surface path

`build_surface_primitives` returns `NULL` when no cell was filled, and freed the
primitive *array* without freeing the `Expr`s in it. `any` is set only by the
polygon-fill passes, but the per-surface colour directive, the mesh lines and the
`ExclusionStyle` edges are all pushed independently of it — so a plot producing
those but no filled cell (every cell clipped away by `RegionFunction`, or every
sample excluded) leaked every primitive it had built.

Found while auditing the compiler work for leaks: `autocompile_tests` reported
one more leaked node than the pre-change baseline, which turned out to be this
path being reached slightly differently rather than anything the compiler did.

### Machine kernels for the exponential-integral family

Nine more `NumericFunction` heads now compile — **coverage 55 → 64 of 103**.

`ExpIntegralEi`, `LogIntegral`, `SinIntegral`, `CosIntegral`, `SinhIntegral`,
`CoshIntegral` and `Sinc` had no double-precision path at all: their modules
compute in MPFR and round at the end, which is right for arbitrary-precision work
but left the NDArray element-wise fast path and the `Compile[]` VM stuck on a
degrade sentinel — and in the compiler's case that meant the *whole surrounding
body* fell back to the interpreter. `src/special_functions/expint_machine.c`
provides real double implementations (series where they are well conditioned,
modified-Lentz continued fractions and asymptotic forms beyond).

`InverseErf` and `InverseErfc` were free: `inverf.c`/`inverfc.c` already
contained pure double algorithms that were simply never exposed or registered.

Every one is registered real-closed with a `real` function only, and **declines**
for an argument whose true value is complex or infinite — `Ci`, `Chi` and `li` of
a negative argument, `Ei` at zero, `li` at one, `InverseErf` at ±1. That is the
engine's standing contract: a real-typed fast path gives way exactly where the
interpreter would leave the real axis. It works end to end —
`CosIntegral[NDArray[{-1., 2.}]]` degrades to the List path and returns the
complex value, rather than the array path inventing a real one.

Accuracy is verified against each module's own MPFR implementation, not asserted:
max relative error ≤ 1.7e-15 (a few ulps) over 300–400 randomised points per
function, plus a chained body and twelve out-of-domain arguments that must all
decline.

One subtlety worth recording: `li(0)` is 0 by the limit, but the interpreter
answers `Indeterminate`, so the machine kernel declines there too rather than
being the only path that produces a number.

### More machine kernels — coverage 64 → 77 of 103

`src/expint_machine.*` grew into `src/special_functions/sf_machine.*` and gained
double implementations for **Erfi** (all-positive Maclaurin series, so no
cancellation, with an asymptotic tail), **ProductLog** (Halley), **FresnelC** /
**FresnelS**, **PolyGamma** (digamma by recurrence + asymptotic, reflection below
zero), **HarmonicNumber**, **Zeta** (Euler–Maclaurin above the critical strip,
the functional equation below), **HurwitzZeta**, and the real continuations of
**Fibonacci** and **LucasL** — all matching their MPFR implementations to machine
precision over 200–400 randomised points each.

`PolyGamma` had to be a **binary** kernel even though it is usually written
unary: the evaluator canonicalises `PolyGamma[x]` to `PolyGamma[0, x]` before
anything downstream sees it. `psi^(n)` for `n >= 1` comes from
`(-1)^(n+1) n! zeta(n+1, x)`, which is why `HurwitzZeta` came along for free.

**`UnitStep`, `Clip` and `Rescale` are lowered by hand rather than registered**,
because for these the *result type* is the whole difficulty:

- `UnitStep[0.5]` is the Integer `1`, not `1.` — a real-valued kernel would
  answer with a different head from the interpreter. A comparison already leaves
  0/1 in the integer half of the slot, so the lowering is the comparison, typed
  `CT_INT`.
- `Clip` and `Rescale` take a *list* of bounds, which no kernel signature can
  express; a literal two-element `List` is destructured in the lowering. Both are
  gated on the bounds being Real, because with exact bounds the interpreter
  returns an exact value where it clips (`Clip[5, {1, 3}]` is the Integer 3) and
  a Real where it does not — no single compiled type matches that.

### Two bugs found by the new parity tests

**`ProductLog` was wrong on `[0.35, 1/e]`.** The seed-selection thresholds left a
gap: the Maclaurin seed covered `|z| < 0.35` and the next one only applies once
`|log z| < 1`, i.e. `|z| > 1/e = 0.3678…`. Arguments in between fell through to
the *asymptotic* seed `L1 - log L1`, and with `log z` negative there `log(log z)`
is complex, so the iteration converged to something that is not a Lambert W value
at all — `ProductLog[0.35]` returned `-2.6422`, whose `w e^w` is `-0.188`, not
`0.35`. The bound is now 0.5, leaving margin on both sides. This is an
interpreter bug, not a compiler one; the compiled path disagreeing with it is
what surfaced it.

**Two tests used `Zeta` as their example of an uncompilable head** — in
`test_compile.c` and `test_ndsolve_compile.c`. Now that `Zeta` compiles they
failed, which is the coverage ratchet working: an assumption written into a test
in 2026-07 stopped being true and said so.

### Pochhammer, Binomial, LegendreP — coverage 77 → 80 of 103

`Pochhammer[a, n]` = `Gamma(a+n)/Gamma(a)` (an exact product for small
non-negative integer `n`, otherwise through `lgamma`), `Binomial[n, k]` through
the same route, and `LegendreP[n, x]` by the three-term recurrence for
non-negative integer degree — a non-integer degree needs the hypergeometric form
and is left to the MPFR path, matching how `BesselJ`/`BesselY` already decline a
non-integer order.

`Binomial` had been classified as "exact integer semantics, not a machine
function", which was wrong: the interpreter evaluates it for real arguments
(`Binomial[5.5, 2.]` is `12.375`) and returns a Real for Real arguments, so a
machine kernel answers the same question rather than a different one.
`FactorialPower` moves the other way — the interpreter leaves
`FactorialPower[5.5, 2.]` *unevaluated*, so it is now recorded as a deliberate
exclusion rather than a pending kernel, alongside `Factorial2`.

**A portability catch worth recording:** the first draft used `lgamma_r` to get
the sign of Gamma alongside its log. That is POSIX, not C99 — the main build
accepted it because macOS headers expose it, and the test build did not. The sign
is now computed directly from the parity of `floor(x)` (Gamma alternates sign on
the negative axis), which also avoids the non-thread-safe global `signgam`.

### Airy — coverage 80 → 84 of 103, and a band deliberately left to MPFR

`AiryAi`, `AiryBi`, `AiryAiPrime` and `AiryBiPrime` come from one implementation:
the ascending series generated by the recurrence `c_{n+3} = c_n/((n+3)(n+2))`
that `y'' = x y` gives directly, and the standard asymptotic expansions beyond.

**The two expansions do not meet in double precision, and that is a property of
the functions rather than of the code.** The series computes a decaying `Ai` as a
difference of growing terms and loses about `2ζ/ln 10` digits; the asymptotic
series has a smallest attainable error of order `e^(-2ζ)`. Measured against the
MPFR implementation:

| region | best relative error |
|---|---|
| series, \|x\| ≤ 2.5 | ~1e-15 |
| series, \|x\| = 3 | 3e-13 |
| asymptotic, \|x\| = 3.5 | **1e-5** |
| asymptotic, \|x\| = 6 | 2e-10 |
| asymptotic, \|x\| ≥ 8 | ~1e-15 |

So the kernel covers `|x| ≤ 2.5` and `|x| ≥ 8` and **declines the band between**,
where the MPFR path answers. Covering it properly needs a third method
(Chebyshev fits, or the modified-Bessel route). Shipping a fast path that is
quietly wrong to five digits would be far worse than being slower over one
interval — and the decline is the same mechanism the engine already uses
wherever a real fast path cannot answer.

This also caught the bail tests a third time: `Zeta`, then `AiryAi`, were each in
turn the example of "a head with no machine kernel", and each in turn started
compiling. The audit exists so that stops being a silent assumption.

**Coverage now 84 of 103 (82%), from 55 at the start of this work.** The 19
remaining are 12 pending numerics (`PolyLog`, `LerchPhi`, `BesselI`/`K`/`JZero`,
`BarnesG`, `Hyperfactorial`, `QPochhammer`, the four hypergeometrics) and 7
deliberate exclusions — `Factorial2` and `FactorialPower`, which the interpreter
leaves unevaluated on reals, and `GCD`, `LCM`, `DigitSum`, `ReIm` and
`QuotientRemainder`, whose semantics are exact-integer or not a single machine
number.

### The last 12 numerics — coverage 84 → 93 of 103, and an interpreter bug found on the way

`PolyLog`, `LerchPhi`, `QPochhammer`, `BesselI`, `BesselK` and the four
hypergeometrics (`Hypergeometric0F1`, `1F1`, `2F1`, `HypergeometricPFQ`) now have
real double kernels in `src/special_functions/sf_machine.c`. That closes every
gap in the coverage audit that was pending work rather than a deliberate
exclusion.

`sf_machine_pfq` is the single implementation; `sf_machine_hyper0f1/1f1/2f1` are
thin wrappers over it. Two implementations of the same series is how a fix to one
silently misses the other — and `Hypergeometric1F1` canonicalises to
`HypergeometricPFQ` before the evaluator ever sees it, so the pFq form is the one
that actually runs.

`HypergeometricPFQ` was also listed as an uncovered head when it was not: the
audit probes each head with `Head[x]` … `Head[x,y,z,w]`, and pFq's real signature
is *two lists and a scalar*. It joins `Clip` and `Rescale` in the `PROBES` table
of shape overrides. A coverage audit that measures the wrong signature reports a
gap that is really a defect in the probe.

**The parity test then failed — and it was the interpreter that was wrong.**
`Hypergeometric1F1[1., 2., -40.]` has the closed form `(e^z - 1)/z`, against
which:

| z | interpreter (before) | compiled kernel |
|---|---|---|
| -40 | **5.3e-2** | 1.7e-17 |
| -37 | 5.0e-4 | 2.4e-17 |
| -30 | 1.6e-6 | 0.0 |
| -20 | 2.6e-10 | 4.0e-17 |
| -10 | 1.9e-14 | 3.8e-17 |

`machine_sum` in `hypergeopfq.c` summed the series in plain doubles. For negative
real `z` that series alternates, and its largest term exceeds the value it sums to
by a factor of order `e^|z|` — at `z = -40` that is 2e17, so every bit of the
answer had already cancelled away before the loop finished. Summing more terms
cannot recover them.

The fix measures the loss instead of guessing it: `machine_sum` tracks
`max|term| / |sum|` and reports `log2` of it, and the dispatcher re-sums through
the existing MPFR path at `53 + lost + 16` bits when that exceeds 4, rounding
back to a machine number. Reporting the loss rather than estimating it from `|z|`
keeps the bound exact for every `p`, `q` and parameter set, including the many
where nothing cancels at all (all-positive terms give `lost = 0` and cost
nothing). Machine-precision arguments still give a machine-precision answer — but
now it is the correctly rounded one, so the *argument* precision decides the
output type rather than the conditioning of the series.

Errors at every `z` in the table above are now 0.0 or one ulp.

**Coverage 93 of 103 (90%).** The remaining 10 are all deliberate, and
`test_compile_coverage.c` now says so in its own header rather than describing
them as pending: `BesselJZero`, `BarnesG`, `Hyperfactorial`, `Factorial2` and
`FactorialPower`, which the *interpreter* leaves unevaluated on machine reals — a
kernel for those would make the compiled path answer where the interpreter
declines, the one divergence the engine forbids — and `GCD`, `LCM`, `DigitSum`,
`ReIm`, `QuotientRemainder`, whose semantics are exact-integer or not a single
machine number.

That structural half is also where the NDSolve bail test now takes its example.
`Zeta`, then `AiryAi`, then `PolyLog` were each used as "a head with no machine
kernel" and each in turn started compiling; `BarnesG` and `QuotientRemainder`
cannot move without breaking interpreter parity, so they will not.

### Threading the fused array loop — 3.2-6.6x at a million elements

A fused elementwise MAP is now split across cores. `OP_APAR` sits immediately
before the strip loop and either fans it out and jumps past it, or falls straight
through into exactly the serial loop that was always emitted there. Declining is
therefore free and always safe — the fallback is not a second implementation, it
is the same instructions.

Measured at 1M elements (16 cores, wall clock, minimum of repeated trials):

| body | serial | threaded | |
|---|---|---|---|
| `Sqrt[v] + v^2` | 2524 us | 782 us | **3.2x** |
| `Sin[v] Exp[-v] + Sqrt[v]` | 14376 us | 2611 us | **5.5x** |
| `Gamma[v] + Erf[v]` | 35900 us | 5479 us | **6.6x** |

Memory-bound bodies gain least, which is the expected shape: `Sqrt[v] + v^2`
reads and writes 16 MB for about three flops per element, so it saturates
bandwidth long before it saturates cores.

**Only maps, never reductions.** Each output element of a map is computed by the
same operations on the same inputs whichever core runs it, so the threaded and
single-threaded programs agree BITWISE — `COMPILE_NO_PAR` gives the A/B and a
test asserts `memcmp` equality over 20 runs at lengths straddling the fan-out
threshold. A reduction is a different matter: floating-point addition is not
associative, so per-thread partial sums would give a genuinely different answer
from the serial fold, and the engine's contract is to agree with the interpreter
rather than merely to come close. Reductions stay serial.

The mechanism is a lifted sub-program. Rather than teach `vm_run` to stop at an
arbitrary pc — a comparison on every dispatch, forever, for one loop — the loop's
instruction range is copied out at finalize time with its jump targets rebased
and its own `OP_RET` appended, so a worker calls the ordinary `vm_run` entry.
The VM's hot path is untouched. Extraction happens after the optimiser, which is
the only correct point: LICM and compaction both move instruction indices, so a
range recorded at emit time would name the wrong instructions by the time it was
used.

Workers are safe with no locking because each gets its own frame, seeded by
copying the parent's registers: scalars by value, array handles as borrowed
pointers (workers only read inputs and write disjoint output elements), and tile
registers re-pointed at the worker's own scratch. Nothing is allocated or freed
across a thread boundary. ThreadSanitizer reports no races; `leaks` reports zero.

#### Two measurement bugs found on the way, both of which had been hiding results

**`tests/CMakeLists.txt` never defined `MATHILDA_THREADS`.** The top-level
makefile always has. So every `nd_parallel_for` in the test build compiled down
to its serial fallback, and no test had ever executed the threaded ND path at
all — not for NDArray maps, not for reductions, not for anything. A guard that
cannot reach the code it guards is worse than no guard, because it reads as
covered. Now set via `find_package(Threads)`; the ND suites pass with it on.

**`bench_compile.c` timed with `clock()`.** That is CPU time summed over every
thread, so a region that scales *perfectly* reports as N times *slower*. The
first measurements of this work came back at 0.56-0.83x and looked like a real
regression; instrumenting the region directly showed it running 6.4x faster than
serial at the same moment the benchmark called it a loss. Every other
`tests/bench_*.c` already used `clock_gettime(CLOCK_MONOTONIC)` — this file was
the exception. Any benchmark a threaded path can reach must be wall-clock.

A pre-fault of the output buffer was added while chasing the wrong explanation
(concurrent first-touch page faults) and then removed once measured: it cost
about 5% rather than saving anything.

### Airy's uncovered band is closed — a third method, and the direction is the point

`2.5 < |x| < 8` used to decline: the ascending series computes a decaying `Ai` as
a difference of growing terms and loses about `2ζ/ln 10` digits, and the
asymptotic expansion has a floor of order `e^(-2ζ)` that only clears double
precision from `|x| ≥ 8`. Between them the best either could do was ~1e-5.

The band is now covered by **Taylor marching of the defining ODE**. About a point
`x0`, writing `y(x0 + h) = Σ c_k h^k` and matching `y'' = (x0 + h) y` term by term
gives

```
(k+2)(k+1) c_{k+2} = x0 c_k + c_{k-1},    c_{-1} = 0
```

with `c_0 = y(x0)`, `c_1 = y'(x0)`. Nothing is approximated: `Ai` and `Bi` are
entire, so this converges for every `h`, and a short step (0.25) converges in a
handful of terms. No fitted coefficients, no new special function, and the same
recurrence shape the ascending series already uses.

**Which direction to march is the whole problem, and getting it wrong is how this
method quietly loses digits.** `y'' = x y` has a recessive and a dominant
solution, and rounding error in the recessive one is amplified by the dominant
one's growth. For `x > 0`, `Bi` grows across the band by a factor of
`e^(ζ(8) − ζ(2.5)) ≈ 2.4e5` — so marching `Ai` forward from 2.5 would let a
1e-16 seed error reach ~1e-11. Each solution is therefore marched in the
direction in which it **dominates**:

| | seeded from | direction |
|---|---|---|
| `Bi`, `Bi'` (x > 0) | ascending series at `|x| = 2.5` | forward, growing |
| `Ai`, `Ai'` (x > 0) | asymptotic at `|x| = 8` | backward, growing as x falls |
| all four (x < 0) | ascending series at `x = −2.5` | one march; neither solution dominates in the oscillatory region |

Measured against the MPFR path over 300 points per function per sign:

| | former band | for comparison |
|---|---|---|
| `AiryAi` | 7.4e-17 / 7.2e-16 | 1.0e-15 in the series region |
| `AiryBi` | 2.6e-15 / 9.3e-16 | 2.9e-16 |
| `AiryAiPrime` | 1.4e-16 / 2.0e-15 | 1.1e-15 |
| `AiryBiPrime` | 2.6e-15 / 1.6e-15 | 5.0e-16 |

The band is now at least as accurate as the two regions that were already
accepted — in places better than the ascending series manages at `|x| = 2.5`.
Two further parity sweeps run across `[-12, 12]` so a discontinuity at either
seam would show. **No Airy argument on the real axis declines any more**, and the
four entries that asserted the decline are gone from the bail list.

### `NUMERIC_FUNCTION_MISSING.md` — and what it found

New top-level document enumerating every `ATTR_NUMERICFUNCTION` head that lacks a
machine fast path, generated from the build rather than hand-maintained
(`COVERAGE_REPORT=1 ./compile_coverage_tests` dumps the table).

Writing it turned up something the coverage audit had never been asked: it probes

| | of 103 |
|---|---|
| full fast path (real **and** complex) | 52 |
| real only — **complex bails** | 41 |
| no fast path at all | 10 |

**Complex arguments are now the single largest source of silent interpreter

### Complex arguments: first three heads, and two result-HEAD bugs the work exposed

Acting on `NUMERIC_FUNCTION_MISSING.md`, the three complex cases that are cleanly
typed are closed: **`Sign`, `FractionalPart`, `Rescale`**. Complex coverage
52 → 55 of 103.

`Sign`'s complex kernel (`z/|z|`, 0 at the origin) had been in the registry the
whole time — the compiler's own inline lowering for `Sign` matched the head first
and bailed on a complex operand, so `try_kernel` was never consulted. A bespoke
lowering that shadows a registered kernel is a coverage gap that no amount of
kernel-writing fixes.

`FractionalPart` needed one componentwise function; `Rescale` is
`(x - lo)/(hi - lo)`, which carries a complex `x` through unchanged. **`Clip`
deliberately does not** — `Min`/`Max` need an order, and the interpreter leaves
`Clip[1. + I, {0., 2.}]` unevaluated, so the compiled path must too.

#### The other four are type-blocked, not mechanical

`Floor`, `Ceiling`, `Round` and `IntegerPart` on a complex return
`Complex[Integer, Integer]` — `Head /@ ReIm[Floor[1.5 + 2.5 I]]` is
`{Integer, Integer}`. The type lattice has `CT_INT` and `CT_COMPLEX` (a
`double _Complex`) but nothing for a complex *integer*, so answering with
`CT_COMPLEX` would give `Complex[Real, Real]` and differ from the interpreter in
head. They need a new type, not a new function pointer. The write-up originally
listed all seven as "cheap and mechanical"; checking result *types* rather than
values cut that to three.

#### `parity_head` — a test for the class of bug the value tests cannot see

The numeric parity tests compare values, and a value compares equal whether it
came back as the Integer `-1` or the Real `-1.`. But those are not
interchangeable downstream (`IntegerQ`, exact arithmetic, printing), so a
compiled path with the wrong result head is answering *differently* from the
interpreter. `parity_head` compares the compiled program's declared result type
against the head the interpreter produces, over every head whose result type
differs from its argument type.

It found two live divergences immediately:

- **`Sign[-2.5]`** is the Integer `-1` in the interpreter; the compiled path
  declared `CT_REAL` and answered `-1.`. `OP_SIGN_R` now writes the integer slot.
  (The tile form `VSIGN_R` stays real — it feeds packed float arrays, where a
  real dtype is the right answer.)
- **`IntegerPart[2.5]`** is the Integer `2`; the compiled path went through the
  registered kernel, which returns a double, and declared `CT_REAL`. It now has a
  bespoke lowering alongside `Floor`/`Ceiling`/`Round` via a new `OP_TRUNC_R` —
  truncation toward zero, which is *not* `Floor` for a negative argument
  (`IntegerPart[-1.5]` is `-1`, `Floor[-1.5]` is `-2`). The kernel stays for the
  array path.

This is the same failure mode `UnitStep` was given a bespoke lowering for, and it
had recurred twice since without being noticed.

### `Quotient` at complex argument was rounding, not flooring

`Quotient[m, n, d]` is `Floor[(m - d)/n]` by definition, and every branch of
`builtin_quotient` agreed except the complex one, which used `round`. So
`Quotient[5.5 + 1. I, 3.]` returned `2` while `Floor[(5.5 + 1. I)/3.]` returned
`1`, and the complex result disagreed with the real result for the same quotient.
Now floors, and matches `Floor[m/n]` at every argument tried including a Gaussian
divisor (`Quotient[10 + 2 I, 3 + I]` = `3 - I`).

### Dead degrade-sentinel scaffolding removed

`ndkernels.c` still carried the `ND_DEGRADE_U`/`ND_DEGRADE_B` descriptors and the
loops that registered them, but both name lists were empty — every head that once
needed a sentinel now has a real kernel. A zero-length array is not standard C99
and gcc was warning that the loop guard is always false. Removed, with a comment
recording how to register a sentinel if one is ever needed again: an explicit
"known, and deliberately has no fast path" reads differently from an absent
registry entry, and the coverage audit distinguishes them.
