# Changelog: week of 2026-08-24 (Mon) – 2026-08-30 (Sun)

## `FindInstance` — undefined-witness soundness fix, solve-one-variable, saturation, all-constraint feasibility, quiet probes, v0.108

A second `FindInstance` stress round: six harder cases, all now solved with sound,
verification-gated, general methods — and the internal solver probes are now silent
(all touching `src/solve/reduce_companions.c` unless noted).

- **Soundness: witnesses must be defined, not just fold to `True`** — the verifier
  (`fi_verify` → new `fi_defined_truth` / `fi_has_nonfinite`) now rejects any point
  where a relation operand evaluates to an infinity/indeterminate sentinel. Previously
  `FindInstance[Log[z^2] == 2 Log[z] + 2 π I, z, Complexes]` returned the **wrong**
  `{{z -> 0}}` (since `Log[0] = -Infinity` and `-Infinity == -Infinity` folds to
  `True`); it now returns the correct `{{z -> -I}}`.
- **Solve one equation for one variable, sample the rest** (`fi_solve_one_sample`) —
  for an equality `E` and a variable `xₖ`, `Solve[E, xₖ]` is combined with a
  constraint-aware, per-variable-compacted candidate grid over the other variables
  (extended with small/large magnitudes). Solves `c1 e^{-L1 t} + c2 e^{-L2 t} == 0 &&
  c1 > 0 && c2 < 0 && L1 > L2 > 0 && t > 0` → `{c2 -> -1, L1 -> 2, L2 -> 1, t -> 1,
  c1 -> E}`, and the tiny-region `(x²-y²)/(x²+y²) == 1/2 && x²+y² < 10⁻¹⁰ && x>0 && y>0`
  → `{y -> 10⁻⁶, x -> √3·10⁻⁶}`.
- **Ideal saturation for declined polynomial systems** (`fi_saturate_solve`) — a
  Rabinowitsch slack `w·∏dᵢ == 1` on the `≠` disequations saturates the ideal so the
  finite variety is zero-dimensional and `Solve` returns its roots. Solves
  `x⁴y³ - 3x²y + y⁴ == 0 && 4x³y³ - 6xy == 0 && x != 0 && y != 0`, which `Solve` alone
  declines as positive-dimensional (`Solve::nsdim`).
- **All-constraint numeric feasibility** (`fi_collect_penalty` replaces the
  equality-only `fi_collect_sq`; `fi_numeric_feasibility`) — the `FindMinimum`
  objective is now a least-infeasibility penalty over *every* constraint (equality
  residuals plus one-sided inequality hinges; disequations skipped), with auxiliary
  definitions `s == c` folded out first (`fi_fold_aux`). Keeps the optimiser inside the
  feasible box and halts on open feasible regions, so it solves the Rastrigin
  sub-level set `… < 0.1 && x != 0 && y != 0` (which `NMinimize` could not take,
  `NMinimize::nimpl`) and the pinned-constant rational system
  `d1 == v²/(2 g (μ − Sin t)) && … && d1 == 3.2 && g == 9.8 && 0 < t < 0.1`. The exact
  grid sampler is now tried **before** this numeric last resort, so exact witnesses are
  preferred (e.g. `t > s+1 && … ` keeps its exact `{t -> 1, s -> -1}`).
- **Quiet internal probes** (new `src/message.{c,h}`: `mth_msg_suppress_push/pop`) —
  `FindInstance` runs its speculative `Reduce`/`Solve`/`NMinimize`/`FindMinimum` probes
  under message suppression, so a sampled `1/0`, an unsupported constraint shape, or an
  inverse-function note no longer leaks (`Power::infy`, `Infinity::indet`,
  `Solve::nsdim`, `Solve::ifun`, `NMinimize::nimpl`, `FindMinimum::lstol`). The flag is
  routed into the existing `arith_warnings_muted()` gate and the `warn_nsdim` / `fm_warn`
  / `emit_ifun` emitters.

Regression: `reduce`, `comparisons`, `reduce_corpus` (0/158), `solve_corpus` (0/99),
`nroots`, `findroot`, `ratcanon_reduce`, `rootreduce` all green; one previously-declining
`reduce_tests` assertion (`x² + y z == 1 && x + 2 y <= 3 z + 1 && x y z > 7`) updated to
its now-verified witness. `make check-c99` clean; valgrind shows no Mathilda frames in
any leak stack (macOS baseline).

## `Equal`/`Unequal` decide numeric constants; five more `FindInstance` methods, v0.107

Nine of ten new `FindInstance` stress cases now solve (the tenth, an exact
transcendental system `Sin[x + I y] == 2`, needs a real trig-system solver and is
left for a future round). One global correctness fix plus four verification-gated
`FindInstance` layers.

- **`Equal`/`Unequal` decide closed-form numeric constants** (`src/comparisons.c`).
  When `compare_numeric` cannot order a pair and both sides are numeric (`NumericQ`,
  via the newly-exported `expr_is_numeric_quantity`, `src/core.c`/`src/numeric.h`), the
  exact zero-test (`zero_test_decide`) settles it. So `I == 0 → False`, `I != 0`,
  `2 I Pi != 0`, `(1+I) == (1-I) → False`, and a complex radical `frac == 0 → True`
  — matching Mathematica, where these previously stayed unevaluated. A free symbol is
  never decided (`x == 0` stays symbolic). This is what makes the `Log[x y] != …` and
  `(x³−1)/(x−1) == 0 && x != 1` instances verify. The Reduce stress-corpus verifier
  (`tests/reduce_check_prelude.m`) was taught to skip sample points where an input
  relation leaves its domain (a pole → `ComplexInfinity`; `Sqrt` of a negative over
  `Reals`), which the domain-restricted `Reduce` output legitimately excludes.
- **Structured candidate sampling (ℂ/ℝ)** — a last-resort verify-gated grid over
  interesting values solves branch-cut disequations `Sqrt[z^2] != z` and
  `Log[x y] != Log[x] + Log[y]`. Never claims `{}`.
- **Sum-of-even-powers integer bounding** — an equality `Σ cᵢ vᵢ^(2k) == C` (`cᵢ>0`)
  bounds each variable to `|vᵢ| ≤ (C/cᵢ)^{1/2k}`, so `a b + b c + c d + d e == 0 &&
  a² + b² + c² + d² + e² == 5` becomes a finite `[-2,2]^5` search.
- **1-variable real transcendental root scan** — bracket a pole-free refactoring of
  `lhs − rhs` (numerator after clearing `Tan`/`Sec`/… denominators), refine by
  high-precision bisection, verify: `Tan[x] == x && x > 10^6`.
- **Residual-minimising feasibility with numeric-tolerance verify** — for inexact-input
  Real systems whose equalities hold only approximately, minimise `Σ(lhsᵢ − rhsᵢ)²` from
  several seeds and verify to tolerance: `E^(−a x) Cos[b x] == 0.1 && E^(−a y) Cos[b y]
  == 0.1 && x ≠ y && a > 0`. The transcendental gate (`fi_is_transc_inexact`) now also
  recognises `PolyGamma`/`LogGamma`/`Zeta` and base-`E` powers, so `Reduce`'s
  (unsound-over-transcendentals) `False` is not trusted for them.

Regression coverage: new asserts in `tests/test_comparisons.c`
(`test_equal_unequal_numeric_constants`) and `tests/test_reduce.c` (the six solved
stress cases). Full suite green; `make check-c99` clean; valgrind at the macOS baseline.

## `Equivalent` evaluates on Booleans; `FindInstance` numerical + Gröbner witnesses, v0.106

Three more `FindInstance` deficiencies fixed with general mechanisms, each still
verification-gated. All in `src/solve/reduce_companions.c` unless noted.

- **`Equivalent` now evaluates and expands** (`src/boolean.c` `builtin_equivalent`,
  `src/attr.c` `Flat|Orderless|OneIdentity|Protected`, `SYM_Equivalent`). Folds literal

## `FindInstance` — parametric families, indexed variables, bounded integer search, v0.105

Four extensions to `FindInstance` (`src/solve/reduce_companions.c`), each still
gated by the same verification (`expr /. instance === True`), so every returned
point remains a true solution and `{}` is emitted only when the set is proven empty:

- **Generated-parameter instantiation.** Parametric families
  `x -> ConditionalExpression[value(C[1]), C[1] >= 1]` are materialised by trying
  the parameter over a small integer grid, reaching the fundamental Pell solution
  `FindInstance[x^2 - 61 y^2 == 1 && x > 0 && y > 0, {x, y}, Integers]` →
  `{{x -> 1766319049, y -> 226153980}}` (at `C[1] == 1`).
- **Solving a parameter against the window.** When the grid misses and a single
  generated parameter remains, the remaining constraints are solved for it over the
  `Reals` (`Ceiling`/`Floor` of a possibly symbolic bound such as `50000/Pi`),
  reaching the periodic instance
  `FindInstance[Sin[1/x] == 0 && 0 < x < 10^-5, x, Reals]` → `{{x -> 1/(31831 Pi)}}`.
- **Indexed variables.** `c[1], …, c[n]` are matched structurally (`expr_eq`, not
  interned-symbol identity), so systems in indexed unknowns are accepted —
  `FindInstance[c[1]^2 + c[2]^2 == 25 && c[1] > 0 && c[2] > 0, {c[1], c[2]}, Integers, 2]`
  → both `{3, 4}` and `{4, 3}`.
- **Bounded integer search** (`fi_integer_search`). Over the `Integers`, when
  `Reduce`/`Solve` decline, an integer box derived from the constraints is enumerated
  under a candidate budget: a finite box is decidable — a Diophantine witness
  (`a^3 + b^3 + c^3 == d^3` → `{5, 4, 3, 6}`) or `{}` on exhaustion, with a linear
  reach-range check giving an instant `{}` for the 0/1 knapsack
  `Total[Array[c, 15]*Prime[Range[15]]] == 500 && 0 <= c[i] <= 1` (sum of the first
  15 primes is 328 < 500); an unbounded domain is best-effort (a witness if small
  enough, else a sound decline — never `{}`, so `a^4 + b^4 + c^4 == d^4` declines
  within budget).

Reduce is skipped as the oracle when a variable is indexed (it rejects `c[1]`),
avoiding a spurious `Reduce::ivar` message; `Solve` and the integer search accept
them. Tests: `test_find_instance` extended to 28 assertions; reduce suite 267 PASS;
reduce corpus 158/158; `check-c99` clean; the new code is at the macOS valgrind
baseline (the one small extra leak on the `Sin` path is pre-existing inside
`Reduce`'s atom canonicalization — `reduce_atom.c`/`ratcanon.c` — surfaced, not
introduced, by feeding it a rational inequality with `Pi`).

## `FindInstance` — witness finder (Reduce Phase 8), v0.104

`FindInstance[expr, vars, dom, n]` finds up to `n` witness points satisfying
`expr` over **Complexes / Reals / Integers / Rationals / Booleans**, returned in
`Solve`'s form (`{{x -> v, ...}}`), `{}` when the set is provably empty, and
unevaluated when it can neither exhibit an instance nor prove emptiness
(`src/solve/reduce_companions.c`, `builtin_find_instance`; new `SYM_FindInstance`;
registered `Protected` in `reduce_companions_init`).

- **Soundness by construction.** Rather than reaching into the three `static` CAD
  paths (`reduce_cad.c`: `nu==1` sign diagram, `nu==2` flat `YRegion` arrays,
  `nu>=3` `CADRegion` tree), witnesses are read off the **public, already-cylindrical**
  output of `Reduce` (the satisfiability oracle) and off `Solve`'s rule-lists, and
  **every** candidate is verified against the original `expr` (`expr /. point`
  must evaluate to `True`). A returned instance is therefore always a true
  solution; `{}` is emitted only when `Reduce` proves emptiness; anything
  unwitnessed and unrefuted is left unevaluated — never guessed.
- **Extraction.** `Reduce` output → walk each top-level `Or` clause: `Element`-declared
  parameters and unpinned free variables are sampled first (interval samples via the
  shared exact `rru_rational_between`), then `Equal` atoms are resolved by an internal
  `Solve`. `Solve` fallback instantiates free listed variables to `0` (grid for extra
  instances) — so `FindInstance` succeeds on cases `Reduce` declines, e.g.
  `FindInstance[x^2 - y z == 1, {x, y, z}] -> {{x -> -1, y -> 0, z -> 0}}`.
- **Booleans** reuses the module's `LogicalExpand` DNF engine: each satisfiable DNF
  clause is a partial assignment (unconstrained variables default `False`), verified
  with the now-evaluating `Xor`/`Implies`.
- **Options**: `Modulus -> p` solves over `Z/pZ`; `Method` / `WorkingPrecision` /
  `RandomSeeding` are accepted and ignored (exact & deterministic); an unknown
  option gives `FindInstance::optx` and stays unevaluated.
- Examples: `x^2 == 2` (C) → `{{x -> -Sqrt[2]}}`; the disk (R) → `{{x -> 0, y -> 0}}`;
  `x^2 - 3 y^2 == 1 && 10 < x < 100` (Z) → `{{x -> 26, y -> -15}}`; the 4-variable
  `Xor` SAT (Booleans); an unsatisfiable system → `{}`.
- Tests: `test_find_instance` in `tests/test_reduce.c` (21 assertions, FullForm-pinned
  + decline checks); reduce corpus 158/158; `make check-c99` clean; valgrind
  byte-identical to the macOS baseline (no FindInstance-attributable leak). While
  here, the pre-existing `-Wdiscarded-qualifiers`/`-Walloc-size` warnings in
  `reduce_companions.c` were also cleared, so the module compiles warning-free.
  `CylindricalDecomposition` remains the last unshipped Phase-8 companion.

## `Xor` and `Implies` now evaluate on Booleans

`Xor` and `Implies` were previously inert on every input — `Xor[True, True]`
and `Implies[True, False]` stayed symbolic. They now evaluate
(`src/boolean.c`, `builtin_xor` / `builtin_implies`; attributes in `attr.c`):

- **`Xor`** (`Flat`, `Orderless`, `OneIdentity`, `Protected`) folds the literal
  Booleans and cancels duplicate arguments (`a` Xor `a` = `False`): `Xor[]` →
  `False`, `Xor[e]` → `e`, `Xor[True, False]` → `True`, `Xor[True, True]` →
  `False`, `Xor[True, a]` → `!a`, `Xor[a, b, a]` → `b`; a fully-symbolic distinct
  `Xor[p, q, r]` stays unevaluated. Nested `Xor` flattens.
- **`Implies`** (`Protected`): `Implies[False, q]` / `Implies[p, True]` → `True`,
  `Implies[True, q]` → `q`, `Implies[p, False]` → `!p`, `Implies[p, p]` → `True`;
  otherwise unevaluated.

This makes the Boolean algebra self-consistent with `LogicalExpand` and the
`Reduce` family (which already expand `Xor`/`Implies` internally) and with the
`Compile[]` logic path (which already lowered them), and lets a truth-table
cross-check like `Table[e1 == LogicalExpand[e1], {a, {True, False}}, ...]` reduce
to all `True`. No regression: the `Reduce` corpus (158/158) and the reduce/
boolean/compile/comparisons/simplify suites stay green.

## Reduce Phase 8 — `LogicalExpand` (+ the `NotElement` head)

The first `Reduce` companion builtin lands (REDUCE_PLAN.md, Phase 8):
`LogicalExpand[expr]` distributes a logical combination of equations,
inequalities and Boolean atoms into **disjunctive normal form** (an `Or` of
`And`s) with idempotence / complementation / absorption contractions, expanding
`Implies` and `Xor` and collapsing to `True` (tautology) or `False`
(contradiction). Examples: `LogicalExpand[p && !(q || r)] -> p && !q && !r`,
`LogicalExpand[(a || b) && !(c || d || e)] -> (a && !c && !d && !e) || (b && !c
&& !d && !e)`, `LogicalExpand[a || !a] -> True`, `LogicalExpand[a && !a] ->
False`, `LogicalExpand[Xor[p, q, r]]` → its four odd-parity minterms,
`LogicalExpand[x == a && y == b || x == a || y == b] -> x == a || y == b`
(absorption), and the multi-variable tautology
`LogicalExpand[Implies[(p || !r) && s, Implies[r && s, p && q || p]]] -> True`.

Because it does **no domain reasoning** (every non-connective subexpression is an
opaque Boolean atom, exactly as Mathematica), `LogicalExpand` cannot reuse the
`RForm`/`RAtom` layer — that layer forces each leaf into a *polynomial* relation.
The engine is therefore a standalone Expr-level DNF distributor
(`src/solve/reduce_companions.c`): a mutually-recursive `to_dnf` / `to_dnf_neg`
that branches only on the recognised logical heads and treats everything else as
a signed literal. A negation folds into the complementary **relation head**
(`x == a` / `x != a`, `x < 1` / `x >= 1`, `Element` / `NotElement`, `a` / `!a`)
so output carries no stray `Not` on a relation, and those pairs are exactly the
complementary literals used by the contractions.

The `True`/`False` collapse is **sound and complete without truth-table
enumeration**: over independent opaque atoms a DNF is unsatisfiable iff every
clause holds a complementary pair — i.e. it distributes to zero surviving clauses
— so `expr` is `False` when its DNF is empty and `True` when the DNF of `!expr`
is empty. The emitted DNF is sound and equivalent but, like the rest of the
`Reduce` family, not guaranteed minimal (Mathematica's extra consensus
contractions can produce a shorter, logically identical cover).

A minimal **`NotElement`** head ships alongside so a negated membership prints as
`x` ∉ `dom` (Mathematica-faithful) rather than `Not[Element[...]]`;
`NotElement[x, dom]` decides whenever `Element[x, dom]` decides and stays
symbolic otherwise. Both heads are `Protected`. New symbols `SYM_LogicalExpand`
and `SYM_NotElement`; registered from `reduce_companions_init` (called by
`reduce_init`). `Reduce` remains exempt from the packed/NDArray and `Compile[]`
surfaces (a symbolic head returning logical formulas), and its companions inherit
that exemption. Tests: `test_logical_expand` in `tests/test_reduce.c`. The other
Phase-8 companions (`FindInstance`, `CylindricalDecomposition`) are still pending.

## Trig functions — `Degree` is interpreted in exact evaluation (bug fix)

`Sin[30 Degree]` (and `Cos`, `Tan`, `Cot`, `Sec`, `Csc` of any `c Degree`) now
fold to the same exact value as `Sin[Pi/6]` — `1/2` — instead of returning the
argument unevaluated. `Degree` is `Pi/180`, so a `c Degree` argument is just a
rational multiple of `Pi` in a second spelling; the fix teaches the single
shared detector `extract_pi_multiplier` in `src/trig.c` to recognise `Degree`
(bare `Degree -> Pi/180`, `c Degree -> c/180 * Pi`). All six circular heads
funnel their argument through that one function, so the change is one place and
costs a single symbol-pointer comparison on the common `Pi` path — no
evaluator-wide substitution, and no effect on the numeric (`N[Sin[30 Degree]]`
was already `0.5` because `Degree` is a registered numeric constant) or
`Compile[]` paths (already lowered `Degree` to a real constant).

The `(n, d)` handed to the `exact_*` callees for a `Degree` argument need not be
in lowest terms — they reduce via `gcd` — and denominators are bounded before
the ×180 scaling so the downstream `2*d` periodicity reduction cannot overflow
`int64`; a pathological coefficient falls through to the numeric path rather
than folding a wrapped value. `Degree` stays opaque everywhere else, matching
Mathematica: `30 Degree` does not auto-expand to `Pi/6`, and `Sin[Degree]` (=
`Sin[Pi/180]`, no closed form) stays symbolic. Regression coverage in
`tests/test_trig.c` (`test_trig_degree`).

## CharacteristicPolynomial — new builtin

`CharacteristicPolynomial[m, x]` gives `Det[m - x I]` as an expanded polynomial
in `x`; `CharacteristicPolynomial[{m, a}, x]` gives the generalized
`Det[m - x a]`. Entries may be integer, rational, machine- or arbitrary-precision
real, complex, or symbolic. Attribute `Protected`.

Rather than the naïve `Expand[Det[m - x I]]` — which would face an `O(n!)`
Laplace expansion of a symbolic-in-`x` matrix — the ordinary case reuses the
eigen module's Faddeev–LeVerrier–Souriau fast path (`eigen_char_poly_faddeev`,
`O(n^4)`), so a 100×100 machine matrix is sub-second. That routine returns
`det(λI − m)`, so odd-`n` results are negated to match `Det[m − x I] = (−1)^n
det(x I − m)` (e.g. `CharacteristicPolynomial[IdentityMatrix[3], x] ->
1 - 3 x + 3 x^2 - x^3`). The generalized case is `Det[m − x a]` via Laplace
expansion (`eigen_build_lambda_matrix` + `eigen_compute_det`), so a shared null
space drops the leading term(s) — an infinite generalized eigenvalue shows as a
degree deficit (`CharacteristicPolynomial[{a, b}, x] -> -1 - x + x^2`). The
polynomial is built in a private internal lambda and the user's second argument
(symbol, number, or expression) is substituted in, then expanded.

New TU `src/linalg/charpoly.c` (an eigen-family unit); registered in
`mateigen_init` (`src/linalg/eigen.c`); declared in `src/linalg/eigen.h`; new
`SYM_CharacteristicPolynomial`; docstring in `src/info.c`. The head returns a
symbolic `Plus`, so it is exempt from the packed/NDArray/`Compile` surfaces; it
consumes packed input safely (visible-NDArray guard + `pack_unpack`). Tests:
`tests/test_characteristicpolynomial.c` (16 groups — every reference case,
exact/degree/`Chop`-identity checks, arity/shape errors, and a repeated-call
leak tripwire). `make check-c99` clean; eigen suite green; no new leaks
(the residual "definitely lost" is byte-identical to the macOS init baseline).

## Reduce — Quantifier elimination (Exists / ForAll / Resolve), v0.095

`Reduce` gained quantifier elimination (REDUCE_PLAN.md Phase 7): the new heads
`Exists`, `ForAll`, and `Resolve` turn a quantified real statement into an
equivalent quantifier-free formula over the remaining free variables — or
`True`/`False` when none remain. `Exists` and `ForAll` are inert (`HoldAll`)
quantifier wrappers; `Resolve[expr, dom]` and a top-level `Exists`/`ForAll`
inside `Reduce[...]` both route to one engine over the Reals.

The engine reuses the existing Cylindrical Algebraic Decomposition
(`reduce_cad.c`) with the quantified variables projected out first. The key
structural fact exploited: `cad_build` already computes the fold — a cell's
`empty` flag is exactly `!Exists` over the bound-variable fibre below it, and its
`all_true` roll-up is the `ForAll` verdict — so QE is a per-cell read, not new
projection machinery. Three regimes:

- **Fully quantified (no free variable)** — a real-closed-field **decision
  procedure**, reusing the whole engine: `Exists[{v}, φ]` is `Reduce[φ, v, Reals]
  =!= False`, `ForAll[{v}, φ]` is `... === True`. E.g.
  `Resolve[Exists[x, x^2 == 4], Reals] -> True`,
  `Resolve[ForAll[x, x^2 > 0], Reals] -> False`,
  `Resolve[Exists[{x, y}, x^2 + y^2 < 1], Reals] -> True`.
- **One free variable (parametric)** — a new public seam `reduce_cad_qe`
  (`src/solve/reduce_cad.{c,h}`) builds the CAD with the free variable outermost,
  labels each of its cells with the `Exists`/`ForAll` verdict over the bound
  fibre, and emits the merged 1-D formula through the shared
  `rru_emit_sign_diagram`. E.g. `Reduce[Exists[y, x^2 + y^2 < 1], {x}, Reals] ->
  -1 < x < 1`, `Reduce[ForAll[y, x^2 + y^2 >= 1], {x}, Reals] -> x <= -1 || x >=
  1`, `Resolve[Exists[x, x^2 == a], Reals] -> a >= 0`,
  `Reduce[ForAll[y, x^2 (1 + y^2) > 0], {x}, Reals] -> x != 0`.

New front-end `src/solve/reduce_qe.{c,h}` (quantifier normalisation — same-kind
flattening, 3-argument `cond` folding — free-variable collection, and A/B/C
routing); new symbols `SYM_Exists`/`SYM_ForAll`/`SYM_Resolve`; the `Exists`/
`ForAll` peel in `builtin_reduce`; `reduce_qe_init` wired from `reduce_init`.
`$VersionNumber` bumped 0.093 → 0.095.

**Soundness over completeness (preserved):** the engine declines (stays
unevaluated) for ≥2 genuine free variables, an alternating quantifier prefix
(`ForAll[x, Exists[y, ...]]`), an explicit non-`Reals` domain, a non-rational

## Eigenvalues/Eigenvectors — conjugate pairs list +imag first (sign-order fix)

`Eigenvalues` sorts by decreasing `|λ|`, and both the numeric Direct kernel and
the symbolic (`Root[]`/radical) path now break an exact modulus tie the same
way: the `+imag` member of a complex-conjugate pair `a ± b I` comes first. This
matches Mathematica (`Eigenvalues[{{0,-1},{1,0}}]` → `{I, -I}`) and makes the
two evaluation paths agree on the sign order — previously the symbolic path fell
back to Solve's natural `Root[]` index order, so `N[Eigenvalues[m]]` disagreed
with `Eigenvalues[N[m]]`:

```
Eigenvalues[{{0,1,0},{0,0,1},{1,1,0}}]
  before:  {Root[…,1], Root[…,2], Root[…,3]}   (* N -> {1.325, -0.662-0.562 I, -0.662+0.562 I} *)
  after:   {Root[…,1], Root[…,3], Root[…,2]}   (* N -> {1.325, -0.662+0.562 I, -0.662-0.562 I} *)
```

Implemented in `eigen_sort_by_abs_desc` (`src/linalg/eigen_common.c`): the sort
key gains an `N[Im[λ]]` secondary field, applied only on an exact `|λ|` tie so
purely real eigenvalues and free-variable symbolic eigenvalues are unaffected.
`Eigenvectors` follows for free — it computes each eigenvector from the sorted
value list, so the vector order tracks the value order. Regression tests added
for the cubic case above and the rotation matrix (`test_eigen.c`).

## REPL — completeness-driven Return (terminal multiline editing)

The interactive REPL's Return key is rebound so that **Return evaluates only
when the current buffer is a complete expression, and otherwise opens a new
line** — replacing the old trailing-`\` continuation convention. A buffer is
"complete" when it has no unterminated `"..."` string or `(* ... *)` comment and
every `(`/`[`/`{` is matched; an *over*-closed buffer (a stray `)`) submits
immediately so the parser reports the error rather than trapping the user on an
endlessly growing line. This is the terminal-native equivalent of a notebook's
Shift+Enter and needs no enhanced-keyboard protocol, so it works on every
terminal.

- **New `repl.c` internals:** `mth_input_complete()` (single-pass lexer-matching
  balance check), `mth_smart_return()` (the RET handler: complete → `rl_newline`,
  else `rl_insert_text("\n")`), `mth_force_return()` (bound to `Esc`-`Return` /
  `Meta`-`Return` to force-submit an open buffer), and `mth_setup_readline()`
  (installs the bindings and enables bracketed paste so multi-line pastes are not
  submitted a fragment at a time).
- **Build:** the feature requires *real* GNU Readline. On macOS the default
  `<readline/readline.h>` and `-lreadline` resolve to Apple's **libedit** shim,
  which silently ignores the RET rebinding and cannot edit multi-line buffers.
  The makefile now probes for a Homebrew GNU Readline on Darwin
  (`brew --prefix readline`, then `/opt/homebrew` and `/usr/local` keg paths) and
  adds its include/lib dirs; it falls back to the single-line shim when none is
  found. Linux resolves GNU Readline through `-lreadline` already. The GNU-only
  `rl_bind_keyseq` calls are guarded by `#ifdef RL_STATE_INITIALIZED` so the tree
  still compiles against the shim.
- Verified end-to-end by driving the REPL through a PTY: open brackets, spanning
  strings, spanning comments, multi-line matrices continue; balanced and
  over-closed inputs submit; `Esc`-`Return` force-submits an open buffer.

## Parser/Printer — `&&` now binds tighter than `||` (was equal precedence)

`And` (2800) and `Or` (2700) had the **same** precedence in both the parser and
the printer's parenthesiser, so mixed boolean expressions were mis-grouped and the
print→parse roundtrip was broken:

```
a || b && c   parsed to   And[Or[a,b], c]   (wrong; now Or[a, And[b,c]])
And[a, Or[b,c]]  printed   a && b || c       (wrong; re-parsed to Or[And[a,b],c])
```

`&&` must bind tighter than `||` (`a || b && c == a || (b && c)`), so `Or` is
lowered to precedence 2700 — looser than `And` (2800) and `Not` (3000), still
tighter than `Repeated` (2500). Now an `Or` nested inside an `And` (or a
parenthesised `Or` on the left of `&&`) prints with the parentheses it needs, and
`ToExpression[ToString[e]] === e` holds for these forms. Surfaced by
`Reduce[x^2 - y^2 < 1, {x, y}, Reals]`, whose (correct) `And[x<=-1, Or[…]]` cells
previously printed as `x <= -1 && y < … || y > …`, dropping the `x<=-1` guard on the
second interval. Fix in `src/parse.c`, `src/print.c` (`get_expr_prec`);
`docs/spec/operators.md` updated.

## Reduce — radicals compose with `Abs` (multivariate); univariate domain-gate soundness fix

Two defects, both exposed by composing a radical with `Abs`, are fixed. The
handling of `Abs` (sign-split into polynomial branches) and of radicals were
built as independent passes that did not compose.

**1. Multivariate radicals now rationalize (`Sqrt[Abs[x]]+Abs[y]<1` was
unevaluated).** After `Abs` splitting leaves a residual `Sqrt[u]`, the
multivariate engines (Fourier-Motzkin, CAD) gate on polynomiality and declined,
so *any* radical in ≥2 variables bubbled back unevaluated. A new preprocessing
pass rewrites `Sqrt[u] REL c` into an exact radical-free equivalent by isolating
one radical and squaring under sign guards, keeping the problem at its original
dimension for the existing polynomial CAD/FM. The `!=` case is derived directly
(not as `Not[==]`) since both are false where `u<0`; multiple radicals are cleared
by iteration; a radical that cannot be isolated with a constant coefficient (or a
non-polynomial radicand) is left in place so the engine declines soundly rather
than guess.

```
Reduce[Sqrt[Abs[x]] + Abs[y] < 1, {x, y}, Reals]  ->  |y| < 1 - Sqrt[|x|]  (was: unevaluated)
Reduce[Sqrt[x^2 + y^2] < 1, {x, y}, Reals]        ->  the open unit disk    (was: unevaluated)
Reduce[Sqrt[x] + y < 1, {x, y}, Reals]            ->  x >= 0 && y < 1 - Sqrt[x]
```

**2. Univariate domain gate is now per-conjunct (`Sqrt[Abs[x]]<1` was a WRONG
`x==0`).** The general univariate sign diagram collected each radical/`Log`/
inverse-trig domain condition into one global `And`-gate over all cells. After
`Abs` splitting, `Sqrt[x]` (needs `x>=0`) and `Sqrt[-x]` (needs `x<=0`) live in
mutually-exclusive branches, so the global gate collapsed the answer to the single
point where both hold. The gate is now scoped to the conjunct that produced each
condition.

```
Reduce[Sqrt[Abs[x]] < 1, x, Reals]  ->  -1 < x < 1            (was: x == 0, bound ignored)
Reduce[Log[Abs[x]] < 0, x, Reals]   ->  -1 < x < 0 || 0 < x < 1   (was: False)
```

Implementation: `reduce_stmt_has_radical` + the rationalization pass (`rationalize_tree`/
`rationalize_relation`, 6-row rewrite table, NNF Not-folding) in `src/solve/reduce_realfn.c`,
wired into the multivariate dispatch (`src/solve/reduce.c`) and the
`reduce_piecewise_preprocess` fixpoint; per-conjunct domain scoping in
`reduce_univar_general`/`form_truth_general` (`src/solve/reduce_realdiag.c`). Covered by
new `reduce_corpus.m` rows (sampled-equivalence + decline cases) and pinned `test_reduce.c`
strings. QE (Phase 7) and algebraic-coefficient CAD fibres (Phase 6b) remain the roadmap
route to the general aux-variable method; see `REDUCE_PLAN.md`.

## Reduce — elementary real functions (radicals, Abs, Log, inverse-trig, Floor/Mod)

`Reduce[…, x, Reals]` now solves univariate statements built from `Abs`, real
radicals `u^(p/q)`, rational poles, `Log`, bounded-domain inverse-trig, and the
isolated integer-part forms (`Floor`/`Ceiling`/`Round`, `Mod`) — a class that
previously bubbled back unevaluated (or echoed the input as `poly == 0`). A
statement containing such a function defaults its domain to the Reals. Examples:

```
Reduce[Sqrt[x+3-4Sqrt[x-1]] + Sqrt[x+8-6Sqrt[x-1]] == 1, x]   ->  5 <= x <= 10
Reduce[Sqrt[x+1-2Sqrt[x]] + Sqrt[x+16-8Sqrt[x]] == 3, x, Reals] -> 1 <= x <= 16
Reduce[(2x-1)^2 (Sqrt[x+4-4Sqrt[x]]+Sqrt[x+9-6Sqrt[x]]-1)==0, x, Reals]
                                                    -> x == 1/2 || 4 <= x <= 9
Reduce[Abs[Abs[x]-2] + Abs[Abs[x]-5] == 3, x, Reals] -> -5<=x<=-2 || 2<=x<=5
Reduce[(Abs[x+3]+Abs[x-3])/x == 2, x, Reals]         -> x >= 3
Reduce[Sqrt[x^2-4] == Sqrt[x-2] Sqrt[x+2], x, Reals] -> x >= 2
Reduce[Floor[2x-1] == 3, x, Reals]                   -> 2 <= x < 5/2
Reduce[Mod[x, 2Pi] == x - 2Pi, x, Reals]             -> 2Pi <= x < 4Pi
Reduce[ArcSin[x] + ArcCos[x] == Pi/2, x, Reals]      -> -1 <= x <= 1
Reduce[Log[x^2] == 2 Log[-x], x, Reals]              -> x < 0
Reduce[Abs[x] < 1, x, Reals]                         -> -1 < x < 1
Reduce[Sqrt[x-1] == 2, x, Reals]                     -> x == 5
```

**How** (`REDUCE_PLAN.md` Phase 9): a general univariate real **sign diagram**
(`src/solve/reduce_realdiag.c`) reusing the existing 1-D cell decomposition and
its emission. Preprocessing (`src/solve/reduce_realfn.c`) rewrites the statement
so the diagram can consume it — `Abs[u]` is eliminated by sign-splitting on the
argument, `Mod[u,m]` becomes `u - m Floor[u/m]`, and an isolated
`Floor`/`Ceiling`/`Round` relation expands to its defining inequalities. The
remaining radical/`Log`/inverse-trig atoms are placed on a diagram whose
breakpoints are the `Solve`-over-Reals roots (descending polynomial factors so an
isolated root of a squared factor survives an identity `{{}}`), the poles, and the
**domain boundaries** from a head→real-domain table (radicand `≥0`, `Log` arg
`>0`, `ArcSin`/`ArcCos` arg in `[-1,1]`, …). Each cell is tested under a
**real-domain gate**, so a point where the identity holds only in ℂ
(`ArcSin[2]+ArcCos[2]==Pi/2`, or `Sqrt[x^2-4]==Sqrt[x-2]Sqrt[x+2]` at `x=0`) is
correctly excluded; transcendental breakpoints (multiples of `Pi`) are ordered by
a numeric-sign fallback. A supporting fix in `src/solve/reduce_atom.c` skips
`Together` for branch-cut transcendentals, since `Together[Log[x^2]-2Log[-x]]`
collapses to the constant `-2 I Pi` — wrong over the reals.

Soundness is preserved: a free parameter, an undecidable sign, or an unsupported
domain node leaves `Reduce` unevaluated. At a removable `0/0` singularity the
sound open boundary is reported (`x/Sqrt[x^2]+Sqrt[x^2]/x==2 -> x > 0`). Covered
by `tests/test_reduce.c` (`test_real_functions`) and the sampling corpus
(`tests/reduce_corpus.m`).

## Reduce — `Max`/`Min`, polynomial-in-`Floor`, and a piecewise soundness gate

Two wrong-answer bugs in the Phase 9 real-function path, both caused by an opaque
atom reaching the general sign diagram (which finds breakpoints only from `Solve`
roots, poles and domain boundaries) and being scored on a single all-of-ℝ cell:

```
Reduce[Max[x^2-1, 1-x^2] > 1/2, x, Reals]     (* was True  *)
    -> x < -Sqrt[3/2] || -1/Sqrt[2] < x < 1/Sqrt[2] || x > Sqrt[3/2]
Reduce[Floor[x]^2 - 3 Floor[x] + 2 <= 0, x, Reals]   (* was False *)
    -> 1 <= x < 3
```

Both are now rewritten away in `reduce_realfn_preprocess` (`src/solve/reduce_realfn.c`)
before the diagram runs:

- **`Max`/`Min` case-split.** An innermost `Max`/`Min[a_1,…,a_n]` is eliminated by
  branching on which argument is the extremum — `Or_i[ And[ a_i ≥ a_j (j≠i),
  stmt|_{node→a_i} ] ]` (`Min` uses `≤`) — the same shape as the existing `Abs`
  sign-split, so the residual is pure-polynomial and the exact engine gives the
  precise algebraic answer. Also fixes `Reduce[Min[x,1-x]>1/4] -> 1/4<x<3/4`,
  `Reduce[Max[x,1]>2] -> x>2`, and n-ary forms.
- **Polynomial-in-`Floor`.** A relation polynomial (any degree) in a *single*
  `Floor`/`Ceiling`/`Round` node — which the linear isolator declines — is solved
  by substituting a fresh integer variable and calling `Reduce[…, k, Integers]`;
  a bounded solution set (`k == 1 || k == 2`) expands each value back to its
  defining interval and merges (`1 <= x < 3`). Works for `Ceiling`/`Round` too.
- **Fixpoint driver.** The four rewrites (`Mod`→`Floor`, `Abs`, `Max`/`Min`,
  integer-part) are iterated to a fixpoint, so a split that exposes a fresh
  `Floor` or `Max`/`Min` leaf is picked up in a later pass.

A **piecewise-head soundness gate** in `reduce_univar_general`
(`src/solve/reduce_realdiag.c`) closes the class for good: if any atom still
carries a `Floor`/`Ceiling`/`Round`/`IntegerPart`/`Mod`/`Max`/`Min`/`Abs` term in
the variable after preprocessing declined to rewrite it (e.g. the unbounded
`Reduce[Floor[x]^2 > 5, x, Reals]`), the diagram declines (stays unevaluated)
instead of guessing from one sample. New corpus cases `rf-max-*`, `rf-min-*`,
`rf-floor-quad`, `rf-ceil-quad` in `tests/reduce_corpus.m`.

## Reduce — multivariate `Max`/`Min`, general piecewise functions, unbounded integers

Extends the piecewise support above to close the gaps it left: multivariate
`Max`/`Min`, every remaining piecewise head, and the unbounded integer sets that
previously declined.

- **General piecewise case-split.** One `eliminate_piecewise`
  (`src/solve/reduce_realfn.c`) driven by a `piecewise_clauses` table splits any
  of `Piecewise`, `Sign`, `UnitStep`, `Ramp`, `Clip`, `HeavisideTheta`, `Boole`,
  `UnitBox`, `IntegerPart`, `FractionalPart` into its first-match
  `Or_i[ And[ !g_0..!g_{i-1}, g_i, stmt|_{node->v_i} ] ]` (plus a default branch);
  a head with no default (`HeavisideTheta`) leaves its undefined point out of
  every branch. `IntegerPart`/`FractionalPart` reduce to `Floor`/`Ceiling`.

  ```
  Reduce[Sign[x-1] < 0, x, Reals]              -> x < 1
  Reduce[UnitStep[x-3] == 1, x, Reals]         -> x >= 3
  Reduce[Clip[x, {-2,2}] < 1, x, Reals]        -> x < 1
  Reduce[Piecewise[{{x^2, x>0}}, -x] > 2, x]   -> x < -2 || x > Sqrt[2]
  Reduce[Boole[x>0] + Boole[x>1] == 2, x, Reals] -> x > 1
  Reduce[IntegerPart[x] == 2, x, Reals]        -> 2 <= x < 3
  ```

- **Multivariate `Max`/`Min`/piecewise.** The selector splits (Abs, Max/Min, the
  piecewise heads) are variable-count- and domain-agnostic, so a new
  `reduce_piecewise_preprocess` runs them for `nv >= 2` and hands the polynomial
  `And`/`Or` result to the Fourier-Motzkin / CAD engines.

  ```
  Reduce[Max[x, y] > 2, {x, y}, Reals] -> x > 2 && y <= x || y >= x && y > 2
  Reduce[Abs[x] + Abs[y] < 1, {x, y}, Reals] -> the four sectors of the L1 ball
  ```

- **Unbounded integer sign diagram.** `reduce_univar_integers`
  (`src/solve/reduce_univar.c`) now emits one-sided rays for a satisfied tail
  (`Reduce[x > 0, x, Integers] -> x >= 1`, `Reduce[k^2 > 5, k, Integers] ->
  k <= -3 || k >= 3`) in addition to the existing bounded enumeration, which fixes
  the unbounded polynomial-in-`Floor` case through the integer sub-solve:

  ```
  Reduce[Floor[x]^2 > 5, x, Reals]    -> x < -2 || x >= 3
  Reduce[Ceiling[x]^2 > 5, x, Reals]  -> x <= -3 || x > 2
  ```

  `translate_ksol` accepts all six `k REL int` relations, and `ip_defining` gains
  the full `Ceiling` relation set (`Round` stays `Equal`-only: it is

## N — bare `N[expr]` now targets machine precision

Fixed `N[expr]` (one-argument) to give a **machine-precision** result even when
`expr` is already an approximate arbitrary-precision number, matching
Mathematica. `N[N[Pi, 100]]` now returns `3.14159` at `MachinePrecision`
instead of keeping the argument's 100 digits; `N[2.5\`100]` likewise collapses
to machine precision. The two-argument form is unchanged — `N[N[Pi, 100], 30]`
gives 30 digits, and it still never manufactures digits (`N[N[Pi, 100], 200]`
stays at 100).

Root cause: the one-argument `N` builtin set a `preserve_inexact` flag on
`NumericSpec` that told `numericalize` to keep an already-approximate MPFR leaf
at its precision under machine mode. That flag existed solely to implement this
(incorrect) behavior — every other call site set it `false` — so it has been
removed entirely from `src/numeric.{c,h}` and its ~15 downstream call sites.

## ComplexPlot — brighter default, 8-argument ColorFunction, muted pole chatter

Three fixes to `ComplexPlot` / `ComplexPlot3D` (`src/graphics/complexplot.c`):

- **Default no longer looks too dark.** The modulus was folded into the phase
  hue as a plain brightness multiplier `|w|/(1+|w|)`, which is `0.5` at
  `|w| = 1`, so a bounded function (`|f| ≈ 1` over most of the plane, e.g.
  `(z^2-1)/(z^2+1)`) rendered at ~50 % brightness everywhere. It is now an
  **HSL lightness** `L = |w|/(1+|w|)`: below `1/2` the saturated hue fades to
  black (zeros → black), above it toward white (poles → white). Mean cell
  luminance on the report case rose `0.265 → 0.523` (≈2×). The default stays
  byte-for-byte identical to `ColorFunction -> "Cyclic"` (both share
  `cp_ramp_color`).

- **`ColorFunction` now receives Mathematica's eight arguments.** A custom
  `ColorFunction` was called `f[Re[f], Im[f]]` (a 2-argument DensityPlot
  convention), so `ColorFunction -> (Hue[#8 + 0.5] &)` failed — `#8` was an
  unsupplied `Slot`. It now supplies `#1 Re[z]`, `#2 Im[z]`, `#3 Abs[z]`,
  `#4 Arg[z]`, `#5 Re[f]`, `#6 Im[f]`, `#7 Abs[f]`, `#8 Arg[f]`, each scaled to
  `[0,1]` across the sampled grid when `ColorFunctionScaling -> True` (the
  default). A one-argument colour map falls back to the scaled `Arg[f]`.
  `is_color_head` now also requires every colour component to be a real number,
  so a half-symbolic `Hue[0.5 + #8]` is rejected rather than handed to the
  renderer.

- **Spurious `Power::infy` at poles muted.** Sampling a function with poles hits
  `1/0` at the grid points sitting on a pole (`z = 0` for `(z^3-3)/z`; `z = ±i`
  for `1/(z^2+1)`); those cells are simply dropped, so the informational
  `Power::infy` messages are now muted during the sampling loop
  (`arith_warnings_mute_push/pop`), exactly as `Plot` and the numeric optimizers
  do. The compiled fast path also gained the `isfinite` guard the interpreter
  path already had, so a compiled pole no longer marks a cell valid with
  `|w| = inf` and poisons the `ColorFunctionScaling` ranges.

Docs and docstrings updated; leak-checked with a differential `valgrind` run
(no new "definitely lost" vs. the prior build); `autocompile_tests`,
`graphics_tests`, `graphics_sampling_tests` pass.

## Interval — special & piecewise functions thread over `Interval[...]`

Elementary functions already threaded over `Interval[{lo, hi}]` (`Sin`, `Exp`,
`Gamma`, …); most **special functions** and the **piecewise** heads did not, so
`Erfi[Interval[{0, 1}]]` or `Round[Interval[{-1/2, 5/2}]]` were left unevaluated.
They now thread the same way — rigorous enclosures where a bound can be
certified, clean symbolic fallback otherwise.

- **General derivative-sign certifier** (`interval_thread_call`, `src/interval.c`;
  wired into the evaluator in `src/eval.c` right after the builtin returns
  `NULL`). For any `NumericFunction` with a single `Interval` argument that no
  builtin handled, it interval-evaluates the symbolic derivative `D[f[x], x]`
  over each pair and, when the enclosure is entirely one sign, threads `f`
  monotonically. Rigorous (interval evaluation only over-estimates, so a
  certified sign is always correct) and general (reuses `D[]` and the
  interval-aware evaluator — no per-function monotonicity analysis). New
  coverage includes `Erfi`, `ExpIntegralEi`, `LogIntegral`, `PolyLog[n, ·]`, and
  the incomplete `Gamma[a, ·]`. A small recursion cap keeps oscillatory heads
  (`BesselJ`, `Sinc`, …) fast and symbolic instead of chasing a derivative chain
  that never bottoms out.

- **Bespoke monotone-sub-domain rows** (`interval_apply_function`) for functions
  whose derivative is self-referential/awkward but which are simply monotone:
  `InverseErf` (on `(-1, 1)`), `InverseErfc` (on `(0, 2)`), `ProductLog`
  (on `(-1/e, ∞)`), `HarmonicNumber` (on `(-1, ∞)`), and `Erfi` (on ℝ).

- **Piecewise/step functions** `UnitStep`, `Ramp`, `Round`, `IntegerPart` now
  thread (non-decreasing, so endpoint threading is a rigorous enclosure),
  joining `Floor`/`Ceiling`. The sawtooth `FractionalPart` stays symbolic.

Verified by the extended `tools/interval_fuzz.py` (`make check-interval`, ~30k
random containment checks now including the new heads) and new cases in
`tests/test_interval.c`.

## Integrate — `nonelem` message emitted once, and no more double cascade

`Integrate[Log[x] Log[Log[x]]/x^2, x]` printed the `Integrate::nonelem`
diagnostic **four** times — twice naming internal recursion variables
(`Integrate`DerivativeDivides`u$N`) and twice naming the real integrand. Two
independent defects were behind it:

- **Leaky recursive messages.** `DerivativeDivides` substitutes `u = Log[x]` and
  recurses via `Integrate[u Log[u] E^(-u), u]`, which reaches the same
  `RischTranscendental` decision stage and emitted a `nonelem` message naming the
  internal gensym. The message now fires only at the outermost integration
  (`g_integrate_depth <= 1`, tracked around the method cascade in
  `builtin_integrate`), so a sub-integral spawned by an internal substitution
  never names its own recursion variable — a user diagnostic only ever names the
  user's integrand.

- **Double cascade.** `Integrate[Times[Log[x], Log[Log[x]], Power[x,-2]], x]`
  reorders under Orderless on the first `evaluate_step`, so the fixed-point loop
  ran a second step and re-invoked the *entire* (Eliminate/Solve-driven) method
  search on the byte-identical integrand — doubling the work and the message.
  `builtin_integrate` now carries a per-command fail-memo: an integrand the
  cascade already proved has no answer this top-level evaluation short-circuits
  to `NULL` immediately. The memo is a fixed 32-slot table keyed on a new
  `eval_toplevel_id()` (bumped once per user command in `evaluate()`), so it
  needs no dynamic allocation and self-invalidates every command — a genuine
  re-run in a later command re-runs the search and re-warns. Several distinct
  failing integrals in one command (e.g. a `List` of them) each keep their own
  slot, so none re-emits when the outer structure takes a second pass.

Result: the reported integral prints the message exactly once, naming
`(Log[x] Log[Log[x]])/x^2`, and the expensive search runs once instead of twice.
Solvable, definite, and list-threaded integrals are unchanged.

## Integrate — wrong `0` for transcendental-coefficient / single-extension integrands

`Integrate[Sin[x]/Log[x], x]` returned a **wrong `0`** (and likewise
`Cos[x]/Log[x]`, `Tan[x]/Log[x]`, `Sin[x]/Log[x]^2`, `ArcTan[x]/Log[x]`,
`Gamma[x]/Log[x]`, `Sin[x]/(1+E^x)`, `BesselJ[0,x]/Log[x]`, …). Root cause: the
single-extension Risch cases (`rt_frac_try`, `rt_hermite_try`,
`rt_hyperexp_case` in `risch_singleext.c`) kernelize the integrand at `t = Log[x]`
(or `E^x`) and then solve a Rothstein-Trager polynomial identity with
`SolveAlways[..., {t, x}]`. Their gate only checked that numerator/denominator
were polynomials in `t` with no *other* log/exp of x — it did **not** verify the
coefficients were rational in x. A transcendental coefficient such as `Sin[x]`
slipped through as a degree-0 "polynomial" in `t`; `SolveAlways` then treated the
stray `Sin[x]` as an independent unknown and solved it away
(`{{Sin[x] -> 0, k -> 0}}`), certifying a bogus antiderivative whose residue
symbols zeroed out to `0`.

Fix: a `C(x)(t)` membership gate (`rt_is_ratl_in_xt`) now guards all three cases
— the kernelized numerator and denominator must be genuine rational functions of
x and the kernel `t` (built only from x, t, x/t-free constants, and Plus/Times/
Power-with-integer-exponent). Integrands outside that field (a transcendental or
algebraic coefficient of x) are declined instead of mis-certified. Every such
integrand now stays unevaluated (with the usual `nonelem` note), while genuine
`C(x)(t)` integrals — `1/(x Log[x]) -> Log[Log[x]]`, `1/(1+E^x)`,
`1/(E^x (1+E^x)^2)`, the special-function recognizers, and elementary
`Sin[x] E^x` (handled by the multi-kernel path) — are unchanged.

## Graphics — Plot3D/Graphics3D frame ticks (inward marks + minor sub-ticks)

The `Axes` bounding box for `Plot3D`, `ParametricPlot3D`, `ComplexPlot3D` and
raw `Graphics3D` previously drew only numeric axis labels — no tick marks. Each
of the three edges meeting at `(xmin, ymin, zmin)` now carries proper ticks,
matching Mathematica's look:

- **Major ticks** land on the shared `nice_step` values, are labelled, and point
  **inward** (into the box); the numeric label sits just **outside** the box on
  the opposite side of the edge.
- **Minor sub-ticks** subdivide each major interval, shorter and unlabelled,
  using the same `frame_minor_divs` policy the 2D frame uses (a major step of 1
  splits into 5, 2 into 4, 5 into 5 — so minors always fall on round values).

Implementation (`src/graphics/render3d.c`, replacing the label-only
`draw_tick_label3`):

- `box_edge_normal` gives the screen-space **outward** unit normal at an edge
  point: `(P − boxcentre)` with the along-edge component zeroed, projected and
  normalised in screen space. Ticks are drawn a fixed pixel length *against*
  that normal (inward); labels a fixed gap *along* it (outward). Working in
  screen space makes every mark a constant pixel length regardless of
  `BoxRatios` scaling or perspective foreshortening.
- `draw_edge_ticks` iterates by **integer index over the minor step**, so major
  detection (`i % sub == 0`) and label values (`(i/sub)·step`) are exact — no
  float-accumulation drift, no spurious `-0` or `0.9999` labels.
- Both render paths (interactive `graphics3d_show` and the offscreen
  `Export`/region path) call the one function, so they cannot drift; labels
  still format from the untransformed data bbox → true data values under any
  `BoxRatios` transform.
- `frame_minor_divs` moved from `render.h` to `render_common.h` (its natural
  home next to `nice_step`) so both the 2D and 3D renderers share the one
  tick-subdivision policy. `render.h` deliberately stays raylib-free (core files
  such as `imageio.c` include it in `USE_GRAPHICS=OFF` builds).

## Reduce — Phase 6d: n-variable Cylindrical Algebraic Decomposition over the Reals

`Reduce[expr, {x1, ..., xn}, Reals]` now solves nonlinear real inequality
statements in **three or more** effective variables (previously declined). The
two-variable CAD from Phase 6a–6c is generalized to a single recursive engine.

- **Recursive engine** (`reduce_cad_nvar` in `src/solve/reduce_cad.c`): an
  iterated McCallum projection builds the projection stack (discriminant, leading
  coefficient, pairwise resultant, all factored), eliminating the variables from
  last to first; the base sign diagram is then lifted by a recursive descent that
  substitutes each cell's rational sample, isolates the next variable's real
  roots, and recurses, with partial-CAD pruning at every level and the innermost
  dimension merged into a symbolic region. Truth is decided at one sample per
  full-dimensional cell by the exact real-algebraic sign oracle.
- **Output**: strict inequalities read as a clean nested conjunction, e.g.
  `Reduce[x^2+y^2+z^2 < 1, {x,y,z}, Reals]` ->
  `-1 < x < 1 && -Sqrt[1-x^2] < y < Sqrt[1-x^2] && -Sqrt[1-x^2-y^2] < z < Sqrt[1-x^2-y^2]`;
  `Reduce[x y z > 0, {x,y,z}, Reals]` -> the four positive octants;
  `Reduce[x^2 < 1 && y^2 < 1 && z^2 < 1, {x,y,z}, Reals]` -> the open box;
  `Reduce[x^2+y^2+z^2 >= 0, ...] -> True`, `... < 0 -> False`. A **closed** region
  currently emits a correct but verbose union of cells (the boundary spheres/arcs/
  poles listed separately); the n-D boundary merge that would close an outer range
  (`-1 <= x <= 1 && ...`) is a later cosmetic pass — the answer is complete and
  sound either way.
- **Soundness invariant** (unchanged): an undecidable sign/ordering, an irrational
  non-innermost breakpoint (v1 rational-fibre regime — real-algebraic-coefficient
  fibre isolation is deferred, so e.g. `x^2+y^2+z^2 <= 2` with base `±Sqrt[2]`
  declines), an un-emittable fibre, or an interval nullification (McCallum
  well-orientedness augmentation deferred) all leave `Reduce` unevaluated rather
  than emit a wrong formula. The two-variable path and its boundary-merged output
  are unchanged (byte-identical).
- **Tests**: `tests/test_reduce.c` gains `test_cad_nvar` (clean-form,
  True/False, and decline pins); `tests/reduce_corpus.m` gains `cad3-*` /
  `cad4-*` rows verified by the form-agnostic sample-point oracle.
  `make check-c99` clean; valgrind leak-clean (only macOS ObjC-runtime baseline
  noise).

### Phase 6d Stage B: n-D boundary merge (closed regions)

The recursive engine now builds a cell **tree** and runs an n-D boundary merge —
the recursive generalization of the two-variable merge — so a **closed** region
closes its outer ranges instead of listing the boundary cells:
`Reduce[x^2+y^2+z^2 <= 1, {x,y,z}, Reals]` ->
`-1 <= x <= 1 && -Sqrt[1-x^2] <= y <= Sqrt[1-x^2] && -Sqrt[1-x^2-y^2] <= z <= Sqrt[1-x^2-y^2]`
(matching the two-variable disk); the sphere surface, closed half-ball, and the
4-variable closed ball merge likewise. A run of interval cells sharing one
symbolic template absorbs the section between (and at the ends) whose fibre equals
the template's limit there; **cell equality is decided by sampling** the emitted
sub-formulas over a grid drawn from the cell structure, so any undecidable
comparison leaves the already-correct unmerged (verbose) form — soundness over
completeness, verified by the corpus oracle. Strict regions stay open. Version
bumped to 0.088.

## Reduce / Solve — zero-dimensional nonlinear systems (issue #69)

`Reduce` and `Solve` now solve a conjunction whose polynomial **equations** pin
the variety to finitely many points (a zero-dimensional ideal), optionally
carrying polynomial inequality / disequation constraints — the case both engines
previously left unevaluated. This is the three-circle system from issue #69:

```
Reduce[u^2 + v^2 == 9 && u^2 + (a + v)^2 == 36 && (a + u)^2 + v^2 == 25 &&
       u > 0 && v > 0 && a > 0, {u, v, a}]
  -> u == ... && v == ... && a == ...        (the single all-positive branch)

Solve[<same>, {u, v, a}]   -> {{u -> ..., v -> ..., a -> ...}}
```

New engine `reduce_zerodim` (`src/solve/reduce_zerodim.{c,h}`), shared by both:

1. Split each conjunct into equations `E` and side relations `O` (`<`,`<=`,`!=`).
2. Solve `E` over the complexes with the existing polynomial-system solver; a
   finite, fully-determined answer means `E` is zero-dimensional (a parametric /
   underdetermined answer means it is not, and the engine **declines**).
3. Keep each solution branch only if every side relation holds there and — over
   the Reals — every coordinate is real, decided **exactly** by the FLINT
   `qqbar` algebraic-number oracle (sign / equality / realness). An undecidable
   test **declines** (sound over complete).

Complete for zero-dimensional systems (the finite solution set is enumerated and
filtered exactly) and sound (any gap yields a decline). `Reduce` emits an `Or` of
`And(var == value)`; `Solve` emits the surviving branches as solution rule-lists.
Wired into `reduce.c` (Complexes and Reals fallbacks, after the linear and CAD
engines) and `solve.c` (an equations-with-constraints pre-pass mirroring the
`Integers` pre-pass). New oracle `flint_qqbar_is_real` distinguishes a non-real
branch (drop) from an undecidable one (decline). Newly-solved cases that were
`decline` are promoted in the corpora; new corpus + unit cases cover decoupled
systems, complex-branch rejection over the Reals (`x^2+y^2==1 && x==2 -> False`),
and the issue's three-circle system. Reduce corpus 158/158, Solve corpus 99/99;
`make check-c99` clean; valgrind shows no new leaks.

## Parser — backslash line continuation in scripts and `Get` (issue #69)

A backslash immediately before a newline is now a line continuation (Mathematica
syntax): the lexer (`skip_whitespace`, `src/parse.c`) joins the two physical
lines into one logical line without emitting a statement break, handling LF, CR,
and CRLF endings. Previously a `\`-continued `.m` file read via `Get[]` / `-file`
failed with `Unexpected character: '\'`. A backslash **not** before a newline
still errors as before, so stray backslashes are unaffected.

## Linear algebra — seamless machine → arbitrary-precision fallback on overflow

`Det`, `Norm`, and `Normalize` now defer from machine `double` to arbitrary
precision when the machine result would over/underflow, instead of returning
`inf` / `0` / a zero vector for inputs whose true answer is representable.

- **`Det` (machine reals)** — the determinant is the product of the LU pivots,
  which can leave the IEEE-double range even for an ordinary matrix (a 200×200
  `RandomReal[{-10,10}]` matrix has `|Det| ≈ 10^340`). `Det[arr]` returned
  `-inf.0`; it now re-accumulates the pivot product in a 53-bit-mantissa MPFR
  value (wide exponent) and returns `≈ -1.08×10^340`, correct to machine
  precision (rel. err ~1e-14 vs. the exact determinant). A mid-product underflow
  that previously collapsed a representable determinant to `0.0` (e.g.
  `Det[DiagonalMatrix[{1e-200, 1e-200, 1e300, 1e300}]]`) now returns the true
  `1e200`. Genuinely singular matrices still return `0`. The complex branch has
  the same protection (`Complex[mpfr, mpfr]` on overflow). New helpers
  `nd_real_det_result` / `nd_complex_det_result` in `src/linalg/ndlinalg.c`.
- **`Det` (arbitrary-precision matrices)** — a genuine MPFR matrix (precision >
  machine) previously fell through to the `O(n!)` Laplace expansion and hung for
  `n ≳ 12` (a 16×16 aborted at 20 s). New `mpfr_det_dispatch`
  (`src/linalg/ludecomp_mpfr.c`, declared in `ludecomp_internal.h`) computes
  `sign(P)·∏U[k,k]` from the existing MPFR Doolittle LU in `O(n^3)`; wired into
  `builtin_det` (`src/linalg/det.c`) after the FLINT exact path and before
  Laplace. A 40×40 MPFR determinant is now instant.
- **`Norm` / `Normalize` (machine vectors)** — the vector 2-norm hand-rolled
  `Sqrt[Σ x^2]`, which overflowed once any `|x_i| > ~1.3×10^154`
  (`Norm[{1e200, 1e200}]` → `inf`) and made `Normalize` return the zero vector.
  The 2-norm now uses LAPACK `dnrm2`'s running-scale recurrence
  (`nd_vec_2norm`), and the `p`-norm scales by the max component; both in
  `src/linalg/ndlinalg.c`. A small unpacked machine `List` is routed to this
  fast path from `src/linalg/norm.c` (exact vectors keep `Sqrt[5]`-style exact
  answers; MPFR vectors stay symbolic, their wide exponent already safe).
- **`CharacteristicPolynomial`** recorded as `EXEMPT` in
  `tools/compile_coverage.py` — it returns a symbolic `Plus` in `x`, not a
  machine array, so (like `Eigenvalues` / `Eigenvectors`, whose result type/shape
  is data-dependent) it cannot lower to a statically-typed compiled register.
  `Det` continues to compile via `ndla_det`.

`Eigenvalues` / `Eigenvectors` on machine matrices already use LAPACK `dgeev`
(finite and fast at 200×200) and were unaffected. Relevant test suites
(`linalg`, `ndarray_linalg`, `normalize`, `eigen`, `ludecomposition_*`,
`compile_linalg`) all green.

## RootReduce — threads over a Rule; `Solve[...] // RootReduce` fixed (bug fix)

`RootReduce` now threads over an (immediate) `Rule`, so applying it to a `Solve`
result reduces the right-hand side of each `u -> value` entry — exactly as
`RootReduce` already reduces each `u == value` in a `Reduce` result. For the
Goursat three-circle system, `Solve[...] // RootReduce` and
`Reduce[...] // RootReduce` now return the *same* `Root` objects
(`u -> Root[207025 - 226216 #1^2 + 31520 #1^4 &, 3]`, ...).

Previously `RootReduce[u -> value]` emitted `RootReduce::argx: called with 0
arguments` and left the rule unevaluated. Root cause: the option/positional
splitter (`is_option_rule` in `src/rootreduce.c`) treated *any* `Rule` with a
symbol left-hand side as a trailing option, so `u -> value` was consumed as an
option and no positional argument remained. It now recognises only a `Rule`
whose LHS names a *registered* option of `RootReduce` (i.e. `Method`, read from
`Options[RootReduce]` via `symtab_get_options`) as an option; every other
symbol-LHS rule is a positional argument. The generic "map RootReduce over the
parts and re-evaluate" tail of the relational threading was factored into a
shared `thread_parts` helper and reused for the `Rule` case: the free-variable
LHS is left intact (`RootReduce` of a bare symbol is the identity) and only the
RHS is reduced. `RuleDelayed` is deliberately *not* threaded — it holds its RHS,
so threading would strand an un-fired `RootReduce` there, and `Solve`/`Reduce`
results are always immediate rules. The `Method` option and the `argx`/`mtd`
diagnostics are unchanged. Regression coverage: `test_rootreduce_rule` in
`tests/test_rootreduce.c`.
