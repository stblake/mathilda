# Changelog: week of 2026-08-24 (Mon) – 2026-08-30 (Sun)

## DSolve — first-order linear PDEs (method of characteristics), milestone M6 start

`DSolve` now solves first-order linear PDEs with constant leading coefficients,
`a u_{v1} + b u_{v2} + c(v1,v2) u == f(v1,v2)`. The characteristic invariant is
`ξ = a v2 - b v1`; along a characteristic (parametrised by v1, v2=(ξ+b v1)/a) the
PDE is the linear ODE `u_{v1} + (c/a) u = f/a`, solved by the integrating factor,
so `u = Exp[-∫ c/a] ( C[1][ξ] + ∫ Exp[·] f/a )` with `ξ -> a v2 - b v1`. The
homogeneous solution carries the arbitrary function `C[1][ξ]`. Solves the
transport equation `u_t + c u_x == 0 → C[1][x - c t]`, `3u_x+5u_y==x`, and
`u_x+3u_y+u==1 → 1 + E^-x C[1][-3x+y]` (matches Wolfram).

Substrate: the `is_pde` dispatch route, plus `dsolve_run_pde` with a
2-variable-`Function` assembler and a PDE verify that (a) substitutes the
derivative TERMS with `D[body,v]` — the evaluator does not reduce
`Derivative[i,j][Function[...]][...]` — and (b) replaces the arbitrary function
with a concrete `C[1][z_]:>Sin[z]` — zero_test cannot sample an arbitrary
function. (Both evaluator limitations, and a segfault in
`D[Function[{x,y},...C[1]...]][x,y]`, are pre-existing and worked around here.)

## DSolve — reduction of order (nonlinear 2nd-order missing y)

`DSolve`ReductionOfOrder` reduces a second-order ODE missing the dependent
variable, `y''==F(x,y')`, to a first-order equation in `p=y'` (solved by
recursing into the scalar engine), then recovers `y=Integrate[p,x]+C[2]`. Solves
`y''==(y')^2 → C[2]-Log[C[1]-x]`. It requires `D[Integrate[p,x],x]==p` before
accepting — a pre-existing `Integrate` bug returns `0` for some rational
integrands with a symbolic parameter (e.g. `Integrate[1/(C[1]-x^2/2),x]`), and the
resulting degenerate `y=const` would otherwise pass back-substitution verify
(a constant trivially satisfies the equation); the guard makes it decline honestly
instead. (The Integrate bug is pre-existing and out of scope here.)

## DSolve — systems of ODEs, milestone M4 (systems)

`DSolve` now solves systems (multiple dependent functions). The substrate gained
`dsolve_verify_system` / `dsolve_fit_system` / `dsolve_assemble_system` and a
`nfun > 1` dispatch route; two system methods:

- **`LinearFirstOrderSystem`** — first-order constant-coefficient `Y' == A Y + b`
  via the eigen-decomposition of A: real eigenvalue λ → `C e^{λx} v`; a complex
  pair `α ± β i` (eigenvector `p ± q i`) → the real solutions
  `e^{αx}(Cos[βx] p ∓ Sin[βx] q)`; constant forcing → particular `-A^{-1} b`.
  Solves `{y'==y-2z, z'==y-z, y[0]==1, z[0]==4}` (complex eigenvalues → `Cos/Sin`)
  and `{y'==z, z'==y}` (real). Diagonalizable case.
- **`DecoupleSystem`** — each equation involving only its own function is solved
  by recursing into the scalar engine, with the generated constants renumbered so
  they don't collide; handles variable-coefficient components
  (`{y'==x^2 y, z'==5z}` → `{y->E^(x^3/3)C[1], z->E^(5x)C[2]}`).

Also fixed a packed-list trap: `Inverse[A].b` and other integer-valued list
results come back as *packed* NDArray lists, which `head_is` / `data.function.args`
cannot read — the new `ds_delist` materialises them before component access.

## DSolve — Euler–Cauchy equations + linear-ODE substrate refactor, milestone M3 (in progress)

**Special-function recognizer** (`DSolve`SpecialFunctionForm`): matches the
normalised second-order form `y'' + P y' + Q y == 0` against a table.
- **Airy**: `P=0`, `Q` linear in x → `AiryAi[u]`, `AiryBi[u]`,
  `u = A^(1/3)(x + B/A)`; `y''-xy==0` → `C[1]AiryAi[x]+C[2]AiryBi[x]` (verifies).
- **Bessel / modified Bessel**: `P=1/x`, `Q = ±1 − ν²/x²` → `BesselJ/Y[ν,x]` or
  `BesselI/K[ν,x]` (ν recovered as `Sqrt[x²(s−Q)]`). Correct heads; the residual
  reduces only via Bessel recurrences that `zero_test` cannot decide, so the
  (structurally exact) solution is kept rather than rejected.


`DSolve`EulerCauchy` solves the equidimensional equation
`a_n x^n y^(n) + ... + a_0 y == g(x)` via the indicial polynomial
`Σ a_k (r)_k` (falling factorial, from the trial `y = x^r`): real roots →
`x^r (Log x)^j`, complex-conjugate pairs → `x^a Cos/Sin[b Log x]`, repeated roots
→ `Log[x]` powers. Matches the reference `x²y''+4xy'+7y==0` →
`(C[1]Cos[√19/2 Log x] − C[2]Sin[√19/2 Log x])/x^(3/2)`. Inhomogeneous forcing is
handled by variation of parameters (real-root forcing works; a complex-root
Wronskian integral that the integrator can't do declines gracefully).

Refactor: the linear-ODE machinery is now shared substrate —
`dsolve_linear_coeffs` (reads `c_k(x)` of `y^(k)` and the forcing `g`),
`dsolve_analyze_roots` (distinct roots + multiplicity + Im, deduplicated), and
`dsolve_variation_of_parameters` (Wronskian/Cramer particular solution) — used by
both `DSolve`LinearConstantCoefficients` and `DSolve`EulerCauchy` (const-coeff
was rewritten onto these with no behavior change).

## DSolve — linear constant-coefficient ODEs, milestone M2

`DSolve`LinearConstantCoefficients` solves `a_n y^(n) + ... + a_0 y == g(x)` for
constant `a_k`, any order:

- **Characteristic polynomial.** Coefficients are read off the residual by
  replacing `y^(k)[x]` with symbols and taking derivatives; `char = Σ a_k λ^k`.
- **Roots + multiplicity.** Distinct roots via `Solve` (deduplicated), each
  root's multiplicity from the derivative test (`char^(j)(r)==0`). Real roots →
  `x^k E^(rx)`; complex-conjugate pairs → the real forms `x^k E^(ax) Cos[bx]`,
  `x^k E^(ax) Sin[bx]` (no sign decision needed — `{Cos,Sin}[bx]` spans the same
  space for either sign of b).
- **Forcing.** Inhomogeneous `g(x)` handled by variation of parameters over the
  fundamental set (Wronskian + Cramer's rule + `Integrate`), the particular
  solution then `Simplify`d.
- **BVP.** Multi-point conditions fit through the shared substrate
  (`y''+y==0, y[0]==0, y[π/2]==1` → `Sin[x]`).

Solves the reference examples `y''+4y==7`, `y''+4y'+5y==0`, `y'''+4y'==5y`
(→ `E^x` + `E^(-x/2)(Cos,Sin)[√19 x/2]`), repeated roots `y''-2y'+y==0`
(→ `C[1]E^x + C[2] x E^x`), and IVP/BVP. Known cosmetic gap: for simple forcing
the var-params particular can retain a homogeneous component (correct + verified,
less tidy than undetermined coefficients).

## DSolve — first-order family completed, milestone M1

Four more first-order methods on the M0 substrate, each also callable as
`DSolve`<Method>[...]`:

- `DSolve`Bernoulli` — `y'[x] == A(x) y + B(x) y^n` (n≠0,1) via `v = y^(1-n)`.
  The exponent n is recovered from the RHS without assuming it is an integer
  (`Y Q_Y / Q` with `Q = F - Y F_Y`), so negative/fractional n work.
- `DSolve`Homogeneous` — `y'[x] == F(y/x)` via `y = v x` (degree-0 homogeneity
  detected by substituting `Y -> v x` and requiring the result free of x).
- `DSolve`Exact` — `M + N y' == 0`, exact (`M_y == N_x`) or made exact by an
  integrating factor `μ(x)` or `μ(y)`; solves the potential `F(x,y) == C[1]`.
- `DSolve`Clairaut` — `y == x y' + f(y')`, general lines `y = C[1] x + f(C[1])`;
  with `IncludeSingularSolutions -> True` the singular envelope is added.

New shared substrate helpers: `dsolve_linear_factor_solve` (integrating-factor
linear solve, shared by Linear/Bernoulli), `dsolve_algebraic_residual`
(`R(x,Y,p)` for methods not solved for y'), `dsolve_extract_solutions` (strips
`ConditionalExpression`), and `ds_free_of` — a **derivative-based** free-of-variable
test (`D[e,var]==0`) that, unlike a syntactic scan, sees through unsimplified
rational forms (this is what makes Bernoulli's `n=-1` detection over `(x²+y²)/(xy)`
work).

## DSolve — symbolic ODE solver, milestone M0 (substrate + first-order core)

New builtin `DSolve` (`src/calculus/dsolve.c`), the symbolic analogue of
`Integrate`: a cascade polyalgorithm whose dispatcher tries a sequence of methods,
each also callable as `DSolve`<Method>[...]`. Attributes `HoldAll, Protected,
ReadProtected`; docstring in `src/info.c`; symbol `SYM_DSolve`. See
`DSOLVE_PLAN.md` for the full method catalog and roadmap.

- **Shared substrate** (`dsolve_common.{c,h}`): parses
  `DSolve[eqn, u|u[x]|{...}, x|{x,xmin,xmax}, opts]` into a `DSolveProblem`
  (dependent/independent variables, orders, residuals, split-out point
  conditions, output form, options `GeneratedParameters`/`Assumptions`/`Method`/
  `IncludeSingularSolutions`). Every candidate branch is **verified** by
  substituting `u -> Function[{x}, body]` into each residual and rejecting only a
  *decidable* non-zero (`zero_test_decide`); initial/boundary constants are
  **fitted** via `Solve`; `C[k]` is renamed to the requested `GeneratedParameters`
  head; results assemble to `{{u -> Function[...]}}` or `{{u[x] -> ...}}`.
- **Methods:** `DSolve`Quadrature` (`y^(n)==f(x)`, integrate n times + constant
  polynomial), `DSolve`LinearFirstOrder` (`y'+p y==q` via integrating factor),
  `DSolve`Separable` (`y'==g(x)h(y)` via `∫dy/h==∫g dx`).
- **Reference examples** solved: `y'+y==a Sin[x]`, `y'==3y` (with IVP `y[0]==5`
  → `5 E^(3x)`), `y'==-3y^2, y[1]==2` → `2/(6x-5)`, `y''==7` → `C[1]+C[2]x+7x²/2`.
  Unsupported equations (e.g. 2nd-order constant-coefficient, not yet
  implemented) stay symbolic rather than returning a wrong answer.
- **Tests:** `tests/test_dsolve.c` (back-substitution / IVP / output-form /
  named-method / decline coverage). DSolve is a symbolic head — a documented
  exemption from the packed-aware and Compile surfaces.


## Reduce — Phase 6e: McCallum well-orientedness augmentation (v0.125)

Completes the CAD roadmap. The n-variable Reals CAD (`src/solve/reduce_cad.c`)
previously **declined** (returned unevaluated) whenever a fibre polynomial
*nullified* — vanished identically in the fibre variable — at the interior sample
of a **positive-dimensional** cell. That decline was sound but cost real answers:
`Reduce[x^2 - y^2 z == 0, {x,y,z}, Reals]` bailed even though Mathematica solves it.

- **Why it happened.** `x^2 - y^2 z`, as a polynomial in the fibre variable `z`, is
  `-y² z + x²`. McCallum projection adds the *leading* coefficient `-y²` (so `y=0`
  is a breakpoint) and the discriminant, but **not the constant term `x²`** — so the
  `x`-axis is never split at `x=0`. When an `x`-interval's sample lands on `0` (with
  `y=0`), the atom becomes `0==0` (true for all `z`) *at* the sample but is false just
  off it: the cell is not truth-invariant, so bailing was correct.
- **The fix (McCallum augmentation).** When a positive-dimensional nullification is
  detected, the build now reports the offending factor and its fibre level (new
  `NullReport`, threaded through `cad_build`/`cad_leaf`). The driver
  `reduce_cad_nvar` adds **all** of that factor's coefficients w.r.t. its fibre
  variable to the projection level below (via the existing `add_proj`, which factors
  and dedups the already-present leading one away), **re-derives the lower projection
  stack**, and rebuilds — so the nullification locus becomes a cell boundary and no
  positive-dimensional cell straddles it. Bounded to four augmentation rounds; a
  nullification that persists still declines. **Resampling to a generic point was
  rejected as unsound** — it would drop the `x=0` solution slice.
- **Cost model.** The common case never nullifies, so `cad_build` succeeds on the
  first round and the augmentation path is not entered — every non-nullifying CAD
  runs the identical code and timing (4 common 3-/4-var cases in 0.14 s). Only a
  genuine nullification pays for the extra rounds.
- **Scope.** The 2-variable driver (`reduce_cad`/`lift_fiber`) is provably
  well-oriented (atom pre-factoring confines nullification to 0-dim sections) and is
  left unchanged; `reduce_cad_qe` (Phase 7) passes `NULL` and keeps its plain
  sound-decline. Soundness invariant preserved: undecidable, or nullification that
  survives augmentation, still returns unevaluated.
- **Verification.** `tests/test_reduce.c::test_cad_well_oriented` (three cases now
  solve; a 4-var system still sound-declines); three `6e-*` corpus rows whose
  sample-oracle **certifies each emitted formula equivalent to its input** (corpus
  170/170); an independent `{x,y,z}`-grid equivalence check for `x^2-y^2 z==0` (zero
  mismatches). Reduce + Solve suites/corpora green; `check-c99` clean; valgrind at the
  macOS baseline (13,440/420, none attributable — the restart frees each superseded
  projection/cache generation). This closes the last CAD roadmap item (§6);
  **7-extended's algebraic free-variable-boundary sub-case remains** the only open
  Reduce item.

## Reduce — Phase 7-extended: multi-variable & alternating quantifier elimination (v0.124)

`Resolve` / `Reduce`'s quantifier-elimination engine (`src/solve/reduce_qe.c` +
the `reduce_cad_qe` seam in `src/solve/reduce_cad.c`) now handles the two regimes
it previously declined: **≥ 2 free variables** and **alternating quantifier
prefixes**. The headline case decides:

```
Resolve[Exists[x, x^2 + b x + c == 0], Reals]     c <= b^2/4   (i.e. b^2 - 4 c >= 0)
Reduce[ForAll[y, x^2 + y^2 >= z], {x, z}, Reals]   z <= x^2
Resolve[ForAll[x, Exists[y, x + y == 0]], Reals]   True
Resolve[Exists[y, ForAll[x, x^2 + y >= 0]], Reals] True
Resolve[ForAll[x, x^2 + a >= 0], Reals]            a >= 0
```

- **Multi-free-variable emission (`reduce_cad.c`).** `reduce_cad_qe` is generalized
  from one free variable to `nfree ≥ 1`: the free variables occupy the *outermost*
  CAD levels (canonical/alphabetical order), the bound variables are projected out
  first, and the *innermost free* level's cells carry the per-cell Exists/ForAll
  verdict (`qe_cell_verdict`). A new self-contained emitter `qe_region_expr` walks
  the free-variable subspace: at the collapse level it reuses the shared 1-D
  sign-diagram merger (`rru_emit_sign_diagram`) — so a closed true run reads
  `c <= b^2/4` rather than an open `... < ... || ... == ...` union — and above it
  wraps each non-empty cell as a `seg(v) && …` cylinder. Eliminating `x` from a
  single polynomial projects to its discriminant, which is exactly why the
  quadratic-root case yields `b^2 - 4 c >= 0`. The shipped `nfree == 1` path and the
  n-variable CAD driver `cad_region_expr` are byte-for-byte untouched.
- **Alternating quantifiers (`reduce_qe.c`).** A different-kind inner block is now
  eliminated by *recursive composition* — the inner quantifier reduces to a
  quantifier-free body, the peeled outer block is rebuilt over it and re-dispatched
  — to arbitrary alternation depth. `Case C` (`nfree ≥ 2`) routes to the generalized
  seam; free variables are canonicalized (`qe_sort_names`) so the answer is stable.
- **Soundness preserved (declines).** A free *leading* coefficient
  (`Exists[x, a x^2 + b x + c == 0]`), a transcendental body (`Exists[x, Sin[x]==a]`),
  an explicit non-Reals domain, or any CAD decline (irrational boundary the 1-D
  emitter cannot spell, undecidable sign, FLINT absent) all leave the input
  **unevaluated** — never a wrong formula.
- **Fold-in — parametric-condition display (`reduce_eq.c`).** A leading-coefficient
  condition that is linear in a single parameter now prints in solved form via a
  `RAtom.display` override: `Reduce[a x == x + 1, x]` gives `a != 1 && x == 1/(a-1)`
  (was `-1 + a != 0 && …`), mirroring `reduce_sys.c`'s `sys_norm_condition`. Bare
  symbol coefficients are unchanged.
- **Verification.** `tests/test_reduce.c`: new `test_quantifiers_multivar` (the five
  headline forms plus a **form-agnostic equivalence guard** that checks the emitted
  discriminant formula against the engine's own decision of the inner existence on
  both sides of the boundary and on it); `test_quantifiers_decline` updated to the
  new sound-decline set. `tests/reduce_corpus.m`: `eq-param-lincoeff` row (167/167).
  Reduce + Solve suites and corpora all green; `make check-c99` clean; valgrind at
  the macOS baseline (13,440/420 definitely-lost, all in libobjc/dyld — none
  attributable to the QE or display code). **Still pending: 6e (McCallum
  well-orientedness) and QE cases needing an algebraic free-variable boundary the
  1-D emitter cannot yet spell.**

## RischNormanBlake — residue/zero-test normal form via extension-aware Cancel/Together (v0.123)

Internal refinement to `Integrate`RischNormanBlake` (`src/calculus/int_rnb.c`).
The exact tier's three `Simplify` calls — the two place-residue reductions
(`rnb_residue_unram`, `rnb_residue_ram`) and the `rnb_is_zero` zero-test — are
replaced by `Cancel[Together[expr, Extension -> Automatic], Extension ->
Automatic]` (new `eval_cancel_together_ext` helper, still `TimeConstrained`-capped
exactly like the `Simplify` it supersedes).

The residues are rational functions over the place's radical number field, so
the extension-aware rational-normal form is a *complete* reduction and zero test
for that domain — more principled than the general `Simplify`, which had no
domain guarantee here and could take a pathologically slow path over a
nested-radical field. Behaviour is unchanged on the whole test corpus: the four
worked paper examples and both complex-place integrands still solve and verify
(numeric diff-back), and the hard pseudo-elliptic / m>=3 cases still decline
within the 4 s wall-clock budget rather than hanging.

## RischNormanBlake — never hangs; complex-place integrands solve (v0.122)

Robustness and coverage fixes for `Integrate`RischNormanBlake` (`src/calculus/int_rnb.c`),
which struggled on simple radical integrands: many hung (>20 s) — and since the
engine also runs inside the default `Integrate` cascade, those were
default-`Integrate` hangs, not just the `Method -> "RischNormanBlake"` path.

- **Imaginary unit linearised before the parallel solve.** The root cause of the
  hangs was `Cancel`/`Together` taking a pathological path (seconds to unbounded)
  whenever the imaginary unit `I` (from a complex affine place's residue logands)
  meets a symbolic mu/gamma ansatz coefficient. `I = Complex[0,1]` is now
  rewritten to an opaque symbol `RNB$I0` before the accumulation (`Complex[a,b] ->
  a + b RNB$I0`) and restored to `I` at equation extraction, so the whole solve
  runs over `Q`. This is sound (`I` carries only `I^2 = -1`) and makes integrands
  whose pole factor has complex roots solve — e.g.
  `Integrate[(x^2-1)/((x^2+1) Sqrt[x^4+1]), x, Method -> "RischNormanBlake"]`
  returns a conjugate pair of complex logs (an ArcTan) where it used to hang the
  whole cascade. Radical constants are deliberately *not* abstracted before the
  accumulation — that would map `Sqrt[6]` and `Sqrt[2] Sqrt[3]` to unrelated
  symbols — they are abstracted only at equation extraction, as before.
- **Hard wall-clock bounds so a run never hangs.** The exact tier's heavy
  algebraic calls over a nested-radical / complex number field (branch `Series`,
  `NullSpace`, `Simplify`, GCD-`Cancel`, `LinearSolve`, `Coefficient`) are each
  capped with `TimeConstrained`; a timeout latches an abort flag that the tier's
  loops poll, and the per-logand accumulation polls the deadline between
  sub-operations. The wall-clock budget is 4 s. Cases beyond the cheap fast path
  now *decline within a few seconds* instead of hanging (e.g.
  `x/((2 x^3-1) Sqrt[x^4-x])`, `x/((x^3+8) Sqrt[x^3-1])`,
  `(x+1)/((x-1) Sqrt[x^4+x^2+1])`, `1/((x+1)(3 x^2+1)^(1/3))`), and the numeric
  diff-back gate is unchanged so a wrong answer is never returned.
- **Tests.** `tests/test_int_rnb.c` gains `test_rnb_complex_places` covering the
  worked `Sqrt[x^4+1]` real- and complex-pole pair; the four worked paper
  examples still pass.

Remaining follow-up (the deeper exact-tier rework, deferred): several elementary
pseudo-elliptic / m>=3 integrands still decline (they now fail fast rather than
hang) because the residue/divisor/S-unit search over their number field is not
yet fast or complete.

## RischNormanBlake — parallel integration over simple radical extensions (v0.121)

New integration engine `Integrate`RischNormanBlake[f, x]`
(`src/calculus/int_rnb.c`), the parallel Risch-Norman method generalised to a
simple radical extension `L = K(y)`, `y^m = q(x)` with `K = Q(x)`, after
S. Blake, *Parallel Integration over Simple Radical Extensions*. It picks up
exactly the single-radical-of-`x` integrands that the transcendental pmint
(`Integrate`RischNorman`) declines, and is wired into the `Integrate` Automatic
cascade (right after `RischNorman`) and selectable via
`Method -> "RischNormanBlake"`. Attributes `Protected`, `ReadProtected`.

- **Integral basis.** The antiderivative numerator ranges over the integral
  closure `O = ⨁_{i<m} R w_i` with the Trager basis `w_i = y^i / E_i`,
  `E_i = ∏_j Q_j^⌊ij/m⌋` from the squarefree decomposition `q = ∏_j Q_j^j`
  (N1/N2 normalisations enforced). Elements are coordinate vectors over `w_i`;
  the multiplication table carries the leading-coefficient factor `c = q/∏Q_j^j`
  on each `m`-th-power wraparound (so `q = 1 − x²` gets its sign right).
- **Hermite denominator + exact degree bounds.** `v = b/(∏_j d_j^{j-1})` with
  per-coordinate bounds `B_i = ⌊(k + eΔ + ν_i)/e⌋` from the valuations at
  infinity (Cor. 4.7 of the paper), shrinking the linear system.
- **`S`-unit logands.** Beyond the irreducible denominator factors: the **units
  at infinity** for `m = 2` (continued fraction of `√q` / polynomial Pell —
  `∫dx/√(x²+1) = Log[x+√(x²+1)]`), and the **branch-place / Jacobian-torsion
  divisor** elements from a residue analysis (unramified branch series /
  ramified trace residues, grouped by value, then `find_element_with_divisor`
  as a nullspace of vanishing conditions, certified by the norm).
- **Number-field linear algebra.** Equation coefficients over `Q(radicals)` are
  extracted by abstracting each algebraic constant (`Sqrt[3/2]`, `(-1)^{1/3}`)
  to a fresh symbol so `Cancel`/`CoefficientList` clear common factors, solved
  with `Solve`, then RootReduce-verified; a final high-precision **numerical
  diff-back** is the safety gate (a mis-built system declines, never wrong).
- **Reproduces the four worked examples** of the paper (all numerically
  diff-back verified): genus-0 `y²=x²+1` (new constants `√2,√3,√6`), genus-1
  `y²=x⁴+1` (unit at infinity + 2-torsion divisor), `m=3` `y³=x²` (three logs
  with `ω`), and the flagship `∫dx/√(x²+1)`.
- **Scope / robustness.** `n = 1`, `K = Q(x)`; the residue tier is real-place
  only for `m ≥ 3` (complex-place branch series is skipped, so such cases
  decline rather than hang). A wall-clock budget bounds the whole run.
  Debug surfaces `Integrate`RNB`Info` / `Residues` / `Logands`. Tests
  `tests/test_int_rnb.c`.

## Matrix decompositions — complex NDArray input stays on the buffer (v0.120)

Follow-up to v0.119: a **complex** (`complex64`) NDArray input to `LUDecomposition`,
`SingularValueDecomposition`, `Eigenvalues`, and `Eigenvectors` used to
`linalg_delist_and_reeval` — unpacking the input into n² boxed `Complex[...]`
`Expr`s and re-evaluating. They now compute on the complex buffer via the LAPACK
`z*` drivers and return **packed `complex64`** factors:

- `LUDecomposition` → `zgetrf` (+ `zlange`/`zgecon` for the condition estimate);
  the combined LU factor is `complex64`.
- `SingularValueDecomposition` → `zgesdd`; `u`, `v` are `complex64`, the singular-
  value matrix stays real `float64`, and `v = ConjugateTranspose[VT]`.
- `Eigenvalues` / `Eigenvectors` → `zgeev`; eigenvalues pack as a `complex64`
  vector and eigenvectors as a `complex64` matrix, in descending `|lambda|` order.

Verified against NumPy/SciPy (`np.linalg.eig`, `np.linalg.svd`): eigenvalues and
singular values match to machine precision, and `m == u.sigma.ConjugateTranspose[v]`,
`m == q.t.q^H`, `m.v == lambda v` reconstruct to ~1e-15. Real paths unchanged;
audits and the linalg/packed suites pass; valgrind clean. Not done (deliberate): a

## Matrix decompositions — packed factors, no Expr boxing (Schur/QR); NDArray[] idempotency (v0.119)

Baselining `SchurDecomposition` against `scipy.linalg` (both on Accelerate LAPACK)
showed the only gap was `Expr`↔buffer marshalling — chiefly boxing n² doubles into
`Expr` nodes on output. This pass keeps decomposition results packed:

- **Shared mechanism** (`src/linalg/numarray.{c,h}`): `na_result_presentation(input)`
  (an NDArray input → its own presentation; a boxed-List input → `NDA_HEAD_LIST`, a

  packed float64/complex64 factor and stamp the presentation in one call. A
  transparent packed-list reads and threads as a plain List but keeps its data in a
  buffer; the helper arms `pack_g_any_created` so the evaluator's transparency gate
  normalizes it in reconstruction arithmetic like `m - q.t.ConjugateTranspose[q]`.
  A **complex** result destined for a boxed-List caller is boxed to a nested
  `Complex[...]` List (a complex packed-list is not a supported representation), while
  a complex NDArray input yields a visible complex64 NDArray.
- **`SchurDecomposition`** (`schurdecomp_machine.c`): loads **real-first** (hitting
  `na_load_matrix`'s float64 memcpy fast path instead of always widening to complex),
  and returns packed factors via the shared helper (no `pack_unpack`). A packed real
  400×400 now decomposes in ~65 ms — on par with / faster than scipy's ~87 ms, the
  marshalling overhead gone.
- **`QRDecomposition`** (`lapack_bridge.c`): a boxed-List input now yields transparent
  packed-list `q`, `r` (was boxed via `ndarray_to_nested_list`); an NDArray input
  still inherits its presentation.

## SchurDecomposition — new builtin (v0.118)

New builtin `SchurDecomposition` (`src/linalg/schurdecomp*.c`), the numerical
Schur factorization:

- `SchurDecomposition[m]` → `{q, t}` with `q` orthonormal, `t` block
  upper-triangular, and `m == q . t . ConjugateTranspose[q]`.
- `SchurDecomposition[{m, a}]` → the generalized (QZ) form `{q, s, p, t}` with
  `q, p` orthonormal, `s, t` upper-triangular, `m == q.s.p^H`, `a == q.t.p^H`.
- Options: `Pivoting -> True` adds a balancing scaling/permutation `d`
  (`m . d == d . q . t . q^H`); `RealBlockDiagonalForm -> False` makes `t`
  complex upper-triangular (default `True` keeps real 2×2 blocks);
  `TargetStructure -> "Dense" | "Structured"` (both return dense — Mathilda has
  no structured-matrix type).

Implementation:

- **LAPACK Schur drivers** — new wrappers `mat_lapack_dgees` / `zgees`
  (standard) and `dgges` / `zgges` (QZ), plus `dgebal` / `dgebak` (balancing
  for `Pivoting`), in `src/linalg/lapack.{h,c}` with the usual Fortran-ABI
  prototypes (guarded out under Accelerate) and no-LAPACK stubs. A real matrix
  with `RealBlockDiagonalForm -> False` loads complex and uses the `z` driver.
- **Machine kernel** (`schurdecomp_machine.c`) marshals both `NDArray`/packed
  and boxed-List inputs through `na_load_matrix`, numericalises symbolic
  constants (`Pi`, `E`, …) via `N[]` on a first-pass miss, and matches the
  result representation to the input (boxed in → boxed out) so a reconstruction
  threads correctly.
- **Arbitrary precision** (`schurdecomp_mpfr.c`) — the standard real form reuses
  the in-house Hessenberg + Francis QR via a new `eigen_schur_real_mpfr`
  (`eigen_direct.c`) that surfaces the orthogonal Schur vectors the eigenvalue
  path already accumulates. Complex / generalized MPFR fall back to machine
  precision (documented gap).
- On `pack.c`'s AWARE list (packed argument passed through, not materialised);
  `Compile[]`-exempt like the sibling decompositions; `ATTR_PROTECTED`;
  docstring in `info.c`; `SYM_RealBlockDiagonalForm` interned; `Information`
  reference in `docs/spec/builtins/linear-algebra.md`.
- Performance: a 100×100 real matrix reconstructs to ~5×10⁻¹⁴ in a few ms.
- Tests: `tests/test_schurdecomp.c` (24 relation-based checks — reconstruction,
  orthonormality, triangularity, block form, `Pivoting`, MPFR, generalized real
  & complex, NDArray, and the unevaluated/error cases).

## JordanDecomposition — new builtin

`JordanDecomposition[m]` returns `{s, j}` with `m == s . j . Inverse[s]`, where
`j` is the Jordan canonical form (Jordan blocks: an eigenvalue on the diagonal,
`1`s on the superdiagonal) and the columns of `s` are the generalized
eigenvectors grouped into Jordan chains. `Protected`. Registered in
`jordandecomp_init` (`src/linalg/jordandecomp.c`), documented in `src/info.c`.

- **Exact / symbolic path.** Eigenvalues from the characteristic polynomial
  (`eigen_char_poly_faddeev` → `eigen_solve_poly`); per eigenvalue `λ`, the
  block sizes come from the nullity sequence `dim ker (m − λ I)^k` computed with
  `eigen_null_space`, and the Jordan chains are built by a top-down chain-top
  selection (a `MatrixRank`-based "extend a spanning set to a basis") followed
  by bottom-up chain generation (`N^i · w`). Reproduces the exact spec examples,
  including the deficient-eigenspace `{{-103,-191,-255},…}` case
  (`j = {{24,0,0},{0,48,1},{0,0,48}}`), the size-3 chain in the `1±10^-16`
  matrix, and the 2×2 symbolic case (verified via `m.s == s.j`).
- **Numeric path.** A distinct spectrum is diagonalizable, so `s` is the numeric
  eigenvectors as columns and `j = DiagonalMatrix` of the eigenvalues.
  - **LAPACK buffer kernel (machine real).** A machine-real matrix — a packed /
    `NDArray` argument is read straight off its float64 payload, with no delist
    to boxed Exprs — goes through a dedicated kernel that calls LAPACK `dgeev`
    **once** and builds `s` (eigenvectors as columns) and `j` directly from the
    raw eigenvalue / eigenvector buffers. This skips everything the boxed path
    pays: the input delist, the intermediate boxed eigenvector list that
    `Eigenvectors` materialises, and a second (`Eigenvalues`) solve. A 100×100
    runs in ~9.6 ms (was ~14 ms), ~1.75× LAPACK-backed scipy `eig` — the
    residual gap is now the `dgeev` library plus the unavoidable boxing of the
    complex `Expr` result.
  - **Component-ratio fallback (complex-entry / no LAPACK).** When `dgeev` does
    not apply (complex matrix entries, or `USE_LAPACK=0`), one `Eigenvectors`
    solve is run and each eigenvalue is recovered from its eigenvector by an
    `O(n)` component ratio `(m.v)_p / v_p`, still avoiding a second solve.
  - **Arbitrary precision (MPFR)** keeps the full-precision `Eigenvectors` +
    `Eigenvalues` solves (those matrices are small).
  - A repeated numeric eigenvalue (defective, or ambiguous at machine precision)
    rationalises → exact core → numericalises, recovering the genuine block
    structure (e.g. `N` of a defective matrix yields a superdiagonal `1`).
    Correctness contract for numeric input is the residual `m ≈ s . j . Inverse[s]`
    plus a block structure matching the numeric nullities; exact block-splitting
    is not bit-reproduced (ill-posed).
- **Surfaces.** On the packed-array `AWARE` list in `src/pack.c` (accepts a
  packed / `NDArray[…]` matrix, delisted and re-evaluated); documented as a
  `Compile[]` exemption in `tools/compile_coverage.py` ("returns a pair of
  matrices"), like `QRDecomposition` / `SingularValueDecomposition`.
- **Limitation.** An exact matrix with an *irrational, defective* eigenvalue
  (whose generalized eigenspace the `is_zero_poly` pivot test cannot span) is
  left unevaluated rather than returned wrong.
- Errors `JordanDecomposition::argx` (arg count) and `JordanDecomposition::matsq`
  (non-square/empty).

Tests: `tests/test_jordandecomp.c` (20 checks: exact relation `m.s == s.j` and
deterministic `j` for the spec examples, symbolic, nilpotent, numeric residuals
for real/complex/MPFR, defective-numeric block, `NDArray` input, arg/shape
errors, docstring). Valgrind-clean across all paths (160 calls add zero
definitely/indirectly-lost bytes over baseline).

## Integrate — exponential-tower polylogarithm ladder (Cherry, general weight + algebraic roots)

Generalises the exp-tower dilogarithm engine (below) to **arbitrary weight** and
**algebraic roots**. New engine `rt_cherry_polylog_exp`
(`src/calculus/cherry_polylog_exp.c`), a `PolyLog` / `RT_SF_TOP_EXP` form
registered ahead of `rt_cherry_dilog_exp`. For an integrand `P(x)/Q(E^(c x))`
(rational in `θ=E^(c x)`, polynomial in `x`) it partial-fractions over the
roots `ρ` of `Q` — **rational or algebraic** — and closes each simple pole by the
exact Cherry polylogarithm ladder

    INT x^n/(θ - ρ) dx = Σ_{k=0}^{n} -(1/ρ)(n!/(n-k)!)/c^{k+1} x^{n-k} PolyLog[k+1, ρ/θ]

(built from `d/dx PolyLog[k, ρ/θ] = -c PolyLog[k-1, ρ/θ]`, `PolyLog[1,z] =
-Log[1-z]`), so an `x^n` numerator yields polylogarithms up to weight `n+1`. The
construction is a telescoping integration by parts, PowerExpand-diff-back verified
over the (possibly algebraic) constant field.

Closes the requested family:
- `Integrate[x^2/(E^x-1),x] = x^2 Log[1-E^-x] - 2 x PolyLog[2,E^-x] - 2 PolyLog[3,E^-x]`
- `Integrate[x^4/(E^(5x)-1),x] = (1/5)x^4 Log[1-E^-5x] - (4/25)x^3 PolyLog[2,E^-5x]
  - (12/125)x^2 PolyLog[3,E^-5x] - (24/625)x PolyLog[4,E^-5x] - (24/3125)PolyLog[5,E^-5x]`
- `Integrate[x/(E^(2x)+E^x-1),x]`, `Integrate[x^2/(E^(2x)+E^x-1),x]` over
  `Q(Sqrt[5])` (roots of `θ^2+θ-1`).

It also supplies the cleaner weight-1/2 rational forms (`Integrate[x/(E^x-1),x] =
x Log[1-E^-x] - PolyLog[2,E^-x]`). Scope: single commensurable kernel, `Q` proper
in `θ` with simple nonzero roots; improper fractions, `θ=0` (Laurent) poles, and
repeated roots decline cleanly; outer-log integrands (`Log[P(E^x)]`) stay with
`rt_cherry_dilog_exp`. Exposed directly as `Integrate\`Cherry\`PolyLogExp[f, x]`.
Tests: `tests/test_cherry_polylog_exp.c` (`cherry_polylog_exp_tests`).

## Integrate — exponential-tower dilogarithm engine (Cherry)

`Integrate` now closes the exponential-tower dilogarithm family, the exp-tower
mirror of the existing logarithmic-tower `R(x) Log[w] → PolyLog[2]` engine. The
flagship `Integrate[x/(-1 + E^x), x]` — previously reported non-elementary — now
returns `x Log[1 - E^-x] - PolyLog[2, E^-x]`.

New engine `rt_cherry_dilog_exp` (`src/calculus/cherry_dilog_exp.c`), registered
as a `PolyLog` / `RT_SF_TOP_EXP` form in `RT_SPECIAL_FORMS[]`
(`src/calculus/risch_special.c`). With the single exponential kernel `θ = E^(c x)`
(`θ' = c θ`), `x = Log[θ]/c` is the "root at 0" tower-log and `Log[θ - ρ_k]` are
the other tower-logs, so a **single input form** — a rational-in-`θ` combination
of the weight-1 logs `{x} ∪ {Log[θ - ρ_k]}`, of total weight 1 — covers both the
rational-times-`x` shape (`x/(E^x-1)`) and the outer-log shape (`Log[1+E^x]`).
Matched natively in the tower (Cherry's algorithm, no substitution): a weight-2
ansatz of `PolyLog[2, Möbius(θ)]`, `x Log[θ-ρ_k]`, `Log-Log` products, and `x^2`
terms; each candidate differentiated, its logs normalised by `Log[z] →
PowerExpand[Log[Factor[Together[z]]]]` and mapped `Log[θ-ρ_k] → u_k`, `Log[θ] →
c x`; coefficients from a linear solve requiring the residual to vanish over
`{θ, x, u_1, …, u_m}`; PowerExpand diff-back verified (a mis-generation declines,
never a wrong form).

Closes `x/(E^x-1)`, `x/(1±E^x)`, `x E^x/(E^x-1)`, `x/(E^(2x)-1)` (rate `c=2`),
`Log[1±E^x]`, `Log[1+E^-x]`, and mixtures. Declines cleanly: weight-`≥2`
integrands (→ `PolyLog[3]`), incommensurate exponentials, algebraic roots. The
engine is gated to the **top-level** integrand (`g_integrate_depth ≤ 1`) so a
`DerivativeDivides` `u=Log[x]` substitution does not pre-empt the cleaner direct
log-tower engine on `Log[x]/(1-x)`. Also exposed directly as the debug surface
`Integrate\`CherryDilogExp[f, x]`. Tests: `tests/test_cherry_dilog_exp.c`
(`cherry_dilog_exp_tests`).

## Reduce — Phase 6b: real-algebraic-coefficient fibre isolation (v0.113)

The Reals CAD engine no longer requires a non-innermost breakpoint to be
rational. A section at an **irrational algebraic** breakpoint pins an outer
variable to an algebraic number, so the deeper fibre is a univariate polynomial
with real-algebraic-number coefficients — which `Solve[…, Reals]` (factoring over
ℚ) cannot isolate. A new primitive **`rru_algebraic_fiber_roots`**
(`src/solve/reduce_algfiber.{c,h}`) supplies the missing capability by
**iterated-resultant tower projection**: the outer assignment forms a tower
ℚ ⊆ ℚ(α₀) ⊆ ℚ(α₀,α₁) ⊆ …, each irrational αᵢ a root of a known factor over ℚ
(carried through the CAD by root provenance); substituting the rational levels
and eliminating each algebraic level by `Resultant` leaves a univariate over ℚ
whose real roots **contain** the fibre's, and an exact `qqbar` zero-test
(`factor(vals…, β) == 0`) keeps exactly the true roots, discarding the
conjugate-spurious ones the resultant introduces. The engine is wired into both
CAD drivers (`src/solve/reduce_cad.c`): the rational-fibre gates are removed and
a section's defining factor is threaded through `cad_build` / `cad_leaf` /
`lift_fiber` / `reduce_cad_qe` via a new borrowed `asgdef[]`; an all-rational
assignment keeps its unchanged fast path.

**Now solved** (all declined before): `Reduce[x^2 == 2 && y < x, {x, y}, Reals] ->
x == -Sqrt[2] && y < -Sqrt[2] || x == Sqrt[2] && y < Sqrt[2]`; the radius-`Sqrt[2]`
closed ball `x^2+y^2+z^2 <= 2`; the sphere positive octant
`x^2+y^2+z^2 == 1 && x>0 && y>0 && z>0 -> 0 < x < 1 && 0 < y < Sqrt[1-x^2] &&
z == Sqrt[1-x^2-y^2]`; the cubic curve `x^3+y^3 == 1 && x>0 && y>0 ->
0 < x < 1 && y == (1-x^3)^(1/3)`; hyperbola branches; and closed 3-/4-balls, all
flowing through `CylindricalDecomposition` too.

**Soundness preserved.** A transcendental (non-algebraic) breakpoint (e.g.
`x^2+y^2+z^2 == Pi && …`, boundary `Sqrt[Pi]`), an undecidable `qqbar` test, an
identically-zero resultant, a resource-budget overrun, or FLINT absent all make
`Reduce` decline (stay unevaluated) rather than emit a wrong formula. The tower
resultants are bounded by a generous var-degree / node-count ceiling that
declines rather than blows up.

Tests: `test_cad_algebraic_fibre` in `tests/test_reduce.c`; seven `alg-*` rows in
`tests/reduce_corpus.m` (corpus 166/166); the stale rational-fibre decline
assertions (`test_cad_nvar`, `test_cylindrical_decomposition`, `cad3-decline-surd`)
updated to the now-solved forms. `check-c99` clean; the full reduce and solve
suites/corpora pass with no regression; valgrind at the macOS baseline
(13,440/420, identical at 1× and 25× invocations — zero per-call leak).

Still deferred: **6e** (McCallum well-orientedness augmentation — an interval
nullification bails) and **7-extended** (≥2-free-variable / alternating-quantifier
QE and the algebraic discriminant-variety boundary, e.g.
`Resolve[Exists[x, x^2 + b x + c == 0]] -> b^2 - 4 c >= 0`, which needs a
nested-QE emitter beyond 6b fibres).

## Statistics — real-only element gate fixed, quantile interpolation made overflow-safe, gate made ~2x cheaper

Follow-up on the `Quantile` family. Three changes, all in the shared helpers
`src/stats/stats_common.c`, so all seven heads that use them are affected:
`Median`, `Quartiles`, `Quantile`, `InterquartileRange`, `MeanDeviation`,
`MedianDeviation`, `MovingMedian`.

- **`stats_is_real_numeric` now rejects an evaluated complex number (bug fix).**
  The gate promised "a rectangular array of real numbers" and tested that with
  `NumericQ[e] && FreeQ[e, I]`. `2 + I` evaluates to the structural node
  `Complex[2, 1]`, which is `NumericQ` and contains no literal symbol `I`, so
  `FreeQ` said `True` and complex data walked straight through: `Median[{1, 2 + I,
  3}]` returned `3` with no message, and `Quartiles[{1, 2 + I, 3, 4}]` returned
  `{2, 7/2, 3 + I/2}` — a complex quartile. A `Complex[re, im]` element is now
  decided on its imaginary part: rejected when that part is nonzero, accepted when
  it is zero. The zero case is not hypothetical — `builtin_complex` normalises an
  int64 or double zero imaginary part away but not an MPFR one, so
  `N[2 + I, 30] + N[Conjugate[2 + I], 30]` really does arrive as
  `Complex[4.0, 0.0]` and is a real number. The literal-`I` case, which always
  worked, is pinned by its own assertion so a future rewrite cannot trade one hole
  for the other.

  **Known remaining gap, stated rather than smoothed over:** this closes the bare
  `Complex` node only. A complex value nested under a numeric head —
  `Sqrt[2 + I]` is `Power[Complex[2, 1], 1/2]` — is still `NumericQ`, still free of
  a literal `I`, and still passes the gate, so `Median[{1, Sqrt[2 + I], 3}]` still
  answers `3`. Closing that needs a real-valuedness test (`Im[e] == 0`) rather than
  a structural one, and is deliberately out of scope here.

- **`stats_quantile_point` interpolates as a convex combination (bug fix).** The
  interpolating branch computed $x_{(j)} + w(x_{(j+1)} - x_{(j)})$. That is an
  identity in exact arithmetic and not in floating point: two neighbours of
  opposite sign near the top of the double range make the difference round to
  `Infinity`, which then survives the multiply and the add.
  `Quantile[{-1.0*10^308, 1.0*10^308}, 1/2, {{1/2, 0}, {0, 1}}]` returned
  `Infinity` where the answer is `0.`. For $w \in [0, 1]$ it is now
  $(1-w)x_{(j)} + w\,x_{(j+1)}$, which never forms a quantity larger in magnitude
  than the two neighbours it interpolates between. Same class as the already-fixed
  $w = 1$ case, which selects the element instead of recomputing it. Exact input is
  unaffected: the two forms agree exactly over integers and rationals.

  The switch is conditional on purpose. $w = c + d\,g$ is user-controlled through
  `{{a,b},{c,d}}` and nothing bounds it to $[0,1]$; every standard Hyndman–Fan type
  lands inside, but *outside* it the convex form is the wrong one — $(1-w)$ and $w$
  have opposite signs, the two products can overflow independently, and
  $\infty + (-\infty)$ is `NaN` on input the difference form gets exactly right.
  `Quantile[{1.0*10^308, 1.0*10^308}, 1/2, {{1/2,0},{0,100}}]` is `1e+308` under
  both the old form and the new one, and was `nan.0` in between. Neither form is
  safe everywhere; each is now used only where it is.

  The same formula has a second live copy in the `NDArray` kernel
  (`ndred_quartiles`, `src/ndreduce.c`), which was carrying the identical overflow:
  `Quartiles[NDArray[{-1.0*10^308, 1.0*10^308}, DataType -> "float64"]]` returned
  `inf.0` in the middle slot while the boxed path returned `0.0`. Fixed there too,
  and both surfaces are now pinned by assertions on the same data. (`g` is a
  fractional part there, always in $[0,1)$, so that copy needs no conditional.)

- **The element gate got a leaf fast path (performance).** Every head above calls
  `stats_is_real_numeric` once per list element, and each call paid two full
  evaluator round-trips (`NumericQ`, then `FreeQ`) — 400,000 evaluations for a
  200,000-element list. A machine integer, machine real, bignum, MPFR real or
  exact `Rational` is real and `I`-free by construction, so those now short-circuit
  with no evaluator at all; everything else takes the same path it always did, so
  the accepted set is unchanged apart from the complex fix above.

  Measured on a 200,000-element list, best of nine (three interleaved base/head
  rounds, three trials each), Apple M-series, gcc-16 `-O3`:

  | expression | before | after | speedup |
  |---|---|---|---|
  | `Quantile[data, 1/2]` (int) | 0.0586 s | 0.0306 s | 1.91x |
  | `Quantile[data, 1/2]` (real) | 0.0694 s | 0.0392 s | 1.77x |
  | `Quantile[data, {1/4, 1/2, 3/4}]` | 0.0583 s | 0.0302 s | 1.93x |
  | `InterquartileRange[data]` | 0.0855 s | 0.0300 s | 2.85x |

  | `MeanDeviation[data]` | 0.1403 s | 0.1123 s | 1.25x |
  | `MedianDeviation[data]` | 0.6602 s | 0.5717 s | 1.15x |

  `Median` is unchanged (0.0034 s vs 0.0032 s, inside the noise): it reaches the

## Statistics — Quantile, InterquartileRange, MeanDeviation, MedianDeviation; stats_tests registered with CTest

Closed the `Quantile` gap (tracked in `benchmarks/ABSENT.md`) and three dispersion
companions, all in `src/stats/` (one builtin per TU, registered in `stats_init`):

- **`Quantile[data, q]`, `Quantile[data, {q...}]`, `Quantile[data, q, {{a,b},{c,d}}]`** —
  the general parameterized quantile. The interpolation engine that lived inline in
  `Quartiles` is now shared (`stats_quantile_point` in `stats_common.c`) with one
  semantic correction the Quartiles defaults could never observe: at integer
  $h = a+(n+b)q$ the Floor/Ceiling neighbors coincide, so the result is $x_{(h)}$ for
  any $c,d$ (previously the loop interpolated toward $x_{(h+1)}$ unconditionally;
  with Quantile's `{{0,0},{1,0}}` defaults that would have returned the wrong element
  on every integer $nq$ — e.g. `Quantile[{1,2,3,4}, 1/2]` must be `2`, and
  `Quartiles[{1,2,3,4}, {{0,0},{1,0}}]` is now `{1, 2, 3}`, both matching Wolfram).
  Default `Quartiles` output is unchanged for uniformly exact or uniformly
  inexact data. It DOES change for a *mixed* list at integer $h$:
  `Quartiles[{1,2,3.,4,5,6}]` was `{2.0, 3.5, 5}` and is now `{2, 3.5, 5}` —
  previously the zero-weighted `A[j+1]` term still dragged the exact element to
  a Real, which the documented Floor/Ceiling definition does not do. Recorded as
  a deliberate deviation from this change's own non-goal.

  The default parameterization SELECTS the order statistic rather than
  recomputing it: `A[j] + 1·(A[j+1] − A[j])` is an identity only in exact
  arithmetic, and returned `0.` instead of the element for a list containing
  `-1.0*10^308`. Weights of exactly 0 or 1 now copy the named element. Matrix input is columnwise; a visible
  `NDArray` argument is materialised to the exact `List` path via `pack_unpack`
  (correctness-first; no buffer kernel yet — declared to the fast-path audits).
- **`InterquartileRange[data]`** — $q_{3/4} - q_{1/4}$ under the Quartiles
  parameterization. Matrix input recurses per column *before* the vector path, so a
  3-column matrix (whose columnwise `Quartiles` result is itself a 3-list) cannot be
  mistaken for a vector's `{q1,q2,q3}` — the guard also requires all three quartiles
  to be scalars.
- **`MeanDeviation[data]` / `MedianDeviation[data]`** — `Mean[Abs[data - Mean[data]]]`
  and `Median[Abs[data - Median[data]]]`, composed through the evaluator so exact
  input stays exact (`MeanDeviation[{1,2,3,4}]` is `1`, not `1.`).
- **Tests**: new `quantile_family_tests` binary (one `assert_eval_eq` per acceptance

  registered with `add_test`, so `ctest` silently skipped the whole statistics suite —

## ArrayReshape and ArrayPad

Two new structural array heads (`src/list/array_reshape.c`,
`src/list/array_pad.c`, with a shared 1-D scheme engine in
`src/list/pad_schemes.c`), both `Protected`.

- **`ArrayReshape[list, dims]` / `[list, dims, padding]`** — arrange the
  flattened elements of `list` into a rectangular `dims` array (row-major),
  dropping extras or padding a shortfall. The input is flattened first, so
  `Flatten[ArrayReshape[list, dims]]` matches `Flatten[list]` up to length.

- **`ArrayPad[array, amounts]` / `[array, amounts, padding]`** — pad (or, with
  negative amounts, trim) an array on every side / per level. `amounts` is a
  scalar `m`, a pair `{m, n}` (applied to each dimension), or per-level
  `{{m1, n1}, ...}` (`{mi}` means `{mi, mi}`). Padding is a constant `c`
  (default `0`), a cyclic list, or a named scheme: `"Fixed"`, `"Periodic"`,
  `"Reflected"`, `"Reversed"`, `"ReversedNegation"`, `"ReflectedDifferences"`,
  `"ReversedDifferences"`, `"Extrapolated"` (option `InterpolationOrder`,
  default `1`, up to `Infinity` = degree `n-1`). A value-difference scheme on an
  axis of length `< 2` raises `ArrayPad::mindimsize`; value-dependent schemes
  skip empty dimensions.

- **Compute surfaces.** Both are on the packed/`NDArray` fast path
  (`ndstruct_arrayreshape`, `ndstruct_arraypad` in `src/ndstruct.c`; `AWARE` and
  `INT64_OK` in `src/pack.c`): a rank-1 buffer reshape/two-sided pad by `memcpy`
  + `nd_fill_run`, declining any shape or fill the buffer cannot hold exactly
  (matching the List path, e.g. the default integer `0` beside reals stays a
  mixed list). Deferred on `Compile[]` (their extra argument is a list/spec/fill,
  not a machine integer) — tracked in `tools/compile_coverage.py` `BASELINE`.

- Docstrings in `src/info.c`; reference in
  `docs/spec/builtins/lists-and-iteration.md`; unit tests in
  `tests/test_array_reshape.c` and `tests/test_array_pad.c`. Zero leaks under the
  macOS `leaks` tool.

## `CylindricalDecomposition` — the last Reduce companion (Phase 8), v0.111

`CylindricalDecomposition[expr, vars]` gives a **cylindrical algebraic decomposition
of the real solution set** of `expr` — a quantifier-free `And`/`Or` formula in which
each variable is bounded cylindrically in terms of the earlier ones. This completes the
Phase-8 companion family of `Reduce` (`REDUCE_PLAN.md`); it was the last unshipped one.

```
CylindricalDecomposition[x^2 > 1, {x}]            x < -1 || x > 1
CylindricalDecomposition[x y > 1, {x, y}]         (x < 0 && y < 1/x) || (x > 0 && y > 1/x)
CylindricalDecomposition[x^2 + y^2 <= 1, {x, y}]  -1 <= x <= 1 && -Sqrt[1-x^2] <= y <= Sqrt[1-x^2]
CylindricalDecomposition[x^2 == -1, {x}]          False
```

- **Design — a thin Reals-only front-end that delegates to `Reduce`.** The one semantic
  difference from `Reduce` is that `CylindricalDecomposition` is **Reals-only** (`Reduce`
  defaults to the Complexes for equations). Since our Reals engine (Fourier–Motzkin / the
  sign diagram / the McCallum-projection CAD `reduce_cad`) *is* a CAD and already emits the
  merged cylindrical formula, the elegant zero-duplication implementation forces the Reals
  domain and reuses the whole `Reduce` pipeline — including its front-end preprocessing (Abs
  sign-split, real radicals, `Mod`→`Floor`), DNF build, and per-arity Reals dispatch — rather
  than forking the CAD cell-walk.
- **Implementation** (`src/solve/reduce_companions.c`, `builtin_cylindrical_decomposition`):
  validate arity (`[expr, vars]`, or `[expr, vars, Reals]` with the redundant domain accepted;
  any other third positional declines), validate `vars` (a symbol or non-empty `List` of
  symbols), then build and evaluate `Reduce[expr, vars, Reals, <trailing option Rules…>]` under
  message suppression. Trailing option Rules are forwarded verbatim, so all of `Reduce`'s
  options (`Modulus`, `Cubics`, `Quartics`, `WorkingPrecision`, …) are reused with no per-option
  logic. If `Reduce` declines (leaves itself unevaluated), so does this — detected by the result
  still being headed by `Reduce` — so `CylindricalDecomposition[…]` stays unevaluated rather than
  echoing an inner `Reduce[…]`.
- **Soundness / declines.** The hard `Reduce` invariant carries over: an undecidable sign/ordering
  (the qqbar oracle "unknown", or FLINT absent) returns unevaluated, never a wrong formula. In
  particular a **positive-dimensional nonlinear real system with irrational fibres** (e.g.
  `x^2+y^2+z^2==1 && x>0 && y>0 && z>0`, the CAD rational-fibre limitation / Phase 6b) declines,
  as does an unsupported third positional or an invalid variable.
- **Registration** (`reduce_companions_init`): `symtab_add_builtin` + `ATTR_PROTECTED` +
  `symtab_set_docstring`; new `SYM_CylindricalDecomposition` (3 sites in `sym_names.{h,c}`). It is
  a symbolic/structural head returning a logical formula (never a machine array), so it is
  legitimately exempt from the packed/NDArray and `Compile[]` surfaces (same class as `Reduce`;
  `check-packed-aware` does not flag it).
- **Tests / verification.** `tests/test_reduce.c::test_cylindrical_decomposition` (14 assertions:
  the cylindrical forms, `True`/`False` decisions, the list-as-conjunction and bare-symbol var
  forms, and the three sound declines); reduce suite + corpus 160/160; `make check-c99` clean;
  valgrind at the macOS baseline (13,440/420 — no new attributable leak). Spec:
  `docs/spec/builtins/solutions-of-equations.md`.

## `Reduce` — accepts a list of equations/inequalities (list = conjunction)

`Reduce[{e1, e2, …}, vars]` previously returned **unevaluated** — only the
`&&` conjunction form was accepted, unlike Mathematica (and unlike `Solve`,
which takes a list). Now a `List` in the statement slot is treated as the
conjunction `e1 && e2 && …`, so `Reduce[{x + y == 3, x - y == 1}, {x, y}]`
gives `y == 1 && x == 2`.
- **Implementation** (`src/solve/reduce.c`, `builtin_reduce`): after the
  variable-validity check, a `List` in `args[0]` is rewritten to `And` of copies
  of its elements (`(n==1) ? parts[0] : expr_new_function(And, …)`, mirroring the
  idiom in `reduce_int.c`); a one-element list unwraps to the element, an empty
  list is left to decline. The new owned temporary is freed on every return path
  (True/False shortcut, `Exists`/`ForAll`, `Modulus`, the parse-fail early
  return, and the final exit); `expr_copy` is a refcount bump, so freeing only
  drops this reference. Valgrind shows identical leak totals for the list and
  `&&` forms.
- **Docs/tests**: docstring and `docs/spec/builtins/solutions-of-equations.md`
  note the list form; `tests/reduce_corpus.m` gains `sys-list-and` and
  `sys-list-singleton` (corpus 160/160 green), and the corpus verifier
  (`reduce_check_prelude.m`) now normalizes a `List` statement to `And` before
  back-sampling so its truth oracle judges a single logical expression.

## `ChineseRemainder` — CRT solver for systems of integer congruences

New builtin `ChineseRemainder[{r1, …}, {m1, …}]` (and the offset form
`ChineseRemainder[{r1, …}, {m1, …}, d]`), giving the smallest `x ≥ 0` (resp.
`x ≥ d`) with `x mod mi == ri mod mi` for all `i`, in `0 ≤ x < LCM[m1, …]` (resp.
`d ≤ x < d + LCM`).
- **Implementation** (`src/numbertheory/chineseremainder.c`): a streaming
  pairwise CRT fold, all GMP. The accumulator congruence `x ≡ x_acc (mod m_acc)`
  is merged with each `(ri, |mi|)` via `mpz_gcdext`
  (`x_acc += ((ri − x_acc)/g)·u·m_acc`, `m_acc = lcm`), reduced modulo the
  running lcm each step; the smallest `x ≥ d` is `d + ((x_acc − d) mod L)`.
  Machine ints and bigints share one path, so the RNS-recovery / CRT-encryption
  idiom over large coprime moduli returns the full bignum.
- **Non-coprime moduli** are supported: a solution exists iff every pair of
  congruences agrees modulo the gcd of their moduli; an inconsistent system
  (e.g. `ChineseRemainder[{1, 2}, {6, 10}]`), a zero modulus, a length mismatch,
  or non-integer/symbolic arguments leave the call unevaluated. Wrong arity emits
  `ChineseRemainder::argt`.
- **Attributes**: `Protected` (deliberately not `Listable` — the residue and
  modulus lists are atomic arguments). Registered in `numbertheory_init`;
  `SYM_ChineseRemainder` interned in `sym_names.c`; docstring in `info.c`.
- **Tests**: `tests/test_chinese_remainder.c` — doc examples, the
  `x mod mi == ri` contract, RNS multiply/recover, a 27-digit bignum verified by
  range + per-modulus round-trip, the offset form (incl. negative `d`),
  non-coprime-consistent merges, no-solution/edge cases, the arity diagnostic,
  and a valgrind stress loop.
- Not on any packed/NDArray/`Compile[]` surface (a list-reduction to a possibly
  bignum scalar with no machine-buffer form), mirroring `ExtendedGCD` /
  `MultiplicativeOrder`.

## `FindInstance` — undefined-witness soundness fix, solve-one-variable, saturation, all-constraint feasibility, quiet probes, v0.108

A second `FindInstance` stress round: six harder cases, all now solved with sound,
verification-gated, general methods — and the internal solver probes are now silent
(all touching `src/solve/reduce_companions.c` unless noted).

- **Soundness: witnesses must be defined, not just fold to `True`** — the verifier
  (`fi_verify` → new `fi_defined_truth` / `fi_has_nonfinite`) now rejects any point
  where a relation operand evaluates to an infinity/indeterminate sentinel. Previously
  `FindInstance[Log[z^2] == 2 Log[z] + 2 π I, z, Complexes]` returned the **wrong**
  `{{z -> 0}}` (since `Log[0] = -Infinity` and `-Infinity == -Infinity` folds to

- **Solve one equation for one variable, sample the rest** (`fi_solve_one_sample`) —
  for an equality `E` and a variable `xₖ`, `Solve[E, xₖ]` is combined with a
  constraint-aware, per-variable-compacted candidate grid over the other variables
  (extended with small/large magnitudes). Solves `c1 e^{-L1 t} + c2 e^{-L2 t} == 0 &&
  c1 > 0 && c2 < 0 && L1 > L2 > 0 && t > 0` → `{c2 -> -1, L1 -> 2, L2 -> 1, t -> 1,
  c1 -> E}`, and the tiny-region `(x²-y²)/(x²+y²) == 1/2 && x²+y² < 10⁻¹⁰ && x>0 && y>0`

## `FindInstance` — witness finder (Reduce Phase 8), v0.104

`FindInstance[expr, vars, dom, n]` finds up to `n` witness points satisfying
`expr` over **Complexes / Reals / Integers / Rationals / Booleans**, returned in
`Solve`'s form (`{{x -> v, ...}}`), `{}` when the set is provably empty, and
unevaluated when it can neither exhibit an instance nor prove emptiness
(`src/solve/reduce_companions.c`, `builtin_find_instance`; new `SYM_FindInstance`;
registered `Protected` in `reduce_companions_init`).

- **Soundness by construction.** Rather than reaching into the three `static` CAD
  paths (`reduce_cad.c`: `nu==1` sign diagram, `nu==2` flat `YRegion` arrays,
  `nu>=3` `CADRegion` tree), witnesses are read off the **public, already-cylindrical**
  output of `Reduce` (the satisfiability oracle) and off `Solve`'s rule-lists, and
  **every** candidate is verified against the original `expr` (`expr /. point`
  must evaluate to `True`). A returned instance is therefore always a true
  solution; `{}` is emitted only when `Reduce` proves emptiness; anything
  unwitnessed and unrefuted is left unevaluated — never guessed.
- **Extraction.** `Reduce` output → walk each top-level `Or` clause: `Element`-declared
  parameters and unpinned free variables are sampled first (interval samples via the
  shared exact `rru_rational_between`), then `Equal` atoms are resolved by an internal
  `Solve`. `Solve` fallback instantiates free listed variables to `0` (grid for extra
  instances) — so `FindInstance` succeeds on cases `Reduce` declines, e.g.
  `FindInstance[x^2 - y z == 1, {x, y, z}] -> {{x -> -1, y -> 0, z -> 0}}`.
- **Booleans** reuses the module's `LogicalExpand` DNF engine: each satisfiable DNF
  clause is a partial assignment (unconstrained variables default `False`), verified
  with the now-evaluating `Xor`/`Implies`.
- **Options**: `Modulus -> p` solves over `Z/pZ`; `Method` / `WorkingPrecision` /
  `RandomSeeding` are accepted and ignored (exact & deterministic); an unknown
  option gives `FindInstance::optx` and stays unevaluated.
- Examples: `x^2 == 2` (C) → `{{x -> -Sqrt[2]}}`; the disk (R) → `{{x -> 0, y -> 0}}`;
  `x^2 - 3 y^2 == 1 && 10 < x < 100` (Z) → `{{x -> 26, y -> -15}}`; the 4-variable
  `Xor` SAT (Booleans); an unsatisfiable system → `{}`.
- Tests: `test_find_instance` in `tests/test_reduce.c` (21 assertions, FullForm-pinned
  + decline checks); reduce corpus 158/158; `make check-c99` clean; valgrind
  byte-identical to the macOS baseline (no FindInstance-attributable leak). While
  here, the pre-existing `-Wdiscarded-qualifiers`/`-Walloc-size` warnings in
  `reduce_companions.c` were also cleared, so the module compiles warning-free.
  `CylindricalDecomposition` remains the last unshipped Phase-8 companion.

## `Xor` and `Implies` now evaluate on Booleans

`Xor` and `Implies` were previously inert on every input — `Xor[True, True]`
and `Implies[True, False]` stayed symbolic. They now evaluate
(`src/boolean.c`, `builtin_xor` / `builtin_implies`; attributes in `attr.c`):

- **`Xor`** (`Flat`, `Orderless`, `OneIdentity`, `Protected`) folds the literal
  Booleans and cancels duplicate arguments (`a` Xor `a` = `False`): `Xor[]` →
  `False`, `Xor[e]` → `e`, `Xor[True, False]` → `True`, `Xor[True, True]` →
  `False`, `Xor[True, a]` → `!a`, `Xor[a, b, a]` → `b`; a fully-symbolic distinct
  `Xor[p, q, r]` stays unevaluated. Nested `Xor` flattens.
- **`Implies`** (`Protected`): `Implies[False, q]` / `Implies[p, True]` → `True`,
  `Implies[True, q]` → `q`, `Implies[p, False]` → `!p`, `Implies[p, p]` → `True`;
  otherwise unevaluated.

This makes the Boolean algebra self-consistent with `LogicalExpand` and the
`Reduce` family (which already expand `Xor`/`Implies` internally) and with the
`Compile[]` logic path (which already lowered them), and lets a truth-table
cross-check like `Table[e1 == LogicalExpand[e1], {a, {True, False}}, ...]` reduce
to all `True`. No regression: the `Reduce` corpus (158/158) and the reduce/
boolean/compile/comparisons/simplify suites stay green.

## Reduce Phase 8 — `LogicalExpand` (+ the `NotElement` head)

The first `Reduce` companion builtin lands (REDUCE_PLAN.md, Phase 8):
`LogicalExpand[expr]` distributes a logical combination of equations,
inequalities and Boolean atoms into **disjunctive normal form** (an `Or` of
`And`s) with idempotence / complementation / absorption contractions, expanding
`Implies` and `Xor` and collapsing to `True` (tautology) or `False`
(contradiction). Examples: `LogicalExpand[p && !(q || r)] -> p && !q && !r`,
`LogicalExpand[(a || b) && !(c || d || e)] -> (a && !c && !d && !e) || (b && !c
&& !d && !e)`, `LogicalExpand[a || !a] -> True`, `LogicalExpand[a && !a] ->
False`, `LogicalExpand[Xor[p, q, r]]` → its four odd-parity minterms,
`LogicalExpand[x == a && y == b || x == a || y == b] -> x == a || y == b`
(absorption), and the multi-variable tautology
`LogicalExpand[Implies[(p || !r) && s, Implies[r && s, p && q || p]]] -> True`.

Because it does **no domain reasoning** (every non-connective subexpression is an
opaque Boolean atom, exactly as Mathematica), `LogicalExpand` cannot reuse the
`RForm`/`RAtom` layer — that layer forces each leaf into a *polynomial* relation.
The engine is therefore a standalone Expr-level DNF distributor
(`src/solve/reduce_companions.c`): a mutually-recursive `to_dnf` / `to_dnf_neg`
that branches only on the recognised logical heads and treats everything else as
a signed literal. A negation folds into the complementary **relation head**
(`x == a` / `x != a`, `x < 1` / `x >= 1`, `Element` / `NotElement`, `a` / `!a`)
so output carries no stray `Not` on a relation, and those pairs are exactly the
complementary literals used by the contractions.

The `True`/`False` collapse is **sound and complete without truth-table
enumeration**: over independent opaque atoms a DNF is unsatisfiable iff every
clause holds a complementary pair — i.e. it distributes to zero surviving clauses
— so `expr` is `False` when its DNF is empty and `True` when the DNF of `!expr`
is empty. The emitted DNF is sound and equivalent but, like the rest of the
`Reduce` family, not guaranteed minimal (Mathematica's extra consensus
contractions can produce a shorter, logically identical cover).

A minimal **`NotElement`** head ships alongside so a negated membership prints as
`x` ∉ `dom` (Mathematica-faithful) rather than `Not[Element[...]]`;
`NotElement[x, dom]` decides whenever `Element[x, dom]` decides and stays
symbolic otherwise. Both heads are `Protected`. New symbols `SYM_LogicalExpand`
and `SYM_NotElement`; registered from `reduce_companions_init` (called by
`reduce_init`). `Reduce` remains exempt from the packed/NDArray and `Compile[]`
surfaces (a symbolic head returning logical formulas), and its companions inherit
that exemption. Tests: `test_logical_expand` in `tests/test_reduce.c`. The other
Phase-8 companions (`FindInstance`, `CylindricalDecomposition`) are still pending.

## CharacteristicPolynomial — new builtin

`CharacteristicPolynomial[m, x]` gives `Det[m - x I]` as an expanded polynomial
in `x`; `CharacteristicPolynomial[{m, a}, x]` gives the generalized
`Det[m - x a]`. Entries may be integer, rational, machine- or arbitrary-precision
real, complex, or symbolic. Attribute `Protected`.

Rather than the naïve `Expand[Det[m - x I]]` — which would face an `O(n!)`
Laplace expansion of a symbolic-in-`x` matrix — the ordinary case reuses the
eigen module's Faddeev–LeVerrier–Souriau fast path (`eigen_char_poly_faddeev`,
`O(n^4)`), so a 100×100 machine matrix is sub-second. That routine returns
`det(λI − m)`, so odd-`n` results are negated to match `Det[m − x I] = (−1)^n
det(x I − m)` (e.g. `CharacteristicPolynomial[IdentityMatrix[3], x] ->
1 - 3 x + 3 x^2 - x^3`). The generalized case is `Det[m − x a]` via Laplace
expansion (`eigen_build_lambda_matrix` + `eigen_compute_det`), so a shared null
space drops the leading term(s) — an infinite generalized eigenvalue shows as a
degree deficit (`CharacteristicPolynomial[{a, b}, x] -> -1 - x + x^2`). The
polynomial is built in a private internal lambda and the user's second argument
(symbol, number, or expression) is substituted in, then expanded.

`mateigen_init` (`src/linalg/eigen.c`); declared in `src/linalg/eigen.h`; new

## Reduce — Quantifier elimination (Exists / ForAll / Resolve), v0.095

`Reduce` gained quantifier elimination (REDUCE_PLAN.md Phase 7): the new heads
`Exists`, `ForAll`, and `Resolve` turn a quantified real statement into an
equivalent quantifier-free formula over the remaining free variables — or
`True`/`False` when none remain. `Exists` and `ForAll` are inert (`HoldAll`)
quantifier wrappers; `Resolve[expr, dom]` and a top-level `Exists`/`ForAll`
inside `Reduce[...]` both route to one engine over the Reals.

The engine reuses the existing Cylindrical Algebraic Decomposition
(`reduce_cad.c`) with the quantified variables projected out first. The key
structural fact exploited: `cad_build` already computes the fold — a cell's
`empty` flag is exactly `!Exists` over the bound-variable fibre below it, and its
`all_true` roll-up is the `ForAll` verdict — so QE is a per-cell read, not new
projection machinery. Three regimes:

- **Fully quantified (no free variable)** — a real-closed-field **decision
  procedure**, reusing the whole engine: `Exists[{v}, φ]` is `Reduce[φ, v, Reals]
  =!= False`, `ForAll[{v}, φ]` is `... === True`. E.g.
  `Resolve[Exists[x, x^2 == 4], Reals] -> True`,
  `Resolve[ForAll[x, x^2 > 0], Reals] -> False`,
  `Resolve[Exists[{x, y}, x^2 + y^2 < 1], Reals] -> True`.
- **One free variable (parametric)** — a new public seam `reduce_cad_qe`
  (`src/solve/reduce_cad.{c,h}`) builds the CAD with the free variable outermost,
  labels each of its cells with the `Exists`/`ForAll` verdict over the bound
  fibre, and emits the merged 1-D formula through the shared
  `rru_emit_sign_diagram`. E.g. `Reduce[Exists[y, x^2 + y^2 < 1], {x}, Reals] ->
  -1 < x < 1`, `Reduce[ForAll[y, x^2 + y^2 >= 1], {x}, Reals] -> x <= -1 || x >=
  1`, `Resolve[Exists[x, x^2 == a], Reals] -> a >= 0`,
  `Reduce[ForAll[y, x^2 (1 + y^2) > 0], {x}, Reals] -> x != 0`.

## Eigenvalues/Eigenvectors — conjugate pairs list +imag first (sign-order fix)

`Eigenvalues` sorts by decreasing `|λ|`, and both the numeric Direct kernel and
the symbolic (`Root[]`/radical) path now break an exact modulus tie the same
way: the `+imag` member of a complex-conjugate pair `a ± b I` comes first. This
matches Mathematica (`Eigenvalues[{{0,-1},{1,0}}]` → `{I, -I}`) and makes the
two evaluation paths agree on the sign order — previously the symbolic path fell
back to Solve's natural `Root[]` index order, so `N[Eigenvalues[m]]` disagreed
with `Eigenvalues[N[m]]`:

```
Eigenvalues[{{0,1,0},{0,0,1},{1,1,0}}]
  before:  {Root[…,1], Root[…,2], Root[…,3]}   (* N -> {1.325, -0.662-0.562 I, -0.662+0.562 I} *)
  after:   {Root[…,1], Root[…,3], Root[…,2]}   (* N -> {1.325, -0.662+0.562 I, -0.662-0.562 I} *)
```

Implemented in `eigen_sort_by_abs_desc` (`src/linalg/eigen_common.c`): the sort
key gains an `N[Im[λ]]` secondary field, applied only on an exact `|λ|` tie so
purely real eigenvalues and free-variable symbolic eigenvalues are unaffected.
`Eigenvectors` follows for free — it computes each eigenvector from the sorted
value list, so the vector order tracks the value order. Regression tests added
for the cubic case above and the rotation matrix (`test_eigen.c`).

## REPL — completeness-driven Return (terminal multiline editing)

The interactive REPL's Return key is rebound so that **Return evaluates only
when the current buffer is a complete expression, and otherwise opens a new
line** — replacing the old trailing-`\` continuation convention. A buffer is
"complete" when it has no unterminated `"..."` string or `(* ... *)` comment and
every `(`/`[`/`{` is matched; an *over*-closed buffer (a stray `)`) submits
immediately so the parser reports the error rather than trapping the user on an
endlessly growing line. This is the terminal-native equivalent of a notebook's
Shift+Enter and needs no enhanced-keyboard protocol, so it works on every
terminal.

- **New `repl.c` internals:** `mth_input_complete()` (single-pass lexer-matching
  balance check), `mth_smart_return()` (the RET handler: complete → `rl_newline`,
  else `rl_insert_text("\n")`), `mth_force_return()` (bound to `Esc`-`Return` /
  `Meta`-`Return` to force-submit an open buffer), and `mth_setup_readline()`
  (installs the bindings and enables bracketed paste so multi-line pastes are not
  submitted a fragment at a time).
- **Build:** the feature requires *real* GNU Readline. On macOS the default
  `<readline/readline.h>` and `-lreadline` resolve to Apple's **libedit** shim,
  which silently ignores the RET rebinding and cannot edit multi-line buffers.
  The makefile now probes for a Homebrew GNU Readline on Darwin
  (`brew --prefix readline`, then `/opt/homebrew` and `/usr/local` keg paths) and
  adds its include/lib dirs; it falls back to the single-line shim when none is
  found. Linux resolves GNU Readline through `-lreadline` already. The GNU-only
  `rl_bind_keyseq` calls are guarded by `#ifdef RL_STATE_INITIALIZED` so the tree
  still compiles against the shim.
- Verified end-to-end by driving the REPL through a PTY: open brackets, spanning
  strings, spanning comments, multi-line matrices continue; balanced and
  over-closed inputs submit; `Esc`-`Return` force-submits an open buffer.

## Parser/Printer — `&&` now binds tighter than `||` (was equal precedence)

`And` (2800) and `Or` (2700) had the **same** precedence in both the parser and
the printer's parenthesiser, so mixed boolean expressions were mis-grouped and the
print→parse roundtrip was broken:

```
a || b && c   parsed to   And[Or[a,b], c]   (wrong; now Or[a, And[b,c]])
And[a, Or[b,c]]  printed   a && b || c       (wrong; re-parsed to Or[And[a,b],c])
```

`&&` must bind tighter than `||` (`a || b && c == a || (b && c)`), so `Or` is
lowered to precedence 2700 — looser than `And` (2800) and `Not` (3000), still
tighter than `Repeated` (2500). Now an `Or` nested inside an `And` (or a
parenthesised `Or` on the left of `&&`) prints with the parentheses it needs, and
`ToExpression[ToString[e]] === e` holds for these forms. Surfaced by
`Reduce[x^2 - y^2 < 1, {x, y}, Reals]`, whose (correct) `And[x<=-1, Or[…]]` cells
previously printed as `x <= -1 && y < … || y > …`, dropping the `x<=-1` guard on the
second interval. Fix in `src/parse.c`, `src/print.c` (`get_expr_prec`);
`docs/spec/operators.md` updated.

## Reduce — radicals compose with `Abs` (multivariate); univariate domain-gate soundness fix

Two defects, both exposed by composing a radical with `Abs`, are fixed. The
handling of `Abs` (sign-split into polynomial branches) and of radicals were
built as independent passes that did not compose.

**1. Multivariate radicals now rationalize (`Sqrt[Abs[x]]+Abs[y]<1` was
unevaluated).** After `Abs` splitting leaves a residual `Sqrt[u]`, the
multivariate engines (Fourier-Motzkin, CAD) gate on polynomiality and declined,
so *any* radical in ≥2 variables bubbled back unevaluated. A new preprocessing
pass rewrites `Sqrt[u] REL c` into an exact radical-free equivalent by isolating
one radical and squaring under sign guards, keeping the problem at its original
dimension for the existing polynomial CAD/FM. The `!=` case is derived directly
(not as `Not[==]`) since both are false where `u<0`; multiple radicals are cleared
by iteration; a radical that cannot be isolated with a constant coefficient (or a
non-polynomial radicand) is left in place so the engine declines soundly rather
than guess.

```
Reduce[Sqrt[Abs[x]] + Abs[y] < 1, {x, y}, Reals]  ->  |y| < 1 - Sqrt[|x|]  (was: unevaluated)
Reduce[Sqrt[x^2 + y^2] < 1, {x, y}, Reals]        ->  the open unit disk    (was: unevaluated)
Reduce[Sqrt[x] + y < 1, {x, y}, Reals]            ->  x >= 0 && y < 1 - Sqrt[x]
```

**2. Univariate domain gate is now per-conjunct (`Sqrt[Abs[x]]<1` was a WRONG
`x==0`).** The general univariate sign diagram collected each radical/`Log`/
inverse-trig domain condition into one global `And`-gate over all cells. After
`Abs` splitting, `Sqrt[x]` (needs `x>=0`) and `Sqrt[-x]` (needs `x<=0`) live in
mutually-exclusive branches, so the global gate collapsed the answer to the single
point where both hold. The gate is now scoped to the conjunct that produced each
condition.

```
Reduce[Sqrt[Abs[x]] < 1, x, Reals]  ->  -1 < x < 1            (was: x == 0, bound ignored)
Reduce[Log[Abs[x]] < 0, x, Reals]   ->  -1 < x < 0 || 0 < x < 1   (was: False)
```

Implementation: `reduce_stmt_has_radical` + the rationalization pass (`rationalize_tree`/
`rationalize_relation`, 6-row rewrite table, NNF Not-folding) in `src/solve/reduce_realfn.c`,
wired into the multivariate dispatch (`src/solve/reduce.c`) and the
`reduce_piecewise_preprocess` fixpoint; per-conjunct domain scoping in
`reduce_univar_general`/`form_truth_general` (`src/solve/reduce_realdiag.c`). Covered by
new `reduce_corpus.m` rows (sampled-equivalence + decline cases) and pinned `test_reduce.c`
strings. QE (Phase 7) and algebraic-coefficient CAD fibres (Phase 6b) remain the roadmap
route to the general aux-variable method; see `REDUCE_PLAN.md`.

## Reduce — elementary real functions (radicals, Abs, Log, inverse-trig, Floor/Mod)

`Reduce[…, x, Reals]` now solves univariate statements built from `Abs`, real
radicals `u^(p/q)`, rational poles, `Log`, bounded-domain inverse-trig, and the
isolated integer-part forms (`Floor`/`Ceiling`/`Round`, `Mod`) — a class that
previously bubbled back unevaluated (or echoed the input as `poly == 0`). A
statement containing such a function defaults its domain to the Reals. Examples:

```
Reduce[Sqrt[x+3-4Sqrt[x-1]] + Sqrt[x+8-6Sqrt[x-1]] == 1, x]   ->  5 <= x <= 10
Reduce[Sqrt[x+1-2Sqrt[x]] + Sqrt[x+16-8Sqrt[x]] == 3, x, Reals] -> 1 <= x <= 16
Reduce[(2x-1)^2 (Sqrt[x+4-4Sqrt[x]]+Sqrt[x+9-6Sqrt[x]]-1)==0, x, Reals]
                                                    -> x == 1/2 || 4 <= x <= 9
Reduce[Abs[Abs[x]-2] + Abs[Abs[x]-5] == 3, x, Reals] -> -5<=x<=-2 || 2<=x<=5
Reduce[(Abs[x+3]+Abs[x-3])/x == 2, x, Reals]         -> x >= 3
Reduce[Sqrt[x^2-4] == Sqrt[x-2] Sqrt[x+2], x, Reals] -> x >= 2
Reduce[Floor[2x-1] == 3, x, Reals]                   -> 2 <= x < 5/2
Reduce[Mod[x, 2Pi] == x - 2Pi, x, Reals]             -> 2Pi <= x < 4Pi
Reduce[ArcSin[x] + ArcCos[x] == Pi/2, x, Reals]      -> -1 <= x <= 1
Reduce[Log[x^2] == 2 Log[-x], x, Reals]              -> x < 0
Reduce[Abs[x] < 1, x, Reals]                         -> -1 < x < 1
Reduce[Sqrt[x-1] == 2, x, Reals]                     -> x == 5
```

**How** (`REDUCE_PLAN.md` Phase 9): a general univariate real **sign diagram**
(`src/solve/reduce_realdiag.c`) reusing the existing 1-D cell decomposition and
its emission. Preprocessing (`src/solve/reduce_realfn.c`) rewrites the statement
so the diagram can consume it — `Abs[u]` is eliminated by sign-splitting on the
argument, `Mod[u,m]` becomes `u - m Floor[u/m]`, and an isolated
`Floor`/`Ceiling`/`Round` relation expands to its defining inequalities. The
remaining radical/`Log`/inverse-trig atoms are placed on a diagram whose
breakpoints are the `Solve`-over-Reals roots (descending polynomial factors so an
isolated root of a squared factor survives an identity `{{}}`), the poles, and the
**domain boundaries** from a head→real-domain table (radicand `≥0`, `Log` arg
`>0`, `ArcSin`/`ArcCos` arg in `[-1,1]`, …). Each cell is tested under a
**real-domain gate**, so a point where the identity holds only in ℂ
(`ArcSin[2]+ArcCos[2]==Pi/2`, or `Sqrt[x^2-4]==Sqrt[x-2]Sqrt[x+2]` at `x=0`) is
correctly excluded; transcendental breakpoints (multiples of `Pi`) are ordered by
a numeric-sign fallback. A supporting fix in `src/solve/reduce_atom.c` skips
`Together` for branch-cut transcendentals, since `Together[Log[x^2]-2Log[-x]]`
collapses to the constant `-2 I Pi` — wrong over the reals.

Soundness is preserved: a free parameter, an undecidable sign, or an unsupported
domain node leaves `Reduce` unevaluated. At a removable `0/0` singularity the
sound open boundary is reported (`x/Sqrt[x^2]+Sqrt[x^2]/x==2 -> x > 0`). Covered
by `tests/test_reduce.c` (`test_real_functions`) and the sampling corpus
(`tests/reduce_corpus.m`).

## Reduce — `Max`/`Min`, polynomial-in-`Floor`, and a piecewise soundness gate

Two wrong-answer bugs in the Phase 9 real-function path, both caused by an opaque
atom reaching the general sign diagram (which finds breakpoints only from `Solve`
roots, poles and domain boundaries) and being scored on a single all-of-ℝ cell:

```
Reduce[Max[x^2-1, 1-x^2] > 1/2, x, Reals]     (* was True  *)
    -> x < -Sqrt[3/2] || -1/Sqrt[2] < x < 1/Sqrt[2] || x > Sqrt[3/2]
Reduce[Floor[x]^2 - 3 Floor[x] + 2 <= 0, x, Reals]   (* was False *)
    -> 1 <= x < 3
```

Both are now rewritten away in `reduce_realfn_preprocess` (`src/solve/reduce_realfn.c`)
before the diagram runs:

- **`Max`/`Min` case-split.** An innermost `Max`/`Min[a_1,…,a_n]` is eliminated by
  branching on which argument is the extremum — `Or_i[ And[ a_i ≥ a_j (j≠i),
  stmt|_{node→a_i} ] ]` (`Min` uses `≤`) — the same shape as the existing `Abs`
  sign-split, so the residual is pure-polynomial and the exact engine gives the
  precise algebraic answer. Also fixes `Reduce[Min[x,1-x]>1/4] -> 1/4<x<3/4`,
  `Reduce[Max[x,1]>2] -> x>2`, and n-ary forms.
- **Polynomial-in-`Floor`.** A relation polynomial (any degree) in a *single*
  `Floor`/`Ceiling`/`Round` node — which the linear isolator declines — is solved
  by substituting a fresh integer variable and calling `Reduce[…, k, Integers]`;
  a bounded solution set (`k == 1 || k == 2`) expands each value back to its
  defining interval and merges (`1 <= x < 3`). Works for `Ceiling`/`Round` too.
- **Fixpoint driver.** The four rewrites (`Mod`→`Floor`, `Abs`, `Max`/`Min`,
  integer-part) are iterated to a fixpoint, so a split that exposes a fresh
  `Floor` or `Max`/`Min` leaf is picked up in a later pass.

A **piecewise-head soundness gate** in `reduce_univar_general`
(`src/solve/reduce_realdiag.c`) closes the class for good: if any atom still
carries a `Floor`/`Ceiling`/`Round`/`IntegerPart`/`Mod`/`Max`/`Min`/`Abs` term in
the variable after preprocessing declined to rewrite it (e.g. the unbounded
`Reduce[Floor[x]^2 > 5, x, Reals]`), the diagram declines (stays unevaluated)
instead of guessing from one sample. New corpus cases `rf-max-*`, `rf-min-*`,
`rf-floor-quad`, `rf-ceil-quad` in `tests/reduce_corpus.m`.

## Reduce — multivariate `Max`/`Min`, general piecewise functions, unbounded integers

Extends the piecewise support above to close the gaps it left: multivariate
`Max`/`Min`, every remaining piecewise head, and the unbounded integer sets that
previously declined.

- **General piecewise case-split.** One `eliminate_piecewise`
  (`src/solve/reduce_realfn.c`) driven by a `piecewise_clauses` table splits any
  of `Piecewise`, `Sign`, `UnitStep`, `Ramp`, `Clip`, `HeavisideTheta`, `Boole`,
  `UnitBox`, `IntegerPart`, `FractionalPart` into its first-match
  `Or_i[ And[ !g_0..!g_{i-1}, g_i, stmt|_{node->v_i} ] ]` (plus a default branch);
  a head with no default (`HeavisideTheta`) leaves its undefined point out of
  every branch. `IntegerPart`/`FractionalPart` reduce to `Floor`/`Ceiling`.

  ```
  Reduce[Sign[x-1] < 0, x, Reals]              -> x < 1
  Reduce[UnitStep[x-3] == 1, x, Reals]         -> x >= 3
  Reduce[Clip[x, {-2,2}] < 1, x, Reals]        -> x < 1
  Reduce[Piecewise[{{x^2, x>0}}, -x] > 2, x]   -> x < -2 || x > Sqrt[2]
  Reduce[Boole[x>0] + Boole[x>1] == 2, x, Reals] -> x > 1
  Reduce[IntegerPart[x] == 2, x, Reals]        -> 2 <= x < 3
  ```

- **Multivariate `Max`/`Min`/piecewise.** The selector splits (Abs, Max/Min, the
  piecewise heads) are variable-count- and domain-agnostic, so a new
  `reduce_piecewise_preprocess` runs them for `nv >= 2` and hands the polynomial
  `And`/`Or` result to the Fourier-Motzkin / CAD engines.

  ```
  Reduce[Max[x, y] > 2, {x, y}, Reals] -> x > 2 && y <= x || y >= x && y > 2
  Reduce[Abs[x] + Abs[y] < 1, {x, y}, Reals] -> the four sectors of the L1 ball
  ```

- **Unbounded integer sign diagram.** `reduce_univar_integers`
  (`src/solve/reduce_univar.c`) now emits one-sided rays for a satisfied tail
  (`Reduce[x > 0, x, Integers] -> x >= 1`, `Reduce[k^2 > 5, k, Integers] ->

  ```
  Reduce[Floor[x]^2 > 5, x, Reals]    -> x < -2 || x >= 3
  Reduce[Ceiling[x]^2 > 5, x, Reals]  -> x <= -3 || x > 2
  ```

  `translate_ksol` accepts all six `k REL int` relations, and `ip_defining` gains
  the full `Ceiling` relation set (`Round` stays `Equal`-only: it is
  round-half-to-even, so its inequalities decline rather than approximate).

New symbols `SYM_Ramp`, `SYM_UnitBox`. Tests: `test_piecewise_functions` in

## N — bare `N[expr]` now targets machine precision

Fixed `N[expr]` (one-argument) to give a **machine-precision** result even when
`expr` is already an approximate arbitrary-precision number, matching
Mathematica. `N[N[Pi, 100]]` now returns `3.14159` at `MachinePrecision`
instead of keeping the argument's 100 digits; `N[2.5\`100]` likewise collapses
to machine precision. The two-argument form is unchanged — `N[N[Pi, 100], 30]`
gives 30 digits, and it still never manufactures digits (`N[N[Pi, 100], 200]`
stays at 100).

Root cause: the one-argument `N` builtin set a `preserve_inexact` flag on
`NumericSpec` that told `numericalize` to keep an already-approximate MPFR leaf
at its precision under machine mode. That flag existed solely to implement this
(incorrect) behavior — every other call site set it `false` — so it has been
removed entirely from `src/numeric.{c,h}` and its ~15 downstream call sites.

## ComplexPlot — brighter default, 8-argument ColorFunction, muted pole chatter

Three fixes to `ComplexPlot` / `ComplexPlot3D` (`src/graphics/complexplot.c`):

- **Default no longer looks too dark.** The modulus was folded into the phase
  hue as a plain brightness multiplier `|w|/(1+|w|)`, which is `0.5` at
  `|w| = 1`, so a bounded function (`|f| ≈ 1` over most of the plane, e.g.
  `(z^2-1)/(z^2+1)`) rendered at ~50 % brightness everywhere. It is now an
  **HSL lightness** `L = |w|/(1+|w|)`: below `1/2` the saturated hue fades to
  black (zeros → black), above it toward white (poles → white). Mean cell
  luminance on the report case rose `0.265 → 0.523` (≈2×). The default stays
  byte-for-byte identical to `ColorFunction -> "Cyclic"` (both share
  `cp_ramp_color`).

- **`ColorFunction` now receives Mathematica's eight arguments.** A custom
  `ColorFunction` was called `f[Re[f], Im[f]]` (a 2-argument DensityPlot
  convention), so `ColorFunction -> (Hue[#8 + 0.5] &)` failed — `#8` was an
  unsupplied `Slot`. It now supplies `#1 Re[z]`, `#2 Im[z]`, `#3 Abs[z]`,
  `#4 Arg[z]`, `#5 Re[f]`, `#6 Im[f]`, `#7 Abs[f]`, `#8 Arg[f]`, each scaled to
  `[0,1]` across the sampled grid when `ColorFunctionScaling -> True` (the
  default). A one-argument colour map falls back to the scaled `Arg[f]`.
  `is_color_head` now also requires every colour component to be a real number,
  so a half-symbolic `Hue[0.5 + #8]` is rejected rather than handed to the
  renderer.

- **Spurious `Power::infy` at poles muted.** Sampling a function with poles hits
  `1/0` at the grid points sitting on a pole (`z = 0` for `(z^3-3)/z`; `z = ±i`
  for `1/(z^2+1)`); those cells are simply dropped, so the informational
  `Power::infy` messages are now muted during the sampling loop
  (`arith_warnings_mute_push/pop`), exactly as `Plot` and the numeric optimizers
  do. The compiled fast path also gained the `isfinite` guard the interpreter
  path already had, so a compiled pole no longer marks a cell valid with
  `|w| = inf` and poisons the `ColorFunctionScaling` ranges.

Docs and docstrings updated; leak-checked with a differential `valgrind` run
(no new "definitely lost" vs. the prior build); `autocompile_tests`,
`graphics_tests`, `graphics_sampling_tests` pass.

## Interval — special & piecewise functions thread over `Interval[...]`

Elementary functions already threaded over `Interval[{lo, hi}]` (`Sin`, `Exp`,
`Gamma`, …); most **special functions** and the **piecewise** heads did not, so
`Erfi[Interval[{0, 1}]]` or `Round[Interval[{-1/2, 5/2}]]` were left unevaluated.
They now thread the same way — rigorous enclosures where a bound can be
certified, clean symbolic fallback otherwise.

- **General derivative-sign certifier** (`interval_thread_call`, `src/interval.c`;
  wired into the evaluator in `src/eval.c` right after the builtin returns
  `NULL`). For any `NumericFunction` with a single `Interval` argument that no
  builtin handled, it interval-evaluates the symbolic derivative `D[f[x], x]`
  over each pair and, when the enclosure is entirely one sign, threads `f`
  monotonically. Rigorous (interval evaluation only over-estimates, so a
  certified sign is always correct) and general (reuses `D[]` and the
  interval-aware evaluator — no per-function monotonicity analysis). New
  coverage includes `Erfi`, `ExpIntegralEi`, `LogIntegral`, `PolyLog[n, ·]`, and
  the incomplete `Gamma[a, ·]`. A small recursion cap keeps oscillatory heads
  (`BesselJ`, `Sinc`, …) fast and symbolic instead of chasing a derivative chain
  that never bottoms out.

- **Bespoke monotone-sub-domain rows** (`interval_apply_function`) for functions
  whose derivative is self-referential/awkward but which are simply monotone:
  `InverseErf` (on `(-1, 1)`), `InverseErfc` (on `(0, 2)`), `ProductLog`
  (on `(-1/e, ∞)`), `HarmonicNumber` (on `(-1, ∞)`), and `Erfi` (on ℝ).

- **Piecewise/step functions** `UnitStep`, `Ramp`, `Round`, `IntegerPart` now
  thread (non-decreasing, so endpoint threading is a rigorous enclosure),
  joining `Floor`/`Ceiling`. The sawtooth `FractionalPart` stays symbolic.

Verified by the extended `tools/interval_fuzz.py` (`make check-interval`, ~30k
random containment checks now including the new heads) and new cases in
`tests/test_interval.c`.

## Integrate — `nonelem` message emitted once, and no more double cascade

`Integrate[Log[x] Log[Log[x]]/x^2, x]` printed the `Integrate::nonelem`
diagnostic **four** times — twice naming internal recursion variables
(`Integrate`DerivativeDivides`u$N`) and twice naming the real integrand. Two
independent defects were behind it:

- **Leaky recursive messages.** `DerivativeDivides` substitutes `u = Log[x]` and
  recurses via `Integrate[u Log[u] E^(-u), u]`, which reaches the same
  `RischTranscendental` decision stage and emitted a `nonelem` message naming the
  internal gensym. The message now fires only at the outermost integration
  (`g_integrate_depth <= 1`, tracked around the method cascade in
  `builtin_integrate`), so a sub-integral spawned by an internal substitution
  never names its own recursion variable — a user diagnostic only ever names the
  user's integrand.

- **Double cascade.** `Integrate[Times[Log[x], Log[Log[x]], Power[x,-2]], x]`
  reorders under Orderless on the first `evaluate_step`, so the fixed-point loop
  ran a second step and re-invoked the *entire* (Eliminate/Solve-driven) method
  search on the byte-identical integrand — doubling the work and the message.
  `builtin_integrate` now carries a per-command fail-memo: an integrand the
  cascade already proved has no answer this top-level evaluation short-circuits
  to `NULL` immediately. The memo is a fixed 32-slot table keyed on a new
  `eval_toplevel_id()` (bumped once per user command in `evaluate()`), so it
  needs no dynamic allocation and self-invalidates every command — a genuine
  re-run in a later command re-runs the search and re-warns. Several distinct
  failing integrals in one command (e.g. a `List` of them) each keep their own
  slot, so none re-emits when the outer structure takes a second pass.

Result: the reported integral prints the message exactly once, naming
`(Log[x] Log[Log[x]])/x^2`, and the expensive search runs once instead of twice.
Solvable, definite, and list-threaded integrals are unchanged.

## Integrate — wrong `0` for transcendental-coefficient / single-extension integrands

`Integrate[Sin[x]/Log[x], x]` returned a **wrong `0`** (and likewise
`Cos[x]/Log[x]`, `Tan[x]/Log[x]`, `Sin[x]/Log[x]^2`, `ArcTan[x]/Log[x]`,
`Gamma[x]/Log[x]`, `Sin[x]/(1+E^x)`, `BesselJ[0,x]/Log[x]`, …). Root cause: the
single-extension Risch cases (`rt_frac_try`, `rt_hermite_try`,
`rt_hyperexp_case` in `risch_singleext.c`) kernelize the integrand at `t = Log[x]`
(or `E^x`) and then solve a Rothstein-Trager polynomial identity with
`SolveAlways[..., {t, x}]`. Their gate only checked that numerator/denominator
were polynomials in `t` with no *other* log/exp of x — it did **not** verify the
coefficients were rational in x. A transcendental coefficient such as `Sin[x]`
slipped through as a degree-0 "polynomial" in `t`; `SolveAlways` then treated the
stray `Sin[x]` as an independent unknown and solved it away
(`{{Sin[x] -> 0, k -> 0}}`), certifying a bogus antiderivative whose residue
symbols zeroed out to `0`.

Fix: a `C(x)(t)` membership gate (`rt_is_ratl_in_xt`) now guards all three cases
— the kernelized numerator and denominator must be genuine rational functions of
x and the kernel `t` (built only from x, t, x/t-free constants, and Plus/Times/
Power-with-integer-exponent). Integrands outside that field (a transcendental or
algebraic coefficient of x) are declined instead of mis-certified. Every such
integrand now stays unevaluated (with the usual `nonelem` note), while genuine
`C(x)(t)` integrals — `1/(x Log[x]) -> Log[Log[x]]`, `1/(1+E^x)`,
`1/(E^x (1+E^x)^2)`, the special-function recognizers, and elementary
`Sin[x] E^x` (handled by the multi-kernel path) — are unchanged.

## Graphics — Plot3D/Graphics3D frame ticks (inward marks + minor sub-ticks)

The `Axes` bounding box for `Plot3D`, `ParametricPlot3D`, `ComplexPlot3D` and
raw `Graphics3D` previously drew only numeric axis labels — no tick marks. Each
of the three edges meeting at `(xmin, ymin, zmin)` now carries proper ticks,
matching Mathematica's look:

- **Major ticks** land on the shared `nice_step` values, are labelled, and point
  **inward** (into the box); the numeric label sits just **outside** the box on
  the opposite side of the edge.
- **Minor sub-ticks** subdivide each major interval, shorter and unlabelled,
  using the same `frame_minor_divs` policy the 2D frame uses (a major step of 1
  splits into 5, 2 into 4, 5 into 5 — so minors always fall on round values).

Implementation (`src/graphics/render3d.c`, replacing the label-only
`draw_tick_label3`):

- `box_edge_normal` gives the screen-space **outward** unit normal at an edge
  point: `(P − boxcentre)` with the along-edge component zeroed, projected and
  normalised in screen space. Ticks are drawn a fixed pixel length *against*
  that normal (inward); labels a fixed gap *along* it (outward). Working in
  screen space makes every mark a constant pixel length regardless of
  `BoxRatios` scaling or perspective foreshortening.
- `draw_edge_ticks` iterates by **integer index over the minor step**, so major
  detection (`i % sub == 0`) and label values (`(i/sub)·step`) are exact — no
  float-accumulation drift, no spurious `-0` or `0.9999` labels.
- Both render paths (interactive `graphics3d_show` and the offscreen
  `Export`/region path) call the one function, so they cannot drift; labels
  still format from the untransformed data bbox → true data values under any
  `BoxRatios` transform.
- `frame_minor_divs` moved from `render.h` to `render_common.h` (its natural
  home next to `nice_step`) so both the 2D and 3D renderers share the one
  tick-subdivision policy. `render.h` deliberately stays raylib-free (core files
  such as `imageio.c` include it in `USE_GRAPHICS=OFF` builds).

## Reduce — Phase 6d: n-variable Cylindrical Algebraic Decomposition over the Reals

`Reduce[expr, {x1, ..., xn}, Reals]` now solves nonlinear real inequality
statements in **three or more** effective variables (previously declined). The
two-variable CAD from Phase 6a–6c is generalized to a single recursive engine.

- **Recursive engine** (`reduce_cad_nvar` in `src/solve/reduce_cad.c`): an
  iterated McCallum projection builds the projection stack (discriminant, leading
  coefficient, pairwise resultant, all factored), eliminating the variables from
  last to first; the base sign diagram is then lifted by a recursive descent that
  substitutes each cell's rational sample, isolates the next variable's real
  roots, and recurses, with partial-CAD pruning at every level and the innermost
  dimension merged into a symbolic region. Truth is decided at one sample per
  full-dimensional cell by the exact real-algebraic sign oracle.
- **Output**: strict inequalities read as a clean nested conjunction, e.g.
  `Reduce[x^2+y^2+z^2 < 1, {x,y,z}, Reals]` ->
  `-1 < x < 1 && -Sqrt[1-x^2] < y < Sqrt[1-x^2] && -Sqrt[1-x^2-y^2] < z < Sqrt[1-x^2-y^2]`;
  `Reduce[x y z > 0, {x,y,z}, Reals]` -> the four positive octants;
  `Reduce[x^2 < 1 && y^2 < 1 && z^2 < 1, {x,y,z}, Reals]` -> the open box;
  `Reduce[x^2+y^2+z^2 >= 0, ...] -> True`, `... < 0 -> False`. A **closed** region
  currently emits a correct but verbose union of cells (the boundary spheres/arcs/
  poles listed separately); the n-D boundary merge that would close an outer range
  (`-1 <= x <= 1 && ...`) is a later cosmetic pass — the answer is complete and
  sound either way.
- **Soundness invariant** (unchanged): an undecidable sign/ordering, an irrational
  non-innermost breakpoint (v1 rational-fibre regime — real-algebraic-coefficient
  fibre isolation is deferred, so e.g. `x^2+y^2+z^2 <= 2` with base `±Sqrt[2]`
  declines), an un-emittable fibre, or an interval nullification (McCallum
  well-orientedness augmentation deferred) all leave `Reduce` unevaluated rather
  than emit a wrong formula. The two-variable path and its boundary-merged output
  are unchanged (byte-identical).
- **Tests**: `tests/test_reduce.c` gains `test_cad_nvar` (clean-form,
  True/False, and decline pins); `tests/reduce_corpus.m` gains `cad3-*` /
  `cad4-*` rows verified by the form-agnostic sample-point oracle.
  `make check-c99` clean; valgrind leak-clean (only macOS ObjC-runtime baseline
  noise).

### Phase 6d Stage B: n-D boundary merge (closed regions)

The recursive engine now builds a cell **tree** and runs an n-D boundary merge —
the recursive generalization of the two-variable merge — so a **closed** region
closes its outer ranges instead of listing the boundary cells:
`Reduce[x^2+y^2+z^2 <= 1, {x,y,z}, Reals]` ->
`-1 <= x <= 1 && -Sqrt[1-x^2] <= y <= Sqrt[1-x^2] && -Sqrt[1-x^2-y^2] <= z <= Sqrt[1-x^2-y^2]`
(matching the two-variable disk); the sphere surface, closed half-ball, and the
4-variable closed ball merge likewise. A run of interval cells sharing one
symbolic template absorbs the section between (and at the ends) whose fibre equals
the template's limit there; **cell equality is decided by sampling** the emitted
sub-formulas over a grid drawn from the cell structure, so any undecidable
comparison leaves the already-correct unmerged (verbose) form — soundness over
completeness, verified by the corpus oracle. Strict regions stay open. Version
bumped to 0.088.

## Reduce / Solve — zero-dimensional nonlinear systems (issue #69)

`Reduce` and `Solve` now solve a conjunction whose polynomial **equations** pin
the variety to finitely many points (a zero-dimensional ideal), optionally
carrying polynomial inequality / disequation constraints — the case both engines
previously left unevaluated. This is the three-circle system from issue #69:

```
Reduce[u^2 + v^2 == 9 && u^2 + (a + v)^2 == 36 && (a + u)^2 + v^2 == 25 &&
       u > 0 && v > 0 && a > 0, {u, v, a}]
  -> u == ... && v == ... && a == ...        (the single all-positive branch)

Solve[<same>, {u, v, a}]   -> {{u -> ..., v -> ..., a -> ...}}
```

New engine `reduce_zerodim` (`src/solve/reduce_zerodim.{c,h}`), shared by both:

1. Split each conjunct into equations `E` and side relations `O` (`<`,`<=`,`!=`).
2. Solve `E` over the complexes with the existing polynomial-system solver; a
   finite, fully-determined answer means `E` is zero-dimensional (a parametric /
   underdetermined answer means it is not, and the engine **declines**).
3. Keep each solution branch only if every side relation holds there and — over
   the Reals — every coordinate is real, decided **exactly** by the FLINT
   `qqbar` algebraic-number oracle (sign / equality / realness). An undecidable
   test **declines** (sound over complete).

Complete for zero-dimensional systems (the finite solution set is enumerated and
filtered exactly) and sound (any gap yields a decline). `Reduce` emits an `Or` of
`And(var == value)`; `Solve` emits the surviving branches as solution rule-lists.
Wired into `reduce.c` (Complexes and Reals fallbacks, after the linear and CAD
engines) and `solve.c` (an equations-with-constraints pre-pass mirroring the
`Integers` pre-pass). New oracle `flint_qqbar_is_real` distinguishes a non-real
branch (drop) from an undecidable one (decline). Newly-solved cases that were
`decline` are promoted in the corpora; new corpus + unit cases cover decoupled
systems, complex-branch rejection over the Reals (`x^2+y^2==1 && x==2 -> False`),
and the issue's three-circle system. Reduce corpus 158/158, Solve corpus 99/99;
`make check-c99` clean; valgrind shows no new leaks.

## Parser — backslash line continuation in scripts and `Get` (issue #69)

A backslash immediately before a newline is now a line continuation (Mathematica
syntax): the lexer (`skip_whitespace`, `src/parse.c`) joins the two physical
lines into one logical line without emitting a statement break, handling LF, CR,
and CRLF endings. Previously a `\`-continued `.m` file read via `Get[]` / `-file`
failed with `Unexpected character: '\'`. A backslash **not** before a newline
still errors as before, so stray backslashes are unaffected.

## Linear algebra — seamless machine → arbitrary-precision fallback on overflow

`Det`, `Norm`, and `Normalize` now defer from machine `double` to arbitrary
precision when the machine result would over/underflow, instead of returning
`inf` / `0` / a zero vector for inputs whose true answer is representable.

- **`Det` (machine reals)** — the determinant is the product of the LU pivots,
  which can leave the IEEE-double range even for an ordinary matrix (a 200×200
  `RandomReal[{-10,10}]` matrix has `|Det| ≈ 10^340`). `Det[arr]` returned
  `-inf.0`; it now re-accumulates the pivot product in a 53-bit-mantissa MPFR
  value (wide exponent) and returns `≈ -1.08×10^340`, correct to machine
  precision (rel. err ~1e-14 vs. the exact determinant). A mid-product underflow
  that previously collapsed a representable determinant to `0.0` (e.g.
  `Det[DiagonalMatrix[{1e-200, 1e-200, 1e300, 1e300}]]`) now returns the true
  `1e200`. Genuinely singular matrices still return `0`. The complex branch has
  the same protection (`Complex[mpfr, mpfr]` on overflow). New helpers
  `nd_real_det_result` / `nd_complex_det_result` in `src/linalg/ndlinalg.c`.
- **`Det` (arbitrary-precision matrices)** — a genuine MPFR matrix (precision >
  machine) previously fell through to the `O(n!)` Laplace expansion and hung for
  `n ≳ 12` (a 16×16 aborted at 20 s). New `mpfr_det_dispatch`
  (`src/linalg/ludecomp_mpfr.c`, declared in `ludecomp_internal.h`) computes
  `sign(P)·∏U[k,k]` from the existing MPFR Doolittle LU in `O(n^3)`; wired into
  `builtin_det` (`src/linalg/det.c`) after the FLINT exact path and before
  Laplace. A 40×40 MPFR determinant is now instant.
- **`Norm` / `Normalize` (machine vectors)** — the vector 2-norm hand-rolled
  `Sqrt[Σ x^2]`, which overflowed once any `|x_i| > ~1.3×10^154`
  (`Norm[{1e200, 1e200}]` → `inf`) and made `Normalize` return the zero vector.
  The 2-norm now uses LAPACK `dnrm2`'s running-scale recurrence
  (`nd_vec_2norm`), and the `p`-norm scales by the max component; both in
  `src/linalg/ndlinalg.c`. A small unpacked machine `List` is routed to this
  fast path from `src/linalg/norm.c` (exact vectors keep `Sqrt[5]`-style exact
  answers; MPFR vectors stay symbolic, their wide exponent already safe).
- **`CharacteristicPolynomial`** recorded as `EXEMPT` in
  `tools/compile_coverage.py` — it returns a symbolic `Plus` in `x`, not a
  machine array, so (like `Eigenvalues` / `Eigenvectors`, whose result type/shape
  is data-dependent) it cannot lower to a statically-typed compiled register.
  `Det` continues to compile via `ndla_det`.

`Eigenvalues` / `Eigenvectors` on machine matrices already use LAPACK `dgeev`
(finite and fast at 200×200) and were unaffected. Relevant test suites
(`linalg`, `ndarray_linalg`, `normalize`, `eigen`, `ludecomposition_*`,
`compile_linalg`) all green.

## RootReduce — threads over a Rule; `Solve[...] // RootReduce` fixed (bug fix)

`RootReduce` now threads over an (immediate) `Rule`, so applying it to a `Solve`
result reduces the right-hand side of each `u -> value` entry — exactly as
`RootReduce` already reduces each `u == value` in a `Reduce` result. For the
Goursat three-circle system, `Solve[...] // RootReduce` and
`Reduce[...] // RootReduce` now return the *same* `Root` objects
(`u -> Root[207025 - 226216 #1^2 + 31520 #1^4 &, 3]`, ...).

Previously `RootReduce[u -> value]` emitted `RootReduce::argx: called with 0
arguments` and left the rule unevaluated. Root cause: the option/positional
splitter (`is_option_rule` in `src/rootreduce.c`) treated *any* `Rule` with a
symbol left-hand side as a trailing option, so `u -> value` was consumed as an
option and no positional argument remained. It now recognises only a `Rule`
whose LHS names a *registered* option of `RootReduce` (i.e. `Method`, read from
`Options[RootReduce]` via `symtab_get_options`) as an option; every other
symbol-LHS rule is a positional argument. The generic "map RootReduce over the
parts and re-evaluate" tail of the relational threading was factored into a
shared `thread_parts` helper and reused for the `Rule` case: the free-variable
LHS is left intact (`RootReduce` of a bare symbol is the identity) and only the
RHS is reduced. `RuleDelayed` is deliberately *not* threaded — it holds its RHS,
so threading would strand an un-fired `RootReduce` there, and `Solve`/`Reduce`
results are always immediate rules. The `Method` option and the `argx`/`mtd`
diagnostics are unchanged. Regression coverage: `test_rootreduce_rule` in
`tests/test_rootreduce.c`.

## Build fix — no-FLINT compile of `reduce_algfiber.c` (Linux CI green)

The Phase 6b fibre-isolation helpers in `src/solve/reduce_algfiber.c`
(`mkfun3`, `is_zero_expr`, `node_count`, `degree_in`, `subst_point`,
`prov_push`, plus their `mkfun2`/`repl` dependencies) are used *only* inside the
`#ifdef USE_FLINT` branch of `rru_algebraic_fiber_roots` — the qqbar oracle is
what the routine needs, and without it the function declines up front. In the
`build-no-mpfr` CI config (`USE_MPFR=0 USE_FLINT=0`) that branch is compiled
out, leaving the helpers as dead `static` functions and tripping
`-Werror=unused-function` (gcc-14/glibc), which broke the Linux build at
commit `4f53852` (v0.113). The helper block is now guarded by `#ifdef USE_FLINT`
so it compiles only when the branch that uses it does. No behavioural change: the
guard is a no-op whenever `USE_FLINT` is defined (every default/test build), and
the no-FLINT path was already a bare `return false`. Verified: clean
`make USE_MPFR=0 USE_FLINT=0 USE_ECM=0 USE_LAPACK=0 USE_GRAPHICS=0` and clean
default `make` both succeed; `make check-c99` clean.

## Computational geometry — Area, Perimeter, RegionCentroid, RegionMember, ConvexHullRegion (Verified)

New `src/geometry.c` module (ticket GEO-1) adding the first computational-geometry
builtins: `Area`, `Perimeter`, `RegionCentroid` and boundary-inclusive `RegionMember`
over simple 2D `Polygon`s, plus `ConvexHullRegion` (monotone-chain hull returning
`Polygon`/`Line`/`Point`). Exact GMP-rational path for exact coordinates — `Area` of a
rational triangle is exactly `1/4`, `Perimeter` produces symbolic radical sums like
`2 + Sqrt[2]` — with machine-double contagion when any `Real` coordinate appears, and
visible-`NDArray` point matrices accepted. Out-of-scope input (symbolic coordinates,
3D points, `Polygon` holes) declines and stays unevaluated. All semantics locked to
live Wolfram kernel reference outputs; spec page `docs/spec/builtins/geometry.md`
carries the deviation list (simple polygons only; zero-area `RegionCentroid` declines;
bare-`Polygon` hull output). Tests: `tests/test_geometry.c` (ctest `geometry_tests`)
plus the end-to-end script `tests/scripts/geometry_e2e.m`.

### Exact geometry paths — 2.4x faster hulls, 1.9x faster point-in-polygon

`geom_cross_sign_q`, the exact cross-product predicate, allocated and freed six
`mpq_t` temporaries on every single evaluation. It runs in two O(n) inner loops --
the monotone-chain hull and `RegionMember`'s edge walk -- so a `sample` profile of
`ConvexHullRegion` over 2000 exact-integer points spent the majority of both chain
loops inside `mpq_inits`/`mpq_clears` and the allocator beneath them rather than in
the arithmetic. The temporaries now live in one caller-owned block per builtin call
(the same hoist `geom_signed_area2_q` already used), so GMP keeps each limb buffer at
its high-water mark and reuses it. Arithmetic and results are unchanged.

Measured on this machine, best of five isolated runs per metric, 2000-point inputs,
each metric in its own process (an in-process benchmark suite mismeasures this by up
to 40% -- the hull's allocator traffic perturbs every metric that follows it):

| metric | before | after | speedup |
|---|---|---|---|
| `ConvexHullRegion`, exact integer | 0.1346 s | 0.0549 s | 2.45x |
| `ConvexHullRegion`, exact rational | 0.1650 s | 0.0823 s | 2.00x |
| `RegionMember`, exact | 0.0406 s | 0.0208 s | 1.95x |
| `ConvexHullRegion`, machine | 0.0042 s | 0.0040 s | 1.05x |
| `Area`/`RegionCentroid`, exact and machine | — | — | unchanged (1.00x) |

`Area` and `RegionCentroid` do not use the predicate and are untouched, as expected.

`tests/test_geometry.c` gains `test_scale_and_scratch_reuse`: the temporaries are now
reused across evaluations within a call, so GMP sizes each buffer to that call's
widest operand and every later, narrower evaluation runs on it. The acceptance rows
are all at most five small vertices and cannot see a fault in that. The new case
builds a 240-point deterministic set spanning six orders of magnitude and asserts
oracle-free invariants -- hull containment, hull idempotence, call-to-call stability,
and exact/machine agreement -- so a stale or aliased temporary fails in the suite.
`tests/scripts/geometry_leakcheck.sh` was confirmed sensitive by injection: removing
one `geom_cross_tmp_clear` makes it report 4800 leaks / 153600 bytes and fail, while
the whole C suite still passes.
