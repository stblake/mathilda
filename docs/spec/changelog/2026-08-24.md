# Changelog: week of 2026-08-24 (Mon) – 2026-08-30 (Sun)

## Integrate — `nonelem` message emitted once, and no more double cascade

`Integrate[Log[x] Log[Log[x]]/x^2, x]` printed the `Integrate::nonelem`
diagnostic **four** times — twice naming internal recursion variables
(`Integrate`DerivativeDivides`u$N`) and twice naming the real integrand. Two
independent defects were behind it:

- **Leaky recursive messages.** `DerivativeDivides` substitutes `u = Log[x]` and
  recurses via `Integrate[u Log[u] E^(-u), u]`, which reaches the same
  `RischTranscendental` decision stage and emitted a `nonelem` message naming the
  internal gensym. The message now fires only at the outermost integration
  (`g_integrate_depth <= 1`, tracked around the method cascade in
  `builtin_integrate`), so a sub-integral spawned by an internal substitution
  never names its own recursion variable — a user diagnostic only ever names the
  user's integrand.

- **Double cascade.** `Integrate[Times[Log[x], Log[Log[x]], Power[x,-2]], x]`
  reorders under Orderless on the first `evaluate_step`, so the fixed-point loop
  ran a second step and re-invoked the *entire* (Eliminate/Solve-driven) method
  search on the byte-identical integrand — doubling the work and the message.
  `builtin_integrate` now carries a per-command fail-memo: an integrand the
  cascade already proved has no answer this top-level evaluation short-circuits
  to `NULL` immediately. The memo is a fixed 32-slot table keyed on a new
  `eval_toplevel_id()` (bumped once per user command in `evaluate()`), so it
  needs no dynamic allocation and self-invalidates every command — a genuine
  re-run in a later command re-runs the search and re-warns. Several distinct
  failing integrals in one command (e.g. a `List` of them) each keep their own
  slot, so none re-emits when the outer structure takes a second pass.

Result: the reported integral prints the message exactly once, naming
`(Log[x] Log[Log[x]])/x^2`, and the expensive search runs once instead of twice.
Solvable, definite, and list-threaded integrals are unchanged.

## Integrate — wrong `0` for transcendental-coefficient / single-extension integrands

`Integrate[Sin[x]/Log[x], x]` returned a **wrong `0`** (and likewise
`Cos[x]/Log[x]`, `Tan[x]/Log[x]`, `Sin[x]/Log[x]^2`, `ArcTan[x]/Log[x]`,
`Gamma[x]/Log[x]`, `Sin[x]/(1+E^x)`, `BesselJ[0,x]/Log[x]`, …). Root cause: the
single-extension Risch cases (`rt_frac_try`, `rt_hermite_try`,
`rt_hyperexp_case` in `risch_singleext.c`) kernelize the integrand at `t = Log[x]`
(or `E^x`) and then solve a Rothstein-Trager polynomial identity with
`SolveAlways[..., {t, x}]`. Their gate only checked that numerator/denominator
were polynomials in `t` with no *other* log/exp of x — it did **not** verify the
coefficients were rational in x. A transcendental coefficient such as `Sin[x]`
slipped through as a degree-0 "polynomial" in `t`; `SolveAlways` then treated the
stray `Sin[x]` as an independent unknown and solved it away
(`{{Sin[x] -> 0, k -> 0}}`), certifying a bogus antiderivative whose residue
symbols zeroed out to `0`.

Fix: a `C(x)(t)` membership gate (`rt_is_ratl_in_xt`) now guards all three cases
— the kernelized numerator and denominator must be genuine rational functions of
x and the kernel `t` (built only from x, t, x/t-free constants, and Plus/Times/
Power-with-integer-exponent). Integrands outside that field (a transcendental or
algebraic coefficient of x) are declined instead of mis-certified. Every such
integrand now stays unevaluated (with the usual `nonelem` note), while genuine
`C(x)(t)` integrals — `1/(x Log[x]) -> Log[Log[x]]`, `1/(1+E^x)`,
`1/(E^x (1+E^x)^2)`, the special-function recognizers, and elementary
`Sin[x] E^x` (handled by the multi-kernel path) — are unchanged.

## Graphics — Plot3D/Graphics3D `Ticks` option (None + custom)

`Plot3D`, `ParametricPlot3D`, `ComplexPlot3D` and raw `Graphics3D` now honour a
`Ticks` option on the `Axes` bounding box (added to `Options[Plot3D]`, default
`Automatic`):

- `Ticks -> None` — the box still draws, but with no ticks or labels.
- `Ticks -> {xspec, yspec, zspec}` — one spec per axis (a missing trailing entry
  is `Automatic`); each spec is `Automatic`, `None`, a list of positions
  `{v1,...}` (labelled majors, no minors), or a list of `{position, label}` pairs
  (string label verbatim, else printed). Bare numbers and `{pos, label}` pairs
  may be mixed.

Implementation:

- New interned `SYM_Ticks`; parsed into `Gfx3DOptions.ticks` (borrowed) in
  `gfx3d_options_parse` (`src/graphics/render3d.c`). `Plot3D`'s generic option
  passthrough already forwards `Ticks` onto the emitted `Graphics3D`, so no
  `plot3d.c` change was needed.
- `draw_box_ticks` became a dispatcher: whole-value `None` skips all ticks;
  otherwise each axis independently takes `Automatic` (`draw_edge_ticks`),
  `None` (skipped), or an explicit list (`draw_edge_ticks_list`). Automatic and
  custom majors share one placement helper (`draw_one_major_tick`), so their
  mark length, thickness, and label gap cannot drift. Both render paths
  (interactive + offscreen/Export) parse and honour it.
- `Ticks -> Automatic` added to the `Options[Plot3D]` table in
  `src/options_builtin.c`.

## Graphics — Plot3D/Graphics3D frame ticks (inward marks + minor sub-ticks)

The `Axes` bounding box for `Plot3D`, `ParametricPlot3D`, `ComplexPlot3D` and
raw `Graphics3D` previously drew only numeric axis labels — no tick marks. Each
of the three edges meeting at `(xmin, ymin, zmin)` now carries proper ticks,
matching Mathematica's look:

- **Major ticks** land on the shared `nice_step` values, are labelled, and point
  **inward** (into the box); the numeric label sits just **outside** the box on
  the opposite side of the edge.
- **Minor sub-ticks** subdivide each major interval, shorter and unlabelled,
  using the same `frame_minor_divs` policy the 2D frame uses (a major step of 1
  splits into 5, 2 into 4, 5 into 5 — so minors always fall on round values).

Implementation (`src/graphics/render3d.c`, replacing the label-only
`draw_tick_label3`):

- `box_edge_normal` gives the screen-space **outward** unit normal at an edge
  point: `(P − boxcentre)` with the along-edge component zeroed, projected and
  normalised in screen space. Ticks are drawn a fixed pixel length *against*
  that normal (inward); labels a fixed gap *along* it (outward). Working in
  screen space makes every mark a constant pixel length regardless of
  `BoxRatios` scaling or perspective foreshortening.
- `draw_edge_ticks` iterates by **integer index over the minor step**, so major
  detection (`i % sub == 0`) and label values (`(i/sub)·step`) are exact — no
  float-accumulation drift, no spurious `-0` or `0.9999` labels.
- Both render paths (interactive `graphics3d_show` and the offscreen
  `Export`/region path) call the one function, so they cannot drift; labels
  still format from the untransformed data bbox → true data values under any
  `BoxRatios` transform.
- `frame_minor_divs` moved from `render.h` to `render_common.h` (its natural
  home next to `nice_step`) so both the 2D and 3D renderers share the one
  tick-subdivision policy. `render.h` deliberately stays raylib-free (core files
  such as `imageio.c` include it in `USE_GRAPHICS=OFF` builds).

## Graphics — classic "Jet" ColorFunction ramp

`ColorFunction -> "Jet"` now resolves to the classic MATLAB/matplotlib `jet`
colormap (dark blue → cyan → green → yellow → red → dark red) across every
gradient plotter — `Plot3D`, `ParametricPlot3D`, `DensityPlot`, `ContourPlot`,
`VectorPlot`, `StreamPlot`, `ArrayPlot`, `Plot`/`ParametricPlot`/`PolarPlot` —
and the rendered colour-scale bar. Previously the name was unrecognised and
silently fell back to the default (`"Viridis"`).

- Added `jet_rgb` in `src/graphics/plot_common.c`, evaluated **exactly** from
  `jet`'s piecewise-linear per-channel segment definition (the three channels
  break at independent positions — the very reason `jet` is not perceptually
  uniform), so it is computed channel-by-channel rather than from a single
  shared stop table.
- Wired into the shared `matplotlib_family_rgb` resolver, which both
  `named_color_ramp` (Expr) and `resolve_ramp_to_rgb` (raw RGB for the legend
  bar) route through, so the surface and its colour bar cannot drift.

## Graphics — ComplexPlot default now identical to ColorFunction -> "Cyclic"

`ComplexPlot[f]` and `ComplexPlot[f, ColorFunction -> "Cyclic"]` rendered
differently: the default multiplied the phase colour by the modulus brightness
`|w|/(1+|w|)` (dark at zeros, bright toward poles), but an explicit string ramp
returned the flat full-brightness ramp. Both now go through one shared
`cp_ramp_color(name, re, im)` path — phase-keyed hue × modulus brightness — so
the two are byte-for-byte identical (verified with `magick compare`, AE = 0).
Every string `ColorFunction` on `ComplexPlot`/`ComplexPlot3D` now carries the
magnitude shading, matching the default (the `PlotLegends` bar stays a flat
full-brightness phase legend, as before).

## Graphics — ComplexPlot resolution, Options, and seam fix on more heads

- **Default `PlotPoints` 200 → 400 for 2D `ComplexPlot`.** The plane is drawn as
  a grid of coloured cells, so the cell pitch is the on-screen resolution; 200
  was visibly pixelated near zeros/poles where the phase turns fastest. The body
  is autocompiled per grid (`autocompile_new_z`, complex argument), so 400×400
  stays well under ~0.5s. `ComplexPlot3D` keeps 200 — it samples a polygon mesh,
  not a raster, so a 400² grid would just be 320k triangles for no comparable
  gain (`split_cplot_options` now takes the default as a parameter).
- **`Options[ComplexPlot]` / `Options[ComplexPlot3D]` registered** (were `{}`):
  `ColorFunction -> "Cyclic"` (the documented default phase colormap),
  `ColorFunctionScaling`, `PlotLegends`, `PlotPoints`, `PlotRange`,
  `RegionFunction` (+`Lighting` for 3D). `OptionValue[ComplexPlot, ColorFunction]`
  now resolves to `"Cyclic"`.
- **Rectangle-tiling seam fix extended to `ArrayPlot` and `ContourPlot`
  shading** (previously only ComplexPlot/DensityPlot). Same overlap-the-neighbour
  approach, oriented to each head's cell draw order (ArrayPlot emits rows
  top→bottom, so it overlaps `+x`/`-y`; the others `+x`/`+y`), clamped at the
  bounds.

## Graphics — ComplexPlot cyclic phase palette + seam fix

Two fixes to `ComplexPlot`/`ComplexPlot3D` phase colouring:

- **Cyclic default palette.** The default keyed the non-cyclic `thermal_rgb`
  ramp to the phase, so a bright colour seam appeared along `arg = ±π` where the
  ramp's ends (blue vs yellow) met, and opposite phases had very different
  brightness. The new default is **`"Cyclic"`** — a soft/pastel cyclic phase
  colormap (cyan→green→yellow→red→magenta→blue→cyan), a 32-stop resampling of a
  reference bar, with cyclic endpoints so the ±π wrap is seamless. Implemented as
  the shared `cyclic_phase_rgb` in `plot_common.c` and exposed as the `"Cyclic"`
  named `ColorFunction` ramp (routed through the shared `matplotlib_family_rgb`
  resolver, so the plot cells and the `PlotLegends` colour bar can't drift — the
  bar previously fell back to Viridis for the `Automatic` default).
- **Rectangle-tiling seam.** `ComplexPlot` and `DensityPlot` tile the plane with
  one `Rectangle` per grid cell; adjacent fills rounded to pixels and left
  sub-pixel gaps, showing the white background as thin horizontal/vertical lines
  (more visible at higher `PlotPoints`). Each cell's far corner now overlaps one
  full cell into its `+x`/`+y` neighbours (which are drawn later and overdraw the
  overlap, so each cell still shows its own colour), clamped at the plot edges.

## Graphics — ContourPlot smoother default (PlotPoints 25 -> 75)

`ContourPlot` draws each level curve as plain marching-squares polylines with no
adaptive refinement, so the grid pitch *is* the facet size. At the old default
`PlotPoints -> 25` a circular level curve (e.g. `ContourPlot[Sin[x] + Cos[y],
{x,-3,3}, {y,-3,3}]`) was visibly polygonal. Raised the default to **75** (facet
~ range/75), which reads as smooth. The body is autocompiled per grid, so even
75×75 ≈ 5.6k evaluations stays well under ~0.1s; a non-compilable body falls to
the interpreter, but that is the exception for a numeric contour plot. Explicit
`PlotPoints -> n` is unchanged.

## Graphics — Plot3D: remove the red hover dot

The interactive/embedded 3D view drew a red sphere at the surface point under
the cursor. Removed the `DrawSphere` marker from both render paths in
`render3d.c` (interactive `graphics3d_show` and offscreen
`graphics3d_render_in_region`). The `(x, y, z)` coordinate readout that also
follows the cursor is kept — only the dot is gone.

## Graphics — Plot3D default lighting (bright tops)

The default 3D key light was `1.0*cam_up + 0.5*fwd` in camera space, which
tilted the light *down into the scene* — so flat surface tops (normal straight
up) came out darker than the tilted flanks, reading as "lit from underneath".
It also collapsed to darkness when the camera looked straight down (`cam_up`
becomes horizontal at high elevation).

New shared helper `scene_key_light(right, fwd)` in `render3d.c` returns a light
**dominated by world-up** (render +y, which `to_v3` maps from the plotted height
z), with a small camera-relative `right`/`-fwd` tilt for form. Upward-facing
surfaces — the tops the viewer looks down on — are now the brightest at every
camera angle. Both render paths (interactive `graphics3d_show` and offscreen
`graphics3d_render_in_region`/Export) call the one helper, so their lighting
cannot drift.

## Graphics — Plot3D BoxRatios + full Options registration

**`Options[Plot3D]` now returns the complete defaulted option set** (previously
`{}`). Registered in `options_builtin.c`'s `options_register_defaults()`:
`Axes`, `Background`, `BoxRatios`, `ColorFunction`, `ColorFunctionScaling`,
`ExclusionStyle`, `ImageSize`, `Lighting`, `MaxRecursion`, `Mesh`, `PlotLabel`,
`PlotPoints`, `PlotRange`, `PlotStyle`, `RegionFunction` — exactly the options
Plot3D's C code honours, with the actual default values. `OptionValue[Plot3D,
name]` resolves against them.

**New `BoxRatios` option** — the z-shape of a Plot3D was flattened to true
scale, hiding surfaces with a small z-range. Now:

- New interned symbol `SYM_BoxRatios`.
- `BoxRatios -> {rx, ry, rz}` sets the display box's side-length ratios
  independent of the data ranges (Mathematica semantics). Plot3D defaults to
  **`{1, 1, 0.4}`** (Mathematica's Plot3D default); a raw `Graphics3D[...]` with
  no `BoxRatios` still renders at true scale.
- Implemented as a single display transform in `render3d.c`: a file-static
  `View3DXform` (per-axis centre + scale) that the one `to_v3()` choke point
  applies, so surface vertices, the bounding box, axis ticks and the camera
  target all share one mapping. `view3d_configure()` derives the transform and
  the transformed centre/diagonal for camera framing. Tick *labels* still read
  true data values (formatted from the untransformed bbox; only their screen
  positions pass through the transform). `plot3d.c`'s `split_options3()` injects
  the default when the user gives none; `gfx3d_options_parse()` reads it.

**`PlotStyle` fix** — an explicit `PlotStyle -> color` on a single surface now
renders it in that solid colour, instead of being silently overridden by the
automatic `"Viridis"` gradient (build_surface_primitives no longer applies the
default gradient when `single_color` is set). An explicit `ColorFunction` still
wins; multi-surface palette behaviour is unchanged.

## Reduce — Phase 6d: n-variable Cylindrical Algebraic Decomposition over the Reals

`Reduce[expr, {x1, ..., xn}, Reals]` now solves nonlinear real inequality
statements in **three or more** effective variables (previously declined). The
two-variable CAD from Phase 6a–6c is generalized to a single recursive engine.

- **Recursive engine** (`reduce_cad_nvar` in `src/solve/reduce_cad.c`): an
  iterated McCallum projection builds the projection stack (discriminant, leading
  coefficient, pairwise resultant, all factored), eliminating the variables from
  last to first; the base sign diagram is then lifted by a recursive descent that
  substitutes each cell's rational sample, isolates the next variable's real
  roots, and recurses, with partial-CAD pruning at every level and the innermost
  dimension merged into a symbolic region. Truth is decided at one sample per
  full-dimensional cell by the exact real-algebraic sign oracle.
- **Output**: strict inequalities read as a clean nested conjunction, e.g.
  `Reduce[x^2+y^2+z^2 < 1, {x,y,z}, Reals]` ->
  `-1 < x < 1 && -Sqrt[1-x^2] < y < Sqrt[1-x^2] && -Sqrt[1-x^2-y^2] < z < Sqrt[1-x^2-y^2]`;
  `Reduce[x y z > 0, {x,y,z}, Reals]` -> the four positive octants;
  `Reduce[x^2 < 1 && y^2 < 1 && z^2 < 1, {x,y,z}, Reals]` -> the open box;
  `Reduce[x^2+y^2+z^2 >= 0, ...] -> True`, `... < 0 -> False`. A **closed** region
  currently emits a correct but verbose union of cells (the boundary spheres/arcs/
  poles listed separately); the n-D boundary merge that would close an outer range
  (`-1 <= x <= 1 && ...`) is a later cosmetic pass — the answer is complete and
  sound either way.
- **Soundness invariant** (unchanged): an undecidable sign/ordering, an irrational
  non-innermost breakpoint (v1 rational-fibre regime — real-algebraic-coefficient
  fibre isolation is deferred, so e.g. `x^2+y^2+z^2 <= 2` with base `±Sqrt[2]`
  declines), an un-emittable fibre, or an interval nullification (McCallum
  well-orientedness augmentation deferred) all leave `Reduce` unevaluated rather
  than emit a wrong formula. The two-variable path and its boundary-merged output
  are unchanged (byte-identical).
- **Tests**: `tests/test_reduce.c` gains `test_cad_nvar` (clean-form,
  True/False, and decline pins); `tests/reduce_corpus.m` gains `cad3-*` /
  `cad4-*` rows verified by the form-agnostic sample-point oracle.
  `make check-c99` clean; valgrind leak-clean (only macOS ObjC-runtime baseline
  noise).

### Phase 6d Stage B: n-D boundary merge (closed regions)

The recursive engine now builds a cell **tree** and runs an n-D boundary merge —
the recursive generalization of the two-variable merge — so a **closed** region
closes its outer ranges instead of listing the boundary cells:
`Reduce[x^2+y^2+z^2 <= 1, {x,y,z}, Reals]` ->
`-1 <= x <= 1 && -Sqrt[1-x^2] <= y <= Sqrt[1-x^2] && -Sqrt[1-x^2-y^2] <= z <= Sqrt[1-x^2-y^2]`
(matching the two-variable disk); the sphere surface, closed half-ball, and the
4-variable closed ball merge likewise. A run of interval cells sharing one
symbolic template absorbs the section between (and at the ends) whose fibre equals
the template's limit there; **cell equality is decided by sampling** the emitted
sub-formulas over a grid drawn from the cell structure, so any undecidable
comparison leaves the already-correct unmerged (verbose) form — soundness over
completeness, verified by the corpus oracle. Strict regions stay open. Version
bumped to 0.088.
