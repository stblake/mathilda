Feature additions and fixes recorded during this week.

## NMinimize: Lennard-Jones cluster integration test (2026-08-14)

Added `tests/test_nminimize.c::test_lennard_jones_cluster` — an 18-D
global-optimization regression that drives the full indexed-variable +
`DifferentialEvolution` path in one call: `Subsets[Range[6], {2}]` enumerates the
15 atom pairs, the coordinates are indexed vars built with
`Table[{x[i], y[i], z[i]}, ...]` then `Flatten`'d to 18 scalars, a
`ljPair[{i_, j_}] := ...` helper supplies the softened pair potential
`1/r2^6 - 2/r2^3` (`r2` the squared distance with a `1e-8` floor), the box
constraints are generated by `Table[-3 <= v <= 3, {v, vars}]` iterating over the
*symbol list* `vars`, and DE's `"ScalingFactor" -> 0.7` sets the differential
weight `F`. The softened potential's global minimum is the octahedron at
`~ -12.712`; under the fixed default seed the search lands at `-12.3029` (a good
near-global basin). The assertion is deliberately loose — an 18-D DE trajectory
drifts across platforms in floating point (cf. `test_de_boundary_no_stagnation`),
so it checks that a compact low-energy cluster forms (`energy < -10`, far below
the `~0` of any scattered/sentinel configuration), that all 18 coordinates are
reported, and that the returned point is feasible inside the `+-3` box. No
behavior change; test-only. Full `nminimize_tests` suite passes.

## FindMinimum: compiled objective + exact compiled gradient (2026-08-14)

Follow-up to the NMinimize compiled-polish change: `FindMinimum` / `FindMaximum`
use a separate driver (`findmin_driver`) that did not compile anything, so all of
its objective and gradient evaluations ran through the interpreter. At
`MachinePrecision` it now lowers the objective **and each symbolic gradient
component** to bytecode over the variables (`compile_expr_ex`, after
`fm_bind_snapshot` so they compile as arguments) and evaluates them on the
register machine, via the same `g_fm_obj_*` objective registry plus a companion
`g_fm_grad_*` gradient registry that `fm_eval_gradient` consults (keyed by the
`g_exprs` array pointer + arity, so constraint gradients stay on the
interpreter). The gradient is the *same* `∂f/∂x_i`, only lowered — **not** finite
differences — so FindMinimum's precision is unchanged; measurement confirmed
byte-identical optima.

A quick value-only experiment showed compiling just the objective did nothing:
the QuasiNewton/CG/Newton cost is dominated by the per-iteration gradient, which
is why the gradient had to be compiled too. Measured (repeated calls, same
optima):

| Case | before | after |
|---|---:|---:|
| 1-D `Cos[x]+0.1 x^2` (Brent) | 0.0207 ms | 0.0073 ms (2.8×) |
| 1-D `Sin[x]Exp[-0.1x]+0.05x^2` | 0.0315 ms | 0.0101 ms (3.1×) |
| 2-D Rosenbrock | 0.266 ms | 0.066 ms (4.0×) |
| 6-D Rosenbrock | 1.756 ms | 0.925 ms (1.9×) |

The one loss is a trivial 2-D pure quadratic that converges in ~2 iterations,
where the fixed compile cost (~8 µs) is not amortised — already a sub-30 µs call.
A user-supplied `Gradient` is compiled the same way. Compilation is skipped when
an `EvaluationMonitor` is set (it fires from the interpreter, which the compiled
path bypasses) and on the MPFR (`WorkingPrecision > MachinePrecision`) path. New
allocations (the compiled programs) are freed on every exit; valgrind shows no
new leaks and the full `findmin_tests` suite passes, including Newton, CG,
constrained/penalty, user-gradient, and the evaluation monitor.

## NMinimize: compiled local polish (2026-08-14)

The machine-precision auto-compiled objective (`NmDriver.f_prog`) now drives the
**local polish** as well as the global-search scoring. Previously the polish
(`nm_local_polish` → `fm_run_bfgs`/`fm_run_penalty`) evaluated the objective
through the symbolic interpreter — deep-copying the tree, installing one
`OwnValue` per variable, evaluating, and numericalizing on **every** trial point.
`"RandomSearch"` runs one local solve per `SearchPoints`, so a 20-variable
`Sum[Abs[x[i]], {i, 1, 20}]` with `"SearchPoints" -> 1000` spent all its time
there: **24.8 s**. All other methods (DE, NelderMead, SA) polish too, so they were
hit in proportion.

Fix: `fm_eval_scalar` gains a compiled fast path — when it is handed the exact
objective expression registered for the current solve (pointer identity +
matching arity), it evaluates the compiled program (`compiled_eval_real`) instead
of the interpreter, falling back on a NULL/non-finite result. Constraint and
gradient sub-expressions are distinct `Expr*` and correctly stay on the
interpreter. The polish's gradient is taken by finite differences **off the
compiled objective** (the driver passes `g_exprs = NULL` when a program is
present), so `2n` compiled evaluations replace `n` interpreter evaluations that
each re-bind `n` `OwnValue`s. Pure speedup, interpreter fallback intact, answers
byte-identical.

Measured (20-D `Sum[Abs[x[i]]]`, box `[-10,10]`, same optimum `1.76e-5`):

| Method | before | after |
|---|---:|---:|
| `"RandomSearch"`, `"SearchPoints" -> 1000` | 24.8 s | 0.54 s |
| `"DifferentialEvolution"` | 0.98 s | 0.023 s |
| `"NelderMead"` | 0.59 s | 0.13 s |

The compiled program is now the single evaluation substrate across the whole
machine-precision optimizer. `FindMinimum` uses a separate driver that does not
yet compile its objective, so it is unchanged (the fast path is inert when no
program is registered); wiring it there is a clean follow-up. General (non-box)
constraints in the local penalty solver likewise still evaluate on the
interpreter. Tests: full `nminimize_tests` / `findmin_tests` suites pass;
`RandomSearch` returns the identical seeded optimum.

## NMinimize: disjunctive (`Or`) constraints (2026-08-14)

`NMinimize` / `NMaximize` now accept **disjunctive constraints** `c1 || c2 || ...`
(at the top level or nested inside an `And`), where a point is feasible if it
satisfies **at least one** branch. Previously any `Or` in the constraints emitted
`NMinimize::nimpl: disjunctive (Or) constraints are not yet supported` and left
the call unevaluated.

```
NMinimize[{(x^2+y-11)^2+(x+y^2-7)^2,
           (x-3)^2+(y-2)^2<=0.1 || (x+2.8)^2+(y+3.1)^2<=0.1},
          {x, y}, Method -> {"RandomSearch", "SearchPoints" -> 500}]
  ⇒ {~0, {x -> 3., y -> 2.}}        (* Himmelblau min, inside the first disk *)

NMinimize[{x^2, x <= -2 || x >= 2}, x]
  ⇒ {4., {x -> -2.}}                (* branch boundary, not the infeasible x = 0 *)
```

**How it works.** Each disjunction is scored by its **minimum-branch penalty** —
the least of the branches' squared-violation penalties, which is `0` exactly when
some branch is satisfied — added into the constraint-violation total that Deb's
feasibility rules already rank trial points by (`nm_eval_pen` → `fm_bool_penalty`,
a recursive `And`=Σ / `Or`=min / comparison=squared-violation evaluator). The
derivative-free global engines (DifferentialEvolution / SimulatedAnnealing /
NelderMead / RandomSearch) consume the non-smooth `min` directly.

The subtle part is the **local polish**. RandomSearch is pure multi-start local
polish with no global move, so if its polish ignores the disjunction it drives
every feasible start into the infeasible gap between branches and the whole run
reports `{Infinity, ...}`. The polish is therefore made disjunction-aware
(`nm_polish_gens`): at the start point it selects each disjunction's
currently-active (minimum-penalty) branch and folds that branch's comparisons
into the smooth quadratic-penalty BFGS solve, so the polish descends *within* the
feasible region the point already occupies. Constraint gradients for the polish
are taken by finite differences rather than symbolic `D[...]`, because the
optimisation variables carry transient value-bindings during the search (a
symbolic derivative taken there differentiates a constant and returns 0). The
post-polish Deb gate keeps the reported point feasible in all cases.

`FindMinimum`, whose gradient penalty method needs a smooth penalty, still rejects
`Or` with `FindMinimum::nimpl`.

Tests: `tests/test_nminimize.c::test_disjunctive_constraints` (Himmelblau two-disk,
the non-convex `x^2` over `x<=-2 || x>=2` under both the default engine and
RandomSearch, a box+disjunction combination, a boundary-optimum nearest-point
problem, and an `NMaximize` disjunction).

## NMinimize `"SimulatedAnnealing"`: adaptive temperature + coverage floor (2026-08-14)

`NMinimize[..., Method -> "SimulatedAnnealing"]` was returning a distinctly
shallower minimum than Mathematica on rugged, deceptive landscapes — on the 2-D
Eggholder `-(y+47) Sin[√|y+x/2+47|] - x Sin[√|x-(y+47)|]` over `[-512, 512]²` it
reported `-716.67`, against Mathematica's `-935.34` and the true global
`-959.64`.

Root cause: the Metropolis acceptance exponent was `-df/T` with a fixed
`T ∈ [1e-4, 1]`, while the objective ranges over hundreds. `Exp[-df/T]` was then
≈ 0 for every uphill move *even at the start temperature*, so the "anneal" was
really greedy descent from the start point — nothing but a fresh random restart
ever crossed a ridge into a deeper basin. That is why only cranking
`"SearchPoints"` up ever helped: each chain was a greedy local search, so you
needed many of them.

Two changes:

- **Adaptive temperature.** Each chain now measures the objective scale `s` from
  a short probe of trial steps at its start point (mean `|Δφ|`) and uses
  `-df/(T·s)` as the built-in exponent, so a move that worsens `φ` by one
  characteristic step is accepted with probability `e^{-1/T}` — a real anneal.
  The probe draws from its own PRNG, leaving the annealing walk's stream
  untouched, so a seeded `"SearchPoints" -> 1` chain follows exactly the
  trajectory it did before. A user `"BoltzmannExponent"` still overrides.
- **Coverage floor.** The automatic chain count went from `Min[2·d, 50]` to
  `Min[Max[2·d, 12], 50]`. At `d = 2` that is 12 rather than 4 independent
  starts; a rugged low-dimensional landscape has far more basins than 4 starts
  can cover. SA is opt-in (the automatic method is DifferentialEvolution), so
  only a caller who asked for SA pays the extra hundredths of a second.

Result at the default settings (2-D, `Timing` on an M-series):

| function | before | after | global |
|---|---:|---:|---:|
| Eggholder | `-716.67` | `-959.64` | `-959.64` |
| Schwefel  | `118.44`  | `2.5e-5`  | `0` |
| Rastrigin | `0`       | `0`       | `0` |
| Griewank  | `0`       | `0`       | `0` |
| Ackley / Booth / Rosenbrock / quadratic | global | global | global |

The Eggholder case now returns the global `-959.64` in ~0.021 s, below
Mathematica's default `-935.34` (~0.031 s). `tests/test_nminimize.c` and
`tests/test_findmin.c` (including `test_griewank_simulatedannealing`,
`test_sa_suboptions`, and the leak smoke tests) pass unchanged.

## NMinimize `"SimulatedAnnealing"`: `"LevelIterations"` sub-option (2026-08-14)

`Method -> {"SimulatedAnnealing", "LevelIterations" -> L, ...}` is now honored
rather than silently dropped. `"LevelIterations"` is the number of trial moves
spent at each temperature level, so a chain's iteration budget is
`MaxIterations · L`. This is a rename, not a new mechanism: the per-chain budget
was already `MaxIterations · 50`, and that hard-coded `50` was exactly the
implicit LevelIterations default — it is now the default value of the option, so
an unset `"LevelIterations"` reproduces the previous schedule bit-for-bit.

An explicit value is honored **verbatim**, past the automatic aggregate iteration
cap — consistent with `"SearchPoints"` — since the caller has asked for that
budget. A positive integer sets it; `Automatic`/`None` restore the default; an
invalid value warns `NMinimize::sopt` and falls back to Automatic. On a seeded
single chain with `"PostProcess" -> False`, the raw best deepens monotonically
with `L` (Eggholder: `-699` at `L = 2`, `-717` at `L = 200`), and wall time
scales with it (Eggholder default: `L = 50` → 0.019 s, `L = 100` → 0.030 s,
`L = 500` → 0.119 s). Covered by `test_sa_suboptions` in `tests/test_nminimize.c`.

## NMinimize: NelderMead per-restart polish + RandomSearch honors SearchPoints (2026-08-15)

Completes the "polish each independent start into its basin minimum and keep the
deepest" principle across all four multi-start engines (RandomSearch already did;
SimulatedAnnealing and DifferentialEvolution were done above).

- **NelderMead — per-restart basin polish.** `nm_neldermead` ranked its restarts
  by their raw simplex-converged vertices and polished only the single winner
  afterward — the same non-monotonicity fixed for SA and DE. Each restart's best
  vertex is now polished into its basin minimum *before* the restarts are ranked
  (gated by `"PostProcess" -> False`; a BFGS overshoot falls back to the raw
  vertex). The automatic default rises from a flat 4 restarts to `Min[2·d, 20]`.
  On Griewank-10 the default reaches `0.0148` (Mathematica `~0.175`) and 40
  restarts reach the global `0`; the result now improves with `"SearchPoints"`
  instead of being decided by the raw vertices.
- **NelderMead / RandomSearch — `"SearchPoints"` honored verbatim.** Both silently
  capped the option (NelderMead at 20, RandomSearch at 40), so a larger value was
  a no-op — RandomSearch returned the byte-identical 40-start result for
  `"SearchPoints" -> 40`, `300`, or `1000`, contradicting the documented "honored
  verbatim". An explicit value is now always run; the *automatic* defaults keep
  their runtime bound (RandomSearch `Clip[8·d, {4, 40}]` starts, unchanged, so no
  default-path slowdown).
- **RandomSearch is structurally limited on wide multimodal boxes** and this is
  documented, not a bug: pure multi-start local search has no global move, so on
  Griewank over `[-600, 600]` (central bowl `~10⁻¹¹` of the 10-D volume) no
  attainable start count reaches the optimum — it reports `~27` regardless.
  DifferentialEvolution / SimulatedAnnealing are the engines for that shape. On a
  reachable box (narrow Griewank) RandomSearch is monotonic: 200 starts (`0.0074`)
  beat 10 (`0.032`), which the silent cap had made impossible.
- **Regression tests** `test_griewank_neldermead` (default `< 0.1`, 40 restarts
  `< 0.01`) and `test_randomsearch_searchpoints_verbatim` (200 starts beat 10 on a
  reachable box) added. Bukin-6 is unaffected (`0.0113679`, within `10⁻⁶` of the
  Mathematica-matched value).

## NMinimize: DifferentialEvolution multi-start basin polish (2026-08-15)

- **The default `"DifferentialEvolution"` now reaches a deeper minimum on
  multimodal problems and no longer degrades as `"SearchPoints"` grows** — the
  same non-monotonicity the SimulatedAnnealing per-chain polish removed, now
  fixed for DE. On Griewank-10 over `[-600, 600]^10`, `Method ->
  "DifferentialEvolution"` drops **0.0442535 → 0.0** (the global minimum),
  beating Mathematica's `0.174985`; `"SearchPoints" -> 100` drops **0.196657 →
  0.0172263** (was *worse* than the default 40-member population).
- **Change in `nm_de`:** on a continuous problem the post-search local polish is
  now a **multi-start over the final population** rather than a single refinement
  of the global best. The best `Min[2·d, 50]` *distinct* members (deduplicated by
  basin — agreement to `10⁻³` of the search span on every coordinate) are each
  polished into their basin minimum and the deepest is kept. Polishing only the
  single best strands DE in whichever basin that member occupied; a larger or
  less-converged population leaves the best member in a shallower basin than
  others hold, so ranking basins by their *minima* — not by the raw fitness of
  the member that found them — is what makes the optimum improve with
  `"SearchPoints"`.
- **Scope and cost.** Gated by `"PostProcess" -> False` (then the raw global best
  is carried through unchanged) and confined to continuous problems: a
  mixed-integer run keeps its single driver polish, so its integer-descent cost
  is unaffected. The polish uses no PRNG draws, so DE's evolution is byte-for-byte
  the same; only the returned continuous optimum can move to a deeper basin.
- **`Method -> Automatic` is unchanged in value** (`~0.0369` on Griewank-10): its
  `150·d`-generation budget converges the population into a single basin before
  the polish runs, so there are no distinct basins to exploit — still well below
  Mathematica.
- **Regression test** `test_griewank_differentialevolution` added: the default and
  `"SearchPoints" -> 100` both reach `< 0.1`, locking in the improvement and the
  restored monotonicity.

## NMinimize: SimulatedAnnealing multi-chain default + per-chain polish (2026-08-15)

- **The default `"SimulatedAnnealing"` now returns a much deeper minimum on
  multimodal problems, beating Mathematica on Griewank-10.** On
  `Sum[x[i]²/4000] - Product[Cos[x[i]/√i]] + 1` over `[-600, 600]^10`
  (`"PerturbationScale" -> 2.0`) the reported optimum drops from **0.307674** to
  **0.0147724** — a 10× improvement over Mathematica's `0.174985` on the same
  problem, and in ~0.29 s versus Mathematica's ~1.9 s.
- **Two coupled changes in `nm_sa`:**
  - **Default `"SearchPoints"` is now `Automatic = Min[2 n, 50]`** (was a single
    chain), matching Mathematica's SimulatedAnnealing default. A single annealing
    walk lands in a basin close to by luck; `Min[2 n, 50]` independent chains
    from random starts explore the landscape properly.
  - **Each chain's best raw point is polished into its basin minimum before the
    chains are ranked** (as `"RandomSearch"` already does per restart), then the
    global best of those local minima is kept. Ranking chains by their local
    minima rather than by their random-walk lows is what makes the reported
    optimum *improve* monotonically with `"SearchPoints"` — previously the lowest
    raw point often sat in a shallower basin than a slightly higher point above a
    deeper one, so more search points could return a *worse* answer (SP 5 →
    0.148 but SP 50 → 0.376). Now: SP 1 → 0.308, SP 5 → 0.148, SP 20 → 0.015,
    SP 50 → ~10⁻¹⁶ (the global 0).
- **Honors `"PostProcess" -> False`/`None`**: the per-chain polish is skipped,
  and the per-chain-best tracking then reduces to the global raw best over the
  same PRNG sequence — bit-for-bit the previous raw-best result.
- **`"SearchPoints" -> 1` is unchanged**: one chain anneals over the identical
  PRNG sequence and its best is polished, which is exactly what the driver's
  post-process produced before, so a seeded single-chain run is unaffected.
- **Regression test** `test_griewank_simulatedannealing` updated to lock in the
  new default (`0 <= First[r] < 0.1`, was `0.1 < First[r] < 1.0`).

## NMinimize: SimulatedAnnealing sub-options now honored (2026-08-14)

- **Bug fixed: the `"SimulatedAnnealing"` engine ignored its whole config.**
  `nm_sa` did `(void)nc`, so `"SearchPoints"` had no effect, and the parser
  silently dropped `"PerturbationScale"` and `"BoltzmannExponent"` entirely.
  All three now take effect:
  - **`"SearchPoints" -> K`** runs `K` independent annealing chains from random
    starts and keeps the global best (default 1). A bounded aggregate iteration
    budget is shared across the chains (`NM_SA_TOTAL_CAP`), so a large `K`
    (e.g. 50) stays fast. On a rugged multimodal surface more restarts reach a
    markedly better raw point (e.g. `x²+y²+10 Sin[3x]²+10 Sin[3y]²`: single
    chain → 1.08, 30 chains → 1.2·10⁻⁴).
  - **`"PerturbationScale" -> s`** multiplies the trial-step size (default 1.0):
    a small scale keeps the walk local, a large one explores more widely. A
    non-positive/non-real value warns (`NMinimize::sopt`) and falls back to 1.0.
  - **`"BoltzmannExponent" -> f`** replaces the Metropolis acceptance exponent
    for an uphill move — the point is accepted with probability
    `Exp[f[i, df, f0]]` (1-based iteration `i`, objective increase `df`, current
    value `f0`). `Automatic`/`None` keep the built-in geometric-cooling exponent
    `-df/T`; an invalid value warns (`NMinimize::bexp`) and falls back to
    Automatic. Evaluated with numeric diagnostics muted, mirroring
    `"PenaltyFunction"`.
- **The default single-chain, default-option path is bit-for-bit unchanged** —
  scale 1.0 is an exact multiply and the PRNG is drawn in the same order — so a
  seeded run without these options gives the identical result to before.
- **Regression tests (Griewank-10).** On the strongly-multimodal Griewank
  function over `[-600, 600]^10`, SimulatedAnnealing settles into a nonzero
  local minimum rather than the global 0, exactly as Mathematica does; the
  default single-chain schedule lands at ~0.234 — the same value Mathematica
  reports. Added `test_sa_suboptions` (each option honored + invalid-value
  fallback) and `test_griewank_simulatedannealing` (the Mathematica-reported
  all-options invocation is parsed, applied, and returns a finite feasible
  minimum) to `tests/test_nminimize.c`.

## NMinimize/NMaximize: no longer HoldAll — option values now resolve (2026-08-14)

- **Attribute correction.** `NMinimize` and `NMaximize` are now `Protected` only,
  **not** `HoldAll` — matching Mathematica, whose `Attributes[NMinimize]` is
  `{Protected}`. (`FindMinimum`/`FindMaximum` stay `{HoldAll, Protected}`: their
  `{x, x0}` specs pair a variable with an initial value that must not evaluate.)
- **Bug fixed: held option values were silently dropped.** Because the arguments
  were held, a `Method` sub-option whose value was a symbol or expression rather
  than a literal — e.g. `"RandomSeed" -> s` with `s` a `Do`/`Table` iterator,
  `"SearchPoints" -> 2 d`, `MaxIterations -> it` bound in a `With`/`Module`, or
  even `"RandomSeed" -> 2 + 40` — reached the literal-only option readers
  unevaluated and was quietly ignored, so the run fell back to the default seed /
  population. A sweep like `Do[NMinimize[…, "RandomSeed" -> s], {s, {…}}]`
  produced the *same* result for every `s`. With the arguments no longer held,
  option values evaluate normally and resolve, so each seed now yields its own
  result (identical to passing the seed as a literal). This resolves the whole
  class, not just `RandomSeed`.
- **Consequence (also matching Mathematica).** Because the objective and variable
  spec now evaluate before the call, an optimization variable that already carries
  a value resolves first, the variable specification is then malformed, and the
  call returns unevaluated with `NMinimize::ivar` — exactly as in Mathematica.
  Optimization variables must be unbound symbols. Variable *locality* during the
  search is unchanged: the Block-style snapshot/restore of each variable's
  OwnValue still guarantees an unbound variable is never left modified.
- The variable-spec parser, indexed-variable synth-symbol rewrite, `{f, cons}`
  splitting, and constraint expansion are unchanged — a pre-evaluated
  `Table[x[i], …]`/`Array[x, n]` arrives already expanded to the list the parser
  already accepted. Tests renamed/strengthened (`test_variable_locality`,
  `test_indexed_variable_locality`) to assert the no-leak guarantee and the new
  unevaluated-on-assigned-variable behavior; all 39 NMinimize/NMaximize tests pass.

## NMinimize: dimension-scaled default (Automatic) DifferentialEvolution budget (2026-08-14)

- **Stronger default global search on hard multimodal problems.** `Method ->
  Automatic` (i.e. plain `NMinimize` / `NMaximize` with no `Method`) now runs DE
  with a *dimension-scaled* budget — population `Clip[10·d, {15, 200}]` and
  `150·d` generations — instead of the flat `Clip[10·d, {15, 40}]` / `100` that
  the DE engine has always used. The flat budget was drastically under-powered for
  `d ≥ 5`: on the 10-D Michalewicz function
  `NMinimize[{-Sum[Sin[x[i]] (Sin[i x[i]^2/Pi])^20, {i,1,10}],
  Table[0<=x[i]<=Pi,{i,1,10}]}, Table[x[i],{i,1,10}]]` the default returned only
  `-6.93335`; it now returns `-9.66015` (the true global minimum, better than
  Mathematica 14's default `-9.04592`) in ~0.63 s — matching Mathematica's speed
  and beating its quality, robustly across seeds (`-9.40 … -9.66`).
- **Free on easy problems.** The budget increase is gated by the DE convergence
  early-break: a run stops as soon as its feasible sub-population collapses to the
  accuracy/precision tolerance, so low-dimensional and convex problems finish in
  the same wall-clock as before (100 low-D solves: ~0.03 s, unchanged) with
  identical results. `d ≤ 4` is unaffected (`10·d ≤ 40`).
- **Explicit DifferentialEvolution is untouched.** The enhanced budget is keyed on
  `nc.method == NM_AUTO` (`src/findmin.c`, `nm_de`); naming
  `Method -> "DifferentialEvolution"` — or supplying `SearchPoints` /
  `MaxIterations` — keeps the flat budget, so a seeded run reproduces bit-for-bit
  (the reference `RandomSeed -> 42, CrossProbability -> 0.75` case still returns
  `-8.65041` at the identical point). Implemented via a new `FmOpts.max_iter_set`
  flag so an explicit `MaxIterations` under `Automatic` is still honored verbatim.

- **Multi-variable integer/real domain declarations.** `NMinimize` /
  `NMaximize` now accept a domain declaration that names several variables at
  once — `Element[x | y, Integers]` (an `Alternatives`) and
  `Element[{x, y}, Integers]` (a `List`) — in addition to the single-symbol
  `Element[x, Integers]`. Previously only a bare symbol was recognised, so the
  common `Element[x1 | x2, Integers]` spelling emitted
  `NMinimize::nimpl: Element / domain constraints are not yet supported` and the
  whole call returned unevaluated. `nm_filter_int` (`src/findmin.c`) now expands
  the `Alternatives`/`List` operand and marks each named optimization variable
  integer (or accepts `Reals`); a declaration on a symbol that is not one of the
  variables is left in place and rejected downstream, unchanged. The pressure-
  vessel MINLP from the report,
  `NMinimize[{0.6224 x1 x3 x4 + …, … && Element[x1|x2, Integers]}, {x1,x2,x3,x4}, …]`,
  now parses and — with the standard variable bounds — solves to `8796.86` at
  `x1 = x2 = 1` (integer), `x3 ≈ 51.81`, `x4 ≈ 84.59`.
- **Mixed-integer continuous-relaxation polish.** A mixed-integer problem whose
  feasible region lies outside the default `±10` DE sampling span was previously
  invisible to the region-confined integer coordinate descent and reported
  infeasible. `nm_local_polish` now adds a relaxation recovery step (new
  `nm_continuous_solve`): solve the continuous relaxation (integers relaxed,
  every coordinate free of the sampling region) to find the basin, round the
  integers, then refine the continuous coordinates with the integers pinned
  (a degenerate `[v,v]` box; `fm_line_search` projects each trial, so the value
  stays fixed). The result is adopted only when it is a Deb-improvement, so it
  can never worsen the region-descent answer. E.g.
  `NMinimize[{(x-15)^2 + (y-3)^2, Element[y, Integers]}, {x, y}]` now recovers
  the optimum at `(15, 3)` (value `0`) even though `x = 15` sits far outside the
  sampling box. Problems that are genuinely unbounded below, or whose feasible
  region the relaxation does not locate, still return `{Infinity, …}`; explicit
  variable bounds make them solvable.
- **Adaptive search-region expansion.** When the default `±10` DE sampling
  region contains no feasible point, the fully-unbounded coordinates are now
  grown by successive powers of ten (up to `±10^5`) and the search is retried,
  so a feasible region whose location is implied by nonlinear constraints
  rather than stated as variable bounds is found instead of reporting
  `{Infinity, …}`. Only fully-unbounded coordinates grow — a coordinate with a
  box bound or a starting-interval hint keeps its resolved region — and the
  first attempt is the base region with the base seed, so a problem already
  feasible there is solved identically to before; expansion triggers only to
  rescue infeasibility and stops at the smallest region that yields
  feasibility (`nm_minimize_driver`, guarded by `NM_MAX_REGION_EXPAND`). E.g.
  `NMinimize[{(x-50)^2 + (y-40)^2, x + y >= 80}, {x, y}]`, whose feasible set
  lies wholly outside `±10`, now returns the optimum `(50, 40)`; a genuinely
  infeasible problem (`x^2 + 1 <= 0`) still returns `{Infinity, …}`. The
  pressure-vessel MINLP from the report now returns a feasible point rather
  than `Infinity` — though, lacking the standard non-negativity bounds, that
  formulation is unbounded below (its true global minimum is a large-negative
  non-physical point), so the physical optimum still needs the benchmark's
  variable bounds.
- Tests: `test_integer_domain_alternatives`, `test_integer_domain_list`,
  `test_region_expansion_rescue`, `test_mixed_integer_outside_region` in
  `tests/test_nminimize.c`. Full `nminimize_tests` and `findmin_tests` suites
  pass.

## NMinimize DifferentialEvolution: bounce-back boundary handling (2026-08-14)

- Fixed **boundary stagnation** in the `"DifferentialEvolution"` engine
  (`nm_de`, `src/findmin.c`). A mutant that overshot a box bound was *clamped*
  to the bound; once several population members shared the exact boundary value
  for a coordinate, their pairwise mutation differentials for that coordinate
  collapsed to zero and it froze on the wall for the rest of the run.
- The reported failure was the 10-D Schwefel function (global optimum at
  `x_i = 420.97`, interior to `[-500, 500]`): the search returned `1758.88`
  with five coordinates pinned to `±500`, worse than Mathematica's `1221.25`.
- Replaced clamping with **bounce-back reinitialisation** (Price, Storn &
  Lampinen 2005): an out-of-range component is redrawn at random between the
  base vector and the violated bound — feasible, but almost never exactly on
  the boundary, so the population keeps its diversity. The same case now solves
  to `~963` (default seed) with no coordinate on the boundary, and no seed in a
  7-seed sweep parks a coordinate at `±500`. Only out-of-range mutants are
  affected, so interior-optimum problems (the existing test suite) are
  unchanged.

## NMinimize / NMaximize: numerical global optimization (2026-08-14)

- New builtins `NMinimize` / `NMaximize` (`HoldAll, Protected`) in
  `src/findmin.c`, layered on the existing `FindMinimum` machinery — same
  `Block`-style variable binding, `{f, cons}` constraint parsing (boxes +
  general `FmGenCon[]`), penalty/BFGS local solvers, MPFR path, and result
  builders — with a new stochastic **global** search on top.
- Four methods, `Method -> Automatic` picks `"DifferentialEvolution"`:
  `"DifferentialEvolution"` (DE/rand/1/bin, the default engine),
  `"NelderMead"` (restarted downhill simplex), `"RandomSearch"` (multistart +
  local polish), `"SimulatedAnnealing"`. A method may carry sub-options
  `{"Name", "SearchPoints" -> n, "ScalingFactor" -> F, "CrossProbability" ->
  cr, "RandomSeed" -> s}`. The PRNG is a deterministic SplitMix64 with a fixed
  default seed, so results are reproducible.
- Constraints use **Deb's feasibility rules** during the global search (no
  penalty-weight tuning) and the quadratic-penalty local solver during the
  final polish. Supports `==`, `<`, `<=`, `>`, `>=`, chained inequalities, and
  their `And` combinations; the first argument may be `{f, cons}` or
  `{f, c1, c2, ...}` (extra elements implicitly `And`-ed, matching
  Mathematica). Scalar integer domains via `Element[x, Integers]` are searched
  on the lattice and returned as exact integers. An empty feasible set returns
  `{Infinity, {x -> Indeterminate, ...}}`.
- `WorkingPrecision > MachinePrecision` refines continuous,
  general-constraint-free problems in MPFR (via `fm_run_bfgs_mpfr`); other
  cases warn and fall back to machine precision, matching `FindMinimum`.
  Options `Method / WorkingPrecision / MaxIterations / AccuracyGoal /
  PrecisionGoal / EvaluationMonitor / StepMonitor` are honoured and registered
  as `Options[NMinimize]` / `Options[NMaximize]`; internal local-solver
  diagnostics are muted during the global search so a successful solve is
  silent.
- Symbols interned (`SYM_NMinimize` / `SYM_NMaximize`), docstrings in
  `info.c`, docs in `docs/spec/builtins/calculus.md`, tests in
  `tests/test_nminimize.c` (29 cases: shape, unconstrained, all constraint
  kinds, integer/mixed-integer, infeasibility, every method, `NMaximize`
  duality, options, `WorkingPrecision`, `HoldAll` locality, memory smoke).
  Valgrind-clean (identical to the `Sin[1.0]` baseline); `make check-c99`
  passes; no `FindMinimum` regression.

### Indexed variables + held Table/Array specs (2026-08-14)

- `NMinimize` / `NMaximize` now accept **indexed variables** `x[i]` and held
  variable/constraint *generators*. Because both arguments are `HoldAll`, a
  spec such as `Table[x[i], {i, 1, n}]` or `Array[x, n]` previously reached the
  parser unevaluated and was rejected with `NMinimize::ivar`. The driver now
  evaluates the variable spec once (with the variable head `Block`-localized so
  it stays symbolic), and — when the constraint argument is a wrapper such as
  `Table[...]` rather than an already-relational tree — expands it the same way
  and treats the resulting list as an implicit `And` (dropping `True` entries;
  a `False` entry marks the system infeasible).
- Indexed variables are rewritten to fresh scalar symbols (`NMinimize$k`,
  removed after the solve) by a structural substitution over the *evaluated*
  objective/constraints, so the entire symbol-keyed solver — binding, gradient,
  box/general constraint collection, MPFR refinement — applies unchanged; the
  result `Rule`s are mapped back to the original `x[i]`. Plain-symbol problems
  and already-relational constraints keep their exact previous code path (no
  evaluation, no rewrite).
- This makes the standard `n`-dimensional benchmarks express directly, e.g. the
  10-D Rosenbrock valley
  `NMinimize[{Sum[100 (x[i+1]-x[i]^2)^2+(1-x[i])^2, {i,1,9}], Table[-5<=x[i]<=5, {i,1,10}]}, Table[x[i], {i,1,10}]]`
  → `{~0, {x[1]->1, ..., x[10]->1}}`.
- New helpers in `src/findmin.c`: `nm_subst` (structural substitution),
  `nm_fresh_symbol`, `nm_heads_localize`/`nm_heads_restore` (Block-localize the
  variable heads while expanding a held spec), `nm_is_var_atom`,
  `nm_is_constraint_tree`; `nm_one_var`/`nm_parse_vars` extended to accept
  indexed atoms. Six new cases in `tests/test_nminimize.c` (Table/Array/literal
  indexed vars, Table constraints, the reported 10-D Rosenbrock, indexed
  `HoldAll` locality). Valgrind leak totals identical to baseline; synthetic
  symbols leave no residue (`Names["NMinimize$*"]` is `{}`); `make check-c99`
  passes; no `FindMinimum`/`NMinimize` regression.

### NelderMead `InitialPoints` + flat-plateau convergence fix (2026-08-14)

- **`"InitialPoints"` sub-option.** `Method -> {"NelderMead", "InitialPoints" ->
  {{x1,...}, ...}}` now seeds the initial simplex (`NmConfig.init_points`, parsed
  in `nm_parse_method`, consumed by new `nm_simplex_from_points` for restart 0;
  later restarts stay random). Each seed point is evaluated + numericalized (so
  `Pi` etc. work); fewer than n+1 points are filled by axis perturbation, extra
  points ignored, and a malformed list (wrong dimension / non-numeric) falls back
  to a random start. It was previously parsed-and-ignored.
- **Flat-plateau convergence fix.** NelderMead's termination required only a
  small objective spread `|f_hi - f_lo|`, which is ≈0 across any flat region — so
  on a broad plateau the simplex "converged" on the first iteration and never
  moved. It now *also* requires the simplex to be geometrically small (max vertex
  coordinate spread ≤ `1e-6 ×` region extent) before stopping, so a plateau
  simplex keeps contracting toward its centroid.
- Together these solve the Easom needle-in-a-haystack:
  `NMinimize[{-Cos[x] Cos[y] Exp[-((x-Pi)^2+(y-Pi)^2)], -100<=x<=100 && -100<=y<=100}, {x,y}, Method -> {"NelderMead", "InitialPoints" -> {{-50,-50},{50,50},{10,10}}}]`
  now returns `{-1., {x -> Pi, y -> Pi}}` (was `≈0` at a random point) — the three
  collinear seeds have centroid ≈ `(Pi,Pi)`, and the plateau-aware simplex slides
  down the spike. New `test_initial_points` in `tests/test_nminimize.c`. All spec
  examples and both suites unchanged; valgrind identical to baseline; `make
  check-c99` passes.

### NMinimize resolves a problem/variable spec given via a bound symbol (2026-08-14)

- `NMinimize`/`NMaximize` are `HoldAll`, and the driver split `{f, cons}` and
  parsed the variable spec on the *held* first two arguments. So the common
  pattern `prob = {f, cons}; vars = Table[x[i], …]; NMinimize[prob, vars]`
  silently failed: the objective symbol `prob` (never a `List` head) was scored
  as a non-numeric objective and returned the infeasible sentinel
  (`{Infinity, {…->Indeterminate}}` / `1e+300` internally), and a variable-list
  symbol `vars` was parsed as one opaque variable keyed by the whole list
  (`{{x, y} -> …}`). Mathematica resolves both. A bare *scalar* objective symbol
  already worked (it is evaluated per point), which masked the list case.

  - **Objective/problem** — the variable spec is now parsed first (it does not
    depend on the objective), and a bare-symbol first argument is then evaluated
    *once with the variable heads localized* (reusing `nm_heads_localize` /
    `nm_heads_restore`), so `prob → {f, cons}` is exposed without capturing any
    global variable values. An inline list/expression is unchanged. The resolved
    tree is owned (`f_eval`) and freed on every exit path.
  - **Variable spec** — a bare symbol is resolved: if it evaluates to a
    `List`/`Element` that is used; if it is unbound (evaluates to itself) or
    resolves to a non-spec it stays a single optimization variable, so
    `NMinimize[f, x]` is unaffected while `vars = {x, y}; NMinimize[f, vars]`
    now expands to the two variables.

  the inline form (measured: the 20-D Rastrigin via `prob`/`vars` symbols runs
  in ~0.03–0.37 s like the inline call, versus ~6 s on the interpreter before
  this landed), and the full result is byte-identical to the inline form
  (`{111.435, {x[1] -> 0.994959, …}}` — which also matches Mathematica exactly
  for that DE configuration).
- Verified: new `test_symbol_indirection` in `tests/test_nminimize.c` (objective

## Inexact contagion no longer numericalizes a non-numeric head's arguments (2026-08-14)

- **Bug.** `0.333 x[1]` evaluated to `Times[0.333, x[1.0]]` — the real
  coefficient numericalized the *index* `1` inside `x[1]`. `Plus`/`Times`
  inexact contagion (`src/numeric.c`, `numeric_contagion_args`) numericalized
  every exact sibling with the full `N` recursion, which threads into the
  arguments of *any* head, including a non-numeric one like `x`.
- **Symptom.** `NMinimize` with an indexed objective carrying a real
  coefficient — e.g. the 10-D Ackley function
  `-20 Exp[-0.2 Sqrt[1/10 Sum[x[i]^2, {i,1,10}]]] - Exp[1/10 Sum[Cos[2 Pi x[i]],
  {i,1,10}]] + 20 + E` — returned the infeasible `1e+300` sentinel. The held
  objective is expanded once (heads localized) before its indexed variables are
  substituted; contagion rewrote `x[i]` to `x[i.]`, the substitution then failed
  to match, and an unbound `x[1.]` survived into the compiled body so every
  trial point scored non-numeric.
- **Fix.** `NumericSpec` gains a `contagion` flag, set only by
  `numeric_contagion_args`. When set, `numericalize_function` returns a
  non-numeric-headed subexpression (`x[1]`, `f[a]`, `Abs[x[3]]`, …) unchanged
  instead of threading `N` into its arguments. Numeric heads (`Plus`, `Times`,
  `Power`, `Sin`, …) still recurse, so a coefficient reached through them is
  numericalized as before: `1. + 2 x` → `1. + 2. x`, `1. + Sin[2]` → `1.9093`.
  Explicit `N[]` leaves the flag false and threads everywhere, so
  `N[x[1]] == x[1.]` — matching Mathematica, which distinguishes arithmetic
  contagion from an explicit `N`.
- **Result.** `0.333 x[1]` → `0.333 x[1]`; the Ackley `NMinimize` now converges
  to the true global minimum (~0 at the origin) rather than a sentinel.
- Verified: `test_inexact_contagion` (`tests/test_numeric.c`) gains the
  non-numeric-head cases; `test_indexed_real_coefficient`
  (`tests/test_nminimize.c`) runs 3-D Ackley to ~0. Valgrind unchanged
  (`13,440/420`, macOS baseline); `make check-c99` passes; `numeric_tests`,
  `nminimize_tests`, and `findmin_tests` green.

## FindRoot on systems: skip the structurally-zero Jacobian entries (2026-08-13)

- `fr_run_newton_system_real` (`src/numerical_roots/findroot.c`) derived, compiled
  and evaluated the full `n²` Jacobian `D[f_i, x_j]`. For a sparse system — a
  tridiagonal Broyden field has 3 non-zeros per row, not `n` — that is almost all
  wasted work. A `jz[i*n+j]` mask now flags the entries that come back a literal
  `0`; those are never compiled and their per-iteration evaluation is replaced by a
  direct `J = 0`, so the cost is O(nnz) rather than O(n²). `benchmarks/58` Broyden
  tridiagonal **N=40: 12.8× → 3.6×** (27 ms → 7 ms), N=10 also faster; roots still
  agree (0 CHECK-FAIL), `findroot_tests`/`nsolve_tests`/`nsolve_stress_tests` pass.
  (A dense small system like Burden–Faires 3×3 is unaffected — it has no zero
  entries; a Broyden rank-1 quasi-Newton update would be the next lever there.)

## Eigenproblems: route the standard machine kernels to LAPACK (2026-08-13)

- The dense machine `Eigenvalues`/`Eigenvectors` kernels (`eigen_direct.c`) were
  hand-rolled Householder/QR. The real symmetric path now calls LAPACK `dsyev`
  (jobz='V' for vectors, jobz='N' — a new `mat_lapack_dsyev_values` — for
  values-only, which is ~half the work), and the real general path calls `dgeev`
  (values-only via a new `mat_lapack_dgeev_values`). Raw LAPACK output is fed
  through the **same** sort/build helpers as the fallback, so the output
  convention is byte-for-byte: eigenvalues descending by `|λ|` (a `±v` tie breaks
  positive-first — `dsyev`'s ascending order is reversed to preserve that),
  eigenvectors unit-2-norm, `dgeev`'s conjugate pairs unpacked as in the LAPACK
  bridge. LAPACK failure falls back to the hand-rolled kernel.
- `benchmarks/54-eigenproblems`: Eigenvalues symmetric 300×300 **5.7× → 3.3×**,
  Eigenvectors symmetric 250×250 **7× → 4.0×**, Eigenvalues general 300×300
  **2.5× → 1.29×** (near parity); 0 CHECK-FAIL, `eigen_tests` /
  `mateigen_direct_tests` pass. The residual is result marshalling (building the
  eigenvalue/eigenvector Lists), shared with the packed-result follow-up. The
  complex Hermitian/general machine kernels (no benchmark-54 coverage) still use
  the working hand-rolled path.

## Evaluator: memoize the structural hash on each Expr node (2026-08-11)

Investigating whether the symbol table or `expr_hash` contributes to the
systemic per-node evaluator constant (`MATHILDA_EVALUATOR_PERFORMANCE.md`): the
symbol table does **not** — name→definition resolution is already an O(1)
cached-pointer read on each node (`data.symbol.def`). But `expr_hash`
(`src/expr.c`) was FNV-1a **recomputed by walking the whole subtree on every
call**, and it is called per-element in `Plus`/`Times` like-term grouping,
Association key indexing (`assoc_index.c`), and the set ops
(`Union`/`DeleteDuplicates`/`Tally`, `list/setops.c`).

- **New field `Expr.hash_cache`** (`src/expr.h`): a lazily-filled memo of
  `expr_hash(node)`, sentinel `0` = unhashed (a genuine hash of 0 just recomputes
  — harmless). Filled on first `expr_hash`, reused thereafter; the recursion
  memoizes the whole subtree bottom-up. Zero-initialised in the single allocator
  `expr_alloc_node`, so every constructor and the `expr_unshare` copy start clean.
- **Invalidation contract** — `expr_invalidate_hash(e)` (inline in `expr.h`) is
  called at every in-place structural mutation of a live node: `eval_flatten_args`
  (Flat), `flatten_sequences`, the generic Orderless `qsort`
  (`src/eval.c`), and the pattern alpha-rename (`src/symtab.c`). The cache is
  benign metadata (ignored by `expr_eq`/`expr_compare`), like `symbol.def`.
- **`MATHILDA_HASH_VERIFY` build** (define-gated in `expr.c`): ignores the cache,
  recomputes every hash, and `abort()`s if a surviving cache value disagrees —
  turning any missed invalidation into a deterministic failure. Ran clean over a
  broad stress corpus, all seven `benchmarks/4x-eval-*`, and ten hash-relevant
  unit suites (`association`, `packed_list`, `sort`, `complement`,
  `intersection`, `mapat`, `replaceat`, `flatten_at`, `array_flatten`,
  `compile_assoc`).

Result: hashing the same subtree repeatedly (Association lookups, dedup/`Tally`
of repeated structural elements, re-grouping a stable sum) drops from
O(subtree) per touch to O(1). Measured up to **~14× faster** on dedup/`Tally` of
a list of repeated deep nodes (4.07→0.30 ms) with no change to results. No new
allocation (inline field), so valgrind is unchanged at the macOS baseline; full
`ctest` shows no new failures (the 6 failing suites — `zero_test`, SVD/eigen/
lapack SEGFAULTs, `partitionsq` timeout — are the documented pre-existing set).
The packed-list ⇄ materialised-`List` hash byte-identity (`test_packed_list.c`)
still holds. Docs: `MATHILDA_EVALUATOR_PERFORMANCE.md`.

## Matcher: `Condition` over a multi-element sequence blank (2026-08-11)

Fixed a conformance bug: a `Condition` wrapping a sequence blank —
`x__ /; test`, `x___ /; test`, and the named/nested/double-named forms
(`c : (b__ /; t)`, `b___ /; c1 /; c2`) — matched **only when the sequence
spanned exactly one element**. For zero or ≥2 elements it failed even with a
literal `True` guard, so the extremely common idiom
`MatchQ[{5, 10}, {b__ /; Total[{b}] == 15}]` returned `False` (WL: `True`).

Root cause in `src/match.c`: `match_args_internal` peels `Pattern`,
`Shortest`, `Longest`, `Optional` and strips `PatternTest` for sequence blanks,
but never handled `Condition[seqblank, guard]`; it fell through to the
single-element path (`min_k = max_k = 1`), so only the width-1 case — which a
`BlankSequence` also matches — slipped through. Fix mirrors the `PatternTest`
handling: strip the `Condition` layer(s) when the inner pattern is a sequence
blank / `Repeated`, remember the guard chain, and evaluate it once (via the new
`eval_seq_conditions`, inner `/;` first) at each commit point after the sequence
variable is bound. Untouched when the inner pattern is a single blank, so the
well-tested `x_ /; test` path is unchanged. `PatternTest` over a sequence and
`Condition` over a single element both already worked and still do.

Regression cases added as section 37 of `tests/match_stress_corpus.m`
(287 → 298 cases, all green). Enumeration counts cross-checked against an
independent brute-force partition enumerator.

## Matcher: fix per-guard-evaluation memory leak (2026-08-11)

Fixed a pre-existing leak in `guard_all_true` (`src/match.c`): the guard leaf
was evaluated as `evaluate(expr_copy(g))` with the `expr_copy(g)` temporary
inlined. `evaluate()` **borrows** its argument (it copies internally), so that
temporary was never freed — one orphaned `Expr` node per guard leaf that did not
evaluate to the literal `True`. Because most backtracking attempts have a
**failing** guard, this leaked ~1 node per *failed* condition check across the
whole system (every `/;` in matching, `Cases`, `ReplaceAll`, conditional
`DownValues`, …). Now the copy is held in a variable and freed. Under valgrind,
a 75,327-guard-evaluation run drops from 75,058 leaked blocks to the constant
macOS startup baseline (422 blocks); named-sequence + `Cases` workloads that lost
332 KB now lose nothing beyond baseline. No result changed — this is purely an
ownership fix.

`MATHILDA_PATTERN_MATCHER_PERFORMANCE.md` (repo root) gains **Case M**, a scaling
study of the equal-sum contiguous-partition family that surfaced both fixes. It is
a head-to-head against Mathematica 14.0 (`wolframscript`) on identical inputs: the
pattern is genuinely exponential *in Mathematica* (the reader's verbatim pattern
takes 6.75 s at N=20; a distinct-block variant 38 s at N=120), but Mathilda's
matcher prunes it to polynomial/constant cost — 100× to 135,000× faster with
identical match counts. The PDF is regenerated with `pandoc --pdf-engine=xelatex`.

## Evaluator: pooled `MatchEnv` (2026-08-11)

First optimization driven by the evaluator-throughput suite above.
`apply_down_values_def` (`src/symtab.c`) allocates and frees one `MatchEnv` — via
`env_new`, three `malloc`s — per candidate DownValue, so recursive rewriting
churns millions (`fib[28]` ≈ 2.5M envs, one per fib call × 3 rules tried).
`env_new`/`env_free` (`src/match.c`) now recycle the whole struct **including its
`symbols`/`values` arrays** through a bounded static free-list (`ENV_POOL_CAP`
256), so reuse is allocation-free after warm-up. Mirrors the existing bounded
`Expr` node pool: single-threaded, reentrant (nested matches draw more from the
pool), pooled envs are program-lifetime "still reachable". The external contract
of `env_new`/`env_free` is unchanged and `env_free` still releases each binding's
`strdup`'d key and value ref — only the arrays and struct are kept.

Effect (Mathilda ÷ WL 14.0 ratio, before → after): `fib[28]` 2.7×→2.2×
(1.57 s→1.33 s), `ack[3,4]` 3.1×→2.5×, mutual recursion 3.0×→2.2×,
`Nest[incr,0,50000]` 2.0×→1.6×; `Count`/`Position` over 5000 `f[k]` nodes crossed
into parity (suite `SLOWER` 17→15). `tests/bench_match.c` shows it directly:
`Cases` 333→196 ns/elem, `Position` 1083→583, `ReplaceAll` 390→237 (1.4×–1.9×).
It deliberately does **not** move the arithmetic-bound rows (Case B, the `//.`
folds, the Orderless sum), which are `Length`/`Plus`/list-rebuild bound, not
env-allocation bound — those are the next targets.

Verified: `bench_eval` and `bench_match` gates PASS; the env-touching unit suites
(`match`, `rule_dispatch`, `eval_timestamps`, `eval_eager_exit`, `expr_sharing`,
`return`) all pass; the 5 pre-existing ctest failures (`zero_test`, and the SVD/
eigen/lapack SEGFAULTs) fail identically with the change stashed, so they are not
regressions; valgrind on a matcher-heavy workload holds at the constant 422-block
macOS baseline with the pooled envs correctly *still reachable* (no new loss). No
result changed — this is an allocation-strategy change only.

## Evaluator: machine-integer fast path for Plus and Times (2026-08-11)

Second optimization from the evaluator-throughput suite. `builtin_plus` /
`builtin_times` (`src/plus.c`, `src/times.c`) ran several O(n) scans (NDArray
probe, neg-Plus distribution, SeriesData, inexact contagion, then
(coeff,base)/(base,exp) grouping) before combining terms — real overhead for the
ubiquitous `Plus[int,int]` / `Times[int,int]` that dominates recursive integer
code (`fib[n-1]+fib[n-2]`) and loop accumulators. Added a fast path after the
n==0/1 checks: when every argument is a machine `EXPR_INTEGER`, fold them with the
overflow-checked `ci_add_i64` / `ci_mul_i64` (Times short-circuits on a 0 factor)
and return a single integer. On overflow, or any non-integer operand, it falls
through to the existing generic path, which promotes to bigint — so results are
unchanged, including the exact bigint answers for `9223372036854775807+1` and
`3037000500^2` (checked byte-for-byte against Mathematica 14.0).

Effect (on top of the MatchEnv pool; Mathilda ÷ WL): `fib[28]` 1.33 s → 1.06 s
(2.7×→1.9× vs 1.57 s baseline), `ack[3,4]` 16.8→14.3 ms, mutual recursion
0.85→0.74 ms, `Nest[incr,0,50000]` into parity. Suite `SLOWER` count 17→14,
`AHEAD` 11→14 cumulatively. Verified: full `ctest` 199/204 (the failures are the
pre-existing `zero_test` + SVD/eigen/lapack SEGFAULTs, plus the flaky
`moebiusmu_tests` which fails at the same ~20% rate on unmodified `de6a69f`);
`bench_eval`/`bench_match` gates PASS; arithmetic edge cases (overflow→bigint, 0
factor, negatives, mixed symbolic, rationals, reals) match WL; valgrind at the
422-block baseline.

A third lever — adopting the evaluator's per-step argument buffer into the
reassembled node (`expr_new_function_adopt`) to skip a malloc+memcpy on large
`List`/`Plus` rebuilds — was built and A/B-measured but **rejected**: the win was
within noise (0–7%, mostly noise) because the large-node cases are dominated by
the operation (`replace_bindings` splice, Orderless grouping), not the reassembly
copy. Not worth a hottest-path change + new public API. The remaining suite gaps
(`//.` folds 4.2×, Case-B-untyped 3.1×, Orderless sum 2.8×) are those
operation-bound costs; see `MATHILDA_EVALUATOR_PERFORMANCE.md` for the next
targets.

## Evaluator: borrow MatchEnv keys instead of copying them (2026-08-11)

Third optimization. The `MatchEnv` pool recycles the struct and its arrays, but
`env_set` (`src/match.c`) still `strdup`'d every binding's key and `env_free`
freed it — one malloc + free per binding, millions in recursive rewriting and
structural mapping. Every `env_set` caller passes a key that already outlives the
per-attempt env: an interned symbol name (`sym->data.symbol.name`, program-
lifetime, owned by the interner) or a string literal (`"$OptionsPattern$"`). So
the key is now stored by **borrow** — no `strdup`, and `env_free`/`env_rollback`
never free it. Comparison is pointer-first (interned keys — the hot path, since
the matcher and `replace_bindings` both pass `sym->data.symbol.name` — hit
immediately) with a `strcmp` fallback so the cross-translation-unit literal
callers still match.

Effect (on top of pool + int fast path): `fib[28]` 1.06→1.05 s, `ack[3,4]`
14.3→13.1 ms, Case B typed into parity, `bench_match` `ReplaceAll` 237→187
ns/elem. Cumulative suite over the three optimizations: **17→13 slower, 11→15
ahead** vs Mathematica 14.0.

Verified: `bench_eval`/`bench_match` gates PASS; matcher correctness (nonlinear
patterns `{a_,a_}`/`{a__,b__,a__}`, `OptionsPattern`, guards, `Cases`/`ReplaceAll`)
matches WL byte-for-byte; `ctest` failures are the pre-existing/flaky set
(`zero_test`, `moebiusmu`, `bench_compile` load-gate, SVD/eigen/lapack SEGFAULTs);
valgrind at 420 blocks — two *below* the 422-block macOS baseline (fewer
allocations), no invalid access, no new loss.

## Evaluator: skip evaluate() for atomic arguments (2026-08-11)

Fourth optimization, and the one found by *profiling* rather than reasoning.
`sample` on the `//.` fold showed the entire cost in `eval_and_free`
re-evaluating the result list each pass — the per-element `evaluate()` calls in
`evaluate_step`'s argument loop, not `replace_bindings` or the match. A raw atom
(Integer/Real/String/BigInt/MPFR/NDArray/Compiled) always evaluates to itself, so
`evaluate()` there just `expr_copy`s it after paying the recursion-depth bump,
trace push, deadline check and fixed-point-loop setup *per call*. The loop now
recognises an atomic argument and goes straight to `expr_copy`, skipping
`evaluate()` entirely — provably equivalent (same pointer, so the change flag
stays clear; an atom is never an in-flight `Throw`/`Goto`). `SYMBOL` is excluded
(it may carry an OwnValue).

This is the hot path whenever a large `List` of numbers is re-evaluated — most
visibly every pass of `list //. rule`, which re-walks the whole (mostly
unchanged) list. Effect vs WL 14.0: `//.` fold on `Range[800]` **4.3× → 2.2×**
(16.8 → 9.2 ms), on `Range[400]` → 2.3×, Case B untyped 3.1× → 2.5× (its guard
builds `{x},{y},{z}` integer lists), and the `ReplaceAll`-rebuild row off the slow
list. Suite `SLOWER` 13 → 11, `AHEAD` 15 → 17.

Cumulative over the four evaluator optimizations this week (MatchEnv pool, Plus/
Times machine-int fast path, borrowed MatchEnv keys, atomic-argument skip): the
evaluator-throughput suite moved from **17 slower / 11 ahead** to **11 slower /
17 ahead** vs Mathematica 14.0, with no regressions. The remaining top gap is the
Orderless sum (`Length[Plus @@ 2000 symbolic terms]`, 3.3×) — symbolic terms, not
atoms — which is the next target. Verified: `bench_eval`/`bench_match` gates PASS;
all 28 suite value checks agree with WL (0 CHECK-FAIL); `ctest` failures are the
pre-existing/flaky set (`zero_test`, `bench_pack`/`bench_compile` load-gates,
SVD/eigen/lapack SEGFAULTs); valgrind at the 420-block macOS baseline.

## Evaluator: skip the redundant sort in builtin_plus (2026-08-11)

Fifth optimization, again found by *profiling* (`sample` on `Plus @@ Table[c[k] x,
{k, 2000}]`): ~half the time was in the final-term `qsort` and its `expr_compare`
per comparison — the grouping hash table and reconstruction were already O(1)/O(n).
But a `Plus` built in order arrives canonically ordered (`c[1] x < c[2] x < …`),
and every re-evaluation of an already-sorted sum re-sorts terms that never moved —
pervasive, since a sum flows through the evaluator to a fixed point. `builtin_plus`
(`src/plus.c`) now guards the `qsort` with an O(n) already-sorted pre-check
(`plus_cmp_ptrs` scan, sort only on the first descent found) — the same technique
already used for the Orderless fast path in `evaluate_step`. Same canonical result:
skipping a no-op sort or sorting an unsorted sum both yield the identical order.

Effect: re-evaluating a canonical 2000-term sum **1.89 → 1.12 ms (−40%)**;
`expr_compare` samples 307 → 80, `qsort` 61 → 20. The suite Orderless-sum row moved
3.3× → 3.0× — its residual is now `Table` construction and the O(n) Infinity/
contagion pre-scans, not the sort. The general win is the re-evaluation path, which
every repeated symbolic-sum evaluation (Expand, polynomial arithmetic, Simplify)
hits.

Verified: `Expand[(1+x+y)^12] = 531441`, term collection (`2x+3x+x → 6x`) and
canonical ordering (`z+a+m+b+3+1 → 4+a+b+m+z`) correct; the full Expand/Simplify/
polynomial/numeric-domain test set passes; `bench_eval`/`bench_match` gates PASS;
`ctest` failures are the pre-existing/flaky set (this change is on the symbolic
grouping path, not the packed path `bench_pack` exercises); valgrind at the
420-block macOS baseline.

## Evaluator: borrow subset/remainder slices in ordered sequence matching (2026-08-11)

Sixth optimization. Re-profiling the `//.` fold *after* the atomic-argument skip
showed the cost had moved off `eval_and_free` and into the matcher:
`match_args_internal` (`src/match.c`) allocated and copied a fresh `remainder`
array (via `extract_subset`) at **every** pattern element — even single blanks —
so one `{a_, b_, r___}` pass paid ~4 O(n) copies of the tail. But
`next_combination` is gated on `is_orderless`, so for an *ordered* (non-Orderless)
head the do-while runs exactly once with `comb = [0..k-1]`: the consumed elements
are the contiguous prefix `exprs[0..k-1]` and the remainder is the contiguous
suffix `exprs[k..]`. Both are slices of the caller's array and are read-only (type
checks, `expr_copy` into `seq_val`/`matched_val`, and the recursive callee), so
they are now **borrowed** instead of malloc+`extract_subset`. The heap copies live
in `subset_owned`/`remainder_owned` (NULL in the borrow case → the free sites are
no-ops); the Orderless combination path is unchanged. The `comb` index array is
also skipped for ordered heads (only `extract_subset`/`next_combination` read it,
both Orderless-only).

This is a **general** matcher speedup, not just the fold — every pattern match over
an ordered head's arguments now avoids the per-element subset/remainder/comb
allocation. `bench_match`: `ReplaceAll` 187 → 99.8 ns/elem, `Cases` 216 → 126,
`Position` 634 → 500, DownValue-Map 613 → 513. Fold `Range[800]` 9.2 → 8.2 ms,
bubble sort `//.` 7.6 → 3.8 ms (2×), Case D 3.8 → 1.6 ms, `ack[3,4]` 13 → 9.5 ms,
`fib[28]` and the `ReplaceAll`-rebuild row into parity.

Cumulative over the six evaluator optimizations this week: the throughput suite
moved from **17 slower / 11 ahead** to **8 slower / 20 ahead** vs Mathematica 14.0,
worst outliers 4.3× → ~2.3×, with no regressions. Verified: the 298-case
`match_stress_corpus` passes (0 failed, 0 crashed); `match_tests`,
`rule_dispatch_tests`, `bench_eval`, `bench_match` PASS; matcher correctness
(nonlinear `{a__,b__,a__}`, `Cases`/`ReplaceList` with guards, OrderlessPatternSequence,
`Plus[a,b,c] /. {x__,y__}`) matches WL; `ctest` failures are the pre-existing/flaky
set (`zero_test`, `primenu` — 2/8 flaky on the committed baseline too,
SVD/eigen/lapack SEGFAULTs); valgrind at the 420-block macOS baseline over both the
borrow (ordered) and copy (Orderless) paths — no invalid access, no double-free of
a borrowed slice.

## Evaluator: Apply/Map/Scan/MapIndexed level short-circuits + Plus/Times special-case short-circuit (2026-08-12)

Follow-up to the *evaluator throughput* campaign, targeting the one row still
trailing Mathematica in `MATHILDA_EVALUATOR_PERFORMANCE.md` — the arithmetic
sentinel `Length[Plus @@ Table[c[k] x, {k, 2000}]]` (4.69 ms vs WL 1.5 ms, 3.1×).
Profiling the three operations on its critical path (`Table` build, `@@`, the
`Plus` grouping) surfaced two avoidable, non-fundamental costs — one of them a
finding the campaign had missed.

**1 — Specialised top-level `Apply` fast path** (`src/funcprog.c`). `f @@ expr`
(default level spec `{0,0}`) went through the general recursive `apply_at_level`,
which (a) called `get_depth(expr)` — a full recursive traversal of the whole
argument tree — at every node, though its only consumer is the negative-level
branch a non-negative spec never takes, and (b) *structurally cloned every element
subtree* (~4000 interior `Times`/`c[k]` nodes for a 2000-element list) even though
Expr trees are immutable and refcount-shared. `builtin_apply` now has a
self-contained fast path — mirroring the existing `f @@ <|assoc|>` one — that, for
`ls == NULL` with a function operand, builds `f[elements…]` by refcount-sharing
each element (`expr_copy` is an O(1) refcount bump) and evaluates once. Provably
equivalent to `apply_at_level(f, expr, 0, {0,0})`. The general `apply_at_level` was
also tightened: for a non-negative spec it skips `get_depth` and returns
`expr_copy(expr)` once `current_level > spec.max` (nothing can apply at that level
or deeper), and an `apply_child` helper folds the same past-max check into the
per-child recursion so `@@@` (`Apply[…, {1}]`) — a common operation whose general
path recursed once per element *and* once per sub-element, the level-2 calls doing
nothing but refcount-share — now shares each element's arguments in O(1). Isolated
`f @@ list` over 2000 elements **~1.3 ms → ~0.05 ms**; `f @@@ list` restructuring
over 5000 elements **~0.93 → ~0.78 ms (−15%)**; the 5000-triple
`Apply[Plus, …, {1}]` benchmark **11.5 → 7.4 ms (2.47× → 1.6× WL)**. Every `Apply`
level-spec form (`@@`, `@@@`, `{2}`, `{1,2}`, `{-1}`, `{-2}`, `Heads->True`, and
deeper nesting) is pinned in `test_core_algebra.c`.

**1b — `Map` (`/@`) shares the subtree past the mapped level** (`src/funcprog.c`
`map_at_level`). Map is bottom-up, and had the *same* `get_depth`-everywhere +
descend-and-rebuild overhead — worse, because it always walked to the leaves: the
common `f /@ list` cost grew with element *depth* even though `f` only touches
level 1. The same two changes apply: skip `get_depth` for a non-negative spec, and
once past the maximum level share the whole subtree by an O(1) refcount bump
instead of descending + rebuilding it. `f /@ 5000 g[a,b,c]` **4.19 → 0.56 ms
(−87%)** and `f /@ 5000 g[h[…],h[…]]` **7.12 → 0.57 ms (−92%)** — the time is now
independent of element depth. `Map[f, expr, {0}]` (map at level 0) becomes a clean
`f[expr]` share too. Every level-spec form (`{0}`, `{2}`, `{0,1}`, `{-1}`,
`Infinity`, `Heads->True`, `Hold`-suppressed) is pinned in `test_core_algebra.c`.

**1c — `Scan` (`src/funcprog.c` `scan_at_level`)** got the same treatment. Scan
discards results so there is no rebuild, but it still descended every element's
whole subtree and called `get_depth` at each node, so `Scan[f, list]` cost grew
with element depth too. Once past a non-negative upper bound the descent now stops
(a visit needs `level <= max`, which only rises with depth), and a pure
non-negative spec skips `get_depth`; the negative-spec paths and the
leaves-before-roots order / `Throw`/`Return` control flow are untouched.
`Scan[f, 5000 g[a,b,c]]` **0.90 → 0.55 ms (−39%)**, `Scan[f, 5000 g[h[…],h[…]]]`
**1.38 → 0.52 ms (−62%)** — depth-independent. Pinned in `test_core_algebra.c`
(`test_scan`), and the existing `scan_tests`/`funcprog_through_tests` are unchanged.

**1d — `MapIndexed` (`src/funcprog.c` `mi_at_level`)** completes the set. It
rebuilds bottom-up while threading each part's `{position}`, and the depth it
accumulates into `*out_depth` is read *only* by a negative-level bound — so under a
non-negative spec it is never used, yet it descended and rebuilt every element's
whole subtree to compute it. Two guards fix that: past the max level share the
subtree (return early, depth left at 1), and at the deepest wrapping level share the
node instead of descending + rebuilding (its children are all past max, so the
rebuild would just reproduce it). `MapIndexed[f, 5000 g[a,b,c]]` **5.55 → 1.57 ms**,
`MapIndexed[f, 5000 g[h[…],h[…]]]` **8.39 → 1.60 ms** — depth-independent, and now
**1.2× WL 14.0** (down from 4.1×; it stays just above WL because it builds a
position vector + two-arg wrapper per element, which no short-circuit removes).
Every level-spec form, the `{i,j,…}` positions, `Heads->True`, and `Association`
`Key[k]` positions are pinned in `test_core_algebra.c` (`test_mapindexed`); the
existing `mapindexed_tests` is unchanged.

**2 — Fused special-case short-circuit in `Plus` and `Times`** (`src/plus.c`,
`src/times.c`). Both ran five independent full O(n) pre-scans before term grouping
— NDArray probe, neg-Plus distribution (Plus only), SeriesData, inexact contagion
(with a size-n `malloc` taken *before* the check), Infinity/Indeterminate — and for
an ordinary symbolic or rational sum/product every one finds nothing. A single
detection pass now decides whether any could act; if not, execution jumps straight
to grouping. The predicate is a provably-correct superset of "some pass would act"
(NDArray→`is_ndarray`, neg-Plus→`is_neg_of_plus`, series→`is_series_data`,
contagion→`arg_is_inexact` — exported from `numeric.c` for this, matching
`numeric_contagion_args`'s own trigger — Infinity→`classify_plus_term`/the inline
Times check), so skipping the passes when it is false is exactly equivalent. The
guarded passes are otherwise byte-for-byte unchanged.

**Result.** `Length[Plus @@ Table[c[k] x, {k, 2000}]]` **4.69 → 2.95 ms (−37%,
3.1× → 2.0× WL)**; the sibling `bench_eval` row "orderless sort (Plus 1200)"
dropped from 0.27 to ~0.19 norm. The residual is now dominated by `Table`'s
per-element symbolic-`Times` evaluation (2.43 ms of the 2.95 ms) — the systemic
per-node evaluator constant, whose largest remaining lever is the fixed-point
double pass (`builtin_times`/`builtin_plus` unconditionally rebuild and trip the
change flag, forcing a confirm-stable step). That is a core-evaluator change of
much broader blast radius and is left for a separate, measured effort.

**Tests.** New `tests/test_core_algebra.c` (wired into CMake as
`core_algebra_tests`) pins Plus/Times/Power/Divide/Apply/Length/ordering/Table
against WL-checked FullForm, deliberately covering the paths these changes touch:
every `Apply` level-spec form (`@@`, `@@@`, `{2}`, `{-1}`, `Heads->True`, empty,
single, atomic) and every guarded Plus/Times special case (cancellation, Infinity,
ComplexInfinity, Indeterminate, contagion, radical fusion, trig canonicalisation).
`tests/bench_eval.c` gains the three flagship regression rows mandated by the perf
doc — `fib[24]` (dispatch), Case B typed (matcher constant), Plus-2000 (this
sentinel). Verified: `core_algebra_tests`, `eval_tests`, `sort_tests`,
`expand_tests`, `collect_corpus_tests`, `power_corpus_tests`, `evaluate_tests`,
`regression_tests`, `match_tests`, `match_extensive_tests` PASS; the 298-case
`match_stress_corpus` passes (0 failed/0 crashed); `bench_eval` PASS with the new
baselines armed; valgrind identical to the empty-session macOS baseline
(13,440 B / 420 blocks, 0 invalid read/write/free) over the Apply fast path and the
Plus/Times short-circuit paths — no new leak.

## Graphics: add ArrayPlot (2026-08-12)

New `ArrayPlot[array, opts...]` (`src/graphics/arrayplot.{c,h}`), a discrete
grid heatmap for a literal 2D array — the counterpart to `DensityPlot`'s
sampled-function heatmap, but with no interpolation: one cell per array entry,
row 1 at the top, column 1 at the left. Unlike the `HoldAll` function-sampling
plotters, `ArrayPlot` is not `HoldAll`; `array` is an ordinary evaluated `List`
or `NDArray`, ingested through the existing `na_load_matrix` loader
(`src/linalg/numarray.h`) that the linear-algebra surface already uses, so
packed and visible `NDArray` inputs work for free.

Colours are deliberately drawn from the **existing** shared ramp table in
`plot_common.c` (`named_color_ramp`/`thermal_rgb`/`resolve_ramp_to_rgb`) rather
than a new palette: the default `ColorFunction` is `"Greyscale"` (white at the
array minimum, black at the maximum) — Mathematica's own `ArrayPlot` default,
and the one plotter in this codebase that doesn't default to the thermal ramp.
`"Rainbow"`, `"Temperature"`, `"CoolTones"`, `"WarmTones"` all work identically
to their use in `DensityPlot`/`ContourPlot`/`StreamPlot`. `Mesh -> All` overlays
grid lines in `GrayLevel[0.5]`, the same neutral grey already used as this
module's ColorFunction fallback. `PlotLegends -> Automatic` reuses the
`$StreamColorBar` metadata node and `render.c`'s existing colour-bar renderer.

A matrix whose every entry is already a colour literal
(`RGBColor`/`GrayLevel`/`Hue`/`CMYKColor`) is detected and painted directly,
letting `ArrayPlot` double as a raw pixel-grid renderer —
`ArrayPlot[{{Red, Blue}, {Blue, Red}}]` — with no `ColorFunction` involved.
`AspectRatio` defaults to `rows/cols` so cells render square. Registered with
`ATTR_PROTECTED`, docstring via `symtab_set_docstring`, `SYM_ArrayPlot` interned
in `sym_names.c` alongside its sibling plot heads.

Six new tests in `tests/test_graphics.c` (`graphics_tests` target) cover: return
head, default greyscale mapping, colour-matrix pass-through order, unevaluated
fallback for a non-array argument, `Mesh` line count, and the `rows/cols`
`AspectRatio` default. Verified: `graphics_tests` all green; `make` clean at
`-O3 -std=c99 -Wall -Wextra` with no new warnings.

## Graphics: ArrayPlot ColorRules, and a leaked-evaluation fix in arrayplot.c (2026-08-12)

Added `ColorRules -> {v1 -> c1, v2 -> c2, ...}` to `ArrayPlot` (reported: colours
weren't showing up — the plot rendered fully greyscale). `ColorRules` gives an
explicit colour to cells whose value exactly equals a named key, checked before
the continuous `ColorFunction` ramp; a cell matching no rule still gets the
normal scaled `ColorFunction` colour rather than being left uncoloured —
`ArrayPlot[{{1,0,0.5},{0,1,0.5}}, ColorRules -> {1 -> Pink, 0 -> Yellow}]` now
paints the `1`/`0` cells Pink/Yellow and the `0.5` cells on the usual grey
ramp. New `SYM_ColorRules` interned in `sym_names.c` alongside the other
`ArrayPlot` option symbols.

Implementing it surfaced a real bug, caught by `leaks --atExit` rather than by
inspection: `evaluate()` **borrows** its argument — it makes its own internal
copy and never frees what it's handed (see `src/eval.c`'s `evaluate`, whose
first act is `current = expr_copy(e)`) — so `evaluate(expr_copy(rhs))` with the
copy inlined leaks that copy's reference. This is the exact bug class already
fixed for `guard_all_true` in `src/match.c` (`docs/spec/changelog/2026-08-10.md`,
"Matcher: fix per-guard-evaluation memory leak"), just not yet applied to
`arrayplot.c`. Because `expr_copy` is a refcount bump rather than a deep clone,
an orphaned bump on a shared subtree (`rhs`) blocks that subtree from ever
reaching refcount 0 during the caller's teardown — so the leak is not one node
but the whole unevaluated option-value subtree, which is why `ColorRules ->
{1 -> Pink, 0 -> Yellow}` (evaluating named colours into `RGBColor[...]`) leaked
visibly (11 blocks/560 B for one call) while a bare `Mesh -> All` leaked a
single 64-byte node per call — both instances of the identical bug, just
different-sized victims. All five call sites in `arrayplot.c`
(`ColorFunctionScaling`, `Mesh`, `PlotLegends`, `ColorRules`, and the generic
Graphics-option passthrough — i.e. every option `ArrayPlot` accepts) shared the
inlined form. Fixed with one local helper, `eval_borrowed()`, that names the
copy and frees it after use; not touched in the sibling plotters
(`densityplot.c` etc.), which share the same idiom and same latent bug but are
outside this change's scope.

Verified: `leaks --atExit` over 50-iteration loops covering
`ColorRules`-matching, `ColorRules -> None`, plain `Mesh -> All`, and the
combined `Mesh`+`PlotLegends`+`ColorFunction` case from the original `ArrayPlot`
changelog entry above — all now **0 leaks** (previously 1–6 leaked
blocks/call depending on the option combination). `graphics_tests` green
including a new `test_arrayplot_color_rules_override_matching_cells` (exact-key
match, unmatched-value fallback, `ColorRules -> None` equivalence to omitting
the option). `make` clean at `-O3 -std=c99 -Wall -Wextra`, no new warnings.

## Graphics: fix a Frame+AspectRatio letterbox, then let ArrayPlot mix numeric and colour cells freely (2026-08-12)

Two follow-up fixes to `ArrayPlot`, both from real usage rather than review.

**1 — Frame plots with an explicit `AspectRatio` letterboxed inside their
own frame** (reported via screenshot: an `ArrayPlot`'s coloured grid sat with
a visible white margin between it and the frame border, on all sides).
Root cause was general renderer logic in `src/graphics/render.c`, not
`ArrayPlot`-specific — reproduced identically on unmodified `Plot3D[...,
Mesh -> All]`, which also sets an explicit `AspectRatio`. `gfx_window_height()`
sizes the *window* to match `AspectRatio`, but `Frame`'s margins are fixed
pixel amounts (some floored, e.g. clearing the toolbar), not proportional
between width and height — so the margin-reduced *data region* lands at a
different aspect ratio than the window, and any `Frame` plot with an explicit
`AspectRatio` (`ArrayPlot`'s `rows/cols` default, `DensityPlot`'s `1`, …) can
letterbox. Added `gfx_window_height_fit_region()`: a few fixed-point
iterations (the margin formula is a contraction — each margin is either
height-independent or ≤7% of height) that solve for the window height whose
*region*, not just the window, hits the target ratio. The margin formulas
themselves were factored into shared `gfx_horizontal_margins()` /
`gfx_vertical_margins()` so the sizing pass and the actual region layout can
never drift apart. `gfx_window_height()` itself is untouched (its pinned
`test_window_height_policy` still passes byte-for-byte); the new function is
called right after it in `graphics_show()`, before `InitWindow`. New
`test_window_height_fit_region_no_letterbox` pins both halves: the corrected
height's region matches the target ratio within 1%, and — to prove the test
actually exercises the bug — the pre-fix (naive) height's region does not
(>5% off) for the same inputs.

*Diagnostic note:* while investigating a *separate* "window freezes on close"
report against this same `ArrayPlot` call, `sample`(1) on the actual running
process showed it had already returned to the REPL prompt (`readline`) —
i.e. `CloseWindow()` had already run. That looks like a stale/ghost frame
left on screen by the OS compositor after close, not a hang in Mathilda; it
self-resolves (switch away and back). No code change from that report; noted
here since it surfaced while looking at the same window-sizing code path.

**2 — `ArrayPlot[{{1, 0, 0, Pink}, {1, 1, 0, Pink}, {1, 0, 1, Red}}]` (mixing
plain numbers and colour literals in the same array) returned unevaluated.**
The array-loading logic required every cell to be numeric *or* every cell to
be a colour literal — a matrix mixing both matched neither shape and fell
through as "can't evaluate this," even though calling out a few specific
cells by colour while the rest follow the normal heatmap is a natural,
common use of the raw-pixel-grid feature. `src/graphics/arrayplot.c`'s
`arrayplot_is_color_matrix` (all-or-nothing) is replaced by `arrayplot_load`,
which classifies **each cell independently**: a colour literal is painted
directly, a plain number goes through `ColorRules`/`ColorFunction` as usual,
and anything else (a symbolic non-color, non-number cell) leaves the whole
call unevaluated, same as before. `ColorFunction`'s `[zmin, zmax]` scaling
range and `PlotLegends`'s eligibility (still "only when at least one cell is
numeric") are now computed by scanning just the numeric cells rather than
gating on an all-or-nothing mode flag. An `NDArray` input is unaffected — a
dense numeric buffer can't contain a colour literal by construction, so it
still goes through `na_load_matrix` as a pure numeric load.

New `test_arrayplot_mixed_numeric_and_color_cells` (named colours paint
directly, numeric cells keep the greyscale ramp) and an added case on
`test_arrayplot_invalid_args_stay_unevaluated` (a genuinely invalid cell,
e.g. `{{1, 2, foo}}`, still leaves the call unevaluated — the new per-cell
loader doesn't accidentally accept everything). `graphics_tests` all green;
`leaks --atExit` over 50 iterations mixing the new code path with the
existing pure-numeric, pure-colour, and both failure shapes: 0 leaks. `make`
clean at `-O3 -std=c99 -Wall -Wextra`, no new warnings.

`make check-packed-aware` failed: `ArrayPlot` checks `data->type == EXPR_NDARRAY`
(its fast path for a matrix argument, `src/graphics/arrayplot.c`) but was never

input's exactness (`arrayplot_load`'s numeric arm converts to `double` either

without this, `ArrayPlot[Table[Mod[i+j,5], ...]]` (an int64 array, per the

Verified: `make check-packed-aware` passes (`AWARE=176`, `INT64_OK=106`, 0

## Compile[]: `Norm[v, p]` two-arg forms + inline-vector auto-compilation (2026-08-12)

`Norm` had a `Compile[]` lowering only for the bare `Norm[v]` / `Norm[m]`
(2-norm / spectral), and a `Norm[{f[x], …}]` body could not auto-compile at all.
Two independent gaps, closed by operand kind. No interpreter behaviour changed —
both fixes live entirely in `src/compile/`, and the packed/NDArray `ndla_norm`
path is unchanged.

**1 — Declared-array two-arg forms (new `V_NORM` opcode).** `Norm[v, 1]`,
`Norm[v, Infinity]`, `Norm[v, k]`, `Norm[v, 2.5]`, and the matrix `Norm[m, 1]` /
`Norm[m, Infinity]` / `Norm[m, "Frobenius"]` now lower to a machine `Real`. The
second argument is a compile-time literal but not always a machine scalar
(`Infinity`, `"Frobenius"`), so it is baked into the instruction immediate
`imm.r` — `0` = none, `+Inf` = Infinity, `NaN` = "Frobenius", a finite positive
value = that `p` (rebuilt as an Integer when integral, since LAPACK keys the
matrix path on Integer 1/2). The VM (`OP_V_NORM`, a `K_ARR` op modelled on
`V_NDRED`) rebuilds `Norm[array, p]` and delegates to `ndla_norm`, so the
compiled answer is bit-identical to the interpreter's NDArray path by
construction. Validity mirrors `ndla_norm` exactly (`nd_norm2_encode` in
`compile_ndtables.c`): a rank-1 operand takes any positive `p` or Infinity; a
rank-2 operand takes `{1, 2, Infinity, "Frobenius"}`; an induced matrix `p`-norm
with `p ∉ {1, 2, Infinity}`, a string method on a vector, and int/complex
operands decline cleanly to the interpreter. The bare `Norm[v]`/`Norm[m]`
reduction (ND_REDS) is untouched.

**2 — Inline vector construction (auto-compilation).** A `Norm[{e1, …, en}, p]`
whose operand is a `List` literal (not a declared array) was the reason a
`Table[Norm[{Sin[x], Cos[x], x}], …]` body bailed wholesale — the compiler could
not lower the inline vector. It now expands to the same scalar arithmetic the
interpreter's `builtin_norm` uses (`norm_try_expand` in `compile.c`, shared by
`emit_node` and `infer_type`): `Sqrt[Σ Abs[ei]^2]` (p=2/Frobenius),
`Σ Abs[ei]` (p=1), `Max[Abs[ei]]` (Infinity), `(Σ Abs[ei]^p)^(1/p)` (general p),
expandable exactly where `builtin_norm`'s symbolic branch is (rank-1 under any p,
any rank under "Frobenius"). This produces inline scalar code with **no
per-iteration buffer allocation** — strictly better than packing a short vector —
and unblocks `Norm[{…}]` bodies inside `Plot`/`Table`/`NIntegrate`/`FindRoot`. A
rank-2 list under an induced norm (needs an SVD) is not expandable and falls
through unchanged.

**Verified.** `CompileDiagnostics` reports `Compiled -> True` for every reported
form and `False` for the correct declines; compiled values equal the interpreter
(bit-identical for the array delegate, within machine tolerance for the scalar
expansion); the `MATHILDA_COMPILE_DIAG=1` auto-compile probe no longer prints
`[compile] interpreting`. New tests in `tests/test_compile_transforms.c`
(`test_cf_norm_array_vector`, `_array_matrix`, `_list_literal`); the compile,
NDArray, normalize, and lstsq suites pass; `make check-c99` clean.

## Packed arrays: `Im` narrowing kernel — off the NOT_AWARE list (2026-08-12)

`Im` had an NDArray projection kernel but sat on `pack.c`'s `NOT_AWARE` list, so
on the *invisible* auto-packed-List surface it materialised to the scalar List
path — `Im[Range[1., 10^7]]` cost ~3.9 s where the sibling `Re` cost ~0.17 s
(~22×). The reason was exactness: `Im` of a real is the exact `Integer 0`, and a
projection kernel would have written `0.0` into a float64 buffer, an observable
wrong element head (the same real→integer trap that kept `Floor`/`Sign` off the
fast path until they got narrowing kernels on 2026-07-30).

Fix: give `Im` a narrowing pair (`NDKU_ImInt` in `src/ndkernels.c`, `to_int`) —
`to_int_r`/`to_int_i` write an `NDT_INT64` zero buffer from real/integer input
(unconditionally 0; the imaginary part of any real is 0, finite or not, so unlike
`Sign` there is nothing to reject), while a COMPLEX input still takes the `ndk_Im_c`
projection arm (the imaginary part, a Real), which `ndarray_map_unary`'s narrowing
branch skips for complex dtypes. `Im` then comes off `NOT_AWARE` and is implicitly
aware via its kernel.

Result: `Im[Range[1., 10^7]]` **3856 ms → 151 ms (~25×)**, matching `Re`; element
heads are identical to the List path (`Im[{2., 3.}] === Take[Im[Range[1., 300.]], 2]`
is `{0, 0}`, both exact `Integer`), a real `NDArray` gives an `int64` zero array,
and a complex `NDArray` still gives the Real imaginary parts. No behaviour changed
— the packed answer was already exact via the slow path; this makes the buffer
path produce it directly.

Incidental: `Abs` and `Im` are now hand-written kernels rather than `UK_PROJ`
macro expansions, dropping the two unused projection descriptors (`NDKU_Abs`,
`NDKU_Im`) so `src/ndkernels.c` compiles clean under `-Wall -Wextra`
(`-Wunused-const-variable`); `ndk_Abs_c`'s body is unchanged.

## Chop and Clip: buffer fast paths + Compile lowerings (2026-08-12)

`Chop` had no fast path on any surface, and `Clip` degraded to the interpreter
whenever it clipped against exact (default `{-1,1}`) bounds. Both are now fast on
the machine-buffer, `Compile[]`, and auto-compilation surfaces, with no change to
any answer. The exactness obstacle for both is the same real→integer trap `Im`
just hit — a chopped/clipped element is an exact `Integer`, which no uniform Real
buffer holds — so each keeps a buffer only where the result is uniform.

- **Chop NDArray fast path** (`chop_ndarray` in `src/core.c`; `Chop` added to
  `pack.c`'s AWARE). An auto-packed `List` used to be materialised before it
  reached Chop (~40× an aware head). Now a cheap alloc-free scan keeps the buffer
  untouched when NOTHING chops (`Chop[Range[1.,10^7]]` **1362 → 131 ms**); when
  something chops, a rank-1 buffer builds the mixed `{…, 0, …}` result in ONE pass
  off the elements (an all-zero result re-packs to int64), and higher ranks take
  the general delist. Complex/int64 buffers delist. Value-identical to
  `chop_recursive`.
- **Chop `Compile[]` + auto-compilation** (`compile_emit_mathfn.c`,
  `compile_infer.c`). `Chop[x]` / `Chop[x, δ]` (δ a literal) lower branchlessly to
  `x * (Abs[x] >= δ)` (the UnitStep mask-multiply, no new opcode) → `Real`; the
  chopped value is a machine `0.` (a CompiledFunction returns machine types). A
  machine integer never chops → identity. So `Chop[…]` now auto-compiles inside
  `Plot`/`Table`/`NIntegrate`/`FindRoot`.
- **Clip scalar `Clip[x]`** (default bounds) now lowers as `Min[Max[x,-1.],1.]`,
  filling the `na==1` gap; the explicit-bounds scalar form was already
  `Min[Max[x,lo],hi]`.
- **Clip exact-bounds buffer, three-way scan** (`ndstruct_clip`). The exact-bound
  path now distinguishes: nothing clips → the Real input; a MIX of clipped
  (Integer) and unclipped (Real) → the exact List path; and EVERYTHING clips to a
  finite exact-Integer bound → a uniform `NDT_INT64` buffer. That last case is the
  common `Clip[reals, {-1,1}]` over out-of-range data: **`Clip[Range[1.,10^7]]`
  4633 → 158 ms (~30×)**. Rational/infinite bounds still take the List path.

Verified: `check-array-exactness` 0 MIXED (Chop/Clip buffers stay single-headed or
degrade correctly), `check-packed-aware` OK (Chop now aware, AWARE 175→176);
compiled == interpreter (Chop/Clip maxdiff 0.0); short == packed element heads for
every Clip regime; `chop_tests`, `clip_tests`, `compile_transforms_tests` (new
`test_cf_chop`, `test_cf_clip_default`, `test_chop_packed_*`,
`test_clip_packed_exact_bounds`) pass; `check-c99` clean; 0 leaked bytes.
Inherent residual: a *partial*-chop / *partial*-exact-clip over a large buffer is a
mixed result the evaluator must walk element-by-element (matching Mathematica,
which also unpacks) — the buffer path covers the uniform cases.

## FindClusters beyond one dimension

`FindClusters` accepted only a flat list of real scalars; a list of vectors —
Wolfram's own second example — returned unevaluated. It now clusters:

- **equal-length numeric vectors** in any dimension,
- **colours** (`RGBColor`, `GrayLevel`, `Hue`, `CMYKColor`), whose arguments are
  coordinates, so a colour is a point in its own space and needs no
  colour-specific code,
- **strings**, on `EditDistance`.

```mathematica
In[1]:= FindClusters[{{1, 1}, {1, 2}, {9, 9}, {9, 8}}]
Out[1]= {{{1, 1}, {1, 2}}, {{9, 9}, {9, 8}}}

In[2]:= FindClusters[{"cat", "cot", "dog", "dig"}, 2]
Out[2]= {{"cat", "cot"}, {"dog", "dig"}}
```

**One dimension is unchanged, by construction.** The file's structure is now a
spanning tree with exact edge weights, and on a line the minimum spanning tree
*is* the sorted adjacency chain — so the general code reduces to the original
algorithm exactly there. The 132 existing acceptance rows are the proof and were
required to stay green; 35 rows were added.

**Exactness survives in n dimensions** because ranking uses *squared* Euclidean
distance, which is rational for rational input and monotone in the true distance.
`FindClusters[{{1/3, 1/7}, {1/3, 1/7 + 1/10^20}, {5, 5}}]` groups the two
near-identical exact vectors rather than collapsing them through a double.

Scope limits, stated rather than discovered:

- Only `Automatic`, `"Agglomerate"` and `"SpanningTree"` accept the new element
  kinds. The other seven methods read a sorted one-dimensional projection and
  decline instead of running on data where it is meaningless.
- Vectors and strings are capped, both being quadratic where a sort avoids that
  only on a line. The ceiling depends on which spanning-tree builder runs — see
  the machine-precision section below.
- `Rational` and `Complex` are numbers, not points: `{1/2, 1/3, 10}` clusters as
  three reals. Point heads are an explicit list precisely so that
  `Rational[1, 2]` is never read as a pair of coordinates.

## Distance functions

Seven functions that did not exist. `Names["*Distance*"]` returned only
`GraphDistance`, while `FindClusters`' `DistanceFunction` option accepted
`EuclideanDistance` and friends as **inert symbols** — which is why its
documentation could truthfully claim all the choices behaved alike.

| Function | Value |
|---|---|
| `EuclideanDistance[u, v]` | `Sqrt[Sum Abs[u_i - v_i]^2]` |
| `SquaredEuclideanDistance[u, v]` | `Sum Abs[u_i - v_i]^2` |
| `ManhattanDistance[u, v]` | `Sum Abs[u_i - v_i]` |
| `CosineDistance[u, v]` | `1 - (u . Conjugate[v]) / (Norm[u] Norm[v])` |
| `EditDistance[u, v]` | Levenshtein distance, strings or lists |
| `HammingDistance[u, v]` | positions differing, equal lengths required |

Exact input gives exact output where the value is rational; complex components
contribute their modulus (`Abs` before squaring, as Mathematica defines it);
symbolic input survives as an expression. Every value was cross-checked against
`wolframscript`, including two conventions that are not derivable:
`CosineDistance` of a zero vector is `0` rather than `Indeterminate`, and
`HammingDistance` on unequal lengths is left unevaluated.

The `DistanceFunction` documentation was corrected: the equivalence of the
Euclidean family is a statement about **one dimension**, where they are monotone
transforms of one another. It does not hold for vectors.

## Fixes

- **`FindClusters` with an explicit count was quadratic.** `FindClusters[data, 10]`
  over 100,000 points took 2.24 s against 0.087 s for `Automatic` on the same
  input, growing fourfold per doubling. The union-find introduced with the
  spanning-tree rewrite had no path compression, so when few edges are cut the
  surviving components form one long chain and every `find` walks it. `Automatic`
  hid the bug because many cuts leave many short components. With path halving
  and union by rank: **2.24 s → 0.083 s**, and linear again.

- **`Abs` and `Sign` decline on rationals with bigint components.**
  `Abs[-1/10^20]` does not evaluate while `Abs[-1/7]` does. This is a
  pre-existing bug, not introduced here, but it silently blocked every exact
  high-precision distance and so made `FindClusters` refuse exact vectors at that
  scale. The distances route around it by taking the sign through the exact
  comparator; **the underlying `Abs`/`Sign` gap remains and is worth fixing
  separately.**

## FindClusters: a machine-precision spanning tree, 219x faster on vectors

Clustering vectors was capped at 2000 points and spent nearly all its time
allocating expressions: exact Prim computes O(n^2) distances, and each one built
and evaluated a chain of `Expr` nodes to keep the comparison exact.

For input whose coordinates are *already* machine numbers, that buys nothing --
there is no precision beyond a double to preserve. Such input now takes a
double-precision Prim; only the n-1 chosen edge weights become expressions, so
allocation drops from O(n^2) to O(n). Input with a `Rational`, bigint or MPFR
coordinate keeps the exact builder, which is the only one that can order it
correctly.

| 2-D points | before | after |
|---:|---:|---:|
| 500 | 95 ms | 0.62 ms |
| 1000 | 398 ms | 2.0 ms |
| 2000 | 1.49 s | 6.8 ms |

**219x at n=2000**, which lifts the machine ceiling from 2000 to 20000 points
(0.81 s there). The exact path keeps its 2000 cap.

Nothing is given up. Distinctness was never decided from a distance on either
path -- it compares the elements with the exact comparator -- so
`FindClusters[{{1/3, 1/7}, {1/3, 1/7 + 1/10^20}, {5, 5}}]` still groups the two
near-identical exact vectors. Two builders for one definition is a standing risk,
so a test clusters the same points both ways (as integers, which are machine, and
divided by a constant, which makes them exact) and requires the partitions to
match, including over 400 random points.

Integer coordinates are required to be within 2^53 to take the fast path, since
beyond that a double stops representing integers exactly and the two builders
would quietly disagree.

## Sum: `Sum`Gosper` rejects var-dependent radicals up front (fixes a nested-sum hang) (2026-08-14)

Building a nested finite sum whose summand carries a fractional power of an
iterator-dependent base hung the evaluator. The trigger was the Thomson-problem
repulsion energy — 10 charges on a unit sphere:

```mathematica
Sum[1/Sqrt[(x[i]-x[j])^2 + (y[i]-y[j])^2 + (z[i]-z[j])^2 + 10^-9],
    {i, 1, n-1}, {j, i+1, n}]     (* n = 10: hung; never returned *)
```

`Sum[f, {i,1,n-1}, {j,i+1,n}]` is rewritten to `Sum[Sum[f, {j,i+1,n}], {i,1,n-1}]`,
and the outer finite sum tries the closed-form cascade *first* (its cost is
independent of span width). That cascade evaluates the inner `Sum[f, {j,i+1,n}]`
with `i` still symbolic, and `Sum`Gosper`'s step-1 `Simplify` — meant to reduce a
term ratio to `num/den` polynomials — diverged trying to rationalise
`Sqrt[q(j)] / Sqrt[q(j+1)]`, a ratio of square roots of a nine-symbol quadratic.

**Root cause and fix.** A hypergeometric term has a *rational* term ratio; a
summand with a fractional power of an `i`-dependent base never does, so Gosper
cannot sum it. `gosper_antidiff` now scans the summand for any `Power[base, exp]`
with a non-integer `exp` and a `base` that depends on the summation variable
(`src/sum/sum_gosper.c`, `has_var_radical`) and returns `NULL` *before* the
term-ratio `Simplify` is ever built. The cascade then declines cleanly, the outer
sum falls through to term-by-term expansion, and the inner sum is evaluated under
each concrete `i` — as the nested-rewrite already intended.

The guard cannot regress a working Gosper closed form: any summand it rejects has
an irrational term ratio and so was never Gosper-summable. All 64 existing
`sum_tests` still pass; three regressions were added
(`Sum[1/Sqrt[k^2+1], k]` stays held, the nested sqrt sum builds with the right
term count, and a nested finite radical sum evaluates to the correct value).

With the fix, the user's original nested-`Sum` objective runs end-to-end:
`NMinimize[{repulsion, constraints}, vars, Method -> {"RandomSearch",
"SearchPoints" -> 30}]` returns energy **32.7169** — the known Thomson N=10
minimum (32.716949…) — with all ten points on the unit sphere to 1e-7, in ~10 s.

## FindClusters accepts a visible NDArray

`FindClusters[NDArray[{1., 2., 10.}]]` clusters. It used to return unevaluated —
and that was documented behaviour rather than an oversight, so this is a
deliberate change with a test row rewritten to match.

The two array surfaces reach a builtin differently, which is the whole reason only
one of them was broken. The packing transparency gate (`src/eval.c`, step 2.7)
materialises a *packed* list for any head not on `src/pack.c`'s `AWARE` list, so
that surface always worked. It tests only `is_packed_list`, though, so a
**visible** `NDArray[...]` passed straight through to a builtin whose shape guard
is `is_listq` — which an `EXPR_NDARRAY` fails. Unevaluated, with no message.

Rank 1 is read as scalars and rank 2 as points, each giving the same partition as
the equivalent `List`. Rank 3 and above still decline: a list-valued component is
not a coordinate, and `fc_probe_shape` already rejected it.

It is a materialise guard, not a buffer fast path, and `FindClusters` stays off
`AWARE` — with an `EXEMPT` entry in `tools/check_packed_aware.py` recording why,
alongside `Cases` and `FlattenAt`, which are exempt for the same reason. Reading
the buffer directly would mean giving up what makes the answers exact: the
spanning tree orders rationals and bigints through `internal_subtract`, the
boundary set compares *elements* because `2^60` and `2^60 + 1` are distinct yet
project to the same double, and the clusters are emitted from the input elements
themselves. Opting in to `AWARE` would also stop the gate materialising a packed
list, which is exactly the plain `args[]` all of that needs.

No speed is given up either. Every value in an `NDArray` is machine by
construction, so `fc_all_machine` is true and the machine spanning-tree builder
runs — the same one a machine `List` takes, with the 20000-point ceiling from the
previous entry.

Ownership is handled by splitting the body into a helper that takes the data list
as a parameter. There are eighteen `return NULL` paths, and the materialised list
must outlive the cluster emission and be freed on all of them; one caller that
owns the temporary and one callee that only borrows it cannot leak or double-free.
