# Changelog: week of 2026-08-10 (Mon) – 2026-08-16 (Sun)

Feature additions and fixes recorded during this week.

## Quartic eigenvalues: biquadratic detection + Root[] default + inexact Root numericalization (2026-08-15)

Fixes an `NMinimize` of `Max[Re[Eigenvalues[matrix[c1, c2]]]]` over a 4×4 that
hung indefinitely (Mathematica: 0.2 s). Four connected changes.

**Biquadratic-after-depression quartics (root cause).** `Eigenvalues` of this
circulant-style matrix has a quartic characteristic polynomial whose *depressed*
form (`x -> x - b/4a`) is biquadratic — solvable in nested square roots. The
solver (`solve_quartic_radical` in `poly/solvepoly.c`) detected the biquadratic
case only with a **literal** zero test on the depressed linear coefficient `q`,
so a *symbolically*-zero `q` was missed and the general resolvent-cubic branch
ran instead: a 9205-leaf expression that was also **numerically wrong** (`q = 0`
forces resolvent root `t = 0`, i.e. `0/0` in `q/Sqrt[2t]`). The detection now
uses `zero_test_decide` (the polynomial-identity test), collapsing the result to
a compact 365-leaf nested radical that evaluates correctly by arithmetic —
`NMinimize` finishes in ~6 s. The parallel `Root`→radical solver
(`radical_quartic` in `radicals.c`) received the same fix.

**Cubics / Quartics default → False.** A *general* irreducible cubic/quartic
characteristic polynomial is now returned as held `Root[]` objects (matching
Mathematica and the spec) rather than explicit Cardano/Ferrari radicals. The
always-solvable families — binomials (`a x^n + b`), quadratic-in-`x^m`, and the
biquadratic-after-depression quartic above — are emitted in radical form
**regardless** of the option (the biquadratic quartic is now ungated in the
`solvepoly.c` dispatch; binomial / n-quadratic already fired before the gate).

**`Root[]` numericalization of inexact-coefficient polynomials.** `N[Root[p, k]]`
previously failed with `Root::nonint` when `p` had machine-real or rational
coefficients. `root_numeric.c` now extracts real coefficients and solves via the
shared companion-QR/canonical-sort/Newton pipeline (a `solve_root_core` refactor
common to the exact and inexact paths); the machine-precision request uses a
LAPACK `dgeev` companion and a graceful fallback to the sorted estimate when
Newton stalls on a clustered root. This keeps `N`, `NMinimize`, etc. working over
the general-quartic `Root[]` eigenvalues that the `False` default now produces.

**SVD** requests `Cubics -> True, Quartics -> True` internally, since its
symbolic pipeline manipulates eigenvalues with `Sqrt`/rational idioms and cannot
consume held `Root[]` objects.

## NMinimize: DifferentialEvolution options + Storn & Price population (2026-08-15)

Three fixes so every `"DifferentialEvolution"` sub-option behaves as documented,
plus a default-population change, driven by a 20-D rotated Rastrigin stress test.

**Default population = Storn & Price's 10n.** The DE population is now
`Clip[10·d, {15, 200}]` whether `"DifferentialEvolution"` is named explicitly or
selected via `Method -> Automatic`. The explicit form was previously clamped to
`[15, 40]`, starving high-dimensional problems (a 20-D solve ran 40 members where
DE's textbook default is 200). `Method -> Automatic` still scales the *generation*
budget with dimension (`150·d` vs. the explicit form's flat `100`); only the
population clamp was unified. `src/numerical_calculus/findmin.c` (`nm_de`).

**`"Tolerance"` now controls DE convergence.** It was parsed but consumed only by
NelderMead's simplex; DE's population-spread early-break used the
AccuracyGoal/PrecisionGoal-derived threshold and silently ignored the sub-option.
DE now uses an explicit `"Tolerance"` as its feasible-sub-population objective-spread
threshold, falling back to the derived default when unset (so seeded runs are
unchanged).

**`"InitialPoints"` now seeds the DE population.** It was consumed only by the
NelderMead simplex; DE always random-initialised. New helper
`nm_population_from_points` sets the leading population members from the list (each
a length-`d` real point, evaluated + numericalized, projected into the box, integer
coordinates rounded) and fills the rest at random; a malformed point ends the
seeding rather than aborting. When no list is given the RNG stream is byte-for-byte
what it was, so existing seeded runs reproduce.

**`"CrossProbability"` / `"ScalingFactor"` are validated.** They previously accepted
any value silently. `"CrossProbability"` must be a real in `[0, 1]` and
`"ScalingFactor"` a real in `(0, 2]`; an out-of-range or non-real value warns
(`NMinimize::sopt`) and falls back to the default, matching the SimulatedAnnealing
sub-options.

**Tests** (`tests/test_nminimize.c`): `test_rotated_rastrigin_stress` (the 20-D
rotated Rastrigin — QRDecomposition rotation, Table vars/constraints, held Sum over
a Dot, DE sub-options, `MaxIterations -> 3000`; a loose feasibility/shape/basin
invariant robust to cross-platform DE drift) and `test_de_options_effective`
(`"Tolerance"`, `"InitialPoints"`, `"CrossProbability"`, `"ScalingFactor"` each
demonstrably steer the search; invalid CR/F warn and fall back).

## Sum: finite-range short-circuit for large summands (2026-08-14)

Fixed a catastrophic slowdown when *building* an objective from a finite `Sum`
whose summand is a large expression — e.g. a rotated Rastrigin,
`Sum[z[[i]]^2 - 10 Cos[2 Pi z[[i]]], {i, 1, 20}]` with `z = q.vars`, where each
`z[[i]]` splices in the whole dotted 20-vector. The 20-D case took **minutes**
to build (the reported `NMinimize` "stress test" never returned); it is now
sub-millisecond, and the objective build scales linearly with size instead of
≈ size⁵.

Root cause: for a finite integer range `Sum` tried the closed-form cascade
(`Sum\`Polynomial` / `Geometric` / `Gosper` / `Rational` → `Cancel` /
`PolynomialGCD` / `Expand` / FLINT `mpoly`) **first**, and only fell through to
direct enumeration when it returned `NULL`. Those stages take the summand apart
symbolically, so their cost scales with *body size*, not term count. On a body
carrying a whole vector each stage churned over it and failed, then enumeration
did the right thing instantly. This was exactly the pathology already fixed for
*array* bodies (the 256×256 Game-of-Life grid, `SUM_ARRAY_EXPAND_MAX`); the
array guard just never covered a large *symbolic* body.

Fix (`src/sum/sum.c`): the array-specific `sum_body_names_array` /
`sum_body_is_array` (a syntactic pre-filter plus a probing evaluation) are
replaced by one helper, `sum_body_is_expensive`, that measures the body's node
count **as the cascade will see it** — capped at `SUM_BODY_CLOSED_FORM_MAX`
(48), charging each symbol the size of its `OwnValue` (so held `Part[z, i]` is
counted as the whole list `z`, not three nodes) and treating an NDArray subtree
as large. For a **short** range (`nterms ≤ SUM_ARRAY_EXPAND_MAX`, 256) with an
expensive body, the closed-form attempt is skipped and the range is enumerated
directly. Long ranges are unchanged (`Sum[i^2, {i,1,10^7}]` still closed-form in
~50 µs; constant-matrix `Sum[m, {i,1,10^5}]` still closed-form). Ordinary scalar
summands stay under the cap and on the closed-form-first path, so results are
byte-identical everywhere — only the path (hence speed) changes. The new helper
also never *evaluates* the body, so a plain scalar `Sum` is if anything slightly
cheaper than before (no probe). Regression test:
`tests/test_sum.c::check_large_body_sum_fast` (a 20-term large-body `Sum` under a
3 s ceiling). All `sum`/`series`/`iter`/`nsum`/`findmin` suites pass.

## NMinimize: Lennard-Jones cluster integration test (2026-08-14)

Added `tests/test_nminimize.c::test_lennard_jones_cluster` — an 18-D
global-optimization regression that drives the full indexed-variable +
`DifferentialEvolution` path in one call: `Subsets[Range[6], {2}]` enumerates the
15 atom pairs, the coordinates are indexed vars built with
`Table[{x[i], y[i], z[i]}, ...]` then `Flatten`'d to 18 scalars, a
`ljPair[{i_, j_}] := ...` helper supplies the softened pair potential
`1/r2^6 - 2/r2^3` (`r2` the squared distance with a `1e-8` floor), the box
constraints are generated by `Table[-3 <= v <= 3, {v, vars}]` iterating over the
*symbol list* `vars`, and DE's `"ScalingFactor" -> 0.7` sets the differential
weight `F`. The softened potential's global minimum is the octahedron at
`~ -12.712`; under the fixed default seed the search lands at `-12.3029` (a good
near-global basin). The assertion is deliberately loose — an 18-D DE trajectory
drifts across platforms in floating point (cf. `test_de_boundary_no_stagnation`),
so it checks that a compact low-energy cluster forms (`energy < -10`, far below
the `~0` of any scattered/sentinel configuration), that all 18 coordinates are
reported, and that the returned point is feasible inside the `+-3` box. No
behavior change; test-only. Full `nminimize_tests` suite passes.

## FindMinimum: compiled objective + exact compiled gradient (2026-08-14)

Follow-up to the NMinimize compiled-polish change: `FindMinimum` / `FindMaximum`
use a separate driver (`findmin_driver`) that did not compile anything, so all of
its objective and gradient evaluations ran through the interpreter. At
`MachinePrecision` it now lowers the objective **and each symbolic gradient
component** to bytecode over the variables (`compile_expr_ex`, after
`fm_bind_snapshot` so they compile as arguments) and evaluates them on the
register machine, via the same `g_fm_obj_*` objective registry plus a companion
`g_fm_grad_*` gradient registry that `fm_eval_gradient` consults (keyed by the
`g_exprs` array pointer + arity, so constraint gradients stay on the
interpreter). The gradient is the *same* `∂f/∂x_i`, only lowered — **not** finite
differences — so FindMinimum's precision is unchanged; measurement confirmed
byte-identical optima.

A quick value-only experiment showed compiling just the objective did nothing:
the QuasiNewton/CG/Newton cost is dominated by the per-iteration gradient, which
is why the gradient had to be compiled too. Measured (repeated calls, same
optima):

| Case | before | after |
|---|---:|---:|
| 1-D `Cos[x]+0.1 x^2` (Brent) | 0.0207 ms | 0.0073 ms (2.8×) |
| 1-D `Sin[x]Exp[-0.1x]+0.05x^2` | 0.0315 ms | 0.0101 ms (3.1×) |
| 2-D Rosenbrock | 0.266 ms | 0.066 ms (4.0×) |
| 6-D Rosenbrock | 1.756 ms | 0.925 ms (1.9×) |

The one loss is a trivial 2-D pure quadratic that converges in ~2 iterations,
where the fixed compile cost (~8 µs) is not amortised — already a sub-30 µs call.
A user-supplied `Gradient` is compiled the same way. Compilation is skipped when
an `EvaluationMonitor` is set (it fires from the interpreter, which the compiled
path bypasses) and on the MPFR (`WorkingPrecision > MachinePrecision`) path. New
allocations (the compiled programs) are freed on every exit; valgrind shows no
new leaks and the full `findmin_tests` suite passes, including Newton, CG,
constrained/penalty, user-gradient, and the evaluation monitor.

## NMinimize: compiled local polish (2026-08-14)

The machine-precision auto-compiled objective (`NmDriver.f_prog`) now drives the
**local polish** as well as the global-search scoring. Previously the polish
(`nm_local_polish` → `fm_run_bfgs`/`fm_run_penalty`) evaluated the objective
through the symbolic interpreter — deep-copying the tree, installing one
`OwnValue` per variable, evaluating, and numericalizing on **every** trial point.
`"RandomSearch"` runs one local solve per `SearchPoints`, so a 20-variable
`Sum[Abs[x[i]], {i, 1, 20}]` with `"SearchPoints" -> 1000` spent all its time
there: **24.8 s**. All other methods (DE, NelderMead, SA) polish too, so they were
hit in proportion.

Fix: `fm_eval_scalar` gains a compiled fast path — when it is handed the exact
objective expression registered for the current solve (pointer identity +
matching arity), it evaluates the compiled program (`compiled_eval_real`) instead
of the interpreter, falling back on a NULL/non-finite result. Constraint and
gradient sub-expressions are distinct `Expr*` and correctly stay on the
interpreter. The polish's gradient is taken by finite differences **off the
compiled objective** (the driver passes `g_exprs = NULL` when a program is
present), so `2n` compiled evaluations replace `n` interpreter evaluations that
each re-bind `n` `OwnValue`s. Pure speedup, interpreter fallback intact, answers
byte-identical.

Measured (20-D `Sum[Abs[x[i]]]`, box `[-10,10]`, same optimum `1.76e-5`):

| Method | before | after |
|---|---:|---:|
| `"RandomSearch"`, `"SearchPoints" -> 1000` | 24.8 s | 0.54 s |
| `"DifferentialEvolution"` | 0.98 s | 0.023 s |
| `"NelderMead"` | 0.59 s | 0.13 s |

The compiled program is now the single evaluation substrate across the whole
machine-precision optimizer. `FindMinimum` uses a separate driver that does not
yet compile its objective, so it is unchanged (the fast path is inert when no
program is registered); wiring it there is a clean follow-up. General (non-box)
constraints in the local penalty solver likewise still evaluate on the
interpreter. Tests: full `nminimize_tests` / `findmin_tests` suites pass;
`RandomSearch` returns the identical seeded optimum.

## NMinimize: disjunctive (`Or`) constraints (2026-08-14)

`NMinimize` / `NMaximize` now accept **disjunctive constraints** `c1 || c2 || ...`
(at the top level or nested inside an `And`), where a point is feasible if it
satisfies **at least one** branch. Previously any `Or` in the constraints emitted
`NMinimize::nimpl: disjunctive (Or) constraints are not yet supported` and left
the call unevaluated.

```
NMinimize[{(x^2+y-11)^2+(x+y^2-7)^2,
           (x-3)^2+(y-2)^2<=0.1 || (x+2.8)^2+(y+3.1)^2<=0.1},
          {x, y}, Method -> {"RandomSearch", "SearchPoints" -> 500}]
  ⇒ {~0, {x -> 3., y -> 2.}}        (* Himmelblau min, inside the first disk *)

NMinimize[{x^2, x <= -2 || x >= 2}, x]
  ⇒ {4., {x -> -2.}}                (* branch boundary, not the infeasible x = 0 *)
```

**How it works.** Each disjunction is scored by its **minimum-branch penalty** —
the least of the branches' squared-violation penalties, which is `0` exactly when
some branch is satisfied — added into the constraint-violation total that Deb's
feasibility rules already rank trial points by (`nm_eval_pen` → `fm_bool_penalty`,
a recursive `And`=Σ / `Or`=min / comparison=squared-violation evaluator). The
derivative-free global engines (DifferentialEvolution / SimulatedAnnealing /
NelderMead / RandomSearch) consume the non-smooth `min` directly.

The subtle part is the **local polish**. RandomSearch is pure multi-start local
polish with no global move, so if its polish ignores the disjunction it drives
every feasible start into the infeasible gap between branches and the whole run
reports `{Infinity, ...}`. The polish is therefore made disjunction-aware
(`nm_polish_gens`): at the start point it selects each disjunction's
currently-active (minimum-penalty) branch and folds that branch's comparisons
into the smooth quadratic-penalty BFGS solve, so the polish descends *within* the
feasible region the point already occupies. Constraint gradients for the polish
are taken by finite differences rather than symbolic `D[...]`, because the
optimisation variables carry transient value-bindings during the search (a
symbolic derivative taken there differentiates a constant and returns 0). The
post-polish Deb gate keeps the reported point feasible in all cases.

`FindMinimum`, whose gradient penalty method needs a smooth penalty, still rejects
`Or` with `FindMinimum::nimpl`.

Tests: `tests/test_nminimize.c::test_disjunctive_constraints` (Himmelblau two-disk,
the non-convex `x^2` over `x<=-2 || x>=2` under both the default engine and
RandomSearch, a box+disjunction combination, a boundary-optimum nearest-point
problem, and an `NMaximize` disjunction).

## NMinimize `"SimulatedAnnealing"`: adaptive temperature + coverage floor (2026-08-14)

`NMinimize[..., Method -> "SimulatedAnnealing"]` was returning a distinctly
shallower minimum than Mathematica on rugged, deceptive landscapes — on the 2-D
Eggholder `-(y+47) Sin[√|y+x/2+47|] - x Sin[√|x-(y+47)|]` over `[-512, 512]²` it
reported `-716.67`, against Mathematica's `-935.34` and the true global
`-959.64`.

Root cause: the Metropolis acceptance exponent was `-df/T` with a fixed
`T ∈ [1e-4, 1]`, while the objective ranges over hundreds. `Exp[-df/T]` was then
≈ 0 for every uphill move *even at the start temperature*, so the "anneal" was
really greedy descent from the start point — nothing but a fresh random restart
ever crossed a ridge into a deeper basin. That is why only cranking
`"SearchPoints"` up ever helped: each chain was a greedy local search, so you
needed many of them.

Two changes:

- **Adaptive temperature.** Each chain now measures the objective scale `s` from
  a short probe of trial steps at its start point (mean `|Δφ|`) and uses
  `-df/(T·s)` as the built-in exponent, so a move that worsens `φ` by one
  characteristic step is accepted with probability `e^{-1/T}` — a real anneal.
  The probe draws from its own PRNG, leaving the annealing walk's stream
  untouched, so a seeded `"SearchPoints" -> 1` chain follows exactly the
  trajectory it did before. A user `"BoltzmannExponent"` still overrides.
- **Coverage floor.** The automatic chain count went from `Min[2·d, 50]` to
  `Min[Max[2·d, 12], 50]`. At `d = 2` that is 12 rather than 4 independent
  starts; a rugged low-dimensional landscape has far more basins than 4 starts
  can cover. SA is opt-in (the automatic method is DifferentialEvolution), so
  only a caller who asked for SA pays the extra hundredths of a second.

Result at the default settings (2-D, `Timing` on an M-series):

| function | before | after | global |
|---|---:|---:|---:|
| Eggholder | `-716.67` | `-959.64` | `-959.64` |
| Schwefel  | `118.44`  | `2.5e-5`  | `0` |
| Rastrigin | `0`       | `0`       | `0` |
| Griewank  | `0`       | `0`       | `0` |
| Ackley / Booth / Rosenbrock / quadratic | global | global | global |

The Eggholder case now returns the global `-959.64` in ~0.021 s, below
Mathematica's default `-935.34` (~0.031 s). `tests/test_nminimize.c` and
`tests/test_findmin.c` (including `test_griewank_simulatedannealing`,
`test_sa_suboptions`, and the leak smoke tests) pass unchanged.

## NMinimize `"SimulatedAnnealing"`: `"LevelIterations"` sub-option (2026-08-14)

`Method -> {"SimulatedAnnealing", "LevelIterations" -> L, ...}` is now honored
rather than silently dropped. `"LevelIterations"` is the number of trial moves
spent at each temperature level, so a chain's iteration budget is
`MaxIterations · L`. This is a rename, not a new mechanism: the per-chain budget
was already `MaxIterations · 50`, and that hard-coded `50` was exactly the
implicit LevelIterations default — it is now the default value of the option, so
an unset `"LevelIterations"` reproduces the previous schedule bit-for-bit.

An explicit value is honored **verbatim**, past the automatic aggregate iteration
cap — consistent with `"SearchPoints"` — since the caller has asked for that
budget. A positive integer sets it; `Automatic`/`None` restore the default; an
invalid value warns `NMinimize::sopt` and falls back to Automatic. On a seeded
single chain with `"PostProcess" -> False`, the raw best deepens monotonically
with `L` (Eggholder: `-699` at `L = 2`, `-717` at `L = 200`), and wall time
scales with it (Eggholder default: `L = 50` → 0.019 s, `L = 100` → 0.030 s,
`L = 500` → 0.119 s). Covered by `test_sa_suboptions` in `tests/test_nminimize.c`.

## NMinimize: NelderMead per-restart polish + RandomSearch honors SearchPoints (2026-08-15)

Completes the "polish each independent start into its basin minimum and keep the
deepest" principle across all four multi-start engines (RandomSearch already did;
SimulatedAnnealing and DifferentialEvolution were done above).

- **NelderMead — per-restart basin polish.** `nm_neldermead` ranked its restarts
  by their raw simplex-converged vertices and polished only the single winner
  afterward — the same non-monotonicity fixed for SA and DE. Each restart's best
  vertex is now polished into its basin minimum *before* the restarts are ranked
  (gated by `"PostProcess" -> False`; a BFGS overshoot falls back to the raw
  vertex). The automatic default rises from a flat 4 restarts to `Min[2·d, 20]`.
  On Griewank-10 the default reaches `0.0148` (Mathematica `~0.175`) and 40
  restarts reach the global `0`; the result now improves with `"SearchPoints"`
  instead of being decided by the raw vertices.
- **NelderMead / RandomSearch — `"SearchPoints"` honored verbatim.** Both silently
  capped the option (NelderMead at 20, RandomSearch at 40), so a larger value was
  a no-op — RandomSearch returned the byte-identical 40-start result for
  `"SearchPoints" -> 40`, `300`, or `1000`, contradicting the documented "honored
  verbatim". An explicit value is now always run; the *automatic* defaults keep
  their runtime bound (RandomSearch `Clip[8·d, {4, 40}]` starts, unchanged, so no
  default-path slowdown).
- **RandomSearch is structurally limited on wide multimodal boxes** and this is
  documented, not a bug: pure multi-start local search has no global move, so on
  Griewank over `[-600, 600]` (central bowl `~10⁻¹¹` of the 10-D volume) no
  attainable start count reaches the optimum — it reports `~27` regardless.
  DifferentialEvolution / SimulatedAnnealing are the engines for that shape. On a
  reachable box (narrow Griewank) RandomSearch is monotonic: 200 starts (`0.0074`)
  beat 10 (`0.032`), which the silent cap had made impossible.
- **Regression tests** `test_griewank_neldermead` (default `< 0.1`, 40 restarts
  `< 0.01`) and `test_randomsearch_searchpoints_verbatim` (200 starts beat 10 on a
  reachable box) added. Bukin-6 is unaffected (`0.0113679`, within `10⁻⁶` of the
  Mathematica-matched value).

## NMinimize: DifferentialEvolution multi-start basin polish (2026-08-15)

- **The default `"DifferentialEvolution"` now reaches a deeper minimum on
  multimodal problems and no longer degrades as `"SearchPoints"` grows** — the
  same non-monotonicity the SimulatedAnnealing per-chain polish removed, now
  fixed for DE. On Griewank-10 over `[-600, 600]^10`, `Method ->
  "DifferentialEvolution"` drops **0.0442535 → 0.0** (the global minimum),
  beating Mathematica's `0.174985`; `"SearchPoints" -> 100` drops **0.196657 →
  0.0172263** (was *worse* than the default 40-member population).
- **Change in `nm_de`:** on a continuous problem the post-search local polish is
  now a **multi-start over the final population** rather than a single refinement
  of the global best. The best `Min[2·d, 50]` *distinct* members (deduplicated by
  basin — agreement to `10⁻³` of the search span on every coordinate) are each
  polished into their basin minimum and the deepest is kept. Polishing only the
  single best strands DE in whichever basin that member occupied; a larger or
  less-converged population leaves the best member in a shallower basin than
  others hold, so ranking basins by their *minima* — not by the raw fitness of
  the member that found them — is what makes the optimum improve with
  `"SearchPoints"`.
- **Scope and cost.** Gated by `"PostProcess" -> False` (then the raw global best
  is carried through unchanged) and confined to continuous problems: a
  mixed-integer run keeps its single driver polish, so its integer-descent cost
  is unaffected. The polish uses no PRNG draws, so DE's evolution is byte-for-byte
  the same; only the returned continuous optimum can move to a deeper basin.
- **`Method -> Automatic` is unchanged in value** (`~0.0369` on Griewank-10): its
  `150·d`-generation budget converges the population into a single basin before
  the polish runs, so there are no distinct basins to exploit — still well below
  Mathematica.
- **Regression test** `test_griewank_differentialevolution` added: the default and
  `"SearchPoints" -> 100` both reach `< 0.1`, locking in the improvement and the
  restored monotonicity.

## NMinimize: SimulatedAnnealing multi-chain default + per-chain polish (2026-08-15)

- **The default `"SimulatedAnnealing"` now returns a much deeper minimum on
  multimodal problems, beating Mathematica on Griewank-10.** On
  `Sum[x[i]²/4000] - Product[Cos[x[i]/√i]] + 1` over `[-600, 600]^10`
  (`"PerturbationScale" -> 2.0`) the reported optimum drops from **0.307674** to
  **0.0147724** — a 10× improvement over Mathematica's `0.174985` on the same
  problem, and in ~0.29 s versus Mathematica's ~1.9 s.
- **Two coupled changes in `nm_sa`:**
  - **Default `"SearchPoints"` is now `Automatic = Min[2 n, 50]`** (was a single
    chain), matching Mathematica's SimulatedAnnealing default. A single annealing
    walk lands in a basin close to by luck; `Min[2 n, 50]` independent chains
    from random starts explore the landscape properly.
  - **Each chain's best raw point is polished into its basin minimum before the
    chains are ranked** (as `"RandomSearch"` already does per restart), then the
    global best of those local minima is kept. Ranking chains by their local
    minima rather than by their random-walk lows is what makes the reported
    optimum *improve* monotonically with `"SearchPoints"` — previously the lowest
    raw point often sat in a shallower basin than a slightly higher point above a
    deeper one, so more search points could return a *worse* answer (SP 5 →
    0.148 but SP 50 → 0.376). Now: SP 1 → 0.308, SP 5 → 0.148, SP 20 → 0.015,
    SP 50 → ~10⁻¹⁶ (the global 0).
- **Honors `"PostProcess" -> False`/`None`**: the per-chain polish is skipped,
  and the per-chain-best tracking then reduces to the global raw best over the
  same PRNG sequence — bit-for-bit the previous raw-best result.
- **`"SearchPoints" -> 1` is unchanged**: one chain anneals over the identical
  PRNG sequence and its best is polished, which is exactly what the driver's
  post-process produced before, so a seeded single-chain run is unaffected.
- **Regression test** `test_griewank_simulatedannealing` updated to lock in the
  new default (`0 <= First[r] < 0.1`, was `0.1 < First[r] < 1.0`).

## NMinimize: SimulatedAnnealing sub-options now honored (2026-08-14)

- **Bug fixed: the `"SimulatedAnnealing"` engine ignored its whole config.**
  `nm_sa` did `(void)nc`, so `"SearchPoints"` had no effect, and the parser
  silently dropped `"PerturbationScale"` and `"BoltzmannExponent"` entirely.
  All three now take effect:
  - **`"SearchPoints" -> K`** runs `K` independent annealing chains from random
    starts and keeps the global best (default 1). A bounded aggregate iteration
    budget is shared across the chains (`NM_SA_TOTAL_CAP`), so a large `K`
    (e.g. 50) stays fast. On a rugged multimodal surface more restarts reach a
    markedly better raw point (e.g. `x²+y²+10 Sin[3x]²+10 Sin[3y]²`: single
    chain → 1.08, 30 chains → 1.2·10⁻⁴).
  - **`"PerturbationScale" -> s`** multiplies the trial-step size (default 1.0):
    a small scale keeps the walk local, a large one explores more widely. A
    non-positive/non-real value warns (`NMinimize::sopt`) and falls back to 1.0.
  - **`"BoltzmannExponent" -> f`** replaces the Metropolis acceptance exponent
    for an uphill move — the point is accepted with probability
    `Exp[f[i, df, f0]]` (1-based iteration `i`, objective increase `df`, current
    value `f0`). `Automatic`/`None` keep the built-in geometric-cooling exponent
    `-df/T`; an invalid value warns (`NMinimize::bexp`) and falls back to
    Automatic. Evaluated with numeric diagnostics muted, mirroring
    `"PenaltyFunction"`.
- **The default single-chain, default-option path is bit-for-bit unchanged** —
  scale 1.0 is an exact multiply and the PRNG is drawn in the same order — so a
  seeded run without these options gives the identical result to before.
- **Regression tests (Griewank-10).** On the strongly-multimodal Griewank
  function over `[-600, 600]^10`, SimulatedAnnealing settles into a nonzero
  local minimum rather than the global 0, exactly as Mathematica does; the
  default single-chain schedule lands at ~0.234 — the same value Mathematica
  reports. Added `test_sa_suboptions` (each option honored + invalid-value
  fallback) and `test_griewank_simulatedannealing` (the Mathematica-reported
  all-options invocation is parsed, applied, and returns a finite feasible
  minimum) to `tests/test_nminimize.c`.

## NMinimize/NMaximize: no longer HoldAll — option values now resolve (2026-08-14)

- **Attribute correction.** `NMinimize` and `NMaximize` are now `Protected` only,
  **not** `HoldAll` — matching Mathematica, whose `Attributes[NMinimize]` is
  `{Protected}`. (`FindMinimum`/`FindMaximum` stay `{HoldAll, Protected}`: their
  `{x, x0}` specs pair a variable with an initial value that must not evaluate.)
- **Bug fixed: held option values were silently dropped.** Because the arguments
  were held, a `Method` sub-option whose value was a symbol or expression rather
  than a literal — e.g. `"RandomSeed" -> s` with `s` a `Do`/`Table` iterator,
  `"SearchPoints" -> 2 d`, `MaxIterations -> it` bound in a `With`/`Module`, or
  even `"RandomSeed" -> 2 + 40` — reached the literal-only option readers
  unevaluated and was quietly ignored, so the run fell back to the default seed /
  population. A sweep like `Do[NMinimize[…, "RandomSeed" -> s], {s, {…}}]`
  produced the *same* result for every `s`. With the arguments no longer held,
  option values evaluate normally and resolve, so each seed now yields its own
  result (identical to passing the seed as a literal). This resolves the whole
  class, not just `RandomSeed`.
- **Consequence (also matching Mathematica).** Because the objective and variable
  spec now evaluate before the call, an optimization variable that already carries
  a value resolves first, the variable specification is then malformed, and the
  call returns unevaluated with `NMinimize::ivar` — exactly as in Mathematica.
  Optimization variables must be unbound symbols. Variable *locality* during the
  search is unchanged: the Block-style snapshot/restore of each variable's
  OwnValue still guarantees an unbound variable is never left modified.
- The variable-spec parser, indexed-variable synth-symbol rewrite, `{f, cons}`
  splitting, and constraint expansion are unchanged — a pre-evaluated
  `Table[x[i], …]`/`Array[x, n]` arrives already expanded to the list the parser
  already accepted. Tests renamed/strengthened (`test_variable_locality`,
  `test_indexed_variable_locality`) to assert the no-leak guarantee and the new
  unevaluated-on-assigned-variable behavior; all 39 NMinimize/NMaximize tests pass.

## NMinimize: dimension-scaled default (Automatic) DifferentialEvolution budget (2026-08-14)

- **Stronger default global search on hard multimodal problems.** `Method ->
  Automatic` (i.e. plain `NMinimize` / `NMaximize` with no `Method`) now runs DE
  with a *dimension-scaled* budget — population `Clip[10·d, {15, 200}]` and
  `150·d` generations — instead of the flat `Clip[10·d, {15, 40}]` / `100` that
  the DE engine has always used. The flat budget was drastically under-powered for
  `d ≥ 5`: on the 10-D Michalewicz function
  `NMinimize[{-Sum[Sin[x[i]] (Sin[i x[i]^2/Pi])^20, {i,1,10}],
  Table[0<=x[i]<=Pi,{i,1,10}]}, Table[x[i],{i,1,10}]]` the default returned only
  `-6.93335`; it now returns `-9.66015` (the true global minimum, better than
  Mathematica 14's default `-9.04592`) in ~0.63 s — matching Mathematica's speed
  and beating its quality, robustly across seeds (`-9.40 … -9.66`).
- **Free on easy problems.** The budget increase is gated by the DE convergence
  early-break: a run stops as soon as its feasible sub-population collapses to the
  accuracy/precision tolerance, so low-dimensional and convex problems finish in
  the same wall-clock as before (100 low-D solves: ~0.03 s, unchanged) with
  identical results. `d ≤ 4` is unaffected (`10·d ≤ 40`).
- **Explicit DifferentialEvolution is untouched.** The enhanced budget is keyed on
  `nc.method == NM_AUTO` (`src/findmin.c`, `nm_de`); naming
  `Method -> "DifferentialEvolution"` — or supplying `SearchPoints` /
  `MaxIterations` — keeps the flat budget, so a seeded run reproduces bit-for-bit
  (the reference `RandomSeed -> 42, CrossProbability -> 0.75` case still returns
  `-8.65041` at the identical point). Implemented via a new `FmOpts.max_iter_set`
  flag so an explicit `MaxIterations` under `Automatic` is still honored verbatim.

## NMinimize: multi-variable `Element` domains + out-of-region rescue (2026-08-14)

- **Multi-variable integer/real domain declarations.** `NMinimize` /
  `NMaximize` now accept a domain declaration that names several variables at
  once — `Element[x | y, Integers]` (an `Alternatives`) and
  `Element[{x, y}, Integers]` (a `List`) — in addition to the single-symbol
  `Element[x, Integers]`. Previously only a bare symbol was recognised, so the
  common `Element[x1 | x2, Integers]` spelling emitted
  `NMinimize::nimpl: Element / domain constraints are not yet supported` and the
  whole call returned unevaluated. `nm_filter_int` (`src/findmin.c`) now expands
  the `Alternatives`/`List` operand and marks each named optimization variable
  integer (or accepts `Reals`); a declaration on a symbol that is not one of the
  variables is left in place and rejected downstream, unchanged. The pressure-
  vessel MINLP from the report,
  `NMinimize[{0.6224 x1 x3 x4 + …, … && Element[x1|x2, Integers]}, {x1,x2,x3,x4}, …]`,
  now parses and — with the standard variable bounds — solves to `8796.86` at
  `x1 = x2 = 1` (integer), `x3 ≈ 51.81`, `x4 ≈ 84.59`.
- **Mixed-integer continuous-relaxation polish.** A mixed-integer problem whose
  feasible region lies outside the default `±10` DE sampling span was previously
  invisible to the region-confined integer coordinate descent and reported
  infeasible. `nm_local_polish` now adds a relaxation recovery step (new
  `nm_continuous_solve`): solve the continuous relaxation (integers relaxed,
  every coordinate free of the sampling region) to find the basin, round the
  integers, then refine the continuous coordinates with the integers pinned
  (a degenerate `[v,v]` box; `fm_line_search` projects each trial, so the value
  stays fixed). The result is adopted only when it is a Deb-improvement, so it
  can never worsen the region-descent answer. E.g.
  `NMinimize[{(x-15)^2 + (y-3)^2, Element[y, Integers]}, {x, y}]` now recovers
  the optimum at `(15, 3)` (value `0`) even though `x = 15` sits far outside the
  sampling box. Problems that are genuinely unbounded below, or whose feasible
  region the relaxation does not locate, still return `{Infinity, …}`; explicit
  variable bounds make them solvable.
- **Adaptive search-region expansion.** When the default `±10` DE sampling
  region contains no feasible point, the fully-unbounded coordinates are now
  grown by successive powers of ten (up to `±10^5`) and the search is retried,
  so a feasible region whose location is implied by nonlinear constraints
  rather than stated as variable bounds is found instead of reporting
  `{Infinity, …}`. Only fully-unbounded coordinates grow — a coordinate with a
  box bound or a starting-interval hint keeps its resolved region — and the
  first attempt is the base region with the base seed, so a problem already
  feasible there is solved identically to before; expansion triggers only to
  rescue infeasibility and stops at the smallest region that yields
  feasibility (`nm_minimize_driver`, guarded by `NM_MAX_REGION_EXPAND`). E.g.
  `NMinimize[{(x-50)^2 + (y-40)^2, x + y >= 80}, {x, y}]`, whose feasible set
  lies wholly outside `±10`, now returns the optimum `(50, 40)`; a genuinely
  infeasible problem (`x^2 + 1 <= 0`) still returns `{Infinity, …}`. The
  pressure-vessel MINLP from the report now returns a feasible point rather
  than `Infinity` — though, lacking the standard non-negativity bounds, that
  formulation is unbounded below (its true global minimum is a large-negative
  non-physical point), so the physical optimum still needs the benchmark's
  variable bounds.
- Tests: `test_integer_domain_alternatives`, `test_integer_domain_list`,
  `test_region_expansion_rescue`, `test_mixed_integer_outside_region` in
  `tests/test_nminimize.c`. Full `nminimize_tests` and `findmin_tests` suites
  pass.

## NMinimize DifferentialEvolution: bounce-back boundary handling (2026-08-14)

- Fixed **boundary stagnation** in the `"DifferentialEvolution"` engine
  (`nm_de`, `src/findmin.c`). A mutant that overshot a box bound was *clamped*
  to the bound; once several population members shared the exact boundary value
  for a coordinate, their pairwise mutation differentials for that coordinate
  collapsed to zero and it froze on the wall for the rest of the run.
- The reported failure was the 10-D Schwefel function (global optimum at
  `x_i = 420.97`, interior to `[-500, 500]`): the search returned `1758.88`
  with five coordinates pinned to `±500`, worse than Mathematica's `1221.25`.
- Replaced clamping with **bounce-back reinitialisation** (Price, Storn &
  Lampinen 2005): an out-of-range component is redrawn at random between the
  base vector and the violated bound — feasible, but almost never exactly on
  the boundary, so the population keeps its diversity. The same case now solves
  to `~963` (default seed) with no coordinate on the boundary, and no seed in a
  7-seed sweep parks a coordinate at `±500`. Only out-of-range mutants are
  affected, so interior-optimum problems (the existing test suite) are
  unchanged.

## NMinimize / NMaximize: numerical global optimization (2026-08-14)

- New builtins `NMinimize` / `NMaximize` (`HoldAll, Protected`) in
  `src/findmin.c`, layered on the existing `FindMinimum` machinery — same
  `Block`-style variable binding, `{f, cons}` constraint parsing (boxes +
  general `FmGenCon[]`), penalty/BFGS local solvers, MPFR path, and result
  builders — with a new stochastic **global** search on top.
- Four methods, `Method -> Automatic` picks `"DifferentialEvolution"`:
  `"DifferentialEvolution"` (DE/rand/1/bin, the default engine),
  `"NelderMead"` (restarted downhill simplex), `"RandomSearch"` (multistart +
  local polish), `"SimulatedAnnealing"`. A method may carry sub-options
  `{"Name", "SearchPoints" -> n, "ScalingFactor" -> F, "CrossProbability" ->
  cr, "RandomSeed" -> s}`. The PRNG is a deterministic SplitMix64 with a fixed
  default seed, so results are reproducible.
- Constraints use **Deb's feasibility rules** during the global search (no
  penalty-weight tuning) and the quadratic-penalty local solver during the
  final polish. Supports `==`, `<`, `<=`, `>`, `>=`, chained inequalities, and
  their `And` combinations; the first argument may be `{f, cons}` or
  `{f, c1, c2, ...}` (extra elements implicitly `And`-ed, matching
  Mathematica). Scalar integer domains via `Element[x, Integers]` are searched
  on the lattice and returned as exact integers. An empty feasible set returns
  `{Infinity, {x -> Indeterminate, ...}}`.
- `WorkingPrecision > MachinePrecision` refines continuous,
  general-constraint-free problems in MPFR (via `fm_run_bfgs_mpfr`); other
  cases warn and fall back to machine precision, matching `FindMinimum`.
  Options `Method / WorkingPrecision / MaxIterations / AccuracyGoal /
  PrecisionGoal / EvaluationMonitor / StepMonitor` are honoured and registered
  as `Options[NMinimize]` / `Options[NMaximize]`; internal local-solver
  diagnostics are muted during the global search so a successful solve is
  silent.
- Symbols interned (`SYM_NMinimize` / `SYM_NMaximize`), docstrings in
  `info.c`, docs in `docs/spec/builtins/calculus.md`, tests in
  `tests/test_nminimize.c` (29 cases: shape, unconstrained, all constraint
  kinds, integer/mixed-integer, infeasibility, every method, `NMaximize`
  duality, options, `WorkingPrecision`, `HoldAll` locality, memory smoke).
  Valgrind-clean (identical to the `Sin[1.0]` baseline); `make check-c99`
  passes; no `FindMinimum` regression.

### Indexed variables + held Table/Array specs (2026-08-14)

- `NMinimize` / `NMaximize` now accept **indexed variables** `x[i]` and held
  variable/constraint *generators*. Because both arguments are `HoldAll`, a
  spec such as `Table[x[i], {i, 1, n}]` or `Array[x, n]` previously reached the
  parser unevaluated and was rejected with `NMinimize::ivar`. The driver now
  evaluates the variable spec once (with the variable head `Block`-localized so
  it stays symbolic), and — when the constraint argument is a wrapper such as
  `Table[...]` rather than an already-relational tree — expands it the same way
  and treats the resulting list as an implicit `And` (dropping `True` entries;
  a `False` entry marks the system infeasible).
- Indexed variables are rewritten to fresh scalar symbols (`NMinimize$k`,
  removed after the solve) by a structural substitution over the *evaluated*
  objective/constraints, so the entire symbol-keyed solver — binding, gradient,
  box/general constraint collection, MPFR refinement — applies unchanged; the
  result `Rule`s are mapped back to the original `x[i]`. Plain-symbol problems
  and already-relational constraints keep their exact previous code path (no
  evaluation, no rewrite).
- This makes the standard `n`-dimensional benchmarks express directly, e.g. the
  10-D Rosenbrock valley
  `NMinimize[{Sum[100 (x[i+1]-x[i]^2)^2+(1-x[i])^2, {i,1,9}], Table[-5<=x[i]<=5, {i,1,10}]}, Table[x[i], {i,1,10}]]`

- New helpers in `src/findmin.c`: `nm_subst` (structural substitution),
  `nm_fresh_symbol`, `nm_heads_localize`/`nm_heads_restore` (Block-localize the
  variable heads while expanding a held spec), `nm_is_var_atom`,
  `nm_is_constraint_tree`; `nm_one_var`/`nm_parse_vars` extended to accept
  indexed atoms. Six new cases in `tests/test_nminimize.c` (Table/Array/literal
  indexed vars, Table constraints, the reported 10-D Rosenbrock, indexed
  `HoldAll` locality). Valgrind leak totals identical to baseline; synthetic
  symbols leave no residue (`Names["NMinimize$*"]` is `{}`); `make check-c99`
  passes; no `FindMinimum`/`NMinimize` regression.

### NelderMead `InitialPoints` + flat-plateau convergence fix (2026-08-14)

- **`"InitialPoints"` sub-option.** `Method -> {"NelderMead", "InitialPoints" ->
  {{x1,...}, ...}}` now seeds the initial simplex (`NmConfig.init_points`, parsed
  in `nm_parse_method`, consumed by new `nm_simplex_from_points` for restart 0;
  later restarts stay random). Each seed point is evaluated + numericalized (so

  to a random start. It was previously parsed-and-ignored.
- **Flat-plateau convergence fix.** NelderMead's termination required only a
  small objective spread `|f_hi - f_lo|`, which is ≈0 across any flat region — so

  moved. It now *also* requires the simplex to be geometrically small (max vertex
  coordinate spread ≤ `1e-6 ×` region extent) before stopping, so a plateau
  simplex keeps contracting toward its centroid.

### NMinimize resolves a problem/variable spec given via a bound symbol (2026-08-14)

- `NMinimize`/`NMaximize` are `HoldAll`, and the driver split `{f, cons}` and
  parsed the variable spec on the *held* first two arguments. So the common
  pattern `prob = {f, cons}; vars = Table[x[i], …]; NMinimize[prob, vars]`
  silently failed: the objective symbol `prob` (never a `List` head) was scored
  as a non-numeric objective and returned the infeasible sentinel
  (`{Infinity, {…->Indeterminate}}` / `1e+300` internally), and a variable-list
  symbol `vars` was parsed as one opaque variable keyed by the whole list
  (`{{x, y} -> …}`). Mathematica resolves both. A bare *scalar* objective symbol
  already worked (it is evaluated per point), which masked the list case.
- Fixed by resolving held symbol indirection before the structural split:
  - **Objective/problem** — the variable spec is now parsed first (it does not
    depend on the objective), and a bare-symbol first argument is then evaluated
    *once with the variable heads localized* (reusing `nm_heads_localize` /
    `nm_heads_restore`), so `prob → {f, cons}` is exposed without capturing any
    global variable values. An inline list/expression is unchanged. The resolved
    tree is owned (`f_eval`) and freed on every exit path.
  - **Variable spec** — a bare symbol is resolved: if it evaluates to a
    `List`/`Element` that is used; if it is unbound (evaluates to itself) or
    resolves to a non-spec it stays a single optimization variable, so
    `NMinimize[f, x]` is unaffected while `vars = {x, y}; NMinimize[f, vars]`
    now expands to the two variables.
- The resolved-symbol objective reaches the same machine auto-compile path as
  the inline form (measured: the 20-D Rastrigin via `prob`/`vars` symbols runs
  in ~0.03–0.37 s like the inline call, versus ~6 s on the interpreter before
  this landed), and the full result is byte-identical to the inline form
  (`{111.435, {x[1] -> 0.994959, …}}` — which also matches Mathematica exactly
  for that DE configuration).
- Verified: new `test_symbol_indirection` in `tests/test_nminimize.c` (objective
  via symbol, variable list via symbol, both, an indexed problem via symbols, and
  the unbound-single-variable case). Valgrind totals unchanged (`13,440/420`,
  macOS baseline — the reorder and `f_eval` leak nothing); `make check-c99`
  passes; `nminimize_tests` and `findmin_tests` green.

## Inexact contagion no longer numericalizes a non-numeric head's arguments (2026-08-14)

- **Bug.** `0.333 x[1]` evaluated to `Times[0.333, x[1.0]]` — the real
  coefficient numericalized the *index* `1` inside `x[1]`. `Plus`/`Times`
  inexact contagion (`src/numeric.c`, `numeric_contagion_args`) numericalized
  every exact sibling with the full `N` recursion, which threads into the
  arguments of *any* head, including a non-numeric one like `x`.
- **Symptom.** `NMinimize` with an indexed objective carrying a real
  coefficient — e.g. the 10-D Ackley function
  `-20 Exp[-0.2 Sqrt[1/10 Sum[x[i]^2, {i,1,10}]]] - Exp[1/10 Sum[Cos[2 Pi x[i]],
  {i,1,10}]] + 20 + E` — returned the infeasible `1e+300` sentinel. The held
  objective is expanded once (heads localized) before its indexed variables are
  substituted; contagion rewrote `x[i]` to `x[i.]`, the substitution then failed
  to match, and an unbound `x[1.]` survived into the compiled body so every
  trial point scored non-numeric.
- **Fix.** `NumericSpec` gains a `contagion` flag, set only by
  `numeric_contagion_args`. When set, `numericalize_function` returns a
  non-numeric-headed subexpression (`x[1]`, `f[a]`, `Abs[x[3]]`, …) unchanged
  instead of threading `N` into its arguments. Numeric heads (`Plus`, `Times`,
  `Power`, `Sin`, …) still recurse, so a coefficient reached through them is
  numericalized as before: `1. + 2 x` → `1. + 2. x`, `1. + Sin[2]` → `1.9093`.
  Explicit `N[]` leaves the flag false and threads everywhere, so
  `N[x[1]] == x[1.]` — matching Mathematica, which distinguishes arithmetic
  contagion from an explicit `N`.
- **Result.** `0.333 x[1]` → `0.333 x[1]`; the Ackley `NMinimize` now converges
  to the true global minimum (~0 at the origin) rather than a sentinel.
- Verified: `test_inexact_contagion` (`tests/test_numeric.c`) gains the
  non-numeric-head cases; `test_indexed_real_coefficient`
  (`tests/test_nminimize.c`) runs 3-D Ackley to ~0. Valgrind unchanged
  (`13,440/420`, macOS baseline); `make check-c99` passes; `numeric_tests`,
  `nminimize_tests`, and `findmin_tests` green.

## FindRoot on systems: skip the structurally-zero Jacobian entries (2026-08-13)

- `fr_run_newton_system_real` (`src/numerical_roots/findroot.c`) derived, compiled
  and evaluated the full `n²` Jacobian `D[f_i, x_j]`. For a sparse system — a
  tridiagonal Broyden field has 3 non-zeros per row, not `n` — that is almost all
  wasted work. A `jz[i*n+j]` mask now flags the entries that come back a literal
  `0`; those are never compiled and their per-iteration evaluation is replaced by a
  direct `J = 0`, so the cost is O(nnz) rather than O(n²). `benchmarks/58` Broyden
  tridiagonal **N=40: 12.8× → 3.6×** (27 ms → 7 ms), N=10 also faster; roots still
  agree (0 CHECK-FAIL), `findroot_tests`/`nsolve_tests`/`nsolve_stress_tests` pass.

  entries; a Broyden rank-1 quasi-Newton update would be the next lever there.)

## Eigenproblems: route the standard machine kernels to LAPACK (2026-08-13)

  hand-rolled Householder/QR. The real symmetric path now calls LAPACK `dsyev`

  Eigenvectors symmetric 250×250 **7× → 4.0×**, Eigenvalues general 300×300

  eigenvalue/eigenvector Lists), shared with the packed-result follow-up. The
  complex Hermitian/general machine kernels (no benchmark-54 coverage) still use
  the working hand-rolled path.

## Evaluator: memoize the structural hash on each Expr node (2026-08-11)

Investigating whether the symbol table or `expr_hash` contributes to the
systemic per-node evaluator constant (`MATHILDA_EVALUATOR_PERFORMANCE.md`): the
symbol table does **not** — name→definition resolution is already an O(1)
cached-pointer read on each node (`data.symbol.def`). But `expr_hash`
(`src/expr.c`) was FNV-1a **recomputed by walking the whole subtree on every
call**, and it is called per-element in `Plus`/`Times` like-term grouping,
Association key indexing (`assoc_index.c`), and the set ops
(`Union`/`DeleteDuplicates`/`Tally`, `list/setops.c`).

- **New field `Expr.hash_cache`** (`src/expr.h`): a lazily-filled memo of
  `expr_hash(node)`, sentinel `0` = unhashed (a genuine hash of 0 just recomputes
  — harmless). Filled on first `expr_hash`, reused thereafter; the recursion
  memoizes the whole subtree bottom-up. Zero-initialised in the single allocator
  `expr_alloc_node`, so every constructor and the `expr_unshare` copy start clean.
- **Invalidation contract** — `expr_invalidate_hash(e)` (inline in `expr.h`) is
  called at every in-place structural mutation of a live node: `eval_flatten_args`
  (Flat), `flatten_sequences`, the generic Orderless `qsort`
  (`src/eval.c`), and the pattern alpha-rename (`src/symtab.c`). The cache is
  benign metadata (ignored by `expr_eq`/`expr_compare`), like `symbol.def`.
- **`MATHILDA_HASH_VERIFY` build** (define-gated in `expr.c`): ignores the cache,
  recomputes every hash, and `abort()`s if a surviving cache value disagrees —
  turning any missed invalidation into a deterministic failure. Ran clean over a
  broad stress corpus, all seven `benchmarks/4x-eval-*`, and ten hash-relevant
  unit suites (`association`, `packed_list`, `sort`, `complement`,
  `intersection`, `mapat`, `replaceat`, `flatten_at`, `array_flatten`,
  `compile_assoc`).

Result: hashing the same subtree repeatedly (Association lookups, dedup/`Tally`
of repeated structural elements, re-grouping a stable sum) drops from
O(subtree) per touch to O(1). Measured up to **~14× faster** on dedup/`Tally` of
a list of repeated deep nodes (4.07→0.30 ms) with no change to results. No new
allocation (inline field), so valgrind is unchanged at the macOS baseline; full
`ctest` shows no new failures (the 6 failing suites — `zero_test`, SVD/eigen/
lapack SEGFAULTs, `partitionsq` timeout — are the documented pre-existing set).
The packed-list ⇄ materialised-`List` hash byte-identity (`test_packed_list.c`)
still holds. Docs: `MATHILDA_EVALUATOR_PERFORMANCE.md`.

## Matcher: `Condition` over a multi-element sequence blank (2026-08-11)

Fixed a conformance bug: a `Condition` wrapping a sequence blank —
`x__ /; test`, `x___ /; test`, and the named/nested/double-named forms
(`c : (b__ /; t)`, `b___ /; c1 /; c2`) — matched **only when the sequence
spanned exactly one element**. For zero or ≥2 elements it failed even with a
literal `True` guard, so the extremely common idiom
`MatchQ[{5, 10}, {b__ /; Total[{b}] == 15}]` returned `False` (WL: `True`).

Root cause in `src/match.c`: `match_args_internal` peels `Pattern`,
`Shortest`, `Longest`, `Optional` and strips `PatternTest` for sequence blanks,
but never handled `Condition[seqblank, guard]`; it fell through to the
single-element path (`min_k = max_k = 1`), so only the width-1 case — which a
`BlankSequence` also matches — slipped through. Fix mirrors the `PatternTest`
handling: strip the `Condition` layer(s) when the inner pattern is a sequence
blank / `Repeated`, remember the guard chain, and evaluate it once (via the new
`eval_seq_conditions`, inner `/;` first) at each commit point after the sequence
variable is bound. Untouched when the inner pattern is a single blank, so the
well-tested `x_ /; test` path is unchanged. `PatternTest` over a sequence and
`Condition` over a single element both already worked and still do.

Regression cases added as section 37 of `tests/match_stress_corpus.m`
(287 → 298 cases, all green). Enumeration counts cross-checked against an
independent brute-force partition enumerator.

## Matcher: fix per-guard-evaluation memory leak (2026-08-11)

Fixed a pre-existing leak in `guard_all_true` (`src/match.c`): the guard leaf
was evaluated as `evaluate(expr_copy(g))` with the `expr_copy(g)` temporary
inlined. `evaluate()` **borrows** its argument (it copies internally), so that
temporary was never freed — one orphaned `Expr` node per guard leaf that did not
evaluate to the literal `True`. Because most backtracking attempts have a
**failing** guard, this leaked ~1 node per *failed* condition check across the
whole system (every `/;` in matching, `Cases`, `ReplaceAll`, conditional
`DownValues`, …). Now the copy is held in a variable and freed. Under valgrind,
a 75,327-guard-evaluation run drops from 75,058 leaked blocks to the constant
macOS startup baseline (422 blocks); named-sequence + `Cases` workloads that lost
332 KB now lose nothing beyond baseline. No result changed — this is purely an
ownership fix.

`MATHILDA_PATTERN_MATCHER_PERFORMANCE.md` (repo root) gains **Case M**, a scaling
study of the equal-sum contiguous-partition family that surfaced both fixes. It is
a head-to-head against Mathematica 14.0 (`wolframscript`) on identical inputs: the
pattern is genuinely exponential *in Mathematica* (the reader's verbatim pattern
takes 6.75 s at N=20; a distinct-block variant 38 s at N=120), but Mathilda's
matcher prunes it to polynomial/constant cost — 100× to 135,000× faster with
identical match counts. The PDF is regenerated with `pandoc --pdf-engine=xelatex`.

## Evaluator: pooled `MatchEnv` (2026-08-11)

First optimization driven by the evaluator-throughput suite above.
`apply_down_values_def` (`src/symtab.c`) allocates and frees one `MatchEnv` — via
`env_new`, three `malloc`s — per candidate DownValue, so recursive rewriting
churns millions (`fib[28]` ≈ 2.5M envs, one per fib call × 3 rules tried).

of `env_new`/`env_free` is unchanged and `env_free` still releases each binding's

## Evaluator: machine-integer fast path for Plus and Times (2026-08-11)

Second optimization from the evaluator-throughput suite. `builtin_plus` /
`builtin_times` (`src/plus.c`, `src/times.c`) ran several O(n) scans (NDArray
probe, neg-Plus distribution, SeriesData, inexact contagion, then
(coeff,base)/(base,exp) grouping) before combining terms — real overhead for the
ubiquitous `Plus[int,int]` / `Times[int,int]` that dominates recursive integer
code (`fib[n-1]+fib[n-2]`) and loop accumulators. Added a fast path after the
n==0/1 checks: when every argument is a machine `EXPR_INTEGER`, fold them with the
overflow-checked `ci_add_i64` / `ci_mul_i64` (Times short-circuits on a 0 factor)
and return a single integer. On overflow, or any non-integer operand, it falls
through to the existing generic path, which promotes to bigint — so results are
unchanged, including the exact bigint answers for `9223372036854775807+1` and
`3037000500^2` (checked byte-for-byte against Mathematica 14.0).

Effect (on top of the MatchEnv pool; Mathilda ÷ WL): `fib[28]` 1.33 s → 1.06 s
(2.7×→1.9× vs 1.57 s baseline), `ack[3,4]` 16.8→14.3 ms, mutual recursion
0.85→0.74 ms, `Nest[incr,0,50000]` into parity. Suite `SLOWER` count 17→14,
`AHEAD` 11→14 cumulatively. Verified: full `ctest` 199/204 (the failures are the
pre-existing `zero_test` + SVD/eigen/lapack SEGFAULTs, plus the flaky
`moebiusmu_tests` which fails at the same ~20% rate on unmodified `de6a69f`);
`bench_eval`/`bench_match` gates PASS; arithmetic edge cases (overflow→bigint, 0
factor, negatives, mixed symbolic, rationals, reals) match WL; valgrind at the
422-block baseline.

A third lever — adopting the evaluator's per-step argument buffer into the

the operation (`replace_bindings` splice, Orderless grouping), not the reassembly

## Evaluator: borrow MatchEnv keys instead of copying them (2026-08-11)

Third optimization. The `MatchEnv` pool recycles the struct and its arrays, but
`env_set` (`src/match.c`) still `strdup`'d every binding's key and `env_free`
freed it — one malloc + free per binding, millions in recursive rewriting and
structural mapping. Every `env_set` caller passes a key that already outlives the

the matcher and `replace_bindings` both pass `sym->data.symbol.name` — hit
immediately) with a `strcmp` fallback so the cross-translation-unit literal
callers still match.

14.3→13.1 ms, Case B typed into parity, `bench_match` `ReplaceAll` 237→187
ns/elem. Cumulative suite over the three optimizations: **17→13 slower, 11→15
ahead** vs Mathematica 14.0.

Verified: `bench_eval`/`bench_match` gates PASS; matcher correctness (nonlinear
patterns `{a_,a_}`/`{a__,b__,a__}`, `OptionsPattern`, guards, `Cases`/`ReplaceAll`)

## Evaluator: skip evaluate() for atomic arguments (2026-08-11)

Fourth optimization, and the one found by *profiling* rather than reasoning.
`sample` on the `//.` fold showed the entire cost in `eval_and_free`
re-evaluating the result list each pass — the per-element `evaluate()` calls in
`evaluate_step`'s argument loop, not `replace_bindings` or the match. A raw atom
(Integer/Real/String/BigInt/MPFR/NDArray/Compiled) always evaluates to itself, so
`evaluate()` there just `expr_copy`s it after paying the recursion-depth bump,
trace push, deadline check and fixed-point-loop setup *per call*. The loop now
recognises an atomic argument and goes straight to `expr_copy`, skipping
`evaluate()` entirely — provably equivalent (same pointer, so the change flag
stays clear; an atom is never an in-flight `Throw`/`Goto`). `SYMBOL` is excluded
(it may carry an OwnValue).

This is the hot path whenever a large `List` of numbers is re-evaluated — most
visibly every pass of `list //. rule`, which re-walks the whole (mostly
unchanged) list. Effect vs WL 14.0: `//.` fold on `Range[800]` **4.3× → 2.2×**
(16.8 → 9.2 ms), on `Range[400]` → 2.3×, Case B untyped 3.1× → 2.5× (its guard
builds `{x},{y},{z}` integer lists), and the `ReplaceAll`-rebuild row off the slow
list. Suite `SLOWER` 13 → 11, `AHEAD` 15 → 17.

Cumulative over the four evaluator optimizations this week (MatchEnv pool, Plus/
Times machine-int fast path, borrowed MatchEnv keys, atomic-argument skip): the
evaluator-throughput suite moved from **17 slower / 11 ahead** to **11 slower /
17 ahead** vs Mathematica 14.0, with no regressions. The remaining top gap is the
Orderless sum (`Length[Plus @@ 2000 symbolic terms]`, 3.3×) — symbolic terms, not
atoms — which is the next target. Verified: `bench_eval`/`bench_match` gates PASS;
all 28 suite value checks agree with WL (0 CHECK-FAIL); `ctest` failures are the
pre-existing/flaky set (`zero_test`, `bench_pack`/`bench_compile` load-gates,
SVD/eigen/lapack SEGFAULTs); valgrind at the 420-block macOS baseline.

## Evaluator: skip the redundant sort in builtin_plus (2026-08-11)

Fifth optimization, again found by *profiling* (`sample` on `Plus @@ Table[c[k] x,
{k, 2000}]`): ~half the time was in the final-term `qsort` and its `expr_compare`
per comparison — the grouping hash table and reconstruction were already O(1)/O(n).
But a `Plus` built in order arrives canonically ordered (`c[1] x < c[2] x < …`),
and every re-evaluation of an already-sorted sum re-sorts terms that never moved —
pervasive, since a sum flows through the evaluator to a fixed point. `builtin_plus`
(`src/plus.c`) now guards the `qsort` with an O(n) already-sorted pre-check
(`plus_cmp_ptrs` scan, sort only on the first descent found) — the same technique
already used for the Orderless fast path in `evaluate_step`. Same canonical result:
skipping a no-op sort or sorting an unsorted sum both yield the identical order.

Effect: re-evaluating a canonical 2000-term sum **1.89 → 1.12 ms (−40%)**;
`expr_compare` samples 307 → 80, `qsort` 61 → 20. The suite Orderless-sum row moved
3.3× → 3.0× — its residual is now `Table` construction and the O(n) Infinity/
contagion pre-scans, not the sort. The general win is the re-evaluation path, which
every repeated symbolic-sum evaluation (Expand, polynomial arithmetic, Simplify)
hits.

Verified: `Expand[(1+x+y)^12] = 531441`, term collection (`2x+3x+x → 6x`) and
canonical ordering (`z+a+m+b+3+1 → 4+a+b+m+z`) correct; the full Expand/Simplify/
polynomial/numeric-domain test set passes; `bench_eval`/`bench_match` gates PASS;
`ctest` failures are the pre-existing/flaky set (this change is on the symbolic
grouping path, not the packed path `bench_pack` exercises); valgrind at the
420-block macOS baseline.

## Evaluator: borrow subset/remainder slices in ordered sequence matching (2026-08-11)

Sixth optimization. Re-profiling the `//.` fold *after* the atomic-argument skip
showed the cost had moved off `eval_and_free` and into the matcher:
`match_args_internal` (`src/match.c`) allocated and copied a fresh `remainder`
array (via `extract_subset`) at **every** pattern element — even single blanks —
so one `{a_, b_, r___}` pass paid ~4 O(n) copies of the tail. But
`next_combination` is gated on `is_orderless`, so for an *ordered* (non-Orderless)
head the do-while runs exactly once with `comb = [0..k-1]`: the consumed elements
are the contiguous prefix `exprs[0..k-1]` and the remainder is the contiguous
suffix `exprs[k..]`. Both are slices of the caller's array and are read-only (type
checks, `expr_copy` into `seq_val`/`matched_val`, and the recursive callee), so
they are now **borrowed** instead of malloc+`extract_subset`. The heap copies live
in `subset_owned`/`remainder_owned` (NULL in the borrow case → the free sites are
no-ops); the Orderless combination path is unchanged. The `comb` index array is
also skipped for ordered heads (only `extract_subset`/`next_combination` read it,
both Orderless-only).

This is a **general** matcher speedup, not just the fold — every pattern match over
an ordered head's arguments now avoids the per-element subset/remainder/comb
allocation. `bench_match`: `ReplaceAll` 187 → 99.8 ns/elem, `Cases` 216 → 126,
`Position` 634 → 500, DownValue-Map 613 → 513. Fold `Range[800]` 9.2 → 8.2 ms,
bubble sort `//.` 7.6 → 3.8 ms (2×), Case D 3.8 → 1.6 ms, `ack[3,4]` 13 → 9.5 ms,
`fib[28]` and the `ReplaceAll`-rebuild row into parity.

Cumulative over the six evaluator optimizations this week: the throughput suite
moved from **17 slower / 11 ahead** to **8 slower / 20 ahead** vs Mathematica 14.0,
worst outliers 4.3× → ~2.3×, with no regressions. Verified: the 298-case
`match_stress_corpus` passes (0 failed, 0 crashed); `match_tests`,
`rule_dispatch_tests`, `bench_eval`, `bench_match` PASS; matcher correctness
(nonlinear `{a__,b__,a__}`, `Cases`/`ReplaceList` with guards, OrderlessPatternSequence,
`Plus[a,b,c] /. {x__,y__}`) matches WL; `ctest` failures are the pre-existing/flaky
set (`zero_test`, `primenu` — 2/8 flaky on the committed baseline too,
SVD/eigen/lapack SEGFAULTs); valgrind at the 420-block macOS baseline over both the
borrow (ordered) and copy (Orderless) paths — no invalid access, no double-free of
a borrowed slice.

## Evaluator: Apply/Map/Scan/MapIndexed level short-circuits + Plus/Times special-case short-circuit (2026-08-12)

Follow-up to the *evaluator throughput* campaign, targeting the one row still
trailing Mathematica in `MATHILDA_EVALUATOR_PERFORMANCE.md` — the arithmetic
sentinel `Length[Plus @@ Table[c[k] x, {k, 2000}]]` (4.69 ms vs WL 1.5 ms, 3.1×).
Profiling the three operations on its critical path (`Table` build, `@@`, the
`Plus` grouping) surfaced two avoidable, non-fundamental costs — one of them a
finding the campaign had missed.

**1 — Specialised top-level `Apply` fast path** (`src/funcprog.c`). `f @@ expr`
(default level spec `{0,0}`) went through the general recursive `apply_at_level`,
which (a) called `get_depth(expr)` — a full recursive traversal of the whole
argument tree — at every node, though its only consumer is the negative-level
branch a non-negative spec never takes, and (b) *structurally cloned every element
subtree* (~4000 interior `Times`/`c[k]` nodes for a 2000-element list) even though
Expr trees are immutable and refcount-shared. `builtin_apply` now has a
self-contained fast path — mirroring the existing `f @@ <|assoc|>` one — that, for
`ls == NULL` with a function operand, builds `f[elements…]` by refcount-sharing
each element (`expr_copy` is an O(1) refcount bump) and evaluates once. Provably
equivalent to `apply_at_level(f, expr, 0, {0,0})`. The general `apply_at_level` was
also tightened: for a non-negative spec it skips `get_depth` and returns
`expr_copy(expr)` once `current_level > spec.max` (nothing can apply at that level
or deeper), and an `apply_child` helper folds the same past-max check into the
per-child recursion so `@@@` (`Apply[…, {1}]`) — a common operation whose general
path recursed once per element *and* once per sub-element, the level-2 calls doing
nothing but refcount-share — now shares each element's arguments in O(1). Isolated
`f @@ list` over 2000 elements **~1.3 ms → ~0.05 ms**; `f @@@ list` restructuring
over 5000 elements **~0.93 → ~0.78 ms (−15%)**; the 5000-triple
`Apply[Plus, …, {1}]` benchmark **11.5 → 7.4 ms (2.47× → 1.6× WL)**. Every `Apply`
level-spec form (`@@`, `@@@`, `{2}`, `{1,2}`, `{-1}`, `{-2}`, `Heads->True`, and
deeper nesting) is pinned in `test_core_algebra.c`.

**1b — `Map` (`/@`) shares the subtree past the mapped level** (`src/funcprog.c`
`map_at_level`). Map is bottom-up, and had the *same* `get_depth`-everywhere +
descend-and-rebuild overhead — worse, because it always walked to the leaves: the
common `f /@ list` cost grew with element *depth* even though `f` only touches
level 1. The same two changes apply: skip `get_depth` for a non-negative spec, and
once past the maximum level share the whole subtree by an O(1) refcount bump
instead of descending + rebuilding it. `f /@ 5000 g[a,b,c]` **4.19 → 0.56 ms
(−87%)** and `f /@ 5000 g[h[…],h[…]]` **7.12 → 0.57 ms (−92%)** — the time is now
independent of element depth. `Map[f, expr, {0}]` (map at level 0) becomes a clean
`f[expr]` share too. Every level-spec form (`{0}`, `{2}`, `{0,1}`, `{-1}`,
`Infinity`, `Heads->True`, `Hold`-suppressed) is pinned in `test_core_algebra.c`.

**1c — `Scan` (`src/funcprog.c` `scan_at_level`)** got the same treatment. Scan
discards results so there is no rebuild, but it still descended every element's
whole subtree and called `get_depth` at each node, so `Scan[f, list]` cost grew
with element depth too. Once past a non-negative upper bound the descent now stops
(a visit needs `level <= max`, which only rises with depth), and a pure
non-negative spec skips `get_depth`; the negative-spec paths and the
leaves-before-roots order / `Throw`/`Return` control flow are untouched.
`Scan[f, 5000 g[a,b,c]]` **0.90 → 0.55 ms (−39%)**, `Scan[f, 5000 g[h[…],h[…]]]`
**1.38 → 0.52 ms (−62%)** — depth-independent. Pinned in `test_core_algebra.c`
(`test_scan`), and the existing `scan_tests`/`funcprog_through_tests` are unchanged.

**1d — `MapIndexed` (`src/funcprog.c` `mi_at_level`)** completes the set. It
rebuilds bottom-up while threading each part's `{position}`, and the depth it
accumulates into `*out_depth` is read *only* by a negative-level bound — so under a
non-negative spec it is never used, yet it descended and rebuilt every element's
whole subtree to compute it. Two guards fix that: past the max level share the
subtree (return early, depth left at 1), and at the deepest wrapping level share the
node instead of descending + rebuilding (its children are all past max, so the
rebuild would just reproduce it). `MapIndexed[f, 5000 g[a,b,c]]` **5.55 → 1.57 ms**,
`MapIndexed[f, 5000 g[h[…],h[…]]]` **8.39 → 1.60 ms** — depth-independent, and now
**1.2× WL 14.0** (down from 4.1×; it stays just above WL because it builds a
position vector + two-arg wrapper per element, which no short-circuit removes).
Every level-spec form, the `{i,j,…}` positions, `Heads->True`, and `Association`
`Key[k]` positions are pinned in `test_core_algebra.c` (`test_mapindexed`); the
existing `mapindexed_tests` is unchanged.

**2 — Fused special-case short-circuit in `Plus` and `Times`** (`src/plus.c`,
`src/times.c`). Both ran five independent full O(n) pre-scans before term grouping
— NDArray probe, neg-Plus distribution (Plus only), SeriesData, inexact contagion
(with a size-n `malloc` taken *before* the check), Infinity/Indeterminate — and for
an ordinary symbolic or rational sum/product every one finds nothing. A single
detection pass now decides whether any could act; if not, execution jumps straight
to grouping. The predicate is a provably-correct superset of "some pass would act"
(NDArray→`is_ndarray`, neg-Plus→`is_neg_of_plus`, series→`is_series_data`,
contagion→`arg_is_inexact` — exported from `numeric.c` for this, matching
`numeric_contagion_args`'s own trigger — Infinity→`classify_plus_term`/the inline
Times check), so skipping the passes when it is false is exactly equivalent. The
guarded passes are otherwise byte-for-byte unchanged.

**Result.** `Length[Plus @@ Table[c[k] x, {k, 2000}]]` **4.69 → 2.95 ms (−37%,
3.1× → 2.0× WL)**; the sibling `bench_eval` row "orderless sort (Plus 1200)"
dropped from 0.27 to ~0.19 norm. The residual is now dominated by `Table`'s
per-element symbolic-`Times` evaluation (2.43 ms of the 2.95 ms) — the systemic
per-node evaluator constant, whose largest remaining lever is the fixed-point
double pass (`builtin_times`/`builtin_plus` unconditionally rebuild and trip the
change flag, forcing a confirm-stable step). That is a core-evaluator change of
much broader blast radius and is left for a separate, measured effort.

**Tests.** New `tests/test_core_algebra.c` (wired into CMake as
`core_algebra_tests`) pins Plus/Times/Power/Divide/Apply/Length/ordering/Table

single, atomic) and every guarded Plus/Times special case (cancellation, Infinity,
ComplexInfinity, Indeterminate, contagion, radical fusion, trig canonicalisation).
`tests/bench_eval.c` gains the three flagship regression rows mandated by the perf
doc — `fib[24]` (dispatch), Case B typed (matcher constant), Plus-2000 (this

## Graphics: add ArrayPlot (2026-08-12)

New `ArrayPlot[array, opts...]` (`src/graphics/arrayplot.{c,h}`), a discrete
grid heatmap for a literal 2D array — the counterpart to `DensityPlot`'s

## Graphics: ArrayPlot ColorRules, and a leaked-evaluation fix in arrayplot.c (2026-08-12)

Added `ColorRules -> {v1 -> c1, v2 -> c2, ...}` to `ArrayPlot` (reported: colours
weren't showing up — the plot rendered fully greyscale). `ColorRules` gives an
explicit colour to cells whose value exactly equals a named key, checked before
the continuous `ColorFunction` ramp; a cell matching no rule still gets the
normal scaled `ColorFunction` colour rather than being left uncoloured —
`ArrayPlot[{{1,0,0.5},{0,1,0.5}}, ColorRules -> {1 -> Pink, 0 -> Yellow}]` now
paints the `1`/`0` cells Pink/Yellow and the `0.5` cells on the usual grey
ramp. New `SYM_ColorRules` interned in `sym_names.c` alongside the other
`ArrayPlot` option symbols.

Implementing it surfaced a real bug, caught by `leaks --atExit` rather than by
inspection: `evaluate()` **borrows** its argument — it makes its own internal
copy and never frees what it's handed (see `src/eval.c`'s `evaluate`, whose
first act is `current = expr_copy(e)`) — so `evaluate(expr_copy(rhs))` with the
copy inlined leaks that copy's reference. This is the exact bug class already
fixed for `guard_all_true` in `src/match.c` (`docs/spec/changelog/2026-08-10.md`,
"Matcher: fix per-guard-evaluation memory leak"), just not yet applied to
`arrayplot.c`. Because `expr_copy` is a refcount bump rather than a deep clone,
an orphaned bump on a shared subtree (`rhs`) blocks that subtree from ever
reaching refcount 0 during the caller's teardown — so the leak is not one node
but the whole unevaluated option-value subtree, which is why `ColorRules ->
{1 -> Pink, 0 -> Yellow}` (evaluating named colours into `RGBColor[...]`) leaked
visibly (11 blocks/560 B for one call) while a bare `Mesh -> All` leaked a
single 64-byte node per call — both instances of the identical bug, just
different-sized victims. All five call sites in `arrayplot.c`
(`ColorFunctionScaling`, `Mesh`, `PlotLegends`, `ColorRules`, and the generic
Graphics-option passthrough — i.e. every option `ArrayPlot` accepts) shared the
inlined form. Fixed with one local helper, `eval_borrowed()`, that names the
copy and frees it after use; not touched in the sibling plotters
(`densityplot.c` etc.), which share the same idiom and same latent bug but are
outside this change's scope.

Verified: `leaks --atExit` over 50-iteration loops covering
`ColorRules`-matching, `ColorRules -> None`, plain `Mesh -> All`, and the
combined `Mesh`+`PlotLegends`+`ColorFunction` case from the original `ArrayPlot`
changelog entry above — all now **0 leaks** (previously 1–6 leaked
blocks/call depending on the option combination). `graphics_tests` green
including a new `test_arrayplot_color_rules_override_matching_cells` (exact-key
match, unmatched-value fallback, `ColorRules -> None` equivalence to omitting
the option). `make` clean at `-O3 -std=c99 -Wall -Wextra`, no new warnings.

## Graphics: fix a Frame+AspectRatio letterbox, then let ArrayPlot mix numeric and colour cells freely (2026-08-12)

Two follow-up fixes to `ArrayPlot`, both from real usage rather than review.

**1 — Frame plots with an explicit `AspectRatio` letterboxed inside their
own frame** (reported via screenshot: an `ArrayPlot`'s coloured grid sat with
a visible white margin between it and the frame border, on all sides).
Root cause was general renderer logic in `src/graphics/render.c`, not
`ArrayPlot`-specific — reproduced identically on unmodified `Plot3D[...,
Mesh -> All]`, which also sets an explicit `AspectRatio`. `gfx_window_height()`
sizes the *window* to match `AspectRatio`, but `Frame`'s margins are fixed
pixel amounts (some floored, e.g. clearing the toolbar), not proportional
between width and height — so the margin-reduced *data region* lands at a
different aspect ratio than the window, and any `Frame` plot with an explicit
`AspectRatio` (`ArrayPlot`'s `rows/cols` default, `DensityPlot`'s `1`, …) can
letterbox. Added `gfx_window_height_fit_region()`: a few fixed-point
iterations (the margin formula is a contraction — each margin is either
height-independent or ≤7% of height) that solve for the window height whose
*region*, not just the window, hits the target ratio. The margin formulas
themselves were factored into shared `gfx_horizontal_margins()` /
`gfx_vertical_margins()` so the sizing pass and the actual region layout can
never drift apart. `gfx_window_height()` itself is untouched (its pinned
`test_window_height_policy` still passes byte-for-byte); the new function is
called right after it in `graphics_show()`, before `InitWindow`. New
`test_window_height_fit_region_no_letterbox` pins both halves: the corrected
height's region matches the target ratio within 1%, and — to prove the test
actually exercises the bug — the pre-fix (naive) height's region does not
(>5% off) for the same inputs.

*Diagnostic note:* while investigating a *separate* "window freezes on close"
report against this same `ArrayPlot` call, `sample`(1) on the actual running
process showed it had already returned to the REPL prompt (`readline`) —
i.e. `CloseWindow()` had already run. That looks like a stale/ghost frame
left on screen by the OS compositor after close, not a hang in Mathilda; it
self-resolves (switch away and back). No code change from that report; noted
here since it surfaced while looking at the same window-sizing code path.

**2 — `ArrayPlot[{{1, 0, 0, Pink}, {1, 1, 0, Pink}, {1, 0, 1, Red}}]` (mixing
plain numbers and colour literals in the same array) returned unevaluated.**
The array-loading logic required every cell to be numeric *or* every cell to
be a colour literal — a matrix mixing both matched neither shape and fell
through as "can't evaluate this," even though calling out a few specific
cells by colour while the rest follow the normal heatmap is a natural,
common use of the raw-pixel-grid feature. `src/graphics/arrayplot.c`'s
`arrayplot_is_color_matrix` (all-or-nothing) is replaced by `arrayplot_load`,
which classifies **each cell independently**: a colour literal is painted
directly, a plain number goes through `ColorRules`/`ColorFunction` as usual,
and anything else (a symbolic non-color, non-number cell) leaves the whole
call unevaluated, same as before. `ColorFunction`'s `[zmin, zmax]` scaling
range and `PlotLegends`'s eligibility (still "only when at least one cell is
numeric") are now computed by scanning just the numeric cells rather than
gating on an all-or-nothing mode flag. An `NDArray` input is unaffected — a
dense numeric buffer can't contain a colour literal by construction, so it
still goes through `na_load_matrix` as a pure numeric load.

New `test_arrayplot_mixed_numeric_and_color_cells` (named colours paint
directly, numeric cells keep the greyscale ramp) and an added case on
`test_arrayplot_invalid_args_stay_unevaluated` (a genuinely invalid cell,
e.g. `{{1, 2, foo}}`, still leaves the call unevaluated — the new per-cell
loader doesn't accidentally accept everything). `graphics_tests` all green;
`leaks --atExit` over 50 iterations mixing the new code path with the
existing pure-numeric, pure-colour, and both failure shapes: 0 leaks. `make`
clean at `-O3 -std=c99 -Wall -Wextra`, no new warnings.

## Compile[]: `Norm[v, p]` two-arg forms + inline-vector auto-compilation (2026-08-12)

`Norm` had a `Compile[]` lowering only for the bare `Norm[v]` / `Norm[m]`
(2-norm / spectral), and a `Norm[{f[x], …}]` body could not auto-compile at all.
Two independent gaps, closed by operand kind. No interpreter behaviour changed —
both fixes live entirely in `src/compile/`, and the packed/NDArray `ndla_norm`
path is unchanged.

**1 — Declared-array two-arg forms (new `V_NORM` opcode).** `Norm[v, 1]`,
`Norm[v, Infinity]`, `Norm[v, k]`, `Norm[v, 2.5]`, and the matrix `Norm[m, 1]` /
`Norm[m, Infinity]` / `Norm[m, "Frobenius"]` now lower to a machine `Real`. The
second argument is a compile-time literal but not always a machine scalar
(`Infinity`, `"Frobenius"`), so it is baked into the instruction immediate
`imm.r` — `0` = none, `+Inf` = Infinity, `NaN` = "Frobenius", a finite positive
value = that `p` (rebuilt as an Integer when integral, since LAPACK keys the
matrix path on Integer 1/2). The VM (`OP_V_NORM`, a `K_ARR` op modelled on
`V_NDRED`) rebuilds `Norm[array, p]` and delegates to `ndla_norm`, so the
compiled answer is bit-identical to the interpreter's NDArray path by
construction. Validity mirrors `ndla_norm` exactly (`nd_norm2_encode` in
`compile_ndtables.c`): a rank-1 operand takes any positive `p` or Infinity; a
rank-2 operand takes `{1, 2, Infinity, "Frobenius"}`; an induced matrix `p`-norm
with `p ∉ {1, 2, Infinity}`, a string method on a vector, and int/complex
operands decline cleanly to the interpreter. The bare `Norm[v]`/`Norm[m]`
reduction (ND_REDS) is untouched.

**2 — Inline vector construction (auto-compilation).** A `Norm[{e1, …, en}, p]`
whose operand is a `List` literal (not a declared array) was the reason a
`Table[Norm[{Sin[x], Cos[x], x}], …]` body bailed wholesale — the compiler could
not lower the inline vector. It now expands to the same scalar arithmetic the
interpreter's `builtin_norm` uses (`norm_try_expand` in `compile.c`, shared by
`emit_node` and `infer_type`): `Sqrt[Σ Abs[ei]^2]` (p=2/Frobenius),
`Σ Abs[ei]` (p=1), `Max[Abs[ei]]` (Infinity), `(Σ Abs[ei]^p)^(1/p)` (general p),
expandable exactly where `builtin_norm`'s symbolic branch is (rank-1 under any p,
any rank under "Frobenius"). This produces inline scalar code with **no
per-iteration buffer allocation** — strictly better than packing a short vector —
and unblocks `Norm[{…}]` bodies inside `Plot`/`Table`/`NIntegrate`/`FindRoot`. A
rank-2 list under an induced norm (needs an SVD) is not expandable and falls
through unchanged.

**Verified.** `CompileDiagnostics` reports `Compiled -> True` for every reported
form and `False` for the correct declines; compiled values equal the interpreter
(bit-identical for the array delegate, within machine tolerance for the scalar
expansion); the `MATHILDA_COMPILE_DIAG=1` auto-compile probe no longer prints
`[compile] interpreting`. New tests in `tests/test_compile_transforms.c`
(`test_cf_norm_array_vector`, `_array_matrix`, `_list_literal`); the compile,
NDArray, normalize, and lstsq suites pass; `make check-c99` clean.

## Packed arrays: `Im` narrowing kernel — off the NOT_AWARE list (2026-08-12)

`Im` had an NDArray projection kernel but sat on `pack.c`'s `NOT_AWARE` list, so
on the *invisible* auto-packed-List surface it materialised to the scalar List
path — `Im[Range[1., 10^7]]` cost ~3.9 s where the sibling `Re` cost ~0.17 s
(~22×). The reason was exactness: `Im` of a real is the exact `Integer 0`, and a
projection kernel would have written `0.0` into a float64 buffer, an observable
wrong element head (the same real→integer trap that kept `Floor`/`Sign` off the
fast path until they got narrowing kernels on 2026-07-30).

Fix: give `Im` a narrowing pair (`NDKU_ImInt` in `src/ndkernels.c`, `to_int`) —
`to_int_r`/`to_int_i` write an `NDT_INT64` zero buffer from real/integer input
(unconditionally 0; the imaginary part of any real is 0, finite or not, so unlike
`Sign` there is nothing to reject), while a COMPLEX input still takes the `ndk_Im_c`
projection arm (the imaginary part, a Real), which `ndarray_map_unary`'s narrowing
branch skips for complex dtypes. `Im` then comes off `NOT_AWARE` and is implicitly
aware via its kernel.

Result: `Im[Range[1., 10^7]]` **3856 ms → 151 ms (~25×)**, matching `Re`; element
heads are identical to the List path (`Im[{2., 3.}] === Take[Im[Range[1., 300.]], 2]`
is `{0, 0}`, both exact `Integer`), a real `NDArray` gives an `int64` zero array,
and a complex `NDArray` still gives the Real imaginary parts. No behaviour changed
— the packed answer was already exact via the slow path; this makes the buffer
path produce it directly.

Incidental: `Abs` and `Im` are now hand-written kernels rather than `UK_PROJ`
macro expansions, dropping the two unused projection descriptors (`NDKU_Abs`,
`NDKU_Im`) so `src/ndkernels.c` compiles clean under `-Wall -Wextra`
(`-Wunused-const-variable`); `ndk_Abs_c`'s body is unchanged.

## Chop and Clip: buffer fast paths + Compile lowerings (2026-08-12)

`Chop` had no fast path on any surface, and `Clip` degraded to the interpreter
whenever it clipped against exact (default `{-1,1}`) bounds. Both are now fast on
the machine-buffer, `Compile[]`, and auto-compilation surfaces, with no change to
any answer. The exactness obstacle for both is the same real→integer trap `Im`
just hit — a chopped/clipped element is an exact `Integer`, which no uniform Real
buffer holds — so each keeps a buffer only where the result is uniform.

- **Chop NDArray fast path** (`chop_ndarray` in `src/core.c`; `Chop` added to
  `pack.c`'s AWARE). An auto-packed `List` used to be materialised before it
  reached Chop (~40× an aware head). Now a cheap alloc-free scan keeps the buffer
  untouched when NOTHING chops (`Chop[Range[1.,10^7]]` **1362 → 131 ms**); when
  something chops, a rank-1 buffer builds the mixed `{…, 0, …}` result in ONE pass
  off the elements (an all-zero result re-packs to int64), and higher ranks take
  the general delist. Complex/int64 buffers delist. Value-identical to
  `chop_recursive`.
- **Chop `Compile[]` + auto-compilation** (`compile_emit_mathfn.c`,
  `compile_infer.c`). `Chop[x]` / `Chop[x, δ]` (δ a literal) lower branchlessly to
  `x * (Abs[x] >= δ)` (the UnitStep mask-multiply, no new opcode) → `Real`; the
  chopped value is a machine `0.` (a CompiledFunction returns machine types). A
  machine integer never chops → identity. So `Chop[…]` now auto-compiles inside
  `Plot`/`Table`/`NIntegrate`/`FindRoot`.
- **Clip scalar `Clip[x]`** (default bounds) now lowers as `Min[Max[x,-1.],1.]`,
  filling the `na==1` gap; the explicit-bounds scalar form was already
  `Min[Max[x,lo],hi]`.
- **Clip exact-bounds buffer, three-way scan** (`ndstruct_clip`). The exact-bound
  path now distinguishes: nothing clips → the Real input; a MIX of clipped
  (Integer) and unclipped (Real) → the exact List path; and EVERYTHING clips to a
  finite exact-Integer bound → a uniform `NDT_INT64` buffer. That last case is the
  common `Clip[reals, {-1,1}]` over out-of-range data: **`Clip[Range[1.,10^7]]`
  4633 → 158 ms (~30×)**. Rational/infinite bounds still take the List path.

Verified: `check-array-exactness` 0 MIXED (Chop/Clip buffers stay single-headed or

## FindClusters beyond one dimension

`FindClusters` accepted only a flat list of real scalars; a list of vectors —
Wolfram's own second example — returned unevaluated. It now clusters:

- **equal-length numeric vectors** in any dimension,
- **colours** (`RGBColor`, `GrayLevel`, `Hue`, `CMYKColor`), whose arguments are
  coordinates, so a colour is a point in its own space and needs no
  colour-specific code,
- **strings**, on `EditDistance`.

```mathematica
In[1]:= FindClusters[{{1, 1}, {1, 2}, {9, 9}, {9, 8}}]
Out[1]= {{{1, 1}, {1, 2}}, {{9, 9}, {9, 8}}}

In[2]:= FindClusters[{"cat", "cot", "dog", "dig"}, 2]
Out[2]= {{"cat", "cot"}, {"dog", "dig"}}
```

**One dimension is unchanged, by construction.** The file's structure is now a
spanning tree with exact edge weights, and on a line the minimum spanning tree
*is* the sorted adjacency chain — so the general code reduces to the original
algorithm exactly there. The 132 existing acceptance rows are the proof and were
required to stay green; 35 rows were added.

**Exactness survives in n dimensions** because ranking uses *squared* Euclidean
distance, which is rational for rational input and monotone in the true distance.
`FindClusters[{{1/3, 1/7}, {1/3, 1/7 + 1/10^20}, {5, 5}}]` groups the two
near-identical exact vectors rather than collapsing them through a double.

Scope limits, stated rather than discovered:

- Only `Automatic`, `"Agglomerate"` and `"SpanningTree"` accept the new element
  kinds. The other seven methods read a sorted one-dimensional projection and
  decline instead of running on data where it is meaningless.
- Vectors and strings are capped, both being quadratic where a sort avoids that
  only on a line. The ceiling depends on which spanning-tree builder runs — see
  the machine-precision section below.
- `Rational` and `Complex` are numbers, not points: `{1/2, 1/3, 10}` clusters as
  three reals. Point heads are an explicit list precisely so that
  `Rational[1, 2]` is never read as a pair of coordinates.

## Distance functions

Seven functions that did not exist. `Names["*Distance*"]` returned only
`GraphDistance`, while `FindClusters`' `DistanceFunction` option accepted
`EuclideanDistance` and friends as **inert symbols** — which is why its
documentation could truthfully claim all the choices behaved alike.

| Function | Value |
|---|---|
| `EuclideanDistance[u, v]` | `Sqrt[Sum Abs[u_i - v_i]^2]` |
| `SquaredEuclideanDistance[u, v]` | `Sum Abs[u_i - v_i]^2` |
| `ManhattanDistance[u, v]` | `Sum Abs[u_i - v_i]` |
| `CosineDistance[u, v]` | `1 - (u . Conjugate[v]) / (Norm[u] Norm[v])` |
| `EditDistance[u, v]` | Levenshtein distance, strings or lists |
| `HammingDistance[u, v]` | positions differing, equal lengths required |

Exact input gives exact output where the value is rational; complex components
contribute their modulus (`Abs` before squaring, as Mathematica defines it);
symbolic input survives as an expression. Every value was cross-checked against
`wolframscript`, including two conventions that are not derivable:
`CosineDistance` of a zero vector is `0` rather than `Indeterminate`, and
`HammingDistance` on unequal lengths is left unevaluated.

The `DistanceFunction` documentation was corrected: the equivalence of the
Euclidean family is a statement about **one dimension**, where they are monotone
transforms of one another. It does not hold for vectors.

## Fixes

- **`FindClusters` with an explicit count was quadratic.** `FindClusters[data, 10]`
  over 100,000 points took 2.24 s against 0.087 s for `Automatic` on the same
  input, growing fourfold per doubling. The union-find introduced with the
  spanning-tree rewrite had no path compression, so when few edges are cut the
  surviving components form one long chain and every `find` walks it. `Automatic`
  hid the bug because many cuts leave many short components. With path halving
  and union by rank: **2.24 s → 0.083 s**, and linear again.

- **`Abs` and `Sign` decline on rationals with bigint components.**
  `Abs[-1/10^20]` does not evaluate while `Abs[-1/7]` does. This is a
  pre-existing bug, not introduced here, but it silently blocked every exact
  high-precision distance and so made `FindClusters` refuse exact vectors at that
  scale. The distances route around it by taking the sign through the exact
  comparator; **the underlying `Abs`/`Sign` gap remains and is worth fixing
  separately.**

## FindClusters: a machine-precision spanning tree, 219x faster on vectors

Clustering vectors was capped at 2000 points and spent nearly all its time
allocating expressions: exact Prim computes O(n^2) distances, and each one built
and evaluated a chain of `Expr` nodes to keep the comparison exact.

For input whose coordinates are *already* machine numbers, that buys nothing --
there is no precision beyond a double to preserve. Such input now takes a
double-precision Prim; only the n-1 chosen edge weights become expressions, so
allocation drops from O(n^2) to O(n). Input with a `Rational`, bigint or MPFR
coordinate keeps the exact builder, which is the only one that can order it
correctly.

| 2-D points | before | after |
|---:|---:|---:|
| 500 | 95 ms | 0.62 ms |
| 1000 | 398 ms | 2.0 ms |
| 2000 | 1.49 s | 6.8 ms |

**219x at n=2000**, which lifts the machine ceiling from 2000 to 20000 points
(0.81 s there). The exact path keeps its 2000 cap.

Nothing is given up. Distinctness was never decided from a distance on either
path -- it compares the elements with the exact comparator -- so
`FindClusters[{{1/3, 1/7}, {1/3, 1/7 + 1/10^20}, {5, 5}}]` still groups the two
near-identical exact vectors. Two builders for one definition is a standing risk,
so a test clusters the same points both ways (as integers, which are machine, and
divided by a constant, which makes them exact) and requires the partitions to
match, including over 400 random points.

Integer coordinates are required to be within 2^53 to take the fast path, since
beyond that a double stops representing integers exactly and the two builders
would quietly disagree.

## Sum: `Sum`Gosper` rejects var-dependent radicals up front (fixes a nested-sum hang) (2026-08-14)

Building a nested finite sum whose summand carries a fractional power of an
iterator-dependent base hung the evaluator. The trigger was the Thomson-problem
repulsion energy — 10 charges on a unit sphere:

```mathematica
Sum[1/Sqrt[(x[i]-x[j])^2 + (y[i]-y[j])^2 + (z[i]-z[j])^2 + 10^-9],
    {i, 1, n-1}, {j, i+1, n}]     (* n = 10: hung; never returned *)
```

`Sum[f, {i,1,n-1}, {j,i+1,n}]` is rewritten to `Sum[Sum[f, {j,i+1,n}], {i,1,n-1}]`,
and the outer finite sum tries the closed-form cascade *first* (its cost is
independent of span width). That cascade evaluates the inner `Sum[f, {j,i+1,n}]`
with `i` still symbolic, and `Sum`Gosper`'s step-1 `Simplify` — meant to reduce a
term ratio to `num/den` polynomials — diverged trying to rationalise
`Sqrt[q(j)] / Sqrt[q(j+1)]`, a ratio of square roots of a nine-symbol quadratic.

**Root cause and fix.** A hypergeometric term has a *rational* term ratio; a
summand with a fractional power of an `i`-dependent base never does, so Gosper
cannot sum it. `gosper_antidiff` now scans the summand for any `Power[base, exp]`
with a non-integer `exp` and a `base` that depends on the summation variable
(`src/sum/sum_gosper.c`, `has_var_radical`) and returns `NULL` *before* the
term-ratio `Simplify` is ever built. The cascade then declines cleanly, the outer
sum falls through to term-by-term expansion, and the inner sum is evaluated under
each concrete `i` — as the nested-rewrite already intended.

The guard cannot regress a working Gosper closed form: any summand it rejects has
an irrational term ratio and so was never Gosper-summable. All 64 existing
`sum_tests` still pass; three regressions were added
(`Sum[1/Sqrt[k^2+1], k]` stays held, the nested sqrt sum builds with the right
term count, and a nested finite radical sum evaluates to the correct value).

With the fix, the user's original nested-`Sum` objective runs end-to-end:
`NMinimize[{repulsion, constraints}, vars, Method -> {"RandomSearch",
"SearchPoints" -> 30}]` returns energy **32.7169** — the known Thomson N=10
minimum (32.716949…) — with all ten points on the unit sphere to 1e-7, in ~10 s.

## Constrained solver: augmented-Lagrangian polish + drift rescue (2026-08-15)

Upgraded the shared constrained local solver `fm_run_penalty`
(`src/numerical_calculus/findmin.c`) — used by both the `NMinimize`/`NMaximize`
polish and `FindMinimum`/`FindMaximum` — from a pure quadratic penalty
(`f + μ·Σc²`, μ ramped to 10⁸) to a **PHR augmented Lagrangian**
(`f + Σλ_k·c_k + μ·Σc_k²`, multipliers updated each outer round). The pure
penalty needs μ→∞ for any active constraint, which is ill-conditioned and could
not restore feasibility on a **nonlinear/bilinear** equality from a far start:
the polish ended infeasible, so `RandomSearch` returned the `{Infinity,…}`
sentinel on a plainly feasible problem, and a larger `MaxIterations` made it
*worse*. With multipliers a moderate μ reaches the constraint surface, exactly as
an SQP method does. **Invariant:** with every multiplier zero the PHR terms are
algebraically identical to the quadratic penalty, so the first outer round — and
any solve that never updates λ — is bit-for-bit unchanged; the multipliers are
threaded through a file static (`g_fm_al_lambda`, gens-pointer identity guard)
touching only `fm_eval_augmented` / `fm_eval_aug_gradient`, leaving the raw
`fm_eval_penalty` feasibility test intact. A companion **drift rescue** in the
outer loop remembers the lowest-objective feasible iterate across the μ schedule
and falls back to it only when the final round ends infeasible (never changes a
feasible-ending run).

Effect, on the A1 refinery **pooling** benchmark (8 vars, bilinear pool-quality
equality `3cA+cB = px·xA+py·yA`, capacity + box constraints; global optimum
−3900): `DifferentialEvolution` now reaches −3900 across every seed in ~52 ms,
versus scipy's `differential_evolution` at ~2.12 s (≈41× faster, same optimum;
scipy's global engine also fails on some seeds). `RandomSearch`, previously
`Infinity`/−450, now lands on −3900 on a good start. Both `findmin_tests` and
`nminimize_tests` pass unchanged; valgrind shows no new leaks (all lost blocks
are macOS libobjc/libswiftCore baseline noise). New regression
`tests/test_nminimize.c::test_refinery_pooling`; scipy comparison recorded in
`benchmarks/63-global-optimization/`.

## NMinimize: one-hot / assignment feasibility repair (2026-08-15)

problems (`src/numerical_calculus/findmin.c`). At driver setup

## Scoping: With/Module/Block substitute into a Table iteration count (2026-08-15)

Fixed a scoping-substitution bug in `src/modular.c`: a bound name was not
substituted into a **length-1 Table iterator** `{n}` (an iteration count), so
`With[{n = 3}, Table[7, {n}]]` and `Module[{n = 4}, Table[0, {n}]]` returned
unevaluated instead of `{7,7,7}` / `{0,0,0,0}`. The iterator-handling code treated

unchanged (`With[{i=99}, Table[i, {i,3}]]` is still `{1,2,3}`), and range bounds

## FindClusters accepts a visible NDArray

`FindClusters[NDArray[{1., 2., 10.}]]` clusters. It used to return unevaluated —
and that was documented behaviour rather than an oversight, so this is a
deliberate change with a test row rewritten to match.

The two array surfaces reach a builtin differently, which is the whole reason only
one of them was broken. The packing transparency gate (`src/eval.c`, step 2.7)
materialises a *packed* list for any head not on `src/pack.c`'s `AWARE` list, so
that surface always worked. It tests only `is_packed_list`, though, so a
**visible** `NDArray[...]` passed straight through to a builtin whose shape guard
is `is_listq` — which an `EXPR_NDARRAY` fails. Unevaluated, with no message.

Rank 1 is read as scalars and rank 2 as points, each giving the same partition as
the equivalent `List`. Rank 3 and above still decline: a list-valued component is
not a coordinate, and `fc_probe_shape` already rejected it.

It is a materialise guard, not a buffer fast path, and `FindClusters` stays off
`AWARE` — with an `EXEMPT` entry in `tools/check_packed_aware.py` recording why,
alongside `Cases` and `FlattenAt`, which are exempt for the same reason. Reading
the buffer directly would mean giving up what makes the answers exact: the
spanning tree orders rationals and bigints through `internal_subtract`, the
boundary set compares *elements* because `2^60` and `2^60 + 1` are distinct yet
project to the same double, and the clusters are emitted from the input elements
themselves. Opting in to `AWARE` would also stop the gate materialising a packed
list, which is exactly the plain `args[]` all of that needs.

No speed is given up either. Every value in an `NDArray` is machine by
construction, so `fc_all_machine` is true and the machine spanning-tree builder
runs — the same one a machine `List` takes, with the 20000-point ceiling from the
previous entry.

Ownership is handled by splitting the body into a helper that takes the data list
as a parameter. There are eighteen `return NULL` paths, and the materialised list
must outlive the cluster emission and be freed on all of them; one caller that
owns the temporary and one callee that only borrows it cannot leak or double-free.

## DistanceFunction selects a metric instead of being discarded

`FindClusters[..., DistanceFunction -> ManhattanDistance]` now clusters by
Manhattan distance. It used to validate the name, return true, and store nothing:
`FcOpts` had no field for the choice and `fc_pair_distance` hardcoded squared
Euclidean.

On a line that was harmless and arguably correct — every accepted metric is a
monotone transform of `|a - b|` there, so all four induce the same ordering of gaps
and the same partition. Above one dimension it is a wrong answer rather than a
missing feature: Manhattan and Euclidean rank pairs differently in the plane, and a
user asking for one and silently getting the other has no way to notice.

```
FindClusters[{{0, 0}, {0, 11}, {8, 6}}, 2]                                → {{{0,0}}, {{0,11},{8,6}}}
FindClusters[{{0, 0}, {0, 11}, {8, 6}}, 2, DistanceFunction -> ManhattanDistance]
                                                                          → {{{0,0},{0,11}}, {{8,6}}}
```

Squared Euclidean weights those edges 121, 100 and 89, so the tree is `{89, 100}`
and cutting its heaviest edge isolates `{0,0}`. Manhattan weights them 11, 14 and
13, so the tree is `{11, 13}` and cutting its heaviest isolates `{8,6}`.

`EuclideanDistance` and `SquaredEuclideanDistance` are deliberately ONE case rather
than two. Squaring is monotone on non-negatives so it preserves edge ranking, and
the threshold test `d > 3 median(d)` holds exactly when `d² > 9 median(d²)` — so the
two always produce the same partition. Collapsing them also avoids taking a square
root of an exact value: `Sqrt[2]` is irrational, and an exact ordering that has to
compare irrationals is a substantially harder problem than this needs.

The threshold factor now tracks the metric rather than the kind. It was squared for
any POINT input because Euclidean weights are squared distances; under Manhattan
the weights are plain sums of absolute differences, so keeping the squared factor
would have applied a threshold nine times too large — a silent, plausible-looking
wrong answer.

Scalar input is untouched: the metric is applied only to points, since a line's
weights are plain exact differences that no accepted metric can change. The
one-dimensional answers of all ten methods are pinned in
`tests/test_findclusters_scalar_pin.c` and unchanged.

`DistanceFunction` takes a metric, not a string — `EuclideanDistance`, not
`"EuclideanDistance"` — the reverse of `Method`. A quoted string leaves the call
unevaluated, which is now pinned, because the two conventions sit next to each
other and are easy to swap.

Both spanning-tree builders were wired, and a test clusters the same points as
integers (machine, double builder) and divided by three (exact rationals, Expr
builder) under Manhattan, requiring identical partitions. Two builders for one
definition is a standing risk, and a metric wired into one of them would make the
answer depend on how the numbers happened to be written.

## MeanShift and NeighborhoodContraction cluster n-dimensional points

Both now work on vectors, not only scalars. Four of the ten methods are
dimension-general: `Agglomerate`, `SpanningTree`, and these two.

```
FindClusters[{{0,0},{1,0},{0,1},{1,1}, {20,20},{21,20},{20,21},{21,21},
              {0,40},{1,40},{0,41},{1,41}}, Method -> "MeanShift"]
  -> the three squares, and the same for NeighborhoodContraction and in 5-D
```

This is one implementation, not a second one beside the 1-D kernel, and three
observations are what let it be:

**The scalar case is not a special case.** `d->val` is a row-major n × 1 buffer
indexed by input position, which is exactly the layout `d->coord` has at dim 1. So
one pointer serves both and the branch disappears.

**The median spanning-tree edge weight generalises the median adjacent gap
exactly.** On a line the minimum spanning tree *is* the sorted adjacency chain, so
its edge weights are precisely the gaps the 1-D code took the median of. Better,
the *mean* edge weight reproduces `(max − min)/(n − 1)`, because those gaps sum to
the range — and that was the 1-D fallback for a zero median, so the fallback
generalises for free. Weights are converted to lengths before the median is taken:
rooting afterwards happens to agree for the median, since a root is monotone, but
not for the mean.

**Merging by union-find reproduces the adjacent-difference pass.** The 1-D merge
walked sorted neighbours, which vectors have no analogue of. Uniting every pair
within tolerance agrees with it on a line, because a point lying between two others
is closer to each than they are to one another — so pairs within tolerance are
always reachable through adjacent steps.

`fc_merge_modes` was deleted rather than kept: it was correct and irreducibly
one-dimensional, and `-Werror=unused-function` turns leaving it into a build
failure, which is the right pressure.

The cap is divided by the dimension. The 1-D limit was chosen for
Θ(iterations × n²); dim multiplies that, so it is not left to grow silently.

Scalar answers are unchanged — all ten methods' 1-D partitions are pinned, and the
new length scale is shared by every method's default radius, so this was the change
most likely to move one. A dim-1 point and the equivalent scalar are asserted to
agree, including where the answer is coarse: with three points the median of two
edge weights averages 1 and 98 into a scale of 49.5, which cannot resolve them, and
both forms return one cluster.

**A quirk found and recorded rather than silently fixed.** When the median edge
weight is zero — any tie-heavy input — the scale falls back to the mean, i.e.
range/(n − 1), and the flat kernel's default radius is three times the scale. At
n = 4 that radius is *exactly* the range, so an outlier sits precisely on the
inclusion boundary and `NeighborhoodContraction` merges everything however far away
it is placed. This is pre-existing 1-D behaviour, identical in both
dimensionalities, so changing it would move a pinned answer and belongs in its own
deliberate change.

Strings still decline for both: there are no coordinates to shift toward higher
density. The gap methods continue to handle them through edit distances in the tree.

## FindClusters: `"KMeans"` in n dimensions

`FindClusters[points, k, Method -> "KMeans"]` now clusters vectors, taking the count
of dimension-general methods to five of ten (`Agglomerate`, `SpanningTree`,
`MeanShift`, `NeighborhoodContraction`, `KMeans`).

**A second implementation, deliberately, not a generalisation.** The previous port
unified MeanShift's two dimensionalities because the n-D form provably reproduced
the 1-D answers. Nothing like that holds here: the 1-D kernel seeds at quantiles of
the sorted distinct values and the n-D one seeds farthest-first, and two
initialisations are two algorithms that settle in different local optima. Routing
one through the other would move pinned answers, so unification is a behaviour
change to argue for on its own, not a tidy-up. The n-D suite now asserts that the
two paths agree on the same data written both ways, which is what would catch them
being merged by accident.

What survives the port is the shape — assign, move the centres, repeat. What does
not is every mechanism the 1-D kernel used to do it quickly: a merge walk over
midpoints of *sorted* centres, a scalar mean over a contiguous run, and an
empty-cluster repair that picks value boundaries in sorted order. All three need a
total order vectors do not have.

**Farthest-first initialisation, and why it is not arbitrary.** The first centre is
the point nearest the centroid; each subsequent one is the point farthest from
everything already chosen.

- It is deterministic, as the quantile seeding it replaces was. There is no
  `RandomVariate` in the tree yet, and this keeps reproducibility from needing one.
- Seeding from the centroid rather than from index 0 makes the result **independent
  of the order the points were given in** — asserted against a permutation and a
  reversal — which a k-means has no business depending on.
- Every centre is a distinct data point, so each cluster starts owning at least
  itself. Distinctness is guaranteed rather than hoped for: the count is capped at
  the distinct-value count, so while fewer than that many centres are chosen some
  point is still at nonzero distance from all of them. A cluster that does empty is
  reseeded at the point currently farthest from its own centre — the order-free form
  of the 1-D boundary repair, and one that cannot loop, since the reseeded centre
  then owns at least that point.

**The ceiling is on `n × k × dim`, not on `n` — the shift methods' cap invites the
wrong shape by analogy.** Lloyd's algorithm is *linear* in `n`, and cheaper than the
spanning tree already built for the same input, so capping `n` would decline work
the builder had just finished paying for. 20000 machine points in ten dimensions is
admitted by `FC_NDIM_MACHINE_MAX_N`, and there is no reason for k-means to be the
step that refuses it: measured **0.60 s** at `k = 3` and at `UpTo[8]`, recovering
the planted groups exactly. What is declined is `k` on the order of thousands at
that size, where the assignment scan becomes a hundred near-quadratic passes. The
bound is conservative in one direction and knowingly so: `k == n` converges in a
single iteration, since farthest-first hands every point its own centre, so it is
refused by a budget that assumes the iteration count — refusing a degenerate request
is cheaper than modelling it.

`Automatic` remains refused for `KMeans` in *both* dimensionalities. That is
`FC_ALLOWED`, not a porting gap, and it is now asserted on both surfaces so the
decline is never mistaken for an unported path and "fixed". `UpTo[k]` is the
data-driven form, and a bare `k` is obeyed exactly — twelve points asked for nine
clusters return nine.

`DistanceFunction` applies: on `{{0, 0}, {0, 11}, {8, 6}}` the apex is nearer the
origin under Euclidean (10 against 11) and nearer the far point under Manhattan
(14 against 11), so the pair that clusters flips. Asserted where the metrics
genuinely differ, since a case both answer identically proves nothing.

Equal points are still never split — the fold over zero-weight tree edges is
kind-agnostic and covers the port for free. KMeans is the method most able to break
that on its own, since a count larger than the distinct-point count could only be
met by splitting a duplicate pair; the count yields instead.

One pin moved deliberately: `tests/test_list.c` recorded
`FindClusters[{{1, 1}, {9, 9}}, 2, Method -> "KMeans"]` as returning unevaluated,
and it now returns `{{{1, 1}}, {{9, 9}}}`.

## FindClusters: `"DBSCAN"` in n dimensions — and one kernel instead of two

`FindClusters[points, Method -> "DBSCAN"]` now clusters vectors: real
ε-neighbourhoods in place of a sorted window, and union-find in place of a
left-to-right sweep. Six of the ten methods are dimension-general.

**The interesting part is that this one *replaced* the 1-D kernel rather than
sitting beside it, and that KMeans could not.** The old kernel linked only
*adjacent* sorted pairs — "consecutive points, one of them core" — where DBSCAN
specifies any pair within ε joined through a core point. Those are not obviously
the same rule. At the default `MinPoints -> 2` they provably collapse together,
since a point with any neighbour inside ε is then automatically core and both
reduce to single linkage at ε; above that default the argument runs out.

So the question went to the pin suite rather than being settled by reasoning: all
22 one-dimensional pins pass through the general kernel unchanged, which says the
general rule is answer-preserving on a line and there is no case for a second
copy. That is exactly the test the pin suite was written for two iterations
earlier, and it is what distinguishes this port from KMeans, where the pins would
have moved and two paths were therefore the honest outcome.

`fc_eps_window` went with the old kernel — DBSCAN was its only caller, and
`-Werror=unused-function` turns leaving a dead 1-D helper behind into a build
failure.

Noise still becomes singletons rather than being dropped, which is what keeps the
result a partition of the input: `{{0,0},{1,0},{0,1},{1,1},{99,99}}` gives the
square and then `{{99, 99}}` alone. `MinPoints` does visible work — raised to 3 on
`{{0,0},{1,0},{50,50},{51,50},{52,50}}`, neither of the first two is core, so both
fall out separately while the triple survives. An explicit
`"NeighborhoodRadius"` reaches the n-D kernel too, not only the default derived
from the length scale.

Strings are now the *only* thing DBSCAN refuses: an ε-neighbourhood needs
coordinates, and edit distances live in the tree, which is what the gap methods
read.

One more pin moved on purpose: `test_list.c` recorded
`FindClusters[{{1, 1}, {9, 9}}, Method -> "DBSCAN"]` as unevaluated.

## FindClusters: `"JarvisPatrick"` in n dimensions

Real k-nearest-neighbour lists and a real set intersection replace index
arithmetic on contiguous windows. Seven of the ten methods now cluster vectors.

Lists are kept sorted by *index* rather than by distance so the intersection is a
linear merge, and selection breaks ties toward the lower index so the result does
not depend on scan order. A point is a member of its own neighbour list, matching
the 1-D window (which spans `sv[i]` *and* its k nearest) and the classical
formulation — two points that are each other's neighbours already share those two
members.

**The default `NeighborCount -> 5` needs groups with more than five points, and
this is worth stating because it looks like a bug.** A 5-nearest-neighbour list
cannot fit inside a 4-point blob, so it must reach into a neighbouring blob, which
then links them: the three 4-point blobs used elsewhere in the test suite come
back as *one* cluster, and `"NeighborCount" -> 3` recovers all three. The 1-D
kernel behaves the same way (a `k` clamped to `n - 1` puts every point in one
window), so this is the algorithm on data too small for its default. The n-D blob
test therefore uses eight points per blob; asserting the merge would have pinned a
data-sizing artefact instead of the method.

**This port corrected the procedure DBSCAN established.** DBSCAN was unified onto
one kernel because all 22 one-dimensional pins passed through the general rule.
The same experiment here also leaves all 22 pins passing — and still moves an
answer that `list_tests` covers and the pin file does not:

```
FindClusters[{1, 2, 10, 12, 3, 1, 13, 25},
             Method -> {"JarvisPatrick", "NeighborCount" -> 2}]
  1-D kernel:  {{1, 2, 1}, {10, 12, 13}, {3}, {25}}
  n-D kernel:  {{1, 2, 3, 1}, {10, 12, 13}, {25}}
```

So the criterion is "does any *covered* 1-D answer move", not "do the pins pass" —
the pin file is a floor, not the whole 1-D contract. The two rules differ because
the 1-D kernel counts shared neighbours as the overlap of two contiguous windows
and links only adjacent sorted pairs, where this one intersects sets over all
pairs. The general rule is very likely the better one, but adopting it on a line
moves a checked answer, so JarvisPatrick keeps two paths like `KMeans` and the
change is left to argue on its own.

Cost is the same order as the other neighbourhood methods: 0.0198 s at n = 2000 in
ten dimensions, against 0.0177 s for DBSCAN on the same input.

Also measured while checking DBSCAN's own ceiling, since the previous entry
asserted a cap without a number: DBSCAN is 1.73 s at n = 20000 in ten dimensions,
scaling cleanly 4x per doubling (0.0013 / 0.0046 / 0.0177 s at 500 / 1000 / 2000).
That is the same order as the spanning-tree build it follows, so the cap stands.

## FindClusters: `"KMedoids"` in n dimensions

Eight of the ten methods now cluster vectors; only `Spectral` and
`GaussianMixture` remain. KMedoids reuses `fc_lloyd_ndim` rather than duplicating
it — farthest-first initialisation already seeds with actual data points, which is
exactly what a medoid needs — and switches only the update step behind a flag, the
same shape the 1-D `fc_lloyd` already had.

**The medoid search is a different complexity class, not a different constant, so
it carries its own tighter ceiling.** A mean is `O(n·dim)`; a medoid compares every
member against every other member of its cluster and is `O(n²·dim)` however small
`k` is. The bilinear budget that admits 20000 points at a small `k` is therefore the
wrong bound here, and the cleanest evidence that the second ceiling is real is that
the *same* 2000×10 input separates the two methods: `"KMeans"` clusters it,
`"KMedoids"` declines.

**The two dimensionalities disagree, and the n-D answer is better — measured, not
asserted.** On `{1, 2, 3, 10, 11, 12, 25}` at `k = 3`:

```
1-D kernel (quantile seeding):     {{1, 2, 3}, {10}, {11, 12, 25}}   cost 16
n-D kernel (farthest-first):       {{1, 2, 3}, {10, 11, 12}, {25}}   cost  4
```

where the cost is the method's own objective, the total distance from each member
to its cluster's medoid. So this is not a port artefact to be hidden behind an
agreement assertion — the 1-D kernel is sitting in a four-times-worse local
optimum. Both are pinned as they actually behave, and adopting farthest-first on a
line is left as its own deliberate change.

**A negative result, recorded so it is not re-derived.** No test claims that
`"KMedoids"` and `"KMeans"` produce different *partitions*: 26 constructed cases
(hand-built plus a 20-point parameter sweep over an outlier's distance and a second
group's offset) all agreed. On well-separated data the medoid/mean distinction
shows up in where the centre *sits*, and only turns into a different partition when
a mean is dragged across a decision boundary. The discriminating evidence for the
port is the objective gap above and the ceiling difference, both of which separate
the methods on real input.

## FindClusters: `"Spectral"` in n dimensions

Nine of the ten methods now cluster vectors; only `GaussianMixture` remains.

**The step that looked one-dimensional was not the one that was.** The 1-D kernel
cuts the widest jumps in the *embedding*, and an embedding is one scalar per point
however many dimensions the data has — so "sort and cut the widest gaps" is a
statement about the Fiedler vector, not about the input. Sorting by embedding value
instead of by data value carries the rule across unchanged, and the k-means-on-the-
embedding step that seemed necessary turned out not to be.

Two real changes: the affinity is `exp(-(dist/h)²/2)` with `dist` from
`fc_dist_pos` and `h` from `fc_scale_ndim`; and the affinity matrix is
*precomputed* rather than rebuilt inside the power iteration. The 1-D kernel
recomputes `exp()` for every pair on every iteration, which costs nothing extra on
a line but would multiply by `dim` here. Precomputing is arithmetically identical,
so it is a speed change only; at the `FC_SPECTRAL_MAX_N` ceiling the matrix is
2000×2000 doubles, 32 MB.

**Connected components are read before the Fiedler vector, and this is the
substance of the port.** The multiplicity of the zero eigenvalue of the normalised
Laplacian equals the number of connected components, so with `c` components the
null space is `c`-dimensional and the leading non-trivial eigenvector is defined
only up to a rotation inside it; power iteration lands on whichever member the seed
favours, which separates two groups at best. This is the *easy* case rather than a
corner case — better separation means smaller cross-affinity, and
`exp(-(60/1.5)²/2)` is zero in double precision, not merely small. Three blobs in
five dimensions came back with two merged and the third split for exactly this
reason, while the same three in two dimensions survived on the luck of the seed.
Components are now read off with union-find, which is what the spectrum says to do
and needs no eigensolver. Asked via `UpTo[k]` for fewer clusters than there are
components, the nearest components merge first, ranked by the spanning tree —
the spectrum cannot choose, because every partition respecting components has zero
cut and all are optimal, so the tie-break has to come from somewhere.

**A threshold finding, and its mirror.** The natural count now compares embedding
jumps against the **mean** jump, not the median. A spectral embedding earns its keep
by collapsing within-cluster distance toward zero, so with tight clusters most jumps
are ~0, the median is ~0, and three times it admits nearly everything: two
well-separated 4-point blobs came back as *four* clusters and three as *five*, while
`UpTo[3]` recovered all three perfectly — the embedding was right and only the count
was wrong. The mean is correct because the jumps sum to the range, so
"wider than three times the mean" is a statement about a jump's share of the whole
spread; it gives 1 on uniform data and `c` on `c` tight clusters, and a lone outlier
inflates it only by `1/m`. The mirror image is why the two paths stay separate:
on raw *data* gaps the median is right and the mean under-counts, so routing scalars
through the n-D kernel turned `{{1,2,3},{10,11,12},{25}}` into
`{{1,2,3,10,11,12},{25}}`. Each statistic is right in its own domain.

**A crash fixed.** `n < 3` has to be handled on the point path itself. Falling
through to the 1-D branch reaches `fc_scatter`, which indexes `d->order` — `NULL`
for point input — so `FindClusters[{{1, 1}, {9, 9}}, Method -> "Spectral"]`
segfaulted. It now returns one cluster, and that row is pinned.

## FindClusters: `"GaussianMixture"` in n dimensions — and the first `src/ml/` module

**All ten `FindClusters` methods now cluster vectors.** The only input still declined
above one dimension is a list of strings, which has no coordinates.

**This one's kernel deliberately does not live in `find_clusters.c`.** The EM fit is
`src/ml/gmm.c`, behind a buffer-level API taking a row-major `n × dim` array rather
than a `FindClusters` internal. The reason is not tidiness: `find_clusters.c` holds
55 static functions and exports exactly *one* symbol, so nothing in it is reachable
from a second builtin — and `GaussianMixture` is the first clustering kernel with two
real consumers, this `Method` and the `LearnDistribution` learner of the same name.
A 56th static function would have forced the distribution learner to re-implement EM.
`ClusteringComponents`, `ClusteringTree`, `Dendrogram` and `NearestNeighborGraph` are
blocked on the same wall. What stayed in `find_clusters.c` is what is genuinely its
business — turning a fit into a partition, and choosing `k`; what moved is what is
nobody's in particular: covariances, Cholesky factors, Mahalanobis distances and a
log-density (`ml_gmm_logpdf`, which is what makes the fitted object a *density*
rather than a partition, and the entry point the distribution learner will use).

Note for anyone adding a directory under `src/`: `makefile`'s `SRC` line is an
explicit per-subdirectory glob list, **not** recursive, so a new directory is
silently never compiled until it is named there. `tests/CMakeLists.txt` collects
sources explicitly too.

Three things are not mechanical generalisations of the scalar kernel:

- **The variance floor becomes a ridge, not a clamp.** `if (var < floor) var = floor`
  has no direct matrix reading; the honest translation is "no direction may have
  variance below the floor", which is a clamp on eigenvalues and costs an
  eigendecomposition per component per iteration. Adding `floor·I` raises every
  direction by exactly the floor, enforcing the same lower bound for one add — it can
  only overshoot, never undershoot — and it is what makes the factorisation succeed on
  a component with fewer points than dimensions.
- **The E-step runs in log space through log-sum-exp.** A component's density is a
  product of `dim` factors, so in linear space a point a few standard deviations from
  every mean underflows the total to zero. The scalar kernel answered a zero total by
  handing that point *uniform* responsibilities — survivable on a line, and actively
  wrong here, since the outlying points are the informative ones.
- **A component whose covariance will not factorise falls back to diagonal** rather
  than failing the fit, so a rank-deficient component (fewer points than dimensions,
  or collinear ones) does not take the whole model with it.

The Cholesky is written in-house rather than routed through `mat_lapack_dpotrf`.
LAPACK is right for a large factorisation, but `dim` is a feature count — single
digits in practice — and this runs once per component per iteration where the cost is
entirely the `O(n·k·dim²)` E-step. Twenty lines with no conditional dependency on
`USE_LAPACK` is the better trade at this size, and the call site is one function if
that ever changes.

**Unified onto one kernel, like DBSCAN.** Routing scalars through the n-D fit left
every covered 1-D answer unchanged — all 22 pins *and* the `list_tests` capability
rows — so the 1-D body and its scalar EM (`fc_gmm_fit`) were deleted rather than kept
alongside. That is the second unification of the eight ports; `KMeans`, `KMedoids`,
`JarvisPatrick` and `Spectral` each kept two paths because the general rule moved a
covered answer.

**Full covariance needs more points per component than dimensions,** and the tests say
so rather than working around it. `k_max` is capped at `n/(dim + 1)`, the minimum for
a non-degenerate scatter matrix, so the nine-point five-dimensional probe the other
methods use correctly returns **one** cluster while twenty-four points per blob
recover all three. Same shape of finding as JarvisPatrick's `NeighborCount` not
fitting inside a 4-point blob: the default is wrong for the data, not the code.
Singular components are asserted directly — four identical points, and five collinear
ones — because the ridge and the diagonal fallback are the only reasons they work.

## Machine learning family 2 begins: `Standardize`, `PrincipalComponents`, `src/ml/pca.c`

The first **new builtins** of the machine-learning work rather than ports, and the
start of Wolfram's DimensionReduction family. Neither `Standardize` nor
`PrincipalComponents` existed; nor do `DimensionReduce`, `MultidimensionalScaling` or
`LatentSemanticAnalysis` yet, which are the next items.

New docs page: [`docs/spec/builtins/machine-learning.md`](../builtins/machine-learning.md).

**Kernels are buffer-level in `src/ml/pca.c`, following `gmm.c`.** Column means and
standard deviations are wanted by `Standardize`, by PCA, by a future `Classify`'s
feature scaling and by `LearnDistribution`'s Multinormal; the symmetric
eigendecomposition is wanted by PCA, by MDS and by LSA. Writing them against an `Expr`
would have put all of that behind a builtin.

**A surface bug found and fixed before it shipped.** The obvious way to return a
machine matrix is `na_build_matrix`, the exported bridge the LAPACK builtins use — and
it returns a **visible `NDArray`**, whose head is `NDArray`. So the first version had
`Standardize[data] === {{…}}` evaluating to **False** against the literal a user would
write, while `Inverse[m] === {{…}}` is `True`: `Inverse`, `Dot` and `LinearSolve` all
return head `List` and let the evaluator's packing gate hold the buffer. The builtins
now build plain `List`s, and a test row pins `Head[…] == List` so the next new builtin
does not repeat it. This was found by *comparing surfaces*, not by assuming the bridge
was appropriate — worth recording because nothing in the bridge warns about it.

**Eigenvector signs are canonicalised**, and this is what makes the output testable at
all. An eigenvector is defined only up to sign, and LAPACK's `dsyev` and the in-house
Jacobi fallback disagree about which they return — so without canonicalisation the
same input gives sign-flipped components depending on how the binary was linked. Each
component is flipped so its largest-magnitude loading is positive.

No `#ifdef USE_LAPACK` at the call site: `mat_lapack_dsyev` is declared
unconditionally and the no-LAPACK build links a stub returning nonzero, so "did it
work" is the same question either way and the Jacobi fallback hangs off the status.
Jacobi is hand-written for the reason `gmm.c`'s Cholesky is — the in-tree symmetric
solvers are `static` to their translation units, `dim` is a feature count, and this
runs once per call.

Assertions in `tests/test_ml_pca.c` are properties any correct implementation must
satisfy, not numbers this one happens to produce, since there is no prior behaviour to
pin:

- `Standardize` must equal `(x - Mean[x])/StandardDeviation[x]` written out by hand,
  which also forces the `n - 1` divisor to match `StandardDeviation`'s — a divisor
  mismatch is invisible on a mean but not on a scale.
- The PCA rotation is orthogonal, so **total variance is preserved** while being
  concentrated in the leading component. Both halves matter: a projection that lost
  variance would still pass a "PC1 is largest" check. Measured 14.0 before and after.
- Rank-one data (five points on a line) must put *exactly* zero in the second
  component.
- `Correlation` must differ from `Covariance` where the columns' scales differ, since
  that is the only case in which the option means anything — a test passing for both
  would prove nothing.
- A constant column standardises to `0`, not `Indeterminate`.

## `DimensionReduce`, with PCA, LSA and classical MDS

Closes the data-in/data-out surface of Wolfram's DimensionReduction family.
`DimensionReduce[data, k]` and `DimensionReduce[data, k, Method -> m]` for
`"PrincipalComponentsAnalysis"` (default), `"LatentSemanticAnalysis"` and
`"MultidimensionalScaling"`.

**The three methods turned out to be one algorithm with three ways of forming the
symmetric matrix to decompose**, which is why they share `ml_sym_eigen_desc` instead
of each carrying its own linear algebra:

| Method | Matrix decomposed |
|---|---|
| PCA | covariance of the **centred** columns |
| LSA | Gram matrix `X'X`, **uncentred** — which *is* a truncated SVD |
| MDS | double-centred squared-distance matrix (Torgerson) |

Two consequences worth stating. LSA needed **no separate SVD path**: the
eigendecomposition of `X'X` gives the same right singular vectors, so the single `if`
that skips the centring is the entire mathematical difference between principal
components and a truncated SVD. And skipping it is not an optimisation — a
term-document matrix is sparse and non-negative, and centring destroys both properties
along with the meaning of a zero entry.

**The strongest piece of evidence in this family so far:** classical MDS on Euclidean
distances reproduces PCA *exactly* — agreement to 1e-8 on the test data — by a
completely different route, an `n × n` double-centred distance matrix rather than a
`dim × dim` covariance. Because the two paths share almost no code, that agreement is
evidence about **both** implementations in a way no self-consistency check could be.
It is asserted in the suite, on absolute values, since an eigenvector's sign is
arbitrary and the two matrices have different shapes so the sign canonicalisation
cannot force the same choice for both. It also means MDS earns its keep only when the
distances come from somewhere other than the coordinates.

Also asserted: reducing to `k` gives *exactly* the first `k` principal components
rather than a separately-fitted `k`-component model, which is what would catch a
reducer that re-derived its axes from a truncated matrix.

`"MultidimensionalScaling"` is capped at 2000 rows, its matrix being `n × n` — the same
order of ceiling, for the same reason, as `FindClusters`' `"Spectral"`.

Asking for more dimensions than the data supports **returns unevaluated rather than
padding with zeros**, since padding would look like a successful reduction to a caller
checking only the shape. An unknown `Method`, a non-positive `k`, an omitted `k` and a
flat list all decline as well.

**Deliberately not implemented:** a `DimensionReducerFunction` applicable to *new*
data. That is a trained model, and the model representation is being designed with the
`Predict` family rather than invented twice — the same reasoning that put the GMM fit
in `src/ml/` before `LearnDistribution` existed.

## Machine learning family 3: `Predict`, `LinearModelFit`, and the trained-model representation

The design task two earlier families deferred to here. `DimensionReduce` could not
return a reusable reducer and `Classify` cannot return a classifier until a **fitted
model** can be represented as an expression that survives storage and re-application.
Decided once, in `src/ml/predict.h`.

**The decision: a plain expression whose head is a symbol and whose arguments are
ordinary expressions.** Two richer designs were rejected, and the obvious one is among
them:

- **A new opaque node type, following `EXPR_COMPILED`** — the codebase's existing
  precedent for a callable carrying binary state, and the answer this was expected to
  reach. Rejected because `EXPR_COMPILED` exists to hold a *VM program*: bytecode, a
  register file, a reference count. A fitted linear model is a short vector of numbers.
  A new node type means new cases in `expr_copy`, `expr_free`, `expr_eq`, `expr_hash`,
  `expr_compare` and `print.c` — touching the core of the system — to store what the
  existing types already hold. Machine precision is not an argument either: a packed
  List already holds a dense double buffer and is still an ordinary List.
- **An `Association` payload**, the most Wolfram-ish shape. Rejected because it buys
  nothing positional arguments do not, while adding an Association dependency to every
  read. Named properties are still exposed — through the *application* path
  (`p["Coefficients"]`), which is where a user reaches for them anyway.

**Application reuses the evaluator's existing composite-head chain.** `eval.c` already
dispatches `Function[…][args]` and `Association[…][key]` by matching on the head's own
head; a fitted model is one more branch in the same chain, so no new evaluation concept
is introduced. A probe function keeps `eval.c` from having to know the model head names.

`Predict[data]` takes either `{features -> value, …}` or a matrix whose last column is
the response, and returns a `PredictorFunction` answering `"Method"`, `"Coefficients"`
and `"FeatureCount"`. `LinearModelFit` returns the same object under the name a reader
of regression code looks for; Wolfram's regression diagnostics (`RSquared`, standard
errors, ANOVA) are **not** implemented and not approximated.

**The verification that matters is agreement with an independent implementation.**
`Fit` already solves least squares in this tree by a different route, and it and
`Predict` agree — `Fit` gives `1.0 + 2.0 x` where `Predict` gives `{1.0, 2.0}`, and the
test asserts agreement at two evaluation points rather than comparing presentations.
That is the same kind of cross-check that validated classical MDS against PCA, and it
is worth more than any hand-chosen constant.

`ml_ols` solves the **normal equations** by Gaussian elimination rather than calling
LAPACK's `dgels`. `dgels` is numerically better — a QR avoids squaring the condition
number — but `A'A` is `(dim+1)` square, a handful of rows at any realistic feature
count, and the normal equations make the singular case *directly* detectable as a zero
pivot. That matters because **declining on a singular fit is deliberate behaviour**
here: collinear features have no unique fit, and a pseudo-inverse would return one of
infinitely many answers while looking like a success.

One test of mine was wrong rather than the code: `Head` of an unevaluated composite
application is the whole head `PredictorFunction[…]`, not the symbol, so the assertion
that a wrongly-shaped input does not produce a prediction became `NumberQ[…] == False`.

## `Predict` with `"NearestNeighbors"`, and `src/ml/mlutil`

`Predict[data, Method -> "NearestNeighbors"]`, with
`Method -> {"NearestNeighbors", "NeighborsNumber" -> k}` to set the neighbour count.

**A nearest-neighbour predictor has no fitted parameters — the training set *is* the
model**, which is why it costs nothing to fit and everything to apply. It is stored as
one matrix with each row's response appended, so features and labels cannot drift
apart. `k` defaults to 3 (enough to average away one noisy response, few enough to stay
local) and is clamped to the number of training rows. Selection is a partial
insertion into a `k`-sized list rather than a sort of all `n`, with ties keeping the
earlier row so the answer does not depend on scan order.

That the parameter slot holds a coefficient list for one method and a training matrix
for another is not a wart — it is why the model representation is *positional with a
method tag* rather than a fixed schema, and why application dispatches on the tag.

**`"NeighborsNumber"` on a `"LinearRegression"` is refused, not ignored.** Silently
accepting a meaningless option hides a real mistake. So does an unrecognised
sub-option, and a non-positive `k`.

**Cross-checked against the existing `Nearest`.** A 1-neighbour predictor must return
the label of whatever `Nearest` picks, and it does — at six query points including both
sides of a midpoint (2.4 → 2.0, 2.6 → 3.0), so the tie-breaking region is actually
exercised. The limit is worth stating: `Nearest` supports only the one-neighbour scalar
form here (its `k` form and its point form decline), so this validates neighbour
*selection* at `k = 1` and says nothing about the averaging, which is asserted directly.

**`src/ml/mlutil.{c,h}`** promotes the helpers that had reached three copies —
`ml_list_of_reals`, `ml_list_matrix`, `ml_read_data`, plus `ml_sqdist`. Two copies is a
coincidence; three is a shared need, and that was the stated trigger.

**An extraction deliberately NOT done.** `find_clusters.c` has a real
machine-precision metric layer (`fc_dist_pos`, `fc_dist_to_point`) that honours a
`DistanceFunction` — and it stays private. Extracting it means introducing a metric
enum in `src/ml` and rewriting a 2600-line file whose 22 one-dimensional answers are
pinned: real risk to a finished family, bought for a four-line squared Euclidean. The
honest trigger is a `src/ml` consumer that needs *metric selection* rather than one
that needs Euclidean — the moment `Predict` or `Classify` gains a `DistanceFunction`
option, that layer has its second real consumer and the refactor pays for itself. This
is the same "extract at the second real consumer" rule that put the GMM fit in
`src/ml`, applied in the direction of *not* acting.

One test of mine was wrong for precisely the reason recorded in this project's own
guidance — "a case where both branches answer identically proves nothing". The
k-NN-differs-from-linear assertion used data that was exactly `y = 10x`, where a
neighbour average at an interior point *equals* the linear prediction, so it passed
while demonstrating nothing. Rewritten on `y = x²`, which has curvature a line cannot
follow.

## `DimensionReduction`: a reusable reducer, and the representation paying off

`DimensionReduction[data, k]` returns a `DimensionReducerFunction` applicable to data it
was never trained on. Wolfram's split is kept: `DimensionReduce[data, k]` gives the
reduced *training* data, `DimensionReduction[data, k]` gives the *reducer*. This closes
the last open row of the DimensionReduce family, which had been deliberately blocked on
the model representation since two iterations earlier.

**The retrofit needed no new machinery**, and that is the point worth recording. A
reducer is the *same* positional, method-tagged object a `PredictorFunction` is, so
adding it required no new `EXPR_` node type, no new evaluation concept, and no change to
`eval.c` beyond the existing probe recognising one more head. That is the return on
having designed the representation once, in one place, rather than per family — and it is
the evidence that the design was the right size rather than merely the smallest.

**The one real hazard was centring, and it is a bug that hides well.** New rows must be
centred on the **training** column means. The plausible alternative — centring each
incoming batch on its own mean — gives *all zeros* for a single point, which is
indistinguishable from a correct projection on data that happens to sit near the origin.
The test therefore trains on data with means `{104, 210}` and asserts both halves: a
point *at* the training mean projects to `0` (which identifies *which* mean is
subtracted), and a point away from it projects far from `0` (which is what fails on the
bug). A symmetry row is added on top: points equally far either side of the training mean
must project to equal magnitudes of opposite sign.

Verified against the sibling builtin too: on its own training data the reducer reproduces
`DimensionReduce` exactly, so the two cannot have drifted apart in centring or
projection.

Only `"PrincipalComponentsAnalysis"` is offered as a reducer. That is a real limit rather
than an omission: classical MDS has no out-of-sample extension without an explicit one
(Nyström), and an LSA reducer would need the term-document vocabulary carried along with
it.

**A note on the session rather than the code:** the automation driving these iterations
was paused for a stretch here because the permission classifier was unavailable, which
blocked scheduling and then shell access. No partial writes occurred — a rejected call
never executes — and the tree stayed clean at the previous commit.

## Fitted models print abbreviated — family 3 closed

`PredictorFunction` and `DimensionReducerFunction` now print their method and elide their
parameters: `PredictorFunction["LinearRegression", <>]`.

**Not cosmetic.** A `"NearestNeighbors"` predictor carries its *entire training set* as its
parameter block, so the unabridged form is unreadable at any real size and scrolls the
useful answer off the screen.

**And not a new scheme** — `print.c` already had this pattern.
`InterpolatingFunction` prints its domain then `, <>`, and its own comment states the
reason: *"FullForm (handled separately) still reveals the full structure."* That is what
makes eliding safe rather than lossy, and it is why following the existing precedent was
better than designing something. The new branch sits directly beside it.

`SYM_PredictorFunction` and `SYM_DimensionReducerFunction` were interned in
`sym_names.c`, per the project convention, rather than string-comparing head names inside
the printer.

The tests assert **both halves**, which is the part that matters: the abbreviated form
*and* that `FullForm`, application, and property access are all untouched. This is a
rendering change, so a change that had instead reached into the object would pass the
first assertion and fail the second — `Length[model["TrainingData"]]` still returns 5.

One error of mine, worth noting for anyone writing similar tests: the C test harness
renders strings *with* quotes where the REPL's `Print` does not, so the expected value is
`PredictorFunction["LinearRegression", <>]` and not the unquoted form the REPL shows.

**Family 3 (Predict) is now closed**, and with families 1 and 2 that is three of the five
Wolfram machine-learning families: clustering (all ten methods, n-dimensional),
dimensionality reduction (PCA / LSA / MDS, plus a reusable reducer), and prediction
(linear regression and nearest neighbours, on a shared trained-model representation).

## Machine learning family 4 begins: `RandomVariate`, `PDF`, distribution objects

The sampling substrate `LearnDistribution` needs. **There was no Gaussian deviate
anywhere in the tree** — `RandomReal` is uniform and the xoshiro stream under it produces
uniforms — so no distribution-based method could sample at all. `RandomVariate`, `PDF`,
`NormalDistribution` and `UniformDistribution` are all new.

**Draws come from the user-visible stream**, via `random_uniform_01` (now exported from
`random.h` rather than `static`). That is the whole reason `SeedRandom` applies to them. A
sampler with its own generator would leave reproducibility **half working** — honoured by
`RandomReal`, silently ignored by `RandomVariate` — which is worse than not working at
all. Note `random_internal_int_range` is explicitly *not* the path for this: it is
reserved for internal decision procedures that must not perturb the user-visible stream,
the opposite requirement.

**The non-obvious bug, fixed by design rather than found by accident.** Box–Muller
produces deviates in *pairs*, so the implementation caches the spare. That means
`SeedRandom` must also clear the cache — otherwise the first draw after reseeding comes
from the *previous* stream. What makes this worth a test rather than a comment is that it
only shows after an **odd** number of prior draws: an even number leaves the cache empty
and hides it completely. Both parities are asserted.

Box–Muller in its **polar** form, which needs no `sin`/`cos` — rejecting the corners of
the square is cheaper than two transcendental calls per pair.

**A specified distribution is deliberately NOT the trained-model representation**, even
though the two look alike. A distribution is *written by the user*, so its parameters are
the information and it prints in full; a fitted model *derives* its parameters and elides
them. Same mechanism, opposite convention on visibility — and a test row pins the full
printing so a later change cannot merge them by accident.

**Invalid parameters decline rather than producing `NaN`.** A non-positive standard
deviation or an inverted range would otherwise propagate `NaN` through an entire sample
and surface much later as a strange plot. `RandomVariate[dist, 0]` is a valid empty
request, not an error.

**Testing a sampler** is awkward because its output is meant to be unpredictable, so the
assertions cover the three things that *are* deterministic: reproducibility under
`SeedRandom`, the **moments** of a large sample (which pin the shape without pinning any
draw — mean 5.00479 and sd 1.99627 against 5 and 2 at n = 20000), and the **PDF**, which
is closed-form and is checked against the same formula written out symbolically.
That last one is a genuine independent cross-check: `PDF[NormalDistribution[], 0]` equals
`1/Sqrt[2 Pi]` as computed by the existing symbolic machinery, which shares no code with
the C density function. Moment tolerances are ~7 standard errors, loose enough not to
flake and tight enough to catch a wrong variance.

## `LearnDistribution` with `"Multinormal"`

`LearnDistribution[data]` fits a mean vector and a sample covariance and returns a
`LearnedDistribution` usable with `PDF`. The covariance uses the `n - 1` divisor, matching
`Variance`, so a one-variable fit agrees with `StandardDeviation` squared.

**Cholesky and Mahalanobis were promoted out of `gmm.c` into `src/ml/mlutil`** — the
second real consumer, which is the same rule that promoted the list builders and that
*declined* to extract `find_clusters.c`'s metric layer. The GMM suite was re-run
immediately after the move, before anything else was built on top, so the promotion was
verified as behaviour-preserving rather than assumed.

**The independent cross-check is unusually strong here.** A one-dimensional fit reaches
its density through a Cholesky factor and a Mahalanobis distance;
`PDF[NormalDistribution[mu, sigma], x]` evaluates the scalar closed form. They share no
code, and they agree exactly — including 3.5σ into the tail, which is where a wrong
log-determinant or a missing `2 pi` would show up as a *small relative* error rather than
an obvious one.

**A normalisation test was added on top of that**, because agreement alone is not enough:
two densities that shared a normalisation error would agree with each other perfectly.
The fitted density integrates to `1.0` over ±6σ by a trapezoid sum, which pins the
constant absolutely.

**A singular covariance returns unevaluated.** Collinear columns, or fewer observations
than dimensions, mean no density exists — a pseudo-inverse would invent one.

**One asymmetry worth knowing:** for a multinormal, `PDF[dist, {x1, …, xd}]` is *one*
point, because the argument is itself a list, while a *matrix* threads to one density per
row. That is the opposite reading from the scalar case, and it has to be — reading a flat
list as many points would silently treat each coordinate as a separate observation.

The fitted object prints elided (`LearnedDistribution["Multinormal", <>]`), the deliberate
opposite of a *specified* distribution, and both conventions are pinned by tests so a
later change cannot merge them.

## `LearnDistribution` with `"GaussianMixture"`

The payoff for extracting `ml_gmm_fit` / `ml_gmm_logpdf` into `src/ml/gmm.h` back in
iteration 9: this method is mostly wiring, because the EM fit was already a reusable
buffer-level kernel rather than a static function inside `FindClusters`.

BIC over `k = 1..k_max` chooses the component count — **one** component for unimodal data,
**two** for bimodal, with the fitted means landing on the modes and equal weights.
`k_max` is bounded by the parameter count rather than the point count, since a full
covariance costs `dim(dim+1)/2` numbers per component.

**The variance floor is the squared median nearest-neighbour distance, and it is
load-bearing rather than defensive.** A mixture's likelihood is *unbounded above* — a
component collapsing onto a single point drives its density to infinity — so with a floor
set merely "small" the BIC search buys arbitrarily many near-singular spikes. That was
measured in the clustering path before its floor existed: six components for eight points.
The median nearest-neighbour distance is the standalone analogue of the median
spanning-tree edge weight `fc_gmm_ndim` uses, and says the same honest thing: structure
finer than the sample spacing is not resolvable. The **median** rather than the mean, so
one tight pair cannot drag the floor toward zero and reopen the hole.

**The planned cross-check turned out not to be exact equality — and pinning down why made
the test stronger than the one intended.** A one-component mixture does *not* equal the
Multinormal fit, because EM maximises the likelihood and so uses the ML (`n`) divisor,
while `"Multinormal"` uses the unbiased (`n-1`) divisor to agree with `Variance`; the
mixture then adds the ridge. The relationship is therefore exact:

```
cov_mixture = ((n-1)/n) · cov_multinormal + floor
1.41        = (40/41)   · 1.435           + 0.01
```

with the floor `0.01` being the squared 0.1 spacing of the test data. A fuzzy "the ratio
is about 1.009" assertion would have hidden a wrong divisor *or* a wrong floor; this pins
both terms. Both estimators are standard and each is correct for what it is.

The density is also asserted **bimodal** (each mode more than a thousand times the valley
between them, which a single wide Gaussian could not manage) and **normalised** (the
trapezoid sum is 1, which a mixture with weights not summing to one would fail while still
looking bimodal).

Cholesky factors and log-determinants are **recomputed on read** rather than stored in the
payload — they are derived, and storing them would double the payload while creating two
places for one fact to live. Same choice the Multinormal path makes.

## `SmoothKernelDistribution` — and machine learning family 4 is closed

A kernel density estimate returned as a `LearnedDistribution`. The sample *is* the model:
nothing is fitted except the bandwidth, so a KDE costs nothing to build and everything to
evaluate — the same trade as a nearest-neighbour predictor.

The kernel is a **product Gaussian** with a per-dimension bandwidth. A full-covariance
kernel would need a bandwidth *matrix*, and estimating one from the same sample it smooths
is a substantially harder problem than the default rule solves — so the diagonal kernel is
the honest scope rather than a simplification. The default bandwidth is the multivariate
normal-reference rule `h_a = sigma_a (4/((dim+2) n))^(1/(dim+4))`, which in one dimension is
exactly Silverman's `1.06 sigma n^(-1/5)`. It **oversmooths strongly multimodal data**,
which is a known property of a normal-reference rule and the reason the explicit-bandwidth
form exists.

**The verification is an exact identity, not an approximation.** A KDE is the empirical
distribution *convolved* with the kernel, so its mean is exactly the sample mean and its
variance is exactly the ML sample variance plus `h²`. One assertion therefore pins the
bandwidth rule, the kernel's own variance, and the normalisation together — break any of
the three and it fails.

**And the way it first failed is the useful part.** The identity came out 1.6e-5 off. The
obvious explanation was quadrature error in the numeric integration, so the grid was
refined four times — 0.05, 0.02, 0.01, 0.005 — and the error *did not move at all*. That
constancy is what identified it: not quadrature error, but a wrong **constant** in the
test, the familiar rounded `1.0592` instead of the exact `(4/3)^(1/5) = 1.059224`. With the
exact constant the identity holds to `3.8e-15`. Loosening the tolerance would have hidden a
real (if small) discrepancy behind a plausible excuse.

**`ContingencyTable` is recorded as out of scope rather than implemented.** It builds a
table over *categorical* data, and the categorical encoding it needs is precisely what
family 5 (`Classify`) has to design. Building it first would mean inventing that encoding
twice, so it is deferred to that family as a follow-up.

**Family 4 is closed**, and with it four of the five Wolfram machine-learning families:
clustering (all ten methods, n-dimensional), dimensionality reduction (PCA / LSA / MDS plus
a reusable reducer), prediction (linear regression and nearest neighbours), and
distributions (`RandomVariate`, `PDF`, Multinormal, Gaussian mixtures with BIC, and kernel
density estimation).

## Machine learning family 5 begins: `Classify`, and the categorical label vocabulary

The piece every earlier family avoided. Clustering, dimensionality reduction, prediction and
distributions all took numeric features and produced numeric answers; `Classify` is where a
**class** arrives, and a class is a string, a symbol, a number, or whatever the user names
it. So something has to turn arbitrary expressions into the dense indices an algorithm can
count with, and back again.

**The label vocabulary gets its own module** (`src/ml/encode.{c,h}`) rather than living
inside `classify.c`, designed once for exactly the reason the model representation was: a
`ContingencyTable`, a categorical *feature* encoder, and any second classifier all need
precisely this, and three copies would be three chances to order the classes differently —
which would make two models disagree about what class 0 means.

Order is **first appearance** in the training data, not sorted. `expr_compare` could supply
a total order, but first appearance is stable under adding classes later, matches how
`FindClusters` numbers its clusters, and reads naturally beside the data that produced it.
What matters is only that it is deterministic — and the *prediction* does not depend on it,
which is asserted.

Class comparison is `expr_eq`, so `"a"` and `a` are **two** classes. That is the same
structural distinction the pattern matcher makes everywhere else; pretending otherwise would
be a silent surprise.

**`ClassifierFunction` is the fourth head on the model representation** from iteration 12,
after `PredictorFunction`, `DimensionReducerFunction` and `LearnedDistribution` — and it
needed no change to that design. Adding it was the documented three steps (extend the probe,
add an apply function, register the head) plus one line in the printer. The payload stores
class *indices* alongside the features, with the vocabulary separate, so the numeric part of
the model stays numeric and a class is named in exactly one place.

**Only the rule form `{features -> class, …}` is accepted, and that is not an omission.** A
matrix with the class in its last column cannot work, because a class need not be a number
and the numeric matrix reader would refuse the entire input. `Predict` accepts a matrix
precisely because its response *is* numeric.

`k` defaults to **1** here, unlike the k-NN *predictor* where it defaults to 3. A regression
averages, so a little smoothing helps; a classifier votes, and at `k = 1` it reproduces its
training labels exactly.

**Both verifications are absolute rather than comparative**, which is what makes them worth
more than an accuracy figure — an accuracy percentage hides *which* rows are wrong:

- a `k = 1` classifier must reproduce **every** training label, because each training point
  is its own nearest neighbour. All six, exactly, not "high accuracy";
- class probabilities must **sum to 1** — asserted at `k = 5` as well, where the vote is a
  genuine 0.6/0.4 split rather than a degenerate 1.0/0.0 that would sum to 1 even with a
  broken normalisation.

## `Classify` with `"NaiveBayes"`

Adding a **method** to an existing head turned out smaller than adding the head was: it is a
dispatch on the method tag inside the fit and apply functions already there — no new
registration, no printer change, no evaluator change. That is the third distinct shape of
extension the model representation has absorbed without modification.

Gaussian naive Bayes: per class a mean and a per-feature variance plus the prior, classified
by the largest log posterior. "Naive" is the independence assumption — the joint density is
the *product* of per-feature densities, i.e. a diagonal covariance — which is why it needs
no Cholesky and works with far fewer points per class than the full-covariance Multinormal.
Everything is computed in log space and softmaxed once, for the reason the mixture and the
KDE are: a product of `dim` densities underflows for a point several standard deviations out
in every feature, and there it would silently make every class equally improbable exactly
where the answer is most obvious.

**The variance floor is load-bearing, and its *form* matters.** A class whose feature takes
one value everywhere has zero variance there and therefore infinite density at that value —
it would win every comparison involving that feature. Same class of problem as the mixture's
unbounded likelihood. But the floor here is a fraction of the feature's **overall** variance
across all classes, not a fixed epsilon, which makes it **scale-invariant**: the same feature
measured in millimetres and in kilometres gets proportionate floors, where a fixed epsilon
would be enormous for one and negligible for the other. Per-class variances use the ML (`n`)
divisor, and the floor is what makes that safe for a single-member class.

**Verified against a closed form, at the boundary.** With one feature and equal priors the
decision reduces to "which prior-weighted Gaussian density is larger", which
`PDF[NormalDistribution[…]]` computes by a completely separate path. The two agree at eight
query points including **4.9 and 5.1** — either side of the boundary at 5.0 — so the test
exercises the decision itself rather than two obviously-separated regions. This also pins the
per-class divisor: using the unbiased `n-1` form instead of ML `n` would shift the boundary
slightly, and the straddling points would catch it.

`"NeighborsNumber"` is refused on a Bayes classifier rather than ignored, and
`"NeighborCount"` is not one of its properties — a meaningless option silently accepted
hides a real mistake. Both methods coexist on the one head, which is asserted.

## `Classify` with `"LogisticRegression"` — and all five machine-learning families are complete

Two-class logistic regression by iteratively reweighted least squares, which is Newton's
method on the log-likelihood: each step is a weighted least squares with weights `p(1-p)`.
More than two classes **declines** rather than silently binarising — multi-class needs
one-vs-rest or a softmax, and guessing which would be worse than saying no.

**The ridge is load-bearing, not cosmetic.** On linearly separable data the unpenalised
likelihood is *unbounded*: pushing the coefficients to infinity drives every fitted
probability to 0 or 1 and the likelihood to its supremum, so plain Newton diverges and never
converges. A small ridge on the non-intercept coefficients makes the penalised objective
strictly concave, so the fit is finite and unique even when the data is separable, with the
iteration count capped as a backstop. The intercept is left unpenalised, which is standard —
shrinking it would bias the predicted base rate. This is the same shape of problem as a
mixture's unbounded likelihood, and it gets the same treatment: penalise, cap, and say so,
rather than hang.

**Verified by an exact identity rather than an accuracy figure.** The fitted boundary is where
`intercept + coef·x = 0`, and the probability there must be *exactly* 0.5, because that is
what the logistic of zero is. That one assertion ties the **fit** and the **application**
together — any error in how coefficients are stored, read back, or recombined at application
time breaks it. On data with a gap from 3 to 7 the boundary lands at exactly 5.0, with
coefficients `{-33.27, 6.65}`: finite, which is the ridge working. A separate row asserts the
coefficients stay bounded, so removing the ridge as "unnecessary" fails a test rather than
silently producing a non-converged fit.

### Two deferrals, recorded rather than done badly

**`DecisionTree` / `RandomForest` are deferred.** They reuse *nothing* built across the five
families — no distance, no density, no label-index arithmetic, no linear algebra. A tree needs
an impurity criterion, a recursive splitter, a stopping rule and its own node representation
in the model payload; a forest needs bootstrap resampling and feature subsampling on top. That
is a family-sized piece of work rather than an iteration, and implementing it thinly to claim
coverage would be worse than naming the gap.

**`ContingencyTable` is deferred too**, though it is now *unblocked* — `src/ml/encode.h` is
exactly the categorical encoder it was waiting for. It is a cross-tabulation utility rather
than a learning method, so it sits outside the five families this work was scoped to, and it
is cheap to add later on top of the vocabulary.

### All five families

| Family | Surface |
|---|---|
| Clustering | all ten `FindClusters` methods, n-dimensional |
| Dimensionality reduction | `PrincipalComponents`, `Standardize`, `DimensionReduce` (PCA / LSA / MDS), `DimensionReduction` |
| Prediction | `Predict` (LinearRegression, NearestNeighbors), `LinearModelFit` |
| Distributions | `RandomVariate`, `PDF`, `LearnDistribution` (Multinormal, GaussianMixture), `SmoothKernelDistribution` |
| Classification | `Classify` (NearestNeighbors, NaiveBayes, LogisticRegression) |

The design that carried it: **one trained-model representation**, designed once and reused by
four heads — `PredictorFunction`, `DimensionReducerFunction`, `LearnedDistribution`,
`ClassifierFunction` — absorbing three distinct shapes of extension (a new head, a new method
on an existing head, a differently-shaped payload) without modification.

## Classify: multi-class LogisticRegression by one-vs-rest (2026-08-14)

`Method -> "LogisticRegression"` accepted only two classes and declined anything more,
with a test pinning that refusal so it would be noticed rather than forgotten. It now
handles any number of classes by **one-vs-rest**: K binary fits, class *k* against
everything else, and the predicted class is the arg-max of the K fitted probabilities.

The IRLS loop that was inline in `builtin_classify` is now `logit_irls(x, y, n, dim, pos,
beta)`, parameterised by which class index counts as the positive outcome — extracted at
the second real consumer rather than in anticipation of one, since one-vs-rest runs the
identical iteration K times changing only `pos`.

**Two classes are untouched**, deliberately: one fit, one coefficient vector, the same
payload shape and the same numbers, because at K = 2 one-vs-rest would fit two models that
are reflections of each other. A test now pins that shape (`Length` 2 flat vector for
two classes, a list of three 3-vectors for three classes in 2-D), because the apply path
distinguishes the two cases by structure alone with no tag stored.

**One-vs-rest over a softmax, and the reason is testability.** A softmax's parameters are
identified only up to an additive constant per feature, so the stored coefficients would
not be unique and no test could pin them — precisely the class of assertion that caught
real bugs in the other four families. One-vs-rest also reuses the existing iteration
instead of needing a new one.

**What it does not give is calibrated probabilities**, and that is stated rather than
papered over: the K sigmoids come from K independent fits with nothing constraining them
to sum to 1, so they are normalised on read. The normalisation is a convention, not a
likelihood; being monotone it cannot move the arg-max, so the class is the better-founded
answer and is what the tests lean on. If every sigmoid underflows to zero the normaliser
would be zero, and that declines rather than inventing a uniform answer.

The ridge matters **more** here than it did before. With well-separated classes every
one-vs-rest sub-problem is separable by construction, so all K fits depend on it to come
back finite, where the two-class version exercised only one such fit.

Five new tests in `ml_classify_tests` (21 total, all passing): every training label
reproduced on three separable blobs and again on four classes; probabilities summing to 1
asserted at a genuinely mixed point rather than a saturated one, where a broken normaliser
would still sum to 1; the reported class equal to the arg-max of the reported
probabilities, which would catch the two being computed by different routes; assignment
unchanged when the training rows are reversed, which is what fails if a class index is ever
confused with a position; and coefficients finite across all K fits.

A single class still declines — it is not a classification problem — and a `NeighborsNumber`
option on a logistic fit still declines, being meaningless there.

## LearnDistribution: the ContingencyTable method for nominal data (2026-08-14)

`LearnDistribution` gains `Method -> "ContingencyTable"`, the fourth of Wolfram's five
methods for it (Multinormal, GaussianMixture and KernelDensityEstimation were already in;
DecisionTree remains). It stores a probability per distinct outcome — in one dimension a
categorical distribution, in several the cross-tabulation case.

**This corrects a mis-scoping in the previous entry.** `ContingencyTable` was recorded as
deferred on the grounds that it was "a cross-tabulation utility rather than a learning
method, outside the five ML families". That was wrong: it is not a standalone function at
all but one of `LearnDistribution`'s own methods, so it was inside the scope the whole time.
Worth stating plainly rather than quietly fixing, because the earlier note would otherwise
keep steering readers away from something in scope.

**The one method here that does not take numbers.** The branch runs *before*
`ml_read_data`, because that reader reads numbers and the whole point is outcomes that are
not numbers — `"red"`, a symbol, a pair `{"a", "x"}`. Pushing them through the numeric
reader would decline exactly the data the method exists for. `PDF` likewise gets its own
nominal path ahead of the `MlDist` machinery, since `MlDist` holds doubles and there is
nothing here to read into a double buffer.

`src/ml/encode.h` needed no change to serve it, which is the third consumer of that
vocabulary and the reason it was given its own module.

**No smoothing, and the consequence is asserted rather than implied:** an outcome never
observed has probability exactly 0. Add-one smoothing would require a claim about the size
of the outcome space, and for arbitrary expressions there is no way to know how many
nominal values were possible but unseen — so a hard zero is the honest answer.

Ragged outcomes decline: differing lengths, or a mix of list and non-list observations,
would be a different table per row, which is not a distribution.

Five new tests in `ml_dist_tests` (26 total, all passing). The counts are chosen so the
probabilities are **exact binary fractions** — 3 and 1 out of 4 give 0.75 and 0.25, 5 out
of 8 gives 0.625 — so the assertions are equalities with no tolerance to hide behind, and a
wrong divisor or an off-by-one count cannot slip through. Sum-to-one is asserted on a
*non-uniform* table, because a uniform one sums to 1 even if every probability were computed
as 1/k while ignoring the counts.

## Classify: the DecisionTree method, and src/ml/tree.c (2026-08-14)

`Classify` gains `Method -> "DecisionTree"`, a CART classification tree. The kernel is a new
`src/ml/tree.{c,h}` at buffer level, because `RandomForest` is this same fit run over
bootstrap resamples and `LearnDistribution` lists `DecisionTree` among its own methods —
writing it inside `classify.c` would guarantee the forest either duplicated it or reached
across into it. Same reasoning that put `gmm.c` in its own module.

This is the first thing in `src/ml` that reuses **nothing** from the other five families: no
distance, no density, no linear algebra, no label-index arithmetic beyond counting. That was
the stated reason for deferring it, and the reason holds up now that it is written.

**Gini rather than entropy**, deliberately: both rank splits almost identically, but Gini is a
sum of squares where entropy is a sum of `x log x` — no logarithm per candidate threshold and
no special case at `p = 0`, and the criterion is evaluated O(dim × n) times per node.

**The sweep is linear, not quadratic.** Sorting a node's points by a feature turns
threshold selection into one pass: move a point at a time from the right child to the left,
updating both histograms incrementally, and evaluate only where the feature value changes.
Recomputing the histograms per candidate threshold is the obvious implementation and is
quadratic.

**Thresholds are midpoints between distinct values**, so the `<=` boundary never depends on
floating-point equality with a training value. Between 1 and 9 the split is exactly 5, which a
test pins as an equality.

**Determinism is a requirement.** Ties break by lower feature index then lower threshold, and
the sort comparator falls back to the point index because `qsort` is not required to be
stable. Without that no test could pin a tree — the same argument that ruled out a softmax for
multi-class logistic regression. `Classify[d, …] === Classify[d, …]` is asserted.

**It grows until pure** (depth 32, min-split 2), which makes "reproduces every training label"
exact rather than an accuracy figure, and which overfits. The trade is stated rather than
hidden: pruning needs a validation split or a complexity parameter, and inventing either
silently would be worse.

One implementation note worth recording: the node's split fields are written **after** its
children are built, because growing the arrays may reallocate them — caching a pointer to the
node's own row across the recursive calls would be a use-after-free.

Six new tests (27 in `ml_classify_tests`): every training label reproduced, in 2-D and 1-D;
the midpoint threshold and the exact node table; probabilities on a genuinely IMPURE leaf,
which needs contradictory data to exist at all since separable data gives 1/0 splits that
would sum to 1 even with a broken normaliser; determinism and row-order stability;
unsplittable data — a constant feature, then every feature constant with disagreeing classes,
which is the case that recurses forever without the no-improvement stop, plus a single-point
tree; and a `NeighborsNumber` option still declining.

## Classify: the RandomForest method (2026-08-14)

`Classify` gains `Method -> "RandomForest"` — fifty CART trees, each on a bootstrap resample of
the rows, each node choosing among `sqrt(dim)` features, class by arg-max of the averaged
predicted distribution. This completes the five `Classify` methods and closes the last of the
four gaps recorded when the ML families landed.

`ml_tree_fit` gained an `mtry` parameter (0 = all features, which is what `DecisionTree`
passes, so its behaviour and its pinned tests are untouched). Feature sampling is a partial
Fisher-Yates shuffle of a per-build feature pool — partial because only the first `mtry`
entries are ever read, so shuffling the whole pool would be wasted work at every node of every
tree.

**Both sources of randomness are needed and the second matters more.** Bootstrapping alone
leaves the trees highly correlated: if every tree may pick the single most informative feature
at its root then they all do, and averaging near-identical trees buys nothing. Restricting each
node's candidate set is what decorrelates them.

**Reproducible under `SeedRandom`**, because both draws come from `random_uniform_01`, the
stream `RandomReal` uses. Asserted in both directions — same seed gives an identical forest,
a different seed gives a different one, and the second row is what stops the first from also
passing for an implementation that ignored the generator entirely. Without reproducibility no
assertion about a forest could be exact; the same concern made multi-class logistic regression
one-vs-rest rather than a softmax.

**Per-tree distributions are normalised before averaging, not pooled as raw counts.** Pooling
would let a tree with a large leaf outvote several trees with small ones, weighting each tree
by its own depth instead of giving it one vote.

Two extractions, both at a genuine second consumer rather than in anticipation:
`tree_to_exprs` (the split and count tables, needed once per tree and so fifty times per
forest) and `tree_leaf_counts` (the routing walk). The apply path is now **one branch for both
methods**, since the only difference is how many trees are consulted.

A pleasant consequence of averaging: the forest's probabilities are genuinely mixed near a
boundary because the trees disagree there, so its sum-to-one assertion is meaningful without
the contrived contradictory data a single tree needed.

Three new tests (30 in `ml_classify_tests`), and one existing row **flipped**:
`test_malformed_input_declines` pinned `Method -> "RandomForest"` as a refusal, so it now pins
the answer and an unknown method name carries the decline instead. That is the third pin this
week written to flip when its gap closed and duly flipping — after the `Nearest` bigint
rational and the two-class logistic guard.

## MemoryInUse and MaxMemoryUsed (2026-08-14)

Two new builtins in a new `src/meminfo.{c,h}`, registered from `core_init` alongside
`info_init`. `MemoryInUse[]` gives the bytes currently resident for the process;
`MaxMemoryUsed[]` gives the lifetime peak. Added so the notebook status bar has a memory
figure to display.

**They report resident set size, which is not Mathematica's quantity, and that is stated in
the docstring rather than left for a user to discover.** Wolfram's `MemoryInUse[]` counts
session data only; this also counts the binary, the shared libraries, the stacks and whatever
the allocator holds without returning it. Reporting session bytes exactly would mean routing
every allocation in the tree through a counting wrapper — some 500 modules, all calling
`malloc` directly — and would still miss allocator retention. RSS is also the more useful
number for a status bar, being what Activity Monitor and `top` show.

`MemoryInUse` reads `mach_task_basic_info` on macOS and `/proc/self/statm` on Linux, scaled
by the real page size rather than an assumed 4096. `MaxMemoryUsed` uses `getrusage`'s
`ru_maxrss`, which is a true OS high-water mark — so it catches a spike between two polls,
where a maximum accumulated over previous `MemoryInUse` calls would miss it.

**Two portability traps, both documented in the file.** `ru_maxrss` is BYTES on Darwin and
KILOBYTES on Linux, so it is scaled per platform; an unconverted use is wrong by 1024x on one
of them and plausible on both. And the feature-test guard here runs *opposite* to every other
file in the tree: `ru_maxrss` is a BSD extension, not POSIX, so on Darwin defining
`_XOPEN_SOURCE` selects the strict POSIX subset and HIDES the field — the same macro every
other module needs in order to see POSIX at all. Each platform therefore gets the macro that
widens its own namespace, still before any include.

An unsupported platform returns unevaluated rather than `0`, because a zero reads as "no
memory in use" — false, and entirely plausible-looking in a status bar. `MemoryInUse[k]` for
a subkernel is refused rather than accepted and ignored, there being no subkernels.

New `meminfo_tests`, five groups. Memory values are machine-dependent and cannot be pinned,
so every assertion is a relation that must hold whatever the number is: positive integer;
peak never below current and never decreasing; an order-of-magnitude window between 1 MB and
16 GB, which is what catches the 1024x unit error; the argument forms declining; and both
symbols `Protected`. The load-bearing one is that it **responds to allocation** — three
million machine integers is 24 MB at 8 bytes each, and resident memory must grow by at least
4 MB — because a hard-coded constant would satisfy every other row in the file.
## Image: the raster representation and its accessors (2026-08-14)

The image subsystem starts, in a new `src/image.{c,h}`: `Image`, `ImageQ`,
`ImageDimensions`, `ImageChannels`, `ImageType`, `ImageData`. Deliberately the foundation and
nothing that filters — `ImageConvolve`, `GaussianFilter`, `Binarize` and `Image3D` all need to
ask an image its size, channel count and pixel type before they can do anything, so those
questions get answered first and answered once. New docs page
`docs/spec/builtins/image-processing.md`, indexed in `Mathilda_spec.md`.

**The canonical form is `Image[data, type]`, which is also real Wolfram syntax**, and `Image[data]`
normalises to it. The normalisation is not cosmetic: a builtin returning `NULL` leaves its
expression alone, so without it a valid `Image[data]` and a nonsensical `Image["hello"]` would be
indistinguishable — both unevaluated. A canonical two-argument form is exactly what passed
validation, which is what `ImageQ` tests.

**The transposition is the trap and is treated as one.** `ImageData` is `height × width`
(`data[[y, x]]`, rows down the image) while `ImageDimensions` is `{width, height}`. That is
Mathematica's convention and the commonest source of silently-wrong image code, so every test row
that touches it uses a **non-square** image — a square one cannot tell the two apart and would
pass with the axes swapped.

**Type inference reads the values and nothing else**: all-integer within `{0,1}` is `"Bit"`,
all-integer within `0..255` is `"Byte"`, anything else `"Real"`. So `Image[{{0,1},{1,0}}]` is a bit
image and `Image[{{0.,1.},{1.,0.}}]` a real one. A *stated* type is refused where the data does not
fit — `Image[{{0,300}}, "Byte"]` declines rather than reinterpreting 300 and corrupting every later
scaling.

**`ImageData` scales out the type**, so a `"Byte"` 255 comes back as exactly `1.0`. The stored
values are the originals and the scaling happens on read, which keeps `Image[…]` round-trippable
and makes the scaling an assertion about one function instead of a property spread across two.
Real data passes through untouched *including* values outside `[0,1]`: clamping silently would
destroy data the caller may want back.

**A benchmark caught a real design flaw and changed the implementation.** Routing every accessor
through the full validator made `ImageDimensions` cost **0.59 ms** on a 512×512 image, because
asking how wide an image is touched all 262,144 pixels — and a filter pipeline queries dimensions
constantly. Since the canonical form can only be produced by `Image[]`, which validates every
pixel once, the accessors now re-check only **rectangularity**, O(height) rather than O(pixels):

| | before | after |
|---|---|---|
| `ImageDimensions` (512×512) | 0.59 ms | 0.58 µs |
| `ImageQ` (512×512) | 0.62 ms | 0.64 µs |

That is ~1000×, and the cheap check is not dropped: a hand-typed `Image[{{1,2},{3}}, "Bit"]` must
still fail `ImageQ`, and a test pins exactly that, because every filter downstream indexes the
array as rectangular.

New `image_tests`, eight groups: the transposition on non-square grey and colour images; exact
byte scaling as equalities (0, 255, and 128/255) so a wrong divisor fails outright; the unscaled
round-trip and the refusal to convert between types; type inference including the integer/real
distinction and the out-of-range refusals; the canonical form as a **fixed point**, which is what
fails if the already-canonical early return is removed; channel counts including inconsistent
pixel lengths; malformed input (ragged, empty, rank-1, symbolic, complex); and `ImageQ` plus
`Protected` on all six symbols.

**On GPU acceleration, honestly.** Nothing here is GPU-accelerated and nothing here needed to be —
it is validation and array walking. The build already links Accelerate (`vImage`/`vDSP`, SIMD) and
FFTW, which together cover separable convolution and frequency-domain filtering at high speed on
the CPU; that is the path `ImageConvolve` should take first. Real GPU compute on macOS means
Metal, which is Objective-C and a genuine portability question for a C99 tree that must also build
against glibc — worth deciding on its merits when there is a kernel whose arithmetic actually
dominates its memory traffic, not before.

## Image filtering: ImageConvolve, GaussianMatrix, BoxMatrix, GaussianFilter (2026-08-14)

The first filters, in a new `src/imagefilter.c`, on the representation that landed earlier today.
`src/image.{c,h}` gained the shared pixel layer they all need — `image_load` (a flat
`h*w*c` buffer of unit-interval reals) and `image_build_real` — designed once because every filter
wants exactly that.

**True convolution: the kernel is reflected.** Not pedantry, and unusually easy to get wrong,
because on any symmetric kernel — Gaussian, box — convolution and correlation agree *exactly*, so
every smoothing test passes either way. It shows up only on an asymmetric kernel. The test uses a
delta in a 1×3 image with kernel `{{1,2,3}}`: convolution gives `{1,2,3}`, correlation `{3,2,1}` —
exact integers, no tolerance, no way to pass by accident. Asserted vertically too, so a transposed
index cannot hide in the row case.

**Padding is `"Fixed"`** (replicate the edge pixel), Mathematica's default. Zero padding would
darken every border, which looks exactly like a real vignetting bug. Clamping also buys an exact
test: a constant image through a kernel summing to 1 is unchanged *everywhere including the
border*, which is what fails if the padding is ever changed.

`GaussianMatrix` normalises by the **realised** sum rather than the analytic `2 pi sigma^2`,
because the analytic constant is right only for an infinite kernel and on a truncated one leaves
the sum under 1 — darkening an image slightly on every pass. `BoxMatrix` is deliberately *not*
normalised, matching Mathematica, so a box convolution is nine times too bright at r=1; a test
pins that it was not helpfully rescaled.

`GaussianFilter` is implemented by building the same matrix and calling the same convolution,
because Mathematica documents `GaussianFilter[i, r] == ImageConvolve[i, GaussianMatrix[r]]` and a
test asserts it. Two independent implementations of one identity is how the identity quietly stops
holding.

**Cross-checked against scipy, and the benchmark corrected a wrong conclusion of mine.**
`scipy.ndimage.convolve` is the right baseline — it reflects the kernel and `mode='nearest'`
replicates the edge exactly like `"Fixed"` — and the two agree to **six significant figures** on
sampled pixels and on the total (2050.0623 either side).

The first timing read **72× slower than scipy**. That was wrong: it had `Image[Table[...]]` inside
the timed region, so it was measuring the construction of 262,144 `Expr` reals and calling it
convolution. Separating them:

| radius | taps | Mathilda | scipy | ratio |
|---|---|---|---|---|
| r=0 | 1 | 4.6 ms | — | marshalling floor |
| r=2 | 25 | 6.3 ms | 3.2 ms | **1.97×** |
| r=4 | 81 | 14.4 ms | — | |

So ~2×, not 72×, and the useful finding is that **the `Expr` round-trip dominates at small radii**:
a single-tap convolution still costs 4.6 ms of pure marshalling, leaving only ~1.7 ms of actual
arithmetic at r=2. Arithmetic scales linearly in taps, as the direct form should.

That redirects the optimisation target away from the inner loop. In order: keep images in packed
buffers so a filter chain does not round-trip through `Expr` at each step; exploit separability for
Gaussians (`kw + kh` instead of `kw × kh`, 2.5× at r=2 and 4.5× at r=4); then Accelerate's
`vImage`, already linked. At ~1.7 ms of arithmetic for a quarter-megapixel image, GPU transfer
would cost more than it saved — `vImage` is the honest next step, not Metal.

New benchmark pair `benchmarks/63-image-convolve/`, with a deliberate `r=0` row measuring the
marshalling floor by itself. Six new test groups (14 in `image_tests`).
