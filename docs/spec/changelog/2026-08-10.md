# Changelog: week of 2026-08-10 (Mon) – 2026-08-16 (Sun)

Feature additions and fixes recorded during this week.

## Evaluator: memoize the structural hash on each Expr node (2026-08-11)

Investigating whether the symbol table or `expr_hash` contributes to the
systemic per-node evaluator constant (`MATHILDA_EVALUATOR_PERFORMANCE.md`): the
symbol table does **not** — name→definition resolution is already an O(1)
cached-pointer read on each node (`data.symbol.def`). But `expr_hash`
(`src/expr.c`) was FNV-1a **recomputed by walking the whole subtree on every
call**, and it is called per-element in `Plus`/`Times` like-term grouping,
Association key indexing (`assoc_index.c`), and the set ops
(`Union`/`DeleteDuplicates`/`Tally`, `list/setops.c`).

- **New field `Expr.hash_cache`** (`src/expr.h`): a lazily-filled memo of
  `expr_hash(node)`, sentinel `0` = unhashed (a genuine hash of 0 just recomputes
  — harmless). Filled on first `expr_hash`, reused thereafter; the recursion
  memoizes the whole subtree bottom-up. Zero-initialised in the single allocator
  `expr_alloc_node`, so every constructor and the `expr_unshare` copy start clean.
- **Invalidation contract** — `expr_invalidate_hash(e)` (inline in `expr.h`) is
  called at every in-place structural mutation of a live node: `eval_flatten_args`
  (Flat), `flatten_sequences`, the generic Orderless `qsort`
  (`src/eval.c`), and the pattern alpha-rename (`src/symtab.c`). The cache is
  benign metadata (ignored by `expr_eq`/`expr_compare`), like `symbol.def`.
- **`MATHILDA_HASH_VERIFY` build** (define-gated in `expr.c`): ignores the cache,
  recomputes every hash, and `abort()`s if a surviving cache value disagrees —
  turning any missed invalidation into a deterministic failure. Ran clean over a
  broad stress corpus, all seven `benchmarks/4x-eval-*`, and ten hash-relevant
  unit suites (`association`, `packed_list`, `sort`, `complement`,
  `intersection`, `mapat`, `replaceat`, `flatten_at`, `array_flatten`,
  `compile_assoc`).

Result: hashing the same subtree repeatedly (Association lookups, dedup/`Tally`
of repeated structural elements, re-grouping a stable sum) drops from
O(subtree) per touch to O(1). Measured up to **~14× faster** on dedup/`Tally` of
a list of repeated deep nodes (4.07→0.30 ms) with no change to results. No new
allocation (inline field), so valgrind is unchanged at the macOS baseline; full
`ctest` shows no new failures (the 6 failing suites — `zero_test`, SVD/eigen/
lapack SEGFAULTs, `partitionsq` timeout — are the documented pre-existing set).
The packed-list ⇄ materialised-`List` hash byte-identity (`test_packed_list.c`)
still holds. Docs: `MATHILDA_EVALUATOR_PERFORMANCE.md`.

## Build: de-duplicate `-lgmp`/`-lmpfr` link flags (2026-08-11)

`pkg-config --libs flint` (and GMP-ECM) re-list `-lgmp`/`-lmpfr`, which the base
`LDFLAGS` and MPFR block already carry, so the raw link line repeated them and
macOS `ld` printed `ignoring duplicate libraries: '-lgmp', '-lmpfr'`. Added a
small `LDFLAGS_DEDUP` helper in `makefile` that collapses each `-l` flag to a
single copy, **keeping its last occurrence** so a provider (`-lgmp`) still
follows every consumer (`-lflint`, `-lmpfr`, `-lecm`) — the dependency order a
static-archive link needs, and the reason `FLINT_LIBS` is appended after the base
`-lgmp`. `-L` search paths and two-word `-framework X` tokens pass through
untouched. The warning is gone; the binary links and runs identically.

## Matcher: `Condition` over a multi-element sequence blank (2026-08-11)

Fixed a conformance bug: a `Condition` wrapping a sequence blank —
`x__ /; test`, `x___ /; test`, and the named/nested/double-named forms
(`c : (b__ /; t)`, `b___ /; c1 /; c2`) — matched **only when the sequence
spanned exactly one element**. For zero or ≥2 elements it failed even with a
literal `True` guard, so the extremely common idiom
`MatchQ[{5, 10}, {b__ /; Total[{b}] == 15}]` returned `False` (WL: `True`).

Root cause in `src/match.c`: `match_args_internal` peels `Pattern`,
`Shortest`, `Longest`, `Optional` and strips `PatternTest` for sequence blanks,
but never handled `Condition[seqblank, guard]`; it fell through to the
single-element path (`min_k = max_k = 1`), so only the width-1 case — which a
`BlankSequence` also matches — slipped through. Fix mirrors the `PatternTest`
handling: strip the `Condition` layer(s) when the inner pattern is a sequence
blank / `Repeated`, remember the guard chain, and evaluate it once (via the new
`eval_seq_conditions`, inner `/;` first) at each commit point after the sequence
variable is bound. Untouched when the inner pattern is a single blank, so the
well-tested `x_ /; test` path is unchanged. `PatternTest` over a sequence and
`Condition` over a single element both already worked and still do.

Regression cases added as section 37 of `tests/match_stress_corpus.m`
(287 → 298 cases, all green). Enumeration counts cross-checked against an
independent brute-force partition enumerator.

## Matcher: fix per-guard-evaluation memory leak (2026-08-11)

Fixed a pre-existing leak in `guard_all_true` (`src/match.c`): the guard leaf
was evaluated as `evaluate(expr_copy(g))` with the `expr_copy(g)` temporary
inlined. `evaluate()` **borrows** its argument (it copies internally), so that
temporary was never freed — one orphaned `Expr` node per guard leaf that did not
evaluate to the literal `True`. Because most backtracking attempts have a
**failing** guard, this leaked ~1 node per *failed* condition check across the
whole system (every `/;` in matching, `Cases`, `ReplaceAll`, conditional
`DownValues`, …). Now the copy is held in a variable and freed. Under valgrind,
a 75,327-guard-evaluation run drops from 75,058 leaked blocks to the constant
macOS startup baseline (422 blocks); named-sequence + `Cases` workloads that lost
332 KB now lose nothing beyond baseline. No result changed — this is purely an
ownership fix.

`MATHILDA_PATTERN_MATCHER_PERFORMANCE.md` (repo root) gains **Case M**, a scaling
study of the equal-sum contiguous-partition family that surfaced both fixes. It is
a head-to-head against Mathematica 14.0 (`wolframscript`) on identical inputs: the
pattern is genuinely exponential *in Mathematica* (the reader's verbatim pattern
takes 6.75 s at N=20; a distinct-block variant 38 s at N=120), but Mathilda's
matcher prunes it to polynomial/constant cost — 100× to 135,000× faster with
identical match counts. The PDF is regenerated with `pandoc --pdf-engine=xelatex`.

## Evaluator: pooled `MatchEnv` (2026-08-11)

First optimization driven by the evaluator-throughput suite above.
`apply_down_values_def` (`src/symtab.c`) allocates and frees one `MatchEnv` — via
`env_new`, three `malloc`s — per candidate DownValue, so recursive rewriting
churns millions (`fib[28]` ≈ 2.5M envs, one per fib call × 3 rules tried).
`env_new`/`env_free` (`src/match.c`) now recycle the whole struct **including its
`symbols`/`values` arrays** through a bounded static free-list (`ENV_POOL_CAP`
256), so reuse is allocation-free after warm-up. Mirrors the existing bounded
`Expr` node pool: single-threaded, reentrant (nested matches draw more from the
pool), pooled envs are program-lifetime "still reachable". The external contract
of `env_new`/`env_free` is unchanged and `env_free` still releases each binding's
`strdup`'d key and value ref — only the arrays and struct are kept.

Effect (Mathilda ÷ WL 14.0 ratio, before → after): `fib[28]` 2.7×→2.2×
(1.57 s→1.33 s), `ack[3,4]` 3.1×→2.5×, mutual recursion 3.0×→2.2×,
`Nest[incr,0,50000]` 2.0×→1.6×; `Count`/`Position` over 5000 `f[k]` nodes crossed
into parity (suite `SLOWER` 17→15). `tests/bench_match.c` shows it directly:
`Cases` 333→196 ns/elem, `Position` 1083→583, `ReplaceAll` 390→237 (1.4×–1.9×).
It deliberately does **not** move the arithmetic-bound rows (Case B, the `//.`
folds, the Orderless sum), which are `Length`/`Plus`/list-rebuild bound, not
env-allocation bound — those are the next targets.

Verified: `bench_eval` and `bench_match` gates PASS; the env-touching unit suites
(`match`, `rule_dispatch`, `eval_timestamps`, `eval_eager_exit`, `expr_sharing`,
`return`) all pass; the 5 pre-existing ctest failures (`zero_test`, and the SVD/
eigen/lapack SEGFAULTs) fail identically with the change stashed, so they are not
regressions; valgrind on a matcher-heavy workload holds at the constant 422-block
macOS baseline with the pooled envs correctly *still reachable* (no new loss). No
result changed — this is an allocation-strategy change only.

## Evaluator: machine-integer fast path for Plus and Times (2026-08-11)

Second optimization from the evaluator-throughput suite. `builtin_plus` /
`builtin_times` (`src/plus.c`, `src/times.c`) ran several O(n) scans (NDArray
probe, neg-Plus distribution, SeriesData, inexact contagion, then
(coeff,base)/(base,exp) grouping) before combining terms — real overhead for the
ubiquitous `Plus[int,int]` / `Times[int,int]` that dominates recursive integer
code (`fib[n-1]+fib[n-2]`) and loop accumulators. Added a fast path after the
n==0/1 checks: when every argument is a machine `EXPR_INTEGER`, fold them with the
overflow-checked `ci_add_i64` / `ci_mul_i64` (Times short-circuits on a 0 factor)
and return a single integer. On overflow, or any non-integer operand, it falls
through to the existing generic path, which promotes to bigint — so results are
unchanged, including the exact bigint answers for `9223372036854775807+1` and
`3037000500^2` (checked byte-for-byte against Mathematica 14.0).

Effect (on top of the MatchEnv pool; Mathilda ÷ WL): `fib[28]` 1.33 s → 1.06 s
(2.7×→1.9× vs 1.57 s baseline), `ack[3,4]` 16.8→14.3 ms, mutual recursion
0.85→0.74 ms, `Nest[incr,0,50000]` into parity. Suite `SLOWER` count 17→14,
`AHEAD` 11→14 cumulatively. Verified: full `ctest` 199/204 (the failures are the
pre-existing `zero_test` + SVD/eigen/lapack SEGFAULTs, plus the flaky
`moebiusmu_tests` which fails at the same ~20% rate on unmodified `de6a69f`);
`bench_eval`/`bench_match` gates PASS; arithmetic edge cases (overflow→bigint, 0
factor, negatives, mixed symbolic, rationals, reals) match WL; valgrind at the
422-block baseline.

A third lever — adopting the evaluator's per-step argument buffer into the
reassembled node (`expr_new_function_adopt`) to skip a malloc+memcpy on large
`List`/`Plus` rebuilds — was built and A/B-measured but **rejected**: the win was
within noise (0–7%, mostly noise) because the large-node cases are dominated by
the operation (`replace_bindings` splice, Orderless grouping), not the reassembly
copy. Not worth a hottest-path change + new public API. The remaining suite gaps
(`//.` folds 4.2×, Case-B-untyped 3.1×, Orderless sum 2.8×) are those
operation-bound costs; see `MATHILDA_EVALUATOR_PERFORMANCE.md` for the next
targets.

## Evaluator: borrow MatchEnv keys instead of copying them (2026-08-11)

Third optimization. The `MatchEnv` pool recycles the struct and its arrays, but
`env_set` (`src/match.c`) still `strdup`'d every binding's key and `env_free`
freed it — one malloc + free per binding, millions in recursive rewriting and
structural mapping. Every `env_set` caller passes a key that already outlives the
per-attempt env: an interned symbol name (`sym->data.symbol.name`, program-
lifetime, owned by the interner) or a string literal (`"$OptionsPattern$"`). So
the key is now stored by **borrow** — no `strdup`, and `env_free`/`env_rollback`
never free it. Comparison is pointer-first (interned keys — the hot path, since
the matcher and `replace_bindings` both pass `sym->data.symbol.name` — hit
immediately) with a `strcmp` fallback so the cross-translation-unit literal
callers still match.

Effect (on top of pool + int fast path): `fib[28]` 1.06→1.05 s, `ack[3,4]`
14.3→13.1 ms, Case B typed into parity, `bench_match` `ReplaceAll` 237→187
ns/elem. Cumulative suite over the three optimizations: **17→13 slower, 11→15
ahead** vs Mathematica 14.0.

Verified: `bench_eval`/`bench_match` gates PASS; matcher correctness (nonlinear
patterns `{a_,a_}`/`{a__,b__,a__}`, `OptionsPattern`, guards, `Cases`/`ReplaceAll`)
matches WL byte-for-byte; `ctest` failures are the pre-existing/flaky set
(`zero_test`, `moebiusmu`, `bench_compile` load-gate, SVD/eigen/lapack SEGFAULTs);
valgrind at 420 blocks — two *below* the 422-block macOS baseline (fewer
allocations), no invalid access, no new loss.

## Evaluator: skip evaluate() for atomic arguments (2026-08-11)

Fourth optimization, and the one found by *profiling* rather than reasoning.
`sample` on the `//.` fold showed the entire cost in `eval_and_free`
re-evaluating the result list each pass — the per-element `evaluate()` calls in
`evaluate_step`'s argument loop, not `replace_bindings` or the match. A raw atom
(Integer/Real/String/BigInt/MPFR/NDArray/Compiled) always evaluates to itself, so
`evaluate()` there just `expr_copy`s it after paying the recursion-depth bump,
trace push, deadline check and fixed-point-loop setup *per call*. The loop now
recognises an atomic argument and goes straight to `expr_copy`, skipping
`evaluate()` entirely — provably equivalent (same pointer, so the change flag
stays clear; an atom is never an in-flight `Throw`/`Goto`). `SYMBOL` is excluded
(it may carry an OwnValue).

This is the hot path whenever a large `List` of numbers is re-evaluated — most
visibly every pass of `list //. rule`, which re-walks the whole (mostly
unchanged) list. Effect vs WL 14.0: `//.` fold on `Range[800]` **4.3× → 2.2×**
(16.8 → 9.2 ms), on `Range[400]` → 2.3×, Case B untyped 3.1× → 2.5× (its guard
builds `{x},{y},{z}` integer lists), and the `ReplaceAll`-rebuild row off the slow
list. Suite `SLOWER` 13 → 11, `AHEAD` 15 → 17.

Cumulative over the four evaluator optimizations this week (MatchEnv pool, Plus/
Times machine-int fast path, borrowed MatchEnv keys, atomic-argument skip): the
evaluator-throughput suite moved from **17 slower / 11 ahead** to **11 slower /
17 ahead** vs Mathematica 14.0, with no regressions. The remaining top gap is the
Orderless sum (`Length[Plus @@ 2000 symbolic terms]`, 3.3×) — symbolic terms, not
atoms — which is the next target. Verified: `bench_eval`/`bench_match` gates PASS;
all 28 suite value checks agree with WL (0 CHECK-FAIL); `ctest` failures are the
pre-existing/flaky set (`zero_test`, `bench_pack`/`bench_compile` load-gates,
SVD/eigen/lapack SEGFAULTs); valgrind at the 420-block macOS baseline.

## Evaluator: skip the redundant sort in builtin_plus (2026-08-11)

Fifth optimization, again found by *profiling* (`sample` on `Plus @@ Table[c[k] x,
{k, 2000}]`): ~half the time was in the final-term `qsort` and its `expr_compare`
per comparison — the grouping hash table and reconstruction were already O(1)/O(n).
But a `Plus` built in order arrives canonically ordered (`c[1] x < c[2] x < …`),
and every re-evaluation of an already-sorted sum re-sorts terms that never moved —
pervasive, since a sum flows through the evaluator to a fixed point. `builtin_plus`
(`src/plus.c`) now guards the `qsort` with an O(n) already-sorted pre-check
(`plus_cmp_ptrs` scan, sort only on the first descent found) — the same technique
already used for the Orderless fast path in `evaluate_step`. Same canonical result:
skipping a no-op sort or sorting an unsorted sum both yield the identical order.

Effect: re-evaluating a canonical 2000-term sum **1.89 → 1.12 ms (−40%)**;
`expr_compare` samples 307 → 80, `qsort` 61 → 20. The suite Orderless-sum row moved
3.3× → 3.0× — its residual is now `Table` construction and the O(n) Infinity/
contagion pre-scans, not the sort. The general win is the re-evaluation path, which
every repeated symbolic-sum evaluation (Expand, polynomial arithmetic, Simplify)
hits.

Verified: `Expand[(1+x+y)^12] = 531441`, term collection (`2x+3x+x → 6x`) and
canonical ordering (`z+a+m+b+3+1 → 4+a+b+m+z`) correct; the full Expand/Simplify/
polynomial/numeric-domain test set passes; `bench_eval`/`bench_match` gates PASS;
`ctest` failures are the pre-existing/flaky set (this change is on the symbolic
grouping path, not the packed path `bench_pack` exercises); valgrind at the
420-block macOS baseline.

## Evaluator: borrow subset/remainder slices in ordered sequence matching (2026-08-11)

Sixth optimization. Re-profiling the `//.` fold *after* the atomic-argument skip
showed the cost had moved off `eval_and_free` and into the matcher:
`match_args_internal` (`src/match.c`) allocated and copied a fresh `remainder`
array (via `extract_subset`) at **every** pattern element — even single blanks —
so one `{a_, b_, r___}` pass paid ~4 O(n) copies of the tail. But
`next_combination` is gated on `is_orderless`, so for an *ordered* (non-Orderless)
head the do-while runs exactly once with `comb = [0..k-1]`: the consumed elements
are the contiguous prefix `exprs[0..k-1]` and the remainder is the contiguous
suffix `exprs[k..]`. Both are slices of the caller's array and are read-only (type
checks, `expr_copy` into `seq_val`/`matched_val`, and the recursive callee), so
they are now **borrowed** instead of malloc+`extract_subset`. The heap copies live
in `subset_owned`/`remainder_owned` (NULL in the borrow case → the free sites are
no-ops); the Orderless combination path is unchanged. The `comb` index array is
also skipped for ordered heads (only `extract_subset`/`next_combination` read it,
both Orderless-only).

This is a **general** matcher speedup, not just the fold — every pattern match over
an ordered head's arguments now avoids the per-element subset/remainder/comb
allocation. `bench_match`: `ReplaceAll` 187 → 99.8 ns/elem, `Cases` 216 → 126,
`Position` 634 → 500, DownValue-Map 613 → 513. Fold `Range[800]` 9.2 → 8.2 ms,
bubble sort `//.` 7.6 → 3.8 ms (2×), Case D 3.8 → 1.6 ms, `ack[3,4]` 13 → 9.5 ms,
`fib[28]` and the `ReplaceAll`-rebuild row into parity.

Cumulative over the six evaluator optimizations this week: the throughput suite
moved from **17 slower / 11 ahead** to **8 slower / 20 ahead** vs Mathematica 14.0,
worst outliers 4.3× → ~2.3×, with no regressions. Verified: the 298-case
`match_stress_corpus` passes (0 failed, 0 crashed); `match_tests`,
`rule_dispatch_tests`, `bench_eval`, `bench_match` PASS; matcher correctness
(nonlinear `{a__,b__,a__}`, `Cases`/`ReplaceList` with guards, OrderlessPatternSequence,
`Plus[a,b,c] /. {x__,y__}`) matches WL; `ctest` failures are the pre-existing/flaky
set (`zero_test`, `primenu` — 2/8 flaky on the committed baseline too,
SVD/eigen/lapack SEGFAULTs); valgrind at the 420-block macOS baseline over both the
borrow (ordered) and copy (Orderless) paths — no invalid access, no double-free of
a borrowed slice.

## Evaluator: Apply/Map level short-circuits + Plus/Times special-case short-circuit (2026-08-12)

Follow-up to the *evaluator throughput* campaign, targeting the one row still
trailing Mathematica in `MATHILDA_EVALUATOR_PERFORMANCE.md` — the arithmetic
sentinel `Length[Plus @@ Table[c[k] x, {k, 2000}]]` (4.69 ms vs WL 1.5 ms, 3.1×).
Profiling the three operations on its critical path (`Table` build, `@@`, the
`Plus` grouping) surfaced two avoidable, non-fundamental costs — one of them a
finding the campaign had missed.

**1 — Specialised top-level `Apply` fast path** (`src/funcprog.c`). `f @@ expr`
(default level spec `{0,0}`) went through the general recursive `apply_at_level`,
which (a) called `get_depth(expr)` — a full recursive traversal of the whole
argument tree — at every node, though its only consumer is the negative-level
branch a non-negative spec never takes, and (b) *structurally cloned every element
subtree* (~4000 interior `Times`/`c[k]` nodes for a 2000-element list) even though
Expr trees are immutable and refcount-shared. `builtin_apply` now has a
self-contained fast path — mirroring the existing `f @@ <|assoc|>` one — that, for
`ls == NULL` with a function operand, builds `f[elements…]` by refcount-sharing
each element (`expr_copy` is an O(1) refcount bump) and evaluates once. Provably
equivalent to `apply_at_level(f, expr, 0, {0,0})`. The general `apply_at_level` was
also tightened: for a non-negative spec it skips `get_depth` and returns
`expr_copy(expr)` once `current_level > spec.max` (nothing can apply at that level
or deeper), and an `apply_child` helper folds the same past-max check into the
per-child recursion so `@@@` (`Apply[…, {1}]`) — a common operation whose general
path recursed once per element *and* once per sub-element, the level-2 calls doing
nothing but refcount-share — now shares each element's arguments in O(1). Isolated
`f @@ list` over 2000 elements **~1.3 ms → ~0.05 ms**; `f @@@ list` restructuring
over 5000 elements **~0.93 → ~0.78 ms (−15%)**; the 5000-triple
`Apply[Plus, …, {1}]` benchmark **11.5 → 7.4 ms (2.47× → 1.6× WL)**. Every `Apply`
level-spec form (`@@`, `@@@`, `{2}`, `{1,2}`, `{-1}`, `{-2}`, `Heads->True`, and
deeper nesting) is pinned in `test_core_algebra.c`.

**1b — `Map` (`/@`) shares the subtree past the mapped level** (`src/funcprog.c`
`map_at_level`). Map is bottom-up, and had the *same* `get_depth`-everywhere +
descend-and-rebuild overhead — worse, because it always walked to the leaves: the
common `f /@ list` cost grew with element *depth* even though `f` only touches
level 1. The same two changes apply: skip `get_depth` for a non-negative spec, and
once past the maximum level share the whole subtree by an O(1) refcount bump
instead of descending + rebuilding it. `f /@ 5000 g[a,b,c]` **4.19 → 0.56 ms
(−87%)** and `f /@ 5000 g[h[…],h[…]]` **7.12 → 0.57 ms (−92%)** — the time is now
independent of element depth. `Map[f, expr, {0}]` (map at level 0) becomes a clean
`f[expr]` share too. Every level-spec form (`{0}`, `{2}`, `{0,1}`, `{-1}`,
`Infinity`, `Heads->True`, `Hold`-suppressed) is pinned in `test_core_algebra.c`.

**2 — Fused special-case short-circuit in `Plus` and `Times`** (`src/plus.c`,
`src/times.c`). Both ran five independent full O(n) pre-scans before term grouping
— NDArray probe, neg-Plus distribution (Plus only), SeriesData, inexact contagion
(with a size-n `malloc` taken *before* the check), Infinity/Indeterminate — and for
an ordinary symbolic or rational sum/product every one finds nothing. A single
detection pass now decides whether any could act; if not, execution jumps straight
to grouping. The predicate is a provably-correct superset of "some pass would act"
(NDArray→`is_ndarray`, neg-Plus→`is_neg_of_plus`, series→`is_series_data`,
contagion→`arg_is_inexact` — exported from `numeric.c` for this, matching
`numeric_contagion_args`'s own trigger — Infinity→`classify_plus_term`/the inline
Times check), so skipping the passes when it is false is exactly equivalent. The
guarded passes are otherwise byte-for-byte unchanged.

**Result.** `Length[Plus @@ Table[c[k] x, {k, 2000}]]` **4.69 → 2.95 ms (−37%,
3.1× → 2.0× WL)**; the sibling `bench_eval` row "orderless sort (Plus 1200)"
dropped from 0.27 to ~0.19 norm. The residual is now dominated by `Table`'s
per-element symbolic-`Times` evaluation (2.43 ms of the 2.95 ms) — the systemic
per-node evaluator constant, whose largest remaining lever is the fixed-point
double pass (`builtin_times`/`builtin_plus` unconditionally rebuild and trip the
change flag, forcing a confirm-stable step). That is a core-evaluator change of
much broader blast radius and is left for a separate, measured effort.

**Tests.** New `tests/test_core_algebra.c` (wired into CMake as
`core_algebra_tests`) pins Plus/Times/Power/Divide/Apply/Length/ordering/Table
against WL-checked FullForm, deliberately covering the paths these changes touch:
every `Apply` level-spec form (`@@`, `@@@`, `{2}`, `{-1}`, `Heads->True`, empty,
single, atomic) and every guarded Plus/Times special case (cancellation, Infinity,
ComplexInfinity, Indeterminate, contagion, radical fusion, trig canonicalisation).
`tests/bench_eval.c` gains the three flagship regression rows mandated by the perf
doc — `fib[24]` (dispatch), Case B typed (matcher constant), Plus-2000 (this
sentinel). Verified: `core_algebra_tests`, `eval_tests`, `sort_tests`,
`expand_tests`, `collect_corpus_tests`, `power_corpus_tests`, `evaluate_tests`,
`regression_tests`, `match_tests`, `match_extensive_tests` PASS; the 298-case

## Graphics: add ArrayPlot (2026-08-12)

New `ArrayPlot[array, opts...]` (`src/graphics/arrayplot.{c,h}`), a discrete
grid heatmap for a literal 2D array — the counterpart to `DensityPlot`'s
sampled-function heatmap, but with no interpolation: one cell per array entry,
row 1 at the top, column 1 at the left. Unlike the `HoldAll` function-sampling
plotters, `ArrayPlot` is not `HoldAll`; `array` is an ordinary evaluated `List`
or `NDArray`, ingested through the existing `na_load_matrix` loader
(`src/linalg/numarray.h`) that the linear-algebra surface already uses, so
packed and visible `NDArray` inputs work for free.

Colours are deliberately drawn from the **existing** shared ramp table in
`plot_common.c` (`named_color_ramp`/`thermal_rgb`/`resolve_ramp_to_rgb`) rather
than a new palette: the default `ColorFunction` is `"Greyscale"` (white at the
array minimum, black at the maximum) — Mathematica's own `ArrayPlot` default,
and the one plotter in this codebase that doesn't default to the thermal ramp.
`"Rainbow"`, `"Temperature"`, `"CoolTones"`, `"WarmTones"` all work identically
to their use in `DensityPlot`/`ContourPlot`/`StreamPlot`. `Mesh -> All` overlays
grid lines in `GrayLevel[0.5]`, the same neutral grey already used as this
module's ColorFunction fallback. `PlotLegends -> Automatic` reuses the
`$StreamColorBar` metadata node and `render.c`'s existing colour-bar renderer.

A matrix whose every entry is already a colour literal
(`RGBColor`/`GrayLevel`/`Hue`/`CMYKColor`) is detected and painted directly,
letting `ArrayPlot` double as a raw pixel-grid renderer —
`ArrayPlot[{{Red, Blue}, {Blue, Red}}]` — with no `ColorFunction` involved.
`AspectRatio` defaults to `rows/cols` so cells render square. Registered with

## Graphics: ArrayPlot ColorRules, and a leaked-evaluation fix in arrayplot.c (2026-08-12)

Added `ColorRules -> {v1 -> c1, v2 -> c2, ...}` to `ArrayPlot` (reported: colours
weren't showing up — the plot rendered fully greyscale). `ColorRules` gives an
explicit colour to cells whose value exactly equals a named key, checked before
the continuous `ColorFunction` ramp; a cell matching no rule still gets the
normal scaled `ColorFunction` colour rather than being left uncoloured —
`ArrayPlot[{{1,0,0.5},{0,1,0.5}}, ColorRules -> {1 -> Pink, 0 -> Yellow}]` now
paints the `1`/`0` cells Pink/Yellow and the `0.5` cells on the usual grey
ramp. New `SYM_ColorRules` interned in `sym_names.c` alongside the other
`ArrayPlot` option symbols.

Implementing it surfaced a real bug, caught by `leaks --atExit` rather than by
inspection: `evaluate()` **borrows** its argument — it makes its own internal
copy and never frees what it's handed (see `src/eval.c`'s `evaluate`, whose
first act is `current = expr_copy(e)`) — so `evaluate(expr_copy(rhs))` with the
copy inlined leaks that copy's reference. This is the exact bug class already
fixed for `guard_all_true` in `src/match.c` (`docs/spec/changelog/2026-08-10.md`,
"Matcher: fix per-guard-evaluation memory leak"), just not yet applied to
`arrayplot.c`. Because `expr_copy` is a refcount bump rather than a deep clone,
an orphaned bump on a shared subtree (`rhs`) blocks that subtree from ever
reaching refcount 0 during the caller's teardown — so the leak is not one node
but the whole unevaluated option-value subtree, which is why `ColorRules ->
{1 -> Pink, 0 -> Yellow}` (evaluating named colours into `RGBColor[...]`) leaked
visibly (11 blocks/560 B for one call) while a bare `Mesh -> All` leaked a
single 64-byte node per call — both instances of the identical bug, just
different-sized victims. All five call sites in `arrayplot.c`
(`ColorFunctionScaling`, `Mesh`, `PlotLegends`, `ColorRules`, and the generic
Graphics-option passthrough — i.e. every option `ArrayPlot` accepts) shared the
inlined form. Fixed with one local helper, `eval_borrowed()`, that names the
copy and frees it after use; not touched in the sibling plotters
(`densityplot.c` etc.), which share the same idiom and same latent bug but are
outside this change's scope.

Verified: `leaks --atExit` over 50-iteration loops covering
`ColorRules`-matching, `ColorRules -> None`, plain `Mesh -> All`, and the
combined `Mesh`+`PlotLegends`+`ColorFunction` case from the original `ArrayPlot`
changelog entry above — all now **0 leaks** (previously 1–6 leaked
blocks/call depending on the option combination). `graphics_tests` green
including a new `test_arrayplot_color_rules_override_matching_cells` (exact-key
match, unmatched-value fallback, `ColorRules -> None` equivalence to omitting
the option). `make` clean at `-O3 -std=c99 -Wall -Wextra`, no new warnings.

## Graphics: fix a Frame+AspectRatio letterbox, then let ArrayPlot mix numeric and colour cells freely (2026-08-12)

Two follow-up fixes to `ArrayPlot`, both from real usage rather than review.

**1 — Frame plots with an explicit `AspectRatio` letterboxed inside their
own frame** (reported via screenshot: an `ArrayPlot`'s coloured grid sat with
a visible white margin between it and the frame border, on all sides).
Root cause was general renderer logic in `src/graphics/render.c`, not
`ArrayPlot`-specific — reproduced identically on unmodified `Plot3D[...,
Mesh -> All]`, which also sets an explicit `AspectRatio`. `gfx_window_height()`
sizes the *window* to match `AspectRatio`, but `Frame`'s margins are fixed
pixel amounts (some floored, e.g. clearing the toolbar), not proportional
between width and height — so the margin-reduced *data region* lands at a
different aspect ratio than the window, and any `Frame` plot with an explicit
`AspectRatio` (`ArrayPlot`'s `rows/cols` default, `DensityPlot`'s `1`, …) can
letterbox. Added `gfx_window_height_fit_region()`: a few fixed-point
iterations (the margin formula is a contraction — each margin is either
height-independent or ≤7% of height) that solve for the window height whose
*region*, not just the window, hits the target ratio. The margin formulas
themselves were factored into shared `gfx_horizontal_margins()` /
`gfx_vertical_margins()` so the sizing pass and the actual region layout can
never drift apart. `gfx_window_height()` itself is untouched (its pinned
`test_window_height_policy` still passes byte-for-byte); the new function is
called right after it in `graphics_show()`, before `InitWindow`. New
`test_window_height_fit_region_no_letterbox` pins both halves: the corrected
height's region matches the target ratio within 1%, and — to prove the test
actually exercises the bug — the pre-fix (naive) height's region does not
(>5% off) for the same inputs.

*Diagnostic note:* while investigating a *separate* "window freezes on close"
report against this same `ArrayPlot` call, `sample`(1) on the actual running
process showed it had already returned to the REPL prompt (`readline`) —
i.e. `CloseWindow()` had already run. That looks like a stale/ghost frame
left on screen by the OS compositor after close, not a hang in Mathilda; it
self-resolves (switch away and back). No code change from that report; noted
here since it surfaced while looking at the same window-sizing code path.

**2 — `ArrayPlot[{{1, 0, 0, Pink}, {1, 1, 0, Pink}, {1, 0, 1, Red}}]` (mixing
plain numbers and colour literals in the same array) returned unevaluated.**
The array-loading logic required every cell to be numeric *or* every cell to
be a colour literal — a matrix mixing both matched neither shape and fell
through as "can't evaluate this," even though calling out a few specific
cells by colour while the rest follow the normal heatmap is a natural,
common use of the raw-pixel-grid feature. `src/graphics/arrayplot.c`'s
`arrayplot_is_color_matrix` (all-or-nothing) is replaced by `arrayplot_load`,
which classifies **each cell independently**: a colour literal is painted
directly, a plain number goes through `ColorRules`/`ColorFunction` as usual,
and anything else (a symbolic non-color, non-number cell) leaves the whole
call unevaluated, same as before. `ColorFunction`'s `[zmin, zmax]` scaling
range and `PlotLegends`'s eligibility (still "only when at least one cell is
numeric") are now computed by scanning just the numeric cells rather than
gating on an all-or-nothing mode flag. An `NDArray` input is unaffected — a
dense numeric buffer can't contain a colour literal by construction, so it
still goes through `na_load_matrix` as a pure numeric load.

New `test_arrayplot_mixed_numeric_and_color_cells` (named colours paint
directly, numeric cells keep the greyscale ramp) and an added case on
`test_arrayplot_invalid_args_stay_unevaluated` (a genuinely invalid cell,
e.g. `{{1, 2, foo}}`, still leaves the call unevaluated — the new per-cell
loader doesn't accidentally accept everything). `graphics_tests` all green;
`leaks --atExit` over 50 iterations mixing the new code path with the
existing pure-numeric, pure-colour, and both failure shapes: 0 leaks. `make`
clean at `-O3 -std=c99 -Wall -Wextra`, no new warnings.

## Build: register ArrayPlot in the packed-array gate (2026-08-12)

`make check-packed-aware` failed: `ArrayPlot` checks `data->type == EXPR_NDARRAY`
(its fast path for a matrix argument, `src/graphics/arrayplot.c`) but was never
added to `src/pack.c`'s `AWARE` list, so the evaluator's transparency gate
materialised any packed argument into a full nested `List` of boxed `Expr`
nodes *before* `ArrayPlot` ever ran — the `EXPR_NDARRAY` branch was dead code
for every packed input, only reachable via an explicit visible `NDArray[...]`.
Concretely, every example in `ArrayPlot`'s own docstring
(`RandomReal[1, {20, 20}]`, `Table[Mod[i + j, 5], {i, 10}, {j, 10}]`) produces
a packed list and was silently taking the slow path.

Added `"ArrayPlot"` to `AWARE`, alongside `Fit`/`DesignMatrix`/
`Interpolation` — the existing heads that read a data table straight off the
buffer via a head-level path rather than a per-element kernel, the same
category `ArrayPlot` falls into via `na_load_matrix`. Also added it to
`INT64_OK`: cell colouring is a machine-real computation regardless of the
input's exactness (`arrayplot_load`'s numeric arm converts to `double` either
way), so an int64 buffer needs no materialisation to match the List path —
without this, `ArrayPlot[Table[Mod[i+j,5], ...]]` (an int64 array, per the
docstring's own example) would still have materialised despite the `AWARE`
fix, since `INT64_OK` is a separate gate for exactness-sensitive heads.

Verified: `make check-packed-aware` passes (`AWARE=176`, `INT64_OK=106`, 0
problems). `ArrayPlot` on a packed real matrix, a packed int64 matrix
(`Table[Mod[...], ...]`), and an explicit `NDArray[...]` all produce
byte-identical `FullForm` output to each other and to the pre-fix
materialised path — the fix only removes the unnecessary materialisation, it
changes no result. `graphics_tests` all green; `make` clean at
`-O3 -std=c99 -Wall -Wextra`, no new warnings.
