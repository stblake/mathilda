# Changelog: week of 2026-08-31 (Mon) – 2026-09-06 (Sun)

## DSolve — SymPy ODE parity audit + heuristic Lie point-symmetry method (M10 L1)

Audited `DSolve` against SymPy's documented ODE solver hints
(`sympy.solvers.ode.allhints` + `dsolve_system`). Mathilda covers most of SymPy
and exceeds it in several areas (full Kovacic, Abel, Chini, Lagrange, operator
factoring — none of which SymPy has); the genuine gaps are recorded in
`DSOLVE_PLAN.md` as two new milestones: **M9** (deterministic: `Factorable`,
`NthAlgebraic`, `AlmostLinear`, `LinearCoefficients`, `SeparableReduced`,
`Liouville`, `UndeterminedCoefficients`, `FirstOrderPowerSeries`) and **M10**
(heuristic Lie point-symmetry, SymPy's `lie_group`).

New builtin **`DSolve`LieSymmetry`** (alias `DSolve`LieGroup`;
`src/calculus/dsolve_lie.c`) — the general first-order backstop, run after the
deterministic specialists and before the series fallback. It is the one
deliberately heuristic method in the cascade: for a first-order ODE the
linearized symmetry condition is one PDE in two unknowns (`ξ`, `η`), which is
underdetermined, so — as in SymPy/Maple — a table of ansatz heuristics
(Cheb-Terrab et al.) is used.

- **Method.** For `y' = ω(x,y)`, each heuristic proposes infinitesimals `(ξ,η)`;
  a `checkinfsol` gate accepts only those satisfying `S = η_x + (η_y − ξ_x)ω −
  ξ_y ω² − ξ ω_x − η ω_y == 0`. The accepted symmetry gives the Lie integrating
  factor `μ = 1/(η − ξ ω)`, whose exact-equation quadrature is the implicit first
  integral `{{G(x,y[x]) == C[1]}}`, returned through `dsolve_run_implicit` and
  verified by implicit differentiation (`y' == −G_x/G_y`). No inert heads — every
  branch back-substitutes.
- **L1.** Substrate (`lie_S_expr` / `lie_check` / `lie_first_integral`) plus the
  `abaco1_simple` heuristic (one-variable ansätze). Solves e.g. `y' == y/x + x`
  (→ `{{-x + y[x]/x == C[1]}}`), `y' == x y²` (→ `{{x²/2 + 1/y[x] == C[1]}}`),
  `y' == 2 x y + x`.
- **L2 `linear`.** The affine ansatz `ξ = a1 x + a2 y + a3`,
  `η = a4 x + a5 y + a6`: the determining system is the coefficient matrix of the
  cleared symmetry condition (`Outer[Coefficient, Flatten[CoefficientList[…]],
  {a1..a6}]`), and its `NullSpace` is a basis of admissible symmetries — no
  `Solve`, hence no free-variable message. Catches the **linear-coefficients**
  class `y' == (a1 x+b1 y+c1)/(a2 x+b2 y+c2)` — e.g. `y' == (x+2y-4)/(2x+y-5)` and
  `y' == (2x+3y-1)/(3x+2y+2)`, both previously unsolved by *any* method — now
  solved through the automatic cascade. Lie runs **after every deterministic
  specialist** (including the homogeneous implicit fallback, which keeps its
  cleaner form for its own equations — regression-checked), immediately before the
  series fallback. Declines `y' == y² + x`.
- **Remaining.** L2 `abaco1_product` / `function_sum` / `abaco2_similar`; L3
  `bivariate` / `chi` / `abaco2_unique_*`.
  Design note: `docs/design/dsolve_lie_symmetry.md` (with reference preprints).
- **Tests.** `tests/test_dsolve.c` `t_method_lie` (pinned, implicit-differentiation
  verified) and `t_lie_declines` (non-vacuous decline). Attributes `Protected`;
  Information string via `symtab_set_docstring`. Builds clean under
  `-std=c99 -Wall -Wextra`; valgrind shows no new leaks beyond the DSolve-engine
  baseline.

## ListGradient — numerical gradient of a sampled array (numpy.gradient port)

New builtin `ListGradient` (`src/list/list_gradient.c`): the finite-difference
numerical gradient of a sampled array, a from-first-principles port of
`numpy.gradient`. Second-order central differences in the interior and one-sided
differences at the edges, computed per axis for an array of any rank — a rank-1
input gives one vector, a rank-`k` input gives `{g1, ..., gk}`.

- **numpy-default semantics.** The default (`Method -> "Centered"`,
  `DifferenceOrder -> 2`) reproduces `numpy.gradient` exactly, including
  first-order one-sided edges (numpy `edge_order = 1`): the edge accuracy is one
  order below the interior.
- **Generalised scheme.** `Method -> "Centered" | "Forward" | "Backward"`;
  `DifferenceOrder -> p` (default 2); `WindowLength -> m` (an alias for the
  order, `m = p + 1` points → order `p`); `Axis -> All | a | {a, ...}` to
  restrict to particular axes.
- **Spacing.** A second positional argument gives uniform spacing (scalar),
  per-axis spacing, or coordinate vectors for non-uniform sampling — the numpy
  `varargs` folded into one argument.
- **One kernel, exact everywhere.** All scheme/order/window/grid combinations run
  through Fornberg's finite-difference-weight recurrence, exact on non-uniform
  grids. Integer input yields exact `Rational`s, symbolic input a symbolic
  result.
- **Fast paths.** Machine `Real` **and complex** arrays compute straight on the
  packed/NDArray buffer (`list_gradient_ndarray`, on `pack.c`'s `AWARE` list),
  one axis at a time via a strided axpy pass (the weights are real, so a complex
  element is two contiguous doubles carried through the same pass);
  `ListGradient[v]` lowers in `Compile[]` (rank-1 array form, `ND_FNS` delegate)
  and therefore auto-compiles. An integer buffer deliberately materialises and
  takes the exact `Rational` `List` path.
- **Number towers.** Verified across the whole numeric stack: machine
  `float64`/`float32`, GMP bignums and exact `Rational`s (exact results), MPFR
  arbitrary precision (results retain the input precision), and complex (exact
  and machine, `List` and packed `NDArray`).
- **Benchmarked against `numpy.gradient` — and now beats it.** Accuracy: the
  default scheme reproduces `numpy.gradient` to machine precision (bit-identical
  on random data, ~3e-15 on smooth uniform grids, ~2e-13 non-uniform); the
  generalized schemes converge at their stated interior order (2/4/6 confirmed).
  Performance (float64, this machine): after vectorising the buffer kernel,
  ListGradient is **1.6–4.3× faster than `numpy.gradient`** on every 1-D and
  multi-dimensional shape measured (e.g. 1-D 10⁶: 0.88 ms vs 2.6–3.9 ms; 2-D
  1000² both axes: 3.58 ms vs 7.8 ms; 3-D 100³ all axes: 5.7 ms vs 12.3 ms),
  with only the 4th-order 5-point scheme (which numpy cannot express) at parity.
  The optimisation was loop structure, **not** the numerics: (1) `restrict`
  pointers so the compiler knows input/output do not alias; (2) a tap-outer
  contiguous axpy over the interior block (SIMD FMA) instead of a per-element
  stencil call, which fixed the `inner=1` shapes (1-D and the strided axis) that
  did not vectorise; (3) a fused single-pass unroll for the common 2-/3-point
  windows to cut memory passes; and (4) building the multi-axis result as one
  stacked rank-(k+1) buffer directly, instead of N arrays the pack gate then
  copies together. Verified: buffer path timed (packed/`NDArray`, zero gate
  materialisations — not Expr trees), accuracy unchanged, all surface audits and
  valgrind clean.
- Registered with attribute `Protected`, an Information docstring, `Options`
  defaults, and a 24-case unit suite (`tests/test_list_gradient.c`) covering
  numpy parity, non-uniform grids, every Method/order/window, multi-axis and
  `Axis` selection, packed/visible-NDArray agreement, compilation, and the
  symbolic/exact and unevaluated paths. Valgrind-clean (no leak beyond the
  REPL-init baseline).

## FindVertexColoring — exported search self-protects its stack buffers (RG-2 #2)

`fvc_search` (exported in `src/graph/graph.h`) drives a branch-and-bound whose
inner `fvc_bb` uses stack arrays `seen[]`/`forbid[]` sized to `FVC_MAX_VERTICES`
(128). The 128-vertex cap was enforced only in the head
`builtin_find_vertex_coloring`, not in `fvc_search` — and because the symbol is
exported while `FVC_MAX_VERTICES` is not, a cross-TU caller passing a larger
graph could not discover the precondition and would overflow those buffers.
`fvc_search` now refuses (`return 0`) when `n > FVC_MAX_VERTICES`, putting the
invariant with the buffers it protects. No behaviour change on the head path,
which already filters `n > 128`. Closes the RG-2 adversarial finding #2.
Regression: a direct `fvc_search` on `CompleteGraph[129]` must return 0 with
zero steps (`test_vertex_coloring_internals`, `tests/test_graph.c`).

## DSolve — Chini second reduction, x^a y^b integrating factor, and a leaked-warning fix

Two solvable first-order ODEs were failing loudly — each printed a cascade of
`Power::infy: 1/0` / `Infinity::indet` and then returned unevaluated:

```
DSolve[y'[x] == -x E^-x - y[x] + x E^(2x) y[x]^3, y[x], x]        (* Chini *)
DSolve[(x y[x] - 2 x) y'[x] == y[x] - y[x]^2 + 3 x^2 y[x]^3, y[x], x]  (* exact via x^a y^b *)
```

Three independent defects, all fixed:

- **Wrong classification → a valid equation rejected (the leaked `1/0`).**
  `DSolve`Bernoulli` and `DSolve`Chini` tested the candidate exponent
  `nexp = Y Q_Y/Q` for `FreeQ[·, x]` **before** reducing it. `Q` is stored
  unexpanded (e.g. `-2 x E^(2x) Y^3` hidden inside a sum), so `nexp ≡ 3` still
  contained `x`/`Y` textually; `ds_free_of` then fell to the numeric zero-test
  sampler, which floating-point-cancelled `Q` to exactly `0.0`, evaluated
  `0^(-1)` (the leaked `Power::infy`), and — worse — read the resulting
  `ComplexInfinity` as *"definitely non-zero"*, so the constant exponent looked
  x-dependent and the classifier declined. Fixed by reducing `nexp` **before** the
  guard. Reduction uses **`Cancel`, not `Simplify`**: this runs on the decline
  path of *every* equation reaching Bernoulli/Chini, and full `Simplify` hangs on
  a symbolic radical ratio (e.g. `y' == Sqrt[y^4 + K]` fed in by
  `AutonomousReduction`), whereas `Cancel` is a cheap rational-GCD that still
  collapses the genuine constant.

- **Chini second reduction (solves the first example).** `dsolve_chini_first_integral`
  tried only reduction (a) (reduce-to-autonomous, `y = f^(-1/(n-1)) u`, needs
  `B = g + f'/((n-1)f)` constant). It now falls back to reduction (b) —
  **linear-term removal**, `y = e^(∫g) w` → `w' = P w^n + R` with `P = f e^((n-1)∫g)`,
  `R = h e^(-∫g)`; when `R/P == c` is constant the equation is separable, giving the
  implicit first integral `∫dw/(w^n+c) − ∫P dx == C[1]`, `w = y e^(-∫g)`. The
  first example returns `∫du/(u^3−1) − x^2/2 == C[1]`, `u = y[x] E^x`. Shared with
  Abel, so more Abel equations solve too; the speculative integrals are bracketed
  with `g_integrate_quiet`.

- **Exact via `x^a y^b` integrating factor (solves the second example).**
  `DSolve`Exact` searched only `μ(x)` and `μ(y)`. It now also proposes
  `μ = x^a y^b` with constant `a,b` from the linear exactness condition
  `b(M/y) − a(N/x) + (M_y − N_x) == 0` (sampled at a few generic points and solved),
  **accepted only after a symbolic exactness re-check** (`(μM)_y == (μN)_x`), with
  the substrate's back-substitution verify as the final backstop. Gated to
  polynomial `M,N` (`PolynomialQ`) so the speculative `Solve` never runs on the
  heavy radical systems the autonomous recursion feeds in. The second example
  returns the two explicit branches of `3x + 1/(xy) − 1/(xy^2) == C[1]`
  (`μ = x^-2 y^-3`).

- **Speculative arithmetic warnings no longer leak.** `builtin_dsolve` brackets the
  whole method cascade in `arith_warnings_mute_push/pop` (the family Frobenius/
  Kovacic already mute per-region): every classifier legitimately forms `1/0`
  while probing an equation that is not of its form, and the verifier is the real
  gate — so a decline is now silent. Even a bare `DSolve[y'==-x/y, y[x], x]`
  (which used to leak one `Power::infy`) is clean.

Both examples verify (residual → 0 by numeric back-substitution). Gates: all three
DSolve ctest suites green (`dsolve_tests` 28 s, unchanged from baseline —
confirming the `Cancel`/`PolynomialQ` choices kept the fix off the hot decline
paths), `make check-c99` clean, valgrind shows no new definitely/possibly-lost
blocks over the one-time ~13.6 KB engine baseline. Files: `dsolve_bernoulli.c`,
`dsolve_chini.c`, `dsolve_exact.c`, `dsolve.c`.

## DSolve — Kovacic stress-test hardening (full Case-1, Bessel-reducible, hang/decline guards)

Triaging a corpus of Kovacic stress tests exposed a fragile 2nd-order path: some
equations hung, some returned bare-unevaluated, and one leaked an integrator
warning. Fixes, all general rather than case-specific:

- **Full classical Kovacic Case 1.** `DSolve`Kovacic`'s apparent-singularity
  completion was limited to pole order ≤ 2 and `r` vanishing to order ≥ 2 at ∞. It
  now implements the complete algorithm (Kovacic 1986): the local principal part
  `[√r]_c` for **even-order poles ≥ 4**, and the polynomial part `[√r]_∞` when `r`
  **grows at infinity** (`O(∞) = degd−degn ≤ 0`), with `ω = s(∞)[√r]_∞ +
  Σ_c(s(c)[√r]_c + α_c^{s(c)}/(x−c))` and degree bound `d = α_∞^{s(∞)} − Σ_c
  α_c^{s(c)}`. Pass 2 now prefers **two independent `P·Exp` families** directly
  (no reduction-of-order integral), which closes completely-reducible cases like
  `y'' − (x² + 3/(4x²))y == 0 → x^(−1/2)(C[1]e^{−x²/2} + C[2]e^{x²/2})` that the old
  δ≥2 slice rejected. The critical constant `b` uses `([√r])²` (not the raw √r
  Laurent series — they diverge at infinity).
- **Bessel-reducible recognizer.** `DSolve`SpecialFunctionForm` now maps the
  pure-power potential `y'' + A xᵐ y == 0` (`m` a number ≠ 0, −2) to
  `Sqrt[x] Z_{1/(m+2)}(...)` — `J/Y` for `A>0`, modified `I/K` for `A<0` — so
  `y'' − x⁴ y == 0 → Sqrt[x](C[1] BesselI[1/6, x³/3] + C[2] BesselK[1/6, x³/3])`
  instead of a truncated series.
- **Hang guard.** A denominator-degree gate in `DSolve`Kovacic` declines a
  high-degree rational `r` up front (before any Factor/Solve/analyze_roots), so
  `y'' + ((x¹⁰−1)/(x¹²+1))y == 0` returns a fast Taylor series instead of looping.
  A reduction-of-order integral in a hang-prone special function (`Erf`/`Erfi`/…)
  is declined rather than Simplify'd (its complex argument would hang), letting
  Case 2 take over.
- **Silent speculative declines.** The Kovacic recovery/second-solution integrals
  are speculative, so a non-elementary result there no longer leaks the
  `Integrate::nonelem` diagnostic (a new `g_integrate_quiet` counter); direct user
  `Integrate` still reports it.
- **Series never returns nothing.** Automatic `DSolve` of a *rational*-coefficient
  linear ODE whose `x=0` is irregular/obstructed now expands about a nearby
  ordinary point (`SeriesData[x, x0, …]`) rather than leaving the equation
  unevaluated. The pinned `DSolve`PowerSeries`/`FrobeniusSeries` keeps its
  "series about the origin, else decline" contract.
- **Cosmetic.** The reduction-of-order second solution's constant factor now folds
  into the arbitrary constant: `y'' − 3/(16x²)y == 0 → C[1] x^(¼(2−√7)) +
  C[2] x^(¼(2+√7))` (was `2 C[2] x^(…)/√7 + …`).

Tests: `tests/test_dsolve.c` (Bessel-reducible, high-degree no-hang) and
`tests/test_dsolve_m5_stress.c` (growth-at-∞ closed forms, growth no-hang).

## DSolve — Kovacic Case 1 apparent-singularity completion (Legendre / Chebyshev / …)

`DSolve` returned a truncated **power series** for Legendre's equation
`(1−x²)y'' − 2x y' + 2y == 0` (and the rest of the integer-degree
Legendre/Chebyshev/Gegenbauer/Jacobi family) even though a closed form exists — the
elementary `C[1] x + C[2](1 − x ArcTanh[x])` that Maple and Mathematica return. The
cascade order was already correct (every closed-form method runs before the series
fallback); the gap was that **no closed-form method succeeded**, so it fell through.

Root cause: `DSolve`Kovacic`'s Case 1 built its ω-ansatz with poles only at the poles
of the normal-form potential `r`. The Legendre solution needs
`ω = 1/x + x/(x²−1)` — the `1/x` is `P'/P` for `P = x`, an **apparent singularity**
(a zero of the solution where `r` is regular). The classical degree-`d` monic
polynomial `P` that captures those existed only for *polynomial* `r`
(`kovacic_case1_poly_r`, gated to `degd == 0`); for rational `r` with genuine poles
it was skipped.

**Fix — `kovacic_case1_general` (`src/calculus/dsolve_kovacic.c`), the classical
Case 1 for arbitrary rational `r`:**
- locates the poles as the roots of `Denominator[r]` (via `dsolve_analyze_roots`, so
  **complex** conjugate pairs are handled), with local exponents
  `α_c^{±} = (1 ± √(1+4 b_c))/2`, `b_c = lim_{x→c}(x−c)² r`;
- builds `θ = Σ_c α_c^{s_c}/(x−c)` per sign mask and a monic `P` of the classical
  degree `d = α_∞^{±} − Σ_c α_c^{s_c}` solving `P'' + 2θP' + (θ'+θ²−r)P == 0`; the
  degree is tested **numerically** (`N[…]`) so complex-α combinations reject instantly
  instead of a per-mask symbolic `Simplify` that took minutes;
- assembles the second solution at the **y-level** (`y2 = y1 ∫ w²/y1² dx`, reduction
  of order on the original ODE) so the recovery radical `w` cancels up front — the
  z-level `z1 ∫ 1/z1²` multiplies `√(x²−1)` into the `ArcTanh` answer and sends
  `Simplify` into a multi-second blow-up (Gegenbauer went 17 s → 0.1 s);
- picks the cleanest first solution (smallest `LeafCount` → the orthogonal
  polynomial) among the sign masks; every candidate is exact by construction
  (`dsolve_run` verifies as the backstop).

Now `DSolve` returns the elementary closed form for Legendre `n=1..5`, Chebyshev,
Gegenbauer, Jacobi, and complex-pole analogues, all in < 0.5 s. `Solve[…, {}]` (empty
variable list) in the monic-`P` solve is short-circuited in `solve_ansatz`, removing a
spurious `Solve::ivar` message.

**Case-2 hang guard.** The Chebyshev equation (and e.g. `(x³+1)y'' + x y' + y == 0`)
used to **hang** in Kovacic Case 2: after Case 1 declined, Case 2's rational-σ
undetermined-coefficient search handed `Solve` a large coupled system over a
degree-≥2 (complex-pole) denominator factor and ran for minutes. Case 2 is now
**skipped when any irreducible denominator factor has degree ≥ 2** — those Liouvillian
solutions are already covered by the general Case 1, and the input otherwise declines
to the series fallback instead of hanging. Tests: 6 new cases in `tests/test_dsolve.c`
(Legendre 1/2, Chebyshev, complex poles, auto-closed-form, no-hang); all DSolve suites
(incl. the m5 Case-2 stress) pass.

## DSolve — OperatorFactor / DFactor (linear-operator factoring)

`DSolve`OperatorFactor` solves a homogeneous linear ODE of order ≥ 3 by **factoring
its differential operator**, and `DSolve`DFactor` exposes the factorization. This
closes the last `[ ]` item in §1c of `DSOLVE_PLAN.md` — the genuinely-new capability
beyond the existing cascade, since `Kovacic` only handles 2nd order, so
variable-coefficient order-≥3 operators that factor previously fell through to the
Frobenius series fallback.

The core primitive is the **first-order right factor** `(D − r)`, `r ∈ C(x)`:
`(D − r)` right-divides `L` iff `y = Exp[∫r]` solves `L[y] == 0` (a hyperexponential
solution), iff the Riccati residual `R(r) = Σ aₖ Pₖ(r)` vanishes (`Pₖ` the Bell
polynomials, `P₀=1`, `P_{k+1}=Pₖ'+r Pₖ`). The method:
- **finds** a rational `r` by an undetermined-coefficient search over a pole/degree-
  bounded ansatz (poles from `FactorList[Denominator[…]]`, simple poles first, low
  polynomial degree), solving the coefficient system with `Solve` and testing the
  exact division remainder for each branch;
- **peels** it via operator right-division to the order-(n−1) quotient
  (`q_{n-1}=aₙ`, `q_{m-1}=aₘ+Σ C(j,m) D^(j-m)[r] q_j`);
- **recurses** `DSolve` on the quotient (which the whole cascade — const-coeff, Euler,
  Kovacic, or a further peel — may solve), then closes with the trailing first-order
  linear solve `(D − r)y == z`, its constant `C[kk]` measured to stay contiguous with
  the quotient's `C[1..n-1]`.

```
In[1]:= DSolve[(x-1)^3 y'''[x] - 7(x-1)^2 y''[x] + 18(x-1) y'[x] - 18 y[x] == 0, y[x], x]
        (* shifted-Euler at x=1 — EulerCauchy only detects the pole at 0, so this is
           OperatorFactor's niche; returns a 3-constant general solution *)

In[2]:= DSolve`DFactor[y'''[x] - 6 y''[x] + 11 y'[x] - 6 y[x] == 0, y[x], x]
Out[2]= {Dx - 1, Dx - 2, Dx - 3}
```

- **Cascade slot / scope.** Runs after `Kovacic` (which owns order 2 and whose Case 1
  is the same rational-factor search), before the reduction/series methods; guarded
  to order ≥ 3, homogeneous, coefficients rational-in-`x` with numeric constants.
  Its unique reach is reducible variable-coefficient operators the earlier methods
  miss (shifted-Euler at a pole ≠ 0, mixed reducible spectra). Finds first-order
  **right** factors only — an operator whose only factorization has an irreducible
  ≥ 2 right factor, or whose reduction integrals are non-elementary (distinct-pole
  compositions produce dilogarithms), declines (no wrong answer; the substrate
  back-substitution is the backstop). Deferred: inhomogeneous forcing, irregular-
  singular (double-pole) `r`, and 2nd-order right factors (Beke).
- **`DSolve`DFactor`** returns the ordered first-order factors as `{Dx − r_i}` (inert
  `Dx`); a not-fully-reducible operator appends an inert remainder operator
  `Σ q_j Dx^j`. Works at any order ≥ 1.
- **Zero regression risk.** The file is self-contained — it reuses only the shared
  `ds_*` substrate and front-end builtins and makes **no** changes to
  `dsolve_kovacic.c` (the small ansatz/search overlap is duplicated deliberately).
- **New file** `src/calculus/dsolve_operator_factor.c` (both builtins + the shared
  `of_find_factor` / `of_divide` core); wired into the scalar cascade and the pinned
  `Method -> "OperatorFactor"` in `dsolve.c`.
- **Tests.** `tests/test_dsolve.c` — `t_method_operfactor` (shifted-Euler flagship),
  `t_operfactor_more` (constant order 3 & 4, resonant repeated factor), `t_operfactor_ivp`,
  `t_operfactor_declines` (Airy-type + order-2 guard), `t_dfactor` (reconstruct the
  operator from the factors), `t_operfactor_auto`. `tests/test_dsolve_stress.c` —
  `operfactor_ok` / `dfactor_ok` forward generators composing `(D − r_i)` over
  all-constant, shifted-Euler, resonant, and Euler families (each back-substituted /
  reconstructed).

Gates: 3/3 dsolve ctest targets green (incl. the Kovacic/M5 stress suite — confirming
zero regression); `make check-c99` exit 0; valgrind shows **no per-call leak** on
both the OperatorFactor and DFactor paths (1× and 6× the same call both = 13,440 B
definitely + 6,312 B indirectly, the one-time DSolve engine baseline).

## DSolve — ExactODE (higher-order exact linear equations)

`DSolve`ExactODE` solves a linear ODE of order ≥ 2 whose left side is a **total
derivative** — `L[y] = Σ aₖ(x) y⁽ᵏ⁾ == g(x)` with `L[y] == d/dx(M[y])` for an
order-(n−1) operator `M`. Such an equation is *exact* and integrates once to the
**first integral** `M[y] == Integrate[g, x] + C[n]`, a lower-order ODE handed back
to the scalar cascade. This is the first of the two `[ ]` §1c items in
`DSOLVE_PLAN.md` (the other, `OperatorFactor`/`DFactor`, remains future work).

The first-integral coefficients follow from matching
`Σ aₖ y⁽ᵏ⁾ = d/dx(Σ bⱼ y⁽ʲ⁾)`: `b_{n-1} = a_n`, `b_{k-1} = a_k − b_k'`, and the
exactness condition is the leftover `a_0 == b_0'` (equivalently
`Σ(−1)ᵏ aₖ⁽ᵏ⁾ == 0`). The order-(n−1) sub-solve emits `C[1..n-1]` and the
integration constant is `C[n]` — contiguous, no renumbering. Iterated exactness
is free: the recursion re-enters `ExactODE` on the reduced equation, so a
doubly-exact 3rd-order equation reduces twice.

```
In[1]:= DSolve[x y''[x] + y'[x] == 0, y[x], x]
Out[1]= {{y[x] -> C[1] + C[2] Log[x]}}

In[2]:= DSolve[x y''[x] + y'[x] == x, y[x], x]          (* forcing folded in *)
Out[2]= {{y[x] -> C[1] + x^2/4 + C[2] Log[x]}}

In[3]:= DSolve[x y'''[x] + y''[x] == 0, y[x], x]         (* order-2 reduction *)
Out[3]= {{y[x] -> C[1] + (C[2] - C[3]) x + C[3] x Log[x]}}
```

- **Placement / scope.** Runs after `EulerCauchy` (cleaner constants there) and
  before the special-function / Kovacic / series machinery (a cheap deterministic
  reduction to an elementary lower-order equation is preferred over a
  special-function or series answer). The reference Airy, Bessel, Euler-Cauchy and
  Kovacic equations are all **not** exact (`a₀ − b₀' ≠ 0`), so their pinned tests
  keep their methods. First cut is linear, order ≥ 2, genuinely exact
  (first-order exact `M + N y' == 0` is `DSolve`Exact`, excluded by the order ≥ 2
  guard); a non-exact equation or a non-elementary `∫g` declines. Integrating-
  factor (adjoint) exactness and nonlinear total-derivative detection are future.
- **Verification.** The substrate back-substitutes the reduced solution into the
  *original* order-n residual; since it satisfies `M[y] == ∫g + C[n]` and
  `L[y] = d/dx(M[y])`, `L[body] − g` vanishes for elementary bodies (a buggy
  reduction is dropped, a messy-but-correct one is kept).
- **New file** `src/calculus/dsolve_exactode.c` (three-function contract, mirrors
  `dsolve_reduce_order.c`: recurse into `DSolve` on the reduced equation, reuse
  the `extract_applied` idiom); wired into the scalar cascade and the pinned
  `Method -> "ExactODE"` / `DSolve`ExactODE` in `dsolve.c`.
- **Tests.** `tests/test_dsolve.c` — `t_method_exactode`, `t_exactode_more`
  (2nd-order + inhomogeneous + 3rd-order), `t_exactode_declines` (non-exact +
  first-order stay symbolic), `t_exactode_auto`. `tests/test_dsolve_stress.c` — an
  `exact_ode_ok` forward generator building the equation as `d/dx(b₁ y' + b₀ y)`
  (exact by construction, reduced solve elementary) over six `(b₁,b₀)` pairs plus
  an inhomogeneous case.

Gates: 3/3 dsolve ctest targets green; `make check-c99` clean; valgrind shows

indirectly, the one-time DSolve engine baseline).

## DSolve — Kummer / Gauss hypergeometric recognizers

`DSolve\`SpecialFunctionForm` now recognises the two flagship classical
second-order linear families, extending the Airy/Bessel table:

- **Kummer (confluent hypergeometric, ₁F₁)** — `x y'' + (b−x) y' − a y == 0`
  → `C[1] Hypergeometric1F1[a,b,x] + C[2] x^(1−b) Hypergeometric1F1[a−b+1,2−b,x]`.
  `a`, `b` are read directly (`b = x(P+1)`, `a = −x Q`, both free of `x`).
- **Gauss (hypergeometric, ₂F₁)** — `x(1−x) y'' + (c−(a+b+1)x) y' − a b y == 0`
  → `C[1] Hypergeometric2F1[a,b,c,x] + C[2] x^(1−c) Hypergeometric2F1[a−c+1,b−c+1,2−c,x]`.
  `c` and `a+b`, `ab` are read off `x(1−x)P` (linear) and `x(1−x)Q` (constant);
  `a`, `b` are the roots of `t² − (a+b) t + ab`, recovered radical-free from the
  quadratic's linear factors (`FactorList`), so a symbolic equation returns clean
  `2F1[a,b,c,x]` rather than a `Sqrt[(a−b)²]` form.

```
In[1]:= DSolve[x y''[x] + (3/2 - x) y'[x] - 2 y[x] == 0, y[x], x]
Out[1]= {{y[x] -> C[1] HypergeometricPFQ[{2}, {3/2}, x]
                 + C[2] HypergeometricPFQ[{3/2}, {1/2}, x] / Sqrt[x]}}

In[2]:= DSolve[x (1-x) y''[x] + (1/2 - (a+b+1) x) y'[x] - a b y[x] == 0, y[x], x]
Out[2]= {{y[x] -> C[1] HypergeometricPFQ[{a, b}, {1/2}, x]
                 + C[2] Sqrt[x] HypergeometricPFQ[{1/2+a, 1/2+b}, {3/2}, x]}}
```

- **Verifies for free.** `Hypergeometric1F1`/`2F1` auto-rewrite to
  `HypergeometricPFQ`, which carries a `deriv.c` z-derivative rule, so the emitted
  branches back-substitute through the substrate's verifier (kept as structurally
  exact, like Airy/Bessel — the residual is a contiguous-relation identity
  zero_test does not discharge symbolically, and the permissive "keep unless
  decidably non-zero" rule keeps it).
- **Scope / declines.** The `x^(1−b)`/`x^(1−c)` second solution is emitted only
  when the exponent parameter (`b` resp. `c`) is a **non-integer number**: an
  integer makes the two solutions dependent (or the pFq lower parameter singular),
  and a *symbolic* exponent makes the verify residual a symbolic-power + pFq sum
  on which `zero_test` currently hangs. Both cases decline to the Frobenius series
  fallback (no wrong answer). The other parameters (`a` for Kummer; `a, b` for
  Gauss) may stay symbolic. The first cut also requires the canonical singular
  points (0 for Kummer; 0 and 1 for Gauss); affine/scaled variants decline.
- **Tests.** `tests/test_dsolve.c` adds pinned + auto-cascade + symbolic-`a`
  (Kummer) / symbolic-`a,b` (Gauss) + integer-decline cases;
  `tests/test_dsolve_m5_stress.c` adds forward-generator families over
  half-integer exponents (all back-substitute to zero). Leak-clean (the recognizer
  and its quadratic-root helper add no allocations; valgrind shows only the
  pre-existing Simplify/engine baseline).

## DSolve — Lagrange singular solutions

`DSolve\`Lagrange` now returns the **singular-line solutions** of
`y = x·φ(y') + ψ(y')` under `IncludeSingularSolutions -> True`. These are the
straight lines `y = p₀·x + ψ(p₀)` for each root `p₀` of the envelope condition
`φ(p) = p` (mirroring `DSolve\`Clairaut`), emitted as explicit branches alongside
the parametric general branch:

```
In[1]:= DSolve[y[x] == x (y'[x])^2 + (y'[x])^3, y, x, IncludeSingularSolutions -> True]
Out[1]= {{x -> Function[{t}, …], y -> Function[{t}, …]},   (* general, parametric *)
         {y -> Function[{x}, 0]}, {y -> Function[{x}, 1 + x]}}   (* singular lines *)
```

- **Heterogeneous output** — a branch is either the parametric pair or an explicit
  `{y -> Function[{x}, line]}`. `dsolve_lagrange_try` emits singular lines in a new
  `DSolve\`Explicit[body]` wrapper (`Yexpr /. p → p₀`); `dsolve_run_parametric`
  branches on the wrapper head — `DSolve\`Param` verifies/assembles parametric,
  `DSolve\`Explicit` verifies as a scalar `y(x)` (`dsolve_verify_body`) and
  assembles `{y -> Function[{x}, body]}` via the new `dsolve_assemble_scalar_branch`.
- Test `t_lagrange_singular` (`tests/test_dsolve.c`): the general branch plus both
  singular lines are returned and each satisfies the ODE; the default (no option)
  still returns the general branch only.

## DSolve — Chini + Abel (1a), implicit first integrals

`DSolve` now solves the Chini equation `y' == f(x) y^n + g(x) y + h(x)`
(n∉{0,1,2}; n=2 is Riccati) and the first-kind Abel equation
`y' == f3 y^3 + f2 y^2 + f1 y + f0` — the last `[ ]` recognizers in §1a of
`DSOLVE_PLAN.md`. This closes the first-order family (bar the deferred
Lagrange singular/IVP work).

General Abel/Chini equations have no closed form; the **reducible-to-autonomous**
sub-class does. The scaling `y = φ·u` with `φ = f^(−1/(n−1))` makes the `y^n`
coefficient 1, giving `u' = u^n + B u + C` with `B = g + f'/((n−1)f)`,
`C = h·f^(1/(n−1))`; when **B, C are free of x** the equation is autonomous, and
since `1/(u^n+Bu+C)` is a rational function of u its antiderivative is elementary.
The solution is the **implicit first integral**

```
∫ du/(u^n + B u + C) − x == C[1],   u = y·f^(1/(n−1)),
```

returned through `dsolve_run_implicit` as `{{G(x,y[x]) == C[1]}}`. Back-substituting
`y' = −G_x/G_y` reproduces the ODE exactly. **Abel** reduces to Chini n=3 by
removing the y² term (`z = y + f2/(3 f3)`), so it is a thin front-end over the
shared reduction.

```
In[1]:= DSolve[y'[x] == x^2 y[x]^3 - y[x]/x + 1/x, y, x]
Out[1]= {{-x + ArcTan[(-1 + 2 x y[x])/Sqrt[3]]/Sqrt[3]
          - 1/6 Log[1 + x^2 y[x]^2 - x y[x]] + 1/3 Log[1 + x y[x]] == C[1]}}
```

- **New files** `src/calculus/dsolve_chini.c` (shared non-static
  `dsolve_chini_first_integral`, Bernoulli-style extraction of `f,g,h,n` with a
  reconstruct-and-reject of any non-`{y^n,y,1}` RHS, decline of n∈{0,1,2}) and
  `src/calculus/dsolve_abel.c` (Taylor-style cubic extraction `f0..f3`, require
  f3≠0 ∧ f2≠0, remove y², call the shared helper with `z = y[x] + f2/(3 f3)`). Both
  wired via `dsolve_method_builtin_implicit`.
- **Cascade slot** (`dsolve.c`): after `Riccati` (n=2), via `dsolve_run_implicit`.
  Pinned `Method -> "Chini"` / `"Abel"`. Earlier methods still claim their forms
  (Bernoulli/separable for the h=0 / autonomous cases).
- **Note:** the assembled G is *not* `Simplify`'d — `Simplify` hangs on a composed
  `Log`/`ArcTan` with radical arguments (`Sqrt[x]·(y+1)`), and the relation is
  correct unsimplified (the implicit verifier differentiates it).
- **Tests:** `t_method_chini` / `t_chini_more` (n=3,4; radical reduction; decline
  boundaries) / `t_method_abel` in `tests/test_dsolve.c`, verified by implicit
  differentiation; a `chini_ok(f,n,B,C)` forward generator (reducible by
  construction) + an Abel case driving `t_stress_chini` in
  `tests/test_dsolve_stress.c`.

Coverage is the reducible-to-autonomous class (B,C free of x); non-reducible
equations decline (honest — they generally have no closed form). The fuller
constant-invariant class (with an x-rescaling) is future work. Gates: 3/3 dsolve
ctest targets green; `make check-c99` clean; valgrind shows **no per-call leak**
(1× and 6× both = 13,440 + 6,312 bytes, the one-time engine baseline).

## DSolve — Lagrange / d'Alembert (1a), parametric general solution

`DSolve` now solves the Lagrange (d'Alembert) equation
`y == x·φ(y') + ψ(y')` (with `φ(y') ≠ y'`, the Clairaut case) — the last cheap
first-order recognizer in §1a. Its general solution is **intrinsically
parametric**: with the slope `p = y'` as the parameter `t`,

```
x = X(t, C),   y = X(t, C)·φ(t) + ψ(t),
```

where `X(t)` solves the linear first-order ODE obtained by differentiating the
equation w.r.t. `x` and reading `x` as a function of `p`:
`dx/dt − [φ'(t)/(t−φ(t))]·x = ψ'(t)/(t−φ(t))`. The integrating factor almost
always introduces transcendental/fractional terms, so there is generically no
explicit `y(x)` — hence a new parametric output shape.

```
In[1]:= DSolve[y[x] == 2 x y'[x] + (y'[x])^2, y, x]
Out[1]= {{x -> Function[{t}, (C[1] - 2/3 t^3)/t^2],
          y -> Function[{t}, (2 C[1] - 1/3 t^3)/t]}}
```

- **New parametric substrate path** (`dsolve_common.{c,h}`), mirroring the
  implicit path: `dsolve_run_parametric` + `dsolve_verify_parametric` +
  `dsolve_assemble_parametric` + `dsolve_method_builtin_parametric`. The try-fn
  returns the branch as the wrapper `DSolve\`Param[X, Y, t]`; verification
  substitutes `x→X`, `y[x]→Y`, `y'[x]→D[Y,t]/D[X,t]` into the residual and requires
  it not be decidably non-zero (permissive, with a `PossibleZeroQ` fallback for
  transcendental `X,Y` — same policy as the implicit/Bessel cases). Output is
  `{{x -> Function[{t}, X], y -> Function[{t}, Y]}}`. An IVP (`ncond > 0`) is
  **declined** rather than silently ignoring the condition (parametric fitting is
  future work). The parameter `t` is a collision-safe bare symbol (first of
  `{t,s,u,w,r,q}` not in the equation).
- **New file** `src/calculus/dsolve_lagrange.c`. Recognition mirrors
  `dsolve_clairaut.c` (solve the algebraic residual for `Yexpr`, then
  `φ = D[Yexpr,x]` free of `x`, `ψ = Yexpr − x·φ` free of `x`/`Y`); declines the
  Clairaut case `φ≡p` and — new guard — a genuinely **linear** equation
  (`φ` constant and `ψ` affine in `p`, owned by `LinearFirstOrder`). The linear ODE
  for `X(t)` is solved with the existing `dsolve_linear_factor_solve` (declines on a
  non-elementary integral); `Y = X·φ + ψ`.
- **Cascade slot** (`dsolve.c`): right after `Clairaut` (its `φ≡p` special case,
  which claims first), via `dsolve_run_parametric`. Pinned `Method -> "Lagrange"` /
  `DSolve\`Lagrange`. Over-claiming is prevented by the `φ,ψ`-free-of-`x` guard plus
  cascade order (all cheaper first-order methods precede it).
- **Tests:** `t_method_lagrange` / `t_lagrange_more` (rational + transcendental
  forms + automatic dispatch) / `t_lagrange_declines` (Clairaut, linear, and the
  deferred-IVP boundaries) in `tests/test_dsolve.c`, verified parametrically
  (`y' = Y'(t)/X'(t)`); a `lagrange_ok` forward generator (`φ=2p`, `3p/2` with
  polynomial `ψ`) driving `t_stress_lagrange` in `tests/test_dsolve_stress.c`.

Gates: 3/3 dsolve ctest targets green; `make check-c99` clean; valgrind shows **no
per-call leak** on the parametric path (1× and 6× the solve both = 13,440 bytes
definitely + 6,312 indirectly, the one-time engine baseline). This closes the
Lagrange item in §1a (singular solutions + parametric IVP-fitting remain future).

## DSolve — Riccati (1a)

`DSolve` now solves the Riccati equation `y'[x] == q0(x) + q1(x) y + q2(x) y^2`
(`q2 ≠ 0`), completing the named first-order family (§1a of `DSOLVE_PLAN.md`) bar
Lagrange/Abel/Chini. The method reuses the M5 2nd-order linear engine almost
entirely: the classical substitution `y = -u'/(q2 u)` linearises the equation to

```
u'' - (q1 + q2'/q2) u' + (q0 q2) u == 0,
```

which is handed back to the scalar cascade (const-coeff / Euler / Airy-Bessel
`SpecialFunctionForm` / Kovacic / — last — a Frobenius series). The recovered `u`
is mapped back through `y = -u'/(q2 u)`. Because the general Riccati solution
depends only on the ratio `C[1]:C[2]`, `C[2]` is collapsed to 1, leaving the single
arbitrary constant `C[1]` (the standard one-parameter parametrisation). When the
linearisation has no closed form the recursion declines and Riccati declines — the
substrate's back-substitution verify is the backstop (permissive: an undecidable
special-function residual is kept, as for Bessel/Kovacic).

```
In[1]:= DSolve[y'[x] == y[x]^2 + x, y, x]              (* linearises to the Airy eqn *)
Out[1]= {{y -> Function[{x}, -((-1)^(1/3) (AiryBiPrime[(-1)^(1/3) x]
          + C[1] AiryAiPrime[(-1)^(1/3) x]))/(AiryBi[(-1)^(1/3) x]
          + C[1] AiryAi[(-1)^(1/3) x]))]}}
In[2]:= DSolve[y'[x] == 2 - 3 y[x] + y[x]^2, y[x], x]
Out[2]= {{y[x] -> -3/2 + 1/2 Tanh[1/24 (-C[1] - 12 x)]}}
```

- **New file** `src/calculus/dsolve_riccati.c` (three-function contract:
  `dsolve_riccati_try` + `builtin_dsolve_riccati` via `dsolve_method_builtin` +
  `dsolve_riccati_init`, `ATTR_PROTECTED` + docstring). Mirrors
  `dsolve_bernoulli.c` (nonlinear-coefficient extraction: `q0 = FY|_{Y=0}`,
  `q1 = FY_Y|_{Y=0}`, `q2 = FY_YY/2`, with a reconstruct-check that rejects any
  non-quadratic nonlinearity and a `q2 ≠ 0` guard so a linear equation is left to
  the earlier methods) and `dsolve_reduce_order.c` (recurse into the scalar engine
  by building `DSolve[u''…==0, u[x], x]`, evaluating, and extracting the body).
- **Cascade slot** (`dsolve.c`): after `FirstOrderSubstitution`, before
  `AutonomousReduction`, so cheaper/cleaner first-order methods claim their forms
  first — notably `fos`, which keeps its clean `-x-Tan[…]` for `y'==(a x+b y+c)^2`
  (also a Riccati, but with an uglier linearisation). Also a pinned
  `Method -> "Riccati"` / `DSolve\`Riccati` entry.
- **Tests:** `t_method_riccati` / `t_riccati_more` (incl. the Airy-linearised
  `y'==y²+x`, the variable-coefficient `y'==x+x y²`, and the linear-declines
  boundary) / `t_ivp_riccati` in `tests/test_dsolve.c`; a `riccati_ok` from-spectrum
  forward generator (`y' == r1 r2 + (r1+r2) y + y²`, elementary/decidable) driving
  `t_stress_riccati` in `tests/test_dsolve_stress.c`.

Gates: 3/3 dsolve ctest targets green; `make check-c99` clean; valgrind shows **no
per-call leak** on the Riccati path (1× and 6× the elementary solve both =
13,440 bytes definitely + 6,312 indirectly, the one-time engine baseline).

## DSolve — implicit first-integral solutions (transcendental homogeneous)

The transcendental homogeneous family — `y'==F(y/x)` whose separable integral is
non-invertible (an ArcTan log-spiral, e.g. `y'==(x+y)/(x-y)`) — previously
declined because DSolve only produced explicit `y[x] -> body` solutions. It now
returns the **implicit first integral** as the solution branch:

```
In[1]:= DSolve[y'[x] == (x + y[x])/(x - y[x]), y, x]
Out[1]= {{-Log[x] + ArcTan[y[x]/x] - 1/2 Log[1 + y[x]^2/x^2] == C[1]}}
```

- **New parallel substrate path** (`dsolve_common.c`): `dsolve_run_implicit`
  (+ `dsolve_method_builtin_implicit`). A try-function on this path returns the
  left-hand side `G` of the general integral `G == C[1]`. Verification is by
  **implicit differentiation**: from `d/dx[G == C] = 0` the ODE forces
  `y' == -G_x/G_y`; substituting that into the residual and requiring it not be
  decidably non-zero (`dsolve_verify_implicit`, the same permissive policy as the
  explicit `dsolve_verify_body`). An initial condition `y[x0]==y0` fits the
  constant as `G(x0,y0)` (`dsolve_implicit_rhs`). Output is
  `{{ G(x,y[x]) == C[1] }}` — an `Equal` branch, not a `y[x] ->` rule.
- **`dsolve_homogeneous_implicit_try`** (`dsolve_homogeneous.c`) builds
  `G = (Integrate[1/(F(v)-v), v] /. v -> y[x]/x) - Log[x]`. It runs *after* the
  explicit Homogeneous method (explicit `y[x] -> …` is preferred whenever the
  inversion exists), both in the automatic cascade (a late fallback, before the
  series methods) and as the pinned `DSolve`Homogeneous` fallback.
- Because the branch is an equation, it is verified in tests by implicit
  differentiation (`D[eq[[1]]-eq[[2]], x] /. y'[x] -> rhs` must vanish), not by
  the `residual /. rule` idiom. New `t_homogeneous_implicit` (unit, incl. IVP fit
  + pinned) and `t_stress_homogeneous_implicit` (five transcendental forms).

Gates: 3/3 dsolve ctest targets green; `make check-c99` clean; valgrind shows no
per-call leak on the implicit path (1× and 6× the transcendental solve both =
13,440 bytes definitely + 6,312 indirectly, the one-time engine baseline). This
closes the last honest Homogeneous gap flagged in `DSOLVE_PLAN.md`.

## DSolve — Homogeneous & ReductionOfOrder: two decline gaps closed

Two first-order/second-order methods declined on whole families they should
handle; both are now solved, verified by back-substitution.

- **`DSolve`Homogeneous`** now inverts the pure-log (real-root) rational family.
  The separable relation `Integrate[1/(F(v)-v), v] == Log[x] + C[1]` was solved
  only when `Solve` could invert the log form directly; for a sum of logs it
  could not (`y'==(x+2y)/(2x+y)` declined). New fallback `homog_exp_log_invert`
  (`dsolve_homogeneous.c`): exponentiate the antiderivative
  (`E^intV //. {E^(a+b):>E^a E^b, E^(c Log[g]):>g^c}`) to the algebraic relation
  `Prod g_i(v)^{c_i} == C[1] x`, clear fractional exponents by raising to a small
  power `d ∈ {1,2,3,4,6}` (`PowerExpand`), then `Solve` — which returns explicit
  `Root` branches. The per-branch verify in `dsolve_run` keeps the genuine sheets
  and drops any spurious root from the exponentiation. The transcendental (ArcTan)
  subset (`y'==(x+y)/(x-y)`, a log-spiral) has no explicit inverse and still
  declines. Now solves `(x+2y)/(2x+y)`, `(2x+y)/(x+2y)`, `(x+3y)/(3x+y)`, ….
- **`DSolve`ReductionOfOrder`** now accepts a correct-but-unsimplified
  antiderivative. The `D[Integrate[p,x], x] == p` guard used `zero_test_decide`,
  which cannot reduce e.g. the multi-`Log` form of `Integrate[Tan[x+C[1]]]` or
  `1/(C[1](1+x^2/C[1]))` from `Integrate[1/(C[1]+x^2)]` to zero, so
  `y''==1+(y')^2` and `y''==-2x(y')^2` declined even though the first-order
  sub-solve succeeded. The guard now falls back to `PossibleZeroQ` (numeric
  sampling, as the derivative-divides integrator gates its own antiderivatives); a
  genuinely wrong antiderivative (`Integrate -> 0`) still fails as `-p != 0`, and
  the final back-substitution verify is the backstop. Opens the autonomous
  `a+b(y')^2` (→ Tan/Tanh) and Riccati-in-`p` `c x (y')^2` families.

Tests: new unit cases `t_homogeneous_algebraic` / `t_reduce_order_riccati`
(`tests/test_dsolve.c`) and broadened stress families (the algebraic
rational-homogeneous set + a `t_stress_reduce_order_riccati` family) in
`tests/test_dsolve_stress.c`. Gates: 3/3 dsolve ctest targets green,

solve both = 13,440 bytes, the one-time engine baseline).

## ReadProtected attribute removed system-wide

Mathilda is fully open source and never hides a symbol's definition, so the
`ReadProtected` attribute has been removed entirely. The flag
(`ATTR_READPROTECTED`, bit 11 of `attr.h`) is gone, `SetAttributes`/`Attributes`
no longer recognise or emit `ReadProtected` (`attr.c`, `SYM_ReadProtected`
dropped from `sym_names`), and it has been stripped from every builtin that set
it (~75 modules) and from the two `.m` tables (`IntegrateTable`,
`Integrate`CRCTable`). `Attributes[f]` for the affected heads now reads e.g.
`{Listable, NumericFunction, Protected}` (Beta, AiryAi, …), `{Protected}`
(DSolve, D, Dt, Limit, Integrate, Area, …), `{Listable, Protected}` (NextPrime).
Tests that asserted `ReadProtected` were updated; docs/reference pages refreshed
(historical changelogs left as-is).

## DSolve — no longer HoldAll

`DSolve` (and every `DSolve`<Method>`) dropped `HoldAll`; attributes are now
`Protected`, matching Mathematica. HoldAll was unnecessary — with
the dependent function undefined, `y'[x] == a Sin[x]` and point conditions
`y[0] == 5` evaluate to unevaluated `Equal[...]` on their own, so equations reach
the solver formal without holding, and the `D[...]`→`Derivative[...]` fold happens
under normal evaluation. It was also harmful: HoldAll made an equation stored in a
variable (`eq = y'[x] + y[x] == a Sin[x]; DSolve[eq, y, x]`) come through as the
bare symbol `eq` and decline; that now solves. Guarded by `t_not_holdall`.

## DSolve — FirstOrderSubstitution (1a) and AutonomousReduction (1d)

Two new methods extend the `DSolve` cascade (`DSOLVE_PLAN.md`), each producing
general solutions the substrate verifies by back-substitution.

### `DSolve`FirstOrderSubstitution` — `y'[x] == F(a x + b y + c)`

The solved-for-`y'` companion to `Homogeneous`: fires when the RHS depends on
`x` and `y` only through one linear combination — a form no earlier first-order
method (linear / separable / homogeneous / exact) recognises. Writing the RHS as
`F(x, Y)` (`Y` a plain symbol for `y[x]`), the level curves are the straight
lines of constant combination, so `F` is a function of that combination iff the
ratio `r = F_x / F_y` is constant. With `v = y + r x`,

```
v' = y' + r = F + r = H(v) + r,   H(W) := F(x, W - r x)  (free of x),
```

an autonomous separable equation solved inline by `Integrate[1/(r + H), W] == x
+ C[1]`, solved for `W = v`, then `y = v - r x`. The ratio is collapsed with
`Simplify` before the substitution (it must be textually free of `Y`), so a
proved-constant ratio that `Simplify` cannot reduce is declined rather than
corrupted.

```
In[1]:= DSolve[y'[x] == (x + y[x])^2, y[x], x]
Out[1]= {{y[x] -> -x - Tan[-C[1] - x]}}

In[2]:= DSolve[y'[x] == (2 y[x] - x)^2, y[x], x]        (* combination 2y - x, r = -1/2 *)
Out[2]= {{y[x] -> x/2 - Tanh[Sqrt[2] (C[1] + x)]/(2 Sqrt[2])}}
```

Cases whose separated antiderivative `Solve` cannot invert (e.g.
`y' == Sqrt[x+y]`, `y' == (x+2y)^3`) stay symbolic rather than shipping an
implicit/wrong answer.

### `DSolve`AutonomousReduction` — `y''[x] == f(y, y')` missing `x`

The nonlinear-higher-order case where `x` is absent. Regarding `p = y'` as a
function of `y`, `y'' = p p'(y)`, so the equation becomes the first-order ODE
`p p'(y) == f(y, p)`, solved by recursing into the scalar cascade; then
`y' == P(y)` (also autonomous, hence separable) is solved by a second recursion.
The two integration constants are kept distinct across the recursions (the first
stage's `C[1]` is frozen to a private marker and renamed `C[2]` afterward). A
degenerate `y = const` — which trivially satisfies any autonomous equation and
would pass back-substitution (cf. the M4 wrong-`Integrate` lesson) — is rejected
by requiring the final body to depend on `x`.

Runs after the linear methods, so genuinely linear autonomous equations
(`y'' == -y`, …) are claimed by the cleaner method first; this one catches the
nonlinear remainder:

```
In[3]:= DSolve[y[x] y''[x] == y'[x]^2, y[x], x]
Out[3]= {{y[x] -> C[1] E^(C[2] x)}}

In[4]:= DSolve[y[x] y''[x] == 2 y'[x]^2, y[x], x]
Out[4]= {{y[x] -> 1/(C[1] - C[2] x)}}
```

Non-elementary / elliptic reductions (`y'' == 2 y^3`, `y'' == -Sin[y]`) stay
symbolic.

### Substrate / cascade

Both methods follow the three-function contract (`_try` + `builtin_` via
`dsolve_method_builtin` + `_init`) with `ATTR_PROTECTED` and
docstrings; appended to the automatic cascade after
`ReductionOfOrder` and to the `Method ->` dispatch, callable as
`DSolve`FirstOrderSubstitution[...]` / `DSolve`AutonomousReduction[...]`.

Tests (`tests/test_dsolve.c`): per-method unit cases (specific closed forms,
named-method entry, and decline-stays-symbolic boundaries) plus randomized
stress families back-substitution-verified — `k (a x + a y + c)^2` /
`(m x + y)^2` for FirstOrderSubstitution, `a y y'' == b (y')^2` for
AutonomousReduction. Gates: `dsolve_tests` green, `make check-c99` clean,
valgrind shows no leak delta over a baseline running the same sub-engines.

## DSolve — general linear systems (M8): defective / singular / triangular

`DSolve` now solves coupled first-order linear systems in full generality, closing
`DSolve[{y'[t] + 1 == 1, x'[t] + y[t] == 0}, {y[t], x[t]}, t]`, which previously
returned unevaluated because its matrix `A = {{0,0},{-1,0}}` is **defective** (one
Jordan block, eigenvalue 0 doubled) **and** singular — the old eigen-only
`LinearFirstOrderSystem` declined on the zero eigenvector, and `DecoupleSystem`
declined because the second equation mentions two functions.

- **`LinearFirstOrderSystem` reworked around the fundamental matrix** `Φ = e^{Ax}`
  for *any* constant `A` (`dsolve_linsys.c`). `Φ = S · e^{Jx} · S^{-1}` from
  `JordanDecomposition[A]`, with `e^{Jx} = e^{Dx} · e^{Nx}`, `e^{Dx} =
  DiagonalMatrix[Exp[λ_i x]]`, and `e^{Nx} = Σ_{m<n} N^m x^m/m!` (finite — `N`
  nilpotent). Homogeneous `Y = Φ · {C[1..n]}`; forcing `b(x)` by variation of
  parameters `Φ·(C + ∫Φ^{-1} b dx)`, which subsumes the old `-A^{-1}b` and stays
  valid when `A` is singular. Complex spectra collapse to real `e^{αx}Cos/Sin[βx]`;
  a repeated real eigenvalue's `Simplify`-preferred `(Cosh+Sinh)^2` is folded back
  to `E^{λx}` by a `Cosh[a]+Sinh[a] -> E^a` rewrite. Symbolic `MatrixExp` is inert,
  so `Φ` is built from Jordan directly.
- **New `DSolve`TriangularSystem`** (`dsolve_triangular.c`): forward substitution
  over a DAG dependency graph — peel an equation isolating one unsolved function,
  solve it with the scalar engine, substitute forward, renumber. Reaches
  coupled-but-triangular systems at **any** coefficient (constant or variable,
  e.g. `{y'==y/x, z'==y}`) that the constant-`A` matrix exponential cannot. Solved
  constants are parked in the private head `DSolve`sysK` during the peel so they do
  not collide with the scalar engine's fresh `C[k]`, then remapped to a contiguous
  `C[1..]` at the end.
- Cascade for `nfun>1` is now `DecoupleSystem → TriangularSystem →
  LinearFirstOrderSystem`. Shared `dsolve_renumber_constants` /
  `dsolve_extract_system_body` factored into `dsolve_common.c` (used by both
  system methods). The only remaining systems gap is genuinely coupled,
  non-triangular, *variable*-coefficient `A` (Floquet/Magnus — future).

Tests (`tests/test_dsolve.c`): `t_sys_defective_singular`,
`t_sys_defective_nontriangular`, `t_sys_triangular_varcoeff`,
`t_sys_singular_forcing`, `t_sys_triangular_ivp` — Head-is-`List` (non-vacuous)
plus back-substitution to zero. Gates: `dsolve_tests` green, `make check-c99`
clean, valgrind shows no definitely-lost delta over the scalar-DSolve baseline.

## DSolve — M5: 2nd-order linear variable-coefficient (NormalForm + Kovacic + Frobenius/PowerSeries)

Second-order linear ODEs `y'' + P(x) y' + Q(x) y == 0` now have closed-form and
series solvers, closing the gap where only `SpecialFunctionForm` (Airy/Bessel)
applied. Three new files, all wired into the scalar cascade in `dsolve.c`.

- **`DSolve`NormalForm`** (`dsolve_normalform.c` + substrate helpers
  `dsolve_second_order_PQ` / `dsolve_normal_form` in `dsolve_common.c`).
  `DSolve`NormalForm[eqn, y, x]` returns `{r, w}`: the substitution `y == w z`
  with `w == Exp[-Integrate[P/2]]` reduces the equation to `z'' == r z`,
  `r == P²/4 + P'/2 − Q`. The `∫P/2` integral is guarded (`D[∫] == P/2`).
  `dsolve_second_order_PQ` (the normalized `P = c₁/c₂`, `Q = c₀/c₂` extractor)
  is now the single source of truth, reused by `SpecialFunctionForm` too.

- **`DSolve`Kovacic`** (`dsolve_kovacic.c`) — Liouvillian solutions of
  `z'' == r z` (`r ∈ C(x)`, gated by `PolynomialQ`). Built on a
  mathematically-transparent **Riccati/undetermined-coefficient** search rather
  than the classical exponent tables (elementary answers are back-substitution
  verified, so a wrong candidate is dropped, never shipped):
  - **Case 1** — `ω' + ω² == r` with `ω` a polynomial part (degree from the
    order of `r` at ∞) plus a principal part over the irreducible factors of the
    denominator; `Solve` the coefficient system, `z1 == Exp[∫ω]`,
    `z2 == z1 ∫ 1/z1²`. Solves `z''=(1+x²)z → Exp[x²/2]`, `z''=(2/x²)z → x², 1/x`.
  - **Case 1b (apparent singularities)** — for polynomial `r`, `z == P Exp[∫ω_base]`
    with `ω_base` the polynomial part of `±√r` and `P` a polynomial of the
    determined degree `d = −[R₂]_{m−1}/(2c_m)` solving `P''+2ω_base P'+R₂P == 0`.
    Captures e.g. `z''=(x²+3)z → x Exp[x²/2]` (root of `P` at a point that is not
    a pole of `r`).
  - **Case 2 (degree-2 algebraic)** — a rational `σ = ω₁+ω₂` solving
    `D'+2σD == 0`, `D = 4r−2σ'−σ²`, gives `ω = (σ ± √D)/2`. Because the residual
    is not symbolically decidable, each candidate is **numerically**
    back-substituted (both basis solutions, several points) before it is returned.
    Solves `z''=(x/4+5/(16x²))z → x^(−1/4) Exp[±x^(3/2)/3]`.
  - **Case 3** (degree 4/6/12) declines. Cascade slot: after `SpecialFunctionForm`,
    before `ReductionOfOrder` (closed form preferred over reduction/series).

- **`DSolve`FrobeniusSeries` / `DSolve`PowerSeries`** (`dsolve_frobenius.c`) — the
  always-available series fallback, tried **last** in the cascade, expanding about
  `x == 0`. Ordinary point → two power series (recurrence
  `a_{n+2} = −[Σ p_k(n−k+1)a_{n−k+1} + Σ q_k a_{n−k}]/((n+2)(n+1))`); regular
  singular → Frobenius `x^s Σ a_n x^n` with the indicial quadratic
  `s(s−1)+p₀s+q₀ == 0` (reusing `dsolve_analyze_roots`), the root difference
  selecting the sub-case (non-integer → two series; equal roots → a `Log`
  solution via `∂/∂s`; obstructed positive-integer difference declines). Output is
  a truncated `SeriesData`; the `x^r` factor is carried by `x^r · SeriesData` so
  the O-term makes the back-substituted residual `O[x]^k` (which is why the
  solution verifies rather than being dropped).

**Substrate change:** `dsolve_verify_body` now back-substitutes each derivative
term as `Derivative[k][y][x] → D[body, {x,k}]` (and `y[x] → body`) directly,
instead of `y → Function[{x}, body]`. This is equivalent for elementary bodies
but essential for a `SeriesData` body, whose pure-function derivative
`Derivative[k][Function[{x}, SeriesData]][x]` the evaluator returns as `0` (a
pre-existing limitation), which would otherwise drop every valid series solution.

**Tests:** 14 new unit tests in `tests/test_dsolve.c` and a new
`tests/test_dsolve_m5_stress.c` (ctest-registered) — a Kovacic forward generator
(pick `ω`, feed `r = ω'+ω²`, so a Liouvillian solution is guaranteed) across
polynomial / apparent-singularity / genuine-pole / Euler families, plus a
Frobenius ordinary-point family; each asserts `Head === List` then a
back-substitution to zero (or `O[x]^k` for series). Gates: `dsolve_tests` and
`dsolve_m5_stress_tests` green, `make check-c99` clean, valgrind shows no
definitely-lost delta over the Integrate/Solve/Simplify engine baseline.
