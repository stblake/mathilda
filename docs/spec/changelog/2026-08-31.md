# Changelog: week of 2026-08-31 (Mon) – 2026-09-06 (Sun)

## DSolve — M6 (Phase 2): heat-equation Cauchy problem by the heat kernel

`DSolve`HeatKernel` (`src/calculus/dsolve_heat.c`) — the Cauchy (initial-value)
problem for the one-dimensional heat equation on the whole line,

    u_t == k u_xx,  u(x, t0) == f(x)
      ->  u(x,t) = 1/Sqrt[4 π k τ] Integrate[f(K) Exp[-(x-K)^2/(4 k τ)],
                                             {K, -∞, ∞}],   τ = t - t0.

Solved automatically by `DSolve` (new route in the `is_pde` cascade, `neq == 2`:
PDE + one initial condition) and via the pinned builtin. Reuses the wave IVP's
condition-sorting approach — the single initial condition `u[x,t0] == f[x]` is a
two-argument point condition the shared parser does not split off, so it arrives as
an ordinary equation and the method identifies the PDE, the condition, the wave/heat
variables (fixed = time, free = space), and the diffusivity `k` itself (requiring
`k > 0`; declining backward-heat, second-order-in-time, advection `u_x`, and reaction
`u` equations).

**The Gaussian convolution is nonelementary** — Mathilda cannot evaluate the
improper `Integrate[f(K) Exp[…], {K, -∞, ∞}]` (and `Simplify` on it hangs), so the
solution is returned as the *unevaluated* heat-kernel integral (matching Mathematica
for a general `f`). The integral node is built WITHOUT attempting integration (the
`Function` body holds it), which sidesteps the hang. Verification is therefore at
the KERNEL level: the heat kernel `G = 1/Sqrt[4 π k τ] Exp[-(x-K)^2/(4 k τ)]` is a
decidable Gaussian, and `D[G,t] - k D[G,{x,2}] == 0` is required (which confirms `k`
was read correctly); the convolution solves the PDE because `G` does (differentiation
under the integral, constant infinite limits), and the initial condition holds by the
kernel's convergence to `δ(x-K)` as `τ → 0+` (a distributional limit, not a
back-substitution) — the honest structural-correctness policy, as with the inert
special-function heads.

Unit tests `t_heat_kernel` (auto + pinned solve and carry the convolution; the kernel
solves the PDE; declines). All three DSolve ctest suites + `make check-c99` green;
valgrind sits exactly at the documented DSolve baseline — `dsolve_heat.c` is fully
leak-clean (the raw-Integrate build avoids even the per-call `Integrate`-engine leak).
First cut: pure heat, constant positive diffusivity, homogeneous — the Erf-producing
step/box data, advection–diffusion, reaction, and finite-interval Fourier-series
problems are future.

## DSolve — M6 (Phase 2): wave-equation IVP by d'Alembert's formula

`DSolve`WaveDAlembert` (`src/calculus/dsolve_wave.c`) — the initial-value problem
for the one-dimensional wave equation on the whole line,

    u_tt == c^2 u_xx,   u(x, t0) == f(x),   u_t(x, t0) == g(x)
      ->  u(x,t) = (f(x - c τ) + f(x + c τ))/2
                   + 1/(2 c) Integrate[g(K), {K, x - c τ, x + c τ}],   τ = t - t0.

Solved automatically by `DSolve` (new route in the `is_pde` cascade) and via the
pinned builtin. The velocity integral is kept unevaluated for an undefined `g`
(clean dummy `K`, collision-guarded). Zero initial velocity drops the integral;
zero initial displacement drops the wave term; concrete data evaluates fully
(`u_t == u_xx`, `u(x,0)==Sin[x]`, `u_t(x,0)==0 -> (Sin[x-2t]+Sin[x+2t])/2`).

**Substrate note.** A PDE initial condition (`u[x,t0] == f[x]`, `Derivative[0,1][u]
[x,t0] == g[x]`) is a *two-argument* point condition that the shared parser's
`ds_is_condition` (single-variable funcapps only) does not split off, so it arrives
as an ordinary equation — a wave IVP reaches the solver as `neq == 3`. The method
therefore sorts the three equations itself (the one with a second-order derivative
is the PDE; the two carrying a u-funcapp at a fixed value of one variable are the
conditions — the fixed variable is *time*, the free one *space*), extracts each
condition's right-hand side sign-robustly, reads the wave speed from the
principal-part coefficients (rejecting parabolic/elliptic discriminants), and runs
its own multi-equation verify/assemble (not the single-equation `dsolve_run_pde`).
Verification rebuilds the solution with concrete test data `f == Cos`, `g == Sin`
(so the integral evaluates and is differentiable — the unevaluated integral of an
undefined `g` cannot be) and requires the PDE residual and both initial conditions
to reduce to zero. First cut: constant wave speed, principal part only, homogeneous
— inhomogeneous / half-line / `Piecewise` data are future.

Unit tests `t_wave_dalembert` (concrete `f`/`g` fully back-substitution verified;
undefined `f`/`g` checked at the displacement condition; auto + pinned; declines).
All three DSolve ctest suites + `make check-c99` green; valgrind leak-clean in
`dsolve_wave.c` itself (decline paths sit exactly at the documented DSolve baseline;
the solving paths inherit only the pre-existing per-call `Integrate`-engine leak,
as `LinearFirstOrder` / `AlmostLinear` do).

## DSolve — M6 (Phase 2): PDEClassify (discriminant classifier)

`PDEClassify[eqn, u, {v1, v2}]` (`src/calculus/dsolve_pdeclassify.c`) — a
standalone classifier for a second-order linear PDE by the discriminant
`Δ = B² − 4 A C` of its principal part `A u_{v1 v1} + B u_{v1 v2} + C u_{v2 v2}`
(only the highest-order terms determine the type): `"Hyperbolic"` (Δ>0, e.g. the
wave equation `u_tt == c² u_xx`), `"Parabolic"` (Δ=0, e.g. the heat equation
`u_t == u_xx`), `"Elliptic"` (Δ<0, e.g. Laplace `u_xx + u_yy == 0`). The
coefficients A, B, C are read from the second-order terms exactly as
`DSolve`PDELinearSecondOrder` reads them (reusing `dsolve_parse`); lower-order
terms are correctly ignored. A discriminant whose sign is not a decidable
constant — a mixed-type / parameter-dependent equation such as Tricomi's
`y u_xx + u_yy == 0` (Δ = −4y) — leaves the call unevaluated rather than
attaching a region-blind label. `PDEClassify` is a top-level `Protected` builtin
(not a solver, so outside the `DSolve\`` namespace). Unit tests `t_pdeclassify`;
all three DSolve ctest suites + `make check-c99` green.

## DSolve — M6 (Phase 2): second-order constant-coefficient linear PDE

`DSolve`PDELinearSecondOrder` (`src/calculus/dsolve_pde2.c`) — the first
second-order PDE method, solving the homogeneous, principal-part-only,
constant-coefficient equation `A u_{v1 v1} + B u_{v1 v2} + C u_{v2 v2} == 0` by
**operator factoring**. The trial `u == f(v2 + λ v1)` reduces it to the
characteristic quadratic `A λ² + B λ + C == 0`, so the principal operator
factors over ℂ and **one** method covers all three discriminant signs:

- **distinct real roots (hyperbolic)** → `u = C[1][v2+λ1 v1] + C[2][v2+λ2 v1]` —
  the **wave equation** `u_tt == c² u_xx → C[1][x - c t] + C[2][x + c t]`
  (d'Alembert);
- **complex conjugate roots (elliptic)** → the complex-characteristic form,
  e.g. Laplace `u_xx + u_yy == 0 → C[1][y - I x] + C[2][y + I x]` (matching
  Mathematica — no realification needed);
- **repeated root (parabolic)** → `u = C[1][w] + v1 C[2][w]`, `w = v2 + λ v1`.

Complex/repeated roots are handled uniformly by the existing
`dsolve_analyze_roots` (distinct roots with multiplicities). `A == 0` is handled
by swapping `v1 ↔ v2`; the pure mixed `B u_{v1 v2} == 0` gives `C[1][v1] +
C[2][v2]`. Every branch is back-substitution verified. This realizes the
`DSOLVE_PLAN.md` §2b `PDEHyperbolicGeneral` item in full generality — a separate
elliptic/parabolic method is unnecessary. First cut: homogeneous, principal-part
only; lower-order terms (telegraph/damped wave), inhomogeneous forcing, and the
wave-IVP d'Alembert formula are future work.

**Substrate:** the shared PDE verifier `dsolve_verify_pde` (`dsolve_common.c`)
was generalized from first-order/single-arbitrary-function to **arbitrary
derivative order** (scanned directly from the residual, since `max_order` is
never populated for PDEs — `ds_scan` only recognises single-index
`Derivative[m][u][x]`) and **multiple arbitrary functions** (`C[1..4]` replaced
by distinct concrete test functions `Sin/Cos/Exp/#²` so an error in one branch
cannot cancel against another). Backward compatible: the first-order PDE tests
are unchanged. Wired into the `is_pde` cascade after `PDELinearFirstOrder`;
pinned REPL builtin; unit tests (`t_pde2_*` in `tests/test_dsolve.c`). All three
DSolve ctest suites + `make check-c99` green; valgrind at the documented DSolve
baseline (no new leaks — the pde2 frames appear only in the pre-existing
`zero_test`/`numericalize` uninitialised-value contexts reached via
`dsolve_analyze_roots`).

## DSolve — M6 (Phase 2): separation of variables

`DSolve`SeparationOfVariables` (`src/calculus/dsolve_pdesep.c`) — a separated
product solution `u(v1, v2) == X(v1) Y(v2)` of a homogeneous, constant-coefficient
linear PDE with **no mixed derivative term**. Substituting the product and dividing
by `X Y` separates the equation into an x-only bracket and a y-only bracket, each
equal to the separation constant λ / −λ, giving two constant-coefficient ODEs:

- x-ODE: `Σ_i a_i X^(i) − λ X == 0`
- y-ODE: `Σ_j b_j Y^(j) + (e + λ) Y == 0`

Each is solved by recursing into the scalar DSolve cascade with λ a symbolic
parameter; λ then becomes a generated constant. The product of two homogeneous
families is over-parameterized by one overall scale, which is absorbed by fixing a
first-order side's lone constant to 1 (no loss of generality — the other side
already free-scales). The general solution is a superposition over λ (an
eigenfunction expansion under boundary conditions), so this returns the
**representative product mode** and is **pinned-only** — not in the automatic
cascade, matching `FirstOrderPowerSeries` / `EigenvalueProblem`.

Examples (back-substitution verified): the heat equation `u_t == u_xx` →
`E^(λ t)(C[1] E^(−√λ x) + C[2] E^(√λ x))`; the Helmholtz-type `u_xx + u_yy + u == 0`
→ a product of two second-order exponential families with λ = `C[5]`; a symbolic
diffusivity `u_t == k u_xx` carries `k` through. Declines mixed-derivative,
inhomogeneous, and non-constant-coefficient equations (and an ODE-in-disguise with
derivatives in only one variable). Unit tests `t_pdesep` in `tests/test_dsolve.c`.
All three DSolve ctest suites + `make check-c99` green; valgrind at the documented
DSolve baseline (no `dsolve_pdesep` frames in the report).

## DSolve — M11: finish Phase-1 ODE gaps (var-coeff systems, formal BVP, eigenvalues)

Three principled additions that close the remaining Phase-1 (ODE) gaps in
`DSOLVE_PLAN.md`, each verified by back-substitution and with extensive unit +
forward-generator stress tests.

- **Refactor: reusable fundamental-matrix machinery.** The constant-coefficient
  system solver's core is factored out of `dsolve_linsys.c` into a new
  `dsolve_linsys.h`: `dsolve_linsys_matexp` (the `e^{Mt}` Jordan builder, formerly
  file-static `mat_exp`), `dsolve_linsys_tidy` (the `Simplify[ComplexExpand[·]] //.
  {Cosh+Sinh->E}` realifier), `dsolve_linsys_extract_Ab` (the `Y'==A Y+b` extractor,
  now with the constant-`A` guard moved to each caller), and
  `dsolve_linsys_assemble(M, t, xvar, b, b_zero, n)` (Jordan → `Φ=e^{Mt}` →
  variation-of-parameters → tidy). `LinearFirstOrderSystem` output is unchanged. As a
  clean-up the realifier now applies `ComplexExpand` **only** when the body actually
  carries the imaginary unit — on an already-real body `ComplexExpand` would
  gratuitously split `Log[x] -> Log[Abs[x]] + I Arg[x]` (which arises in the new
  variable-coefficient forcing integral).

- **`DSolve`​`LinearSystemVarCoeff`** (`dsolve_linsys_varcoeff.c`) — genuinely-coupled,
  non-triangular, **variable-coefficient** systems `Y' == A(x) Y + b(x)` of the
  scalar-factor class `A(x) == f(x) B` (`B` constant). The substitution
  `t = Integrate[f, x]` reduces the system to `dY/dt == B Y`, so `Φ = e^{B t}` is the
  constant-coefficient fundamental matrix evaluated at `t` — computed by reusing
  `dsolve_linsys_assemble`. Detects `f` as any nonzero entry of `A`, requires
  `B = A/f` to be constant, and declines a non-elementary `∫f`. Cascade slot (for
  `nfun>1`): after `DecoupleSystem` / `TriangularSystem` / `LinearFirstOrderSystem`;
  declines a constant `A`. Solves e.g. `{y'==(2y+z)/x, z'==(y+2z)/x}` (→ `x`, `x³`
  modes) and `{y'==x z, z'==-x y}` (→ `Cos/Sin[x²/2]`), both previously declined;
  SymPy `dsolve` agrees on the solution space. Documented exempt: the wider
  commutative-antiderivative class (`[A,∫A]=0` but not scalar×constant) and the
  non-commuting Floquet/Magnus case (both need a symbolic `MatrixExp` of a variable
  matrix).

- **Formal Linear BVP soundness** (substrate, `dsolve_common.c`). An
  inconsistent / over-determined boundary-value problem such as
  `y''+y==0, y[0]==1, y[Pi]==1` used to silently return the *unfitted general
  solution* (constants still free); it now returns `{}` (no solution), matching
  Mathematica. The constant-fitters (`dsolve_fit_constants` / `dsolve_fit_system`)
  gained a `no_solution` out-parameter set when `Solve` proves the conditions
  inconsistent (an empty `{}` result); `dsolve_run` / `dsolve_run_system` return the
  concrete empty list `{}` (distinct from `NULL` = decline) when a verified general
  solution has no consistent fit. Undecided fits still keep the general solution, an
  under-determined BVP still returns the family with its free constant, and every
  0-condition / IVP method is untouched (the empty-`Solve` signal is the only new
  trigger).

- **`DSolve`​`EigenvalueProblem`** (`dsolve_eigenvalue.c`) — a pinned-only first-cut
  Sturm-Liouville solver for `y'' + λ y == 0` on `[a,b]` with two homogeneous BCs
  (Dirichlet `y==0`, Neumann `y'==0`, or mixed) at two distinct points. It detects the
  eigenparameter `λ` as the coefficient ratio `c0/c2` (a bare symbol), derives the
  spectrum analytically (`w_n = n Pi/(b-a)` for same-type BCs, `(2n-1)Pi/(2(b-a))` for
  mixed; eigenfunction `Sin` for Dirichlet-at-`a`, `Cos` for Neumann-at-`a`), and
  **verifies every eigenpair by back-substitution** (`TrigReduce` + `Simplify` under
  the integer-index assumption), so a mis-derivation can only decline. Output
  `{{λ -> ConditionalExpression[w_n², Element[C[1],Integers] && C[1]>=1],
  y -> Function[{x}, C[2] Sin/Cos[w_n(x-a)]]}}` with `C[1]` the integer index
  (matching Solve's `C[1]∈Integers` family convention) and `C[2]` the amplitude.
  Pinned-only, so it never misfires on an ordinary IVP/BVP call. Future: non-constant
  weight, Robin/periodic BCs, the `λ==0` Neumann mode, and `DEigensystem`/
  `DEigenvalues` surfaces.

Validation: `dsolve_tests` (new `t_sys_varcoeff_*`, `t_bvp_*`, `t_eig_*`),
`dsolve_stress_tests` (new `t_stress_linsys_varcoeff` forward-generator family), and
`dsolve_m5_stress_tests` all green; `make check-c99` clean; valgrind leak-clean (no new
leaks; total at the pre-existing macOS baseline). SymPy (`python3.11`) cross-validated
the coupled variable-coefficient systems.

## DSolve — M10 Lie `chi` heuristic + all methods REPL-callable

- **`chi` (Cheb-Terrab, Duarte & da Mota, CPC 101 1997, 5th algorithm).** The
  `η = ξω + χ` reformulation: since `S(ξ, ξω+χ) = S(0, χ)`, a `χ` solving the linear PDE
  `χ_x + ω χ_y − ω_y χ == 0` gives the symmetry `[0, χ]`. `χ` is found by a **rich-basis**
  ansatz — a polynomial (constant coeffs × a `{1,x,y}` factor) in the transcendental
  ATOMS of `ω` (`Sin/Cos`, `Sinh/Cosh`, `Log`, inverse trig) over their product `Dtrans`
  — substituted into the PDE, cleared (multiplying by a high power of every atom, which
  also folds `Csc/Cot/…` back to `Sin/Cos`), reduced modulo the Pythagorean relations,
  and split by `CoefficientList` → `NullSpace`. Candidates are integrated simplest-first
  (no `lie_check` — the null vectors are exact PDE solutions; the result is still
  back-substitution verified). This is the one heuristic whose `χ` may be a genuine
  transcendental beyond `bivariate`'s polynomial reach: Kamke ODE 357,
  `x y' ln(x) sin(y) + cos(y)(1 − x cos(y)) == 0`, now solves →
  `−x + Log[x] Sec[y[x]] == C[1]` (~1.2 s, verified). Because `chi` owns the trig case,
  the cascade now **skips the rational/algebraic classifiers** (`abaco1_product`,
  `function_sum`, `abaco2_similar`) when `ω` contains trig (they cannot solve it and are
  slow on it), and `abaco1_simple` uses the bounded `lie_ratsimp` in place of `Simplify`.
  New test `t_lie_chi`; valgrind leak-flat; `make check-c99` clean. The formal §4.4.2
  Case I/II (`abaco2_unique_general`) stays a documented exemption (impractical per the
  source; untestable non-vacuously). This completes the M10 heuristic table.

- **Every DSolve method is now REPL-callable with a docstring.** The four methods that
  had only automatic-dispatch coverage now have pinned `DSolve`<Name>[...]` builtins:
  `DSolve`DecoupleSystem`, `DSolve`TriangularSystem`, `DSolve`LinearFirstOrderSystem`
  (systems, via the new `dsolve_method_builtin_system`) and `DSolve`PDELinearFirstOrder`
  (via `dsolve_method_builtin_pde`), each `Protected` with a docstring. The top-level
  `DSolve` docstring is rewritten to catalog **all** methods by category. New test
  `t_sys_pde_pinned_methods`.

## DSolve — M10 Lie point-symmetry: `function_sum` (§4.2) + `abaco2_unique_unknown` (§4.4.1)

Two more Cheb-Terrab & Roche (1998) ansätze added to `DSolve`LieSymmetry`
(`dsolve_lie.c`), completing **L2** and opening **L3**'s `abaco2_unique` family. Both
plug into the existing `lie_check` (checkinfsol gate) + `lie_first_integral`
(integrating-factor quadrature) pipeline, so every branch back-substitutes to zero via
`dsolve_run_implicit` — no inert heads, a mis-derived candidate can only decline.

**`function_sum`** — the additive symmetry `[ξ = F(x) + G(y), η = 0]` and its inverse
`[0, F(x)+G(y)]` (the sum-analogue of `abaco1_product`; §4.2). The classifying quantity
is the **rational** factor `ω·∂²ₓ(1/ω) = F''/(F+G)` (Eq 27 — the leading `ω` cancels the
transcendental part of `1/ω`, which is generally Log/ArcTan). Its reciprocal's
`∂_y` is product-separable with x-factor `1/F''` (Eq 28), giving
`ξ = F+G = 1/(xfactor·factor)`; `F ≡ 0` marks the invert-linear case and declines.
Reuses `lie_sep_xfactor`/`lie_run_with_inverse`. Chained after `abaco1_product`.

**`abaco2_unique_unknown`** — the symmetries `[ξ=F(x), η=G(y)]` and `[ξ=G(y), η=F(x)]`,
found from the functions / non-integer powers of both variables present in `ω` (§4.4.1,
Prop 7). A recursive tree-walk `lie_collect_kernels` gathers each such mapping `M`
(a non-arithmetic function application, or a power with non-integer/variable exponent
that holds both `x` and `y`); for each, `R = M_y/M_x` (Eq 63, the chain-rule factor
cancels), and when `R` is product-separable with x-factor `X`, the two candidates of
scheme (iib) — `[X, −X/R]` and `[−R/X, 1/X]` — are gated and integrated. A purely
rational `ω` yields no kernels → instant decline. Chained after `abaco2_similar`. Solves
e.g. `DSolve`LieSymmetry[y'[x] == (x/y[x])(x²+y[x]²)^(1/3), y, x]` (symmetry `[1/x, −1/y]`).

The cheapest-first Lie sub-cascade is now `abaco1_simple → linear → abaco1_product →
function_sum → abaco2_similar → abaco2_unique_unknown → bivariate`.

Validation: unit tests `t_lie_function_sum` / `t_lie_abaco2_unique_unknown` and
forward-family stress tests `t_stress_lie_function_sum` (five Log-form members) /
`t_stress_lie_unique_unknown` (six non-integer-power members). Each test ODE is
**isolating** — per-heuristic attribution in the REPL confirms the new heuristic is the
one that fires, so no pass is vacuous. All three DSolve ctest suites and `make check-c99`
green. Per-solve valgrind: `function_sum` leak-flat; `abaco2_unique_unknown` adds only
the pre-existing 56 B/call FLINT `rat_canon` leak (`tasks/flint_ratcanon_leak.md`, same
`Together` path `bivariate`/`abaco2_similar` expose — its own allocations are balanced).
Deferred (out of scope): `abaco2_unique_general` (§4.4.2 Cases-I/II) and `chi`.

## Reduce — trig/hyperbolic INEQUALITY ∧ bounding inequalities

`Reduce[Sin[x] > 1/2 && 0 < x < 2 Pi, x]` used to return a wrong `False` (the
sign diagram cannot represent a periodic function). It now sign-decomposes the
bounded window into a union of intervals:

```
Reduce[Sin[x] > 1/2  && 0 < x < 2 Pi, x] -> Pi/6 < x < 5 Pi/6
Reduce[Sin[x] >= 1/2 && 0 < x < 2 Pi, x] -> Pi/6 <= x <= 5 Pi/6
Reduce[Sin[x] < 1/2  && 0 < x < 2 Pi, x] -> 0 < x < Pi/6 || 5 Pi/6 < x < 2 Pi
Reduce[Cos[x] > 0    && 0 < x < 2 Pi, x] -> 0 < x < Pi/2 || 3 Pi/2 < x < 2 Pi
Reduce[Sin[x] != 1/2 && 0 < x < 2 Pi, x] -> three intervals excluding Pi/6, 5 Pi/6
```

New engine `reduce_trig_ineq_region` in
[`src/solve/reduce_trigregion.c`](../../../src/solve/reduce_trigregion.c),
dispatched from the Reals branch of `reduce.c` when the statement is an `And`
with a trig/hyperbolic inequality (`<`, `<=`, `>`, `>=`, `!=`) over the
variable. A **1-D sign-decomposition** over the bounded region — sound because
every cell is decided by an exact sample:

1. Bound the variable to a finite interval by `Reduce`-ing the non-trig atoms;
   an unbounded region declines.
2. The real zeros of every trig atom (via Solve + family enumeration in the
   window) cut the interval into sign-constant cells.
3. Evaluate the FULL statement at a sample point of each cell (numerically in
   the interior, exactly at each boundary) and merge the true cells into a
   union of intervals / points, choosing open/closed endpoints from the exact
   boundary re-check (so `>` vs `>=` and closed feasible boundaries fall out).

Only pole-free real heads (`Sin`, `Cos`, `Sinh`, `Cosh`, `Tanh`, `Sech`) are
handled; a pole-bearing head (`Tan`, `Cot`, `Sec`, `Csc`, `Coth`, `Csch`), an
unbounded region, or a shape it cannot read makes it decline, and on this shape
the sign diagram is deliberately not run — so the statement is left unevaluated
(sound) rather than answered wrongly. `Sin[x] > 2 && 0 < x < 2 Pi -> False` and
`Sin[x] > -2 && 0 < x < 2 Pi -> 0 < x < 2 Pi` come out correctly.

## Reduce — periodic trig/hyperbolic equation ∧ bounding inequalities

`Reduce[Sin[x] == 1/2 && 0 < x < 2 Pi, x]` used to return a WRONG `False`: a
conjunction of a periodic equation with inequalities is not a single equation,
so it took the sign-diagram path, which cannot represent a periodic family.
Now it selects the finitely many family members inside the region:

```
Reduce[Sin[x] == 1/2 && 0 < x < 2 Pi, x]   -> x == Pi/6 || x == 5 Pi/6
Reduce[Sin[x] == 0   && 0 <= x <= 2 Pi, x] -> x == 0 || x == Pi || x == 2 Pi
Reduce[Sinh[x] == 2  && 0 < x < 10, x]     -> x == ArcSinh[2]
Reduce[Sin[x] == 2   && 0 < x < 2 Pi, x]   -> False
Reduce[Sin[2 x] == 1/2 && 0 < x < Pi, x]   -> x == Pi/12 || x == 5 Pi/12
```

New engine [`src/solve/reduce_trigregion.c`](../../../src/solve/reduce_trigregion.c),
dispatched from the Reals branch of `reduce.c` when the statement is
`And[<one circular-trig/hyperbolic equation over the variable>, <inequalities>…]`.
Method — **enumerate a numeric candidate set, then keep only what exactly
verifies** (so numeric interval arithmetic never decides membership on its own):

1. Solve the equation over the Reals into its families `a + p·C[k]`.
2. For a real period, substitute `a + p·k` into the constraints and `Reduce`
   that over the **real** parameter `k` (which, unlike Integers, handles the
   `Pi` coefficients) to a bounded interval; a non-real period (Sinh/Exp)
   contributes only its single real member at `k = 0`.
3. Enumerate the integers in the interval (widened by ±1 for safety), keep each
   candidate iff the FULL original statement evaluates to `True`, then sort
   numerically and emit `Or[var == value, …]` (or `False`).

The shape is precise (exactly one periodic equation; every other atom an
inequality over the variable), and on it the sign diagram is deliberately NOT
run — so an **unbounded** feasible region (`Sin[x] == 1/2 && x > 0`) is left
unevaluated (sound) rather than answered wrongly. Non-trig conjunctions
(`x^2 < 4 && x > 0`) are untouched.

## Reduce — single forward circular-trig equations `f[A(x)] == c` now solved

`Reduce[Sin[x] == 1/2, x]` (and every single forward circular-trig equation —
`Sin`, `Cos`, `Tan`, `Cot`, `Sec`, `Csc` over an affine argument) previously
did the wrong thing on **every** domain:

- **Complexes / default**: echoed the polynomial residual `-1 + 2 Sin[x] == 0`
  (the polynomial engine treats `Sin[x]` as a degree-0 generator).
- **Reals**: the sign-diagram engine was **unsound** — `Reduce[Sin[x]==1/2, x,
  Reals]` returned `False`, `Reduce[Sin[x]==0, x, Reals]` returned `True`.

These were routed nowhere (a single circular-trig head was explicitly excluded
from the two-argument pair reducer and left to the sign diagram, which
mishandles them exactly as it does the hyperbolics). Now they route to Solve —
which inverts the kernel into its complete periodic family — and
`reduce_eq_transcendental` renders the rule list as an `And`/`Or` formula:

```
Reduce[Sin[x] == 1/2, x]
  -> (C[1] ∈ Integers && x == 2 C[1] Pi + 5/6 Pi)
     || (C[1] ∈ Integers && x == 2 C[1] Pi + 1/6 Pi)
Reduce[Sin[x] == 1/2, x, Reals]   -> (same real family)
Reduce[Sin[x] == 2, x, Complexes] -> the two ArcSin[2] families
Reduce[Sin[x] == 2, x, Reals]     -> False   (no real solution)
```

Two changes, both mirroring the existing hyperbolic handling in
[`src/solve/reduce.c`](../../../src/solve/reduce.c):

1. A `reduce_is_circular_trig_resid` predicate (a circular-trig head over the
   variable in a degree-0 residual) wired into **both** the Complexes and Reals
   equation-dispatch branches, alongside the existing trig-pair / hyperbolic /
   pure-exponential predicates.
2. A soundness fix in `collapse_reals_families`
   ([`src/solve/reduce_eq.c`](../../../src/solve/reduce_eq.c)): a real-period
   family `a + b·C[k]` was kept whenever the **period** `b` was real, but if the
   **offset** `a` is non-real (e.g. `ArcSin[2] + 2 Pi C[k]`) every member is
   non-real, so the family must be dropped. The Reals branch now checks both,
   giving `Reduce[Sin[x]==2, x, Reals] -> False`.

## Solve/Reduce — generalized two-argument trigonometric & hyperbolic equations

`Solve` and `Reduce` now solve equations of the form `f[A(y)] ± g[B(y)] == c`
where `f, g ∈ {Sin, Cos, Tan, Cot, Sec, Csc, Sinh, Cosh, Tanh, Coth, Sech,
Csch}`, `A, B` are affine/polynomial in the solve variable (other symbols are
parameters, which may be **symbolic coefficients**), and `c` is a constant.
Previously every such two-argument form returned unevaluated. New engine:
[`src/solve/solvetrigpair.c`](../../../src/solve/solvetrigpair.c) (qualified
builtin `Solve`SolveTrigPair`), inserted in the `Solve` dispatch ahead of the
`solvetrig` TrigToExp fallback.

- **Argument-pair reducer (primary).** Reciprocal-normalizes Tan/Cot/Sec/Csc →
  Sin/Cos and Tanh/… → Sinh/Cosh (under `trig_canon` suppression, since the
  evaluator otherwise folds `Sin/Cos → Tan` straight back), combines over a
  common denominator, then factors the numerator into single-argument atoms
  with an explicit sum-to-product / reverse-angle-addition rule table. Each
  atom `H[arg] == 0` is solved by the existing inverse-function specialist
  (`solveinv`, with `solvetrig_solve_poly_in_kernel` as a fallback for
  `p(Cosh[y]) == 0` shapes). Produces clean `ConditionalExpression[…,
  Element[C[1], Integers]]` output and uniquely handles symbolic coefficients.
- **Pole / spurious gate.** A solution family is dropped when a denominator
  factor vanishes identically on it (representative `C[k] → 0`, decided by the
  leak-free zero test). Turns `Sec[x+y] - Tan[x+y] == 0` and
  `Csch[x+y] - Coth[x+y] == 0` into no-solution.
- **Degenerate cases.** A numerator that factors to `0` (parity identity, e.g.
  `Tan[x+y] + Tan[-x-y] == 0`) yields `True`; one that factors to a nonzero
  constant (contradiction, e.g. `Coth[x+y] - Tanh[x+y] == 0`) yields `False`.
- **Exponential-generator fallback.** For non-collapsing constant-RHS
  (`Tan[x+y] - Tan[x-2y] == 1`) and numeric mixed Sinh/Cosh
  (`Sinh[x+y] - Cosh[x-2y] == 0`), a self-contained single rational generator
  `u = E^(σ·y)` (σ = I/q circular, 1/q hyperbolic; q from the rational gcd of
  the var-coefficients) reduces to a Laurent polynomial in `u`, solved and
  unwound through `peel_exp`. Output is a `Log[Root[…]]` form. Symbolic
  coefficients admit no generator and decline (documented non-goal).
- **Reduce routing.** New `reduce_has_trig_pair` / `reduce_is_trig_resid` gate
  routes trig/hyperbolic residuals through `reduce_eq_transcendental` on both
  the Complexes and Reals branches, rendered as an `Or` of
  `Element[C[k], Integers] && y == …` conjuncts (or `True`/`False`).
- **Reals-domain fixes.** Two pre-existing Reduce bugs corrected via a
  family-collapse in `reduce_eq_transcendental`: `Reduce[Exp[y] == 3, y,
  Reals]` now returns `y == Log[3]` (was `False`) and `Reduce[Sinh[y] == 0, y,
  Reals]` returns `y == 0` (was `True`). A periodic family with a **real**
  period is kept whole (all members real, e.g. `2 Pi C[k]`); one with an
  **imaginary** period keeps only its real member at `C[k] = 0`.

## solverad — hang fix in radical-solution verification

`Solve` of a rational-in-radical equation with a **parametric `Power`-valued
RHS** — e.g. `Solve[Sqrt[t]/(x - Sqrt[t]) == q^2, t]` — used to **hang**.
`verify_candidate` (`src/solve/solverad.c`) verifies each candidate root
`N[]`-first, `Simplify`-fallback; with free parameters (`q`, `x`) `N[]` cannot
numericise, and the `Simplify` fallback denested `Sqrt[q^4 x^2/(1+q^2)^2]`
unboundedly.

The fix recognises that with a free parameter present, rejection is *unsound*
anyway (a squared-radical candidate can hold on one parameter regime and fail on
another — the reason `Solve[Sqrt[a x + c] + 3 x == 5, x]` keeps both branches
with `Solve::nongen`). New `has_free_parameter` returns `VERIFY_UNKNOWN` (keep +
nongen) for a free-parameter residual **without** calling `Simplify`; `Simplify`
now runs only on a parameter-free residual, where it terminates. Regression
test: `test_hang_parametric_rational_radical` in `tests/test_solveradicals.c`.

A larger fix — abstracting opaque var-free constants (`E^C[1]`, `Sqrt[5]`, `2^q`)
so `Together` clears a radical denominator against them, which would have solved
the `Power`-RHS *declines* including `1/2 Log[t] - Log[x - Sqrt[t]] == C[1]` — was
implemented and **reverted**: it made solverad *attempt* transcendental-radical
inversions that `DSolve\`Homogeneous` relies on it *declining*, re-hanging
`dsolve_tests`. The fragile cases, the landed fix, and the reverted attempt with
its lesson ("in solverad, declining is load-bearing") are written up in
[`SOLVERAD_IMPROVEMENTS.md`](../../../SOLVERAD_IMPROVEMENTS.md); the `Power`-RHS
declines remain a documented, safe (unevaluated) limitation.

## Solve/Reduce — general logarithmic & exponential transcendental equations

`Solve` and `Reduce` now invert two broad families of transcendental equations
(solving for the embedded variable `t`, with the other symbols as parameters and
`C[1]` a free constant):

- **Logarithmic** — sums/differences `Σ cᵢ·Log[uᵢ(t)] == rhs`, where each `uᵢ`
  is a rational (or radical) function of `t`. Examples now solved:
  `Log[2 t] - Log[x + t] == C[1]` → `t = E^{C[1]} x / (2 - E^{C[1]})`;
  `Log[t] + Log[x - t] == C[1]` (quadratic); `3 Log[t] - Log[t^3 - x] == C[1]`
  (cubic); `Log[t^2 - x^2] - Log[t - x] == C[1]` (cancels to linear).
- **Exponential** — products/quotients of `Exp[·]` and polynomials/rationals in
  `Exp[t]`: `Exp[2 t] - x Exp[t] + C[1] == 0`, `Exp[t]/(x - Exp[t]) == C[1]`,
  `Exp[t] Exp[x]/Exp[x^2 - t] == C[1]`, `Exp[a t^2 + b t + c] == C[1]`, etc.

**How.** The exponential family already worked at the REPL because the evaluator
gathers `Exp[a] Exp[b]/Exp[c] → E^(a+b−c)` for free and `try_exp_kernel`
substitutes `u = Exp[t]`; the missing piece was the *logarithmic* analogue.

- New `simp_log_fuse_all(e, var)` (`src/simp/simp_log.c`/`.h`) — an
  *unconditional* linear-combination-of-logs fuser reusing `try_fuse_plus`'s
  `Σ cᵢ Log[aᵢ] → Log[∏ aᵢ^cᵢ]` machinery with the positivity gate forced open
  and a `Cancel` on the fused argument (so `Log[t²−x²]−Log[t−x] → Log[t+x]`). It
  fuses only logs containing `var`, leaving var-free logs as additive constants.
- Wired into `solveinv_drive` (`src/solve/solveinv.c`): the residual `lhs−rhs`
  is fused before `isolate_residual`, collapsing a multi-log block to one `Log`
  head so the existing Log peel + polynomial/rational solvers finish the job.
  Principal-branch (as is the whole inverse-function surface); `Solve::ifun`
  fires and solutions carry the `ConditionalExpression` strip/period condition.
- `Reduce` gained `reduce_eq_transcendental` (`src/solve/reduce_eq.c`/`.h`): a
  single invertible Log/Exp equation (detected by `reduce_has_log_or_exp` +
  a not-a-positive-degree-polynomial test, so ordinary polynomials keep their
  leading-coefficient case split) is routed back through `Solve` and its
  rule-list rendered as an `Or` of `cond && var == value` conjuncts. It runs on
  the Complexes single-equation path and as a fallback in the Reals branch after
  the sign-diagram engines decline (so `Log[x^2] == 2 Log[-x]` over Reals still
  yields `x < 0`). Forward-trig is deliberately excluded — `Reduce[Sin[x]==0,x]`
  stays as before.

Tests: 31 back-substitution-verified cases in `tests/solve_corpus.m` (a new
`T-*` block); exact-form + count assertions in `tests/test_solve.c`
(`test_transcendental_log_exp`) and `tests/test_reduce.c`. Known limitations
(documented, not regressions): `1/2 Log[t] - Log[x - Sqrt[t]] == C[1]` declines
(a pre-existing `solverad` gap on a rational-in-`Sqrt[t]` equation with a
`Power`-valued constant RHS); `Log[t^n] - n Log[x - t] == C[1]` with symbolic
`n` is a symbolic-degree equation with no finite closed form (deliberately not
branch-collapsed, which would drop solutions of the numeric-`n` twins);
`Exp[t]^n/Exp[n t] == C[1]` is the degenerate identity `1 == C[1]`.

## PackedArrayQ — Mathematica-name predicate for the packed-List surface

New builtin `PackedArrayQ[expr]`: `True` when `expr` is a packed array (a `List`
stored as a dense machine-precision buffer, i.e. an `EXPR_NDArray` with
`present_as == NDA_HEAD_LIST`), else `False`. It is Mathematica's name
(`Developer`​`PackedArrayQ`) for the test.

Deliberately narrower than the existing `NDArrayQ`: `NDArrayQ` uses `is_ndarray`
and is `True` for *both* surfaces of an `EXPR_NDARRAY` (a packed `List` and a
visible `NDArray[...]`), whereas `PackedArrayQ` uses `is_packed_list` and is
`True` only for the packed-`List` surface. A visible `NDArray[...]` — a
Mathilda-only atom with no Mathematica counterpart — gives `False`, so the two
predicates differ only on that one input.

Implementation: `builtin_packedarrayq` in `src/ndarray.c`, registered in
`ndarray_init` with `ATTR_PROTECTED` and a docstring; declared in `ndarray.h`;
`SYM_PackedArrayQ` interned in `src/sym_names.{h,c}`. Crucially the head is added
to **both** the `AWARE` and `INT64_OK` lists in `src/pack.c` next to `NDArrayQ`
— a packedness predicate must be packed-aware or the transparency gate would
materialise its packed argument (for `int64` buffers as well as `float64`) before
it runs, making it wrongly answer `False` for every packed input. No numeric
kernel / `Compile[]` surface applies: it returns a boolean by reading node
metadata, it does not map over or reduce a buffer.

## ToPackedArray / ToNDArray — coerce a mixed Integer/Real list to a Real buffer

`ToPackedArray[{1, 2, 3.}]` previously returned the list unchanged (`{1, 2, 3.}`,
`PackedArrayQ` → `False`): `pack_sniff` rejected any list mixing exact `Integer`
and inexact `Real` leaves. That rule is right for **automatic** packing — silently
widening the exact `1` to `1.` is an observable head change (`1 === 1.` is
`False`), which a representation choice made on its own must never be — but wrong
for the **explicit** `ToNDArray`/`ToPackedArray`, where the user asked to pack.
It now widens the mix to a `"float64"` buffer (the integers become doubles),
matching Mathematica's `Developer` `ToPackedArray`.

Scope: `pack_sniff`/`pack_build` gained a `coerce` flag; only `builtin_tondarray`
sets it (via a new `pack_force_coerce`). `pack_force` itself is unchanged and
still declines a mixed list, so every automatic/listable caller keeps lossless
behaviour — `Sin[{1, 2, 3.}]` remains `{Sin[1], Sin[2], 0.1411…}` (the exact
integers stay symbolic), not a numericalised buffer. A new `pack_fold_class`
centralises the class-merge rule; `Bool` never unifies with a number, so
`{True, 1, 2.}` still declines. An all-`Integer` list still infers `"int64"`, and
an explicit `DataType -> "int64"` still refuses to round a `Real` into an integer
buffer. The visible `NDArray[...]` constructor already coerced (it defaults to
`"float64"`), so it was unaffected.

## Interpolation / ListInterpolation — packed-buffer table build (10–40× faster, now ahead of FITPACK)

`benchmarks/16-interpolation` showed the interpolant **build** 9.6–13× behind
scipy/FITPACK while evaluation was already at parity. Profiling (`sample`)
localised the entire gap to **Expr allocation churn**, not numeric work: the
`InterpolatingFunction[domain, table, …]` object stored `table` as a boxed List
of *n* `{coord, value}` pairs, so a machine-real build allocated ~3n small Expr
nodes (and `ListInterpolation`/`Interpolation[NDArray]` also boxed the whole
value tensor first). The numeric spline build itself was ~2 ms — competitive
with FITPACK's 3.2 ms — buried under boxing.

**Fix — a packed `n × (m+1)` `float64` table** (row *i* = `[c_{i,1}, …, c_{i,m},
v_i]`) for machine-real, **scalar-valued, value-only** interpolants
(`Ksupplied == 0`, non-`Hermite`); exact-`Integer`/`Rational`, MPFR,
array-valued, supplied-derivative, and `Hermite` interpolants keep the boxed
table unchanged (so exact node values, precision, and FD-Hermite are preserved).
The dimension-uniform packed row mirrors what `entry_coord`/`entry_value` return,
so the packed accessors are a straight column read and the numeric core
(`spline_solve_M`, `interp_ppoly_ensure`, the eval kernels) is untouched.

- **Build (the win).** `builtin_listinterpolation` builds the packed table
  directly from the value tensor with **double-only abscissae**
  (`listinterp_axis_double` + `listinterp_pack_emit`/`_buffer`) — no boxed
  `{coord,value}` pairs and no boxed coordinates. `builtin_interpolation` gains a
  buffer-direct fast path (`interp_ndarray_fast`) for a real rank-1 / rank-2-n×2
  `NDArray`, so `Interpolation[NDArray[…]]` no longer delists to 3n boxed nodes.
  `builtin_interpolation_impl` packs a machine-real plain-List data table via
  `interp_try_pack_data`. Stored as a **visible NDArray** (a transparent packed
  List would be materialised by the gate into flat `{c,v}` triples the boxed
  readers cannot parse).
- **Readers.** `build_grid` branches to `build_grid_packed`, which reads
  coordinates per column and fills the value buffer `f->V` **directly** (no boxed
  `entryAt`); `table_Ksupplied`, `obj_cache_load`, the exact-node query in
  `interp_apply`, and the two `value_shape` sites gain packed branches.
  `Integrate[InterpolatingFunction[…]]` (`integrate_interp.c`, a cold path)
  delists the packed table once for its coordinate scan.
- **Shared substrate.** `interp_finish_object` (object assembly + immediate
  eval-point), `interp_parse_option`, and `interp_resolve_periodic` are factored
  out and used by both the boxed and packed paths.

**Result (this machine, 10⁵-point builds).** `ListInterpolation` 1-D build
30 ms → **0.82 ms**, 2-D 200×200 17 ms → **0.34 ms**, `Interpolation[NDArray]`
34 ms → **0.42 ms** — all now **ahead of** scipy/FITPACK (3.0 / 1.5 / — ms),
where they were 4.5–13× behind. Every `16-interpolation` build/eval row is now
`AHEAD`; the only remaining `SLOWER` row is the scalar-loop
`Table[ifn[x], …]` (evaluator per-call overhead — the vectorised `ifn[array]`
path is at parity). Also a ~10× **memory** reduction for a machine interpolant's
stored table (16 vs ~150 B/point).

Verification: `tests/test_interp.c` `test_packed_table` (rank-1/rank-2 `NDArray`
fast paths, large 1-D and 2-D packed builds, domain grid, `Spline`, `Integrate`
round-trip, and exact-Integer-stays-boxed); interp / interp_poly / ndsolve
suites green; `make check-c99`, `check-packed-aware`, `check-array-exactness`
(0 MIXED), `check-nd-surfaces` green; valgrind leak-flat (definitely-lost
identical at 1× and 12×). `check-compile-coverage` exempts the interpolation
heads (they return `InterpolatingFunction`/polynomial objects, no compiled
machine type).

## ListInterpolation — values on a regular grid

New builtin `ListInterpolation` (`src/interp.c`), the value-only companion to
`Interpolation`. It interpolates a raw rectangular **array of values** on a
regular grid, synthesising the abscissae itself and delegating to the proven
`Interpolation` engine (`builtin_interpolation_impl`), so all of the numerics,
options, MPFR handling, and the vectorised `InterpolatingFunction` object are
shared verbatim — the new code is purely the front-end.

- `ListInterpolation[array]` — grid at integer positions `1, 2, …` per axis;
  the nesting depth of `array` is the dimensionality.
- `ListInterpolation[array, {{xmin, xmax}, …}]` — equally-spaced grid. Exact
  integer endpoints give an **exact** interior grid (rationals
  `xmin + i(xmax-xmin)/(d-1)`), so a high-precision data table keeps full MPFR
  precision instead of degrading to machine precision.
- `ListInterpolation[array, {{x1, x2, …}, …}]` — explicit grid-line positions.

```
In[1]:= ListInterpolation[{1, 2, 3, 5, 8, 5}][2.5]
Out[1]= 2.4375
In[2]:= ListInterpolation[{1, 2, 3, 5, 8, 5}, {{0, 1}}][0.5]
Out[2]= 3.875
In[3]:= ListInterpolation[{{1, 2}, {3, 4}}][1.5, 1.5]
Out[3]= 2.5
```

Attributes `Protected`; Options `InterpolationOrder -> 3`, `Method -> Automatic`,
`PeriodicInterpolation -> False` (passed through, so `"Spline"`/`"Hermite"` and
per-axis periodicity work). Interned `SYM_ListInterpolation`; added to `pack.c`'s
`AWARE` list so a packed / `NDArray` value tensor is delisted once rather than
materialised by the transparency gate. `Information` docstring in `info.c`.
Extensive tests in `tests/test_interp.c` (default/domain/explicit-position grids,
2-D, options, packed/NDArray/vectorised, malformed declines, MPFR); leak-clean.

**Buffer-direct NDArray construction.** For a scalar-valued real `NDArray` value
tensor (grid dimensions equal to the array rank), `ListInterpolation` now builds
the `{coord, val}` table straight from the packed buffer via
`ndarray_buffer_element_to_expr`, skipping the intermediate nested `List` that
`ndarray_to_nested_list` would materialise (its per-row/sub-array `List` wrappers
and one extra O(N) traversal). Value leaves are created once either way, and int64
buffers keep exact-`Integer` nodes; array-valued (grid rank < array rank) or
complex `NDArray`s still take the delist path. Behaviour is identical to the
delist path across List / packed / `NDArray` surfaces (verified) — this is a
construction-time constant-factor win, on top of the existing zero-copy vectorised
application path.

## Interpolation — fix gcc-16.1.0 IPA-CP miscompile of supplied 2nd-derivative Hermite

`Interpolation` with supplied second derivatives (`{{coords}, f, f', f''}`,
`Ksupplied == 2`) returned garbage — e.g. the `x^5` Hermite
`Interpolation[{{{0},0,0,0},{{1},1,5,20},{{2},32,80,160},{{3},243,405,540}}][1.5]`
gave `-8.84375` instead of `1.5^5 = 7.59375`. Root cause: **GCC 16.1.0's
interprocedural constant-propagation** miscompiles `eval_component_double`
(`src/interp.c`) — it specialises a clone on a constant `Ksupplied` and routes the
runtime `Ksupplied == 2` call to a clone that has const-folded the derived order
`k` to `1`, so `build_basis(k)` receives `1` (a 16-double cubic basis) while
`build_T` on the next line still receives `2`; the basis is then read as if `k ==
2` (36 doubles), an out-of-bounds read. Confirmed with `-fno-ipa-cp-clone` (the
whole suite passes). Fixed by excluding just that function from IPA with a guarded
`__attribute__((noipa))` — no behaviour or performance change elsewhere. The
existing `test_supplied_1d` quintic case, which had been silently failing (and
aborting the interp suite), now passes.

## DSolve — AutonomousReduction & Lie elliptic-quadrature speedups

Two performance fixes to the second-order autonomous path, each a large speedup on
the elliptic quadratures these methods produce (e.g. `DSolve[y'' == 2 y^3, y, x]`,
which correctly declines):

- **`AutonomousReduction` froze its intermediate constant to a plain symbol.** The
  reduction `p = y'(y)`, `p p'(y) == f` solves for `p` (getting e.g.
  `Sqrt[y^4 + C[1]]`), then integrates `y' == p(y)`.  It previously renamed the first
  constant to a plain symbol (`DSolve\`arK`) before the second solve.  A plain
  symbolic parameter inside an elliptic integrand sends the first-order cascade down
  a ~27x slower path (`DSolve[y' == Sqrt[a + y^4]]` ~ 11 s vs
  `DSolve[y' == Sqrt[C[2] + y^4]]` ~ 0.4 s — a generated constant `C[n]` takes the
  fast decline, a plain symbol does not).  Freezing to the generated constant `C[2]`
  (distinct from the second solve's `C[1]`, so no rename is needed) cuts
  `DSolve[y'' == 2 y^3]` from ~9.4 s to ~0.4 s; solvable autonomous ODEs
  (`y y'' == (y')^2 -> C[1] E^(C[2] x)`) are unchanged.  `dsolve_autonomous.c`.

- **Lie `lie_first_integral` sign-normalizes the quadrature.** The Integrate engine
  takes a far slower path on a leading-negative non-elementary integrand
  (`Integrate[-1/Sqrt[y^4+C], y]` ~ 3.7 s vs `Integrate[1/Sqrt[y^4+C], y]` ~ 0.4 s);
  the `mu = 1/(eta - xi omega)` factor routinely produces such a sign.  The Lie
  quadrature now integrates the sign-normalized form and re-applies the sign (pure
  linearity), so the symmetry integrator is fast on elliptic first integrals.
  `dsolve_lie.c` (`lie_integrate_signfix`).

## DSolve — M10 Lie point-symmetry: `abaco1_product` (first quadrature ansatz)

Added the `abaco1_product` heuristic to `DSolve`LieSymmetry` (`dsolve_lie.c`), the
first of the Cheb-Terrab & Roche (1998) quadrature ansätze. It finds the symmetry
`[ξ = F(x) G(y), η = 0]` and its inverse `[0, F(x) G(y)]` — a rational-but-non-
polynomial infinitesimal (e.g. `ξ = y/x`) that the polynomial `linear`/`bivariate`
ansätze cannot represent. Necessary condition is the paper's Eq 19 (product-
separability of `L = (ω_xy ω − ω_x ω_y)/ω⁴`); `F` is the x-factor, `g(y) = F·∂_x(1/(F
ω))` (Eq 20), `G = Exp[∫g dy]`. The inverse pattern reuses the same extractor on the
inverse ODE `1/ω(y,x)`. Every branch back-substitutes to zero via
`dsolve_run_implicit`, so no inert heads. Solves e.g.
`DSolve`LieSymmetry[y'[x] == 2 x y[x]/(x² + 2 y[x]⁴ + 2), y, x]`.

New shared substrate reused by the remaining quadrature heuristics: `lie_sep_xfactor`
(product-separable x-factor), `lie_free_of_var` (a **fast rational free-of** test —
`P/Q` is free of a variable iff `P_v Q − P Q_v` expands to 0, a polynomial zero-test
~6× cheaper than the general `zero_test` on the rational derivative), `lie_ratsimp`
(`Cancel[Together]` in place of `Simplify` on the hot path), and
`lie_swap_xy`/`lie_inverse_omega` (the inverse-ODE machinery). The Lie sub-cascade is
now ordered **cheapest-first** (`abaco1_simple` → `linear` → `abaco1_product` →
`bivariate`), so the degree-2/3 NullSpace runs only as a last resort.

Validation: unit tests (`t_lie_abaco1_product`) and a forward-generator stress family
(`t_stress_lie_product`, seven fully-isolating y⁴ ODEs verified in the REPL to admit
no polynomial symmetry of degree ≤ 3). SymPy 1.14's `lie_group` (`infinitesimals`)
*times out* (>25 s) on the pure product family `2xy/(x²+2y⁴+c)` that Mathilda solves
in ~30 ms. Per-solve valgrind is leak-flat (`definitely lost` identical for `1+1`,
1×, and 8× runs). All three DSolve ctest suites and `make check-c99` green.

## DSolve — M10 Lie point-symmetry: `abaco2_similar` (§4.3 similarity ansatz)

Added the `abaco2_similar` heuristic to `DSolve`LieSymmetry` (`dsolve_lie.c`, Cheb-
Terrab & Roche §4.3), the first ansatz that finds a symmetry with **both** components
single-variable functions `[ξ = F(x), η = H(x)]` (and its inverse `[F(y), H(y)]`).
Condition: `Q = ω_y/ω_yy`; `T = Q_x/Q_y` must be free of `y` (Eq 44a) and
`(T·ω_y − T_x − ω_x)/(ω+T)` must be free of `y` (Eq 44b); then
`F = Exp[∫(that integrand) dx]` and `H = −T·F` (Eqs 43,40). The `Q_y = 0` sub-case is
declined (deferred). This is the first heuristic to reach **irrational** ODEs the
rational ansätze cannot touch: it solves `y' == Sqrt[a x + b y + c]` and
`y' == (a x + b y + c)^p` (non-integer `p`) — e.g. `DSolve[y'[x] == Sqrt[x + y[x]],
y[x], x]` returns the verified implicit first integral
`x − 2 Sqrt[x+y] + 2 Log[1 + Sqrt[x+y]] == C[1]`. Sits after `abaco1_product` and
before `bivariate` in the cheapest-first Lie sub-cascade. Every branch back-
substitutes to zero via `dsolve_run_implicit`.

Validation: unit test `t_lie_abaco2_similar` and a forward-generator stress family
`t_stress_lie_similar` (eight radical/root ODEs, each isolating the heuristic — the
rational ansätze all decline on an irrational `ω`). Per-solve valgrind leak-flat.

**Supporting fixes** landed with this work:
- **`NthAlgebraic` declines implicit-`Root[]` branches** (`dsolve_nth_algebraic.c`).
  When `Solve[eqn, y^(n)]` returns `Root[…]` objects (no explicit closed form for the
  top derivative — e.g. a general cubic `p³ + x p² − y == 0`), recursing
  `DSolve[y^(n) == Root[…]]` is futile and could **hang**. The method now declines the
  whole ODE so a later specialist (Lagrange/d'Alembert) claims it. Fixes a production
  hang on `DSolve[y == x (y')² + (y')³, y, x, IncludeSingularSolutions -> True]`;
  genuine explicit-root cases (`(y')² == 4y`) still solve.
- **`Simplify` power-distribution leak** (`simp_power.c`). `power_distribute_walk`
  malloc'd the factor array for `Power[Times[…], e] → Times[Power[…], e]…` and handed
  it to `expr_new_function` (which **copies** the array), then never freed the heap
  holder — leaking on every distributed power. Three branches fixed. Surfaced as a
  ~90 B/solve leak on the Lie first-integral path; independent of DSolve.
- **DSolve test suites now load `init.m`** (`test_load_init_m` in `test_utils.h`, called
  from all three DSolve mains) so they exercise the same environment as the REPL /
  `-file` mode (deriv.m rules + CRC integral tables). Without it the suite tested a
  non-production DSolve — the very reason the Lagrange/NthAlgebraic hang above was
  invisible to tests. Watchdog raised 60 s → 120 s to absorb the extra startup.

## DSolve — M9 SymPy deterministic parity gaps (all eight methods)

Implemented milestone **M9** in full: the eight deterministic ODE methods that
close Mathilda's remaining gaps against SymPy's documented `dsolve` hints. All are
decision procedures (the project's preference over the heuristic Lie method) and
reduce to methods already in the cascade — no new substrate beyond one shared
helper. Each is a self-contained `src/calculus/dsolve_<m>.c` on the three-function
contract, wired into `dsolve.c` (enum / `ds_method_from_string` / cascade / pinned
switch) with a pinned `DSolve`<Method>` builtin, an Information docstring,
`ATTR_PROTECTED`, unit tests (`tests/test_dsolve.c`), and a forward-generator
stress family (`tests/test_dsolve_stress.c`). `DSolve` remains the documented
symbolic-head exemption from the packed/`Compile[]` surfaces.

- **`Factorable`** (`dsolve_factorable.c`) — factors the residual as a product in
  the derivatives and recurses the cascade on each factor, unioning the branches.
  Runs at the FRONT of the cascade. Two robustness points: it factors over
  plain-symbol substitutes under a `PolynomialQ` gate (`FactorList` HANGS on a
  non-polynomial funcapp argument such as a `Sqrt[y[x]]` coefficient, and even
  misfactors polynomial funcapp forms); and it keeps only genuine DIFFERENTIAL
  factors (containing a derivative `d_k`, `k≥1`) so the trivial `y==0` branch never
  hijacks the recursive callers (`AutonomousReduction`) that take the first
  sub-solution. Solves `(y'-y)(y'+y)==0`, products of linear ODEs, etc.
- **`NthAlgebraic`** (`dsolve_nth_algebraic.c`) — algebraic (degree ≥ 2) in the top
  derivative: `Solve` for `y^(n)`, recurse each branch (a branch free of `y` hits
  `Quadrature`), union; plus the degenerate no-derivative case. Also at the front.
  Solves `(y')^2 == 4 y → (x+C)^2`, `(y')^2 == 2 → ±Sqrt[2] x + C[1]`.
- **`LinearCoefficients`** (`dsolve_lincoeff.c`, explicit + implicit two entries,
  mirroring `DSolve`Homogeneous`) — `y' == (a₁x+b₁y+c₁)/(a₂x+b₂y+c₂)`: det≠0 shifts
  to the lines' intersection giving a homogeneous equation (explicit Root-form, or
  the implicit log-spiral first integral); det=0 (parallel) substitutes
  `v=a₁x+b₁y` for a separable one. Deterministic and earlier than the Lie `linear`
  heuristic that also reached this class (`t_lie_linear_coefficients` now pins the
  Lie builtin to keep exercising it).
- **`AlmostLinear`** (`dsolve_almostlinear.c`) — `f(x)g(y)y' + k(x)l(y) + m(x)==0`:
  the substitution `u=Integrate[g,y]` linearises it to `u'+P(x)u==Q(x)` (with
  `P=−H_y/g`, `Q=H+Pl`, `H=−B/f`, all required free of `y`), solved by the
  integrating factor, then `l(y)==U(x)` solved for `y`. Solves
  `2 y y' + y² − x == 0`.
- **`SeparableReduced`** (`dsolve_sepreduced.c`) — `x y'/y == G(x^n y)`: the power
  `n = x r_x/(y r_y)` (constant iff the form holds), substitution `w = x^n y` gives
  a separable equation, and the implicit first integral is returned through
  `dsolve_run_implicit`. Solves `y' == y²/(1 + x y)`.
- **`Liouville`** (`dsolve_liouville.c`) — `y'' + g(y)(y')² + h(x)y' == 0` (distinct
  from `AutonomousReduction`/`ReductionOfOrder`, which need `h==0` / `g==0`) by two
  quadratures: `Integrate[Exp[Integrate[g,y]],y] == C[1] Integrate[Exp[−Integrate[h,x]],x]
  + C[2]`, solved for `y`. Solves `y'' + (y')²/y + y'/x == 0`.
- **`UndeterminedCoefficients`** (`dsolve_undetcoeff.c`) — a tidy particular for
  constant-coefficient linear ODEs with UC forcing (polynomial · exp · sin/cos, and
  sums), by superposition over the additive terms of `Expand[g]`, each with the
  ansatz `x^s Exp[ax](Cos[bx]ΣA_k x^k + Sin[bx]ΣB_k x^k)`, where the resonance shift
  `s` is found by incrementing `s=0,1,2,…` until the coefficient system solves (no
  root-multiplicity bookkeeping). Runs immediately before
  `LinearConstantCoefficients` (which stays the variation-of-parameters fallback for
  any other forcing). `y''+y==x² → x²−2+…`, `y''−y==E^x → …+½ x E^x` (resonance).
  The residual is matched with `Expand` (not `Simplify`, which rewrites `Cos[2x]` and
  breaks the `Coefficient[·,Cos[bx]]` extraction). Also exposes the shared
  `dsolve_homog_basis` (moved from `dsolve_constcoeff.c` into `dsolve_common.c`;
  identical code, both methods now call it — no behaviour change).
- **`FirstOrderPowerSeries`** (extends `dsolve_frobenius.c`) — a truncated power
  series about the ordinary point `x0=0` for `y'==F(x,y)` (a₀=C[1]; `[xⁿ]F` depends
  only on a₀..aₙ, so one Taylor read per order). PINNED-ONLY (not in the automatic
  cascade): a first-order ODE with no closed form stays unevaluated by default,
  matching SymPy's opt-in `1st_power_series` and Mathematica. Gives series for
  nonlinear `y'==x+y²` etc.; declines a pole at `x0` (probe muted so the decline is
  silent).

Cascade order (scalar `DS_AUTOMATIC`): `Factorable`, `NthAlgebraic` (front) →
existing first-order specialists → `UndeterminedCoefficients` before `constcoeff` →
existing 2nd-order/1st-order-hard block → `LinearCoefficients`, `AlmostLinear`,
`SeparableReduced` (first-order reductions) → `autonomous`, `Liouville` → existing
implicit fallbacks → `LinearCoefficients` (implicit) before `lie` → series fallback.

Gates: all three DSolve ctest suites green (`dsolve_tests`, `dsolve_stress_tests`,
`dsolve_m5_stress_tests`); `make check-c99` exit 0; the seven new self-contained
methods are per-call valgrind-flat (1× == 6× at the 13,440 B one-time engine
baseline). `AlmostLinear` inherits a **pre-existing** per-call leak in the `Integrate`
engine (`integrate.c` ~920/256) that `LinearFirstOrder` — and a bare
`Integrate[Exp[x] Sin[x], x]` — exhibit identically (≈168 B/call); it is not new to
M9 and is flagged for a separate core-integrator fix.

## DSolve — SymPy ODE parity audit + heuristic Lie point-symmetry method (M10 L1)

Audited `DSolve` against SymPy's documented ODE solver hints
(`sympy.solvers.ode.allhints` + `dsolve_system`). Mathilda covers most of SymPy
and exceeds it in several areas (full Kovacic, Abel, Chini, Lagrange, operator
factoring — none of which SymPy has); the genuine gaps are recorded in
`DSOLVE_PLAN.md` as two new milestones: **M9** (deterministic: `Factorable`,
`NthAlgebraic`, `AlmostLinear`, `LinearCoefficients`, `SeparableReduced`,
`Liouville`, `UndeterminedCoefficients`, `FirstOrderPowerSeries`) and **M10**
(heuristic Lie point-symmetry, SymPy's `lie_group`).

New builtin **`DSolve`LieSymmetry`** (alias `DSolve`LieGroup`;
`src/calculus/dsolve_lie.c`) — the general first-order backstop, run after the
deterministic specialists and before the series fallback. It is the one
deliberately heuristic method in the cascade: for a first-order ODE the
linearized symmetry condition is one PDE in two unknowns (`ξ`, `η`), which is
underdetermined, so — as in SymPy/Maple — a table of ansatz heuristics
(Cheb-Terrab et al.) is used.

- **Method.** For `y' = ω(x,y)`, each heuristic proposes infinitesimals `(ξ,η)`;
  a `checkinfsol` gate accepts only those satisfying `S = η_x + (η_y − ξ_x)ω −
  ξ_y ω² − ξ ω_x − η ω_y == 0`. The accepted symmetry gives the Lie integrating
  factor `μ = 1/(η − ξ ω)`, whose exact-equation quadrature is the implicit first
  integral `{{G(x,y[x]) == C[1]}}`, returned through `dsolve_run_implicit` and
  verified by implicit differentiation (`y' == −G_x/G_y`). No inert heads — every
  branch back-substitutes.
- **L1.** Substrate (`lie_S_expr` / `lie_check` / `lie_first_integral`) plus the
  `abaco1_simple` heuristic (one-variable ansätze). Solves e.g. `y' == y/x + x`
  (→ `{{-x + y[x]/x == C[1]}}`), `y' == x y²` (→ `{{x²/2 + 1/y[x] == C[1]}}`),
  `y' == 2 x y + x`.
- **L2 `linear`.** The affine ansatz `ξ = a1 x + a2 y + a3`,
  `η = a4 x + a5 y + a6`: the determining system is the coefficient matrix of the
  cleared symmetry condition (`Outer[Coefficient, Flatten[CoefficientList[…]],
  {a1..a6}]`), and its `NullSpace` is a basis of admissible symmetries — no
  `Solve`, hence no free-variable message. Catches the **linear-coefficients**
  class `y' == (a1 x+b1 y+c1)/(a2 x+b2 y+c2)` — e.g. `y' == (x+2y-4)/(2x+y-5)` and
  `y' == (2x+3y-1)/(3x+2y+2)`, both previously unsolved by *any* method — now
  solved through the automatic cascade. Lie runs **after every deterministic
  specialist** (including the homogeneous implicit fallback, which keeps its
  cleaner form for its own equations — regression-checked), immediately before the
  series fallback. Declines `y' == y² + x`.
- **L3 `bivariate` (new).** General **degree-2 then degree-3 bivariate-polynomial**
  ansatz `ξ, η = Σ c_{ij} x^i y^j` — the exact generalization of `linear` (its
  degree-1 case). Shared `lie_poly_symmetry(ω, degree, …)` builds the ansatz over
  interned `DSolve\`lieB*` coefficients and runs `linear`'s identical pipeline
  (`Numerator[Together[S]]` → `CoefficientList[·,{x,y}]` → `Flatten` →
  `Outer[Coefficient, forms, coeffs]` → `NullSpace` → gate + `lie_first_integral`
  per basis vector). Runs after `linear` declines; rationality (`PolynomialQ`) and
  clean-system (`ds_free_of(M,x/y)`) guards reused; degree capped at 3. Catches
  genuinely **quadratic / projective** symmetries (`ξ=x², η=x y`; the projective
  group) the affine ansatz misses — e.g. the family `y' = y/x + A(y/x)/x` with
  symmetry `(x², x y)`: `y' == -1/x + y/x + y²/x³` → `{{-1/x + ½Log[x+y] −
  ½Log[-x+y] == C[1]}}`. The Riccati `y' == y² + x` still declines (regression-checked).
- **Remaining.** L2 `abaco1_product` / `function_sum` / `abaco2_similar`; L3
  `chi` / `abaco2_unique_*`.
  Design note: `docs/design/dsolve_lie_symmetry.md` (with reference preprints).
- **Tests.** `tests/test_dsolve.c` `t_method_lie` (pinned, implicit-differentiation
  verified), `t_lie_declines` (non-vacuous decline), `t_lie_linear_coefficients`,
  and **`t_lie_bivariate`** (two isolation ODEs with a genuinely degree-2 symmetry —
  verified in the REPL that the degree-1 determining `NullSpace` is trivial and
  every `abaco1_simple` ratio depends on both variables, so `bivariate` is the only
  heuristic that can solve them; not a vacuous pass). Stress family
  `t_stress_lie_bivariate` (`tests/test_dsolve_stress.c`): an 8-member forward
  generator over `A(u)` in `ω = y/x + A(y/x)/x`. Attributes `Protected`; Information
  string via `symtab_set_docstring`. All three DSolve ctest suites green; builds
  clean under `-std=c99 -Wall -Wextra`; `make check-c99` exit 0.
- **Known issue (pre-existing, orthogonal — filed `tasks/flint_ratcanon_leak.md`).**
  A bivariate-solved ODE leaks **56 bytes / call** — traced to a pre-existing orphan
  in the FLINT-bridge rational canonicalizer (`fmpz_mpoly_to_expr` `flint_bridge.c:2434`

## ListGradient — numerical gradient of a sampled array (numpy.gradient port)

New builtin `ListGradient` (`src/list/list_gradient.c`): the finite-difference
numerical gradient of a sampled array, a from-first-principles port of
`numpy.gradient`. Second-order central differences in the interior and one-sided
differences at the edges, computed per axis for an array of any rank — a rank-1
input gives one vector, a rank-`k` input gives `{g1, ..., gk}`.

- **numpy-default semantics.** The default (`Method -> "Centered"`,
  `DifferenceOrder -> 2`) reproduces `numpy.gradient` exactly, including
  first-order one-sided edges (numpy `edge_order = 1`): the edge accuracy is one
  order below the interior.
- **Generalised scheme.** `Method -> "Centered" | "Forward" | "Backward"`;
  `DifferenceOrder -> p` (default 2); `WindowLength -> m` (an alias for the
  order, `m = p + 1` points → order `p`); `Axis -> All | a | {a, ...}` to
  restrict to particular axes.
- **Spacing.** A second positional argument gives uniform spacing (scalar),
  per-axis spacing, or coordinate vectors for non-uniform sampling — the numpy
  `varargs` folded into one argument.
- **One kernel, exact everywhere.** All scheme/order/window/grid combinations run
  through Fornberg's finite-difference-weight recurrence, exact on non-uniform
  grids. Integer input yields exact `Rational`s, symbolic input a symbolic
  result.
- **Fast paths.** Machine `Real` **and complex** arrays compute straight on the
  packed/NDArray buffer (`list_gradient_ndarray`, on `pack.c`'s `AWARE` list),
  one axis at a time via a strided axpy pass (the weights are real, so a complex
  element is two contiguous doubles carried through the same pass);
  `ListGradient[v]` lowers in `Compile[]` (rank-1 array form, `ND_FNS` delegate)
  and therefore auto-compiles. An integer buffer deliberately materialises and
  takes the exact `Rational` `List` path.
- **Number towers.** Verified across the whole numeric stack: machine
  `float64`/`float32`, GMP bignums and exact `Rational`s (exact results), MPFR
  arbitrary precision (results retain the input precision), and complex (exact
  and machine, `List` and packed `NDArray`).
- **Benchmarked against `numpy.gradient` — and now beats it.** Accuracy: the
  default scheme reproduces `numpy.gradient` to machine precision (bit-identical
  on random data, ~3e-15 on smooth uniform grids, ~2e-13 non-uniform); the
  generalized schemes converge at their stated interior order (2/4/6 confirmed).
  Performance (float64, this machine): after vectorising the buffer kernel,
  ListGradient is **1.6–4.3× faster than `numpy.gradient`** on every 1-D and
  multi-dimensional shape measured (e.g. 1-D 10⁶: 0.88 ms vs 2.6–3.9 ms; 2-D
  1000² both axes: 3.58 ms vs 7.8 ms; 3-D 100³ all axes: 5.7 ms vs 12.3 ms),
  with only the 4th-order 5-point scheme (which numpy cannot express) at parity.
  The optimisation was loop structure, **not** the numerics: (1) `restrict`
  pointers so the compiler knows input/output do not alias; (2) a tap-outer
  contiguous axpy over the interior block (SIMD FMA) instead of a per-element
  stencil call, which fixed the `inner=1` shapes (1-D and the strided axis) that
  did not vectorise; (3) a fused single-pass unroll for the common 2-/3-point
  windows to cut memory passes; and (4) building the multi-axis result as one
  stacked rank-(k+1) buffer directly, instead of N arrays the pack gate then
  copies together. Verified: buffer path timed (packed/`NDArray`, zero gate
  materialisations — not Expr trees), accuracy unchanged, all surface audits and
  valgrind clean.
- Registered with attribute `Protected`, an Information docstring, `Options`
  defaults, and a 24-case unit suite (`tests/test_list_gradient.c`) covering
  numpy parity, non-uniform grids, every Method/order/window, multi-axis and
  `Axis` selection, packed/visible-NDArray agreement, compilation, and the
  symbolic/exact and unevaluated paths. Valgrind-clean (no leak beyond the
  REPL-init baseline).

## DSolve — Chini second reduction, x^a y^b integrating factor, and a leaked-warning fix

Two solvable first-order ODEs were failing loudly — each printed a cascade of
`Power::infy: 1/0` / `Infinity::indet` and then returned unevaluated:

```
DSolve[y'[x] == -x E^-x - y[x] + x E^(2x) y[x]^3, y[x], x]        (* Chini *)
DSolve[(x y[x] - 2 x) y'[x] == y[x] - y[x]^2 + 3 x^2 y[x]^3, y[x], x]  (* exact via x^a y^b *)
```

Three independent defects, all fixed:

- **Wrong classification → a valid equation rejected (the leaked `1/0`).**
  `DSolve`Bernoulli` and `DSolve`Chini` tested the candidate exponent
  `nexp = Y Q_Y/Q` for `FreeQ[·, x]` **before** reducing it. `Q` is stored
  unexpanded (e.g. `-2 x E^(2x) Y^3` hidden inside a sum), so `nexp ≡ 3` still
  contained `x`/`Y` textually; `ds_free_of` then fell to the numeric zero-test
  sampler, which floating-point-cancelled `Q` to exactly `0.0`, evaluated
  `0^(-1)` (the leaked `Power::infy`), and — worse — read the resulting
  `ComplexInfinity` as *"definitely non-zero"*, so the constant exponent looked
  x-dependent and the classifier declined. Fixed by reducing `nexp` **before** the
  guard. Reduction uses **`Cancel`, not `Simplify`**: this runs on the decline
  path of *every* equation reaching Bernoulli/Chini, and full `Simplify` hangs on
  a symbolic radical ratio (e.g. `y' == Sqrt[y^4 + K]` fed in by
  `AutonomousReduction`), whereas `Cancel` is a cheap rational-GCD that still
  collapses the genuine constant.

- **Chini second reduction (solves the first example).** `dsolve_chini_first_integral`
  tried only reduction (a) (reduce-to-autonomous, `y = f^(-1/(n-1)) u`, needs
  `B = g + f'/((n-1)f)` constant). It now falls back to reduction (b) —
  **linear-term removal**, `y = e^(∫g) w` → `w' = P w^n + R` with `P = f e^((n-1)∫g)`,
  `R = h e^(-∫g)`; when `R/P == c` is constant the equation is separable, giving the
  implicit first integral `∫dw/(w^n+c) − ∫P dx == C[1]`, `w = y e^(-∫g)`. The
  first example returns `∫du/(u^3−1) − x^2/2 == C[1]`, `u = y[x] E^x`. Shared with
  Abel, so more Abel equations solve too; the speculative integrals are bracketed
  with `g_integrate_quiet`.

- **Exact via `x^a y^b` integrating factor (solves the second example).**
  `DSolve`Exact` searched only `μ(x)` and `μ(y)`. It now also proposes
  `μ = x^a y^b` with constant `a,b` from the linear exactness condition
  `b(M/y) − a(N/x) + (M_y − N_x) == 0` (sampled at a few generic points and solved),
  **accepted only after a symbolic exactness re-check** (`(μM)_y == (μN)_x`), with
  the substrate's back-substitution verify as the final backstop. Gated to
  polynomial `M,N` (`PolynomialQ`) so the speculative `Solve` never runs on the
  heavy radical systems the autonomous recursion feeds in. The second example
  returns the two explicit branches of `3x + 1/(xy) − 1/(xy^2) == C[1]`
  (`μ = x^-2 y^-3`).

- **Speculative arithmetic warnings no longer leak.** `builtin_dsolve` brackets the
  whole method cascade in `arith_warnings_mute_push/pop` (the family Frobenius/
  Kovacic already mute per-region): every classifier legitimately forms `1/0`
  while probing an equation that is not of its form, and the verifier is the real
  gate — so a decline is now silent. Even a bare `DSolve[y'==-x/y, y[x], x]`
  (which used to leak one `Power::infy`) is clean.

Both examples verify (residual → 0 by numeric back-substitution). Gates: all three
DSolve ctest suites green (`dsolve_tests` 28 s, unchanged from baseline —
confirming the `Cancel`/`PolynomialQ` choices kept the fix off the hot decline
paths), `make check-c99` clean, valgrind shows no new definitely/possibly-lost
blocks over the one-time ~13.6 KB engine baseline. Files: `dsolve_bernoulli.c`,
`dsolve_chini.c`, `dsolve_exact.c`, `dsolve.c`.

## DSolve — Kovacic stress-test hardening (full Case-1, Bessel-reducible, hang/decline guards)

Triaging a corpus of Kovacic stress tests exposed a fragile 2nd-order path: some
equations hung, some returned bare-unevaluated, and one leaked an integrator
warning. Fixes, all general rather than case-specific:

- **Full classical Kovacic Case 1.** `DSolve`Kovacic`'s apparent-singularity
  completion was limited to pole order ≤ 2 and `r` vanishing to order ≥ 2 at ∞. It
  now implements the complete algorithm (Kovacic 1986): the local principal part
  `[√r]_c` for **even-order poles ≥ 4**, and the polynomial part `[√r]_∞` when `r`
  **grows at infinity** (`O(∞) = degd−degn ≤ 0`), with `ω = s(∞)[√r]_∞ +
  Σ_c(s(c)[√r]_c + α_c^{s(c)}/(x−c))` and degree bound `d = α_∞^{s(∞)} − Σ_c
  α_c^{s(c)}`. Pass 2 now prefers **two independent `P·Exp` families** directly
  (no reduction-of-order integral), which closes completely-reducible cases like
  `y'' − (x² + 3/(4x²))y == 0 → x^(−1/2)(C[1]e^{−x²/2} + C[2]e^{x²/2})` that the old
  δ≥2 slice rejected. The critical constant `b` uses `([√r])²` (not the raw √r
  Laurent series — they diverge at infinity).
- **Bessel-reducible recognizer.** `DSolve`SpecialFunctionForm` now maps the
  pure-power potential `y'' + A xᵐ y == 0` (`m` a number ≠ 0, −2) to
  `Sqrt[x] Z_{1/(m+2)}(...)` — `J/Y` for `A>0`, modified `I/K` for `A<0` — so
  `y'' − x⁴ y == 0 → Sqrt[x](C[1] BesselI[1/6, x³/3] + C[2] BesselK[1/6, x³/3])`
  instead of a truncated series.
- **Hang guard.** A denominator-degree gate in `DSolve`Kovacic` declines a
  high-degree rational `r` up front (before any Factor/Solve/analyze_roots), so
  `y'' + ((x¹⁰−1)/(x¹²+1))y == 0` returns a fast Taylor series instead of looping.
  A reduction-of-order integral in a hang-prone special function (`Erf`/`Erfi`/…)
  is declined rather than Simplify'd (its complex argument would hang), letting
  Case 2 take over.
- **Silent speculative declines.** The Kovacic recovery/second-solution integrals
  are speculative, so a non-elementary result there no longer leaks the
  `Integrate::nonelem` diagnostic (a new `g_integrate_quiet` counter); direct user
  `Integrate` still reports it.
- **Series never returns nothing.** Automatic `DSolve` of a *rational*-coefficient
  linear ODE whose `x=0` is irregular/obstructed now expands about a nearby
  ordinary point (`SeriesData[x, x0, …]`) rather than leaving the equation
  unevaluated. The pinned `DSolve`PowerSeries`/`FrobeniusSeries` keeps its
  "series about the origin, else decline" contract.
- **Cosmetic.** The reduction-of-order second solution's constant factor now folds
  into the arbitrary constant: `y'' − 3/(16x²)y == 0 → C[1] x^(¼(2−√7)) +
  C[2] x^(¼(2+√7))` (was `2 C[2] x^(…)/√7 + …`).

Tests: `tests/test_dsolve.c` (Bessel-reducible, high-degree no-hang) and
`tests/test_dsolve_m5_stress.c` (growth-at-∞ closed forms, growth no-hang).

## DSolve — Kovacic Case 1 apparent-singularity completion (Legendre / Chebyshev / …)

`DSolve` returned a truncated **power series** for Legendre's equation
`(1−x²)y'' − 2x y' + 2y == 0` (and the rest of the integer-degree
Legendre/Chebyshev/Gegenbauer/Jacobi family) even though a closed form exists — the
elementary `C[1] x + C[2](1 − x ArcTanh[x])` that Maple and Mathematica return. The
cascade order was already correct (every closed-form method runs before the series
fallback); the gap was that **no closed-form method succeeded**, so it fell through.

Root cause: `DSolve`Kovacic`'s Case 1 built its ω-ansatz with poles only at the poles
of the normal-form potential `r`. The Legendre solution needs
`ω = 1/x + x/(x²−1)` — the `1/x` is `P'/P` for `P = x`, an **apparent singularity**
(a zero of the solution where `r` is regular). The classical degree-`d` monic
polynomial `P` that captures those existed only for *polynomial* `r`
(`kovacic_case1_poly_r`, gated to `degd == 0`); for rational `r` with genuine poles
it was skipped.

**Fix — `kovacic_case1_general` (`src/calculus/dsolve_kovacic.c`), the classical
Case 1 for arbitrary rational `r`:**
- locates the poles as the roots of `Denominator[r]` (via `dsolve_analyze_roots`, so
  **complex** conjugate pairs are handled), with local exponents
  `α_c^{±} = (1 ± √(1+4 b_c))/2`, `b_c = lim_{x→c}(x−c)² r`;
- builds `θ = Σ_c α_c^{s_c}/(x−c)` per sign mask and a monic `P` of the classical
  degree `d = α_∞^{±} − Σ_c α_c^{s_c}` solving `P'' + 2θP' + (θ'+θ²−r)P == 0`; the
  degree is tested **numerically** (`N[…]`) so complex-α combinations reject instantly
  instead of a per-mask symbolic `Simplify` that took minutes;
- assembles the second solution at the **y-level** (`y2 = y1 ∫ w²/y1² dx`, reduction
  of order on the original ODE) so the recovery radical `w` cancels up front — the
  z-level `z1 ∫ 1/z1²` multiplies `√(x²−1)` into the `ArcTanh` answer and sends
  `Simplify` into a multi-second blow-up (Gegenbauer went 17 s → 0.1 s);
- picks the cleanest first solution (smallest `LeafCount` → the orthogonal
  polynomial) among the sign masks; every candidate is exact by construction
  (`dsolve_run` verifies as the backstop).

Now `DSolve` returns the elementary closed form for Legendre `n=1..5`, Chebyshev,
Gegenbauer, Jacobi, and complex-pole analogues, all in < 0.5 s. `Solve[…, {}]` (empty
variable list) in the monic-`P` solve is short-circuited in `solve_ansatz`, removing a
spurious `Solve::ivar` message.

**Case-2 hang guard.** The Chebyshev equation (and e.g. `(x³+1)y'' + x y' + y == 0`)
used to **hang** in Kovacic Case 2: after Case 1 declined, Case 2's rational-σ
undetermined-coefficient search handed `Solve` a large coupled system over a
degree-≥2 (complex-pole) denominator factor and ran for minutes. Case 2 is now
**skipped when any irreducible denominator factor has degree ≥ 2** — those Liouvillian
solutions are already covered by the general Case 1, and the input otherwise declines
to the series fallback instead of hanging. Tests: 6 new cases in `tests/test_dsolve.c`
(Legendre 1/2, Chebyshev, complex poles, auto-closed-form, no-hang); all DSolve suites
(incl. the m5 Case-2 stress) pass.

## DSolve — OperatorFactor / DFactor (linear-operator factoring)

`DSolve`OperatorFactor` solves a homogeneous linear ODE of order ≥ 3 by **factoring
its differential operator**, and `DSolve`DFactor` exposes the factorization. This
closes the last `[ ]` item in §1c of `DSOLVE_PLAN.md` — the genuinely-new capability
beyond the existing cascade, since `Kovacic` only handles 2nd order, so
variable-coefficient order-≥3 operators that factor previously fell through to the
Frobenius series fallback.

The core primitive is the **first-order right factor** `(D − r)`, `r ∈ C(x)`:
`(D − r)` right-divides `L` iff `y = Exp[∫r]` solves `L[y] == 0` (a hyperexponential
solution), iff the Riccati residual `R(r) = Σ aₖ Pₖ(r)` vanishes (`Pₖ` the Bell
polynomials, `P₀=1`, `P_{k+1}=Pₖ'+r Pₖ`). The method:
- **finds** a rational `r` by an undetermined-coefficient search over a pole/degree-
  bounded ansatz (poles from `FactorList[Denominator[…]]`, simple poles first, low
  polynomial degree), solving the coefficient system with `Solve` and testing the
  exact division remainder for each branch;
- **peels** it via operator right-division to the order-(n−1) quotient
  (`q_{n-1}=aₙ`, `q_{m-1}=aₘ+Σ C(j,m) D^(j-m)[r] q_j`);
- **recurses** `DSolve` on the quotient (which the whole cascade — const-coeff, Euler,
  Kovacic, or a further peel — may solve), then closes with the trailing first-order
  linear solve `(D − r)y == z`, its constant `C[kk]` measured to stay contiguous with
  the quotient's `C[1..n-1]`.

```
In[1]:= DSolve[(x-1)^3 y'''[x] - 7(x-1)^2 y''[x] + 18(x-1) y'[x] - 18 y[x] == 0, y[x], x]
        (* shifted-Euler at x=1 — EulerCauchy only detects the pole at 0, so this is
           OperatorFactor's niche; returns a 3-constant general solution *)

In[2]:= DSolve`DFactor[y'''[x] - 6 y''[x] + 11 y'[x] - 6 y[x] == 0, y[x], x]
Out[2]= {Dx - 1, Dx - 2, Dx - 3}
```

- **Cascade slot / scope.** Runs after `Kovacic` (which owns order 2 and whose Case 1
  is the same rational-factor search), before the reduction/series methods; guarded
  to order ≥ 3, homogeneous, coefficients rational-in-`x` with numeric constants.
  Its unique reach is reducible variable-coefficient operators the earlier methods
  miss (shifted-Euler at a pole ≠ 0, mixed reducible spectra). Finds first-order
  **right** factors only — an operator whose only factorization has an irreducible
  ≥ 2 right factor, or whose reduction integrals are non-elementary (distinct-pole
  compositions produce dilogarithms), declines (no wrong answer; the substrate
  back-substitution is the backstop). Deferred: inhomogeneous forcing, irregular-
  singular (double-pole) `r`, and 2nd-order right factors (Beke).
- **`DSolve`DFactor`** returns the ordered first-order factors as `{Dx − r_i}` (inert
  `Dx`); a not-fully-reducible operator appends an inert remainder operator
  `Σ q_j Dx^j`. Works at any order ≥ 1.
- **Zero regression risk.** The file is self-contained — it reuses only the shared
  `ds_*` substrate and front-end builtins and makes **no** changes to
  `dsolve_kovacic.c` (the small ansatz/search overlap is duplicated deliberately).
- **New file** `src/calculus/dsolve_operator_factor.c` (both builtins + the shared
  `of_find_factor` / `of_divide` core); wired into the scalar cascade and the pinned
  `Method -> "OperatorFactor"` in `dsolve.c`.
- **Tests.** `tests/test_dsolve.c` — `t_method_operfactor` (shifted-Euler flagship),
  `t_operfactor_more` (constant order 3 & 4, resonant repeated factor), `t_operfactor_ivp`,
  `t_operfactor_declines` (Airy-type + order-2 guard), `t_dfactor` (reconstruct the
  operator from the factors), `t_operfactor_auto`. `tests/test_dsolve_stress.c` —
  `operfactor_ok` / `dfactor_ok` forward generators composing `(D − r_i)` over
  all-constant, shifted-Euler, resonant, and Euler families (each back-substituted /
  reconstructed).

Gates: 3/3 dsolve ctest targets green (incl. the Kovacic/M5 stress suite — confirming
zero regression); `make check-c99` exit 0; valgrind shows **no per-call leak** on
both the OperatorFactor and DFactor paths (1× and 6× the same call both = 13,440 B
definitely + 6,312 B indirectly, the one-time DSolve engine baseline).

## DSolve — ExactODE (higher-order exact linear equations)

`DSolve`ExactODE` solves a linear ODE of order ≥ 2 whose left side is a **total
derivative** — `L[y] = Σ aₖ(x) y⁽ᵏ⁾ == g(x)` with `L[y] == d/dx(M[y])` for an
order-(n−1) operator `M`. Such an equation is *exact* and integrates once to the
**first integral** `M[y] == Integrate[g, x] + C[n]`, a lower-order ODE handed back
to the scalar cascade. This is the first of the two `[ ]` §1c items in
`DSOLVE_PLAN.md` (the other, `OperatorFactor`/`DFactor`, remains future work).

The first-integral coefficients follow from matching
`Σ aₖ y⁽ᵏ⁾ = d/dx(Σ bⱼ y⁽ʲ⁾)`: `b_{n-1} = a_n`, `b_{k-1} = a_k − b_k'`, and the
exactness condition is the leftover `a_0 == b_0'` (equivalently
`Σ(−1)ᵏ aₖ⁽ᵏ⁾ == 0`). The order-(n−1) sub-solve emits `C[1..n-1]` and the
integration constant is `C[n]` — contiguous, no renumbering. Iterated exactness
is free: the recursion re-enters `ExactODE` on the reduced equation, so a
doubly-exact 3rd-order equation reduces twice.

```
In[1]:= DSolve[x y''[x] + y'[x] == 0, y[x], x]
Out[1]= {{y[x] -> C[1] + C[2] Log[x]}}

In[2]:= DSolve[x y''[x] + y'[x] == x, y[x], x]          (* forcing folded in *)
Out[2]= {{y[x] -> C[1] + x^2/4 + C[2] Log[x]}}

In[3]:= DSolve[x y'''[x] + y''[x] == 0, y[x], x]         (* order-2 reduction *)
Out[3]= {{y[x] -> C[1] + (C[2] - C[3]) x + C[3] x Log[x]}}
```

- **Placement / scope.** Runs after `EulerCauchy` (cleaner constants there) and
  before the special-function / Kovacic / series machinery (a cheap deterministic
  reduction to an elementary lower-order equation is preferred over a
  special-function or series answer). The reference Airy, Bessel, Euler-Cauchy and
  Kovacic equations are all **not** exact (`a₀ − b₀' ≠ 0`), so their pinned tests
  keep their methods. First cut is linear, order ≥ 2, genuinely exact
  (first-order exact `M + N y' == 0` is `DSolve`Exact`, excluded by the order ≥ 2
  guard); a non-exact equation or a non-elementary `∫g` declines. Integrating-
  factor (adjoint) exactness and nonlinear total-derivative detection are future.
- **Verification.** The substrate back-substitutes the reduced solution into the
  *original* order-n residual; since it satisfies `M[y] == ∫g + C[n]` and
  `L[y] = d/dx(M[y])`, `L[body] − g` vanishes for elementary bodies (a buggy
  reduction is dropped, a messy-but-correct one is kept).
- **New file** `src/calculus/dsolve_exactode.c` (three-function contract, mirrors
  `dsolve_reduce_order.c`: recurse into `DSolve` on the reduced equation, reuse
  the `extract_applied` idiom); wired into the scalar cascade and the pinned
  `Method -> "ExactODE"` / `DSolve`ExactODE` in `dsolve.c`.
- **Tests.** `tests/test_dsolve.c` — `t_method_exactode`, `t_exactode_more`
  (2nd-order + inhomogeneous + 3rd-order), `t_exactode_declines` (non-exact +
  first-order stay symbolic), `t_exactode_auto`. `tests/test_dsolve_stress.c` — an

## DSolve — Kummer / Gauss hypergeometric recognizers

`DSolve\`SpecialFunctionForm` now recognises the two flagship classical
second-order linear families, extending the Airy/Bessel table:

- **Kummer (confluent hypergeometric, ₁F₁)** — `x y'' + (b−x) y' − a y == 0`
  → `C[1] Hypergeometric1F1[a,b,x] + C[2] x^(1−b) Hypergeometric1F1[a−b+1,2−b,x]`.
  `a`, `b` are read directly (`b = x(P+1)`, `a = −x Q`, both free of `x`).
- **Gauss (hypergeometric, ₂F₁)** — `x(1−x) y'' + (c−(a+b+1)x) y' − a b y == 0`
  → `C[1] Hypergeometric2F1[a,b,c,x] + C[2] x^(1−c) Hypergeometric2F1[a−c+1,b−c+1,2−c,x]`.
  `c` and `a+b`, `ab` are read off `x(1−x)P` (linear) and `x(1−x)Q` (constant);
  `a`, `b` are the roots of `t² − (a+b) t + ab`, recovered radical-free from the
  quadratic's linear factors (`FactorList`), so a symbolic equation returns clean
  `2F1[a,b,c,x]` rather than a `Sqrt[(a−b)²]` form.

```
In[1]:= DSolve[x y''[x] + (3/2 - x) y'[x] - 2 y[x] == 0, y[x], x]
Out[1]= {{y[x] -> C[1] HypergeometricPFQ[{2}, {3/2}, x]
                 + C[2] HypergeometricPFQ[{3/2}, {1/2}, x] / Sqrt[x]}}

In[2]:= DSolve[x (1-x) y''[x] + (1/2 - (a+b+1) x) y'[x] - a b y[x] == 0, y[x], x]
Out[2]= {{y[x] -> C[1] HypergeometricPFQ[{a, b}, {1/2}, x]
                 + C[2] Sqrt[x] HypergeometricPFQ[{1/2+a, 1/2+b}, {3/2}, x]}}
```

- **Verifies for free.** `Hypergeometric1F1`/`2F1` auto-rewrite to
  `HypergeometricPFQ`, which carries a `deriv.c` z-derivative rule, so the emitted
  branches back-substitute through the substrate's verifier (kept as structurally
  exact, like Airy/Bessel — the residual is a contiguous-relation identity
  zero_test does not discharge symbolically, and the permissive "keep unless
  decidably non-zero" rule keeps it).
- **Scope / declines.** The `x^(1−b)`/`x^(1−c)` second solution is emitted only
  when the exponent parameter (`b` resp. `c`) is a **non-integer number**: an
  integer makes the two solutions dependent (or the pFq lower parameter singular),
  and a *symbolic* exponent makes the verify residual a symbolic-power + pFq sum
  on which `zero_test` currently hangs. Both cases decline to the Frobenius series
  fallback (no wrong answer). The other parameters (`a` for Kummer; `a, b` for
  Gauss) may stay symbolic. The first cut also requires the canonical singular
  points (0 for Kummer; 0 and 1 for Gauss); affine/scaled variants decline.
- **Tests.** `tests/test_dsolve.c` adds pinned + auto-cascade + symbolic-`a`
  (Kummer) / symbolic-`a,b` (Gauss) + integer-decline cases;
  `tests/test_dsolve_m5_stress.c` adds forward-generator families over
  half-integer exponents (all back-substitute to zero). Leak-clean (the recognizer
  and its quadratic-root helper add no allocations; valgrind shows only the
  pre-existing Simplify/engine baseline).

## DSolve — Lagrange singular solutions

`DSolve\`Lagrange` now returns the **singular-line solutions** of
`y = x·φ(y') + ψ(y')` under `IncludeSingularSolutions -> True`. These are the
straight lines `y = p₀·x + ψ(p₀)` for each root `p₀` of the envelope condition

the parametric general branch:

```
In[1]:= DSolve[y[x] == x (y'[x])^2 + (y'[x])^3, y, x, IncludeSingularSolutions -> True]
Out[1]= {{x -> Function[{t}, …], y -> Function[{t}, …]},   (* general, parametric *)
         {y -> Function[{x}, 0]}, {y -> Function[{x}, 1 + x]}}   (* singular lines *)
```

- **Heterogeneous output** — a branch is either the parametric pair or an explicit
  `{y -> Function[{x}, line]}`. `dsolve_lagrange_try` emits singular lines in a new

## DSolve — Chini + Abel (1a), implicit first integrals

`DSolve` now solves the Chini equation `y' == f(x) y^n + g(x) y + h(x)`
(n∉{0,1,2}; n=2 is Riccati) and the first-kind Abel equation
`y' == f3 y^3 + f2 y^2 + f1 y + f0` — the last `[ ]` recognizers in §1a of
`DSOLVE_PLAN.md`. This closes the first-order family (bar the deferred
Lagrange singular/IVP work).

General Abel/Chini equations have no closed form; the **reducible-to-autonomous**
sub-class does. The scaling `y = φ·u` with `φ = f^(−1/(n−1))` makes the `y^n`
coefficient 1, giving `u' = u^n + B u + C` with `B = g + f'/((n−1)f)`,
`C = h·f^(1/(n−1))`; when **B, C are free of x** the equation is autonomous, and
since `1/(u^n+Bu+C)` is a rational function of u its antiderivative is elementary.
The solution is the **implicit first integral**

```
∫ du/(u^n + B u + C) − x == C[1],   u = y·f^(1/(n−1)),
```

returned through `dsolve_run_implicit` as `{{G(x,y[x]) == C[1]}}`. Back-substituting
`y' = −G_x/G_y` reproduces the ODE exactly. **Abel** reduces to Chini n=3 by
removing the y² term (`z = y + f2/(3 f3)`), so it is a thin front-end over the
shared reduction.

```
In[1]:= DSolve[y'[x] == x^2 y[x]^3 - y[x]/x + 1/x, y, x]
Out[1]= {{-x + ArcTan[(-1 + 2 x y[x])/Sqrt[3]]/Sqrt[3]
          - 1/6 Log[1 + x^2 y[x]^2 - x y[x]] + 1/3 Log[1 + x y[x]] == C[1]}}
```

- **New files** `src/calculus/dsolve_chini.c` (shared non-static
  `dsolve_chini_first_integral`, Bernoulli-style extraction of `f,g,h,n` with a
  reconstruct-and-reject of any non-`{y^n,y,1}` RHS, decline of n∈{0,1,2}) and
  `src/calculus/dsolve_abel.c` (Taylor-style cubic extraction `f0..f3`, require
  f3≠0 ∧ f2≠0, remove y², call the shared helper with `z = y[x] + f2/(3 f3)`). Both
  wired via `dsolve_method_builtin_implicit`.
- **Cascade slot** (`dsolve.c`): after `Riccati` (n=2), via `dsolve_run_implicit`.
  Pinned `Method -> "Chini"` / `"Abel"`. Earlier methods still claim their forms
  (Bernoulli/separable for the h=0 / autonomous cases).
- **Note:** the assembled G is *not* `Simplify`'d — `Simplify` hangs on a composed
  `Log`/`ArcTan` with radical arguments (`Sqrt[x]·(y+1)`), and the relation is
  correct unsimplified (the implicit verifier differentiates it).
- **Tests:** `t_method_chini` / `t_chini_more` (n=3,4; radical reduction; decline
  boundaries) / `t_method_abel` in `tests/test_dsolve.c`, verified by implicit
  differentiation; a `chini_ok(f,n,B,C)` forward generator (reducible by
  construction) + an Abel case driving `t_stress_chini` in
  `tests/test_dsolve_stress.c`.

Coverage is the reducible-to-autonomous class (B,C free of x); non-reducible
equations decline (honest — they generally have no closed form). The fuller
constant-invariant class (with an x-rescaling) is future work. Gates: 3/3 dsolve
ctest targets green; `make check-c99` clean; valgrind shows **no per-call leak**
(1× and 6× both = 13,440 + 6,312 bytes, the one-time engine baseline).

## DSolve — Lagrange / d'Alembert (1a), parametric general solution

`DSolve` now solves the Lagrange (d'Alembert) equation
`y == x·φ(y') + ψ(y')` (with `φ(y') ≠ y'`, the Clairaut case) — the last cheap
first-order recognizer in §1a. Its general solution is **intrinsically
parametric**: with the slope `p = y'` as the parameter `t`,

```
x = X(t, C),   y = X(t, C)·φ(t) + ψ(t),
```

where `X(t)` solves the linear first-order ODE obtained by differentiating the
equation w.r.t. `x` and reading `x` as a function of `p`:
`dx/dt − [φ'(t)/(t−φ(t))]·x = ψ'(t)/(t−φ(t))`. The integrating factor almost
always introduces transcendental/fractional terms, so there is generically no
explicit `y(x)` — hence a new parametric output shape.

```
In[1]:= DSolve[y[x] == 2 x y'[x] + (y'[x])^2, y, x]
Out[1]= {{x -> Function[{t}, (C[1] - 2/3 t^3)/t^2],
          y -> Function[{t}, (2 C[1] - 1/3 t^3)/t]}}
```

- **New parametric substrate path** (`dsolve_common.{c,h}`), mirroring the
  implicit path: `dsolve_run_parametric` + `dsolve_verify_parametric` +
  `dsolve_assemble_parametric` + `dsolve_method_builtin_parametric`. The try-fn
  returns the branch as the wrapper `DSolve\`Param[X, Y, t]`; verification
  substitutes `x→X`, `y[x]→Y`, `y'[x]→D[Y,t]/D[X,t]` into the residual and requires
  it not be decidably non-zero (permissive, with a `PossibleZeroQ` fallback for
  transcendental `X,Y` — same policy as the implicit/Bessel cases). Output is
  `{{x -> Function[{t}, X], y -> Function[{t}, Y]}}`. An IVP (`ncond > 0`) is
  **declined** rather than silently ignoring the condition (parametric fitting is
  future work). The parameter `t` is a collision-safe bare symbol (first of
  `{t,s,u,w,r,q}` not in the equation).
- **New file** `src/calculus/dsolve_lagrange.c`. Recognition mirrors
  `dsolve_clairaut.c` (solve the algebraic residual for `Yexpr`, then
  `φ = D[Yexpr,x]` free of `x`, `ψ = Yexpr − x·φ` free of `x`/`Y`); declines the
  Clairaut case `φ≡p` and — new guard — a genuinely **linear** equation
  (`φ` constant and `ψ` affine in `p`, owned by `LinearFirstOrder`). The linear ODE
  for `X(t)` is solved with the existing `dsolve_linear_factor_solve` (declines on a
  non-elementary integral); `Y = X·φ + ψ`.
- **Cascade slot** (`dsolve.c`): right after `Clairaut` (its `φ≡p` special case,
  which claims first), via `dsolve_run_parametric`. Pinned `Method -> "Lagrange"` /
  `DSolve\`Lagrange`. Over-claiming is prevented by the `φ,ψ`-free-of-`x` guard plus
  cascade order (all cheaper first-order methods precede it).
- **Tests:** `t_method_lagrange` / `t_lagrange_more` (rational + transcendental
  forms + automatic dispatch) / `t_lagrange_declines` (Clairaut, linear, and the
  deferred-IVP boundaries) in `tests/test_dsolve.c`, verified parametrically
  (`y' = Y'(t)/X'(t)`); a `lagrange_ok` forward generator (`φ=2p`, `3p/2` with
  polynomial `ψ`) driving `t_stress_lagrange` in `tests/test_dsolve_stress.c`.

Gates: 3/3 dsolve ctest targets green; `make check-c99` clean; valgrind shows **no
per-call leak** on the parametric path (1× and 6× the solve both = 13,440 bytes
definitely + 6,312 indirectly, the one-time engine baseline). This closes the
Lagrange item in §1a (singular solutions + parametric IVP-fitting remain future).

## DSolve — Riccati (1a)

`DSolve` now solves the Riccati equation `y'[x] == q0(x) + q1(x) y + q2(x) y^2`
(`q2 ≠ 0`), completing the named first-order family (§1a of `DSOLVE_PLAN.md`) bar
Lagrange/Abel/Chini. The method reuses the M5 2nd-order linear engine almost
entirely: the classical substitution `y = -u'/(q2 u)` linearises the equation to

```
u'' - (q1 + q2'/q2) u' + (q0 q2) u == 0,
```

which is handed back to the scalar cascade (const-coeff / Euler / Airy-Bessel
`SpecialFunctionForm` / Kovacic / — last — a Frobenius series). The recovered `u`
is mapped back through `y = -u'/(q2 u)`. Because the general Riccati solution
depends only on the ratio `C[1]:C[2]`, `C[2]` is collapsed to 1, leaving the single
arbitrary constant `C[1]` (the standard one-parameter parametrisation). When the
linearisation has no closed form the recursion declines and Riccati declines — the
substrate's back-substitution verify is the backstop (permissive: an undecidable
special-function residual is kept, as for Bessel/Kovacic).

```
In[1]:= DSolve[y'[x] == y[x]^2 + x, y, x]              (* linearises to the Airy eqn *)
Out[1]= {{y -> Function[{x}, -((-1)^(1/3) (AiryBiPrime[(-1)^(1/3) x]
          + C[1] AiryAiPrime[(-1)^(1/3) x]))/(AiryBi[(-1)^(1/3) x]
          + C[1] AiryAi[(-1)^(1/3) x]))]}}
In[2]:= DSolve[y'[x] == 2 - 3 y[x] + y[x]^2, y[x], x]
Out[2]= {{y[x] -> -3/2 + 1/2 Tanh[1/24 (-C[1] - 12 x)]}}
```

- **New file** `src/calculus/dsolve_riccati.c` (three-function contract:
  `dsolve_riccati_try` + `builtin_dsolve_riccati` via `dsolve_method_builtin` +
  `dsolve_riccati_init`, `ATTR_PROTECTED` + docstring). Mirrors
  `dsolve_bernoulli.c` (nonlinear-coefficient extraction: `q0 = FY|_{Y=0}`,
  `q1 = FY_Y|_{Y=0}`, `q2 = FY_YY/2`, with a reconstruct-check that rejects any
  non-quadratic nonlinearity and a `q2 ≠ 0` guard so a linear equation is left to
  the earlier methods) and `dsolve_reduce_order.c` (recurse into the scalar engine
  by building `DSolve[u''…==0, u[x], x]`, evaluating, and extracting the body).
- **Cascade slot** (`dsolve.c`): after `FirstOrderSubstitution`, before
  `AutonomousReduction`, so cheaper/cleaner first-order methods claim their forms
  first — notably `fos`, which keeps its clean `-x-Tan[…]` for `y'==(a x+b y+c)^2`
  (also a Riccati, but with an uglier linearisation). Also a pinned
  `Method -> "Riccati"` / `DSolve\`Riccati` entry.
- **Tests:** `t_method_riccati` / `t_riccati_more` (incl. the Airy-linearised
  `y'==y²+x`, the variable-coefficient `y'==x+x y²`, and the linear-declines
  boundary) / `t_ivp_riccati` in `tests/test_dsolve.c`; a `riccati_ok` from-spectrum
  forward generator (`y' == r1 r2 + (r1+r2) y + y²`, elementary/decidable) driving
  `t_stress_riccati` in `tests/test_dsolve_stress.c`.

Gates: 3/3 dsolve ctest targets green; `make check-c99` clean; valgrind shows **no
per-call leak** on the Riccati path (1× and 6× the elementary solve both =
13,440 bytes definitely + 6,312 indirectly, the one-time engine baseline).

## DSolve — implicit first-integral solutions (transcendental homogeneous)

The transcendental homogeneous family — `y'==F(y/x)` whose separable integral is
non-invertible (an ArcTan log-spiral, e.g. `y'==(x+y)/(x-y)`) — previously
declined because DSolve only produced explicit `y[x] -> body` solutions. It now
returns the **implicit first integral** as the solution branch:

```
In[1]:= DSolve[y'[x] == (x + y[x])/(x - y[x]), y, x]
Out[1]= {{-Log[x] + ArcTan[y[x]/x] - 1/2 Log[1 + y[x]^2/x^2] == C[1]}}
```

- **New parallel substrate path** (`dsolve_common.c`): `dsolve_run_implicit`
  (+ `dsolve_method_builtin_implicit`). A try-function on this path returns the
  left-hand side `G` of the general integral `G == C[1]`. Verification is by
  **implicit differentiation**: from `d/dx[G == C] = 0` the ODE forces
  `y' == -G_x/G_y`; substituting that into the residual and requiring it not be
  decidably non-zero (`dsolve_verify_implicit`, the same permissive policy as the
  explicit `dsolve_verify_body`). An initial condition `y[x0]==y0` fits the
  constant as `G(x0,y0)` (`dsolve_implicit_rhs`). Output is
  `{{ G(x,y[x]) == C[1] }}` — an `Equal` branch, not a `y[x] ->` rule.
- **`dsolve_homogeneous_implicit_try`** (`dsolve_homogeneous.c`) builds
  `G = (Integrate[1/(F(v)-v), v] /. v -> y[x]/x) - Log[x]`. It runs *after* the
  explicit Homogeneous method (explicit `y[x] -> …` is preferred whenever the
  inversion exists), both in the automatic cascade (a late fallback, before the
  series methods) and as the pinned `DSolve`Homogeneous` fallback.
- Because the branch is an equation, it is verified in tests by implicit
  differentiation (`D[eq[[1]]-eq[[2]], x] /. y'[x] -> rhs` must vanish), not by
  the `residual /. rule` idiom. New `t_homogeneous_implicit` (unit, incl. IVP fit
  + pinned) and `t_stress_homogeneous_implicit` (five transcendental forms).

Gates: 3/3 dsolve ctest targets green; `make check-c99` clean; valgrind shows no
per-call leak on the implicit path (1× and 6× the transcendental solve both =
13,440 bytes definitely + 6,312 indirectly, the one-time engine baseline). This
closes the last honest Homogeneous gap flagged in `DSOLVE_PLAN.md`.

## DSolve — Homogeneous & ReductionOfOrder: two decline gaps closed

Two first-order/second-order methods declined on whole families they should
handle; both are now solved, verified by back-substitution.

- **`DSolve`Homogeneous`** now inverts the pure-log (real-root) rational family.
  The separable relation `Integrate[1/(F(v)-v), v] == Log[x] + C[1]` was solved
  only when `Solve` could invert the log form directly; for a sum of logs it
  could not (`y'==(x+2y)/(2x+y)` declined). New fallback `homog_exp_log_invert`
  (`dsolve_homogeneous.c`): exponentiate the antiderivative
  (`E^intV //. {E^(a+b):>E^a E^b, E^(c Log[g]):>g^c}`) to the algebraic relation
  `Prod g_i(v)^{c_i} == C[1] x`, clear fractional exponents by raising to a small
  power `d ∈ {1,2,3,4,6}` (`PowerExpand`), then `Solve` — which returns explicit
  `Root` branches. The per-branch verify in `dsolve_run` keeps the genuine sheets
  and drops any spurious root from the exponentiation. The transcendental (ArcTan)
  subset (`y'==(x+y)/(x-y)`, a log-spiral) has no explicit inverse and still
  declines. Now solves `(x+2y)/(2x+y)`, `(2x+y)/(x+2y)`, `(x+3y)/(3x+y)`, ….
- **`DSolve`ReductionOfOrder`** now accepts a correct-but-unsimplified
  antiderivative. The `D[Integrate[p,x], x] == p` guard used `zero_test_decide`,
  which cannot reduce e.g. the multi-`Log` form of `Integrate[Tan[x+C[1]]]` or
  `1/(C[1](1+x^2/C[1]))` from `Integrate[1/(C[1]+x^2)]` to zero, so
  `y''==1+(y')^2` and `y''==-2x(y')^2` declined even though the first-order
  sub-solve succeeded. The guard now falls back to `PossibleZeroQ` (numeric
  sampling, as the derivative-divides integrator gates its own antiderivatives); a
  genuinely wrong antiderivative (`Integrate -> 0`) still fails as `-p != 0`, and
  the final back-substitution verify is the backstop. Opens the autonomous
  `a+b(y')^2` (→ Tan/Tanh) and Riccati-in-`p` `c x (y')^2` families.

## ReadProtected attribute removed system-wide

Mathilda is fully open source and never hides a symbol's definition, so the
`ReadProtected` attribute has been removed entirely. The flag
(`ATTR_READPROTECTED`, bit 11 of `attr.h`) is gone, `SetAttributes`/`Attributes`
no longer recognise or emit `ReadProtected` (`attr.c`, `SYM_ReadProtected`

(historical changelogs left as-is).

## DSolve — no longer HoldAll

`DSolve` (and every `DSolve`<Method>`) dropped `HoldAll`; attributes are now
`Protected`, matching Mathematica. HoldAll was unnecessary — with
the dependent function undefined, `y'[x] == a Sin[x]` and point conditions
`y[0] == 5` evaluate to unevaluated `Equal[...]` on their own, so equations reach
the solver formal without holding, and the `D[...]`→`Derivative[...]` fold happens
under normal evaluation. It was also harmful: HoldAll made an equation stored in a
variable (`eq = y'[x] + y[x] == a Sin[x]; DSolve[eq, y, x]`) come through as the
bare symbol `eq` and decline; that now solves. Guarded by `t_not_holdall`.

## DSolve — FirstOrderSubstitution (1a) and AutonomousReduction (1d)

### `DSolve`FirstOrderSubstitution` — `y'[x] == F(a x + b y + c)`

The solved-for-`y'` companion to `Homogeneous`: fires when the RHS depends on
`x` and `y` only through one linear combination — a form no earlier first-order
method (linear / separable / homogeneous / exact) recognises. Writing the RHS as
`F(x, Y)` (`Y` a plain symbol for `y[x]`), the level curves are the straight
lines of constant combination, so `F` is a function of that combination iff the
ratio `r = F_x / F_y` is constant. With `v = y + r x`,

```
v' = y' + r = F + r = H(v) + r,   H(W) := F(x, W - r x)  (free of x),
```

an autonomous separable equation solved inline by `Integrate[1/(r + H), W] == x
+ C[1]`, solved for `W = v`, then `y = v - r x`. The ratio is collapsed with
`Simplify` before the substitution (it must be textually free of `Y`), so a
proved-constant ratio that `Simplify` cannot reduce is declined rather than
corrupted.

```
In[1]:= DSolve[y'[x] == (x + y[x])^2, y[x], x]
Out[1]= {{y[x] -> -x - Tan[-C[1] - x]}}

In[2]:= DSolve[y'[x] == (2 y[x] - x)^2, y[x], x]        (* combination 2y - x, r = -1/2 *)
Out[2]= {{y[x] -> x/2 - Tanh[Sqrt[2] (C[1] + x)]/(2 Sqrt[2])}}
```

Cases whose separated antiderivative `Solve` cannot invert (e.g.
`y' == Sqrt[x+y]`, `y' == (x+2y)^3`) stay symbolic rather than shipping an
implicit/wrong answer.

### `DSolve`AutonomousReduction` — `y''[x] == f(y, y')` missing `x`

The nonlinear-higher-order case where `x` is absent. Regarding `p = y'` as a
function of `y`, `y'' = p p'(y)`, so the equation becomes the first-order ODE
`p p'(y) == f(y, p)`, solved by recursing into the scalar cascade; then
`y' == P(y)` (also autonomous, hence separable) is solved by a second recursion.
The two integration constants are kept distinct across the recursions (the first
stage's `C[1]` is frozen to a private marker and renamed `C[2]` afterward). A
degenerate `y = const` — which trivially satisfies any autonomous equation and
would pass back-substitution (cf. the M4 wrong-`Integrate` lesson) — is rejected
by requiring the final body to depend on `x`.

Runs after the linear methods, so genuinely linear autonomous equations
(`y'' == -y`, …) are claimed by the cleaner method first; this one catches the
nonlinear remainder:

```
In[3]:= DSolve[y[x] y''[x] == y'[x]^2, y[x], x]
Out[3]= {{y[x] -> C[1] E^(C[2] x)}}

In[4]:= DSolve[y[x] y''[x] == 2 y'[x]^2, y[x], x]
Out[4]= {{y[x] -> 1/(C[1] - C[2] x)}}
```

Non-elementary / elliptic reductions (`y'' == 2 y^3`, `y'' == -Sin[y]`) stay
symbolic.

### Substrate / cascade

Both methods follow the three-function contract (`_try` + `builtin_` via
`dsolve_method_builtin` + `_init`) with `ATTR_PROTECTED` and
docstrings; appended to the automatic cascade after
`ReductionOfOrder` and to the `Method ->` dispatch, callable as
`DSolve`FirstOrderSubstitution[...]` / `DSolve`AutonomousReduction[...]`.

Tests (`tests/test_dsolve.c`): per-method unit cases (specific closed forms,

## DSolve — general linear systems (M8): defective / singular / triangular

`DSolve` now solves coupled first-order linear systems in full generality, closing
`DSolve[{y'[t] + 1 == 1, x'[t] + y[t] == 0}, {y[t], x[t]}, t]`, which previously
returned unevaluated because its matrix `A = {{0,0},{-1,0}}` is **defective** (one
Jordan block, eigenvalue 0 doubled) **and** singular — the old eigen-only
`LinearFirstOrderSystem` declined on the zero eigenvector, and `DecoupleSystem`
declined because the second equation mentions two functions.

- **`LinearFirstOrderSystem` reworked around the fundamental matrix** `Φ = e^{Ax}`
  for *any* constant `A` (`dsolve_linsys.c`). `Φ = S · e^{Jx} · S^{-1}` from
  `JordanDecomposition[A]`, with `e^{Jx} = e^{Dx} · e^{Nx}`, `e^{Dx} =
  DiagonalMatrix[Exp[λ_i x]]`, and `e^{Nx} = Σ_{m<n} N^m x^m/m!` (finite — `N`
  nilpotent). Homogeneous `Y = Φ · {C[1..n]}`; forcing `b(x)` by variation of
  parameters `Φ·(C + ∫Φ^{-1} b dx)`, which subsumes the old `-A^{-1}b` and stays
  valid when `A` is singular. Complex spectra collapse to real `e^{αx}Cos/Sin[βx]`;
  a repeated real eigenvalue's `Simplify`-preferred `(Cosh+Sinh)^2` is folded back
  to `E^{λx}` by a `Cosh[a]+Sinh[a] -> E^a` rewrite. Symbolic `MatrixExp` is inert,
  so `Φ` is built from Jordan directly.
- **New `DSolve`TriangularSystem`** (`dsolve_triangular.c`): forward substitution
  over a DAG dependency graph — peel an equation isolating one unsolved function,
  solve it with the scalar engine, substitute forward, renumber. Reaches
  coupled-but-triangular systems at **any** coefficient (constant or variable,
  e.g. `{y'==y/x, z'==y}`) that the constant-`A` matrix exponential cannot. Solved
  constants are parked in the private head `DSolve`sysK` during the peel so they do
  not collide with the scalar engine's fresh `C[k]`, then remapped to a contiguous
  `C[1..]` at the end.
- Cascade for `nfun>1` is now `DecoupleSystem → TriangularSystem →
  LinearFirstOrderSystem`. Shared `dsolve_renumber_constants` /
  `dsolve_extract_system_body` factored into `dsolve_common.c` (used by both
  system methods). The only remaining systems gap is genuinely coupled,
  non-triangular, *variable*-coefficient `A` (Floquet/Magnus — future).

Tests (`tests/test_dsolve.c`): `t_sys_defective_singular`,
`t_sys_defective_nontriangular`, `t_sys_triangular_varcoeff`,
`t_sys_singular_forcing`, `t_sys_triangular_ivp` — Head-is-`List` (non-vacuous)
plus back-substitution to zero. Gates: `dsolve_tests` green, `make check-c99`
clean, valgrind shows no definitely-lost delta over the scalar-DSolve baseline.

## DSolve — M5: 2nd-order linear variable-coefficient (NormalForm + Kovacic + Frobenius/PowerSeries)

Second-order linear ODEs `y'' + P(x) y' + Q(x) y == 0` now have closed-form and
series solvers, closing the gap where only `SpecialFunctionForm` (Airy/Bessel)
applied. Three new files, all wired into the scalar cascade in `dsolve.c`.

- **`DSolve`NormalForm`** (`dsolve_normalform.c` + substrate helpers
  `dsolve_second_order_PQ` / `dsolve_normal_form` in `dsolve_common.c`).
  `DSolve`NormalForm[eqn, y, x]` returns `{r, w}`: the substitution `y == w z`
  with `w == Exp[-Integrate[P/2]]` reduces the equation to `z'' == r z`,
  `r == P²/4 + P'/2 − Q`. The `∫P/2` integral is guarded (`D[∫] == P/2`).
  `dsolve_second_order_PQ` (the normalized `P = c₁/c₂`, `Q = c₀/c₂` extractor)
  is now the single source of truth, reused by `SpecialFunctionForm` too.

- **`DSolve`Kovacic`** (`dsolve_kovacic.c`) — Liouvillian solutions of
  `z'' == r z` (`r ∈ C(x)`, gated by `PolynomialQ`). Built on a
  mathematically-transparent **Riccati/undetermined-coefficient** search rather
  than the classical exponent tables (elementary answers are back-substitution
  verified, so a wrong candidate is dropped, never shipped):
  - **Case 1** — `ω' + ω² == r` with `ω` a polynomial part (degree from the
    order of `r` at ∞) plus a principal part over the irreducible factors of the
    denominator; `Solve` the coefficient system, `z1 == Exp[∫ω]`,
    `z2 == z1 ∫ 1/z1²`. Solves `z''=(1+x²)z → Exp[x²/2]`, `z''=(2/x²)z → x², 1/x`.
  - **Case 1b (apparent singularities)** — for polynomial `r`, `z == P Exp[∫ω_base]`
    with `ω_base` the polynomial part of `±√r` and `P` a polynomial of the
    determined degree `d = −[R₂]_{m−1}/(2c_m)` solving `P''+2ω_base P'+R₂P == 0`.
    Captures e.g. `z''=(x²+3)z → x Exp[x²/2]` (root of `P` at a point that is not
    a pole of `r`).
  - **Case 2 (degree-2 algebraic)** — a rational `σ = ω₁+ω₂` solving
    `D'+2σD == 0`, `D = 4r−2σ'−σ²`, gives `ω = (σ ± √D)/2`. Because the residual
    is not symbolically decidable, each candidate is **numerically**
    back-substituted (both basis solutions, several points) before it is returned.
    Solves `z''=(x/4+5/(16x²))z → x^(−1/4) Exp[±x^(3/2)/3]`.
  - **Case 3** (degree 4/6/12) declines. Cascade slot: after `SpecialFunctionForm`,
    before `ReductionOfOrder` (closed form preferred over reduction/series).

- **`DSolve`FrobeniusSeries` / `DSolve`PowerSeries`** (`dsolve_frobenius.c`) — the
  always-available series fallback, tried **last** in the cascade, expanding about
  `x == 0`. Ordinary point → two power series (recurrence
  `a_{n+2} = −[Σ p_k(n−k+1)a_{n−k+1} + Σ q_k a_{n−k}]/((n+2)(n+1))`); regular
  singular → Frobenius `x^s Σ a_n x^n` with the indicial quadratic
  `s(s−1)+p₀s+q₀ == 0` (reusing `dsolve_analyze_roots`), the root difference
  selecting the sub-case (non-integer → two series; equal roots → a `Log`
  solution via `∂/∂s`; obstructed positive-integer difference declines). Output is
  a truncated `SeriesData`; the `x^r` factor is carried by `x^r · SeriesData` so
  the O-term makes the back-substituted residual `O[x]^k` (which is why the
  solution verifies rather than being dropped).

**Substrate change:** `dsolve_verify_body` now back-substitutes each derivative
term as `Derivative[k][y][x] → D[body, {x,k}]` (and `y[x] → body`) directly,
instead of `y → Function[{x}, body]`. This is equivalent for elementary bodies
but essential for a `SeriesData` body, whose pure-function derivative
`Derivative[k][Function[{x}, SeriesData]][x]` the evaluator returns as `0` (a
pre-existing limitation), which would otherwise drop every valid series solution.

**Tests:** 14 new unit tests in `tests/test_dsolve.c` and a new
`tests/test_dsolve_m5_stress.c` (ctest-registered) — a Kovacic forward generator
(pick `ω`, feed `r = ω'+ω²`, so a Liouvillian solution is guaranteed) across
polynomial / apparent-singularity / genuine-pole / Euler families, plus a
Frobenius ordinary-point family; each asserts `Head === List` then a
back-substitution to zero (or `O[x]^k` for series). Gates: `dsolve_tests` and
`dsolve_m5_stress_tests` green, `make check-c99` clean, valgrind shows no
definitely-lost delta over the Integrate/Solve/Simplify engine baseline.

## TimeConstrained — per-call memory leak fixed (root of the "Integrate engine" leak)

`TimeConstrained[body, t, fail]` leaked its evaluated body **on every normal
(non-timeout) call** — the `evaluate()`-borrows-its-argument contract was violated
in two spots in `builtin_time_constrained` (`src/core.c`):

- the time-budget parse did `evaluate(expr_copy(time_arg))` and never freed the
  anonymous copy → now the `eval_and_free(expr_copy(time_arg))` idiom;
- the guarded body ran `tc_run_guarded(expr_copy(expr_arg))`, whose `evaluate(body)`
  borrows `body` and returns a fresh tree; nothing freed `body` on the success path
  (the code comment only accounted for the deliberate siglongjmp leak on the
  *timeout* path). The copy is now held in a named `body` local and freed by the
  caller after the timer is disarmed and `tc_jmp_env` restored — safe against an
  in-flight SIGPROF. On the timeout path `body` is still (deliberately) left for the
  documented bounded leak.

This was the **root cause of the pre-existing "Integrate engine per-call leak"**:
the `Integrate` Automatic cascade's Goursat stage wraps every attempt in
`TimeConstrained[…]`, so **every** `Integrate[]` (and every DSolve method that
integrates — `LinearFirstOrder`, `AlmostLinear`, …) inherited the leak (~728 B tree
+ ~56 B/call). After the fix `Integrate[Exp[x] Sin[x], x]`, DSolve `AlmostLinear`,
and `TimeConstrained[Expand[…], t, $Failed]` are all flat at the leak-free baseline
across a 1×-vs-6× valgrind diff (def 13,440 B / indir 6,312 B, unchanged).

Also fixed a sibling instance of the same `evaluate(expr_copy(…))` anti-pattern in
`integrate_goursat.c` (`combine_radicals` on the square-root pseudo-elliptic path).

Correctness unchanged: `time_constrained_tests`, `integrate_goursat_tests`,
`integrate_dispatch_tests`, `integrals_tests`, `dsolve_tests`,
`integrate_jeffrey_tests`, `integrate_risch_transcendental_tests` all green; the
timeout / Infinity / non-positive-budget / symbolic-failexpr paths verified;
valgrind shows zero Invalid-free/read/write on all paths including timeout.

Known residual (separate, pre-existing, ~56 B/call): a single bare node is orphaned
whenever the Goursat stage's nested `TimeConstrained` `evaluate()` runs inside an
enclosing Integrate whose earlier `try_rational` populated the eval memo — a subtle
interaction with the GROUND fixed-point epoch, not an ownership bug in
`TimeConstrained`. Left for a focused follow-up in the eval-memo machinery.

## Apart — two-argument form now decomposes radicals of the given variable

`Apart[expr, x]` (explicit variable) now applies the same algebraic-generator
substitution the one-argument form already used, so it agrees with `Apart[expr]`
whenever the rational function is built from a radical/fractional power of `x`.

Previously:

```
Apart[1/((Sqrt[x] + 2) (Sqrt[x] + 3)), x]   (* -> 1/(6 + 5 Sqrt[x] + x)  -- WRONG *)
Apart[1/((Sqrt[x] + 2) (Sqrt[x] + 3))]      (* -> 1/(2 + Sqrt[x]) - 1/(3 + Sqrt[x]) *)
```

The two-argument form fell through to `Together`, and the follow-up
`PolynomialQ[D, x]` guard failed (the denominator carries `Sqrt[x] = x^(1/2)`,
not polynomial in `x`), so it returned the recombined single fraction instead of
the partial-fraction decomposition.

**Fix** (`src/parfrac.c`, `apart_impl`). The algebraic-generator pass — detect a
generator `g = u^(1/m)`, substitute `g -> fresh symbol`, run `Apart` in that
symbol, back-substitute — was gated on `apart_argc == 1`. It now also runs for
the two-argument form, but only when the detected generator is a genuine radical
of the requested variable itself (`base == var`, `atom == 1`); the recursion pins
the decomposition variable to the fresh generator so it is not swayed by any
other symbol present. A radical of a *different* symbol
(`Apart[1/((Sqrt[y]+2)(x+3)), x]`) is still treated as an opaque constant in `x`,
and plain-rational / `Extension` behaviour is unchanged.

Both forms now return `1/(2 + Sqrt[x]) - 1/(3 + Sqrt[x])`; the radical +
`Extension -> Sqrt[2]` combination composes correctly. New regression test
`test_apart_radical_of_variable` in `tests/test_parfrac.c` locks in the exact
forms, recombination-to-zero, and the different-symbol non-substitution.
`parfrac_tests`, `extension_options_tests`, `extension_auto_builtins_tests`,
`radical_polyops_tests`, `intrat_tests`, `intrat_corpus_tests`, `simplify_tests`
all green; valgrind shows no new leaks (def 13,440 B / indir 6,312 B — identical
to the startup baseline).
