# Changelog: week of 2026-09-21 (Mon) – 2026-09-27 (Sun)

## PossibleZeroQ — structural non-zero certificate: `-E^(-a x)` no longer a false positive (v0.204)

`PossibleZeroQ[-E^(-a x)]` returned `True` — a wrong answer: `-e^{-ax}` is nowhere zero.
The expression has free symbols, so it reached the Schwartz–Zippel sampler, where the
exponent `-a x` reaches `~10^3` at the sampler's moderate `|sample|` range — every point
drives `E` into IEEE over/underflow, so the residual read as `0` at each and the value was
mistaken for an identity (the decay false positive logged in
`POSSIBLE_ZEROQ_IMPROVEMENTS.md`).

- **Fix (algorithmic, sound):** a new **structural non-zero certificate** (`provably_nonzero`,
  Stage 0b in `src/zero_test.c`) run right after the structural stage and *before* the guards
  that route to sampling. It proves an expression is not identically zero — decided `FALSE`
  with no numeric work — using the fact that the exponential is entire and has no zeros
  (`E^z ≠ 0` for all `z`): certified are a finite non-zero literal, a known non-zero constant,
  `Exp[_]`/`Power[E, _]`, `Power[b, _]` with `b` itself certified (`b ≠ 0 ⇒ b^e ≠ 0`), and
  `Times[…]` of certified factors. It fires in both the plain and the assumption-aware cores;
  being unconditional (`E^z` has no zeros for any `z`), its `FALSE` is sound under any
  `Assumptions`.
- **Soundness:** the certificate never fires on anything that can vanish (`Plus`, a
  possibly-zero or possibly-infinite base, a bare symbol are all excluded), so no identity is
  affected — every genuine zero still decides `True`. Confirmed: `Sin[x]^2+Cos[x]^2-1`,
  `E^x - E^x`, the denest/log/Euler/Machin identities all unchanged; `-E^(-a x)`, `E^x`,
  `3 E^(x+y)`, `2^n`, `(E^x)^y`, `3 + I y` now decide `False`.
- **Tests:** new Group 17 in `tests/test_zero_test.c` (7 cases). Full `zero_test`,
  `possiblezeroq_*`, `trigexp_zero`, and the dependent `simplify`/`fullsimplify`/`radical_simplify`/
  `trigrat`/`sum_rational`/`intrat`/`series`/`solve`/`limit`/`rat` suites pass with no
  regressions. (`dsolve_tests` has one pre-existing `SpecialFunctionForm` assertion,
  independent of this change — it fails identically on the prior `zero_test.c`.)
- **Book:** §4.2 "Is it zero?" updated — the `-E^(-a x)` example, which showcased the false
  positive, now demonstrates the certificate recognising a non-vanishing exponential; the
  Pitfall reframed around the heuristic nature of a `True` and Richardson undecidability.

## Refine — soundness fix in the assumption zero test, plus seven new assumption rewrites (v0.203)

A first-principles stress corpus of 159 `Refine` cases (every documented surface, plus
adversarial soundness/robustness probes) drove one soundness fix and a batch of missing-feature
fixes. Corpus result went from 137/159 to 151/159 passing, with **zero wrong answers** remaining
(the 8 open cases all return the input unchanged — missing reductions, never incorrect ones).

- **Soundness: assumption-aware zero test no longer returns a wrong `False` under an equality
  fact.** `zero_test_decide_assuming`'s Schwartz–Zippel sampler (`src/zero_test.c`) draws each
  symbol independently from its own single-variable region, so it silently ignored any *coupling*
  fact — an equality between variables, or a membership of a compound. It then sampled points the
  assumptions exclude and reported a genuine identity as non-zero: `Refine[a == b, a - b == 0]`
  gave `False`, and even `Refine[a == b, a == b]` gave `False`; `PossibleZeroQ[a - b,
  Assumptions -> a - b == 0]` gave `False`. The sampler now downgrades a `False` verdict to
  `Unknown` whenever a ctx fact touching the expression's symbols is an equality/compound membership
  it cannot honour. Inequalities (`a > b`) are unaffected — they carve out a full-measure region on
  which "identically zero" is unchanged, so their `False` stays sound. `True` verdicts are never
  affected. This repairs `PossibleZeroQ` as well as `Refine`.
- **`Refine` decides `Equal`/`Unequal` under equality assumptions.** The `Equal` branch
  (`src/refine.c`) now, when the zero test is inconclusive, rewrites the difference under the
  assumptions (the same substitution that already makes `Refine[a - b, a == b]` give `0`) and
  checks it is unconditionally zero — so `Refine[a == b, a - b == 0]`, `Refine[a^2 == b^2, a == b]`
  → `True`, while `Refine[a == b, a > b]` → `False`.
- **Sign domains as queried membership.** `element_decide` (`src/simp/simp_builtins.c`) now decides
  `Element[x, Positive|Negative|NonNegative|NonPositive]` via the sign provers, so
  `Refine[Element[x, Positive], x > 0]` and `Refine[Element[k^2, NonNegative], Element[k, Reals]]`
  → `True`. `Element` and `Assuming` benefit too.
- **NonPositive rewrites.** A symbol assumed `x <= 0` (not only strict `x < 0`) now reduces
  `Sqrt[x^2] -> -x`, `Abs[x] -> -x`, `(x^2)^r -> (-x)^(2r)`.
- **`Arg` under a sign fact.** `Arg[x] -> 0` for `x > 0`, `Arg[x] -> Pi` for `x < 0`.
- **`Abs` of a complex expression with real parts.** `Abs[a + b I] -> Sqrt[a^2 + b^2]` (real
  `a, b`), via the same all-symbols-real `ComplexExpand` pass that already handled `Re`/`Im`/
  `Conjugate`/`Arg`.
- **Log identities.** For real `x`: `Log[x^2] -> 2 Log[Abs[x]]`, `Log[E^x] -> x`. For positive
  factors: `Log[x rest] -> Log[x] + Log[rest]`.
- **Robustness: rule synthesis restricted to symbols the target uses.** `apply_assumption_rules`
  (`src/simp/simp_assume_rewrite.c`) now prunes each per-symbol rule bucket to the symbols that
  actually occur in the input, before building the 8192-byte rule string. Previously, ~16+ assumed
  symbols overflowed the buffer (driven by the O(n²) pairwise-positive rules) and silently dropped
  *every* rule, so `Refine[Abs[a1], a1 > 0 && … && a20 > 0]` returned `Abs[a1]` unchanged; it now
  gives `a1`. This also removes wasted rule generation in the common case.
- **Tests.** `tests/test_refine.c` gains `test_stress_fixes` (24 assertions) covering all of the
  above; the `PossibleZeroQ`, `Simplify`, `Element`, and `Assuming` suites are unchanged (no
  regressions from the shared-engine changes).
- **Known follow-ups (return input unchanged, never wrong):** integer-linear trig arguments
  (`Exp[2 Pi I k]`, `Cos[2 k Pi]`, `Sin[(2k+1) Pi/2]`), `Element[Sqrt[2], Algebraics]`, deep
  positivity for non-strict/compound-real bases (`Abs[(x-1)^2]`, `Sqrt[(x-1)^2]`), the `> 6`-variable
  CAD ceiling, and `Sign` of an exact algebraic zero.

## Graphs: structural predicates + `TopologicalSort`; `RandomGraph` leak fixed (v0.202)

Nine new graph heads, all linear-time over the existing `GraphAdj`/`GraphVIdx` substrate
(`src/graph/graphprops.c`, `membership.c`, `acyclic.c`). Each `*Q` predicate gives `False` for a
non-graph. Return types are Booleans or vertex lists, so no packed/`Compile` surface applies.

- **`UndirectedGraphQ`, `EmptyGraphQ`** — all edges undirected (edgeless graphs included) / no edges.
- **`CompleteGraphQ[g]`, `CompleteGraphQ[g, vlist]`** — every ordered pair of distinct vertices
  joined in that direction (directed graphs need both `u->v` and `v->u`); the 2-argument form tests
  the induced subgraph.
- **`BipartiteGraphQ`** — 2-colouring of the underlying undirected graph.
- **`VertexQ`, `EdgeQ`** — SameQ membership; `EdgeQ` accepts `->`/`<->` sugar, matches undirected
  edges in either orientation, and never blurs direction.
- **`AcyclicGraphQ`** — exact for undirected (forest), directed (DAG) *and mixed* graphs, by
  contracting undirected components and running Kahn on the contraction. `1->2, 2->1` is a cycle.
- **`TreeGraphQ`** — connected, `>= 1` vertex, `n - 1` edges, direction ignored.
- **`TopologicalSort[g]` / `TopologicalSort[{rules}]`** — Kahn with a min-heap, so ties go to the
  vertex earliest in `VertexList`; unevaluated for a cyclic graph or one with an undirected edge.
- **`DirectedGraphQ` fix** — an edgeless graph is now `False` (Wolfram: "the empty graphs are
  undirected"), so it and `UndirectedGraphQ` are never both `True`.
- **Validated-graph memo + per-graph caches** (`graph_util.c`). Every accessor used to re-validate
  its graph from scratch (`O(V + E)`), so an `O(1)` question like `VertexQ` cost ~6 ms on a
  100000-vertex graph. The memo keeps the last 4 validated graph nodes, holding a reference to each
  (which is what makes pointer keying sound), along with their vertex index, edge-key set and
  endpoint indices. `Graph[...]` seeds it at construction; lookups become `O(1)`; adjacency is now
  a single CSR block built without hashing. The four algorithmic heads cache their answers on the
  graph, as Mathematica's atomic `Graph` does.
- **`Graph` construction 1.6x faster** (40000 edges: 5.1 ms → 3.2 ms; Mathematica 4.1 ms). A valid
  graph is detected as a fixed point up front instead of being rebuilt and `expr_eq`-compared. Each
  vertex is hashed once rather than twice, with the index handed to the memo. Already-normalized
  edges are shared rather than rebuilt, and rebuilt edges share one head-symbol node instead of
  interning 40000.
- **Benchmarks** — new `benchmarks/92-graph-predicates` (Mathilda / Mathematica 15.0 / networkx
  3.6), warm and cold cases, all check values agreeing. Cold (fresh graph per call, construction
  untimed): `AcyclicGraphQ` 0.85 ms vs 1.8 ms (Mathematica) vs 41 ms (networkx); `TopologicalSort`
  1.7 / 2.0 / 40 ms; `BipartiteGraphQ` 0.92 / 265 / 24 ms; `TreeGraphQ` 0.25 / 0.66 / 10.8 ms;
  every lookup head at clock resolution in all three.
- **`RandomGraph` leak fixed** — `generators.c` assumed `evaluate()` consumes its argument; it does
  not, so every call leaked its whole `O(n^2)` candidate-edge list (~364 KB at `n = 50`, previously
  documented as a known limitation). `leaks --atExit` now reports 0 leaks for `RandomGraph` and for
  all the new heads. Seeded output is unchanged.

## Refine — new builtin (v0.197)

Added `Refine[expr, assum]` / `Refine[expr]` (`src/refine.c`), a thin orchestrator
over the shared assumption engine that gives the form `expr` would take if its
symbols satisfied `assum`. It is `Protected`, registered in the symbol table, has
an `Information` string (`src/info.c`) and `SYM_Refine` interned in
`src/sym_names.c`, and options `Assumptions -> $Assumptions` and
`TimeConstraint -> 30`. Argument/option semantics mirror `PossibleZeroQ`/`Simplify`
exactly (an `Assumptions ->` option replaces `$Assumptions`; a positional
assumption is `And`-combined with it).

`Refine` delegates rewrites to `apply_assumption_rules` and predicate decisions to
`element_decide` (now exported), the assumption-aware zero test, and the
`Reduce`/CAD entailment (`P` is `True` iff `assum && !P` is unsatisfiable over the
reals; `TimeConstraint` bounds each check via `Simplify`'s cooperative wall-clock
budget, never the async `TimeConstrained`). A `Refine`-local deep-positivity pass
resolves `Sign[p]`/`Abs[p]`/`Sqrt[p^2]` for symbolic polynomials the fast prover
cannot settle (e.g. `Sign[x^2 - x y + y^2 + 1] -> 1`).

To reach full parity the **shared** engine was extended (so `Simplify` benefits
too):
- `simp_assume.c` — `prov_re`/`prov_int` now cover `Gamma`/`Factorial`/`LogGamma`/
  `Pochhammer` of positive arguments, `Floor`/`Ceiling`/`Round`/`IntegerPart` of a
  real as integer, and `int^(nonneg-int)` with a symbolic exponent; a bare symbol
  appearing algebraically in an inequality assumption is now taken as real.
- `simp_assume_rewrite.c` — new rule families (`(x^m)^r` for `x >= 0`, `(a^b)^c`
  for `-1 < b < 1`, `a^p b^p -> (a b)^p`, `Log[x] -> I Pi + Log[-x]` for `x < 0`,
  `Cos/Sin[x + k Pi]`, `Tan[x + k Pi]`) plus a structural post-pass handling
  `Floor`/`Ceiling`/`Round`/`IntegerPart`/`FractionalPart`, `Mod` from an
  `Element[(a+c)/m, Integers]` fact, `Re`/`Im`/`Conjugate`/`Arg` of real-symbol
  expressions (via `ComplexExpand`), and `ArcTan[Tan[x]]` on the principal domain.

Every example in the `Refine` specification reproduces. Extensive unit tests in
`tests/test_refine.c`; the `simp`/`fullsimplify`/`element`/`possiblezeroq`/`reduce`
suites and corpora are unchanged (no regressions), and the Refine paths are
valgrind-clean (no leaks over the baseline). `Refine` is purely symbolic, so it
carries no packed/NDArray kernel or `Compile[]` lowering by design.

## Association overhaul — atomicity, Part, ordering, operator forms, new heads (v0.198–v0.201)

This work addresses the audit in `reports/association/`. The Mathematica 15 differential battery (271 cases) now matches on 250 cases, up from 211, with no regressions. (The four development streams below were authored as v0.197–v0.200; they rebase onto main's Refine v0.197 and land here as the single merge release **v0.201**.)

  - A table-driven operator-form mechanism (`src/opform.c`) gives 43 heads their curried forms, e.g. `Lookup[k][a]`, `Select[p][x]`, `GroupBy[f][l]` and `Map[f][x]`.

  - `AssociationQ` requires well-formed entries.
  - `==`/`!=` compare associations.

  - `KeyTake` keeps the requested order.
  - Multi-level `GroupBy`.
  - `Append`/`Prepend` move an existing key.
  - `Catenate` takes the values.
  - `Partition` stays unevaluated.
  - `Pick` accepts an association mask.
  - `RuleDelayed` survives a rebuild.
- **v0.201: new heads and threading.**
  - New heads: `KeyIntersection`, `KeyComplement`, `MissingQ`, `Discard`, `CountDistinct`, `CountDistinctBy`, `SubsetQ`, `JoinAcross` (all join types), `ApplyTo`, `AssociationComap` and `Splice`.
  - `Keys`/`Values` take a function and thread over lists.
  - `KeyUnion` fills missing keys.
  - `AssociationMap` and `PositionIndex` work on associations.
  - `Merge` accepts rule lists, and `Association` accepts nested rule lists.
  - `Normal` reaches nested associations, and `Transpose` works on associations.
  - Listable heads thread over association values (`<|a->1|> + 1`), and `Total`/`Mean` work on lists of associations.
  - `Key` and `Missing` are documented.

## Factor — decline instead of returning a wrong answer on an uncombined fraction (v0.196)

`Factor` combines its argument over a common denominator (`Together`), then
factors `Numerator`/`Denominator` as polynomials. `Together` deliberately
**declines** to combine a sum of fractions whose numerators share two or more
dependent trigonometric/hyperbolic kernels over `Q(i)` (a GCD-blow-up guard,
correctness-preserving — it leaves the expression uncombined). But `Factor` then
factored that *uncombined* numerator — a `Plus` still carrying `Power[linear,-1]`
denominators — as if it were a polynomial, treating `1/(x - I)` as an
indeterminate and returning a **non-equivalent** result. Concretely

```
Factor[(-1/2*I) (Cosh[x] + Sinh[x])/(-I + x) + (1/2*I) (Cosh[x] + Sinh[x])/(I + x)]
```

collapsed to `0`, and because `Simplify` offers `Factor`/`TrigFactor` as
transforms and trusts them to be equivalence-preserving, this silently poisoned
`Simplify`/`FullSimplify` — e.g. `D[Integrate[Exp[x]/(x^2+1), x], x] // Simplify`
returned `0` instead of `E^x/(1 + x^2)` (reported bug).

**Fix.** `builtin_factor` now checks that the `Numerator`/`Denominator` it
derived from `Together` are genuinely denominator-free before feeding them to the
polynomial factorer (`factor_has_leftover_denominator`, a recursive scan for a
`Power[symbol|compound, negative]`). When a leftover denominator is present —
i.e. `Together` under-combined — `Factor` returns the input unchanged (correct,
if not maximally combined) rather than a false factorisation. This is a general
equivalence guard: it converts wrong answers to safe no-ops for *any* input
`Together` cannot fully combine, and never touches the well-combined cases
(polynomials, rationals, single-trig, symbol sums, real-denominator sums, `f[x]
+ g[x]`, Gaussian-integer polynomials all factor exactly as before). The
underlying `Together` capability gap (not combining ≥2-dependent-trig numerators
over `Q(i)`) is left as a separate follow-up; the guard makes it harmless.

## DownValues / OwnValues — return held rules, not live ones (v0.194)

`DownValues[f]` and `OwnValues[f]` returned each stored rule as a bare, evaluable
`Rule[lhs, rhs]`. Because the returned list is itself evaluated, the left-hand side
(e.g. `f[x_]`) re-matched its own definition and fired: a recursive definition blew the
recursion limit when merely queried, and a right-hand side such as `RandomInteger[...]`
was re-evaluated afresh on every query.

**Root cause.** `rules_to_list` (`src/core.c`) emitted `Rule[expr_copy(pattern),
expr_copy(replacement)]` — no `HoldPattern` around the pattern, and `Rule` (immediate)
rather than `RuleDelayed`.

**Fix.** Each rule is now returned as `HoldPattern[lhs] :> rhs`: the `HoldPattern`
(HoldAll) keeps the pattern from re-matching and `RuleDelayed` (HoldRest) keeps the
right-hand side unevaluated, so the returned list is inert. This matches Mathematica,
which displays values as `{HoldPattern[lhs] :> rhs}`. `OwnValues` shares the same helper
and is fixed by the same change.

## Factor / Simplify — soundness: binomial descent no longer misreads non-monomial terms (v0.193)

`Factor[Cos[r^2] - r^2]` returned the mathematically wrong `-(-1 + r) (1 + r)`, and,
because `Simplify` runs `Factor` as a candidate transformation and keeps the shortest
form, `Simplify[Laplacian[Sin[r^2], {r, t}, "Polar"]]` collapsed the correct
`4 Cos[r^2] - 4 r^2 Sin[r^2]` to the wrong `4 - 4 r^2`.

**Root cause.** The heuristic two-term `a^k ± b^k` factoriser (`factor_binomial` in
`src/poly/facpoly_simple.inc`) parses each term of the `Plus` into a monomial via
`extract_monomial`. The inner walk correctly returns `false` for an opaque term
(`Cos[r^2]`, `r^2 Sin[r^2]`, a generic `f[r^2]`), but the `extract_monomial` wrapper had
a `void` return and discarded that flag, leaving the term looking like the bare constant
`1` (coefficient 1, zero variables). `factor_binomial` then applied the genuine
difference-of-squares identity to `1^2 - r^2` and returned `(1 - r)(1 + r)`.

**Fix.** `extract_monomial` now returns `bool`, and `factor_binomial` bails to `NULL`
(leaving the input unfactored) unless *both* terms parse as genuine polynomial monomials.
Legitimate binomials (`x^4 - y^4`, `8 a^3 - 27 b^3`, `x^6 + y^6`, `Sin[x]^2 - 1`) are
unaffected — both terms parse, so the descent runs exactly as before.

## Integrate — `ParallelMixedTower`: keep nested radicals fused on genus-0 conics — global branch fidelity (v0.192)

`Integrate[Sqrt[x + Sqrt[x]], x, Method -> "ParallelMixedTower"]` returned
`1/4 Log[x^(1/4) + Sqrt[1 + Sqrt[x]]] + 1/12 Sqrt[1 + Sqrt[x]] (-3 x^(1/4) + 2 x^(3/4) + 8 x^(5/4))`,
a correct antiderivative **only for x > 0**. Its derivative agrees with the integrand on
the positive reals but not off them (e.g. at `x = -1/2` or `x = 2 + I`), because the tower
builder had split the integrand's own nested radical.

**Root cause.** `BuildTower`'s `rootNormalize` (`src/internal/mixed/ParallelMixed.m`) pulled
any squarefree factor that is itself a generator out from under a root — for
`Sqrt[Sqrt[x] (1 + Sqrt[x])]` it split off `Sqrt[Sqrt[x]] = x^(1/4)`, leaving
`Sqrt[1 + Sqrt[x]]`. That is the identity `Sqrt[a b] = Sqrt[a] Sqrt[b]`, valid only for
`a, b > 0`, so the whole tower (generator `x^(1/4)`, radical `y^2 = 1 + Sqrt[x]`) — and thus
the surface answer — was faithful only on `x > 0`. The numeric verify-or-decline gate samples
only positive-real rationals, where the split identity holds, so it could not catch the
defect.

**Fix.** The pure-generator-factor split is branch-unsafe, so it now runs **only when it is
needed** to reduce the radicand to a handled curve: when a simple radical already exists
(keeping the factor fused would demand a second radical), or when the fused squarefree
radicand is not yet a genus-0 conic (total degree ≥ 3 in the generators, so pulling a linear
generator factor lowers the genus — e.g. the cubic `Sqrt[2 t (1 + t^2)] → Sqrt[2] Sqrt[t]
Sqrt[1 + t^2]` still splits). When the fused radicand is already a genus-0 conic (total
degree ≤ 2), it serves directly as the simple radical `y^2 = q`, and keeping it fused makes
the back-substitution `y → Sqrt[q]` globally faithful. `Sqrt[x + Sqrt[x]]` now integrates to
`1/8 Log[1/2 + Sqrt[x] + Sqrt[Sqrt[x] + x]] + 1/12 Sqrt[Sqrt[x] + x] (-3 + 2 Sqrt[x] + 8 x)`,
whose derivative equals the integrand at negative and complex points too.

**Validation.** New regression case in `tests/test_parallelmixedtower.c` asserts the result is
free of `x^(1/4)` and diff-backs to the integrand at the complex point `x = 2 + I`. Charlwood
corpus unchanged at 48/50 (A19, A39 still open) with zero regressions; only two cases (P9,
A35) change output form, both to the fused radical and both still verified. Integrate unit
suite green. `v0.192`.

## Integrate — Goursat stage moved to the end of the cascade; pseudo-elliptic grind gates (v0.191)

Reordered the `Integrate[f, x]` Automatic cascade so `Integrate`GoursatAlgebraic`
(pseudo-elliptic `F/R^p`) runs **last**, after `Integrate`ParallelMixedTower`,
instead of at its former early position — every general method now gets first
crack at any integrand it also handles, and Goursat is the deterministic
specialist that closes what they leave. The explicit
`Method -> "GoursatAlgebraic"` / `"ParallelMixedTower"` surfaces are unchanged.

Moving Goursat to the end exposed a pre-existing performance trap: the general
*search* stages that now run ahead of it grind for tens of seconds on
pseudo-elliptic integrands (which only Goursat closes) before declining. The
grind was masked before because Goursat used to short-circuit these integrands
first. Fixed with a shared, cheap structural gate — an integrand carrying a
fractional power of a degree-≥3 polynomial in `x` (`has_pseudoelliptic_radical`)
— applied to the three offenders:

- **`try_linearity`** — its product-over-sum (`c·(g+h)`) distribution branch no
  longer fires on such integrands (splitting a shared `Sqrt`/odd-root of a
  cubic+ shreds it into individually non-elementary elliptic pieces).
- **`try_derivdivides`** — routes them to the direct-quotient-only entry point
  (`integrate_derivdivides_try`) instead of the full Eliminate/Solve
  branch-search; the genuine derivative-divides folds (`x^2/(x^3-1)^(1/3)`, …)
  still close via the direct pass.
- **`ParallelMixedTower`** — skipped in the *cascade* for these (its tower
  search over a genus>0 algebraic curve only grinds before declining); the
  explicit `Method` surface still runs it fully.

Net effect: `(x-1)/((x+2) Sqrt[x^3-1])` (period-3), its cyclotomic sibling, and
`(x^4+2x^3-4)/(x^2 Sqrt[(x^2-1)(x^2-4)])` went from an effective hang / ~45 s to
~0.07 s, with identical closed-form answers. All 14 affected integrate test
suites (`integrate_goursat`, `integrate_dispatch`, `integrate_derivdivides`,
`parallelmixedtower`, …) pass. Files: `src/calculus/integrate.c`.

- **Fix:** a persistent per-node symbol-set cache. A new `symset_cache` field on the Expr

- **Cost:** one pointer per node — `sizeof(Expr)` 56 → 64 (a deliberate memory-for-speed trade;

- **Verified:** A28 4.44 s → 3.15 s (~29 %); Charlwood direct-method tail (9 heavy cases) 21.7 s →

## RowReduce: FLINT exact-rational fast path for "OneStepRowReduction" (v0.186)

`rowreduce_divfree` (the default `RowReduce` method) has long taken a FLINT `fmpq_mat_rref` fast
path for a pure-rational matrix, but `rowreduce_onestep` (`Method -> "OneStepRowReduction"`) did
not — it always ran the Expr-level division-free Gauss-Jordan. The reduced row echelon form is
unique, so this was pure lost time whenever a caller asked for `"OneStepRowReduction"` over a
rational system. The ParallelMixedTower ansatz does exactly that on its `alg=False` rungs (it
selects `"OneStepRowReduction"` because it is far faster on the AlgebraicNumber systems of the
algebraic rungs), so Charlwood **A1** — a 311×152 **rational** system — was reducing by the Expr

## Orderless canonicalisation: per-sort symbol-set memo — faster large algebraic sorts (v0.185)

Profiling the Charlwood parallel-mixed integrals showed that essentially all of the time in the
arithmetic-bound cases (e.g. A28, ~4.9 s) was in **one C function**: `collect_symbols_in`
(`src/sort.c`). `expr_compare`'s polynomial-degree tier walks *both* operands to collect their
symbols on *every* pairwise comparison, so canonically ordering an *n*-argument `Orderless` head
(`Plus`/`Times`) re-walks each argument's whole subtree `O(log n)` times — and the arguments in an
algebraic residue computation are large. This is the cost the Maxima port's own profile names as
`RATREP*`/canonical re-entry (`rn-radicals-maxima.pdf` §3).

- **Fix.** `expr_orderless_sort` installs a per-sort memo (`sort.c`) that caches each node's symbol
  set by identity for the duration of one sort — during which the sorted arguments and their
  subexpressions are immutable and never freed — so each distinct subtree is walked at most once.
  The memo only ever *caches* `collect_symbols_in`; the resulting canonical order is byte-for-byte
  identical (verified by a differential run with the memo disabled). The symbol arrays live in a
  bump **arena** (a per-node `malloc` made the memo a net loss on the common many-small-term sort),
  and a cheap **size gate** engages the memo only when an argument's subtree is large, so ordinary
  small `Plus`/`Times` take the plain path with zero added overhead.
- **Wiring.** `builtin_plus`/`builtin_times` (their collapsed-output sort), `eval_sort_args`, and the
  evaluator's generic `Orderless` sort all route through `expr_orderless_sort`. A `sort_abort_reset()`
  at the `TimeConstrained` `siglongjmp` recovery (`core.c`) drops any memo left installed by an
  unwind so a later comparison never dereferences it. `MATHILDA_NO_SYMMEMO=1` disables the memo
  (A/B measurement / bisection).
- **Effect.** ~16 % faster on the heaviest arithmetic-bound Charlwood case (A28, in-process A/B
  4.90 s → 4.11 s); no regression on many-small-term sums (size-gated); all Charlwood cases still
  solve and numerically verify. General: any workload that canonically orders large algebraic
  `Plus`/`Times` benefits. Value-identical (differential-tested); `sort`, `expand`, `eval`,
  `evaluate`, `expandfrac`, `parallelmixedtower`, `rootreduce` suites unchanged.

## ToNumberField: fix uninitialised-tail free in the compositum builder (v0.184)

`flint_qqbar_to_number_field_common` (the multi-atom `ToNumberField[{a0,…}]` primitive-element
builder, `src/poly/flint_qqbar.c`) allocated its `items` result array with `malloc` and filled it in
a loop that stops at the first field-membership miss (`for (i=0; i<n && good; i++)`). On that
error path the cleanup freed **every** non-NULL entry across all `n` slots — including the
**uninitialised tail** `items[j+1 … n-1]` that the early exit never wrote — so it called
`expr_free` on wild pointers. Under AddressSanitizer this was a hard SEGV in `expr_free`; in a
normal build it silently corrupted the heap, surfacing much later as **non-deterministic wrong
numeric values** in a long-running process that had earlier hit a `ToNumberField` membership miss
(found via an ASan hunt of a 50-integral batch run).

- Fix: `calloc` the array so unwritten slots are `NULL` and the cleanup skips them (matching the
  correct `built`-counter pattern already used by `list_in_field`). The sibling arrays
  (`minpoly_slot_expr`, the integral-basis builder, `poly_to_algnum` padding) were audited and are
  safe (counter-tracked or fully filled).
- Effect: ASan-clean on the batch run (the `expr_free` SEGV is gone); no behaviour change on any
  correctly-constructed field (`rootreduce`, `nf_rowreduce`, `nullspace`, `parallelmixedtower`
  suites unchanged). This was a genuine memory-safety bug on the `ToNumberField` error path.

## ParallelMixedTower: fourth-root-of-unity branch gate — solves Charlwood A35 (v0.183)

The verify-or-decline soundness gate (`src/internal/mixed/ParallelMixed.m`) pins the branch of the
formal radical `y` (`y² = q`), which the method maps back as the principal `Sqrt[q]`. It previously
accepted only a **real** sign: `D[surf] == +f` (return `surf`), `== -f` (return `-surf`), or a `±f`
branch-cut flip. But when `q` is negative on the real domain, `Sqrt[q] = I·Sqrt[-q]` leaves the
surface off by a factor of `I` — `D[surf] == -I·f` for Charlwood A35 — which the gate rejected as
"verification failed".

- The gate now pins the branch to a **fourth root of unity** `u ∈ {1, -1, I, -I}`: it finds the exact
  unit with `D[surf] == u·f` at every real sample and returns `surf/u` (`= Conjugate[u]·surf`).
  Soundness is unchanged — acceptance still requires `D[surf]` to equal `u·f` *exactly* (to 1e-12) at
  every finite real sample for a single unit `u`; a genuinely wrong surface matches none. The `±f`
  branch-cut case (A34) is retained.
- **Solves Charlwood A35** (`√(√(Sec+1) − √(Sec−1))`, ~1.3 s, `u = -I`); A11 (`u = -1`) and A34
  (branch cut) still solve and verify. Charlwood direct-method: **48/50**. (Implementation note: the
  unit search uses a `Do` loop with `Slot` predicates rather than nested pure functions.)

## ParallelMixedTower: field-consistent `quo` — solves Charlwood A2, A3, P8 (v0.182)

The ansatz assembly (`AnsatzSystem`, `src/internal/mixed/ParallelMixed.m`) clears the distinct
column denominators by multiplying through by a common multiple `L` and the quotients `L/dd`. When
the denominators carried `AlgebraicNumber[θ]` coefficients (the split rungs whose constants are
`Root` objects), the old code either ran `PolynomialLCM` — which has **no** number-field path and
returns a spurious factor for an `AlgebraicNumber` coefficient — or mapped back to raw radicals and
`Cancel[…, Extension -> Automatic]`, which could drop a factor of a special over the extension. Both
produced an **inconsistent, over-generated** linear system (e.g. A2/A3's conic-split rung assembled
72–73 equations where Mathematica assembles 34), so the solve failed and the retry ladder ran to the
budget.

- The algebraic branch now uses the **product** of the distinct denominators as the common multiple:
  any common multiple gives an equivalent system (`L` is unknown-free, so multiplying the polynomial
  identity by an extra factor preserves its solution set), and each quotient `L/dd` is the product of
  the *other* denominators — exact by construction, needing no field GCD/LCM or radical round-trip.
  The Q-only branch keeps the minimal `PolynomialLCM`. Depends on the native field `Expand` (v0.176).
- **Solves Charlwood A2** (`ArcTan[x+√(1-x²)]`, ~1.4 s), **A3** (~1.7 s), **P8**
  (`√(Tan²+2Tan+2)`, ~3.7 s) — all numerically verified (`|N[(∂ₓr−f)/.x→1/3,30]| < 1e-15`). No
  regression on the already-solving field cases (A1/A16/A19/A37/P4 still solve+verify) or the
  ParallelMixedTower suite. Charlwood direct-method: **47/50** (with A27 at v0.180). A35 now fails
  fast on the branch/sign gate rather than the budget (a separate item); A40's first-rung Q(√5)
  coefficient remains open.

## ToNumberField: degree-gated membership-precision escalation — solves Charlwood P4 (v0.178)

## ParallelMixedTower: native number-field arithmetic + field-coefficient `Expand`; Charlwood misses unlocked (v0.176)

The ParallelMixedTower ansatz is assembled and solved over one algebraic number field
`K = Q(θ)` with `AlgebraicNumber[θ, coords]` coefficients. Previously **all** of that field
arithmetic ran through the WL evaluator on the expression representation, with an expr↔qqbar
round-trip per scalar operation — so the split-specials ansatz over a `Q(i)` or `Q(√d)` field did
thousands of `AlgebraicNumber` `Plus`/`Times`/`Expand` operations, each re-canonicalising every
field element. This landed the native field-arithmetic layer that SymPy's `QQ<alpha>` domain and
Mathematica's compiled AlgebraicNumber arithmetic use, and unlocked 7 previously-missed Charlwood
radical integrals (A1, A11, A16, A19, A20, A34, A37) via the direct `ParallelMixedTower` method.

- **Native scalar field arithmetic** (`flint_qqbar.c`). A generator cache (`genfd_get`) keyed on θ's
  minimal polynomial: `AlgebraicNumber` add/mul/pow and rational combination reduce the coords as
  `fmpq_poly` mod the cached minpoly — no `to_qqbar` of θ, no `qqbar_to_expr` rebuild, no
  re-canonicalisation. A canonical fast path in `flint_qqbar_algebraic_number` returns an
  already-reduced `AlgebraicNumber` unchanged. Plus a `qqbar_to_expr` degree≥3 `Root`-memo and a
  per-minpoly sorted-roots memo (`wl_root_index`).
- **Native field-coefficient `Expand`** (`flint_bridge.c`, `flint_expand_polynomial_field`, wired
  into the top-level FLINT fast path in `expand.c`). A polynomial in the tower generators whose
  coefficients are `AlgebraicNumber[θ, {..}]` is expanded natively: substitute θ → a fresh variable
  τ, expand over `Q[gens, τ]` in packed `fmpq_mpoly`, reduce modulo θ's minimal polynomial `M(τ)`
  with `fmpq_mpoly_divrem`, and read the reduced polynomial back as `AlgebraicNumber`-coefficient
  terms in ONE pass. This replaces the generic term-by-term `Times`→`evaluate` distribution that
  dominated the field-arithmetic profile. Output is byte-identical (after canonical re-ordering) to
  the generic `Expand` it replaces; a bare-`Complex` (Gaussian) expression such as a general-
  integration residue `x + I` is deliberately left to the generic path so its structural form is
  preserved for downstream pattern matching. Differential-tested against `Expand` over random
  `Q(i)` / `Q(√2)` polynomials.
- **`TimeConstrained` clock-read throttle** (`eval.c`). The cooperative wall-clock backstop
  (`tc_check_deadline`) was read on every `evaluate()` loop iteration — ~10% of a `DSolve` `Q(i)`
  profile. It is now sampled once per 128 iterations (the SIGPROF async timer, and allocation
  safepoints inside async-deferred regions, remain the primary deadline mechanism); a pre-elapsed
  deadline still trips on the first iteration. Broad, machine-wide reduction of `TimeConstrained`
  overhead.
- **Effect.** `DSolve` over an incidental `Q(i)` intermediate (e.g. `y' == (Cos x + 1)/(2 - Sin y)`)
  dropped from ~40.9 s to ~8 s. The field-arithmetic canonicalisation block that dominated the
  profile is gone. The full `Integrate[]` cascade blow-up on A11 (`x^3 ArcSin[x]/Sqrt[1-x^4]`) is a
  separate, pre-existing issue (present on the prior release too); the direct `ParallelMixedTower`
  method solves and verifies it.

## DSolve M57 — `SolvableForY` / `SolvableForX`: the `y=G(x,y′)` differentiation method (v0.173)

Two new first-order methods (`src/calculus/dsolve_solvefor.c`) implementing the "dp" differentiation
method (Maple's `dp`/`dp2`), the general form of which `DSolve`Lagrange` is the linear special case.
For an ODE `F(x,y,y')==0` polynomial in `y`, `SolvableForY` isolates `y = G(x,p)` (`p=y'`),
differentiates w.r.t. `x` (`p = G_x + G_p p'`), and recurses the cascade on the induced first-order ODE
`dx/dp = G_p/(p − G_x)` for `x = X(p,C)`, returning the **parametric** general solution
`{{x->Function[{p},X], y->Function[{p},G(X,p)]}}` through the existing parametric substrate
(`dsolve_run_parametric`), which back-substitution-verifies every branch (**0 FAIL by construction**).

- **Reuse.** The parametric substrate is reused verbatim (`DSolve`Param[X,Y,p]` wrapper → verify by
  `y' = D[Y,p]/D[X,p]` → assemble). The new logic is: solve `R==0` for `y` (resp. `x`) generally,
  build the induced ODE, and recurse — where `DSolve`Lagrange` only handled the R-linear-in-`y` case
  whose induced ODE is linear.
- **Latency gate.** A cheap `PolynomialQ[R, solve_var]` pre-gate (mirroring `NthAlgebraic`) declines
  the transcendental time-burners (`Tan[x y]`, `Log[Log[y]]`, …) that never close — `y'==Sin[x y]`
  went 20 s → 0.24 s — while keeping the tractable class. All recursion is bounded (`TimeConstrained`
  sub-solves, a wall-clock deadline, a re-entry guard, a decline memo, and a bounded Simplify).
- **`SolvableForX` is pinned-only** (opt-in, like `FirstOrderPowerSeries`/`EigenvalueProblem`): its
  automatic corpus yield is ~0 while a degree-1-in-`x` form with a cubic-denominator induced ODE
  produces a transcendental branch whose back-substitution verify is slow. `SolvableForY` is automatic
  (runs after every named first-order specialist, before the Lie backstop).
- **Solves** the 12000.org `y=_G(x,y')` class, flagship `x^(n-1)(y')^n − n x y' + y == 0` (where
  `y = n x y' − x^(n-1)(y')^n` is not affine in `x`, so `DSolve`Lagrange` declines).
- **§2.1.2 corpus:** clean re-run **585 → 590 (net +5), 0 FAIL**. The **deterministic** M57 gain is
  **+2** — `2.1.2-347` (`y=_G(x,y')`) and `2.1.2-352` (`_with_symmetry_[F(x),G(y)]`) now solve via
  `SolvableForY` (both verified: it returns them, the M56 reference did not). The other +3 is the
  documented `_with_linear_symmetries` timing cluster (2nd/high-order cases `SolvableForY` declines
  instantly) oscillating P↔U by machine load. More solvable-for-y cases (350, 351) solve but exceed
  the 8 s forked corpus budget (arbitrary-function-coefficient induced ODEs). Gate baseline 631 → 629.

## DSolve M56 — second-order integrating factors, Stage 2: μ(x, y′) → reduction-of-order first integral

Completes the "next increment" the plan had marked open inside M18 (`DSolve`ReducibleIntegratingFactor`,
Cheb-Terrab & Roche 1999). Stage 1 (μ(x, y)) already shipped; Stage 2 adds the **μ(x, y′)** search
(Section 2.2, Lemma 3, Cases A/C/D + the Lemma-2 μ̃(x) recovery) and **unblocks** it by emitting the
reduced first integral as a Maple-style reduction-of-order answer.

- **μ(x, y′) search (`src/calculus/dsolve_ifactor.c`).** From `Υ = Φ_y`: **Case A** (`∂_{y′}(Υ_y/Υ)≠0`)
  takes 𝓕 = 1/(the y′-only factors of Υ); **Case C** (`Υ_y≠0`, `∂_{y′}(Υ_y/Υ)=0`) takes the y-only
  factors `w`, `𝓗=w_y/w`, `p'=𝓗_x/𝓗_y`, `𝓕=(p'+y')w/Υ`; **Case D** (`Υ_y=0`, narrow degenerate
  family) takes `p'=Ψ_x` with `Ψ=Φ/Υ−y`, `𝓕=(p'+y')/Υ`. `μ̃(x)` by Lemma 2 (φ₁…φ₄, the x-only
  integrand existence test). The factor split uses `FactorList`; any imperfection is caught by the
  gate below, so a wrong 𝓕 only ever declines.
- **Correctness gate (unchanged guarantee).** Every candidate μ reconstructs `R = ∫μ dy′ + G(x,y)` and
  must pass the exactness test `A(R)=R_x+y'R_y+Φ R_{y'}==0` **symbolically and numerically** before it
  is used, so a wrong μ or a mis-extracted factor is a clean decline — never a wrong answer.
- **Reduction-of-order emit (`dsolve_run_first_integral`, `src/calculus/dsolve_common.c`).** When the
  first integral `R(x,y,y')==C[1]` is not elementarily solvable as a first-order ODE (which is the
  common case — the reduced equations are non-elementary, and Maple/Mathematica return them
  implicitly), the new `DSolve`ReducibleFirstIntegral` method returns `{{ R(x, y[x], y'[x]) == C[1] }}`
  verbatim, verified by `d/dx(R)` vanishing modulo `y''==Φ`. A one-constant reduction (still carries
  `y'[x]`), so it runs in the automatic cascade **after** the full-solution 2nd-order methods
  (explicit integrating factor, then `SecondOrderSymmetry`) and **declines an IVP** (one constant
  cannot fit two conditions). Examples: Kamke 226 `y''=(x²yy'+xy²)/y'` → `y'[x]²/2 − x²y[x]²/2 == C[1]`;
  Kamke 136 `y''=(1+y'²)/(x−y)`; Kamke 66 `y''=a(c+bx+y)(1+y'²)^{3/2}`.
- **Tests.** New pinned builtin `DSolve`ReducibleFirstIntegral` with docstring + `ATTR_PROTECTED`; unit
  tests `t_m56_*` in `tests/test_dsolve.c`; anti-overfit forward-generator families (Cases A/C/D grids,
  intrinsic first-integral verification) in `tests/test_dsolve_m56_stress.c`. §2.1.2 corpus:
  **568 → 585 (+17), 0 FAIL** — the whole net gain is the `2nd_reducible_mu` bucket (38 → 55),
  confirmed first integrals for `_mu_x_y1`/`_mu_xy` cases that SymPy does not solve.

A 114-integrand stress test comparing the strict `` Integrate`ParallelMixedTower ``
surface against its Python/sympy reference (`mixed/parallel_mixed.py`; harness kept in

## `Simplify` over `Root[...]` objects — no hang, and algebraic collapse (v0.165)

`Simplify` now handles expressions containing `Root[poly&, k]` algebraic-number
objects robustly and, where the algebra permits, collapses them. The motivating
case: `Integrate[Sqrt[Tan[x]], x]` (via `ParallelMixedTower`) returns an
antiderivative `F` whose coefficients are the quartic roots of `1 + t^4` (field
`Q(i, Sqrt[2])`); `Simplify[D[F, x] - Sqrt[Tan[x]]]` used to **hang > 300 s** and now
returns `0` in ~9 ms, and `Simplify[D[F, x]]` returns `Sqrt[Tan[x]]`.

- **Root cause of the hang.** `collect_variables` (`src/poly/poly.c`) enumerated each
  distinct `Root[...]` object as an independent polynomial *variable*. Several
  algebraically-dependent roots (all roots of one polynomial) then gave the
  multivariate GCD a degenerate pseudo-remainder sequence that never terminated — the
  same class as the earlier `Sqrt[Tan[x]]` hang, now reached through a Root coefficient
  set rather than `Sqrt[2]`.
- **Fix (robustness).** A `Root[...]` object is a **constant** algebraic number, not a
  variable, so `collect_variables` now skips it (matching Mathematica:
  `Variables[Root[..] + x]` is `{x}`). This removes the exponential blow-up at its
  source for every poly-engine caller (Factor / Cancel / Together / GCD). Belt-and-
  braces: the post-search polish `Factor` and the algebraic-`Plus` `Together` fast
  paths decline on Root-bearing inputs, and `exact_poly_div` (`poly.c`) gained the same
  degree-monotonicity guard that already protects `pseudo_rem`.
- **Fix (simplification).** `rr_thread_coeffs` was promoted to a public qqbar-engine
  primitive `flint_qqbar_reduce_coeffs` (`src/poly/flint_qqbar.{c,h}`), which
  canonicalises every maximal constant-algebraic subexpression via FLINT `qqbar`
  (reducing *numbers* only — it never touches the multivariate poly engine, so it
  cannot blow up). `Simplify` runs it as a pre-pass (`src/simp/simp_search.c`) whenever
  a `Root` head is present, so bare Root arithmetic collapses:
  `Simplify[Root[1+#^4&,2]^3 + Root[1+#^4&,2]]` → `I Sqrt[2]`.
- **Reaching 0 on the trig identity.** The numerator of `D[F,x] - Sqrt[Tan[x]]` is zero
  only *modulo the trig ideal*, which trigrat's Cancel handles for ordinary radical
  coefficients but not for opaque Root coefficients. `simp_trig_rational`
  (`src/simp/trigrat.c`) now converts radical-expressible Roots (degree ≤ 4, or
  binomials) to `Sqrt`/`I` form with `ToRadicals` at entry, so the existing radical
  machinery reduces them; a genuinely non-radical (degree ≥ 5) Root is left untouched
  (graceful — no hang, no spurious change). Non-trig Root-coefficient rational
  identities (e.g. `D[Integrate[x/(x^3-2),x]] - x/(x^3-2)`) collapse to `0` via
  `Together` + the qqbar coefficient pass.
- Tests: `tests/test_simplify_hang.c` gains a forked termination case plus exact-output
  assertions (bare Root arithmetic, the `Sqrt[Tan[x]]` residual → 0, the derivative →
  `Sqrt[Tan[x]]`, and a non-trig cubic-field identity → 0). Symbolic-only path: no
  NDArray/Compile surface (EXEMPT — returns Root/AlgebraicNumber, non-machine objects).

## `Function` — lexical closure over an enclosing `Function`'s parameter

`Function` now closes over the parameters of an enclosing `Function`, matching the
Wolfram Language. Previously an outer named parameter was **invisible** inside a
nested pure function: `Function[x, (x + #) &][10]` returned `(x + #1) &` with a free
`x` instead of `(10 + #1) &`, and `Function[n, Function[x, x^n]][2]` returned
`Function[x, x^n]` with a free `n` instead of `Function[x, x^2]`.

- **Cause.** `substitute_names` (`src/purefunc.c`) treated *every* nested `Function`
  as opaque and copied it unsubstituted, on the theory that a nested body always
  shadows the outer parameters. That is only true when the nested `Function` rebinds
  the **same name**. The Wolfram rule is asymmetric: a **named** parameter is shadowed
  only by a nested `Function` that rebinds that name, whereas a **slot** (`#`) is
  claimed by the innermost enclosing `Function` of any form.
- **Fix.** `substitute_names` now descends into nested `Function` expressions,
  dropping from the substitution set only the names a given nested `Function` rebinds
  as its own parameters (a slot-form inner function `(… # …)&` rebinds none, so every
  outer name flows into it). Slot handling (`substitute_slots`) is unchanged — nested
  functions still shield their slots. Shadowing (`Function[x, Function[x, x]][1][2] ->
  2`), multi-parameter partial shadowing, and deep nesting are all covered by the new
  `tests/test_purefunc.c::test_purefunc_closure`.
- **What this unblocks.** `Integrate[Sqrt[Tan[x]], x, Method -> "ParallelMixedTower"]`
  (previously unevaluated) now returns a correct antiderivative, matching its SymPy
  reference and Mathematica. `Sqrt[Tan[x]]` flattens to `Integrate[2 u^2/(1 + u^4), u]`;
  the tower special `1 + u^4` is split into its four linear factors over `Q(i, Sqrt[2])`
  (SplitSpecials, Theorem 6.1), and the gate that enables the split
  (`ParallelMixed.m`'s `splittable`) is computed by exactly this nested-`Function`
  idiom — so it silently evaluated `False` before. No change to the integrator; it is
  the core-evaluator fix that makes the natural WL code work. Regression:
  `tests/test_parallelmixedtower.c::test_method_split_specials` (head check plus a
  numeric branch-pin; symbolic `Simplify` over the `Root` objects is too heavy for a
  unit test, and `D[]` of an unevaluated `Integrate` would let a decline pass a residual
  test vacuously). `v0.164`.

## `AlgebraicNumberNorm`

New head **`AlgebraicNumberNorm[a]`** — the field norm of an algebraic number: the
product of the roots of its minimal polynomial (equivalently, the product of the
conjugates of `a` over the rationals). Faithful to the Wolfram Language and a
companion to the other `AlgebraicNumber*` heads.

- **Absolute norm, exact and cheap.** From the `qqbar` primitive integer minimal
  polynomial `c_n x^n + ... + c_0` the norm is `(-1)^n c_0 / c_n` — a two-coefficient
  read, no field build. Integers and rationals return themselves
  (`AlgebraicNumberNorm[2]` → `2`, `AlgebraicNumberNorm[-2/3]` → `-2/3`); radicals,
  roots of unity, `Root` and `AlgebraicNumber` objects all work
  (`Sqrt[2]` → `-2`, `1/Sqrt[Sqrt[2]+3]` → `1/7`, `E^(Pi I/8)` → `1`,
  `Root[-1+#1+#1^2+#1^3+#1^4&,1]` → `-1`, `AlgebraicNumber[Sqrt[2] I,{1,2}]` → `9`,
  `9+Sqrt[10]` → `71`).
- **`GoldenRatio` now algebraic in the `qqbar` layer.** The shared converter
  `to_qqbar` (and `flint_qqbar_is_constant_algebraic`) recognises `GoldenRatio` as
  `(1+Sqrt[5])/2` — the sole algebraic named constant — so `AlgebraicNumberNorm[GoldenRatio]`
  → `-1`, and `RootReduce`, `AlgebraicNumber`, `ToNumberField` and the algebraic
  comparison surface gain `GoldenRatio` for free.
- **Relative norm via `Extension -> theta`.** `AlgebraicNumberNorm[a, Extension -> theta]`
  is the norm over `Q(theta)` for `a ∈ Q(theta)`, computed by transitivity of the norm
  in the tower `Q ⊆ Q(a) ⊆ Q(theta)`:
  `N_{Q(theta)/Q}(a) = N_{Q(a)/Q}(a)^{[Q(theta):Q(a)]}` (the absolute norm raised to the
  tower index; membership decided by `qqbar_express_in_field`). So
  `AlgebraicNumberNorm[Sqrt[2], Extension -> E^(Pi I/4)]` → `4`,
  `AlgebraicNumberNorm[2 Sqrt[5], Extension -> Sqrt[5]]` → `-20`, and a norm computed
  in the compositum `Q(Sqrt[3], Sqrt[-5])` (via `ToNumberField[…, All]`) → `64`. The
  norm is multiplicative over a fixed field.
- **Attributes** `{Listable, Protected}`, default option `Extension -> None`:
  `AlgebraicNumberNorm[{2 Sqrt[2], E^(Pi I/8), 1+I}]` → `{-8, 1, 2}`, with a trailing
  `Extension` option repeated across the list.
- **Diagnostics**: a non-algebraic argument emits `AlgebraicNumberNorm::nalg`; an
  argument not in the extension field emits `AlgebraicNumberNorm::ext`; either stays
  unevaluated.

Requires FLINT (the `qqbar` engine); a `USE_FLINT=0` build leaves the head
unevaluated.

## `AlgebraicNumberTrace`

New head **`AlgebraicNumberTrace[a]`** — the field trace of an algebraic number: the
sum of the roots of its minimal polynomial (equivalently, the sum of the conjugates
of `a` over the rationals). The additive counterpart of `AlgebraicNumberNorm`, and
faithful to the Wolfram Language.

- **Absolute trace, exact and cheap.** From the `qqbar` primitive integer minimal
  polynomial `c_n x^n + ... + c_0` the trace is `-c_{n-1} / c_n` — a two-coefficient
  read, no field build. Integers and rationals return themselves
  (`AlgebraicNumberTrace[2]` → `2`, `AlgebraicNumberTrace[-2/3]` → `-2/3`); radicals,
  roots of unity, `Root` and `AlgebraicNumber` objects all work
  (`5+Sqrt[2]` → `10`, `Sqrt[1+Sqrt[2]]` → `0`, `GoldenRatio` → `1`,
  `E^(Pi I/8)` → `0`, `Root[#1^4+11#1^3+#1^2+#1+1&,1]` → `-11`,
  `AlgebraicNumber[Sqrt[2] I,{1,2}]` → `2`).
- **Relative trace via `Extension -> theta`.** `AlgebraicNumberTrace[a, Extension -> theta]`
  is the trace over `Q(theta)` for `a ∈ Q(theta)`, computed by transitivity of the
  trace in the tower `Q ⊆ Q(a) ⊆ Q(theta)`:
  `Tr_{Q(theta)/Q}(a) = [Q(theta):Q(a)] · Tr_{Q(a)/Q}(a)` (the absolute trace scaled
  by the tower index; membership decided by `qqbar_express_in_field`). So
  `AlgebraicNumberTrace[5, Extension -> Sqrt[2]]` → `10`,
  `AlgebraicNumberTrace[3, Extension -> Sqrt[2]+Sqrt[3]]` → `12`, and
  `AlgebraicNumberTrace[E^(2 Pi I/3), Extension -> ToNumberField[{2^(1/3), E^(2 Pi I/3)}, All][[1,1]]]`
  → `-3`. The trace is additive over a fixed field.
- **Attributes** `{Listable, Protected}`, default option `Extension -> None`:
  `AlgebraicNumberTrace[{5+Sqrt[2], E^(Pi I/8)}]` → `{10, 0}`, with a trailing
  `Extension` option repeated across the list.
- **Diagnostics**: a non-algebraic argument emits `AlgebraicNumberTrace::nalg`; an
  argument not in the extension field emits `AlgebraicNumberTrace::ext`; either stays
  unevaluated.

Requires FLINT (the `qqbar` engine); a `USE_FLINT=0` build leaves the head
unevaluated.

## `AlgebraicNumberDenominator`

New head **`AlgebraicNumberDenominator[a]`** — the smallest positive integer `n`
such that `n a` is an algebraic integer. Faithful to the Wolfram Language, and the
companion to [`AlgebraicIntegerQ`](../builtins/algebra.md#algebraicintegerq)
(`AlgebraicIntegerQ[x]` is the `AlgebraicNumberDenominator[x] == 1` case).

- **Same argument surface as `AlgebraicIntegerQ`**: rationals, radicals
  (`1/Sqrt[3]` → `3`, `1/Sqrt[Sqrt[2]+3]` → `7`, `(1+3I)^(-1/3)` → `10`), `Root`
  objects (`Root[5-6#1+3#1^3&,1]` → `3`), and `AlgebraicNumber` objects
  (`AlgebraicNumber[Sqrt[2],{1/5,1}]` → `5`). An algebraic integer gives `1`.
- **Exact, and correct where the naive route is not**: computed from the minimal
  polynomial by a **per-prime valuation**, not the raw min-poly leading
  coefficient. The two diverge — `1/5 + Sqrt[2]` has primitive minimal polynomial
  `25 x^2 - 10 x - 49` (leading coefficient `25`) yet denominator `5`, because
  `5 (1/5 + Sqrt[2]) = 1 + 5 Sqrt[2]` is already an algebraic integer. Writing the
  monic minimal polynomial of `n a`, its `x^i` coefficient is `(a_i/a_n) n^{n-i}`,
  so `n` is the least integer with `denom(a_i/a_n) | n^{n-i}` for every `i`;
  `n | a_n`, so one factorisation of `a_n` plus a valuation scan is exact.
- **Attributes** `{Listable, Protected}`: `AlgebraicNumberDenominator[{Sqrt[2],
  1/Sqrt[2], 1/3}]` → `{1, 2, 3}`. By construction
  `AlgebraicIntegerQ[AlgebraicNumberDenominator[a] a]` is `True`, so `n a` (equally
  `n ToNumberField[a, theta]`) is the algebraic-integer numerator of `a = alpha/n`.
- **Diagnostics**: a non-algebraic argument (`Pi`, a free symbol) emits
  `AlgebraicNumberDenominator::nalg` and stays unevaluated.

Requires FLINT (the `qqbar` engine); a `USE_FLINT=0` build leaves the head
unevaluated.

## `NumberFieldIntegralBasis` and `AlgebraicIntegerQ`

Two new heads for algebraic-integer computations in a number field, faithful to
the Wolfram Language.

**`NumberFieldIntegralBasis[a]`** — an integral basis for the field `Q(a)`
generated by the algebraic number `a`: a list of algebraic integers generating
the ring of integers `O_K` as a module over `Z`.

- **Maximal order, not just the equation order**: forms the algebraic-integer
  generator `phi` of `Q(a)` (rescaling `a` when it is not an algebraic integer,
  e.g. `Root[2+3#^3&,2]` → `phi = 3 a`), then enlarges `Z[phi]` to `O_K` by
  **Round 2 (Pohst–Zassenhaus)** wherever it is not already maximal. So
  non-monogenic fields are correct: `Q(Sqrt[5])` gives `{1, (1+Sqrt[5])/2}` (not
  `Z[Sqrt[5]]`), and `Q(Sqrt[2]+Sqrt[3])` a genuine 4-element basis.
- **Canonical presentation**: the (arbitrarily-ordered, unreduced) Round-2 basis
  is put into the standard lower-triangular Hermite normal form in the
  theta-power basis, so the result begins with `1` and each element `omega_k` has
  degree `k`. Monogenic fields are unchanged (`{1, theta, ..., theta^(n-1)}`).
- **Result form**: each element is a canonical `AlgebraicNumber` object (or a
  plain integer/rational); apply `N` for the numeric display. `Q(a) = Q` gives
  `{1}`.
- **Attributes** `{Listable, Protected}`: `NumberFieldIntegralBasis[{a1, ...}]`
  threads to one basis per generator.
- **Diagnostics**: a non-algebraic argument, a degree over the cap, or an
  uncertifiable maximal order emits `NumberFieldIntegralBasis::nintbas` and stays
  unevaluated.

**`AlgebraicIntegerQ[x]`** — `True` iff `x` is an algebraic integer, decided
exactly: its primitive integer minimal polynomial is monic. Rational integers
qualify; non-integer rationals, non-algebraic quantities (`Pi`), symbols, and
lists do not (`Protected`, not `Listable`). Companion predicate for the integral
basis: every returned element, and every integer combination of them, is an
algebraic integer.

Both require FLINT (the `qqbar` engine plus the number-field maximal-order layer
`src/numbertheory/`); a `USE_FLINT=0` build leaves the heads unevaluated.

`flint_qqbar_algebraic_integer_q` in `src/poly/flint_qqbar.c` (reusing
`to_qqbar`, `algint_generator`, `poly_to_algnum`, and `nf_field_create` /
`nf_ok_basis`), thin WL wrappers `src/poly/numberfieldintegralbasis.c` and
`src/poly/algebraicintegerq.c` (new, registered from `src/core.c`), docstrings in
`src/info.c`, `SYM_NumberFieldIntegralBasis` / `SYM_AlgebraicIntegerQ` in

## `AlgebraicNumberPolynomial`

New head **`AlgebraicNumberPolynomial[a, x]`** — the inverse view of
[`AlgebraicNumber`](../builtins/algebra.md#algebraicnumber): for
`a = AlgebraicNumber[theta, {c0, ..., cn}]` it returns the polynomial
`c0 + c1 x + ... + cn x^n`, from which `a` is recovered by `x -> theta`. Faithful
to the Wolfram Language.

- **Number passthrough**: an integer or rational `a` is the constant polynomial and
  is returned unchanged (`AlgebraicNumberPolynomial[2, x]` → `2`,
  `AlgebraicNumberPolynomial[1/2, x]` → `1/2`).
- **Polynomial build**: reads the coefficient vector already stored in the
  `AlgebraicNumber` object and assembles `c0 + c1 x + ... + cn x^n`; the evaluator
  drops zero terms and orders monomials by degree
  (`AlgebraicNumber[2^(1/3), {1,0,3}]` → `1 + 3 x^2`).
- **Attributes** `{Listable, Protected}`: threads over lists in both arguments
  (`AlgebraicNumberPolynomial[{2, AlgebraicNumber[Sqrt[2], {1,2}]}, x]` →
  `{2, 1 + 2 x}`).
- **Diagnostics**: a non-`AlgebraicNumber`, non-rational argument emits
  `AlgebraicNumberPolynomial::naobj` and stays unevaluated.
- **Use**: makes same-generator algebraic-number arithmetic explicit at the
  polynomial level — adding two `AlgebraicNumberPolynomial` results, substituting
  the generator, and `RootReduce`-ing reproduces the sum of the numbers.

Purely structural (coefficient read + polynomial build): **no FLINT** is used, so
the head is usable in a `USE_FLINT=0` build (though only a FLINT build produces the
`AlgebraicNumber` objects it consumes).

Implementation: `src/poly/algebraicnumberpolynomial.c` (new, registered from
`src/core.c`), docstring in `src/info.c`, `SYM_AlgebraicNumberPolynomial` in
`src/sym_names.{c,h}`, tests in `tests/test_algebraicnumberpolynomial.c` and the
leak gate `tests/scripts/algebraicnumberpolynomial_leakcheck.sh`. Added to
`SKIP_EXPLOSIVE` in `tools/nd_fastpath_sweep.py` (a Listable thread of a numeric
no-op, not a missing buffer fast path — the head returns a symbolic polynomial).
`v0.156`.

## `TimeConstrained` — heavy methods run safely inside it (ParallelMixedTower)

`TimeConstrained` aborts an over-budget computation with a `siglongjmp` from an
**async** `SIGPROF` handler, which can land inside a regular (non-GMP) `malloc`
holding libmalloc's zone lock — unwinding then leaves the lock held and the next
allocation traps (the known `_os_unfair_lock_recursive_abort` crash). GMP allocs
were already guarded; a malloc-heavy `.m` method like `Integrate`ParallelMixedTower`
(Expr nodes, FLINT structures) was not, so v0.161 simply had it **decline** while a
deadline was active — which made it inert inside DSolve's `TimeConstrained[Integrate[…]]`.

Now it runs there safely. A new **async-jump-defer** region
(`tc_async_defer_push`/`pop`, `src/core.c`) keeps the whole method call in
cooperative-only mode: the SIGPROF handler defers instead of jumping, and the
deadline is still enforced at safe points (`tc_check_deadline` every rewrite step,
`tc_alloc_safepoint` after each GMP alloc) — so a runaway is still aborted, just
cleanly. The defer count doubles as the method's re-entry guard, and both it and
the message-suppression depth are save/restored across the timeout unwind by
`tc_run_guarded` (a `Quiet[]`/depth region abandoned by a timeout no longer leaks
into the session — a latent fix beyond ParallelMixedTower). Stress-verified: 360
mid-computation aborts inside tight `TimeConstrained` windows, zero crashes.

`Integrate`ParallelMixedTower` no longer declines inside `TimeConstrained`. `v0.162`.

## `Compile` — `RuntimeOptions -> "Speed"` on integer `Power` returned garbage/stale (bug fix)

`Compile[{{n, _Integer}}, n^3, RuntimeOptions -> "Speed"][3000000]` (wrap mode,
`"CatchMachineIntegerOverflow" -> False`) returned a **non-deterministic** value and
could **leak a prior call's result** — `cf[3000000]` after `cf[1000]` returned
`1000^3`. Root cause in `src/checked_int.h`: the overflow-checked binary-exponentiation
helpers `ci_powi` / `ci_powi_i64` returned `true` on the first overflowing multiply
**without writing `*out`**, violating the header's own "writes the wrapped result
either way" contract. In the default checked path the caller bails and never reads
`*out`, so it was invisible; in wrap mode (`IF_NOCHK`) the VM skips the bail and used
the **unwritten** destination register — stack garbage on a cold frame, the previous
call's value on a reused per-program frame. `POWI_I` was the only affected opcode
(the other `IF_NOCHK` arithmetic helpers already write the wrapped value; the
integer-closed heads never carry `IF_NOCHK`).

**Fix.** Both helpers now accumulate the wrapped product on every step (OR-ing the
overflow flag) and always write `*out`, so wrap mode gets the true modular
(`mod 2^64`, signed int64) power: `...["Speed"][3000000]` is now
`8553255926290448384` deterministically, and the stale-state leak is gone. The
returned overflow flag is unchanged (still true iff some step overflowed), so the
default checked path — and every existing test — is untouched. New regression
coverage in `tests/test_compiledfunction.c` (`test_cf_runtime_options`); the
`ci_powi_i64` twin is fixed identically for the packed int64 layer. `v0.195`.
