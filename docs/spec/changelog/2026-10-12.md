# Changelog: week of 2026-10-12 (Mon) – 2026-10-18 (Sun)

## Correctness: wrong answers across Series printing, string patterns, special functions, PossibleZeroQ/FullSimplify, Reduce, Abs/Sign, ComplexExpand and DSolve ; v0.464

A batch of independently verified fixes for wrong answers found while regenerating the reference site.

- **Series at ±Infinity prints a re-parseable form.** `Series[x + 1/x, {x, Infinity, 2}]` printed `1/1/x + 1/x + O[1/x]^3`, which reads back as `1/x`; it now prints `x + 1/x + O[1/x]^3`. A quotient-valued denominator is parenthesised (`1/(1/x)`, `1/(2/3)`), integer powers of `1/x` fold to powers of `x`, and a series summand splices its terms into an outer sum (`Log[x] - 1/(2 x) - ...`, not `+ -1/(2 x)`).
- **`_?DigitQ` in string patterns is ASCII-only**, like `DigitQ`. It compiled to PCRE2-UCP `[[:digit:]]`, which matches every Unicode digit, so `StringMatchQ["١", _?DigitQ]` returned `True`.
- **HypergeometricU / WhittakerW / StruveH at machine precision.** A terminating U (`a` or `a - b + 1` a non-positive integer) is summed as a finite sum. It used to collapse to `0.0`: `HypergeometricU[-1, 2, 1.]` is now `-1.0` and `WhittakerW[2, 1/2, 1.]` is now `-0.606531`. `StruveH[-(n + 1/2), x]` skips the terms killed by the Γ poles, so `StruveH[-3/2, 2.]` is `-0.491294`, where it used to return `0.0 HypergeometricPFQ[...]`. `Compile[]` now lowers HypergeometricU, WhittakerM/W, 1F1, 2F1 and LerchPhi at rank-1 array shape.
- **BesselJ/Y/I/K at large order.** The MPFR cores chose the Hankel expansion on |z| alone; it is now admitted only when its terms reach the target precision. Large orders use the three-term order recurrence instead. `N[BesselJ[51/2, 100], 20]` gave `-0.2001` (true value `0.07458`), and `BesselJ[500.5, 1000.]` gave `1.798` (true value `-0.006834`). `BesselY[1500., 5000.]` drops from 27 s to 1 ms.
- **PossibleZeroQ samples non-holomorphic symbols at complex points**, so `PossibleZeroQ[Conjugate[x] - x]` is `False`. FullSimplify's Gamma pairs are the analytic reflection forms: `Gamma[1/2 + I b] Gamma[1/2 - I b]` gives `Pi Sech[Pi b]`, where it used to give the wrong `Pi Sech[Pi Im[...]]`. The real-log rules (`Log[Sec[x] + Tan[x]]` to `ArcTanh[Sin[x]]`, and the others like it) fire only when the assumptions prove the argument positive. FullSimplify now binds a positional assumption to `$Assumptions`.
- **Reduce over Reals no longer returns a false `False`.** Parametric families are kept under their reality condition: `Reduce[Exp[x] == a, x, Reals]` gives `a > 0 && x == Log[a]`, and `Reduce[Sin[x] == a, x, Reals]` gives two families under `-1 <= a <= 1`. A sign diagram whose roots cannot be found now declines instead of deciding the whole real line from one sample. `Sin[x] > x/2` and `Sin[x] > 0` are left unevaluated, and so `Refine[Cos[x] > 0]` is no longer `True`.
- **Abs / Sign / Re / Im / ReIm / Arg of exact numeric constants**, with each sign certified by an Arb ball evaluation (`flint_cert_parts_sign`). Examples: `Abs[Pi - 4] = 4 - Pi`, `Sign[Pi] = 1`, `Re[Pi] = Pi`, `Arg[-1 + I Sqrt[2]] = Pi - ArcTan[Sqrt[2]]`. An exact zero that does not autosimplify is left unevaluated.
- **ComplexExpand of real radicals of constants** keeps the plain form: `ComplexExpand[Sqrt[2 + Sqrt[3]]]` gives `Sqrt[2 + Sqrt[3]]`, and `ComplexExpand[Sqrt[1 - Sqrt[3]]]` gives `I Sqrt[-1 + Sqrt[3]]`.
- **LerchPhi / HurwitzZeta / Zeta / Erf.** LerchPhi for |z| > 1 takes its continuation from arb. On the negative real axis it was wrong: `LerchPhi[-3., 1.5, .5]` gave `6.35 + 1.45 I`, and the true value is `2.06336`. With Re s < 0, HurwitzZeta and `Zeta[s, a]` now carry guard bits against cancellation. `HurwitzZeta[-2.5, -0.5]` now keeps its imaginary part. The arb bridge no longer prints the midpoint of a wide interval that contains zero. `Erf[3. + 30. I]` now returns its extended-exponent value instead of `Overflow[]`.
- **DSolve, degenerate Kummer/Laguerre equations.** When the 1F1 solution is a polynomial, the {1F1, U} basis was dependent. `x y'' + (1 - x) y' + 2 y == 0` now gives the logarithmic partner as well: `C[1] (1 - 2 x + x^2/2) + C[2] (E^x (3/2 - x/2) + ExpIntegralEi[x] (1 - 2 x + x^2/2))`.

## Feature: StruveH numeric surfaces — arb arbitrary precision + machine/packed/Compile ; v0.433

Closes the coverage gap flagged under v0.432: `StruveH` now numericalizes.
FLINT/arb ships no Struve kernel, so one is composed from the rigorous
*regularized* generalized hypergeometric,
`H_ν(z) = (z/2)^(ν+1) · ₁F̃₂(1; 3/2, ν+3/2; −z²/4)` (DLMF 11.2.1) — the regularized
form folds the `1/Γ` factors in, so it is entire in ν (no pole at ν = −3/2, −5/2,
…) and valid over the whole complex plane. New bridge entry `flint_num_struveh`
(`src/flint_num_bridge.c`): `acb_hypgeom_pfq(regularized=1)` × `acb_pow`, on a
hand-rolled precision ladder that pre-adds a cancellation allowance (~1.44·|z|
bits) so a large |z| is resolved in one shot while the ball ladder still renders
only correct digits. `N[StruveH[1,13/10],50]` and `N[StruveH[1,1+2I],30]` match
mpmath to all requested digits. (`N[StruveH[1,1.3],50]` now returns the machine
value — a machine `1.3` carries only 53 bits, as for every sibling; use an exact
argument for 50 digits.)

The machine surface is now complete too (previously only a slow symbolic ₁F₂ + N
round-trip, and no packed/Compile path). A fast real `double` kernel
`sf_machine_struve_h` (`src/special_functions/sf_machine.c`) — convergent
series / `Y_ν + K_ν` asymptotic (DLMF 11.6.1 + 10.17.4), picking the more accurate
regime per argument — backs the scalar path, an NDArray binary kernel
(`ndk_StruveH_c`, `REG_B(StruveH, …)`, registered → `packed_aware` + `Compile[]`
for free, as for Bessel), and `Compile[]` (`CompileDiagnostics` reports
`Compiled -> True` at scalar and rank-1; its `test_compile_coverage.c` gap entry
is retired). Scalar == List == packed == NDArray == Compile bit-for-bit;
packed 10⁶ throughput 0.027 s (16× over the unpacked path).

**Speed (cache-safe, distinct args; vs scipy 1.17 / the reference / mpmath 1.4):**
machine vectorized 27 ns/elt vs scipy 5251 (**193×**) and the reference 376413
(**~13800×** — no packed Struve path); machine scalar 0.57 µs/call vs scipy 6.47
(**11×**) and the reference 371 (**~650×**); arbitrary 50-digit 0.022 ms/call vs
the reference 0.79 (**37×**) and mpmath 0.16 (**7.5×**). Faster than both reference
systems on every axis. Accurate to the double
floor everywhere, no silent declines; in the narrow transition band z ∈ [~17,~24]
(small ν) both elementary series are intrinsically ill-conditioned and the machine
value degrades to ~1e-9 absolute (scipy's `struve` shares this) — the arb path
gives full precision there. Permanent guard: `struveh` probe in
`tools/numeric_sweep.py` (oracle `scipy.special.struve`). Attributes unchanged
(`Listable`, `NumericFunction`, `Protected`). `StruveH[nu,0]=0` and the Mellin
reduction are unchanged.

## Performance: LerchPhi machine path now uses its double kernel ; v0.427

Follow-up to v0.426. Adding the `lerchphi` coverage probe exposed a deeper issue:
`LerchPhi`'s scalar numeric path went straight to the MPFR series — **628 µs per
call** — even for machine-real arguments, although a shared `double` kernel
(`sf_machine_lerchphi`, already the Compile VM kernel) existed and was never
reached. So a 10⁶-element argument took ~650 s (the sweep probe reported no result
at all). This is the machine-scalar surface contract violated: the scalar path
must reuse the ND/Compile kernel's helper.

Fix: `lerchphi_single` now tries `sf_machine_lerchphi` first when `z, s, a` are all
real machine leaves and the convention is default, falling through to the MPFR path
on decline (`|z| ≥ 1`, a non-positive-integer `a`, overflow). `builtin_lerchphi`
threads the same kernel directly over a single NDArray argument
(`lerchphi_ndarray`, mirroring `whittaker_w_ndarray`) and returns a packed result,
delisting only for the awkward cases. Results:

- scalar `LerchPhi[0.5, 2., a]`: **628 → 2.5 µs/call (~250×)**;
- `LerchPhi[0.5, 2., v]` over 10⁶: **~650 s → 1.04 s**, now slightly ahead of the
  numpy truncated-sum baseline (1.15 s) and no longer a sweep timeout;
- a visible `NDArray` argument returns a packed `NDArray`, bit-identical to the
  scalar path (diff 0.0), accuracy ≤2.1e-16 vs the 30-digit value.

MPFR / complex / `|z| ≥ 1` paths are untouched. Verified: `lerchphi_tests` pass;
`check-packed-aware`, `check-array-exactness`, `check-nd-surfaces` green.

## Correctness: LerchPhi left a visible NDArray argument unevaluated ; v0.426

Found during the special-functions sweep. `LerchPhi[0.5, 2., NDArray[{1.5, 2.5,
3.5}]]` returned **unevaluated** (head stayed `LerchPhi`) — a visible NDArray in
any slot fell straight through `builtin_lerchphi`. Per the packed-array contract
that is a wrong answer, not merely a slow path: the transparency gate leaves
visible NDArrays alone, and `LerchPhi`'s only ND kernel is the N-ary Compile
kernel (`NDKN_LerchPhi`), not an element-wise one, so nothing handled it. (The
static `check-packed-aware` and curated `check-nd-surfaces`/`check-array-exactness`
audits all missed it — `LerchPhi` had no element-wise dispatch site to diff and no
probe, the same blind spot that hid `Commonest` and the `int64` NDArray truncation.)

Fix: `builtin_lerchphi` now delists any NDArray argument and re-evaluates
(`ndarray_delist_and_reeval`), so `Listable` threads every element through the
accurate scalar path, and `LerchPhi` is added to `pack.c`'s `AWARE` list so the
gate hands packed buffers to the builtin rather than materialising them a step
early. `LerchPhi[0.5, 2., NDArray[{1.5,2.5,3.5}]]` is now `{0.554291, 0.219693,
0.119386}`, matching the scalar path bit-for-bit; a 2000-element auto-packed List
argument matches element-by-element too. Audits green (`check-packed-aware`,
`check-nd-surfaces`, `check-array-exactness`); `lerchphi_tests` pass.

## Performance: Fresnel machine kernel — real-arithmetic continued fraction ; v0.425

Special-functions perf sweep. `FresnelC`/`FresnelS` over 10⁶ reals ran ~5× slower
than SciPy. Profiling `frenel_double` (`src/special_functions/sf_machine.c`) split
the cost cleanly: the power-series branch (|x| ≤ 1.5) is already fast (~24 ns/el,
SciPy-competitive), but the Lentz continued-fraction branch (|x| > 1.5) was **13×**
slower (95 vs 7 ms / 300 k). Cause: it was written with C99 `double _Complex`, and
each `1/z` compiles to libgcc's `__divdc3` (the Annex-G infinity-safe complex
divide) — a function call per iteration. Rewrote the CF in explicit real/imag pairs
with the plain reciprocal `z*/|z|²` (the CF intermediates stay O(1)…O(n²) in this
range, so no overflow scaling is needed). The branch dropped ~1.9× and the values
are unchanged to ≤1.7e-16 relative (full double precision, bit-tracking the
30-digit value).

Net: `FresnelC[v]` over 10⁶ went **147 → 59 ms**, closing the gap from 5.1× to
**2.36×** vs SciPy. The residual is the CF converging slowly just above the x=1.5
crossover (it is designed for large x); SciPy's cephes `fresnl` uses rational
auxiliary functions f(x),g(x) there instead of iterating — a dedicated
auxiliary-rational path is the scoped follow-up (raising the series crossover was
rejected: it would trade away accuracy). MPFR path untouched. Only `sf_machine.c`.

## Performance: PolyLog machine kernel — constant-ζ tables + integer power ; v0.424

Part of the special-functions performance sweep (the review the Whittaker fix
began, now applied to every head). `PolyLog` was the largest machine-precision
gap: `PolyLog[2, v]` over 10⁶ reals ran **24× slower than SciPy's `spence`**
(453 ms vs 19 ms). Two root causes in `sf_machine_polylog`
(`src/special_functions/sf_machine.c`):

1. The Jonquière `mu`-series (the `0.5 < x < 1` branch) called `sf_machine_zeta`
   (Euler–Maclaurin / functional equation) **once per term** for `ζ(s−k)`. For an
   integer order `s` those summands are the SAME constants for every element, so a
   buffer recomputed ~15–20 zeta evaluations per element. They are now read from
   two `static const` tables — `ζ(2..24)` and `ζ(0..−44)` (the non-positive ones
   are the exact Bernoulli rationals, rounded to double) — via `polylog_zeta_int`,
   which falls back to the kernel only outside the tabulated range. The `mu`-series
   branch dropped **5.5×** (368 → 67 ms / 300 k).
2. The defining series (`|x| ≤ 1/2`) called `pow(k, s)` per term; for integer `s`
   (dilog, trilog, …) it now uses a short integer power — bit-exact (`k·k` is exact)
   and far cheaper than the transcendental `pow`.

Net: `PolyLog[2, v]` over 10⁶ went **453 → 76 ms (≈6×)**, closing the gap from
24× to **4.75×** vs SciPy. The residual is architectural — SciPy's `spence` is a
specialised minimax-rational *dilog* (~16 ns/element, no loop), whereas Mathilda
computes the general `PolyLog[s, x]` by series; full parity would need a dedicated
rational dilog for `s = 2` (recorded as a scoped follow-up in the triage report,
`tasks/special_functions_perf_review_2026-10-16.md`). Accuracy is unchanged
(relerr ≤ 1.3e-16 vs the 30-digit value, Li₂ and Li₃); the MPFR scalar path
(mpfr_zeta/gamma in `polylog.c`) is untouched. Only `sf_machine.c` changed.

## Performance: WhittakerW integer-`m` machine kernel — digamma recurrence ; v0.423

Reviewed `WhittakerM` / `WhittakerW` machine- and arbitrary-precision speed
against SciPy and the reference (both heads were already wired across the
scalar / NDArray-packed / `Compile[]` surfaces, but their speed had never been
measured). One real gap surfaced: vectorized `WhittakerW` at integer or
half-integer `m` (so `b = 2m+1` is an integer) was **1.8× slower than SciPy**
over 10⁶ reals — 1510 ms vs 837 ms — while every other regime already matched
or beat it.

Root cause: for integer `b`, `sf_machine_hyperu` takes the DLMF 13.2.9 log
series (`hyperu_integer_b`), which called `sf_machine_digamma` **three times per
term** (`ψ(a+k)`, `ψ(k+1)`, `ψ(n+k+1)`), each a shift loop + `log` + 7-term
asymptotic. Since those arguments step by 1 each term, they now advance by the
exact recurrence `ψ(x+1) = ψ(x) + 1/x` from three seed evaluations — one
division per term instead of a full digamma. The asymptotic branch has already
peeled off every terminating (pole) case before this series runs, so `a` is
never a non-positive integer and `a+k` never crosses a pole.

Result (10⁶-element packed buffer, Apple M-series): `WhittakerW` integer-`m`
**1510 ms → 420 ms** (3.6×), now **1.8× faster than SciPy** and ~1000× faster
than the reference (which has no packed Whittaker path: 20 s for the same
`WhittakerM` buffer). Scalar integer-`m` latency 3.55 → 1.95 µs/call. Accuracy
is unchanged (≤1e-14 relative vs the 30-digit FLINT value), and the kernel stays
bit-for-bit identical across the scalar, NDArray and `Compile[]` surfaces
(verified: scalar − NDArray = scalar − Compile = 0.0 at every probe). The MPFR
path (via the `HypergeometricU` / `Hypergeometric1F1` FLINT evaluator) is
untouched and already beats the reference on every case.

Permanent guard: `whittakerm` / `whittakerw` probes added to
`tools/numeric_sweep.py` (the coverage sweep), composing SciPy's
`exp·z^(m+½)·{hyp1f1,hyperu}` as the fair baseline — Whittaker is now faster
than SciPy, so it belongs in the coverage sweep rather than the gap-driven
`bench-gap` job. Only `src/special_functions/sf_machine.c` changed on the kernel
side.

## Portability: Windows CI — a third unused-static orphan under the threads-off build ; v0.422

Follow-up to v0.421. With the two `#ifndef _WIN32` orphans fixed, the Windows
`make` step advanced and then failed on `src/compile/compile_vm.c:860:
'par_chunk' defined but not used`. Same shape, different guard: `par_chunk`
(and its `ParCtx`) are reached only from `vm_par_run`'s `#ifdef
MATHILDA_THREADS` branch, but their definitions sat outside it. On Windows the
makefile forces `USE_THREADS=0` (no `pthread`), so `MATHILDA_THREADS` is
undefined and the helper compiled unreferenced → `-Werror=unused-function`.
Guarded the `ParCtx` typedef and `par_chunk` with `#ifdef MATHILDA_THREADS`
(`VM_STACK_SLOTS` stays outside — the serial VM frames use it too). No
behaviour change anywhere threads are enabled (`$VersionNumber` 0.421 ->
0.422).

This one was missed by v0.421's by-hand audit (its name matched no thread
keyword). The lesson, applied here: reproduce the **exact** Windows flag set
locally — `USE_ECM=0 USE_READLINE=0 USE_GRAPHICS=0 USE_LAPACK=0 USE_FLINT=0
USE_REGEX=0 USE_FFTW=0 USE_THREADS=0` — for both `make` and `make lib`. That
build (clean, zero `unused-function` diagnostics) catches every
guard-driven orphan at once, rather than discovering them one CI cycle at a
time. The only class it still cannot see is a genuine error *inside* a
`#ifdef _WIN32` branch, which needs the real MinGW compile.

## Portability: unblock the Windows CI leg — two `#ifndef _WIN32` unused-static orphans ; v0.421

The `build-windows` (MSYS2/MinGW UCRT64) leg had been red on every push since it
was added (v0.406): v0.420 fixed the first Windows compile error
(`open_memstream` in `src/print.c`), but because the build stops at the first
error, fixing it only exposed the next one. Two sources had the same latent
shape — a `static` helper **defined outside** any guard while **every caller**
sits inside a `#ifndef _WIN32` block, so on Windows the function is compiled but
unreferenced and `-Werror=unused-function` rejects it (no behaviour change on

## DSolve: new inverse-orientation method — solve first-order ODEs via the reciprocal x(y) ; v0.416

that no specialist solves in the y(x) orientation is retried in the x(y)
orientation, where its reciprocal `dx/dy == 1/F` is often a class the cascade
already handles — e.g. `y' == 1/(x y + x^3 y^3)` inverts to `x'[y] == x y + x^3 y^3`,

among the first-order backstops, top-level only, re-entry guarded, and with its
speculative sub-solve messages suppressed; `MATHILDA_NO_INVERSE` disables it for
A/B. §2.2.45 corpus 93→94/100, 0 FAIL, no regression.

## Divergent definite integrals with an interior/boundary pole stay unevaluated (bug: Integrate[1/x,{x,-1,1}] -> 0) ; v0.411

`Integrate[1/x, {x, -1, 1}]` (no `PrincipalValue`) returned `0`, a wrong answer: an
ordinary (non-PV) definite integral whose integrand has a non-integrable pole in the
CLOSED interval diverges and must be left unevaluated (only `PrincipalValue -> True`
gives the Cauchy value `0`). Four "trick" stages applied an identity valid only for a
convergent integrand without a convergence check, so an odd pole's two infinite
one-sided pieces cancelled to the principal value:

- **King reflection** (`integrate_king.c`): `∫f = c(b-a)/2` from `f+f̃ = c` — for `1/x`
  on `[-1,1]`, `f+f̃ = 0 -> 0`, and the symmetric NIntegrate backstop also averages to
  ~0. Now declines on an interior zero of `Denominator[Together[f]]`.
- **Origin symmetry** (`integrate_symmetry.c`): odd->0 / even->2·half. Now declines a
  non-integrable pole at the centre (`Limit[x f, x->0] != 0`); and propagates
  `PrincipalValue` into the half, so a genuine PV even reduction
  `∫Cos[x]/(x^2-a^2) over R (PV) = 2 PV ∫_0^inf` takes its half as a PV.
- **Newton-Leibniz** (`integrate_newton_leibniz.c`): the telescoping over pole
  breakpoints silently returned the PV. Now tests integrability on the integrand
  (`Limit[(x-p) f, x->p] != 0`) at interior poles AND finite endpoints, emitting
  `Integrate::idiv` and declining.
- **Differentiation under the integral sign** (`integrate_diffunderint.c`): declines a
  finite interval whose denominator vanishes strictly inside.

The integrability test distinguishes a genuine pole (order >= 1) from an integrable or
removable singularity, so `∫Log[x]` on `[0,1] = -1`, `∫1/Sqrt[x]` on `[0,1] = 2`,
`∫Sin[x]/x` on `[-1,1] = 2 SinIntegral[1]`, and convergent odd/even reductions are
unchanged. Covered by `tests/test_integrate_divergent.c` (16 cases) and the restored
`test_integrate_principalvalue.c` default-off test.

## Parser: empty argument / element slots are Null ; v0.408

The reference reads an omitted element next to a comma as `Null`. Mathilda used to
drop a leading comma silently (`f[,x]` parsed as `f[x]`, `{,1}` as `{1}`) and
rejected trailing and doubled commas as syntax errors.

| Input | Before | Now (= reference) |
|---|---|---|
| `f[,x]` | `f[x]` | `f[Null, x]` |
| `f[x,]` | syntax error | `f[x, Null]` |
| `f[x,,y]` | syntax error | `f[x, Null, y]` |
| `{,1}` / `{1,}` | `{1}` / syntax error | `{Null, 1}` / `{1, Null}` |
| `f[]`, `{}` | empty | empty (unchanged) |

- **`src/parse.c`**: the duplicated argument loops of `parse_list` and
  `parse_function` are replaced by one `parse_sequence(s, close, what, &n)`,
  which implements the rule: an empty pair has no elements, and every slot
  around a comma is an element, `Null` when nothing is written. A missing
  closer (`f[x y`, `{1, 2`) is still a syntax error, now reported once at the
  level where it is missing instead of once per enclosing bracket.
- Regression test: `test_parse_empty_slots_are_null` (`tests/test_parse.c`).

## Parser: a bare `[` is a syntax error, not a NULL-head call (segfault fix) ; v0.407

`f[x,[x]]` and `Solve[x,[x]]` (issue #89) segfaulted. `parse_primary` treated a
`[` that has nothing in front of it as an "anonymous function" and built an
`EXPR_FUNCTION` with a **NULL head**. It survived parsing (`FullForm` printed it as
`Null[x]`), and the evaluator crashed reading `head->type` in `evaluate_step`. No
other code builds a NULL-head node.

- **`src/parse.c` `parse_primary`**: a leading `[` is now a parse failure, so the
  input gets the usual `syntax error` report (REPL: `Parse error`; `-file`: exit
  1), as in the reference. `g[[x]]` (Part) and `f[x][y]` are postfix on a real head
  and are unaffected.
- **`;` followed by `[`** (`a; [y]`): an implicit trailing `Null` is no longer
  inserted when the next token is `[`. Before this, the `[y]` was silently parsed
  as a call on `CompoundExpression[a, Null]`. Now it is a syntax error. Trailing
  `a;`, `f[a;]` and `(a;)` still give `CompoundExpression[a, Null]`.
- **Leak**: `parse_function` now frees its `head` on both failure paths. Its only
  caller drops the head when the call returns NULL, so every function-call syntax
  error (`f[x,]`, `f[x, (]`, …) used to leak the head. Valgrind on the error path
  now matches the clean-run startup baseline.
- Regression test: `test_parse_headless_bracket` (`tests/test_parse.c`).

## Definite integration of the parameter / Frullani-log family ; v0.405

New definite-integration stage `Integrate\`FeynmanParameter`
(`src/calculus/integrate_feynparam.c`) — differentiation under the integral sign
w.r.t. a present parameter, specialised to the family that makes the trick close in
one step:
`Integrate[(Sum_i c_i x^(e_i))/Log[x], {x,0,1}] = Sum_i c_i Log[e_i + 1]`, valid when
`Sum_i c_i = 0` (so the `1/Log[x]` singularity at `x=1` is integrable) and each
`e_i + 1 > 0`. Closes the archetype `Integrate[(x^a-1)/Log[x], {x,0,1}] = Log[a+1]`
(`a > -1`) — the MSE *tough integrals* thread's parameter-differentiation example —
and generalises it: `(x^a-x^b)/Log[x] → Log[(a+1)/(b+1)]`,
`(x^3-x^(1/2))/Log[x] → Log[8/3]`, `(2x^4-x-1)/Log[x] → Log[25/2]`.

- The inner `x`-power integral is taken **directly** as `1/(e+1)` rather than via
  `Integrate`, which sidesteps the current `Beta[1+a,1]` / `Gamma[1+a]/Gamma[2+a]`
  form the simplifier does not reduce to `1/(1+a)` (so the integrate-back closes),
  and keeps the stage cheap — it does no long re-entrant `Integrate` and stays clear
  of the slow parametric cascade. Each `e_i + 1 > 0` is proved from Assumptions, and
  the closed form is numerically cross-checked against `NIntegrate` at an in-domain
  parameter sample before returning; it declines otherwise (`Sum c_i != 0`, a
  non-power term, an unprovable domain, or a failed check). `Integrate[1/Log[x],
  {x,0,1}]` (sum of coefficients `!= 0`, divergent) is correctly left unevaluated.
- Reachable as `Method -> "FeynmanParameter"`; runs in the pre-FTC `[0,1]` block
  (these integrands have no elementary antiderivative). Symbolic-result stage, so
  packed/NDArray and `Compile[]` do not apply.
- Completes the MSE "simple techniques" campaign: the dedicated corpus
  `tests/MseTrickIntegralsCorpus.m` is now 15/15 CORRECT, 0 WRONG. See
  `tasks/mse_trick_integrals_2026-10-14.md`.

## Definite integration by general King reflection ; v0.404

New definite-integration stage `Integrate\`King` (`src/calculus/integrate_king.c`),
the general **King reflection** `x -> a+b-x`: for a finite interval
`Integrate[f,{x,a,b}] = (1/2) Integrate[f(x)+f(a+b-x),{x,a,b}]`, and when the
reflected sum `f(x)+f(a+b-x)` is a **constant** `c` the value is `c (b-a)/2`. This
closes the classic trick integral with no elementary antiderivative
`Integrate[1/(1+Tan[x]^Sqrt[2]), {x,0,Pi/2}] = Pi/4` (and the whole
`1/(1+Tan[x]^s)` / `1/(1+Cot[x]^s)` family for any real `s`, integer or
irrational).

- The constancy of `f(x)+f(a+b-x)` cannot be proved symbolically — Simplify does
  not know `(Tan·Cot)^s = 1` — so the constant is read at the interval **midpoint**
  (`Simplify[h /. x->(a+b)/2]`), screened numerically across several interior
  points, and the final value is **cross-checked against `NIntegrate`**. A
  mis-detected constancy produces `c(b-a)/2 != ∫f`, which the check rejects, so the
  stage never returns a wrong answer; it declines (returns the input unevaluated)
  otherwise.
- **Numeric-domain precondition** (correctness + robustness): King is an inherently
  numeric method, so it fires only on a parameter-free integrand (one that
  evaluates to a number at a numeric `x`), screened cheaply up front before any
  reflection/Simplify work. A parametric integrand such as `(x^a-1)/Log[x]` is out
  of scope and declined immediately.
- Complements the existing `integrate_kingreflect_try` (the distinct `x·g(x)`,
  `g` invariant shape). Reachable as `Method -> "King"` / `"Reflection"`; runs
  before Newton–Leibniz so these no-elementary-antiderivative integrands close
  without a spurious `Integrate::nonelem`.
- Symbolic-result stage (returns closed-form constants), so the packed/NDArray and
  `Compile[]` surfaces do not apply. No new leaks (identical fixed startup
  baseline); valgrind shows no invalid access; check-c99 / check-messages pass.
- Corpus `tests/MseTrickIntegralsCorpus.m` + gate `mse_trick_corpus_tests`
  (`tests/test_mse_trick_corpus.c`).

## Definite integration by series expand → term-by-term → resum ; v0.404

New definite-integration stage `Integrate\`SeriesExpansion`
(`src/calculus/integrate_series.c`) — the **alternating sibling** of
`integrate_ratlog01_try`. It closes log-weighted rational integrals on `[0,1]`
with a root-of-unity denominator `1 ± x^d` whose antiderivative is a non-elementary
PolyLog, by expanding the geometric series, integrating term-by-term with the exact
identity `Integrate[x^m Log[x]^k, {x,0,1}] = (-1)^k k!/(m+1)^(k+1)`, and resumming
each residue class with the existing `Sum[]` engine (→ `Catalan`, `DirichletBeta`,
`Zeta`). New results include:

- `Integrate[Log[x]/(1+x^2), {x,0,1}] = -Catalan`
- `Integrate[Log[x]^2/(1+x^2), {x,0,1}] = Pi^3/16`
- `Integrate[Log[x]/(1+x), {x,0,1}] = -Pi^2/12`, `…^2/(1+x) = (3/2)Zeta[3]`,
  `…^3/(1+x) = -7 Pi^4/120`
- `Integrate[x^2 Log[x]/(1+x^2), {x,0,1}] = Catalan - 1` (polynomial-division path)
- general cyclotomic denominators, e.g. `Log[x]/(1+x^3)`, `Log[x]^2/(1+x^2+x^4)`.

- **Correct by construction**: the general coefficient comes from exact cyclotomic
  divisibility (`PolynomialRemainder[1 ∓ x^d, Q, x] == 0`) and the geometric-series
  identity — never inferred from samples — and the `Log[x]^k` weight (`k >= 1`)
  forces the resummed p-series to converge absolutely (`p = k+1 >= 2`). The value is
  additionally **cross-checked against `NIntegrate`**; it declines on any
  non-rational factor, non-`[0,1]` interval, pole at `x=0`, non-cyclotomic
  denominator, or unclosed resummation. The `1 - x^m` HurwitzZeta family stays
  owned by `integrate_ratlog01_try` (runs first); the alternating `1 + x^d` case it
  cannot represent is this stage's.
- Reachable as `Method -> "SeriesExpansion"` / `"SeriesTermByTerm"`; runs in the
  pre-FTC `[0,1]` block so these PolyLog-antiderivative integrands close without a
  spurious `Integrate::nonelem`.
- Symbolic-result stage, so packed/NDArray and `Compile[]` do not apply. No new
  leaks; check-c99 / check-messages pass; the three existing definite-integral
  corpora (extreme, singular, intrat) stay green.

These extend the definite-integration suite toward the "simple techniques" of the
MSE *tough integrals* thread; see `tasks/mse_trick_integrals_2026-10-14.md`.

## LegendreP / LegendreQ: associated forms evaluate by Horner over arrays ; v0.376

Stress-testing the associated `LegendreP[n, m, x]` (and the type-2/3
`LegendreP[n, m, a, x]`) against SciPy's `lpmv` over machine arrays found a
high-degree performance pathology.

- **The gap.** These forms build the explicit degree-`n` polynomial and evaluate
  it over the buffer as a sum of monomials `Σ cₖ xᵏ` -- each `xᵏ` its own
  full-buffer `pow()`. So the cost was `O(n)` `pow()` passes and grew
  pathological with `n`: `LegendreP[30, 4, array]` over 10⁶ points did not finish
  in ~85 s (SciPy's `lpmv`: 20 ms). Low degree was already correct, packed, and
  ahead of SciPy -- only high degree suffered.
- **The fix.** For a packed-List / `NDArray` machine argument the polynomial is
  now evaluated by **Horner in machine `double`** (`leg_poly_from_coeffs`, plus
  `legendre_2f1reg_core` for types 2/3) -- `O(n)` fused multiply-adds, no
  `pow()`. The Plus/Times buffer fast paths take a Real scalar but not a
  Rational, so the coefficients are coerced to `double` (exactly what the buffer
  arithmetic did anyway), keeping the answer unchanged to rounding (~1e-13
  vs the scalar path). The Horner route fires **only** for a numeric buffer, so
  the symbolic output of every form -- `LegendreP[5, x]`, `LegendreP[5, 3, x]`,
  the type-2/3 branch forms -- is byte-identical. `LegendreQ`'s associated form
  shares `leg_poly_from_coeffs` and is fixed with it.
- **Result (10⁵ points).** `LegendreP[12, 3, x]` 14.8 ms → 6.7 ms;
  `LegendreP[30, 4, x]` >85 s → 10.6 ms; `LegendreP[50, 3, x]` → 20.5 ms. The
  three-argument form is now faster than SciPy's `lpmv` at every degree tested
  (≈1.4–1.9×); it was already correct (matches `lpmv`), packed, and
  cross-surface consistent. A grid of `(n, m, x)` points (real/complex,
  types 1/2/3) is unchanged against the scalar path to ~1e-12.

Touched: `src/special_functions/legendre.c`, `src/version.h`. Spec:
`docs/spec/builtins/special-functions.md`.

## LaguerreL: generalized three-argument form threads over arrays ; v0.375

Stress-testing `LaguerreL` against SciPy (`eval_laguerre` / `eval_genlaguerre`)
and the reference over machine arrays exposed a performance and consistency gap in
the **generalized three-argument** form `LaguerreL[n, a, x]` over a packed-List
or visible `NDArray` argument.

- **The gap.** The two-argument form reaches a binary ND kernel at the REPL
  element-wise fast path, but a three-argument call has no arity-≥3 element-wise
  path there (the N-ary kernel is read only by `Compile[]`). So `LaguerreL[n, a,
  NDArray]` fell through to the builtin and re-expanded the explicit degree-`n`
  polynomial over the buffer — correct, but ~20–40× slower than the scalar
  machine recurrence and **not bit-identical** to it (the array path differed
  from the scalar/List/`Compile[]` answer by ~1e-12).
- **The fix.** `builtin_laguerre_l` now threads the *same* machine helper
  `sf_machine_laguerre_l_assoc[_c]` element-wise over a real or complex buffer
  (`src/special_functions/laguerre_l.c`), holding the integer order and machine
  parameter constant and returning a buffer that inherits the argument's
  presentation (packed List ↔ visible `NDArray`). Because it reuses the scalar
  path's helper, `scalar == List == packed == NDArray == Compile[]` is now
  bit-identical for the three-argument form too. An `"int64"` buffer, a
  non-machine parameter, order `n > 1000`, or an overflowing element declines
  and delists to the exact / MPFR route unchanged.
- **Result (1e6 points).** `LaguerreL[12, 2.5, x]` over a packed array: 148 ms →
  39 ms. `LaguerreL[50, 2.5, x]`: previously exhausted memory, now 222 ms. The
  three-argument form is now faster than SciPy for degrees up to ~12 (≈1.75×),
  at parity at degree 50, and ~50–500× faster than the reference (which does not
  vectorise `LaguerreL` over a packed array). The two-argument form was already
  ~4.7× faster than SciPy and is unchanged. A full grid of 900+ `(n, a, x)`
  points (real/complex, integer/non-integer/negative order, orders to 300)
  matches mpmath to < 4.1e-14.

Touched: `src/special_functions/laguerre_l.c`, `src/version.h`. Spec:
`docs/spec/builtins/special-functions.md`.

## LaguerreL: Laguerre and generalized Laguerre polynomials ; v0.374

New builtin `LaguerreL[n, x]` (Laguerre polynomial `L_n(x)`) and `LaguerreL[n,
a, x]` (generalized `L_n^(a)(x)`, with `LaguerreL[n, x] == LaguerreL[n, 0, x]`),
to the ChebyshevU bar — symbolic, numeric, packed/NDArray, and `Compile[]`.

- **Exact polynomial.** A non-negative integer order yields the explicit
  polynomial: exact rational coefficients via the three-term recurrence for a
  numeric/absent parameter `a`, and the expanded polynomial in `a` and `x` for a
  symbolic `a`. `LaguerreL[5, x] = 1 - 5 x + 5 x² - 5/3 x³ + 5/24 x⁴ - 1/120 x⁵`,

  `Table[LaguerreL[10, x], {x, 1, 5}] = {168919/403200, -4381/14175,
  -31361/44800, 931/675, 254927/145152}`.
- **Numerics.** Integer order with an inexact argument uses the *stable*
  recurrence rather than polynomial substitution, so `LaguerreL[100, 0, N[5,
  20]] = 1.4555271625328812607` instead of the catastrophically-cancelled
  `1.4557…`. Non-integer / complex order evaluates through the entire form
  `Binomial[n+a, n] Hypergeometric1F1[-n, a+1, x]` — machine or MPFR, real or
  complex: `LaguerreL[6., 5] = -2.09028`, `LaguerreL[6. - I, 5] = -2.76039 -

- **Special values.** `LaguerreL[0, x] = 1`, `LaguerreL[n, 0] = Binomial[n+a,
  n]` (= 1 for the ordinary polynomial).
- **Derivative.** `D[LaguerreL[n, x], x] = -LaguerreL[n-1, 1, x]`;
  `D[LaguerreL[n, a, x], x] = -LaguerreL[n-1, a+1, x]`.
- **Fast paths.** A binary ND kernel (`sf_machine_laguerre_l[_c]`) gives the
  two-argument form NDArray + packed + `Compile[]` + auto-compilation, with a
  machine-complex arm; the scalar machine path dispatches to the same helper, so
  scalar == List == packed == NDArray == `Compile[]` bit-for-bit. The generalized
  three-argument form adds an N-ary kernel for scalar `Compile[]`.
- **Attributes.** `Listable`, `NumericFunction`, `Protected`. Diagnostics route
  through `mth_message` (`LaguerreL::argt`).

## RealDigits: correct exponent and digits at powers of the base ; v0.358

**Bug fix (correctness).** `RealDigits[x]` for an inexact `x` returned a wrong
second element (the exponent) — and, for an exact power of the base, wrong
digits — whenever `x` sat at or just below a power of the base. The digit list
was placed from the full-precision canonical exponent (`mpfr_get_str` at the
available precision), but the reported exponent and `start_pos` came from two
*different*, carelessly-rounded estimates, so the two disagreed exactly at the
boundary:

- `RealDigits[0.9991251116426123]` → exponent `1` (should be `0`); likewise
  `0.999`, `0.9999999999`, `99.6` (gave `3`), `0.0999999999999999` (gave `0`).
  Cause: a fix-up that re-derived the exponent with a **2-significant-digit,
  round-to-nearest** `mpfr_get_str` — a `99…` tail rounds up to `10…` and carries
  the exponent a whole decade.
- `RealDigits[1000.]` → `{{0,0,…,Indeterminate}, 4}` (should be
  `{{1,0,0,0,…}, 4}`); same for `N[10^15]`. Cause: `rd_inexact_natural_exp`
  used `floor(log(x)/log(b)) + 1`, and `log(1000.)/log(10.) = 2.9999999996`
  floors to 2, so `start_pos` was one short and the leading digit fell off the
  front of the window.
- Large magnitude: `RealDigits[N[9959306433341448*10^240]]` → exponent `257`
  (should be `256`) — the same `99…`-carry.

**Fix (`src/real.c`).** `rd_inexact_natural_exp` now reads the exponent from
`mpfr_get_str` at the *same* digit count (`rd_available_digits`) and rounding
(`RNDN`) that `rd_inexact_canonical_digits` uses to lay the digits out, so the
reported exponent and the digit placement are the one same quantity and cannot
disagree. A carry there (a value that rounds up to a power of the base at full
precision) is self-consistent: the digits become `10…` and the exponent moves
with them. The old 2-digit boundary fix-up is removed. The no-`MPFR` build keeps
the `log`-quotient estimate. Controls unchanged: `123.55555` → `{…, 3}`,
`0.89`/`0.95`/`0.1` → `{…, 0}`, `1.0` → `{…, 1}`, `N[Pi, 50]` → `{…, 1}`,

**A cross-system stress test of `ChebyshevT` confirmed it correct and highly

complex path merely carried a zero imaginary part through). No new builtins,

## MeijerG: a machine kernel for the log case ; v0.446

The log case of `MeijerG` (two of `b1…bm` an integer apart, where Slater's
`π/sin` coefficients have cancelling poles) used to decline every machine point
to the arb perturbation engine: the shootout's `MeijerGlog` row cost **119 s per
10⁶-element buffer** and 456 µs per scalar call. It now has its own machine
kernel. The buffer takes ~0.3 s (~375×) and a scalar call ~3 µs (~140×); complex
`z` takes ~6 µs. Machine values agree with 30-digit references to ≤ 4.5×10⁻¹⁶.

- **Method** (`src/special_functions/sf_machine_meijerg.c`). `G = −Σ Res F(s) w^s`
  over the poles `s = β + k` of each integer-spaced class of `b1…bm` (base `β`,
  pole order up to the class size `T`). The residue at `w^(β+k)` is a polynomial
  of degree `< T` in `log w` whose coefficients `c[k][j]` do not depend on `z`.
  The plan tabulates them once, 256 terms per class (`SfMgLogTab`): the Laurent
  expansion of `F` about `β` comes from arb (`flint_mg_laurent`, new in
  `src/flint_num_bridge.c`: products of `acb_poly_rgamma_series` with the known
  pole orders divided out). Each next row comes from the exact step
  `F(s+1) = F(s) R(s)` with `R` rational, as truncated power series in `ε` in
  double-double. A linear factor whose constant is an exact (snapped) zero only
  moves the pole order.
- **Per point.** Each class is summed in double while measuring its own
  cancellation (term mass against the sum). Past 3 bits it is re-summed with
  `log w` and `w` in double-double (`src/special_functions/sf_dd.h`, new:
  header-only dd/complex-dd arithmetic with QD-style `exp`/`log`/`sincos`,
  Dekker products, no FMA). Past 45 bits, or at the end of the table, the point
  goes to arb as before. Integer parameter differences are snapped by the same
  `is_int` rule that detected the case.
- **A parameter-rounding fix found on the way.** The dual expansion (`p ≥ q`)
  formed `1 − b` in double. `MeijerG[{{1,2},{}},{{1/3,1/5},{}},5.]` amplifies
  that 5.5×10⁻¹⁷ rounding into a 7×10⁻¹⁵ error (`∂G/∂b ≈ 80`). The log table now
  carries the dual's parameters exactly (hi + lo): 1 ulp. The non-log Slater
  dual still forms `1 − b` in double, unchanged.
- **Plan lifetime.** A log-case plan owns heap tables: `sf_mg_plan_free`, and
  `sf_mg_plan_get`, which looks up / publishes to the process-wide 16-slot plan
  memo (ownership moves into the memo). The scalar builtin and the buffer path
  memoise log-case plans, so repeated calls build the table once (~100 µs). The
  `Compile[]` / n-ary kernel memoises every plan, as before. Past 16 parameter
  sets a plan is built and freed per call.
- **Tests** (`tests/test_meijerg.c`). New `test_mg_log_case`: 36 references
  (real/complex lanes, negative axis, a triple pole, equal `b`'s, 1/Γ zeros on the
  lattice, mixed classes, complex parameters, `n > 0`, `p = q` both sides, `p > q`,
  `r ≠ 1`) at 1×10⁻¹⁵. A 10⁵-buffer timing guard (< 1.5 s; the arb path took
  ~12 s). 24 parameter sets past the memo. Bit-for-bit
  scalar = List = packed = NDArray = Compile surface checks for the log case
  (real, complex, the dual, a triple pole). valgrind: equal to the `1+1`
  startup baseline.

## FactorInteger: rebuilt — word engine, native SIQS + block Lanczos, every method callable as `FactorInteger`name` ; v0.452

`FactorInteger` moved from `src/facint.c` into `src/numbertheory/factorinteger/`, one
file per algorithm. Every method was rewritten or tuned, and each one is now a builtin of

**Automatic.**
- **Below 2^64: a new word engine.** Montgomery arithmetic, a deterministic Miller–Rabin
  test, and micro-ECM (Suyama curves, baby-step/giant-step stage 2), with rho and SQUFOF

## FactorInteger: parallel QS and ECM, double large primes, faster word methods ; v0.453

- **Parallel quadratic sieve.** From 45 digits, polynomial families are sieved on every
  online CPU (up to 16), one A per thread. Each thread keeps a private relation log, and
  the main thread replays the logs in worker order, so the result is the same for a given
  thread count. Timings: 60 digits 2.6 s → 0.46 s; 50 digits 0.23 s → 0.054 s.
- **Parallel ECM.** For n ≥ 2^160, GMP-ECM curves (thread-safe since 7.0) run one per
  thread. Sigmas are assigned in curve order and successes are taken in curve order.
- **Thread safety for timeouts.** The shared region helper (`fi_par.c`) blocks signals on
  the workers, opens a `tc_async_defer` region, and parks the main thread in
  `pthread_join`. `src/core.c`: `tc_alloc_safepoint` now takes a deferred
  `TimeConstrained` jump only on the main thread, since workers allocate through the same
  guarded GMP hooks.
- **`TimeConstrained` budgets.** These are process CPU time, so they are consumed
  correspondingly faster while factoring threads run.
- **Double large primes** (QS, kN ≥ 240 bits). Cofactors up to lp_max^1.8 are split in word
  arithmetic. Partial relations are now edges of a large-prime graph: union-find counts
  cycles, and each cycle becomes a full relation via the spanning-forest path (the old
  one-prime pairing is the 2-cycle case). 80 digits: 217 s → 145 s single-threaded
  (PARI 398 s).
- **Automatic.** Adds a two-limb micro-ECM tier (8 curves, B1 = 150) for 64–126-bit
  composites. The QS crossover was recalibrated: below ~45 digits QS follows the Fermat
  probe directly; p+1 runs one seed below 70 digits. Random 40-digit batch:
  1.9 s → 0.79 s.
- **Faster setup.** The Knuth–Schroeppel multiplier uses word Jacobi symbols and
  (kN/p) = (k/p)(N/p). It was 14,000 `mpz_kronecker` calls, half of a 30-digit QS run.
- **Named methods on words** take an allocation-free path, including a fast word
  perfect-power test (prime exponents only). `FactorInteger`PollardRho` on a 40-bit
  input now costs the same as Automatic (9 µs). Lehman uses inverse-multiply trial
  division (24 µs at 40 bits; FLINT 23 µs).
- **Bug fixes.**
  - Word SQUFOF falls back to two-word forms when kN overflows: it failed on 10% of
    60-bit semiprimes.
  - Lehman and Fermat fall back to their bignum versions beyond the word range.
  - CFRAC could loop for ever. For some (N, k), every dependency of the expansion of
    sqrt(kN) is trivial (an independent Python reproduction confirms it for
    12791 · 5060983 with k = 2, both primes ≡ 7 mod 8). CFRAC now switches multiplier,
    with a fresh base and relation store, when the period closes or after three
    all-trivial solves.
  - CFRAC and Dixon report a large prime that divides n (possible on small n) as the
    factor.

## FactorInteger: threaded CFRAC and Dixon relation collection, parallel p+1 seeds ; v0.454

After the QS sieve and ECM curves (v0.453), the remaining single-core methods with independent work
now run on threads.

- **CFRAC.** The continued-fraction recurrence is sequential, but it costs about a tenth of the trial
  division of each Q, so collection is pipelined. In each parallel region, worker 0 first extends the
  expansion into the *next* batch, then joins the other workers trial-dividing the *current* batch.
  Work is claimed in chunks of 64 terms, because early abort makes the costs uneven. The main thread
  then replays the hits in term order through the unchanged logic: the large-prime-divides-n check,
  the solve, and the multiplier restart on a closed period or repeated trivial solves. A restart
  discards the batch generated ahead. Batches start at 64 terms and double to 1024 per thread.
- **Dixon.** The main thread draws a batch of random words. The workers build and trial-divide the
  candidates (sqrt(kN) + j), and the hits are replayed in draw order. The context generator is then
  rewound to exactly where the serial loop would stop, so later splitters see the same random stream.
- **p+1.** The seeds (three for the method, and for Automatic from 70 digits) run one per thread,
  through all three backends: GMP-ECM, FLINT and native. The first success in seed order is taken.
- **Shared code.** The engine is `src/numbertheory/factorinteger/fi_smooth.c`. Two pieces are now
  shared: QS's relation log is hoisted into `fi_gf2.c` as `FiRelLog`, with a by-tag merge, and
  `fi_par.c` gains a work-claim counter (`FiClaim`).

**Same answers, by construction.** CFRAC's and Dixon's relation streams equal the serial method's for
every thread count. The test is the smallest `"Iterations"` budget that succeeds, which is a sharp
fingerprint of the stream. It matches the v0.453 serial binary on every probe:
- CFRAC at 24/26/31/32/35 digits, including the period-restart case 12791·5060983 (423);
- Dixon at 16/18/20 digits;
- with 1, 3 and 16 threads, and with batches of a single candidate.

`test_factorinteger.c` pins three of these thresholds (both sides of each), and adds a
`TimeConstrained` interruption of each threaded collector.

## Strings: named captures reach the RHS (issue #98); the full string-pattern language ; v0.455

`StringCases["abc123", (x__ ~~ "123") :> x]` returned `{"abc123"}`; it is now
`{"abc"}`. The defect was wider than the report. The translator gave every
pattern name its own capture group, then threw away the name-to-group table, and
any non-string right-hand side fell back to the whole match. So every `:>` or
`->` rule with an expression RHS in `StringCases`, `StringReplace` and
`StringSplit` was silently wrong: `x:DigitCharacter.. :> ToExpression[x]` gave
strings, and `StringReplace["abc123", a__ ~~ "123" :> a <> "!"]` left the text
unchanged.

- **Binding.** The translator now returns its name table (`SpInfo`), and
  `regex_rule_eval_rhs` binds each name to the text it matched (`""` for an
  untaken alternative) through the matcher's scoping-aware `replace_bindings`,
  then evaluates. `StringCases`, `StringReplace` and `StringSplit` all go
  through this one helper.
- **`StringReplace` with a non-string value** returns a `StringExpression` of the
  pieces, as the reference does: `"abc"~~1~~2~~3`.
- **`$n` templates** apply only to `RegularExpression` patterns. Elsewhere
  `"$1"` is literal text (`StringReplace["abc", "b" -> "$0"]` is `"a$0c"`).
- **Parser.** `:` was rated below `~~`, so `x__ ~~ y:DigitCharacter..` parsed as
  `Optional[x__ ~~ y, …]`. `:` now follows the reference: Pattern (`sym:p`) binds
  tighter than `~~`, and Optional (`p:v`) sits just below Pattern. So
  `x:_:1` is `Optional[x_, 1]` and `a:b:c:d` is `Optional[a:b, c:d]`.
  `a|b|c`, `a~~b~~c` and `a<>b<>c` now parse n-ary.
- **Pattern language** (`string_pattern.c`, rewritten onto one output buffer):
  - `Condition` and arbitrary `PatternTest` via PCRE2 callouts. A failed test
    backtracks, with auto-possessification off so it can.
  - `Shortest` and `Longest`.
  - `Repeated`/`RepeatedNull` with `n`, `{n}` or `{m, n}`.
  - A name inside a repeated pattern binds once: `(x:LetterCharacter)..`
    matches `"aaa"`, not `"abc"`.
  - New pattern objects: `StartOfLine`, `EndOfLine`, `WordBoundary`,
    `HexadecimalCharacter`, `PunctuationCharacter`, `CharacterRange[a, b]`,
    `Except[p, q]`.
  - The blanks now match newlines; `.` inside a `RegularExpression` keeps PCRE's
    meaning.
  - An empty `Alternatives` matches nothing.
  - Too many groups now fails cleanly instead of desynchronising names.
- **`StringMatchQ`**: the `*` and `@` wildcards in literal strings, and
  `IgnoreCase`.
- **`StringTrim`** removes one match at each end, as the reference does:
  `StringTrim["xxabxx", "x"]` is `"xabx"`. It used to strip to a fixed point.
  The front is matched `PCRE2_ANCHORED` and the back `PCRE2_ENDANCHORED`. It now
  also takes `IgnoreCase`.
- **Engine.**
  - Compile flags are real PCRE2 options. The `(?i)` prefix broke user regexes
    that start with a `(*VERB)`, and leading verbs are now hoisted out of the
    anchoring wrapper.
  - A match re-entered from its own callout uses private match data.

## FactorInteger: Blake rational base descent rebuilt from the two papers ; v0.457

`FactorInteger`BlakeRationalBaseDescent` was a verbatim port of the first paper's reference Python. It was
incomplete and had bugs:
- It tested for termination before searching, so it missed the corner case the paper calls out.
- It had no perfect-power filter.
- A base below 1 failed silently.
- It ran every gcd at every depth from `n` down, single-threaded, over a fixed a + b order.

It is replaced by a full implementation of both papers ("Rational Base Descent" and "Lattice-Augmented
Rational Base Descent"), with six variants, each selected by `"Variant"` and also available as the head
`FactorInteger`BlakeRationalBaseDescent<Variant>`:
- **Exact** (the default): the scaled exact descent, whose window of four values does not depend on the
  base. Nothing is tested above `sqrt(cmax n)`, and that depth is reached by one division. Gcds are batched
  through an accumulator mod `n`, which is shifted to whole limbs so GMP skips divisor normalisation.
- **Classic**: the reference algorithm R1–R4, kept as the oracle.
- **AllHits**: truncation-divisibility hit records, refined into coprime divisors, with a cache the driver's
  cofactor calls split from.
- **Lattice**: the Howgrave-Graham detector in the depth band. FLINT's `fmpz_lll` is used when available,
  else a native integral LLL; integer roots are found p-adically on the square-free part.
- **TwoPass**: P1 exact, then P2 lattice over a Stern–Brocot-convergent grid.
- **Coppersmith**: a known base, coefficient and exponent.

New suboptions: `"Variant"`, `"Order"`, `"Height"`, `"Bases"`, `"MaxCoefficient"`, `"Multiplier"`,
`"Tolerance"`, `"Beta"`, `"Multiplicity"`, `"Dimension"`, `"BaseRange"`, `"Coefficient"`, `"Exponent"`.
`"Base"` now takes a list. The parent head has a long `?` docstring explaining the method; every variant
head has its own.

The core (`fi_rbd.h`; `fi_rbd_descent.c`, `fi_rbd_bases.c`, `fi_rbd_lattice.c`, `fi_rbd_lll.c`) is plain GMP
(optionally FLINT): reentrant, no global state, per-thread scratch, written so it could move into FLINT
as is. Base searches run on every thread through `fi_par.c`. The lowest-indexed success wins, so answers
do not depend on the thread count. A lattice base is parallel over its band, two depths per thread per
region, so `TimeConstrained` aborts in about 0.2 s. `fi_par.c` gains `fi_claim_cap`/`fi_claim_end`, and
worker threads now call `flint_cleanup()`.

Verification:
- Every claim in the papers is reproduced and checked against an independent Python implementation of the
  reference algorithm:
  - Example 1: the 255-bit q at step 512, misses −2 and 0.
  - 2^1041 + 1 base 2: exactly 3, 9, 2083 and 2^347 + 1, at (1,1), (1,4), (35,−3), (345,4).
  - R₂₂₂₄ base 10: 14 gcds, R₁₁₁₂ at (1111, 1).
  - (153^153 + 1)/154 base 153: 7 gcds, the largest 110 digits at (50, 0).
  - The comb sweep: 533 primitive bases with a + b ≤ 60; only 22/7 and 11/7 fire, at (150, −1).
  - The lattice paper's 197-bit planted-miss instance: Classic fails, Lattice and Coppersmith succeed.
- `verify_methods.py --rbd-planted` runs randomised planted instances through Exact, Classic, the
  unknown-base search and Lattice: 975 calls, 0 wrong.
- The paper's 2048-bit challenge modulus is factored from scratch, with no base given, in 106 s on 16
  threads.
- `leaks`: 0 over every variant. Gates: `check-c99`, `check-messages` and `check-packed-aware` pass.

Speed, single thread, per Stern–Brocot base against a random semiprime: 61 µs (256 bits), 151 µs
(512 bits) and 546 µs (1024 bits), against 2.2, 11.4 and 54.8 ms before (37×, 75×, 100×). The paper's
Example 1 takes 2.8 ms (Exact) and 27 ms (Classic).

Known gap: the native LLL (non-FLINT builds) is exact but slow, 0.2–0.7 s per detector call at 197 bits,
against milliseconds with FLINT.

### New Integrate stage: polylogarithm ladders (v0.458)

The largest Mathar failure class was integrals whose antiderivative needs
`PolyLog` beyond the trivial `Log[1 + a x]/x`. `Integrate[Log[x]/(1 + x^2), x]`,
`Integrate[Log[x]^2/(1 + x), x]` and `Integrate[x^2 Csc[x], x]` all came back
unevaluated.

The new cascade stage and method `"PolyLogLadder"` (`src/internal/PolyLogLadder.m`) closes two classes:

- `R(x) Log[a x + b]^k`: any rational `R` (algebraic or complex poles, any multiplicity, symbolic parameters) and any log power.
- A polynomial in x times a rational function of trig or hyperbolic functions, rewritten in one exponential kernel and closed by the exponential ladder.

Both are exact identities, accepted after a differentiation check. Definite results include:

| Integral | Value |
|---|---|
| `Log[x]/(1 + x^2)` on [0,1] | `-Catalan` |
| `Log[x]^2/(1 + x)` on [0,1] | `3/2 Zeta[3]` |
| `x Csc[x]` on [0, Pi/2] | `2 Catalan` |

Supporting changes:

- **`Power`**: `E^(I q Pi)` (q integer or half-integer) evaluates as `Exp` did. Before, `E^(I Pi)` stayed unevaluated.
- **`PolyLog[2, +-I]`**: now `+-I Catalan - Pi^2/48`.
- **Newton–Leibniz, real form**: it now reduces a complex-written value of a real integrand to its real form with `ComplexExpand`/`Simplify`, adopted only after numeric equality.
- **Newton–Leibniz, endpoint poles**: the endpoint pole test now treats `f` finite at the endpoint as no pole, and zero-tests with a tolerance. `Integrate[Log[x]/(1 + x^2), {x, 0, 2 - Sqrt[3]}]` was falsely reported divergent.

Tests: `tests/test_integrate_polylog.c`.

### TimeConstrained unwind no longer frees in-use Block values (v0.458)

A `TimeConstrained` timeout `siglongjmp`s past C frames. `tc_run_guarded` then
drains the `Block` frames that were jumped over, and that drain freed the values
the Blocks had installed. Code above the jump target could still hold nodes of
those values:

- The trigger was a ParallelMixedSpecial `$part2Memo` Association, read again
  later in the same `Integrate` call.
- The result was a use-after-free (segfaults; timing-dependent) on eight Mathar
  corpus integrals, e.g. `Integrate[(Cos[a x] - Cos[b x])/(E^(x z) x), {x, 0, Infinity}]`.

**Fix:** rule lists restored by an unwind are parked and freed at the next
top-level statement boundary (`mth_block_graveyard_flush`, called by the REPL,
script, pipe and FFI loops). The cost is that the values of a Block interrupted
by a timeout live until the statement completes.

**How it was found:** a debug build that poisons freed nodes instead of
recycling them (type 99, refcount 0, top-level free site recorded in the node)
localised the free to `blk_restore_frame` called from `mth_block_depth_unwind`.

### PolyLogLadder: logarithms of trig rationals (v0.459)

`P(x) Log[G(trig)]` now closes. Examples: `Log[Sin[x]]`, `x Log[Sin[x]]`,
`Log[Cot[x]]`, `x^2 Log[2 Cos[x]]`, `Log[Cosh[x]]`, `x Log[2 Sin[Pi x/2]]`.

Method: write `G` in T = E^(base x), so `Log[G] = D + e base x + Sum m Log[1 - T/rho]`.
D is exact and piecewise constant, `Log[K Prod (-rho)^m] + 2 Pi I n`, with the
integer n fixed numerically. The `x^n Log[1 - T/rho]` terms are the exponential
ladder.

Definite results: `Integrate[x Log[Sin[x]], {x, 0, Pi}] = -Pi^2 Log[2]/2`. The
following now evaluate (values verified, surface not yet reduced to Catalan):

| Integral | Value |
|---|---|
| `Log[Sin[x]]` on [0, Pi/4] | `-(2 Catalan + Pi Log[2])/4` |
| `Log[Cot[x/2]^2]` on [0, Pi/2] | `4 Catalan` |

Newton–Leibniz changes:

- **Continuity cross-check:** it now also fires for an antiderivative holding
  `PolyLog`/`Log` of an exponential of x (branch jumps along the real axis).
- **Imaginary residue:** the cross-check now accepts a value with a negligible
  imaginary rounding residue.

Mathar corpus, definite: 80/166 -> 93/191 (symbolic/instance); WRONG/CRASH 0.

### New definite Integrate stage: Meijer G convolution (v0.460)

`Integrate[C x^alpha K1(x) K2(x), {x, 0, Infinity}]` now closes when the integrand has
exactly two kernels. Each kernel may be `BesselJ`, `BesselY`, `BesselK`, `E^(-p x)`,
`E^(-p x^2)`, `Cos`, `Sin` or `(a + x^2)^-r`, with any argument scale and symbolic
orders. Examples: `BesselJ[1, x] BesselY[1, 3 x]`, the Laplace transform of
`BesselJ[nu, a x]`, `Cos[a x]/(x^2 + b^2)`, and `BesselK[0, x] E^(-x)`.

Method:
- Each kernel is written as a Meijer G-function of u = x^2. For exp, cos and sin this
  uses the duplication formula.
- The power x^alpha is absorbed into the first G-function's parameters.
- The two G-functions are combined into one by the convolution theorem (Prudnikov–
  Brychkov–Marichev 2.24.1.1), which Mathilda's MeijerG evaluator then reduces.

Convergence is decided from the kernels' behaviour at 0 and at Infinity, together
with each kernel's side condition (`Re[a] > 0` for `(a + x^2)^-r`):
- A refuted condition declines.
- A condition that is not proved returns a `ConditionalExpression`.
- No numeric quadrature is used.

The prover checks the condition conjunct by conjunct and runs `Refine` to a fixed
point first, because `Simplify[-b^2 > 0, b > 0]` returns `b^2 < 0` instead of `False`.
This Simplify gap is recorded in `docs/design/mathar_integrate_triage.md`. Without the
side condition, `x^2 - b^2` (real poles) matched the algebraic kernel and gave wrong
finite values for three principal-value integrals. Those integrals are now covered by
decline tests.

Tests: `tests/test_integrate_meijerconv.c`. Mathar corpus, definite: 93/191 -> 106/203
(symbolic/instance); WRONG/CRASH 0.

### New indefinite Integrate stage: holonomic ansatz and Wronskian route (v0.461)

`Method -> "Holonomic"` (`src/internal/Holonomic.m`) runs after `PolyLogLadder` in the
cascade, gated on a Bessel or Airy head. It has two exact routes:

- **Module ansatz.** Each Bessel `J`/`Y`/`I`/`K`, Airy or `Sin`/`Cos` kernel family of linear
  argument spans a 2-dimensional space closed under d/dx. Orders nu0 + k are rewritten by
  recurrence. So `x^alpha L(x)` times a kernel monomial lies in a finite-dimensional
  differential module, and the stage solves one linear system for an antiderivative there:
  - The window at 0 comes from the exact indicial exponents.
  - The window at Infinity is a heuristic, since a complete bound needs Barkatou's
    super-reduction.
  - Every answer is re-checked symbolically.
- **Wronskian route.** For two solutions with Wronskian W, `INT W g(y1, y2) dx = INT g(1, t) dt`
  with t = y2/y1, for any g homogeneous of degree -2. Pairs: AiryAi/AiryBi, BesselJ/BesselY,
  BesselI/BesselK.

| Integral | Result |
|---|---|
| `BesselJ[1, x]^4/x`, `x^2 BesselJ[1/3, x]^3`, `BesselJ[3, x]^4/x^3` | Bessel-polynomial closed forms (the reference leaves all three open) |
| `BesselJ[nu, x]^2/x^4`, `x^(1+mu+nu) BesselJ[mu, x] BesselY[nu, x]`, `BesselJ[nu, x] Sin[x]/x^(3/2)` | closed |
| `1/AiryAi[x]^2` | `Pi AiryBi[x]/AiryAi[x]` |
| `AiryAi[x]^(-2-n) AiryBi[x]^n`, `1/(AiryAi[x] AiryBi[x])`, `1/(x BesselJ[nu, x]^2)` | closed |

`x BesselJ[1, x]` (needs Struve H) and kernels with poles away from 0 decline.

measured 103/198 against 106/203 at v0.460, with more timeouts; the cause (load or a
slowdown) is under investigation, and the definite floor is set to 100/194 meanwhile.

  List of equations made the linear solver decline. It is now an all-zero row, and a literal
  `False` gives `{}`. This matches the reference.
- **PossibleZeroQ false negatives.** `PossibleZeroQ[Sin[2 (Pi/2 + x)] + Sin[2 x]]` was
  `False`. The constant-phase expansion only split an argument that is literally a Plus, so
  a multiple of a sum (or a sum with such a term) kept its trig head as an opaque generator.
  The relaxed decision then proved a true identity non-zero, a definitive answer callers
  trust. The argument is now expanded first. This also fixes the verification in
  `Solve[Tan[x + y] - Cot[x - 2 y] == 0, y]`.
- **Sum/Product with a Part index.** `Sum[D[a^2 + b^2, {a, b}[[j]]], {j, 1, 2}]` was 0. The
  closed-form attempt evaluated the body at a symbolic j, where the Part stays opaque and
  `D` folds to 0. A Part position that mentions the index now forces enumeration, as an
  index predicate (`EvenQ[k]`) already did. `Product` had the same bug.
- **Test expectations.** Stale nested-`Times` FullForm expectations in `tests/test_solve.c`
  were corrected; they predate this change.

## v0.462: Flat ordered-head rules match interior and suffix runs

- **ReplaceAll / DownValues / UpValues on Flat, non-Orderless heads.** A rule whose LHS head
  is Flat but not Orderless (`**`, `Dot`, `And`, `Or`, any head with only `Flat`) used to fire
  only on a leading run of operands. It now matches a contiguous run anywhere:
  `x ** y ** z /. y ** z -> w` gives `x ** w`, `ff[x, y, z] /. ff[y, z] -> w` gives
  `ff[x, w]`, and the UpValue `op /: op[i_] ** op[j_] := op[i + j]` now rewrites
  `x ** op[1] ** op[2]` to `x ** op[3]`. The leftmost run is rewritten first, one rewrite per
  application (`//.` or a re-firing definition does the rest). `match_flat_leftover` retries
  the leftover match at each start offset and pre-screens offsets when the pattern's first
  element can only match one operand. MatchQ stays a whole-expression test; Orderless heads
  and the normal-match-first order are unchanged. A failing rule whose first element is a
  group-absorbing blank (`ff[x_, x_]`) pays one full match per offset.

## Fixes: FactorInteger`Lehman reaches k >= 2 on bignums; TimeConstrained budgets elapsed time ; v0.463

**Lehman.** On bignums, `fi_split_lehman` scanned the whole k = 1 Fermat window
(n^(1/6)/4 values) before trying k = 2, and did not cap it by `"Iterations"`.
Above ~45 digits that single window exceeded the 2^24 budget, so factors with
p/q near a small rational u/v (found at multiplier k = uv) were never reached.
The (multiplier, window-fraction) plane is now swept in rounds of a growing
level c: multiplier k is scanned to min(1, c/k) of its window, and c grows 4×
per round. The total, set-up included, honours `"Iterations"`; at
c ≥ n^(1/3) it is Lehman's complete search. Ratio-3 composites at 51 and 61
digits now factor in milliseconds; before, they failed after 0.6 s and 29 s.
The trade-off: a pure near-square factor costs ~3× more steps.

**TimeConstrained.** The budget is now elapsed (wall-clock) time, as in
the reference. The `ITIMER_PROF` timer counts CPU summed over threads, so it is
kept only as a wake-up that re-checks a monotonic deadline. Before, threaded
ECM/QS aborted 10–16× early: `TimeConstrained[FactorInteger`ECM[bal], 3]` gave
`$Aborted` after 0.3 s and now aborts at 3.07 s. Nested scopes clamp to the
outer's absolute deadline and charge their time to it. `Pause` stops at the
deadline (`TimeConstrained[Pause[5], 1]` used to sleep 5 s and return `Null`).
Threaded FactorInteger workers stop when the deadline passes: GMP-ECM through
`stop_asap`, the QS every 16 polynomials, RBD per candidate.

## Build: no Cygwin search paths on native Windows; platform-aware compiler errors (passagemath PR #2966)

Build tooling only, so no version bump. These came up while passagemath and MSYS2 were
packaging Mathilda for Windows:

- **`/usr` search paths.** The makefile hard-coded `-I/usr/include -I/usr/local/include`
  on `CFLAGS` and `-L/usr/local/lib` on `LDFLAGS` and in the ECM/LAPACK probes. Under
  MSYS2, `/usr` is the Cygwin runtime tree, so with `msys2-runtime-devel` installed the
  native UCRT64 toolchain read Cygwin headers ahead of its own and the build failed.
  passagemath worked around it with a `sed` over the makefile. Now `-I/usr/include` is
  never added (on Linux and macOS it was a no-op, since GCC ignores `-I` for a system
  directory). `/usr/local` is controlled by the new `SYSTEM_PREFIX` variable: it defaults
  to `/usr/local` on Unix and to nothing on Windows, it is added only when the directories
  exist, and `SYSTEM_PREFIX=` turns it off, mirroring `HOMEBREW=`. The macOS flags are
  unchanged apart from the dropped `-I/usr/include`. A packager can pass
  `HOMEBREW= SYSTEM_PREFIX=` so the makefile searches only the paths it is given.
- **`make print-flags`** prints the expanded `CFLAGS`/`LDFLAGS`. The Windows CI leg uses it
  to fail if any `-I/usr…` or `-L/usr…` reaches a native compile.
- **Compiler errors name the right fix per platform.** Clang is still rejected everywhere.
  The error no longer tells Linux and Windows users to `brew install gcc`. On Windows it
  points at the MSYS2 UCRT64/MINGW64 GCC and states that CLANG64/CLANGARM64 are not
  supported.
