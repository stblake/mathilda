# Changelog: week of 2026-11-16 (Mon) – 2026-11-22 (Sun)

## LinkedList, Push, Pop, PopFirst: a mutable list object -- storage, constructor, stack and queue (v0.6625)

Phase 1 of `LINKED_LIST_DESIGN.md`.

- **New atom type `EXPR_LINKEDLIST`.** A reference-counted, *mutable* payload
  (`src/linkedlist.{c,h}`): assignment and argument passing share one list.
  `expr_eq`/`expr_hash`/`expr_compare` use the payload's stable id, so a
  mutation never makes a cached hash stale; `Head` is `LinkedList`, `AtomQ` is
  `True`, `_LinkedList` matches, and it prints as `LinkedList[<n>]`.
- **Storage.** A deque of two runs of doubling chunks, each run randomly
  addressable through a chunk directory: append, prepend, pop at either end,
  index and set are all `O(1)`, and elements never move on growth. A queue's
  dead prefix is reclaimed by an amortised rebase, so memory stays `O(live)`
  (10^6 push/pop pairs on a 10-element queue hold under 4 KB). All-machine
  integer, real or complex contents are stored raw; the first other element
  converts the list once.
- **`LinkedList[]`, `LinkedList[list]`, `LinkedList[ll]`.** The constructor takes
  a List, packed array or NDArray (packed buffers are memcpy'd: on the `AWARE`
  and `INT64_OK` lists, so `LinkedList[Range[10^6]]` costs ~8 ms including
  `Range`, not the 120 ms an unpacking gate cost), or a LinkedList to copy.
  `LinkedList::list` for anything else. `Normal[ll]` (packed when typed) and
  `Length[ll]` (`O(1)`) accept it.
- **`Push`, `Pop`, `PopFirst`** (`HoldFirst`, `Protected`, Mathilda-only names):
  push at the back, pop the last or first element, all `O(1)` and in place. A
  variable holding a plain List is accepted too and rebound (`O(n)`, as
  `AppendTo`). `Pop::empty`/`PopFirst::empty` for an empty list; `Push::llcyc`
  rejects storing a list into itself, directly or through other lists (a
  reference cycle no refcount could free). 10^6 `Push` calls in a `Do` take
  0.69 s against 0.95 s for `Sow` under `Reap`.
- **Caches.** A LinkedList is never INERT or GROUND; every mutation advances the
  evaluation clock (`eval_clock_tick`, which leaves the INERT and GROUND epochs
  alone); and a pure builtin called with a LinkedList argument taints its
  dependency frame, since its answer can change with no binding changing.
- Tests: `tests/test_linkedlist.c` (storage core through the C API, plus the
  surface).

## Together: a numeric radical in a denominator is a unit -- sums with algebraic-constant denominators combine (v0.6624)

- **The bug.** `Together[b/(Sqrt[2] + 2 u) + a/(1 + Sqrt[2] u)]` came back as its
  input. `PolynomialLCM` of the denominators is `Sqrt[2] + 2 u`, and the strict
  divide-back in `together_recursive` (`src/rat.c`) needs
  `(Sqrt[2] + 2 u)/(1 + Sqrt[2] u)`, whose leading-coefficient step divides `2` by
  `Sqrt[2]`. `exact_poly_div`'s coefficient-ring base case (`src/poly/poly.c`)
  accepted only a rational, Gaussian or `AlgebraicNumber` divisor, so it failed, and
  `together_recursive` reassembled the sum. Every shape whose denominators share a
  factor up to a numeric algebraic unit failed this way, with or without symbolic
  numerators: `1/(Sqrt[2] + 2 u) + 1/(1 + Sqrt[2] u)`, `x (1/(1 + Sqrt[2] t) + 1/(1 - t))`.
- **The fix.** A numeric radical divisor (`Sqrt[2]`, `1 + Sqrt[2]`, `2^(1/3)`) is now a
  unit there. Its inverse is computed from its minimal polynomial (qqbar),
  `1/B = -(c1 + c2 B + ... + cn B^(n-1))/c0`, expanded into the radical basis, and
  certified by `B (1/B) == 1` before use. So the quotient is performed, not asserted. A
  symbolic radical (`Sqrt[c]`) still declines. So do `Root` and `AlgebraicNumber`
  (their own paths) and a nested radical (`Sqrt[3/4 - 1/Sqrt[2]]`, which the
  evaluator's radical products respell). The unit is off inside a Together/Cancel of an
  expression that has a nested radical, and in the exact linear-algebra divider
  (`src/linalg/util.c`). There, a rationalised `1/(a + b Sqrt[d])` cancels
  catastrophically under machine `N`: an exact SVD lost 3 digits. Those keep their old
  results.
- **A gcd's spurious unit.** The classical PRS gcd over `Q(Sqrt[2])` can carry a
  radical unit (`(1 - Sqrt[2]) (1 + u)`). That was harmless while the divide-back
  failed. Now it is removed in `poly_gcd_internal`: the gcd is rescaled by its leading
  or trailing coefficient when that makes it rational, or to trailing coefficient 1
  when neither end is rational. `PolynomialLCM[1 + u, 1 + Sqrt[2] u, 1 + 2 u + u^2,
  1 + 2 Sqrt[2] u + 2 u^2]` is the least `(1 + Sqrt[2] u)^2 (1 + 2 u + u^2)`, where it
  was the product of all four.
- **Risch.** The F9 hunt's `decide: integrand not rational in the tower` mark is gone
  from the undecided cases. It covered 54 of them: 27 alone, 15 + 12 with other marks.
  f9hunt2 undecided goes from 91 to 44, and True from 357 to 400 over the three seeds.
  There are 0 false certificates in every seeded hunt. hunt, hunt2, f12hunt, dephunt
  and primhunt are unchanged. f8hunt reported more timeouts in the batch runs (seeds
  802/803: 1 -> 5-6). Re-timed case by case on an idle machine, base and fix behave
  identically there (the same cases time out at 30 s in both), so this is load, not
  the change.
- **Printed forms.** `Cancel[(x^2 - 2 y^2)/(x - Sqrt[2] y)]` is `x + Sqrt[2] y`, as the
  univariate case already was. `Together[x/Sqrt[2] + y/Sqrt[3]]` is
  `(Sqrt[3] x + Sqrt[2] y)/Sqrt[6]` (it was uncombined).
  `Together[a/Sqrt[2] + b/(2 Sqrt[2])]` is `1/4 (2 Sqrt[2] a + Sqrt[2] b)` (it was
  uncombined). An exact `SingularValueDecomposition` of a rank-deficient integer matrix
  comes back smaller (2858 leaves instead of 3978) and still reconstructs exactly and
  under `N`.
- Test: `field_together_cancel_tests` (`test_numeric_radical_denominator`).
## MemoryConstrained; TimeConstrained without the jump; CheckAbort's failexpr abort-protected, PropagateAborts (v0.6623)

- **`MemoryConstrained[expr, b]` / `MemoryConstrained[expr, b, failexpr]`**, `HoldAll | Protected`.
  It stops `expr` once the memory it holds grows by more than `b` bytes, and gives
  `failexpr` or `$Aborted`. `Infinity` means no limit. Any other non-positive-integer
  budget is `::ipnfm` and leaves the call unevaluated; a wrong argument count is
  `::argt`/`::argtu`. Every documented example matches the reference, and so do its
  probed semantics:
  - the count is net;
  - nested frames are attributed correctly;
  - a plain `Abort[]` passes through;
  - an inner `AbortProtect` defers the abort, an enclosing one does not;
  - `CheckAbort` catches it.
- **Accounting** (`src/memacct.{c,h}`). One net live-bytes count covers expression
  nodes, strings, array buffers and GMP/MPFR limbs (through the existing guarded GMP
  hooks). It is charged only while a frame is open, since a budget is a delta. When
  idle, that costs one predicted branch per allocation: +0.5% of the instructions in
  an interpreter loop and about +1% on a mixed workload.
- **Refusing up front.** `Range`, `RandomReal`/`RandomInteger`/`RandomComplex`,
  `ConstantArray`, `ndbuild_open*` and the Compile VM's array opcodes call
  `mth_mem_request` before allocating. An over-budget request is refused, so
  `MemoryConstrained[RandomReal[1, 10^10], 10^3]` never touches 80 GB.
- **The abort.** An overrun becomes the ordinary `Abort[]` sentinel at the
  evaluator's per-step poll, beside Ctrl-C. `tc_deadline_passed()` reports it too, so
  heavy C loops that already poll it (CAD, FactorInteger) decline cleanly. A
  `TimeConstrained` unwind pops any frames it crosses.
- **Compile.** `MemoryConstrained` lowers natively with no interpreter callback; for
  example `Compile[{{n,_Integer}}, MemoryConstrained[Total[Range[n]], 10^4, -1]]`.
  - The new opcodes are `OP_MC_ENTER` and `OP_MC_LEAVE`. An allocation refused inside
    the body resumes at its handler from `vm_fail`.
  - `A_PUSH` growth is charged.
  - `CompileDiagnostics` reports `Compiled -> True`.
  - The two-argument form hands an overrun to the interpreter, which answers `$Aborted`.
- **CheckAbort** (reference behaviour, verified):
  - `failexpr` now runs abort-protected. `CheckAbort[CheckAbort[Abort[], Abort[];
    Print["after"]], "o"]` prints `after`; it used to abort `failexpr` at once.
  - It accepts `PropagateAborts -> True | False | Automatic`; `Options[CheckAbort]` is
    `{PropagateAborts -> Automatic}`. `True` re-raises the same abort after `failexpr`.
    `Automatic` passes on a constraint's abort (`TimeConstrained`, `MemoryConstrained`) and
    absorbs `Abort[]` and Ctrl-C. `False` absorbs everything; an absorbed timeout never fires
    again.
- **TimeConstrained: the timeout is now the ordinary `Abort[]`, not a jump.** The siglongjmp
  skipped every C frame between the deadline check and the TimeConstrained, leaking what they
  held (valgrind: 168 bytes for `TimeConstrained[MemoryConstrained[While[True], 10^6], 0.5]`),
  and it bypassed `CheckAbort` and `AbortProtect`.
  - **The frame.** TimeConstrained pushes a TIME frame on the constraint stack it now shares
    with MemoryConstrained. The deadline trips it, the evaluator's poll raises the sentinel,
    and every frame unwinds through its own cleanup. valgrind's definitely-lost count over six
    timeout scenarios now equals the empty-script baseline.
  - **The backstop.** `siglongjmp` remains for code that reaches no evaluator step, or ignores
    the `Abort[]`, for 50 ms of CPU after the deadline. It is never taken inside an
    `AbortProtect` in the body. The handler now keeps re-arming while a GMP allocation or a
    deferred region holds it off, and an evaluator step is a forced-unwind safe point.
  - **Reference behaviour verified.** All 15 probed cases now match: nesting, inner and outer
    `AbortProtect`, `CheckAbort` with each `PropagateAborts` setting, a spent frame, `Catch`,
    `Check`, and a protected `Pause`.
  - **Three consequences fixed.**
    - An abort during `Get` (`mathilda_run_file`) now unwinds `Begin`/`BeginPackage` and
      restores `$Context`/`$ContextPath`. A timeout inside Integrate's lazy package load had
      left the session in its `Private` context.
    - The message funnel drops messages while a constraint abort is in flight: an `N` loop
      that took the `Abort[]` as data issued `N::meprec`, and `Check` then fired.
    - The MPFR `Det`/`LUDecomposition`/`LinearSolve`/`LinearSolveFunction` callers no longer
      fall back to a slower path after the factorisation declines on the deadline; `Det`
      fell back to Laplace expansion and hung.
  - **Tests.** `test_timeconstrained_abort` in `tests/test_abort.c`, 20 reference cases.
- Tests: `tests/test_memory_constrained.c` (13 groups, covering the examples, net
  accounting, every memory kind, protection, nesting, TimeConstrained interplay,
  Compile and auto-compilation, and state at rest after each group), plus
  `test_checkabort_failexpr` in `tests/test_abort.c`.

## Risch: the decision's silent declines -- every undecided exit marked; a tower-order bug and a dropped hypertangent certificate fixed (v0.6622)

- **The count.** 32 of the hunts' undecided `Risch`ElementaryIntegralQ` cases (27 in
  F9, 4 in F8, 1 in F12) carried no `rde_cert_mark` at all, so the completeness ratchet
  could not see them. Every `UNKNOWN` exit of the decision (`rt_decide_field`,
  `rt_decide_tower`) now names itself (`decide: ...`), and the ratchet scans
  `integrate_risch_transcendental.c` too. Two of the 32 causes were bugs.
- **Tower order (fixed).** The ordering pass compared adjacent levels only, and
  containment is not a total order. A kernel separated from one it contains by an
  unrelated level never moved above it: `E^(u Tan[1 + u])` stayed below `Tan[1 + u]`
  across an `E^u`. Its derivative then named a higher level, and the tower was refused,
  for the decision and for the integrator alike. A topological pass now runs first. The
  three F8 hunt cases are `True`.
- **The hypertangent certificate (fixed).** `Risch`IntegrateHypertangent`'s
  `{g, False}` ("no elementary integral over `k(t)`") was dropped. Over `k = C(x)`, real
  and circular, every source of it is a theorem: the residue criterion, the coupled
  system (complete base-field RDE), and `D c ≠ 0`. It now certifies there; elsewhere it
  is marked. `ElementaryIntegralQ[(1 + Tan[u]^2/u^2)^2/(1 + Tan[u]/u), u]` is `False`:
  the residue at `Tan[u] = -u` is `4u/(u^2 + 2)`. The coupled system now calls
  `Risch`RischDECertified`, not `Risch`RischDE` (which stays unevaluated for "no" and for
  "undecided" alike), and the certificate requires that none of its base RDEs was
  undecided. The F8 hunt's random half gains 5 such verdicts, among them
  `Log[u + Tan[u]] (1 + Tan[u]^2)` and `u Log[Tan[u]] (1 + Tan[u]^2)`; both were checked
  by hand.
- **What the rest are.** The 27 F9 cases are `decide: integrand not rational in the
  tower`. `Together` leaves a sum uncombined when algebraic constants sit in
  denominators under symbolic numerators (`b/(Sqrt[2] + 2 u) + a/(1 + Sqrt[2] u)`), so
  the gate cannot see a rational function. That is the algebraic-constants follow-up.
  The F12 case is `decide: dependent monomials`.
- **Found, pre-existing (v0.6621 too):** `Risch`ElementaryIntegralQ` segfaults after
  about 4 minutes on `Together[D[E^(Tan[1 + u]^2)/Tan[1 + u]^2 + E^u u Cot[1 + u]/(1 + Tan[1 + u]^2), u]]`.
  Recorded in `tasks/todo.md`.
- The recovered hunts are in `tools/bronstein_hunts/` (run them with `run.sh`). Test:
  `test_campaign_silent_declines`.

## Risch: a Liouvillian primitive top -- Erf, Erfi, Erfc, Ei (C completeness campaign, steps 3b and 3c, v0.6621)

- `Risch`ElementaryIntegralQ` decides integrands over an `Erf`/`Erfi`/`Erfc`/
  `ExpIntegralEi` level, which were all undecided before. Examples:
  - `Erf[x]`, `x Erf[x]`, `E^(-x^2) Erf[x]` and `ExpIntegralEi[x]` are `True`;
  - `Erf[x]/x`, `ExpIntegralEi[x]/x`, `Erf[x]^2` and `E^x ExpIntegralEi[x]` are `False`
    (the last two need `Erf[Sqrt[2] x]` and `Ei[2 x]`, kernels not in the tower);
  - `Integrate[ExpIntegralEi[x]/x, x]` now reports `Integrate::nonelem`.
- **3b.** The field integrator treats such a top as a primitive monomial (it was
  treated as an exponential). LimitedIntegrate `r = Ds + c η` is:
  - the v0.6620 parametric Risch DE for the coefficients of `θ^i`, `i ≥ 1`;
  - at `θ^0`, for `η = g τ^k` (`τ` the exponential just below), a parametric Risch DE
    on the `τ^k` Laurent term, with the rest integrated separately; the term decouples
    in hyperexponential integration.

  `Risch`RischDECertified` and `Risch`ParametricRischDE` accept these kernels:
  `RischDECertified[0, Erf[x], x]` is `x Erf[x] + E^(-x^2)/Sqrt[Pi]`.

  decided non-elementary over the levels below it, over the tower itself, so `Erfc`
  beside `Erf` is caught. This replaces the v0.6603 blanket demotion.
- `π` is accepted as a parameter in a decision when it is the only transcendental
  constant and the integrand has no logarithm or trigonometric kernel; there `π` cannot
  arise as `Log[-1]`. `ElementaryIntegralQ[E^(-x^2)/Sqrt[Pi], x]` is now `False`.
- Seeded hunt (scratch `primhunt.m`, 117 integrands `D[F]`): 109 `True`, 5 `False`, 3

  monomial). Theory: `bronstein_extensions.tex` §T12. Tests:

## Risch: the parametric Risch DE, `Risch`ParametricRischDE` (C completeness campaign, step 3a, v0.6620)

- New: `Risch`ParametricRischDE[f, {g0, g1, ..., gm}, x]` solves
  `D[y] + f y == g0 + c1 g1 + ... + cm gm` for `y` and the constants `c_i` together
  (Bronstein [SI] ch. 7). It returns `{y, {c1, ...}}`, `"NoSolution"` (proved) or
  `$Failed` (undecided, with a reason). Examples: `{E^x/x, E^x/x^2}` gives
  `{E^x/x, {-1}}`, and `{1/Log[x], 1/x}` is `"NoSolution"`. It is the core that
  LimitedIntegrate over a Liouvillian primitive top (step 3b) needs, and that the
  generalised new-log certificate (step 2) and a C LimitedIntegrate (step 9) will reuse.
- Method: the ordinary C solver runs with the `c_i` as named constants in the
  right-hand side. The operator side never contains them, and no step divides by a
  right-hand-side quantity, so every bound (degree, valuation, normal denominator) is
  valid for every value of the constants. Each right-hand-side "no solution" exit drops
  its part and continues. The identity gate records the residual, linear in the `c_i`,
  as a constraint, and the constraints are solved at the end. An inconsistent system,
  or a failure at an exit free of the constants, is a proof.
- The cancellation case, which ordinary mode integrates in `K`, runs a linear
  top-down pass:
  - exponential tops decouple by degree;
  - primitive tops carry a fresh unknown `λ` times the homogeneous solution down the
    degrees, which is LimitedIntegrate.
- Not converted (undecided, and on the completeness baseline): the hypertangent boxes,
  and an undecided log-derivative test on the pass.
- Seeded hunt (base, exp, log and mixed towers, 25 each): 100/100 solved and verified,
  0 false `"NoSolution"`, 4/4 non-elementary right-hand sides proved. Ordinary
  (non-parametric) solves are unchanged: every new branch is gated on the unknowns
  being present. Proofs in `docs/notes/bronstein_extensions.tex` §T11. Test:
  `test_campaign_step3a_param_rde`.

## DSolve: Chini equations whose reduced coefficient is only locally constant (issue #137, v0.6619)

- `DSolve[y'[x] == x^2 y[x]^3 - y[x]/x + 1/Sqrt[x^2], y, x]` returned an implicit
  solution whose derivative left a residual of `-1/(6x)`. The reduced equation
  `u' = u^3 + C` has `C = x/Sqrt[x^2]`, which is constant on each half-line, so the
  equation is autonomous there. But `Integrate[1/(u^3 + C), u]` with that `C` still
  inside chose a u-free term that depends on x (`Log[x (1 - C u + u^2)]`), so
  `Xi(u) - x` was no longer a first integral.
- Such a coefficient is now replaced by a fresh constant for the quadrature and
  restored afterwards, in both Chini reductions (autonomous, and the one that
  removes the linear term). Coefficients free of x take the old path, so their
  output is unchanged.

## Overflow[] and Underflow[] are numbers: NumericQ, order, comparisons (v0.6618)

As in the reference, where each is a `Real`:

- **Predicates.** `NumericQ`, `NumberQ` and `InexactNumberQ` are `True` for both;
  `MachineNumberQ` and `ExactNumberQ` stay `False`.
- **Order.** They sort among the numbers by value: `Underflow[]` is a positive
  number below every positive number, `-Underflow[]` the negative one just below
  `0`, and `Overflow[]` follows every finite number. So `x + Overflow[]` is
  `Overflow[] + x`, and
  `Sort[{x, Overflow[], 2, Underflow[], -Underflow[], 0, -1}]` is
  `{-1, -Underflow[], 0, Underflow[], 2, Overflow[], x}`.
- **Comparisons.** `+-Underflow[]` is nonzero, with a sign:
  - `Underflow[] == 0` is `False`;
  - `Underflow[] > 0` and `Underflow[] < 1/10^400` are `True`;
  - `Positive[Underflow[]]` and `Negative[-Underflow[]]` are `True`;
  - `Sign[-Underflow[]]` is `-1`.

  `Overflow[]` has no sign: it is unequal to every finite number
  (`Overflow[] == 1` is `False`), but `Overflow[] > 1`, `Positive[Overflow[]]` and
  `Sign[Overflow[]]` stay unevaluated. Making `NumericQ` True without this would
  have numericalised `Underflow[]` to `0.` inside the comparisons, so
  `Underflow[] == 0` would have been `True`.
- **Functions.**
  - `Abs[Overflow[]]` is `Overflow[]`.
  - `Chop[+-Underflow[]]` is `0`.
  - `b^Underflow[]` is `1 + Underflow[]` for an exact positive `b` with
    `Log[b] > 0`, and `1 - Underflow[]` when `Log[b] < 0`. So `Exp[Underflow[]]` is
    `1 + Underflow[]`, as in the reference, and a positive machine `b` gives `1.`.
  - `b^Overflow[]` and `Exp[Overflow[]]` stay unevaluated. `Overflow[]` may stand
    for `-Exp[10.^10]`, whose exponential is below the range, not past it.

## N of the log of a huge exact integer; exact half-integer factorials (issue #139, v0.6618)

- **`N[LogGamma[10^6]]` took 19 s** (now 0.2 s). The exact `LogGamma[10^6]` is
  `Log[999999!]`, as in the reference. Before evaluating, `N` raises the working
  precision so that each exact integer is represented without loss, which
  `Sin[10^30 + 1]` needs. That meant the log of the 5.5-million-digit factorial was
  taken at 18.5 million bits. `Log` of an integer `n` with `|n| >= 2` is well
  conditioned, so `n` now only needs the target precision.
  `N[Log[3^(10^6) + 1]]` went from 1.3 s to 6 ms. A `Log` inside a sum keeps the
  old rule, because the sum may cancel: `N[Log[10^1000 + 1] - 1000 Log[10]]`, about
  `10^-1000`, needs the `+1`.
- **`N[Binomial[10^6, 1/2], 30]` took 96 s** (now 0.4 s). The exact value goes
  through `Gamma[10^6 + 1/2]`, and the half-integer factorial built its odd double
  factorial with a loop of n single-limb multiplications, which is quadratic. It
  now uses GMP's `mpz_2fac_ui`. A half-integer factorial past the factorial memory
  cap stays symbolic, as an integer one does (`Gamma[10^30 + 1/2]`).

## Overflow[] keeps symbolic operands; Gamma overflow is not a pole; huge exact powers no longer abort; HermiteH at negative order without MPFR (numeric-tower close-out follow-ups, v0.6617)

- **`Overflow[]` arithmetic.** It absorbed every factor and term: `Overflow[] x`,
  `Overflow[] + x` and `Overflow[] 0` were all `Overflow[]`. Now, as in the
  reference, numeric operands are absorbed and symbolic ones stay (`x Overflow[]`,
  `x + Overflow[]`); an exact `0` gives `0`; `Infinity`, `-Infinity`,
  `ComplexInfinity` and `Indeterminate` win; `Overflow[]^0.5` is `Overflow[]`.
- **One `General::ovfl`.** `Exp[10.^10]` printed the message five times (the
  MPFR-promotion probe's passes each announced it); now once.
- **`Gamma`.** `N[Gamma[5000000000/3], 20]` was `ComplexInfinity`. The value is
  past MPFR's range, so it is `Overflow[]` with `General::ovfl`; only a real
  integer <= 0 is a pole, and a result below the range is `Underflow[]`.
- **Exact powers.** `2^(2^40 + 1/2)`, `12^(2^40 + 1/2)` and `Sqrt[2]^(2^41 + 1)`
  aborted the process inside GMP; they are `Overflow[]`. A power below every
  representable magnitude is `Underflow[]`, signed (`2^(-2^40)`,
  `(-2)^(-2^40 - 1)` is `-Underflow[]`, `2^(-10^30)` was unevaluated).
  `Solve[..., Integers]`'s bounded exponential enumeration declines a box whose
  powers would pass 2^26 bits.
- **`HermiteH` without MPFR.** In a `USE_MPFR=0` build `HermiteH[-100., 10.]` was
  `0.` (value `1.31*^-138`): a machine path for real order < 0 through the
  Laplace-type integral replaces the cancelling 1F1 difference there.
- **Not a bug.** `HypergeometricU[5.*^9, 0.5, 100.]` is `Underflow[]` correctly
  (about 10^(-4.6*10^10), below MPFR's floor), contrary to the close-out note.

## Portability: int64 operands reach GMP and MPFR intact on LLP64 Windows; the Integers Solve guards are 64-bit (numeric-tower review F2 follow-up, v0.6616)

- **`USE_MPFR=0`.** The v0.6615 `Underflow[]` arithmetic sat inside an MPFR-only
  region of `numeric.c`, so a `USE_MPFR=0` build failed to link. The rules have
  no MPFR dependency and are now built in every configuration.

On native Windows `long` is 32 bits, so every GMP/MPFR `_si`/`_ui` call
(`mpz_mul_si`, `mpz_cmp_si`, `mpq_set_si`, `mpz_fdiv_ui`, `mpfr_set_si`, ...)
truncates an int64 above 2^31. macOS and Linux are LP64, so none of this
showed there and **no answer changes on them**; the changes are what a
Windows build computes.

- **New helpers** (`src/expr_gmp64.c`, declared in `expr.h`):

## Every buffer and compiled kernel lane is checked against the machine range by default (numeric-tower review G5, G6, v0.6612)

- **The bug.** The scalar path recomputes a degenerate machine result in MPFR:
  non-finite, subnormal, or `0.` from a nonzero argument. The packed, NDArray
  and Compile surfaces applied that check only to an opt-in list of nine
  "decaying" heads, and to no binary kernel at all. So every other head
  flushed or leaked silently:

    treated as safe;
  - compiled `Csch`, `Sech` and `Erfc` at `+-1.*^308` were `0.`.

  about the function:
  - `ND_LANE_NONE`: proven unable to leave the machine range (`Sin`, `Log`,

  - `ND_LANE_RANGE`: an exact zero is a value (`Mod`, `Log[b, 1.]`,

## Compile: a `_Real` argument with no machine representation goes to the interpreter (numeric-tower review E12, v0.6610)

Found by the Phase 8 `check-machine-boundary` gate, still in development.

- **The bug.** `Compile[{{x, _Real}, {y, _Real}}, x^y][0.5, 10^400]` was `0.`;

## Risch: logarithms in tower variables folded by the structure theorem; integrals in the field decided three ways (v0.6605)

Step 1 of the C completeness campaign.

- **Logarithms in tower variables.** The lower-field integrator answers in tower
  variables. A new logarithm or ArcTan that is the tower's own level in another
  form (`Log[I + t0]` and `ArcTan[t0]` for the levels `Log[1 -+ I E^u]`) was not
  recognised. It passed down as part of the next integrand, and the lower
  integration then declined without a mark: `D[ArcTan[E^u]^3]` was undecided.

  The structure theorem now decides each such logarithm:
  - when its logarithmic derivative lies in the rational span of the tower's
    generators, it is folded into the tower variables;
  - otherwise it is a new logarithm.

  `Integrate`RischTranscendental` gives `ArcTan[E^u]^3` and `ArcTan[E^u]^2/2`. A
  real `E^u` is no longer written `Cosh[u] + Sinh[u]` in a trigonometric answer.
- **Integrals in the field, three ways.** The Risch DE's side integrals answer "in
  K", "proved none", or "undecided". The side integrals are the degree bound's

## Underflow[], demotion back to machine numbers, and machine printing (numeric-tower review phase 6) (v0.6604)

These are the policy items decided on 2026-11-17.
- **D5: `Underflow[]`.** A value below MPFR's exponent range was a zero that looked exact
  (`Exp[-10.`30^10]` was `0.e-30`; machine `Exp[-10^10 1.]` was `0.`). It is now

    and `Quiet` see the message.

## Machine quotients are rounded once; machine complex `Sqrt` is `csqrt` (numeric-tower review phase 4c, K1 and K2) (v0.6600)

Two bugs from the Kahan-style corpus (`tests/test_numeric_kahan.c`).
- **K1: `a/b` was rounded twice.** It parses to `Times[a, Power[b, -1]]`. The reciprocal
  was rounded, then the product, so `-0.3/0.1` was `-3.0` instead of the correctly rounded
  `-2.9999999999999996`. `(1.*^16 + 1.)/3.` and `1.*^-10/7.` were off by one ulp, and
  `x/x` was not `1.` at `x = 1.*^-300`.
  - **Fix.** Times evaluates the base of a `Power[b, -1]` argument first. A machine divisor
    (a Real, a machine Complex, a float64/complex64 buffer, or a List of these) meets the
    machine numerator to its left as `Divide[a, b]`: one division per element.
    Several divisors are multiplied first: `a/b/c` is `Divide[a, b c]`. That is the same
    two roundings as a left fold, but it does not depend on the order of the divisors
    (Times is Orderless). A left fold broke the exact symmetry of `Correlation`'s
    `c/(s_i s_j)` matrix. Symbolic quotients and `(1/b) a` are unchanged.
  - **The other surfaces now agree.** `Divide` gained a machine complex branch
    (`mth_cdiv_machine`, C99 complex division, the operation `Compile` already used) and a
    buffer kernel (`ndarray_divide`: parallel, vectorised, with the lane test, and delisting
    on division by zero or under/overflow). `Compile` emits a true divide for `x/y`, for
    scalars and for real or complex arrays. So `0.3/0.1`, `{0.3}/0.1`, the packed and
    NDArray forms, and the compiled form are the same double.
    `(1. + 2. I)/(3. + 4. I)` is `0.44 + 0.08 I` (it was `0.07999999999999999`).
  - **Cost.** A packed `v/2.5` is a vector divide, not a multiply: 2.2 ms against 1.8 ms
    for 10^6 elements. That is the cost of a correctly rounded quotient (NumPy pays it too).
    Symbolic and exact division are unchanged within noise.
- **K2: machine complex `Sqrt`** went through `cpow`, i.e. `exp(log(z)/2)`, which lost
  about 220 ulps at `|z| ~ 10^+-200`. It is now libm `csqrt` on the scalar path, in the
  buffer power kernel and in `Compile` (`SQRT_C` already called it), so all three agree bit
  for bit.
- **S2** (`Exp[I Pi 1.] == -1` is `False`, because complex `Equal` compares parts
  separately) is accepted as it is.
- **Corpus.** 321 cases, 0 expected failures. It gains cross-surface quotient and `Sqrt`
  cases.

## Risch over symbolic parameters: identities solved over Q(params); a v0.6590 false certificate fixed (v0.6591)

- **A false certificate, introduced in v0.6590 and now fixed.**
  `Risch`ElementaryIntegralQ[D[a ArcTan[u] Log[1 + u]^2 - 2 u Log[1 + u]^3 + Log[1 + a u] Log[a + u^2], u], u]`
  was `False`, but the integrand is a derivative. Reproduced on a v0.6590 build; it is now
  `True`.
  - **Cause.** v0.6589's `rt_solve_always_params` made the integrand's parameters
    `SolveAlways` variables. The unknowns of these identities (residues, log coefficients,
    the fold's `c_k`) are constants of the derivation, and so are the parameters, so a
    solution may depend on them (`c = a` beside `a Log[1 + u]`, `c = 1/a` beside
    `Log[1 + a u]`). With the parameters as variables, `{}` only meant "no solution
    independent of a". The v0.6590 new-logarithm certificate read it as a proof. The v0.6589
    sites decline on failure, so they lost answers but gave none wrong.
  - **Fix.** With parameters present, the identity's coefficients in the tower variables
    are taken (`CoefficientList`) and solved for the unknowns only (`Solve`), with the
    parameters left as parameters. Solutions are generic in them, and `{}` means
    inconsistent for generic values: the E4.4 semantics of every parametric verdict.
    Without parameters this is plain `SolveAlways`, as before.
- **New-logarithm certificate.** The parameter scan reads the system (`A'`, `t_k'`), not
  `A`, so `Log[u]/(u + a)` and `Log[u]^2/(u + a)` get generic certificates. `Log[u]/(u + Sqrt[a])`
  stays undecided, which is conservative.
- **Checks.** No false certificate on 80 seeded parametric random towers or 100 numeric ones;
  `a Log[u] Log[1 + u]`, `a ArcTan[u]^2` and `Log[u] Log[u + a]` are True. The Risch suite
  gains the reproducer and a seeded parametric property test.
- Still open: `Log[a + u]/u` is undecided, with no mark, unlike `Log[2 + u]/u` (fixed in
  v0.6592: the cause was a parameter that appears only inside a tower kernel).

## Equality soundness: `22/7 == Pi` was True (v0.6584)

- **`22/7 == Pi` was `True`, and so was `22/7 != Pi`.** A sweep of
  continued-fraction convergents of 22 constants found 263 of 550 rational
  approximations judged equal to the constant, or ordered both ways or neither
  way. The false answers spread to `If`, `TrueQ`, `Max`, chains, complex
  equality, and to `Simplify[Pi == 22/7]` (`True`) and
  `Reduce[x == Pi && x == 22/7, x]` (`x == Pi`). There were three causes.
  - **PossibleZeroQ called a steady residual a zero.** `22/7 - Pi` sits
    2^-12.25 of scale, just under the machine "obviously non-zero" gate, so it
    climbs the precision ladder. A genuine value never shrinks, and the
    "never shrank" branch returned the lenient zero for every non-algebraic
    expression.
    - Now a rung whose value honoured its precision keeps climbing, and the top
      rung's floor decides. Only a rung whose head ignored the requested
      precision is still lenient. `pinned` now also flags an MPFR leaf far short
      of the rung.
    - A plateau on low rungs alone is not evidence, which keeps the |x| ~ 60
      Tanh identities true.
    - The deep-zero early exit now needs the residual below the floor of the
      rung that saw the shrink: `E^Pi - r` at 8.6 10^-29 had "shrunk" from
      machine noise to its true value.
    - A constant with an exact term below the ladder's reach
      (`I (Pi + 10^-400) - I Pi`) is read once at the precision that keeps it.
  - **Equal let the zero test override a clear inequality; Unequal did not.**
    Both now read every pair through one verdict, `equal_pair_decide`. An order
    reached exactly, or by the tolerance, is final. Only an order of exact
    operands read off doubles is confirmed by the zero test.
  - **The order of exact quantities.** `cmp_exact_order` now:
    - tries the exact difference first (`Pi + 10^-400 - Pi` is `10^-400`;
      `Pi + Exp[-Exp[10]] - Pi` is Plus-free);
    - measures MPFR resolution against the operands' structural magnitude;
    - returns "unresolved" instead of "equal".

    Doubles may decide only between operands that contain no `Plus`. Before,
    `Sign[PolyLog[2, 1/3] - 2006534954/5479143815]` was `-1` for a value of
    +6.9 10^-21. The ordering heads no longer let the zero test overrule an
    MPFR-resolved order: `Pi < r` and `Pi > r` had both been `False`.
- **``Internal`$EqualTolerance`` and ``Internal`$SameQTolerance``** are now
  real, `Block`-able variables (defaults 2.10721 and 0.30103 digits, that is 7
  bits and 1 bit).
  - The machine rule lives in `src/equal_tol.h` and replaces the hand-copied
    2^-46 in `comparisons.c`, `numloop.c` and `sparse_reduce.c`.
  - The compiled VM's real comparisons use it too, read at call time:
    `Compile[{x, y}, x == y][1., 1. + 2^-50]` is `True` and the matching `<` is
    `False`, as in the reference. Real comparisons are no longer
    constant-folded.
  - SameQ ignores its last bit, leaf-wise, at the lower precision:

  - `DeleteDuplicates` and `Tally` defaults are still exact. This is a known

## DSolve: implicit IVPs over a y-integral that does not close; qqbar memos released at exit (v0.6583)

- **`DSolve[{y'[x] == Log[1 + y[x]^2], y[0] == 1}, y, x]` returned junk:**
  `Integrate[Log[5]/Log[1 + y[x]^2], y[x]] - x Log[5] == Integrate[Log[5]/Log[2], 1]`.
  There were two defects.
  - The y-side quadrature had stayed an *active*, unevaluated `Integrate[f, y[x]]`.
    The point-condition fit replaced `y[x] -> 1` everywhere, including the
    integration-variable slot. The rewrite to the definite form only recognised
    `Inactive[Integrate]`. Now, before the fit, such a node is turned into its inert
    twin, which is the same value, so the existing definite-form path applies and
    re-verifies through the Leibniz rule. The answer is now
    `Inactive[Integrate][1/Log[1 + t^2], {t, 1, y[x]}] - x == 0`.
  - `Log[5]` came from the separable split. The structural split needed factors
    on both sides, so an autonomous `F(y)` fell through to the sampled split and
    took `g = F(x, 2)`. An empty side is now `1`, and the general solution is
    `Integrate[1/Log[1 + y[x]^2], y[x]] - x == C[1]`.

  were reachable cache entries.** `flint_qqbar.c` memoises qqbar values, Root forms,
  sorted roots and generator minimal polynomials in static tables, and nothing
  freed them at exit. Their fmpz bigints are referenced only through FLINT's
  tagged pointers, which `leaks` and valgrind cannot follow, so each entry showed
  up as an orphaned mpz page plus its limbs. Repeating the same call left the
  count unchanged and distinct calls grew it up to the cache bound, which is
  what showed it was a cache. `flint_bridge`'s exit handler now calls

## Build fix: `src/poly/ffield/ff_fnx.c` compiles against FLINT < 3.3 (Ubuntu)

- The build failed on Ubuntu (FLINT 3.0.1) with `void value not ignored as it
  ought to be` in `fnx_write` / `fnx_ctx_write`. `gr_stream_write` and
  `gr_stream_write_si` return a status `int` only from FLINT 3.3.0; before
  that they return `void`. Two local macros, `FNX_SW` / `FNX_SW_SI`, gated on
  `__FLINT_RELEASE >= 30300`, return the real status on new FLINT and
  `GR_SUCCESS` on old FLINT.
- The same function called `fmpz_mpoly_q_get_str_pretty`, which FLINT added
  in 3.1.0. Below 3.1 it now prints `(num)/(den)` with
  `fmpz_mpoly_get_str_pretty`.
- Checked by compiling against the real FLINT 3.0.1 headers (which reproduce
  the reported errors before the fix) and against 3.6.0. A sweep of all 56
  FLINT-using sources against 3.0.1 found no other errors.
