## Machine quotients are rounded once; machine complex `Sqrt` is `csqrt` (numeric-tower review phase 4c, K1 and K2) (v0.6600)

Two bugs from the Kahan-style corpus (`tests/test_numeric_kahan.c`).
- **K1: `a/b` was rounded twice.** It parses to `Times[a, Power[b, -1]]`. The reciprocal
  was rounded, then the product, so `-0.3/0.1` was `-3.0` instead of the correctly rounded
  `-2.9999999999999996`. `(1.*^16 + 1.)/3.` and `1.*^-10/7.` were off by one ulp, and
  `x/x` was not `1.` at `x = 1.*^-300`.
  - **Fix.** Times evaluates the base of a `Power[b, -1]` argument first. A machine divisor
    (a Real, a machine Complex, a float64/complex64 buffer, or a List of these) meets the
    machine numerator to its left as `Divide[a, b]`: one division per element.
    Several divisors are multiplied first: `a/b/c` is `Divide[a, b c]`. That is the same
    two roundings as a left fold, but it does not depend on the order of the divisors
    (Times is Orderless). A left fold broke the exact symmetry of `Correlation`'s
    `c/(s_i s_j)` matrix. Symbolic quotients and `(1/b) a` are unchanged.
  - **The other surfaces now agree.** `Divide` gained a machine complex branch
    (`mth_cdiv_machine`, C99 complex division, the operation `Compile` already used) and a
    buffer kernel (`ndarray_divide`: parallel, vectorised, with the lane test, and delisting
    on division by zero or under/overflow). `Compile` emits a true divide for `x/y`, for
    scalars and for real or complex arrays. So `0.3/0.1`, `{0.3}/0.1`, the packed and
    NDArray forms, and the compiled form are the same double.
    `(1. + 2. I)/(3. + 4. I)` is `0.44 + 0.08 I` (it was `0.07999999999999999`).
  - **Cost.** A packed `v/2.5` is a vector divide, not a multiply: 2.2 ms against 1.8 ms
    for 10^6 elements. That is the cost of a correctly rounded quotient (NumPy pays it too).
    Symbolic and exact division are unchanged within noise.
- **K2: machine complex `Sqrt`** went through `cpow`, i.e. `exp(log(z)/2)`, which lost
  about 220 ulps at `|z| ~ 10^+-200`. It is now libm `csqrt` on the scalar path, in the
  buffer power kernel and in `Compile` (`SQRT_C` already called it), so all three agree bit
  for bit.
- **S2** (`Exp[I Pi 1.] == -1` is `False`, because complex `Equal` compares parts
  separately) is accepted as it is.
- **Corpus.** 321 cases, 0 expected failures. It gains cross-surface quotient and `Sqrt`
  cases.

## Risch: algebraic constants in the structure theorem and the RDE (a released false certificate); composite exponential classes; the flat ansatz skipped on a proof; a v0.6593 regression fixed (v0.6599)

Phase 2b, findings F9, F12 and the rest of F6 of `docs/notes/RISCH_TRANSCENDENTAL_REVIEW.md`.
- **A false certificate in v0.6593, now fixed.**
  `Risch`ElementaryIntegralQ[D[Sqrt[2] E^(2 u + Sqrt[2] u) u^2/(1 + u), u], u]` was `False`.
  - **Cause.** The base RDE `q' + (2 + Sqrt[2]) q = p` has the solution
    `Sqrt[2] u^2/(1 + u)`. But the no-cancellation loop divides by `2 + Sqrt[2]`, and
    `Together` does not rationalise a numeric denominator. The leading terms then failed to
    cancel, the loop reported no solution, and that "no" was treated as a theorem.
    `Risch`RischDE[2 + Sqrt[2], ...]` and `Risch`RischDE[1 + Sqrt[3], ...]` stayed
    unevaluated for the same reason.
  - **Fix.** The quotient is reduced with `RootReduce`. A polynomial-solve or SPDE failure
    when `f` or `g` carries an algebraic constant is now a marked uncertain step, not a
    proof. The structural "no"s (the normal-denominator divisibility) stay authoritative, so
    `E^(Sqrt[2] u)/u` is still `False`.
- **F9: `Risch`RationalSpan` over algebraic constants.** `RationalSpan[2, {Sqrt[2]}, {u}]`
  was `$Failed`; it is `False`. The rule: when SolveAlways's solution is unique (every rule
  binds an unknown, every unknown is bound to an explicit algebraic number) and the
  identity re-checks exactly, a non-rational value proves there is no rational relation.
  The value is `RootReduce`d first, because `(3 + 3 Sqrt[2])/(1 + Sqrt[2])` is 3; the
  development hunt caught exactly that false `False`. Transcendental values (`Pi`,
  `Log[2]`) stay open. New certificates, which FriCAS confirms (Ei):
  `E^(Sqrt[2] u) + E^(2 u)/u`, `E^(Sqrt[2] u) (2 + u) + E^(2 u)/(u - a)`,
  `E^u u^Sqrt[2]/(1 + u)`.
- **F6: the flat ansatz is skipped on a proof.** It only finds elementary antiderivatives,
  and its size is uncapped. It now runs only when the field decision has not proved the
  integrand non-elementary. `TrigToExp[u^5 ArcTan[u]^3]` takes 0.1 s, in both the
  integrator and `Risch`ElementaryIntegralQ`. It was 16–18 s at v0.6591, and about 6 s
  after the unknowns were named.
- **Flags restored on a `TimeConstrained` abort.** `g_rt_decide_mode`, the decision's
  Cherry skip, and the re-entry guards of the flat-ansatz gate and the log-combine retry
  are now registered with the unwind registry (`tc_register_unwind_counter`). Before, a
  timeout that longjmped out mid-decision left decide mode on for the rest of the
  session, so later integrals ran with the decision's stricter rules and lost answers.
  The seeded hunt showed it as 2–6 fewer True verdicts in the family after a timed-out
  one.
- **Hunts.** 0 false certificates in 450 elementary towers over algebraic constants (three
  seeds), 0 false spans in 800 rational combinations, and the 1200-case general hunt is
  clean, with True counts back to v0.6593's.
- **A v0.6593 regression, fixed.** v0.6593's LogToReal guard declined every complex
  pair, including the trig callers' `E^(I x)` towers, which need LogToReal's real
  reconstruction. `Integrate[Log[61/36 - 5/3 Cos[2 x]] Sin[x] Sin[9 x], {x, 0, Pi}]` went
  from 5 s to over 100 s, and `integrate_gr132_1_tests` hit its 120 s alarm in every push
  run from v0.6593 on. The check that caught it was missing from my v0.6593 verification:
  I grepped for `Failed|Timeout`, and a SIGALRM prints as `Exception`. The guard now tests
  Rioboo's actual precondition, that the residue factors are closed under conjugation. The
  trig forms are back to v0.6592's, the suite takes 37 s, and the wrong 0 on
  `1 + 4 I z^2` still falls back to the RootSum.
- **F12: composite exponential classes.** The evaluator re-merges `E^(2 u) E^(u^2)` into a
  third kernel `E^(2 u + u^2)`. With all three as tower levels the monomials were
  dependent, and every verdict over the tower was demoted: the Together form of
  `D[3 E^(2 u) + Log[1 + E^(-u^2)]]` was not integrated. Now a class primitive that is an
  integer combination of the other primitives gets no level. Its members become the
  monomials `t_(2u)^1 t_(u^2)^1`, in tower variables, where nothing re-merges. That
  integrand integrates to `3 E^(2 u) - u^2 + Log[1 + E^(u^2)]`. On a seeded hunt over
  sum-of-exponent kernels, True rises from 42 and 47 to 119 and 118 (of 120 each), with 0
  false certificates.
- **Integrated on top of v0.6594–v0.6596** (the numeric-tower review, another session):
  this release is v0.6599.
- **Tests.** `test_review_f6_f9` in the Risch suite.

## $MinPrecision and $MaxPrecision (v0.6597)

New system variables, bounds in digits on the precision of every
arbitrary-precision number. They default to `0` and `Infinity`, are settable,
work under `Block`, and have docstrings. Spec:
`docs/spec/builtins/expression-information.md`.
- **One enforcement point.** Every MPFR number is made by the MPFR
  constructors, which clamp its width to the bounds (`numeric_mpfr_prec_clamp`,
  installed in `expr.c`). Literals, arithmetic, functions, `N`, contagion and
  compiled outputs all obey them; machine doubles are unaffected.
  - The bounds are read live through cached `SymbolDef` pointers, so `Block`,
    `Clear` and `Unset` take effect at once. There is no C-side copy to go
    stale.
  - The default costs nothing measurable: a 60-digit arithmetic loop runs
    0.450 s against 0.454 s.
- **Requests.** `N[x, p]` and `SetPrecision[x, p]` outside the bounds use the
  bound, with `::preclg` / `::precsm`. N's adaptive extra precision stops at
  `$MaxPrecision`.
- **Assignment** is validated (min a real `>= 0`, max a positive real or
  `Infinity`, min `<=` max). An invalid value gives `::precset` and the old
  value is kept.
- `$MaxExtraPrecision` has a docstring too.
- **Numeric-tower stress corpus** (`tests/test_numeric_tower_stress.c`,
  generated by `tools/numeric_tower_stress_cases.py`).
  - 318 boolean cases whose truth follows from exact mathematics, over ten
    areas: the int64/BigInt boundary, rationals, IEEE edge cases, the
    overflow/underflow policy, complex arithmetic, cross-surface agreement,
    iterators and reductions, arbitrary precision, round trips, and literals.
  - 309 pass. The 9 that fail are seven newly found bugs, S1-S7 in
    `docs/design/numeric_tower_review.md`, ratcheted as XFAIL: a case that
    starts to pass prints XPASS.

## Numeric tower: the int64/BigInt and machine/MPFR boundaries (v0.6594)

Phases 1–3 of the numeric-tower review (`docs/design/numeric_tower_review.md`):
three crashes, eight wrong answers in exact arithmetic, and one machine/software
boundary policy applied at every choke point. Corpus:
`tests/test_numeric_tower_review.c`.

- **Crashes and undefined behaviour.**
  - `Sqrt[-2^63]` crashed: the `Power` code negated INT64_MIN. It now evaluates
    `(-1)^r 2^(63 r)`, giving `2147483648 I Sqrt[2]`.
  - `x^(-2^63/3)` printed `1/(1/(1/(...` until the stack overflowed. The
    printer's negation now goes through `make_rational_neg`.
  - `3^(2^62)` and `(2^1000/3)^(10^9)` aborted the process inside
    `mpz_pow_ui`. Now `General::ovfl` and `Overflow[]`, at GMP's own bound:
    `INT_MAX` limbs, the same as `BitShiftLeft`.
  - `Quotient[1.*^300, 1]` was `-2^63` (an undefined cast); it is now the exact
    integer.
  - The INT64_MIN fusion case in `Times` could raise SIGFPE (`INT64_MIN % -1`).
  - A huge `Norm` p-literal in `Compile` made an undefined cast.
- **Exact arithmetic.**
  - `Divide[1/3^39, 3^39]` wrapped to a negative number; it is now `1/3^78`.
  - `GCD[-2^63]` and `LCM[-2^63, 3]` were negative.
  - `(-3)^-41` was `Rational[1, -3^41]`. A BigInt exponent works:
    `(-1)^(2^70)` is `1`.
  - `Rational[2^70, 2^70]` now reduces to `1`.
  - `000000000000000000001` is an `Integer`. An int64-sized BigInt hashes as an
    Integer, so `Hash`, `Union` and `Association` lookup agree with `SameQ`.
  - The internal `lcm()` saturates at INT64_MAX instead of wrapping.
  - `expr_bigint_normalize` uses a portable int64 test. `mpz_fits_slong_p` is
    only 32 bits on Windows.
- **Machine/MPFR boundary: a machine number has a 53-bit mantissa and a normal
  exponent.** Results that overflow, underflow or would be subnormal are kept
  at machine precision as a 53-bit MPFR. `Power`/`Exp` already did this for
  overflow (`Exp[1000.]`).
  - `Plus`/`Times`: `1.*^308 + 1.*^308` and `10.^308*10` were `Overflow[]`.
    `1.*^-200 * 1.*^-200` was a silent `0.`.
  - The parser: `1.*^400` gave a raw `inf.0` that survived `Hold`, `1.*^-400`
    gave `0.`, and `1.*^-320` gave a subnormal with four good digits.
  - No subnormal machine numbers. `N`, the demoter and the promoters stop at
    `$MinMachineNumber`, so `N[10^-320] == 10^-320`. The v0.6179 tie test now
    asserts the exact 53-bit value.
  - Machine operands are read correctly rounded (`numeric_machine_value`). A
    BigInt no longer truncates, and a `Rational[BigInt, BigInt]` no longer reads
    as `0`.
- **`Sqrt[-1.]` was `6.1*10^-17 + 1. I`** on the scalar, packed, NDArray and
  Compile surfaces. `(-x)^y` now reduces `pi y` exactly (`mth_sincospi`). The
  scalar builtin and the ND kernel share one helper, so they agree bit for bit.
- **Machine contagion.**
  - `N[Pi, 30]^1.5` and `1.5^N[Pi, 30]` now have machine precision.
  - `Complex[]` holds one kind of number: `Complex[1.0, 2] === Complex[1.0, 2.0]`.
    `Complex[1.5`30, 2.]` and `Abs[Complex[N[Pi, 30], 1.5]]` are now machine
    precision. `Complex[2^70, 0.]` is a Real. MPFR zero parts, MPFR parts of
    different widths, and `Complex[x_MPFR, 0.]` are left alone: an earlier,
    broader draft lost precision in DirichletL, HankelH1 and SinhIntegral.
- **Comparisons and canonical order.**
  - `1.5 < 10^400` and `1.*^308 < 10^309` now evaluate; they stayed
    unevaluated.
  - Values of different kinds sort **exactly** (via MPFR). `2.^53` now sorts

## Risch over symbolic parameters: identities solved over Q(params); a v0.6590 false certificate fixed (v0.6591)

- **A false certificate, introduced in v0.6590 and now fixed.**
  `Risch`ElementaryIntegralQ[D[a ArcTan[u] Log[1 + u]^2 - 2 u Log[1 + u]^3 + Log[1 + a u] Log[a + u^2], u], u]`
  was `False`, but the integrand is a derivative. Reproduced on a v0.6590 build; it is now
  `True`.
  - **Cause.** v0.6589's `rt_solve_always_params` made the integrand's parameters
    `SolveAlways` variables. The unknowns of these identities (residues, log coefficients,
    the fold's `c_k`) are constants of the derivation, and so are the parameters, so a
    solution may depend on them (`c = a` beside `a Log[1 + u]`, `c = 1/a` beside
    `Log[1 + a u]`). With the parameters as variables, `{}` only meant "no solution
    independent of a". The v0.6590 new-logarithm certificate read it as a proof. The v0.6589
    sites decline on failure, so they lost answers but gave none wrong.
  - **Fix.** With parameters present, the identity's coefficients in the tower variables
    are taken (`CoefficientList`) and solved for the unknowns only (`Solve`), with the
    parameters left as parameters. Solutions are generic in them, and `{}` means
    inconsistent for generic values: the E4.4 semantics of every parametric verdict.
    Without parameters this is plain `SolveAlways`, as before.
- **New-logarithm certificate.** The parameter scan reads the system (`A'`, `t_k'`), not
  `A`, so `Log[u]/(u + a)` and `Log[u]^2/(u + a)` get generic certificates. `Log[u]/(u + Sqrt[a])`
  stays undecided, which is conservative.
- **Checks.** No false certificate on 80 seeded parametric random towers or 100 numeric ones;
  `a Log[u] Log[1 + u]`, `a ArcTan[u]^2` and `Log[u] Log[u + a]` are True. The Risch suite
  gains the reproducer and a seeded parametric property test.
- Still open: `Log[a + u]/u` is undecided, with no mark, unlike `Log[2 + u]/u` (fixed in
  v0.6592: the cause was a parameter that appears only inside a tower kernel).

    Kahn ordering ignored omega, so it could rank above a radical whose radicand
    holds it. `g^2 - a - omega y` then led with `omega y`: no Groebner basis, and
    a wrong normal form (`1/Sqrt[a + I y]` came out as
    `(2 a Sqrt[a + I y])/(a^2 + y^2)` during development). The same latent
    ordering affected any radicand holding `(-1)^(1/q)`.
  - **Trig over `E^(I x)`** (`simp_algebraic_field`, `src/simp/radrat.c`). With
    circular or hyperbolic heads present, Simplify also reduces
    `TrigToExp[input]` and reads it back with `ExpToTrig`, keeping the
    lower-scoring form. Bronstein writes `Sqrt[3 + Sin[x]]` as
    `Sqrt[(Cos[x] + I Sin[x]) (...)/2]`, and only over one exponential generator
    is that radicand visibly `3 + Sin[x]`. `D[Integrate[Cos[x]/Sqrt[3 + Sin[x]],
    x, Method -> "Bronstein"], x] // Simplify` is now `Cos[x]/Sqrt[3 + Sin[x]]`.
  - **Radicals read back with the smaller spelling.** A radical is read back with
    its input spelling, unless the expanded radicand is strictly smaller.
  - **Out-of-sample sweep** `tools/simplify_atoms/gen.m`: 15 integrand families
    (`E^(k x)`, `b^x`, `Log[x]`, `Sin`/`Cos`, cube roots, `3/2` powers), random
    coefficients, 50 cases per seed, 3 seeds, Bronstein and Automatic. Of the 300
    cases, 285 are decided and all are recovered: 279 as the integrand itself and
    6 up to numeric radicand content. 0 fail, about 14 s. The 15 skips are
    integrands Integrate does not decide (`Integrate::incomplete`). Unit tests are
    in `test_radical_simplify.c` (`..._transcendental_atoms`).

## Equality soundness: `22/7 == Pi` was True (v0.6584)

- **`22/7 == Pi` was `True`, and so was `22/7 != Pi`.** A sweep of
  continued-fraction convergents of 22 constants found 263 of 550 rational
  approximations judged equal to the constant, or ordered both ways or neither
  way. The false answers spread to `If`, `TrueQ`, `Max`, chains, complex
  equality, and to `Simplify[Pi == 22/7]` (`True`) and
  `Reduce[x == Pi && x == 22/7, x]` (`x == Pi`). There were three causes.
  - **PossibleZeroQ called a steady residual a zero.** `22/7 - Pi` sits
    2^-12.25 of scale, just under the machine "obviously non-zero" gate, so it
    climbs the precision ladder. A genuine value never shrinks, and the
    "never shrank" branch returned the lenient zero for every non-algebraic
    expression.
    - Now a rung whose value honoured its precision keeps climbing, and the top
      rung's floor decides. Only a rung whose head ignored the requested
      precision is still lenient. `pinned` now also flags an MPFR leaf far short
      of the rung.
    - A plateau on low rungs alone is not evidence, which keeps the |x| ~ 60
      Tanh identities true.
    - The deep-zero early exit now needs the residual below the floor of the
      rung that saw the shrink: `E^Pi - r` at 8.6 10^-29 had "shrunk" from
      machine noise to its true value.
    - A constant with an exact term below the ladder's reach
      (`I (Pi + 10^-400) - I Pi`) is read once at the precision that keeps it.
  - **Equal let the zero test override a clear inequality; Unequal did not.**
    Both now read every pair through one verdict, `equal_pair_decide`. An order
    reached exactly, or by the tolerance, is final. Only an order of exact
    operands read off doubles is confirmed by the zero test.
  - **The order of exact quantities.** `cmp_exact_order` now:
    - tries the exact difference first (`Pi + 10^-400 - Pi` is `10^-400`;
      `Pi + Exp[-Exp[10]] - Pi` is Plus-free);
    - measures MPFR resolution against the operands' structural magnitude;
    - returns "unresolved" instead of "equal".

    Doubles may decide only between operands that contain no `Plus`. Before,
    `Sign[PolyLog[2, 1/3] - 2006534954/5479143815]` was `-1` for a value of
    +6.9 10^-21. The ordering heads no longer let the zero test overrule an
    MPFR-resolved order: `Pi < r` and `Pi > r` had both been `False`.
- **``Internal`$EqualTolerance`` and ``Internal`$SameQTolerance``** are now
  real, `Block`-able variables (defaults 2.10721 and 0.30103 digits, that is 7
  bits and 1 bit).
  - The machine rule lives in `src/equal_tol.h` and replaces the hand-copied
    2^-46 in `comparisons.c`, `numloop.c` and `sparse_reduce.c`.
  - The compiled VM's real comparisons use it too, read at call time:
    `Compile[{x, y}, x == y][1., 1. + 2^-50]` is `True` and the matching `<` is
    `False`, as in the reference. Real comparisons are no longer
    constant-folded.
  - SameQ ignores its last bit, leaf-wise, at the lower precision:
    `1. === 1. + 2^-52`, `{1.} === {1. + 2^-52}` and ``1`30 === 1`20`` are
    `True`.
  - `DeleteDuplicates` and `Tally` defaults are still exact. This is a known
    gap, documented in `comparisons.md`.
- **Sign / Abs of a real exact constant the FLINT certificate declines**
  (`Zeta[3] - 1`) now take the sign the comparison heads decide. Only a
  nonzero sign is used, so a hidden zero keeps `Abs[...]` unevaluated, as in
  the reference.
- **Structural magnitude recurses** through `Times` and positive rational
  `Power`, and declines on any other head that wraps a sum. Without this,
  `169 (-1 + Sqrt[16 - 6 Sqrt[7]] + Sqrt[11 - 4 Sqrt[7]]) == 0` (a hidden zero
  at x = 7) read `False`, and Reduce lost the `4 <= x <= 9` branch of
  `(2x - 1)^2 (Sqrt[x + 4 - 4 Sqrt[x]] + Sqrt[x + 9 - 6 Sqrt[x]] - 1) == 0`.
  `test_image.c` now reads its one-ulp grayscale result with
  ``Block[{Internal`$SameQTolerance = 0}, ...]``.
- **Crash fixed.** `d = Pi - 22/7; Abs[d] == -d` segfaulted. Abs's negation
  moved the terms out of the refcount-shared argument, which left `d =
  Plus[Null, Null]`.
- **Gate.** `make check-equality` (`tools/check_equality_soundness.m`) runs 814
  probes covering `==`, `!=`, `<`, `<=`, `>`, `>=`, PossibleZeroQ, Max, Sign,
  complex Equal, and the Equal⊕Unequal and Less⊕GreaterEqual invariants over
  convergents and 10^-k shifts. Unit tests are in `tests/test_comparisons.c`.
- The Lean tests that pinned PossibleZeroQ's false positive on `(1 + x)^20 ==
  Expand[(1 + x)^20] - x/10^25` now expect `Missing["Heuristic", False]`, and
  the golden record is updated accordingly.

## DSolve: implicit IVPs over a y-integral that does not close; qqbar memos released at exit (v0.6583)

- **`DSolve[{y'[x] == Log[1 + y[x]^2], y[0] == 1}, y, x]` returned junk:**
  `Integrate[Log[5]/Log[1 + y[x]^2], y[x]] - x Log[5] == Integrate[Log[5]/Log[2], 1]`.
  There were two defects.
  - The y-side quadrature had stayed an *active*, unevaluated `Integrate[f, y[x]]`.
    The point-condition fit replaced `y[x] -> 1` everywhere, including the
    integration-variable slot. The rewrite to the definite form only recognised
    `Inactive[Integrate]`. Now, before the fit, such a node is turned into its inert
    twin, which is the same value, so the existing definite-form path applies and
    re-verifies through the Leibniz rule. The answer is now
    `Inactive[Integrate][1/Log[1 + t^2], {t, 1, y[x]}] - x == 0`.
  - `Log[5]` came from the separable split. The structural split needed factors
    on both sides, so an autonomous `F(y)` fell through to the sampled split and
    took `g = F(x, 2)`. An empty side is now `1`, and the general solution is
    `Integrate[1/Log[1 + y[x]^2], y[x]] - x == C[1]`.
- **The 155 "leaks" after `DSolve[{y'[x] == Sqrt[x - y[x]], y[a] == a - 1}, y, x]`
  were reachable cache entries.** `flint_qqbar.c` memoises qqbar values, Root forms,
  sorted roots and generator minimal polynomials in static tables, and nothing
  freed them at exit. Their fmpz bigints are referenced only through FLINT's
  tagged pointers, which `leaks` and valgrind cannot follow, so each entry showed
  up as an orphaned mpz page plus its limbs. Repeating the same call left the
  count unchanged and distinct calls grew it up to the cache bound, which is
  what showed it was a cache. `flint_bridge`'s exit handler now calls
  `flint_qqbar_release_caches()` and then `flint_cleanup_master()`, in that
  order, because clearing an fmpz after FLINT's pools are torn down is unsafe.
  The DSolve case and a 79-expression `Simplify` batch over its radicals now
  report 0 leaks. The per-call `rat_canon` leak in `tasks/flint_ratcanon_leak.md`
  is a different, real leak and is still open.
- Test: `t_implicit_ivp_active_integral` (test_dsolve.c).

## DSolve corpus 2.2.1 and 2.2.35 green again: tangent-line IVPs, and Gamma[a, z] in the left half-plane (v0.6582)

- **Five cases, two causes, neither new.** `dsolve_corpus_2_2_1_tests` and
  `dsolve_corpus_2_2_35_tests` were over their baselines.
- **2.2.1-28, -32, -35 had never really passed.** At v0.6143 they scored PASS on
  junk implicit answers such as `ExpIntegralEi[Log[y[x]]] - x^2/2 == -Infinity`:
  the corpus trusts an implicit relation, and the fitted constant was infinite.
  Later the implicit path rightly dropped such branches, and the cases went
  unevaluated. Each initial value lies on an invariant curve that the
  general-solution methods divide out, so no member of their family reaches it.
  - New last Automatic stage, `DSolve`TangentLine` (`src/calculus/dsolve_tangentline.c`):
    for `y' == F(x, y)`, `y(x0) == y0`, the tangent line
    `L = y0 + F(x0, y0)(x - x0)` is returned when the zero test proves that it
    satisfies the ODE and `F_y(x0, y0)` is finite (Picard–Lindelöf: then it is the
    unique solution). `y' == x Log[y], y(1) == 1 → 1`;
    `y' == Log[1 + y^2], y(0) == 0 → 0`; `y' == Sqrt[x - y], y(2) == 1 → x - 1`.
  - The singular-IVP fallback in `dsolve_run`, which tried only the constant
    `y == y0` when a family provably cannot meet its condition, now tries the
    line too. `y' == 1 + (y - x)^2, y(0) == 0` used to ship its Riccati family
    `x + 1/(-x - C[1])` with `C[1]` unfitted, a wrong answer; it now gives `y == x`.
- **2.2.35-3495 (`y'' - y == x^n`) was a PossibleZeroQ stall, bisected to v0.6200.**
  That release made `Gamma[a, z]` evaluate for real negative `z` through the
  complex routine, whose region rule (series iff `Re z < Re a + 1`) is the rule
  for positive real `a`. For a negative `a` and a small negative `z` it chose the
  continued fraction, which is valid only for `Re z > 0`: 200000 iterations
  (~3 s) per call, and the value stayed unevaluated anyway. PossibleZeroQ
  samples exactly such points, so on the verifier's PowerExpand-ed residual
  (identically zero, carrying `Gamma[1 + n, ±x]`) it ran out of budget. The
  continued fraction is now used only where it is valid and fast; the lower
  series takes the rest of the plane, with `~1.44|z|` guard bits for its
  cancellation when `Re z < 0`. `N[Gamma[-17/10, -1/2], 30]` goes from 2.6 s
  and unevaluated to 3 ms. Across 63 points in both regions and on the cut,
  `Gamma[a + 1, z] == a Gamma[a, z] + z^a E^-z` holds to 40 digits.
- Tests: `t_tangent_line_ivp` (test_dsolve.c), and
  `test_gamma_incomplete_left_half_plane` (test_gamma.c).

## Bare names resolve to an existing Global` symbol at Global`'s position on $ContextPath (v0.6581)

- **The defect.** Global` symbols are stored under their bare key (`zz`, not
  ``Global`zz``), but `context_resolve_name` probed ``Global`zz`` for both
  `$Context` and the `Global`` entry of `$ContextPath`, so the probe always
  missed. A same-named symbol in a context listed *after* `Global`` then won:
  after `zz = 1; $ContextPath = Join[$ContextPath, {"Foo`Private`"}];
  Foo`Private`zz = 2`, `Context[zz]` was ``"Foo`Private`"``.
- **Effect in the Bronstein unit harness**, which appends `Bronstein`Private``
  to the path: once package code had created ``Bronstein`Private`a``, a bare `a`
  in a later test string meant the package symbol. A parametric specialisation
  then substituted nothing, and package pattern variables `a_` captured it.
- **The fix** (`src/context.c`): the path is searched in order, and at the
  `Global`` position the bare key is tested (a SymbolDef whose home context is
  `Global``). A context listed before `Global`` (as `EndPackage` places a
  package) still wins over an existing Global` symbol, so a name typed before a
  package loads does not hide the package's export. Inside `Begin["P`Private`"]`
  the current context is still probed first, as before.
- Tests: `tests/test_context.c` `test_bare_name_path_order` (path order both
  ways, `EndPackage` precedence, private symbols for a name Global` has). Doc:
  `Context` in `docs/spec/builtins/expression-information.md`.

## Bronstein over Q(a): symbolic parameters, Phase 4.4 step 5 (v0.6578)

- `Integrate[f, x, Method -> "Bronstein"]` used to refuse every symbolic parameter
  ("radicand is not rational in the tower (symbolic parameter)"). It now decides
  over C = Q(a, ...), like Trager since v0.6574. An antiderivative holds outside a
  Zariski-closed set of parameter values; "not elementary" holds outside a
  countable set (theory note E4.4).
  - Antiderivatives: `Sqrt[a + Log[x]]/x` gives
    `1/3 (2 a Sqrt[a + Log[x]] + 2 Log[x] Sqrt[a + Log[x]])`;
    `E^x/Sqrt[E^(2 x) + a]` gives `-Log[-E^x + Sqrt[a + E^(2 x)]]`.
    `1/Sqrt[E^(3 x) + a]` and `E^x/(a + E^(3 x))^(1/3)` (genus 1, special
    places) also close.
  - Certificates: `Sqrt[a + Log[x]]`, `Log[x]/Sqrt[x^2 + a]`,
    `1/Sqrt[1 + a E^x + E^(3 x)]`. `(x + a)/(x Sqrt[x + Log[x]])` is certified
    too, though it is elementary at a = 1, a point of the exceptional set.
  - About 30 parametric integrands, elementary and not, agree with their
    specialisations at a = 2, 3, −5/7. This includes the E3 examples with a
    parameter in the radicand.
- **How.**
  - Every coefficient field carries the parameters (`brFn`, `brWithParams`).
    `brFieldOver` handles residue fields over Q(a), and `brParamRoot` gives a
    root in radicals for presenting a log term.
  - `Risch\`RischDECertified[f, g, x, {kernels}, {params}]` is a new
    five-argument form: the certified C Risch DE admits the declared parameters
    as constants (`rde_cert_set_params`). The constant systems of the algebraic
    part and of limited integration are normalised over Q(a), with an exact zero
    test (`brConstantEquations`).
  - A κ in Q(a) at a special place is a constant (`brGammaForm`,
    `brMthPowerCofactor`), so its places are built.
  - Residues of degree ≥ 2 over Q(a) are taken one orbit at a time, as
    `RootSum`s.
  - Special-place torsion specialises the parameters at a good point first
    (`brParamSpecialSpecialization`: field, curve, Bp/E, frame point, residues,
    κ, place degrees, special locations, frame degrees all kept), then x (E3).
    `torsionOrderWith` now refuses parameters as an Internal error, and the
    specialised frame is checked to be free of stray symbols.
- The numeric κ and sign region checks give no certificate when a parameter is
  present; they decline. The Automatic cascade's Bronstein stage admits only x
  and `Constant` symbols (`cg_symbol_ok`) until the step-6 A/B run, as Trager's
  stage has since v0.6576.
- Not yet: parameters with Q(i) or radical constants; a radical of a parameter;
  a log term over a non-binomial extension of Q(a) of degree ≥ 3 outside the
  per-orbit path. Each is in the completeness baseline.
- Corpus: `G-param-1` moved from the open gaps to `examples.m`, with three new
  E4.4 examples (88/88 pass, 8 open gaps unchanged).
- Tests: the new suite `test_bronstein_params_bronstein.c` (68 assertions).
- A kernel defect found on the way (open): a bare name misses an existing
  `Global\`` symbol, stored under its bare key, when a later `$ContextPath`
  context has the same name. Reproduce with `zz = 1; $ContextPath =
  Join[$ContextPath, {"Foo\`Private\`"}]; Foo\`Private\`zz = 2; Context[zz]`,
  which gives `Foo\`Private\``.

## The Solve corpus verifier checks branch-conditioned answers on their region (test tooling, no version change)

- The nightly `solve_corpus_tests` gate had been red since v0.6127 on ten
  `T-log-*` cases such as `Solve[Log[t] + Log[x - t] == C[1], t]`. Solve's
  answers were right. They are principal-branch generic solutions, carrying
  the condition `-Pi < Im[C[1]] <= Pi`, so the residual is zero only where
  every `Log` stays on its principal branch, and a nonzero multiple of
  `2 Pi I` elsewhere. Before v0.6127 `PossibleZeroQ` skipped `C[1]`, so the
  check passed without testing anything. Once it began sampling `C[1]` over
  the whole complex space, the check failed.
- `tests/solve_check_prelude.m` now asks the right question of a
  `ConditionalExpression` answer with no integer family. `scGenericZero`
  takes a fixed, deterministic cloud of exact Gaussian-rational points and
  keeps those where the answer's own condition holds. It then requires the
  residual to vanish to 10^-20 at 30 digits at one of them. The residual is
  analytic off its cuts, so a wrong answer vanishes only on a measure-zero
  set. One such zero is therefore a witness that the answer is right on an
  open set, and that its stated condition overlaps that set.
- Corpus: 130/130 pass, up from 120. Every `T-log-*` answer is confirmed at
  4–47 of the 48 points. The check rejects deliberately wrong answers: a
  wrong discriminant, a wrong linear term, a 10^-12 perturbation, a wrong
  cube-root scale, and a condition that never holds.
