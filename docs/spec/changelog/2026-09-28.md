# Changelog: week of 2026-09-28 (Mon) – 2026-10-04 (Sun)

## `Integrate`ParallelMixedSpecial` — the special-function stage of the parallel integrator (v0.239)

The third stage of S. Blake's parallel Risch–Norman integrator: the ansatz of
`Integrate`ParallelMixedTower` extended with **special-function kernels**, so an
answer may carry `ExpIntegralEi`, `LogIntegral`, `Erf`/`Erfc`/`Erfi`, the
incomplete `Gamma[s, z]`, `SinIntegral`/`CosIntegral`, or the elliptic
`EllipticF`/`EllipticE`/`EllipticPi` of a pencil — plus a partial mode returning
`answer + Inactive[Integrate][remainder, x]`.

### Three surfaces

`Integrate`ParallelMixedSpecial[f, x]`; `Method -> "ParallelMixedSpecial"`; and
the Automatic cascade, where it is now the **last** stage, after Goursat. Last on
purpose: it is the only stage that may answer with a non-elementary function, and
an elementary antiderivative is always the better answer, so every stage that can
produce one gets first crack. It is *not* gated on the pseudo-elliptic shape the
way `ParallelMixedTower` is — that gate keeps the elementary-only stage off a
genus>0 `F/R^p` curve where it grinds and closes nothing, and an elliptic pencil is
exactly what this stage closes. The cascade calls only the complete-answer
surface, so plain `Integrate[f, x]` can never return a half-solved sum.

The worker answers with the pair `{answer, verified}`; the builtin unwraps a
*verified* pair to the bare antiderivative and otherwise hands back exactly what
the package said, so `Head[r] === List` stays the caller's test for "no answer"
and the qualified surface still shows the package's own words. Both lazy loaders
now go through `mathilda_load_module`, so the 217 KB Part II file is no longer
evaluated twice in a session that reaches both methods. `Integrate::method`'s
valid-name list gains both parallel methods — it had been missing
`ParallelMixedTower` too.

### The package, and how it is loaded

`src/internal/ParallelMixedSpecial.m` (1868 lines) is loaded **into**
`ParallelMixed`Private``, the `mixed/logrewrite.m` pattern, so Part II's 41
internals resolve by their short names. The research original is a package that
does `AppendTo[$ContextPath, "ParallelMixed`Private`"]` instead; that cannot work
here, because Mathilda resolves a short private *variable* through `$ContextPath`
but not a short private *function*, and all 41 would have stayed unevaluated.

Part II (`src/internal/mixed/ParallelMixed.m`) takes the stage's additive delta:
`StructureRelation` and the Risch structure theorem behind
`BuildTower[…, "StructureTheorem" -> True]` (off by default), the exponential
merge/split, `AnalyseSteps`/`Analyse`/`AnalysisSpecials`/`AnalysisColumn` factored
out of `iPIM`, the `*Orig` hook indirection that lets `ExtendedBounds` `Block` the
four bound-decision symbols, `AnsatzSystem[…, extra]`, and an 8-prime non-torsion
certificate. **Part II's own behaviour is unchanged**: `parallelmixedtower_tests`
11/11 and a 30-case differential byte-identical before and after.
`Exp[2 x]/(1 + Exp[x])` now closes as `E^x - Log[1 + E^x]` through the new
structure-theorem path.

## Elliptic integrals, and five core fixes the special-function integrator needs (v0.238)

Groundwork for porting the **special-function stage** of the parallel Risch–Norman
integrator (S. Blake, *Parallel Integration over Simple Radical Extensions*, the
special-function paper) — the stage that answers with `Ei`/`li`, `erf` family,
incomplete `Gamma`, `Si`/`Ci` and the elliptic integrals, plus a partial mode
returning `answer + Inactive[Integrate][remainder, x]`. Of the heads that stage
emits, Mathilda had every one **except** the elliptic family, and five core
behaviours it relies on were wrong or missing. Each is a real defect in its own
right, so each is listed on its own terms rather than as porting scaffolding.

### `Block` now restores `DownValues`, not just `OwnValues`

```mathematica
gg[a_] := "orig";
Block[{gg}, gg[a_] := "patched"; gg[1]]     (* "patched"                  *)
gg[1]                                        (* was "patched", now "orig" *)
```

`Block`'s locals are dynamically scoped, so whatever they held is restored on the
way out — but only `own_values` was saved, so a rule written to a `Block`-ed
*function* symbol stayed installed for the rest of the session. That is not a
missing nicety: `Block`-ing a function symbol is the standard way to install a
temporary rewrite hook, and the first such call permanently repointed the symbol.
Attributes are deliberately still not cleared — Mathematica's `Block` does not
clear them either.

Frames are additionally threaded on a stack that `tc_run_guarded` drains after a
timeout, so a `TimeConstrained` `siglongjmp` out of a `Block` body cannot leave
the binding installed. Same treatment the async-jump-defer count already had.

### `Block` is no longer alpha-renamed by capture-avoiding substitution

The A11 capture-avoidance fix (v0.212) applied to every scoping construct,
including `Block` — but `Block` is *dynamic* scope, so a symbol arriving inside a
caller's value is precisely what it means to rebind, and renaming the local
defeated the construct entirely. Verified against Mathematica:

```mathematica
g[v_] := Block[{e = 1}, v + e];   g[e + 1]    (* 3     -- dynamic  *)
g[v_] := Module[{e = 1}, v + e];  g[e + 1]    (* 2 + e -- lexical  *)
```

Mathilda now gives both. The visible consequence was that a held body handed into
a `Block` that installs a hook kept reaching the *original* symbol, because the
hook had been installed on a renamed one.

### `Do`, `Sum` and `Product` iterators no longer capture a caller's symbol

`MATHILDA_DIVERGENCES.md` **A18**, and it was never only `Do`:

```mathematica
g[v_] := Module[{s = 0}, Do[s += v, {k, 2}]; s];   g[k]   (* was 3, now 2 k *)
Sum[v, {k, 2}]     with v = k                              (* was 3, now 2 k *)
Product[v, {k, 2}] with v = k                              (* was 2, now k^2 *)
```

Only `Table` was registered as a scoping construct, so the other three bound
their iterator by name and silently replaced any same-named parameter of the
caller with a loop index. `is_iterator_scope_head` now covers all four. Measured
no cost (min-of-5, alternating runs, indistinguishable from the previous build) —
the single-shot slowdown that first appeared was load noise from a parallel build.

**One integral changed answer as a result, for the better.** `DerivativeDivides`'
substitution search had been losing the fold `u = Log[x]`, and with the capture
fixed it finds it, after which the base-field Cherry erf engine closes the reduced
integral:

```mathematica
Integrate[E^(Log[x]^2), x]
  (* was: unevaluated *)
  (* now: I Sqrt[Pi] Erf[-I (1 + 2 Log[x])/2] / (2 E^(1/4)) *)
```

The derivative matches the integrand to ~1e-30, and Mathematica returns the same
closure. `tests/test_risch_rde_tower.c` carried a guard reading
`FreeQ[Integrate[E^(Log[x]^2), x], Integrate] === False`, written to stop the RDE
*tower* over-solving this non-elementary integrand, and it forbade any answer from
the whole cascade. It is restated as what it means rather than relaxed: the RDE
tower path (`Method -> "RischTranscendental"`) must still decline, and an answer
from the wider cascade must be non-elementary *and* differentiate back — an
elementary claim here would still be the defect the guard was written against.

### Nested `Association` element assignment auto-vivifies

```mathematica
a = <||>; a["k", "s"] = 7      (* was a SILENT no-op; now <|k -> <|s -> 7|>|> *)
```

A deep write through a key that did not exist yet placed nothing at all: the
`Set` was left unevaluated and `;` discarded it, so the association stayed empty
with no message. Data loss with no diagnostic, and the memo-table idiom
`$cache[key, "field"] = v` depends on the auto-vivification. Sibling keys are not
disturbed and value semantics hold (`u2 = u1; u2["k","s"] = 9` leaves `u1`).

### `CoefficientArrays`, `BooleanQ`, `SymbolName`, `Internal`SyntacticNegativeQ`

- **`CoefficientArrays[polys, vars]`** — the coefficient arrays of a polynomial
  system grouped by total degree, so `{b, m} = CoefficientArrays[eqs, vars]` is
  the constant vector and coefficient matrix of a linear system. Matches
  Mathematica including the upper-triangular placement (`x y` puts its 1 at
  `{1, 2}` and leaves `{2, 1}` zero) and `Modulus ->`. The arrays are dense
  `List`s rather than `SparseArray`s — documented, and `Normal` of a `List` is the
  identity, so the usual `Normal[CoefficientArrays[...]]` spelling is unaffected.
  A visible `NDArray` argument is materialised rather than being read as a single
  (non-)polynomial and answered with a silently unevaluated call.
- **`BooleanQ[e]`** — `True` for exactly the symbols `True` and `False`. Unlike
  `TrueQ`, `BooleanQ[False]` is `True`.
- **`SymbolName[sym]`** — the name as a string with any context prefix stripped.
- **`Internal`SyntacticNegativeQ[e]`** — does `e` carry a minus sign in the
  leading position of its printed form. A `Plus` never does, which is why callers
  compose it with a `First[]` test; that asymmetry is what SymPy's
  `could_extract_minus_sign` is built on.

`RowReduce[..., ZeroTest -> f]` was expected to be a sixth gap and turned out to
work already — the probe that suggested otherwise used a matrix entry that
auto-simplified to `0` before `RowReduce` saw it, so the option had nothing to
decide.

### `EllipticK`, `EllipticF`, `EllipticE`, `EllipticPi`

The Legendre elliptic integrals, in the **parameter** convention `m = k²` that the
Wolfram Language uses — not the modulus `k`. `EllipticE` and `EllipticPi` are
arity-overloaded exactly as in Wolfram (one argument complete for `E`, two for
`Π`); there is no `EllipticK[φ, m]`, which is `EllipticF`. Full details in
`docs/spec/builtins/special-functions.md`.

Numerics route through **FLINT/Arb**'s `acb_elliptic_*`, which already uses that
convention and Wolfram's branch placement, and supplies the three things a
hand-rolled kernel most easily gets wrong: the quasi-periodic extension off the
principal strip, complex `φ` — which `EllipticF[ArcSin[z], m]` produces as soon as
`|z| > 1`, the normal case for a pencil in `ArcSin` form — and the Cauchy
principal value for `EllipticPi` with `n > 1`, where the path crosses the pole at
`sin²t = 1/n`.

`EllipticK`, `EllipticE` and `EllipticF` also carry `double` kernels on Carlson's
`R_F`/`R_D` for the packed/NDArray element-wise paths, declining outside the real
principal domain so the buffer is abandoned and the exact path answers.
Registering those kernels also made all three compile: `CompileDiagnostics`
reports `Compiled -> True` at scalar and rank-1 shapes, and the compiled values
match the interpreter. `EllipticPi` deliberately has no machine kernel — its
principal value needs `R_J` with the `p < 0` transformation, and a wrong principal
value is a wrong answer.

φ-derivatives are the integrands, which is what lets a numeric verification of an
antiderivative built from these kernels close; `m`-derivatives of `K`, `E(m)` and
`E(φ,m)` are the standard closed forms. `D[EllipticF[φ, m], m]` and the `n`- and
`m`-derivatives of `EllipticPi` are left as inert `Derivative[...]` forms rather
than guessed, as `BesselJ` does for its order.

**Verification.** Every numeric value was checked against mpmath at 35 working
digits *and* against direct quadrature of the defining integrals — the reference
constants recalled into the first draft of the tests were themselves wrong, and
the quadrature is what caught them. Every shipped derivative agrees with a central
difference to ~1e-16. Most importantly, the seven Mathematica reference
antiderivatives of the elliptic block of the stress corpus (cases 100–114)
**differentiate back to their integrands** at the corpus sample points, to ~1e-29
or exactly 0 — including the two `EllipticPi` cases past the pole. That single
check ties the numerics, the branch placement and the derivative rules together
against another CAS's answers. `tests/test_elliptic.c` (12 groups) carries all of
it.

## `flint_field_gcd` — stress-tested and hardened (v0.232)

The multivariate number-field GCD added last commit was correct on its tests and faster than the
baseline on Charlwood, but every case it had been validated against was a handful of terms in a
degree 2–4 field. Pushed on coefficient size, field degree, term count and variable count it
turned out to have three silent failures. All three **answered** — which is exactly why none had
been noticed, and why the new harness treats a decline as a failure rather than a slow row.

**A decline is not a slow answer, it is a worse one.** When the engine cannot certify a candidate
it returns NULL and `poly_gcd_internal`'s post-check answers `1`. That is a valid common divisor,
so nothing downstream complains and the real gcd is simply lost.

| | v0.230 | v0.232 |
|---|---|---|
| coefficient ceiling | declines past **~831 bits** | no decline at 13,288 bits |
| `[K:Q] = 6` via radicals | declines for **every** generator | works |
| compositum `{√2, √3}` | correct, but a degree-4 `Root` per coefficient | `1 + x^3 + Sqrt[2] x y + y^2` |
| 628-term operands | 63 ms | 30 ms |
| residue-field work | — | 2.4–2.6× less |
| Charlwood 50 | 12.5 s, 49/50 | 12.5 s, 49/50 (unchanged) |

- **The ceiling was arithmetic, not subtlety.** `FG_MAX_PRIMES 64` × 29-bit primes is 1856 bits of
  modulus and rational reconstruction needs roughly twice the coefficient size, so the engine gave
  up above ~900 bits — measured, 10^250 passed and 10^300 did not. Primes are now 62-bit (`nmod`
  and `fq_nmod` take any word-size modulus, so this is free) and the prime cap is a backstop
  against grinding rather than a correctness-relevant limit: the *certificate* is what makes the
  answer right, so extra primes only ever cost time. Cost is now near-linear in coefficient size —
  997 bits 7 ms, 13,288 bits 136 ms.
- **Every degree-6 radical field declined**, and the cause was upstream in the qqbar compositum
  (`flint_qqbar_to_number_field_common`). It picked a primitive element by TRIAL membership, and
  `qqbar_express_in_field_esc` deliberately does not escalate past 64 bits of working precision
  when the generator has degree `<= 6`. Degrees 2–5 resolve inside 64 bits and 7+ are allowed to
  escalate, so **degree 6 alone** failed — for every candidate multiplier, hence the whole field:
  `ToNumberField[{2^(1/6), 2^(1/3)}]` came back unevaluated and every degree-6 radical gcd
  answered 1. The primitive element is now chosen by DEGREE instead: `alpha + c*b` always lies in
  `Q(alpha, b)`, so `Q(alpha + c*b)` is the compositum exactly when their degrees agree, which
  needs no membership test that could fail for an unrelated reason. The shared `in_field` keeps its
  degree gate — the DSolve-facing callers ask about membership they have no reason to expect, and
  ungated escalation had regressed them.
- **The render-back gave up on compositums.** It mapped the answer through the product basis of the
  caller's atoms, but `Expand` folds `Sqrt[2] Sqrt[3]` into `Sqrt[6]`, so a `Q(√2, √3)` problem has
  atoms `{√2, √3, √6}` and a product basis of 8 against `[K:Q] = 4`. The overshoot was read as
  "these atoms do not span" and the answer fell back to a degree-4 `Root` per coefficient. Atoms
  are now taken greedily, largest degree first, until the product reaches `n`; the invertibility of
  the change-of-basis matrix remains the test that they really do span.
- **Speed: choose primes that split least.** `fg_gcd_mod_p` runs one multivariate gcd per
  irreducible factor of `M mod p`, and those gcds are essentially the entire cost — 0.062 s against
  0.008 s for lift, CRT, reconstruction and the certificate combined, over 200 calls. The direction
  was measured, not assumed: a split prime has cheaper (single-word) coefficient arithmetic but
  pays FLINT's per-call cost `r` times, and choosing the *most*-split prime instead was 1.6× slower
  at `n = 2` and 2.6× slower at `n = 8`. The prime sequence is also generated once per process
  rather than per call — `n_nextprime` near 2^62 costs several strong pseudoprime tests, and
  re-deriving it made the small cases 4× slower even as the residue work got 2.6× faster.
- **Two code-reading suspects that measurement cleared.** The certificate looked like the expensive
  step (an exact multivariate ideal division over Q, run after every prime); it is ~5 µs against
  ~150 µs for one prime's residue gcds, so gating it on a stabilised reconstruction *cost* an extra
  prime of the dominant work and was reverted — it now certifies each distinct candidate once,
  immediately, so an easy input finishes on the first prime. Hoisting the per-component input
  reduction was likewise dropped: lift is 8% of the time. Only the `O(L²)` keyed-insert image
  construction was worth replacing with `push_term` + `sort_terms`, and term count is now
  sub-quadratic (2.33× the time for 1.94× the terms).
- **`MATHILDA_FIELD_GCD_STATS=1`** prints primes tried vs used, certificates attempted vs passed,
  and elapsed time per stage.
- **`tests/bench_field_gcd.c`** is the standing gate (22 cases, in the default build and ctest).
  Every case is built as `d·u` and `d·v` with `u`, `v` coprime by construction and must come back
  an associate of `d`, verified numerically at two rational points — a decline counts as a failure,
  and `PolynomialQuotient` cannot divide by a `Root`-coefficient polynomial so an exact check would
  produce false negatives. A second gate gives the term-count doubling ratio a ceiling of 3.0.

Also recorded in `MATHILDA_DIVERGENCES.md` A26a, both pre-existing and outside this engine
(identical at v0.230 and with `MATHILDA_NO_FIELD_GCD=1`): `PolynomialGCD[0, f]` with algebraic
coefficients answers 1 where Mathematica answers `f`, and a coefficient mixing an inexact real with
an algebraic constant returns a garbage near-zero float rather than declining.
## Fixes from a worked-example sweep (v0.231)

Bugs that turned up while running several hundred worked examples (graphs, optimization, machine learning, image processing, the notebook) through the binary. They are fixed in one batch. Each has a regression test; the full ctest run has no new failures against v0.230.

### Core language fixes: comparison chains, list Equal, Normal[SparseArray], symbolic iterator bounds, Log10/Log2

- **Variadic `SameQ` / `UnsameQ` / `Unequal` chains.** The parser nested a run
  of `===` as `SameQ[SameQ[a, b], c]`, comparing the Boolean `True` with `c`, so
  `1 === 1 === 1` was `False`; `=!=` and `!=` had the same defect
  (`1 != 2 != 1` evaluated to `True != 1`). A bare run of one of these operators
  now collects into one variadic call, as in Mathematica: `SameQ[a, b, c]`,
  `UnsameQ[a, b, c]`, `Unequal[a, b, c]`. Parenthesised operands still nest,
  and `Unequal` mixed with an ordering operator joins the chain's `Inequality`
  (`a < b != c` is `Inequality[a, Less, b, Unequal, c]`), which `Inequality`
  now evaluates and prints. Equal/Less chains were already folded correctly
  into `Inequality`; their `==` / `!=` pairs are now decided by the `Equal` /
  `Unequal` builtins themselves, so the list tolerance and the exact zero test
  apply inside a chain too.
- **`Equal` on Lists.** `{0.1 + 0.2} == {0.3}` stayed unevaluated although the
  scalar `0.1 + 0.2 == 0.3` is `True`: lists that were not structurally
  identical never reached a numeric comparison. Two Lists are now compared
  element by element with `Equal`, recursively: `True` when every position is,
  `False` for different lengths or one decidably unequal position
  (`{x, 1} == {y, 2}`), otherwise unevaluated (`{x} == {y}`). `Unequal` uses the
  same test (`{1, 2} != {1, 3}` is `True`).
- **`Normal[SparseArray[...]]`.** Mathilda has no sparse storage, so
  `SparseArray[...]` is inert and `Normal` handed it back unchanged. `Normal`
  now builds the dense nested List for the constructor forms (explicit
  positions with or without dims and default, `{p1, p2} -> {v1, v2}`, pattern
  rules such as `{i_, i_} -> 1`, `Band[...]`, a dense list) and for the
  InputForm of Mathematica's internal `SparseArray[Automatic, dims, default,
  {1, {rowptr, colidx}, vals}]`, at any depth (new `src/sparsearray.c`).
- **Numeric symbolic iterator bounds.** `Table[x, {x, 0., 2 Pi, 1.}]` and
  `Table[x, {x, 0, Pi, 0.5}]` stayed unevaluated, as did `Range[Pi]`,
  `Range[0, 2 Pi, 1.]`; `Do[..., {x, 0, 2 Pi, Pi/2}]` looped forever; and
  `Sum[i, {i, 1, Pi}]` took its closed form over the raw bound and answered
  `Pi (1 + Pi)/2` instead of `6`. The shared iterator parser now normalises a
  range whose bounds are real `NumericQ` but not explicit numbers: the upper
  bound becomes the exact last lattice point `imin + n di`,
  `n = Floor[(imax - imin)/di]`, as Mathematica iterates. Table, Do, Sum,
  Product and Range all go through it, and a symbolic running value now
  advances the loops' termination test. `Range` with BigInt bounds
  (`Range[10^20, 10^20 + 2]`) is also counted exactly in GMP instead of being
  refused.
- **`Log10` and `Log2`** did not exist. Both are now builtins
  (`Listable`, `NumericFunction`, `Protected`) defined as `Log[10, z]` /
  `Log[2, z]`: `Log10[100]` is `2`, `Log10[x]` is `Log[x]/Log[10]`,
  `Log10[2.]` is `0.30103`, and a positive machine real uses libm
  `log10`/`log2` so `Log10[1000.]` is exactly `3.`. Each has an NDArray kernel
  (packed and visible arrays) and lowers in `Compile[]` at scalar and rank-1
  shape. `Log[b, z]` now also gives exact rationals whenever `b` and `z` are
  powers of one common rational (`Log[4, 8] = 3/2`, `Log[10, 1/100] = -2`,
  `Log[10, 10^30] = 30`) where it previously handled only machine-integer
  `z = b^k`.

### Image processing: rotation direction, stated-type coercion, Bit morphology, image templates

**`ImageRotate` now turns counterclockwise.** Both the quarter-turn permutation (`rot90_run`, whose
odd turns were swapped) and the free-angle bilinear resampler (`rot_free_run`, whose inverse map
used the y-up matrix on y-down rows) rotated clockwise. That contradicted the docstring and
Mathematica. `ImageRotate[Image[{{1,2,3},{4,5,6}}]]` now gives `{{3,6},{2,5},{1,4}}`, and negative
angles turn clockwise. The existing tests were all compositions (four turns, two turns against a
half turn, the dimension swap), and none of them can see direction. New rows pin the pixels for
both paths, for colour images and for large packed images. Mathematica's side forms now work too:
`ImageRotate[img, side]` (meaning `Top -> side`) and `ImageRotate[img, side1 -> side2]`. Also
fixed a leak: the `N[angle]` wrapper was never freed on any call with an angle argument.

**`Image[data, type]` now coerces the data, as Mathematica documents** ("values in data are
coerced to the specified type by rounding or clipping"):

- Integer types round to the nearest integer (halves round up) and clip to their range.
  `Image[{{0, 300}}, "Byte"]` stores `{{0, 255}}`, and `Image[{{0.5, 2}}, "Bit"]` stores `{{1, 1}}`.
- `"Bit16"` (0..65535) is a new type.
- `"Real32"` and `"Real64"` are accepted as other names for `"Real"`, which is never clipped.
- Non-numeric, complex or ragged data is left unevaluated, and `ImageQ` gives `False` for it.
- `Image[image, type]` and `Image3D[volume, type]` convert between types and keep brightness.

The old behaviour had two root causes. First, a declined `Image[data, type]` stayed unevaluated in
exactly the canonical shape, and `image_info` only checked the shape, so `ImageQ` said `True` and
`ImageData` returned `300/255`. Second, a large literal array auto-packed into an int64 buffer,
and the fixed-point early return accepted that buffer without looking at its values. Now
`image_info` checks every element of nested data (buffers are still checked in O(1)). The fixed
point checks the range of an integer buffer and requires a float64 buffer for `"Real"`.

`"Bit"` image or volume now return a `"Bit"` image, as in Mathematica. This is exact, because the
max or min of 0/1 values is still 0 or 1. Other types still return `"Real"`.

**`ImageCorrelate` accepts an `Image` template.** A single-channel image is used as its unit-scale
pixel matrix, for both plain correlation and `"NormalizedCrossCorrelation"`. A multichannel
template declines.

**Test fix.** `test_ncc_finds_the_patch_it_was_given` failed on main and aborted the whole image
suite. Its test image `Mod[13 i + 7 j, 97]/97` contains a second copy of the template, shifted by

### Numerical optimization: FindMinimum / FindMaximum / NMinimize / NMaximize fixes

`NMaximize[{f, c1, c2, ...}, vars]` no longer returns `{-1e+300, garbage}`: the
wrapper negated the whole problem list, so `Times[-1, {...}]` threaded over the
constraints; it now negates only the objective (FindMaximum had the same
latent bug, and FindMinimum/FindMaximum now accept the `{f, c1, c2, ...}` form
too). `FindMinimum[f, {x, x0, x1}]` treats `x0, x1` as Mathematica's two
starting values instead of as bounds (it used to hand back `x0`): the interval
is used as the initial bracket only when an interior point lies below both
ends, otherwise the bracket is expanded downhill, so
`FindMinimum[x Cos[x], {x, 5, 8}]` gives `{-9.47729, {x -> 9.52933}}` (machine
and MPFR). FindMinimum keeps its variables held but now evaluates starting
values, bounds and the scalar option values (`Method`, `MaxIterations`,
`WorkingPrecision`, goals) — `Table[FindMinimum[x Cos[x], {x, s}], {s, {2, 7}}]`
no longer reads `{x, s}` as two variables, `{x, Pi}` is a start value, and a
symbol bound to a spec list is resolved (NMinimize/NMaximize are not HoldAll
and FindRoot's parser already evaluated its starts; both are now covered by
tests). The 1-D bracket search (machine and MPFR) backs off when an expansion
step leaves the objective's real domain, fixing "MPFR bracket-finding failed"
on `FindMinimum[x^2 - 2 Log[x], {x, 3}, WorkingPrecision -> 30]`. Powell
restarts a stalled cycle from a rotated orthonormal basis, so it leaves the
kinks of Abs/Max objectives (7.0 -> 3.0 and 1.3 -> 0.3 on the reported cases).
Every local method now emits `FindMinimum::cvmit` when MaxIterations is reached
(through the Quiet/Check funnel). ConjugateGradient gained a strong-Wolfe line
search with Powell restarts and now solves Rosenbrock from (-1.2, 1) to 1e-23
instead of stalling at 6e-4. COBYLA's single radius (halved on every rejected
trial) is split into a monotone resolution rho and a ratio-controlled trust
radius, and its step is the Euclidean trust-region step rather than a box
corner (sign descent): Rosenbrock reaches 0.077 in 500 iterations (was 2.02,
silently) and HS071 reaches 17.014 (was 17.33). The projected BFGS, CG and
Newton solvers hold binding box bounds fixed (an active set), which lets the
default method reach the published 17.0140 on Hock–Schittkowski 71 (was 19.84)
and lets NMinimize's polish return a genuinely feasible fixed-charge flow
(residual 5e-8, cost 724.4; that test asserts a feasible optimum again).
SLSQP gives up on feasibility only after 30 non-improving iterations instead of
any 8 infeasible ones, so the 10-link hanging chain converges (violation 1e-15,
was 2.5e-2 with an `infeas` warning). NMinimize's NelderMead restart polish no
longer keeps a fixed-penalty vertex 1e-6 outside an active constraint; it now
matches the other methods' ~4e-12 feasibility, and the `NM_FEAS_RETURN` comment
states its units and provenance. The reference page now describes NMinimize as
non-HoldAll throughout and no longer lists `Or` constraints as unsupported.

### Graphs: minimum spanning trees, options on `Graph[edges, ...]`, strong `ConnectedComponents`; LearnDistribution mixture floor

- **`FindSpanningTree` honours `EdgeWeight`.** It used a BFS tree whatever the weights,
  so the example `Graph[{a,b,c,d,e}, {a<->b, a<->c, b<->c, b<->d, c<->d, d<->e},
  EdgeWeight -> {4,1,2,5,8,3}]` gave total weight 13 where the minimum is 11. It now
  follows Mathematica case by case, checked against Mathematica 15 output for output:
  Kruskal with union-find for a weighted undirected graph (a minimum spanning forest when
  disconnected, ties broken by vertex position as Mathematica breaks them); Chu-Liu/Edmonds
  (`O(E log V)`, leftist heaps, rollback union-find) for a weighted directed graph, giving
  the minimum spanning arborescence, or the lightest spanning branching with the fewest
  roots; a BFS forest or forward BFS branching when unweighted. Weights are compared exactly
  as GMP rationals (`Sqrt[2]`, `Pi` through `N[w, 40]`), a non-real weight leaves the call
  unevaluated, and each tree edge keeps its own weight (and capacity) in the result.
  `FindSpanningTree[{g, v}]` gives the tree grown from `v`, an invalid `v` emits
  `FindSpanningTree::inv`, `Method -> ...` is accepted, and a mixed graph stays
  unevaluated, as in Mathematica.
- **`Graph[edges, opts]` accepts options.** `Graph[{u<->v, ...}, EdgeWeight -> w]` was
  left unevaluated; only the explicit-vertex form took `EdgeWeight`. Both forms now accept
  `EdgeWeight -> {...}` and a new stored `EdgeCapacity -> {...}`, in either order. The
  canonical graph lists them after the edges in a fixed order, so every spelling of one
  graph is the same expression. Consumers read these lists through
  `graph_edge_weight_list` / `graph_edge_capacity_list`, not by argument position, so
  GraphQ, printing, `GraphDistance`, `FindShortestPath`, the cut family and the edit
  heads all see the weights. `FindMaximumFlow` uses the graph's own `EdgeCapacity` when
  no option is given, which is Mathematica's documented rule.
- **`ConnectedComponents` on a directed graph gives the strongly connected components,**
  as Mathematica does. It used to give the weakly connected ones, which was a documented
  deviation. They are listed with no edge from a component to a later one (Tarjan's
  completion order), which reproduces Mathematica's order exactly. On undirected graphs
  the largest component now comes first. `ConnectedComponents[g, {v...}]` is new.
  `WeaklyConnectedComponents` stays weak, now ordered largest first.
  `StronglyConnectedComponents` shares the directed order. `ConnectedGraphQ` on a graph
  with directed edges now requires strong connectivity.
- **`LearnDistribution[..., Method -> "GaussianMixture"]` on rounded data.** The variance
  floor was the squared median nearest-neighbour distance counted over all points. Once
  more than half the values had an exact duplicate, that median was 0 and the floor fell
  to `1e-300`. On 45 iris petal lengths (to 0.1 cm), BIC then chose 9 components, two of
  them a single point at weight 1/45. The spacing is now measured between distinct points,
  and the floor is held to at least `1e-4` of the average variance. The component count is
  also capped by the number of distinct points, as `FindClusters` caps it. The same data
  now gives 2 components, weights {1/3, 2/3} with means 1.42 and 4.91, the model
  Mathematica 15 learns.

## `PolynomialGCD` — a native multivariate GCD over a number field (v0.230)

`PolynomialGCD` returned a **non-divisor** whenever its coefficients lived in a number field and
it had more than one variable. `PolynomialGCD[f, g]` gave back `g` and `PolynomialGCD[g, f]` gave
back `f`; `PolynomialGCD[x + a y, Expand[(x + a y)(x + 2)]]` gave a "gcd" of higher degree than
one of its own operands. Every engine that understood a number field was univariate — they are
built on `gr_poly` over an antic `nf_t`, which is `K[x]` and nothing wider — so multivariate
input fell through to the classical pseudo-remainder sequence, whose content is INTEGER content.
A coefficient in `K` contributes content 1, both operands stay non-primitive over `K`, and the
very first pseudo-remainder `lc(B)*A - lc(A)*B` vanishes identically whenever the two share a
factor and agree in degree — so the loop returned the second operand. See
`MATHILDA_DIVERGENCES.md` A26, which this closes along with two further defects it did not
record: `Extension -> Automatic` on radical input *missed* a factor (returning 1) once the
cofactors carried algebraic constants, and every explicit `Extension -> <value>` form never
reached a field engine at all.

The new `flint_field_gcd` (`src/poly/flint_bridge.c`) is the certified answer. FLINT has no
multivariate GCD over a number field — `gr_mpoly.h` declares no arithmetic whatsoever and there
is no `nf_elem_mpoly` — so this is the classical modular (Encarnación) algorithm: reduce modulo a
prime, let `fq_nmod_mpoly_gcd` do the multivariate work in the residue fields, then CRT and
rationally reconstruct. Splitting the residue ring is a necessity rather than an optimisation:
for a non-cyclic Galois group such as `Q(sqrt2, sqrt3)` **no** prime keeps the minimal polynomial
irreducible, so `M mod p` is factored, the gcd is taken in each `F_p[t]/(m_i)` separately, and
the components are CRT'd back into `F_p[t]/(M)`.

- **Every result is certified before it is returned.** The candidate is monic, so its leading
  monomial is tau-free while `M`'s is `tau^n`; the two are coprime, `{G, M}` is therefore a
  Gröbner basis by Buchberger's first criterion, and `fmpq_mpoly_divrem_ideal` decides "divides
  over `K`" exactly. An unlucky prime or a premature reconstruction costs an iteration, never a
  wrong answer.
- **Both coefficient spellings.** `AlgebraicNumber[theta, {..}]` directly; radicals, nested
  radicals and `Root` objects are mapped into one common field and rendered back through the
  PRODUCT BASIS of the caller's own atoms, so `x + 2^(1/3) y` comes back as `x + 2^(1/3) y`
  rather than as qqbar's `Root` spelling of the primitive element. A PARAMETRIC radical
  (`Sqrt[k]`) is declined: that is a rational function field, and it stays with
  `flint_parametric_sqrt_gcd`.
- **Wired at two points**, so it is not just `PolynomialGCD`: `poly_gcd_internal`'s inner FLINT
  fast path (reaching `Factor`, `SquareFreeQ`, `FactorTerms`, `PolynomialLCM`, `Cancel`,
  `Together` and the Risch/DSolve consumers that call it directly) and `builtin_polynomialgcd`'s
  FLINT block, ahead of the Phase C/D tower paths. `Cancel` and `Together` over such a fraction
  now match Mathematica exactly in all five option forms.
- **A safety net** for whatever it declines (a build without FLINT, a generator qqbar does not
  model, an input that never certified): the multivariate classical path now *checks* its answer
  and returns `1` when it does not divide both operands — always a valid common divisor, and what
  Mathematica returns for these inputs under its default `Extension -> None`. Checked rather than
  pre-empted: refusing every multivariate input that merely carries an algebraic constant is too
  blunt and cost a `DSolve` case whose answer runs through `Q(Sqrt[17])`. Univariate is never
  checked (one variable means the un-stripped `K`-content only scales the answer) and neither is
  `Q(i)` (`get_int_content` does understand Gaussian integers).
- The answer is **monic**, where Mathematica returns a different associate; a gcd over a field is
  defined only up to a constant of that field, so the tests assert by divisibility rather than by
  printed form.
- **Two memos, both load-bearing.** Profiling the A40 antiderivative showed the modular GCD
  itself costs 0.003 s across 43 calls, while *building the field* for radical input cost 1.065 s
  across 113 — the qqbar primitive-element search with precision escalation, repeated for an atom
  set that is a property of the tower and never changes. Caching it by atom list (the C analogue
  of the `.m` layer's `FieldDataMemo`) takes that to 0.180 s. A second memo records whether a node
  is an algebraic-constant atom at all, because qqbar's own generator cache remembers only
  successes, so every *declining* node paid a fresh construction: 496 constructions became 19.
- `MATHILDA_NO_FIELD_GCD=1` A/Bs the engine. `logrewrite.m`'s `KGcd` drops the multivariate
  workaround it carried for A26. Charlwood's fifty: 49/50, 0 wrong, and 13.1 s → **12.5 s**.

## `Integrate` — `ParallelMixedTower`: the real form of the logarithmic part (`logrewrite.m`)

The Mathilda port of the research campaign of 2026-09-28 (`logrewrite.{py,wl,mac}`): the
logarithmic part of an antiderivative comes out of the residue analysis and the ansatz as
`Sum c_k Log[u_k]` with algebraic constants, and a real integrand gives its non-real terms in
conjugate pairs. The new module `src/internal/mixed/logrewrite.m` (a post-processing layer, not
part of the parallel algorithm; one function per function of `logrewrite.wl`) collapses every
pair `(c, u), (conj c, conj u)` to a real logarithm and arctangents (Rioboo's `LogToAtan`: a sum
of arctangents of polynomials in the top generator when the radical is absent, one arctangent of
a polynomial in the radical over the generators otherwise), every pair conjugate under
`Sqrt[p] -> -Sqrt[p]` to a real logarithm and a hyperbolic arctangent when its argument is a
polynomial, and, for a real problem, averages an unpaired non-real term with its formal
conjugate. `Integrate`ParallelMixedTower[1/(x (Log[x]^2 + 1)), x]` is now `ArcTan[Log[x]]`,
`1/(x^2 - 2)` gives `-ArcTanh[x/Sqrt[2]]/Sqrt[2]`, `Sqrt[x]/(1 + x)` gives
`2 Sqrt[x] - 2 ArcTan[Sqrt[x]]`; the trace line `real form: N pair(s) of logarithms collapsed
(Rioboo): k to arctan, l to artanh` is the same in the four ports. `.m` files only, no C change.

- **Loading.** `ParallelMixed.m` ends with `LoadModule["mixed/logrewrite.m"]` inside its private

  `RootFree`/`RootRadicals` replace Root objects before any `NumericQ` test and write a quartic

## `FileSize` (v0.221)

Added `FileSize`, a filesystem-size query alongside the other `File*` builtins in
`src/files.c`.

- **`FileSize["name"]`** — the size of the file `"name"` in bytes, returned as a
  plain `Integer` (deliberately **not** a `Quantity`, unlike Wolfram's
  `FileByteCount`). `"name"` is interpreted relative to the current working
  directory; `$Path` is not searched.

Implemented with `stat()`, so symbolic links are followed and the target file's
size is reported. A path that cannot be `stat`'d (most often a missing file)
emits a `FileSize::nffil` message and returns `$Failed`; the message is routed
through a `Quiet[]`/`Check[]`-aware helper (mirroring `dt_msg` in
`src/datetime.c`), so `Quiet[FileSize[...]]` silences it while `Check[]` still
sees it. A non-string argument or wrong arity leaves the call unevaluated, so
symbolic arguments flow through unchanged. Attribute `Protected`; `SYM_FileSize`
interned in `src/sym_names.c`; docstring in `src/info.c`.

## `UnixTime` (v0.220)

Added `UnixTime`, the seconds-since-1970 companion to `AbsoluteTime` (seconds
since 1900). It is `AbsoluteTime` shifted by the fixed 1900→1970 epoch offset
`days_since_1900[1970,1,1] * 86400 == 2208988800`, and **always returns an
integer** (the nearest whole second — a deliberate difference from `AbsoluteTime`,
which keeps a real for fractional seconds).

- **`UnixTime[]`** — the current time as the true POSIX epoch second, from
  `time()` (GMT), matching the operating-system clock / `date +%s`.
- **`UnixTime[time]`** — a number taken as an `AbsoluteTime` (seconds since 1900),
  shifted to the Unix epoch: `UnixTime[3849984000] == 1640995200`.
- **`UnixTime[{y, m, d, h, m, s}]`** — a date-list spec, elided from the right and
  normalized exactly as `DateList`/`AbsoluteTime`: `UnixTime[{1970,1,1,0,0,0}]`
  → `0`, `UnixTime[{2022,1,1,0,0,0}]` → `1640995200`,
  `UnixTime[{2022,2,31}] == UnixTime[{2022,3,3}] == 1646265600`. Year and month
  must be integers — otherwise `UnixTime::arg` and the input is left unevaluated.
- **`UnixTime["string"]`** and **`UnixTime[{"string", {e1, ...}}]`** — the same
  date-string / format-element specs `DateList` accepts, reusing the `DateList`
  parser verbatim so the two heads always agree on interpretation.

**Reuse.** The date-list form shares `datelist_parts_to_abstime` with
`AbsoluteTime`; the string forms call `datelist_from_string` /
`datelist_from_format` and read the resulting list back to seconds via a new
`datelist_result_to_abstime` helper, then subtract the epoch offset and round.
Attribute `Protected`. Implemented in `src/datetime.c`; `SYM_UnixTime` interned
in `src/sym_names.c`; docstring in `src/info.c`.

Tests: `tests/test_datetime.c` gains epoch-zero, known-instant, elision,
out-of-range normalization, numeric-arg, the `AbsoluteTime` relation, string /
format parity, fractional-second rounding, current-time range, unevaluated /
bad-month, and the `Protected` attribute. No leaks; `make check-c99` clean.

## `DateList` (v0.219)

Added `DateList`, the broken-down date/time accessor and inverse of
`AbsoluteTime`. It returns `{year, month, day, hour, minute, second}` with the
first five as integers and the second as a real.

- **`DateList[]`** — the current local date and time, with sub-second precision
  from `clock_gettime(CLOCK_REALTIME)` (falling back to `time()`).
- **`DateList[time]`** — inverts an `AbsoluteTime` number (seconds since 1900).
- **`DateList[{y, m, d, h, m, s}]`** — a date-list spec, elided from the right
  (`{y}` ≡ `{y,1,1,0,0,0}`) and normalized: out-of-range and fractional fields
  reduce exactly as `AbsoluteTime` does (`DateList[{2022,0}]` →
  `{2021,12,1,0,0,0.}`, `DateList[{2022,1,0}]` → `{2021,12,31,0,0,0.}`,
  `DateList[{2022,3,15.5}]` → `{2022,3,15,12,0,0.}`). Year and month must be
  integers — a non-integer month issues `DateList::arg` and leaves the input
  unevaluated.
- **`DateList["string"]`** — heuristic string parse: month names (full or
  3-letter), a four-digit year, and `AM`/`PM`. A purely numeric string with no
  four-digit year is order-ambiguous, so the US `Month/Day/Year` order is taken
  and `DateList::ambig` is issued (`DateList["05/10/1"]` → `{2001,5,10,0,0,0.}`);
  a leading four-digit token reads as ISO `Year/Month/Day`.
- **`DateList[{"string", {e1, ...}}]`** — format-element parse. Elements
  `"Year"`, `"YearShort"`, `"Quarter"`, `"Month"`, `"MonthName"`, `"Day"`,
  `"DayName"`, `"Hour"`, `"Hour12"`, `"AMPM"`, `"Minute"`, `"Second"`,
  `"Millisecond"` are read in order; non-element strings between them are
  separators. Unfilled fields default to `{current year, 1, 1, 0, 0, 0}`.
  `DateList[{"09/28/26",{"Day","Month","YearShort"}}]` → `{2028,4,9,0,0,0.}`.

**One normalization backend.** Every form reduces to a raw `{y,m,d,h,mi,s}`
parts array, is converted to absolute seconds by the same
`datelist_parts_to_abstime` (reusing `days_since_1900`, factored out of
`builtin_absolute_time` so the two heads agree bit-for-bit), and inverted by a
new `gregorian_from_abstime` (inverse Fliegel & Van Flandern plus an intraday
split). Attribute `Protected`. Implemented in `src/datetime.c`; `SYM_DateList`
interned in `src/sym_names.c`; docstring in `src/info.c`.

Tests: `tests/test_datetime.c` gains structural coverage for absolute-time
inversion, elision, out-of-range/fractional normalization, the string and
format-element parses (including explicit separators, `YearShort`, current-year
fill, and the ambiguity path), the `DateList::arg` non-evaluation path, the
`DateList[]` shape, and the `Protected` attribute — and the `datetime_tests`
target is now registered with ctest (previously built but never run).

## `Pause`, `SessionTime`, `TimeUsed`, `$TimeUnit` (v0.218)

Added `Pause[n]`, which blocks for at least `n` seconds of wall-clock time and
returns `Null`, together with the three symbols its documentation references.

- **`Pause[n]`** — sleeps on `nanosleep` (a wall-clock timer that consumes no
  CPU), resuming across signal interruptions so the full duration is always
  observed. The argument is coerced to a machine double via a robust path that
  accepts integers, reals, bignums, rationals (`Pause[1/4]`), MPFR reals, and
  any `NumericQ` symbolic form (`Pause[Pi]`); zero/negative returns immediately
  and a non-numeric argument leaves `Pause[x]` unevaluated. Attribute
  `Protected`. Implemented in `src/datetime.c`; `SYM_Pause` interned in
  `src/sym_names.c`.
- **`SessionTime[]`** — wall-clock seconds since kernel start-up, from the same
  monotonic clock (`clock_gettime(CLOCK_MONOTONIC)`) used by `AbsoluteTiming`,
  measured against a baseline captured in `datetime_init()`.
- **`TimeUsed[]`** — CPU seconds used so far this session, via `clock()`.
- **`$TimeUnit`** — read-only real constant, `1 / CLOCKS_PER_SEC`, the
  resolution of the `clock()`-based timers and the granularity `Pause`
  documents itself against. Registered in `system_constants_init()`
  (`src/core.c`).

**The counted/not-counted semantic falls out of the existing two-clock design.**
`Timing`/`TimeUsed` read CPU time (`clock()`), which does not advance during a
`nanosleep`, so `Pause` is invisible to them (`Timing[Pause[1]]` ≈ `{0, Null}`).
`AbsoluteTiming`/`SessionTime` read the monotonic wall clock, so `Pause` is fully
counted (`AbsoluteTiming[Pause[1]]` ≈ `{1.0, Null}`). No special-casing is
needed; the two clock sources do the accounting.

Tests: `tests/test_datetime.c` gains coverage for the `Null` return, the
"at least `n` seconds" wall-clock guarantee, `Protected` attribute, symbolic
non-evaluation, the CPU-invisible / wall-counted split, and the three helpers.

## Message routing: every diagnostic now supports `Quiet[]` and `Check[]` (v0.222–v0.227)

each emission site must uphold — `mth_msg_note_fired()` so `Check` sees the
firing, plus a `mth_msg_suppressed()` guard so `Quiet` silences the print — but
there was no single choke-point, and an audit found **~294 diagnostics** emitted

  bad]` returns `1`, not `bad`), while `Quiet` still notes so `Quiet[Check[…]]`

- **Migration.** All ~294 sites across `linalg/`, `poly/`, `numerical_calculus/`,
  `numerical_roots/`, `calculus/`, `solve/`, `special_functions/`,

- **Enforcement.** New `make check-messages` (`tools/check_message_routing.py`,

  See `docs/design/message_routing.md`.

## `Series` resolves a held series variable that names a symbol (v0.229)

`Series` and `SeriesCoefficient` are `HoldAll`, so the series *variable* arrives
unevaluated. Mathematica nevertheless resolves one that carries an OwnValue
naming another symbol —

```
Module[{w}, w = Unique["w"]; Normal[Series[Sqrt[1 + w^4], {w, 0, 4}]]]
   Mathematica:  1 + w11^4/2
   Mathilda was: Sqrt[1 + w11^4]        (* the input, silently *)
```

— and a `.m` routine that expands in a freshly generated symbol does exactly
that. Without the resolution the held symbol does not occur in the (evaluated)
expression at all, so the expression is *constant* in it and the "series" is the
input itself, returned with no message. `series_resolve_spec_vars`
(`src/calculus/series.c`) now resolves such a variable before parsing the spec,
for both heads. A value that is not a symbol is left alone, matching
Mathematica: a numeric value leaves the call unevaluated, an expression value is
treated as a variable the input is constant in.

This was silently crippling `ParallelMixed.m`: `RealiseClass` built the rows of
its exact linear algebra from `Series[Sqrt[q(1/w) w^(2h)/lc], {w, 0, n}]` in a
`Unique["w"]`, so the unbalanced configurations at infinity were solved against a
matrix carrying a square root of a polynomial where a rational number belonged,
and never realised a class. On the 371-integral review corpus:
**304 correct / 67 gap → 329 correct / 42 gap, 0 wrong**, kernel time 582 s → 249 s
(the binomial family 130 → 153 correct).

## `Integrate` — `ParallelMixedTower`: the Charlwood fifty at 1.8x the speed (v0.229)

Cost work only — the method computes the same things, and the suite still returns
49/50 verified antiderivatives (A39 the same honest `failed` as every system).
Kernel time over Charlwood's fifty, one process per integral: **23.53 s → 13.10 s**
(1.80×), against 9.34 s for Maxima and 17.18 s for Mathematica measured the same
way on the same day. Mathilda is now faster than Mathematica on the suite as a
whole, and on four rows it is faster than *both*: P8 0.64 s against 1.36 / 1.56,
P4 1.24 against 1.73 / 2.27, A33 and A17; A28 and A38 sit on the target. Biggest

  package's canonical form `CanRaw` was `Cancel[Together[e], Extension -> Automatic]`
  unconditionally. Measured on this kernel, the plain one-argument `Cancel`

  1.11, the suite −1.4 s.

  (`src/match.c`). It recursed into arguments through the public entry point, so
  the set — a full walk of every binding value — was rebuilt at *every node* of
  every rule RHS; and it is needed only when the RHS actually contains a
  `Module`/`With`/`Table`-style binder. Interned names also make the `strcmp`

## Notebook: `%` history and infix LaTeX (v0.234)

Two bugs reported from the notebook front end, both in the kernel rather than in
the app.

### `%`, `%%`, `%n` did nothing in a notebook

`Integrate[x^5 E^x, x]` in one cell and `% // Factor` in the next printed a
literal `Out[-1]`.

`%` is not a REPL feature. The parser turns it into `Out[-1]` (`src/parse.c`) and
`builtin_out` resolves the negative index against `$Line`, so any front end that
evaluates without recording `$Line` / `In[n]` / `Out[n]` leaves it unevaluated.
The interactive loop did that bookkeeping inline in `process_input`; the NDJSON
pipe the notebook talks over did none of it.

`src/repl.c` now keeps the session history in three shared helpers
(`repl_set_line`, `repl_store_in`, `repl_store_out`) that both front ends call,
so the two cannot drift apart again. In a notebook cell:

- one line per **statement**, as the interactive loop numbers them, so `%` means
  "the previous result" whether that came from the cell above or the line above
  inside the same cell;
- `$Line` is set **before** evaluation, because `%` in a statement is
  `Out[$Line - 1]`;
- `Out[n]` is stored even when the result is suppressed by `;` or is `Null` —
  `x = 5;` then `%` is 5, as in Mathematica;
- a new `{"id":N,"type":"line","line":L}` protocol message reports the line the
  statement took. The notebook labels the cell `In[L]` with it, which it has to:
  one kernel serves every notebook on the canvas, so a counter kept by the front
  end would label a cell `In[2]` while `%2` addressed a line typed in another
  pane.

**Plain (non-`cell`) requests are untouched** — no numbering, no `line` message,
no `Out[n]`. Those come from batch tools (the site generator, the audit sweeps,
the book tools), which have no history to refer back to, and holding every result
of a 10⁷-element sweep alive in `Out[n]` would grow without bound. The `cell`
flag already draws exactly this line.

### Rules and relations typeset as FullForm

`DSolve[y''[x] - 3 y'[x] == y[x], y[x], x]` came back as
`\{\{Rule[y[x], ...]\}\}` — FullForm dressed up as mathematics, and the most
visible output in the application, since every `Solve`, `DSolve` and `Reduce`
answer is built from these heads.

`src/print_latex.c` (the notebook's renderer, distinct from `print.c`'s
`TeXForm`) had no infix arm at all, so `Rule`, the relations and the logical
connectives all fell through to the generic `Head[a, b]` case. It now carries the
same operator table `print.c` already had — `Rule`, `RuleDelayed`, `Set`,
`SetDelayed`, `And`, `Or`, `Equal`, `Unequal`, `Less`, `Greater`, `LessEqual`,
`GreaterEqual`, `SameQ`, `UnsameQ`, `Not` and the chained `Inequality` — with
precedence levels below `Plus` so nesting parenthesises correctly
(`(a || b) && c` brackets, `a && b || c` does not, since `∧` binds tighter).
`True`, `False`, `Null` and `Indeterminate` now set upright, where math mode was
rendering `False` as a product of five italic variables.

`RuleDelayed` renders as `:\to` in **both** renderers, where both previously
printed `\to` for it: a delayed rule is a different object from an immediate one,
and one glyph for both made `a -> b` and `a :> b` indistinguishable once
typeset. It mirrors `SetDelayed`'s `:=`.

### Gates

`tools/check_pipe_protocol.py` grew the history and LaTeX sections (`%`, `%%`,
`Out[n]`, intra-cell `%`, the `;`-suppressed line, one line per statement,
`$Line`, and the LaTeX of a `Solve` answer), and its existing cell-mode
expectations now spell out the `line` message so the protocol's shape stays
visible in the gate. `tests/test_print.c` gained `test_operator_latex`;
`frontend/scripts/check-notebook.mjs` gained section 1g for the `In[n]`
reconciliation.

### `Factor` multiplied a product out instead of factoring it

Following the `%` fix, the reported cell became `Integrate[x^5 E^x, x] // Factor`
— which evaluated, and came back *expanded*:
`-120 E^x - 60 x^2 E^x - 5 x^4 E^x + ...`.

`Factor` normalises through `Together`, and `Together` expands a multivariate
product: `Together[E^x (x^2 - 1)]` is `-E^x + x^2 E^x`. The expansion is then not
a polynomial in the single variable `collect_variables` finds (`x`) — its
coefficients carry `E^x` — so `bz_factor_to_expr` had nothing to work with and
handed the expansion straight back. `Factor[E^x (x^2 - 1)]` returned
`-E^x + x^2 E^x`: less factored than its own input.

Factoring is multiplicative, so a **denominator-free** product is now factored
factor by factor:

```
Factor[E^x (x^2 - 1)]                      E^x (-1 + x) (1 + x)
Factor[Log[x] (x^2 - 1)]                   (-1 + x) (1 + x) Log[x]
Factor[y (x^2 - 1)]                        (-1 + x) (1 + x) y
Integrate[x^5 E^x, x] // Factor            E^x (-120 + 120 x - ... + x^5)
```

The last is the reported case: the quintic is irreducible over `Q`, so the answer
is the integrator's own output — unchanged, rather than multiplied out.

The denominator case is deliberately excluded, because a sum is the correct answer
there: `Factor[(x^2 - 1)/(x - 1)]` is `1 + x`, and threading over that `Times`
would hand back an uncancelled `(x - 1)(x + 1)/(x - 1)`. Under that guard the
rewrite fires only where the polynomial path has already failed to factor, so
nothing that factors today changes route — `test_factor_of_a_product_stays_a_product`
in `tests/test_factor_baseline.c` pins both sides.

**The root defect is `Together`'s expansion, and it is left alone.** A great deal
of the integrator, `DSolve` and `Simplify` is tuned around the shape `Together`
returns, so changing it is its own piece of work with its own corpus runs rather
than a rider on this one.

Regression runs, all unchanged: the factor suites (`facpoly`, `factor_baseline`,
`factor_phase0`, `factor_recombine`, `factor_terms`, `factorlist`,
`factorsquarefreelist`, `field_together_cancel`, `expand`, `expandfrac`), the
simplify suites (`simplify`, `fullsimplify`, `fullsimplify_corpus`,
`collect_corpus`, `logexp_simplify`, `radical_simplify`, `invtrig_simplify`,
`factorial_simplify`, `simplify_hang`), all twenty `integrate_*` suites, and
`poly`, `mpoly`, `rat`, `ratcanon_*`, `parfrac`, `solve`, `reduce`, `series`,
`limit`, `groebner`, `residue`, `zupoly`, `bpoly`, `trigreduce`, `polymod`.
`crc_corpus_tests` fails identically with and without the change (the same six
cases, 6 against a checked-in baseline of 3) — verified by an A/B build, so it is
a pre-existing red on main.

### Build: `./build-sidecar.sh` after a default `make`

The script builds the notebook's kernel sidecar with `USE_ECM=0` (the bundled app
must not need a `libecm` the user has not installed). Object files do not record

## DSolve M60 — higher-order linear ODEs: reducibility completion + generalised Airy

Gap-driven wave on the largest measured bucket of the 12000.org §2.1.2 corpus
(`3rd_high_linear`: 142 ODEs Maple and Mathematica both solve, of which 101 were declined).
Probing the binary against the real corpus equations split that bucket into three
independently addressable mechanisms plus one outright defect; all four are addressed here.
Every new branch is gated by an in-method numeric back-substitution **and** the DSolve
substrate's own verification, so the corpus's 0-FAIL record holds by construction.

### `DSolve\`GeneralizedAiry` (new)

The n-th order **pure-power potential** `u^(n) == A x^m u` — the higher-order analogue of
Airy's equation — with fundamental set, for `j = 0..n-1` and `p = m + n`,

```
u_j = x^j HypergeometricPFQ[{}, {1 + (j-i)/p : i = 0..n-1, i != j}, A x^p / p^n]
```

so `DSolve[y'''[x] == x y[x], y, x]` now returns `₀F₂({}, {1/2, 3/4}, x⁴/64)` and its `x`,
`x²` partners instead of declining. The equation reaches that shape through a **depression
(gauge) pre-pass** that generalises `DSolve\`SymmetricSquare`'s order-3 gauge to any order:
with `v = -c_{n-1}/n` and the Bell recurrence `W_0 = 1`, `W_{i+1} = W_i' + v W_i`, the
conjugated operator is `L[w u]/w = Sum_j d_j u^(j)` with `d_j = Sum_{k>=j} c_k C(k,j) W_{k-j}`
— written in terms of the logarithmic derivative, so no `Exp` ever has to cancel. That is what
maps `x y''' + 3 y'' == A x² y` (gauge `w = 1/x`) onto `u''' == A x u`.

`A` and `m` may be symbolic (`y''' == a x^b y` solves), forcing is added by variation of
parameters, and the method declines — cleanly, to the series fallback — when `p == 0` (the
Euler case), when a lower parameter is a non-positive integer (exponents differing by a
multiple of `p`, the logarithmic Frobenius case: `x w''' + w == 0`, `x² y'''' == A y`), or when
the potential is not a power.

### `DSolve\`OperatorFactor`: order 2, forcing, and left factors

Three restrictions lifted.

**Order 2.** The method was gated to order ≥ 3, on the reasoning that `Kovacic` owns order 2.
Kovacic does run first and does own the tidy answers — but what it *declines* was falling
through to a truncated Frobenius series even when a rational first-order right factor existed.
`DSolve\`DFactor` would find that factor; `DSolve` would not use it. So
`x²(1+x) y'' + 2x(2+x) y' + 2 y == 0` came back as `O[x]^6` when `y = 1/x` is a solution. It is
now a closed form, and because that equation is the order-2 *quotient* of the third-order
2.1.2-253, the order-3 peel closes too.

**Forcing.** The monic-normalised right-hand side is handed to the recursive quotient solve, so
an inhomogeneous reducible operator solves rather than declining.

**Left factors (the classical Beke case).** When no first-order right factor exists, the same
search runs on the adjoint `L* = Sum (-1)^k D^k o a_k`. Since `(A o B)* = B* o A*` and
`(D - s)* = -(D + s)`, a first-order right factor of `L*` is a first-order **left** factor
`(D + s)` of `L` — i.e. an order-`(n-1)` **right** factor, which for `n = 3` is exactly the
"2nd-order right factor" case, reached without exterior powers. Left division
(`q_{n-1} = a_n`, `q_{m-1} = a_m - q_m' - s q_m`, remainder `a_0 - q_0' - s q_0`) is the exact
acceptance test, so a mis-found `s` can only decline.

`DSolve\`DFactor` reports the left factor as well. Its list is **innermost first** —
`L = (Dx - rk) o ... o (Dx - r1)` — and a left factor, being the outermost operator, is emitted
last: `(D + 1/x) o (D² - x)` returns `{Dx² - x, Dx + 1/x}`, an order-2 right factor of an
operator with no first-order right factor at all. (The previous documentation claimed the
opposite ordering; the code was right and the text was wrong.)

### `DSolve\`SpecialFunctionForm`: a general Bessel row

`Q = A x^m + B x^(-2)` gives `Sqrt[x] Z_nu(kappa x^((m+2)/2))` with
`nu = Sqrt[1-4B]/(m+2)`, `kappa = 2 Sqrt[A]/(m+2)`, `Z = BesselJ/BesselY`. This strictly
generalises the existing single-power row (`B == 0` reproduces its `nu = 1/(m+2)`) and reaches
the inverse-power pair `{-1,-2}` that the Whittaker two-term condition `P_big - 2 P_sm == 2`
cannot see, e.g. `y'' + (1/x + 1/x²) y == 0` → `Sqrt[x] Z_{I Sqrt[3]}(2 Sqrt[x])`. A complex
order is admissible — `BesselJ`/`BesselY` numericize there, so the numeric self-verify gate
stays genuine.

### Three latency root-causes (all pre-existing, all newly exposed)

The wider reach turned three dormant costs into visible ones; each is fixed at the root.

1. **The trailing integrand was built unsimplified.** `Exp[-(Log[x] + Log[1+x²]/2)]` sends
   `Integrate` down the transcendental-tower path, where the trailing integrand of 2.1.2-250
   costs 3.98 s **and still fails**; the same integrand written as `1/(x Sqrt[1+x²])` is
   algebraic, closes, and costs 0.015 s. The gauge factor is now simplified — and then
   *checked* (`w' == r w`) rather than trusted, falling back to the raw form if the simplifier
   picks a branch that breaks the identity.
2. **Symbolic constants inside the algebraic integrator.** Integrating
   `(C1 + C2 x)/(x³(1+x²)^(3/2))` costs 2.06 s; the same integrand with numeric coefficients
   costs 0.011 s. The trailing integral and the left peel's variation of parameters are now
   split along the generated constants by linearity.
3. **The factor search bounded the pole count but not the ansatz width.** Two double poles plus
   a degree-2 polynomial part is 11 unknowns in a *cubic* determining system, which does not
   return. A new `OF_MAX_UNKNOWNS` bound declines those combinations up front (every factor the
   search has ever found needed at most four unknowns), and the ansatz pole order is capped at 1 —
   a *double* pole in `r` is an irregular singularity, which this method's documented scope defers
   anyway, so searching for one doubled the width of every combination while earning nothing
   (verified: every corpus case gained by this wave still solves at pole order 1). A failing search
   on a two-pole third-order operator went from 60.2 s to 0.72 s.

Together these took 2.1.2-250 from a >120 s non-answer to a 2.6 s solve. A structural gate also
declines the left peel when the quotient's fundamental set is a series or a special function,
where the variation-of-parameters integrals churn for seconds without ever closing (2.1.2-294:
11.9 s → 0.37 s decline).

## Notebook: printer directives are honoured, and the notebook format is `.mnb` (v0.235)

### `expr // InputForm` no longer typesets the form it was asked not to show

`D[Log[1 - Sqrt[x]] Sqrt[x], x] // InputForm` came back in the notebook as a typeset
derivative — StandardForm, with a fraction bar and a radical — rather than the input form
the directive asked for. The same held for `FullForm`, `TeXForm` and `NumberForm`: outside
the terminal REPL, all four did nothing.

The cause was a division of labour with no one on the second half. `print.c` consumes each
of these heads and renders its argument in the notation requested, so the kernel's
**text** payload was correct all along. `print_latex.c` knew only `HoldForm`, so the
wrapper fell through its generic `Head[a, b]` arm and came out as
`InputForm[\frac{1}{2}]` — and because the front end prefers the `latex` field over the
payload whenever it is non-empty, that leak *was* the visible result.

Typesetting **is** StandardForm; it has no second notation to offer. So `expr_to_latex`
now answers with the **empty string** for an expression carrying a printer directive —
the signal both the notebook and the FFI already read as "use the text payload", which is
by construction the form the directive asked for. The scan covers the whole tree rather
than the outermost head, so `Hold[InputForm[x]]` and `{InputForm[1/2], 3}` cannot leak
either. `HoldForm` is deliberately not on the list: it is transparent to both printers.

The front end had a matching half-bug. With no `latex` field it fell back to running the
payload through KaTeX — and with `throwOnError` off, `Sqrt[x]` does not fail, it silently
typesets as the juxtaposed letters S q r t beside a bracketed x. So the kernel's fix alone
would have swapped one wrong rendering for another. `renderOutput` now sends an
un-typeset payload out as code, which is safe because `latex` comes from the kernel and
nothing else: its absence is a statement, not a gap.

Nothing changes at the REPL, where all four directives already printed correctly, and an
ordinary result still typesets — the directive scan costs it nothing.

Gated in two places, because the bug lived in the seam between them:
`tests/test_print.c` pins `expr_to_latex` (each directive empty, each text form intact,
an undirected expression still rendering), and `tools/check_pipe_protocol.py` pins the
same thing one layer out, at the NDJSON boundary the notebook actually consumes.

### The notebook extension is now `.mnb`

A single notebook saves as **`.mnb`** ("Mathilda notebook") instead of `.mathilda`. The
format itself — the plain-text stanza format in `src-tauri/src/notebook_format.rs` — is
unchanged; only the extension the Save As dialog writes has moved.

## Notebook: File > Open Recent

The File menu had no way back to yesterday's file: every reopen was a trip through the
Open dialog and a walk down the filesystem. **File > Open Recent**, directly under
Open…, now holds the last 10 files opened or saved — `.mnb` notebooks and `.lb`
libraries in one list, newest first, **Clear Menu** at the foot.

Reopening a file already listed moves it to the top rather than adding a second line.
Two files sharing a name get their folder appended (`notes.mnb — drafts`), because two
menu rows reading alike is worse than a longer label — the reader cannot tell which one
they are about to open, and picking the wrong `.lb` replaces the canvas. An entry whose
file has moved is dropped: on load if it is already gone, and otherwise the first time
clicking it fails, so the menu never keeps offering a dead end.

**Where it lives.** The list, the JSON store and the native submenu are all in Rust
(`src-tauri/src/recent.rs`), because the menu is native — only Rust can draw it — and
the list has to be on disk before the webview has booted. The webview still owns the
*acting*: Rust emits `menu:recent-3` like any other item and `App.svelte` indexes the
list with it. `openFile()` was split so the dialog and the menu share one `openPath()`;
a second copy of the `.mnb`-versus-`.lb` branch is how those two would have drifted.

This is the first state the app keeps across restarts. `src/lib/properties.ts` records
the standing decision that UI preferences do not persist until they all can, and that
decision stands — a recent-files list is document history, not a preference.

**Three things the redraw has to get right**, all three found by reading muda rather than
by running it, and each documented at the code:

1. The whole redraw happens in **one** `run_on_main_thread` hop. Every individual menu
   call posts to the main thread and blocks until the event loop pumps, so a naive
   redraw is ~thirty blocking round trips from an async command — each one stalling for
   as long as a menu is open or a file dialog is up.
2. A slot handle is appended **at most once** per redraw. muda removes a child by id but
   detaches every `NSMenuItem` it holds for that menu, so appending one handle twice
   leaves its item list and the real `NSMenu` disagreeing and later removals hit the
   wrong row.
3. The list lock is released **before** any menu call. The main thread takes the same
   lock when a click arrives, so holding the guard across a call that waits on the main
   thread is a two-party deadlock.

Drain-and-append rather than rebuilding the menu: `set_menu` tears the whole menu bar
down first (`setMainMenu(None)` on macOS), which would flicker the Mathilda and Edit
menus and drop every key equivalent on each recent-files change.

**Gate.** `make check-menu-ids` covers the new ids in both directions (49 native, 49
subscribed, 49 handled) — the ten slots are spelled out longhand on both sides precisely
so it can see them. It gains one check it could not make before: the `recent-N` run must
be contiguous from 0, because the digit is an *index* into the list. Delete `recent-4`
from all three sides and every existing check still passes while the menu silently opens
the wrong file from the fifth row down. Verified by doing exactly that.

Eight unit tests in `recent.rs` cover the pure list logic — promote-to-front, the cap,
dedupe, forget, label disambiguation, and a store that is missing, corrupt, or points at
files that no longer exist.

## `Series` and `SeriesCoefficient` no longer have the `HoldAll` attribute (v0.236)

`Attributes[Series]` and `Attributes[SeriesCoefficient]` were `{HoldAll, Protected}`.
Mathematica's are `{Protected}`, and so are Mathilda's own `Limit` (since the
equivalent fix in `4e7b0515`), `D` and — the closest sibling — `NSeries`. This
supersedes the *"`Series` resolves a held series variable that names a symbol
(v0.229)"* section above: the hand-rolled resolution that section describes is now
what ordinary argument evaluation does, and `series_resolve_spec_vars` is gone.

**The hold bought nothing.** Every argument the engine needs, it already evaluated
by hand: `do_series_single` evaluates `f` and `x0`, `series_effective_assumptions`
evaluated the `Assumptions` option RHS, `parse_series_spec` evaluates a
non-literal order `n`, and `series_resolve_spec_vars` existed purely to undo the
hold for the series variable.

**It cost real bugs**, every one of them the same shape — a *named* argument
behaving differently from the literal it stood for:

| input | was | now |
|---|---|---|
| `s = {x, 0, 3}; Series[Exp[x], s]` | frozen | the expansion |
| `s = {x, 0, 3}; SeriesCoefficient[Exp[x], s]` | frozen | `1/6` |
| `r = (x -> 0); Series[Sin[x] - x, r]` | frozen | `-x^3/6 + O[x]^5` |
| `Series[Exp[x], Sequence @@ {{x, 0, 3}}]` | frozen, unspliced | the expansion |
| `l = {Sin[x], Cos[x]}; Series[l, {x, 0, 2}]` | `{0,1} + {1,0} x + …`, one series with List coefficients | `{x + O[x]^3, 1 - x^2/2 + O[x]^3}`, as the literal list already gave |
| `g = Gamma[x]; Series[g, {x, Infinity, 3}]` | echoed `g` | echoes `Gamma[x]` |

The list row is the worst of them: the threading test read the head of the
*unevaluated* first argument, so the same input gave two different answers
depending on whether it had been named.

### The expansion variable is now type-checked: `Series::ivar`

Removing the hold exposes a gap that had been masked rather than handled. Nothing
downstream checks that the expansion variable is a symbol, and `expr_free_of` is
purely structural. With `x = 5` in scope the spec is now `{5, 0, 3}`, so
`do_series_single`'s "f is free of x" early-out cannot fire for a literal that
occurs in the body, and the Taylor engine would proceed into
`replace_all_of(f, 5, 0)` and `D[Sin[5], 5]`. Fed the forms the evaluator now
produces, the old code answered:

```
Series[Sin[5], {5, 0, 3}]                    5 - 1/6 5^3 + O[5]^4
Series[Sin[5] + 5, {5, 0, 2}]                2 5 + O[5]^3
SeriesCoefficient[Sin[5], {5, 0, 3}]         -1/6
SeriesCoefficient[ProductLog[5], {5, 0, n}]  the symbolic-n general term
Series[Sqrt[1 + (1+u)^4], {1 + u, 0, 2}]     1 + O[1 + u]^3
```

So `series_spec_vars_ok` rejects a non-symbol expansion variable with a funnelled
`Series::ivar` / `SeriesCoefficient::ivar` (`5 is not a valid variable.`) and
leaves the call unevaluated — matching Mathematica's `General::ivar` and the
`ivar` decline `NSeries` already had. It runs *first* in both builtins,
before the inexact dispatch and before `SeriesCoefficient`'s `ProductLog` /
`FresnelC` / `FresnelS` symbolic-index branches, which match on the raw spec.
A second argument that is no spec at all (`Series[f, x]`) still declines
**silently**, as do unrecognised option names.

This is a small capability removal as well as a gate: a compound expansion
variable (`Series[Sin[f[t]]/f[t], {f[t], 0, 4}]`) used to expand, by accident of
the structural `expr_free_of`/`D`. Mathematica rejects it, so Mathilda now does.

**Throttled, and the throttle is the interesting part.** The iterator heads are
`HoldAll`, so they bind a fresh value on every step: `Plot[Normal[Series[Sin[x],
{x, 0, 5}]], {x, 0, 1}]` hands the guard `{0.01, 0, 5}`, `{0.02, 0, 5}`, … —
one complaint per sample point, each a distinct form, so deduplicating on the form
would not help. Mathematica prints three and then `General::stop`; the Mathilda
funnel has no repeat limiter, so the cap lives at the emission site: three per
*head* (a swallowed `SeriesCoefficient::ivar` hiding behind a `Series::ivar` would
be a lie), re-armed by the next well-formed call, and only spent on a message the
user actually saw — a `Quiet[]` region still emits, because the funnel notes a
firing before the suppression check and that is how `Check[]` detects a silenced
diagnostic. The `Plot` spelling above stays wrong either way; as in Mathematica it
needs `Plot[Evaluate[...], ...]`.

### `Limit`'s speculative `Series` probe had to be guarded

`split_rule` does not check that the limit variable is a symbol, and `Limit` has
not held its arguments since `4e7b0515` — so `x = 5; Limit[Sin[x]/x, x -> 0]`
reaches `layer2_series` with `ctx->x == 5` and issued `Series[Sin[5]/5, {5, 0, k}]`
in its order-escalation loop. That is a *speculative probe inside a cascade*: the
new `ivar` leaked out of `Limit`, and because the funnel notes a firing even under
`Quiet[]`, it flipped an enclosing `Check[]` to its failure branch — a wrong
answer, reachable through the explicit `Limit`Series[...]` method head.
`layer2_series` now declines silently on a non-symbol variable and lets the cascade
continue.

**Upstream renumbered.** 12000.org regenerated on 2026-09-28 and swapped its chapter-2
section numbers: the sequential "Problems N to M" pages moved from §2.2.N to **§2.1.N**
(`Ch2.S1.SSN.htm`), and the "not solved, but Maple and Mathematica solve" corpus we call

`2.2.34` spelling for continuity with the thirty-three checked-in sections; the mapping is

### A condition point must be a point (converter)

`is_condition_row` required the left-hand side to be exactly `y(…)`, which a whole-LHS
*product* written with `\left(…\right)` also satisfies. So `y(1+{y'}^2) = 2xy'` was read as
the initial condition `y[1+(y')²] == 2xy'`, the ODE row vanished, and the record degenerated
to a `NO ODE ROW` placeholder. The argument must additionally be free of `\prime`, of the
dependent functions, and of the independent variable — a real condition point is a number, a
constant, or a parameter, never a function of `x`. Measured across all thirty-three sections
the fix is a **no-op on thirty-one** and repairs three latent records: §2.2.34-3313,
§2.2.33-3296 (a miss M53 documented and left) and §2.2.16-1593 (which nobody had noticed).

### A non-elementary variation-of-parameters particular, held inert

The largest cluster in the block was second-order linear equations at a regular singular
point with polynomial forcing. Their homogeneous part solves to a Bessel or hypergeometric
fundamental set, but the variation-of-parameters quadratures are not elementary, and the
case was simply lost: `DSolve`SpecialFunctionForm` is homogeneous-only by construction, so it
found the fundamental set and threw it away because the equation had a right-hand side.

`DSolve`VariationOfParameters` gains a second mode, in the **last** cascade slot — after
every other method, including both Frobenius fallbacks, has declined. That placement is a
correctness property rather than a convenience: from there the slot can only turn an
unevaluated result into an answer, so no case that already passes can be lost to it, and its
cost lands only on equations that were returning nothing. It solves the homogeneous part with
the pinned `SpecialFunctionForm`, which *structurally* guarantees a closed-form basis — so a
truncated-series basis, over which an inert integral would be meaningless, can never reach the
quadrature step. The particular is returned with its non-closing integrals held inert as
`Inactive[Integrate]`, which is Mathematica's own answer shape here.

Two details carry the mode. An integrand whose **denominator** carries a special function is
never handed to `Integrate` at all: the failing attempt on a Bessel Wronskian quotient costs
up to 47.8 s, which blows every solve budget, while the screen costs microseconds. (It is a
denominator test, not a blanket one — `Integrate` genuinely closes a special function in the
numerator.) And correctness rests on an in-method gate, because nothing downstream can catch a
wrong inert answer: both numeric verifiers keep a residual containing an integral and
`PossibleZeroQ` answers `True` for one. The gate exploits the particular being *linear* in its
inert integrals — replace each by a symbol, split with `Coefficient`, and require every
coefficient of the resulting linear form to vanish, since the fundamental theorem of calculus
must cancel the forcing and each `L[basis_i]` must be zero. Sampling is at **exact rationals**:
the same Bessel residual reads 1e-7 at machine reals, where twelve digits vanish to
cancellation between terms of magnitude 1e4, and 1e-28 exactly. Measured separation between a
correct answer and three planted-wrong bases is 5.4e-51 against 0.18–0.49, and both are pinned
in the stress suite so the margin is tested rather than merely observed. An initial-value
problem **declines**: an inert particular has no value at a point, so its constants cannot be
fitted, and returning the unfitted general solution would look solved.

*Solves* §2.2.34-3387/3388/3389/3392/3395. `D` also gains the Leibniz rule for the inert
**definite** integral, the companion of the M59 indefinite rule.

### An autonomous IVP whose reduction constant was never fitted

`DSolve`AutonomousReduction` carried its stage-1 constants into stage 2 unfitted, even though
for an initial-value problem the point conditions determine them exactly and independently of
the quadrature (`D_k(y0) == y⁽ᵏ⁾(x0)`, the same derivative chain the reduction is built from).
Fitting them *first* is what closes the class: `y'' + 2 y y' == 0, y(0) = 0, y'(0) = 1` reduces
to `p == C[2] − y²`, whose quadrature is a symbolic-parameter `ArcTanh` the stage-2 spin guard
turns away — while with `C[2] == 1` fitted it is just `ArcTanh[y]`, and the answer is
`Tanh[x]`. Previously the case fell through to the inert first integral with `C[2]` still free,
which is the general solution with the conditions unapplied.

Where the quadrature stays non-elementary the relation is now **fitted** all the same, written
in definite form `Inactive[Integrate][1/p, {t, y0, y[x]}] == …`. The indefinite form could not
be fitted at all: substituting `y[x] -> y0` is a blind replacement, so it rewrote the
integral's *variable slot* too and produced `Inactive[Integrate][1, 0]` — a meaningless
expression which, once no free constant remained, would have scored as a solved answer. A
radical over a transcendental function of `y` also now declines the explicit path quickly
(measured: that stage-2 sub-solve costs 90 s and returns an inert relation anyway), where the
existing denominator test could not see it.

*Solves* §2.2.34-3345/3347.

### A separable IVP that loses its singular solution

Dividing by `h(y)` drops the constant solutions `h(y) == 0`, so `y' == x² y²` with `y(1) = 0`
shipped the family `1/(C[1] − x³/3)` with its constant unfitted — no finite constant makes it
vanish. Mathematica returns `y → 0`, and now so do we. The criterion is deliberately *not*
`h(y0) == 0`, which also holds for `y' == y, y(0) = 0`, for `y' == y(1−y), y(0) = 1` and for
`y' == Sqrt[y], y(0) = 0` — all three already correct, so testing it would emit a duplicate
branch on two and a Mathematica-divergent extra branch on the third. What fires exactly when
needed is "the regular family provably cannot reach the initial point", i.e. the fitter's own
empty-`Solve` state, and the equilibrium is accepted only after it verifies. Placed in the
shared substrate, so it covers Bernoulli, Homogeneous, Chini and Abel too.

*Solves* §2.2.34-3336.

### Two latency root causes with reach well beyond this corpus

**The parametric verify substituted an uncancelled `dY/dX`.** The residual may raise it to a
power — `x (y')³ == y y' + 1` cubes it — and an uncancelled quotient of two rational functions
then explodes in degree, so `zero_test`'s canonicalisation did not return: the equation hung
for over 120 s. `Together` on the quotient *before* it is substituted collapses it to `t` in
0.05 s and the zero-test answers in 0.003 s. This is the normalisation the two sibling
verifiers already had and this one lacked, and it affects every parametric answer —
`Lagrange`, `SolvableForY`, `SolvableForX` — so any user ODE of d'Alembert shape could hang
the kernel. Cancelling the residual instead does not work; it has to happen before the power.

**`DSolve`NthAlgebraic` recursed without a bound.** It is the second method tried on every
scalar ODE and its per-root recursion is a full `DSolve` whose *implicit* results it then
discards — on `(y − x y')² == 1 + (y')²` that was two 5.9 s solves thrown away, repeated by the
evaluator's fixed-point re-invocation for ~25 s in total, on an equation `Clairaut` answers in
0.01 s. It now carries the standard kit: a wall-clock deadline, a per-branch
`TimeConstrained`, and a decline memo.

*Solves* §2.2.34-3312 and, with the next item, 3331.

### A Clairaut equation written nonlinearly in `y`

`(y − x y')² == 1 + (y')²` is textbook Clairaut — its roots `y = x p ± Sqrt[1 + p²]` are two
Clairaut equations — and it was reachable by no method at all: `DSolve`Clairaut` required the
algebraic residual to be *linear* in `y`, and `DSolve`SolvableForY`, which does isolate the
roots, discards them deliberately (for a Clairaut equation its denominator `p − dG/dx` vanishes
identically, and its comment says the family is "owned earlier", which it was not). The
residual now need only be **polynomial** in `y`: it is solved for `y` and each root run through
the same `d/dx Yexpr == p` test. The linear path is unchanged, envelope included.

### Verification

§2.2.34 measured twice; the eleven gains are exactly 3313, 3312, 3331, 3336, 3345, 3347, 3387,
3388, 3389, 3392, 3395, with no case lost. Six `t_m61_*` units plus
`tests/test_dsolve_m61_stress.c` — seven families including an eighteen-member forward
generator over the generalised-Bessel grid, a latency bound that notices if the denominator
screen stops firing, and the gate-margin controls above. All fifteen DSolve unit and stress
suites report no failure; `make check-c99` and `make check-messages` are green. Where a suite
truncates at its own 120 s alarm (`dsolve_tests`, and two stress suites) the behaviour is
identical on a HEAD binary built in an isolated worktree, and the new assertions were verified
by direct evaluation — thirty of them, all passing.

Regression is measured as a **same-machine A/B against that HEAD binary**, because the
checked-in per-section reports are stale and several section gates are already red on main. Over
eleven exposed sections M61 is **better on six, equal on five, 0 FAIL in all twenty-two runs**
(§2.2.12 5→4 non-PASS, §2.2.14 3→1, §2.2.19 11→10, §2.2.25 4→2, §2.2.27 5→2, §2.2.33 18→12). On
the 1204-case master corpus: **616 → 621 PASS, 0 FAIL both, crashes 3 → 1**; of the four cases
that move the other way, all four solve in 3–5 s on *both* binaries — the documented eight-second
timing cluster flipping under fork load, with M61 no slower on any of them.

That master run also earned its keep by catching a regression of this wave's own making. The
parametric-verify cancellation above, applied ungated, is itself the expensive step on a
candidate carrying radicals: 2.1.2-980 went from 6 s to **51 s** plus a recursion-limit blowup,
and 2.1.2-702 from 8 s to 56 s. Neither the section corpus nor any of the fifteen suites saw it.
Gating the cancellation to a quotient rational in the parameter removes the regression and keeps
the gain. The general form of the lesson — a normalisation inserted to make one class cheap will
meet inputs where it is the dominant cost, so gate it to the class it helps — is in
`tasks/lessons.md`.
